# 窗口上限管的是这一次请求发出去多少，不是这场对话一共聊了多久

对话进行到第十四轮，请求突然失败，报的是上下文长度超限。你百思不得其解：这场对话一共才聊了二十分钟，怎么就"超出上下文"了？把最前面两轮删掉，同样的第十四轮又发得出去了。**限制从来不作用在"这场对话的总长度"上，它作用在你这一次发出去的那一串字符上**——而那一串里包含了全部历史。

第二种翻车安静得多：账单涨得比用量快。用户数没变，人均对话轮数没变，只是轮次变长了。这是[第 1 章 A 组](/ai-apps/llm-api-basics)那道算术的直接后果：无状态 API 每轮全量重发，单次请求的输入随轮次**线性**增长，一段对话的累计输入随轮次**平方**增长。那一章把裁剪、摘要、缓存这些手段留给了本章。

第三种最难查：你加了摘要，之后模型开始否认自己前面的结论。用户第 3 轮说过"必须用顺丰发货"，第 19 轮问"给我下单"，它换了承运商。你以为是模型不稳定，实际可能是那句原文根本没在第 19 轮的发出去的内容里。

第四种是"我以为省了钱"：听说有提示缓存这回事，于是开了，账单没动。差别常常在拼装顺序上——你把一个每轮都变的时间戳放在了最前面，于是两个请求逐字相同的段落只剩开头那一行。

## 字符、码点、字节、token：四个口径里只有三个能在本机测准

先在能测准的那三个上把地基打牢，否则后面每个数字都没有意义。

```js
export function sizes(s) {
  return {
    units: s.length,                            // UTF-16 码元
    codePoints: [...s].length,                  // Unicode 码点
    utf8Bytes: Buffer.byteLength(s, 'utf8'),    // UTF-8 字节
  }
}
```

本机拿四类真实会出现的文本各测一次：

```text
=== A 同一段文本的三种长度口径 ===
  样本          字符码元(.length)     码点([...].length)  UTF-8 字节    字节/码元
  纯中文         20                20                60          3.00
  中英混排        54                54                58          1.07
  带表情         16                14                38          2.38
  代码片段        32                32                32          1.00
```

这四个比值告诉你两件确定的事。**一**，字节和字符之间不是常数倍：同一段代码片段是 1.00 倍，纯中文是 3.00 倍。所以"用字节数当长度"这种偷懒做法，会在中文内容上把你的估计放大到三倍——这个放大方向恰好和账单相反，因为厂商看的是 token 而不是字节。**二**，带表情那一行 `.length` 是 16 而码点是 14：两个 emoji 各占两个 UTF-16 码元。这不是脚本的怪癖，是标准的定义——MDN 对 `String.length` 的原文是「String 类型的 length 数据属性表示字符串的 UTF-16 码元长度」，并接着写明「每个 Unicode 字符可以编码为一个或两个码元，因此 length 返回的值可能与字符串中 Unicode 字符的实际数量不匹配」；RFC 3629 则规定 `U+0000..U+10FFFF` 范围内的字符「are encoded using sequences of 1 to 4 octets」，也就是说一个字符占几个字节取决于它落在哪个区段。

然后是第四个口径，它测不准。**token 不是字符、不是码点、也不是字节，它是厂商分词器吐出来的单元**，而分词器不在本机——本站没有安装任何 tokenizer，也没有调用厂商接口。于是任何"这段大概多少 token"都只能是带假设的区间：

```text
=== B 同一封工单正文（62 码元 / 62 码点 / 136 UTF-8 字节），三档假设下的输入量 ===
  假设（不评价哪档接近任何真实分词器）        得到输入量    相对最省的那档
  每 1 个码点算 1 个单位                 62          3.88 倍
  每 1.5 个码元算 1 个单位               41          2.56 倍
  每 4 个字符算 1 个单位                 16          1.00 倍
```

同一段文本，`16` 到 `62`，最贵档是最省档的 **3.88 倍**。这条不是为了教你选哪一档，而是教你怎么读结论：**如果三档假设下结论方向一致，估算可用；如果结论会翻，就必须换成厂商的分词接口去拿精确数**。要精确值，用的是厂商提供的计数接口或用量回报字段，而不是自己乘一个系数——具体叫什么名字、返回哪些字段，属于第 1 章那份核对清单，本章无法替你核实。

## 窗口上限是输入加输出的共同预算，两种失败形态完全不同

把窗口当成"预算"比当成"容量"准确：这一次请求里，你发出去的输入和模型要生成的输出**共用**同一个上限。所以有两件事要分开守。

第一件是**输入别超**。这是你自己能算的部分：把每次请求体的长度打进日志，就是本章的度量口径。

```js
const WINDOW_BUDGET = Number(process.env.WINDOW_TOKENS ?? 0)   // 数值来自当期官方文档，不许凭记忆填
const RESERVE_OUT = Number(process.env.RESERVE_TOKENS ?? 0)    // 留给输出的预算，同样是核对来的

export function guard(promptChars, estimate) {
  const est = estimate(promptChars)          // 用你选定假设算出的区间，返回 { lo, hi }
  if (WINDOW_BUDGET === 0 || RESERVE_OUT === 0) throw new Error('未核对，禁止发送')
  return est.hi + RESERVE_OUT <= WINDOW_BUDGET ? 'send' : 'trim-or-reject'
}
```

第二件是**输出别被截**。如果模型生成到上限还没说完，你会拿到一个状态码成功、内容不完整的结果——这正是第 1 章失败分类里 `长度上限截断` 那一行，也是本章反复强调"预算"的原因：输入占得越多，留给输出的空间越少，两者是同一笔预算的两端。超限时到底是报错还是静默截断、截断时响应里用什么字段告诉你，本批无法核实（见文末），所以守卫逻辑按最坏情况写：**当成会被静默截断来设计**，凡是要被程序消费的输出一律过校验。

一个具体的算术感受一下预算的挤压：C 组那场对话里，全量重发到第 24 轮的单次请求体是 `7,525` 字符，而只留最近六条时是 `1,147` 字符——同一轮，差 6.6 倍。如果你的窗口预算按"典型请求"设，那"典型"必须是**最老的那一轮**，不是第一轮。这也是很多"前几轮好用、后面开始失败"的根源：你按第一轮的长度做了容量规划。

## 三种裁剪策略算同一笔账：省下的量，和丢掉的那句话

策略无非三族：**截断**（只保留最近若干条）、**摘要**（把老的压成一段较短的转述）、**滑动窗口加锚点**（最近的照留，另外固定携带几条不能丢的关键信息）。它们省下的量和丢掉的量都不是一回事，本机用同一场 24 轮合成对话（固定种子 `20261021`）跑一遍：

```text
=== C 三种策略：同一场对话，输入量与事实可见性 ===
  策略        24 轮累计输入字符        单轮峰值字符        事实最后一次可见的轮次   相对 full 的输入量
  full      96,972            7,525         24                    100.0%
  keep6     22,514            1,147         5                     23.2%
  summary   43,161            2,176         24                    44.5%
```

那句"事实"是第 3 轮用户消息里的原文：`订单号 SO-77120 必须用顺丰发货，别的承运商不接`。检查方法不需要模型：

```js
export function factVisible(messages, fact) {
  return JSON.stringify(messages).includes(fact)     // 逐字包含，才算发出去了
}
```

于是 `keep6` 那一行给出的是一条**确定性**结论：从第 6 轮起，那句原文不在你发出去的任何东西里。用户第 19 轮问"帮我下单"，模型回答用了别的承运商，你排查了三小时怀疑模型不可靠——真正的答案是这一行：不是它忘了，是**你没发**。摘要策略那行的"全程可见"则是因为本站把原句写进了摘要文本，这条只证明字符串在请求体里，不证明模型会引用它。

三族的取舍按这张表读。**截断**最省（输入量降到 23.2%），代价是硬丢弃，凡是"用户早先说过的约束"都可能被丢掉。**摘要**省得少一些（44.5%），代价转移成另一个问题：摘要里留了什么由写摘要的代码决定，而摘要本身每次请求也要重发、也要占预算。**锚点**最便宜也最脆：它要求你**提前**知道哪几句不能丢，而这正是产品里最值得工程化的地方——关键约束应该结构化地存（订单号、承运商、地址），每轮按需拼进去，而不是指望模型从二十轮前的原文里自己找出来。

摘要还有一处不能忽略的成本：生成摘要本身是一次调用，要读进旧历史、要付费。把它做成"每次请求前重算"，你只是把账单从一处挪到另一处。常见做法是累积摘要（把新丢的几轮并进已有摘要），并且像本章对示例做的那样，给摘要写一条可检查的规则而不是"看起来还行"——例如要求摘要必须逐字保留所有编号类实体。这条能不能达成，本机测不了，但**有没有达成可以测**：C 组那个 `factVisible` 就是检查器。

## 前缀：重复发送的那段能不能复用，先看你是不是真的逐字重复

第 2 章留了一个数字：每条 few-shot 示例每次请求 21.8 个字符，同一段任务里逐字不变。既然逐字不变，理论上它就有被复用的余地——而这件事的字符串侧前提，本机可以精确测：**两个连续请求体的最长公共前缀有多长**。

```text
=== D 相邻两次请求体的最长公共前缀（字符数）===
  相邻两次        时间戳在最前            时间戳在最后            各自的总长度
  第 1→2 次     19                    98                    136 / 136
  第 3→4 次     19                    98                    136 / 136
  第 6→7 次     19                    98                    136 / 136
```

把每轮都变的时间戳放在开头，公共前缀被截断在 `19` 个字符——第一个不匹配的字节就把整段可变之后的一切都排除在外；把它挪到末尾，前面的指令与示例整段都是公共的，`98` 个字符。这条结论的形状值得记下来：**公共前缀长度是"可复用部分"的上界**，任何按前缀复用的机制都不可能覆盖超过逐字相同的那一段。

至于厂商到底按什么复用、什么时候算命中、最小可缓存的段落多长、命中与写入的价格各是多少、有效期多久、哪些字段参与——**本批一条都没能核实**（厂商文档访问失败，记录在文末），所以本章不写这些参数的名字，也不写"开了就好"。你能立刻做的是把拼装顺序定成纪律：

```text
稳定在前：指令 → 输出约束 → few-shot 示例 → 长期资料 → 本轮历史 → 每轮都变的值放最后
```

这条纪律同时服务另外两件事，即使缓存这件事在你的厂商那里不存在也不亏：它让请求哈希之间的差异只落在真正变化的那段（第 2 章 E 组），也让 `system` 保持"一份模板"而不是"每轮一份"（第 2 章 D 组：版本数 1 对 6）。反过来，一个时间戳、一个 `Date.now()`、一个每次生成的随机分隔符放在开头，就同时打掉这三样。

## 账单是一条算式，先把口径写清楚再往里代数字

成本不是一个数，是一个函数。把它写成代码比写成散文不容易自欺：

```js
export function cost({ inTokens, outTokens, priceIn, priceOut }) {
  return inTokens * priceIn + outTokens * priceOut      // 单位必须与 price 的口径一致
}
// 多轮对话：inTokens 是第 k 轮的历史量，它随 k 增长（第 1 章 A 组：第 12 轮单次输入是第 1 轮的 61.0 倍）
// 所以「日活 × 平均一轮」必然偏低：平均抹平了递增，而账单来自递增本身。
```

三个参数里，本站能给的只有输入量那部分（本机可测），两个 `price` 都必须由你去当期官方文档核实。可以给的是**比值**：假设每轮输出等长（300 字符）、每人每天 24 轮，取 C 组的输入量，令输出单价是输入单价的 `r` 倍：

```text
=== E 三种策略的相对账单（无量纲，基准 = full）===
  策略        r=1         r=4         说明
  full      1.000       1.000       基准
  keep6     0.285       0.408       输入量是基准的 23.2%
  summary   0.483       0.572       输入量是基准的 44.5%
```

读这张表的正确方式：**当输出更贵（`r` 从 1 到 4），裁剪输入换来的相对节省会缩水**——`keep6` 从省 71.5% 变成省 59.2%。如果你的产品输出很长（生成长文、生成代码），裁剪输入的边际收益不如控制输出长度；如果输出很短而输入很长（长文档问答、多轮工单），裁剪才是主战场。这两个方向都是算术，不需要知道单价就能定策略；要算出钱，把 `r` 和单价换成你核实过的当期数字。

量级演练（这一段的每个数都来自 C 组同一套量，只用于说明"怎么推"）：一场 24 轮对话在全量重发下是 `96,972` 个请求体字符，一人一天一轮这么用的话，1000 个日活一天约 9,700 万字符、一个月约 29 亿字符。要把"字符"换成能乘单价的量纲，中间那一步必须过厂商的分词口径——按 B 组的三档假设，这 29 亿字符对应的单位量在约 7.3 亿到 29 亿之间，**差 3.88 倍**。所以本章对"每月大概花多少钱"这个要求的交付形态是：你能带着这条链走完全程，唯独在最后一步用你核实的单价收尾；任何跳过中间那一步、直接给出金额的教程，都在用一个你没有的假设。

最后一句口径纪律，来自第 1 章那张印着 `9,396` 与 `24,552` 两个数的表：同一个"用量"，采样点之和与逐轮累计差了 2.6 倍，两者都算对。**写进 README、写进监控面板、写进给同事的成本估算，每一个数字都要带口径**。本章所有数字的口径写在每一张表的第一行。

## 常见错误与排查

**1. 现象：窗口超限报错，你把最大输出调大，结果失败得更频繁。**

原因：输入和输出共用同一个预算，最大输出是从预算里切走的，切得越多，输入允许的余量越小。

怎么确认：把每次请求的输入字符数与当时的输出上限一起打进日志，看两者之和的分布；只看输入长度看不出问题。

怎么修：按最老那一轮的输入量做容量规划（C 组里同一轮全量重发是 7,525 字符，裁剪后 1,147 字符），输出预算按任务实际需要的上限取，两者相加留余量。厂商的具体上限数值本章未核实，动手前查当期文档。

**2. 现象：模型开始否认用户早先给过的硬约束。**

原因：那句原文根本不在这一轮发出去的内容里——被截断策略裁掉了，或者被摘要改写掉了。

怎么确认：用 `factVisible` 那条检查（逐字包含），把关键实体写进测试；不要靠"我记得我发过"。

怎么修：把硬约束从历史里挪出来，结构化存储、每轮按需锚定注入（C 组第三族）；摘要策略则要求摘要保留编号类实体原文。

**3. 现象：加了摘要之后账单没降，甚至更高。**

原因：摘要文本每次请求也要重发、也占输入预算；而生成摘要本身是一次额外调用。

怎么确认：分别记摘要段长度与请求体总长度；`summary` 在 C 组里仍是 `full` 的 44.5%，不是 0。

怎么修：累积式摘要而不是每轮重算，控制摘要段的长度上限，并把"值不值"交给 E 组那张比值表算，而不是凭感觉。

**4. 现象：用"一个词≈一个 token"估的账单，实际高出一大截。**

原因：中文产品里字符与 token 的关系和英文文档里的经验值不同，而单点估算把这种差异藏起来了。

怎么确认：换成区间估算重算一遍——B 组那段 62 个字符的文本在三档假设下给出 16 / 41 / 62，最贵是最省的 3.88 倍。

怎么修：结论在区间内一致就用估算，不一致就去调厂商的计数接口或读它的用量回报字段；别自己定系数然后当事实用。

**5. 现象：听说有提示缓存，开了之后账单没动。**

原因：多半是前缀不稳定——每轮都变的东西被放在了开头，两个请求逐字相同的段落只剩下几个字符。

怎么确认：对相邻两个请求体算最长公共前缀的字符数（本章 D 组那张表就是这么来的，函数在 `ai-apps/.scratch/context-cost.cjs` 里）；本站测到的对比是 19 对 98 个字符。

怎么修：把可变值挪到末尾，稳定段落（指令、约束、示例、长期资料）严格排在前；再确认你的厂商是否真有此机制、命中条件是什么——这几条本批未核实，必须自己查。

依次是 UTF-16 码元数、Unicode 码点数、UTF-8 字节数、按空白切出的片段数（粗略"词数"）。

前三个是标准定义的口径，本站已在 A 组实测过同类样本：emoji 让码元数大于码点数，中文让字节数是码元数的三倍左右。第四个既不稳定也不可靠（`SO-77120` 会被切成一个，而真实分词很可能把它切成几段）。

它们都不能直接当 token，因为 token 是厂商分词器的输出单位，与这三个标准口径之间**没有常数倍关系**：B 组同一段文本在三档假设下差到 3.88 倍。可用的做法是给出区间并检查结论是否随假设翻转，要精确值就调用厂商的计数能力。

</template>

</Exercise>

<Exercise title="设计一个不会被裁掉的关键约束" difficulty="进阶">

你的工单助手里有两条信息：A「用户要求必须用顺丰发货」，B「当前时间」。请说明它们在拼装顺序里各自应该出现在哪一段，并写出你会怎么用脚本检查它们有没有真的发出去。

<template #answer>

A 属于**不能被历史裁剪丢掉**的硬约束：结构化存储（订单号 + 承运商 + 来源轮次），每轮按锚点重新注入到固定段落里，而不是依赖原文留在历史中。B 是每轮都变的值：放最后，绝不进 `system`（第 2 章 D 组：放进去之后 6 轮里 `system` 版本数变成 6），也不放在开头（D 组：公共前缀被打到 19 个字符）。

检查手段分两条。A 用逐字包含检查：`JSON.stringify(messages).includes(FACT)`，C 组用的就是这条，它给出的是确定性答案（在不在发出去的东西里）。B 用相等检查：对 `system` 去重计数，期望恒为 1。

两条都不能证明模型会用 A——那需要行为实验。但"没发出去"是可以当场证伪的，而线上多数这类问题恰好就是没发出去。

</template>

<Exercise title="故意让可见性检查骗过你" difficulty="挑战">

摘要策略下，`factVisible` 报告第 19 轮"事实可见"。请构造一个摘要写法，让检查报可见、但模型实际上得不到足够信息，并说明这条检查的边界在哪里、你该怎么补。

<template #answer>

构造：摘要写成「用户强调过发货承运商有特殊要求」。这句里包含"承运商"，如果把检查改成关键词命中（而不是原句逐字包含），它会通过——但原文里那个决定性的值 `顺丰` 已经没了，模型只能猜。

这条检查的边界要说清楚：它判的是**字符串在不在请求体里**，不是**语义有没有保全**。逐字包含检查（`includes(FACT)`）能挡住改写丢失，但挡不住另一种情况：原句在，可它被埋在两百条消息中间而模型没引用——那属于行为问题，本机无法测。

## 官方文档与延伸阅读

- [RFC 3629 · UTF-8, a transformation format of ISO 10646](https://www.rfc-editor.org/rfc/rfc3629.txt) —— 本批已核实可访问（2026-10-21，正文逐字存于 `ai-apps/.scratch/docs/rfc3629.txt`）。用于支撑「一个字符编码为 1 到 4 个字节、取决于码点区段」，也就是 A 组里字节/码元比值从 1.00 到 3.00 的标准依据。
- [MDN · String.length](https://developer.mozilla.org/zh-CN/docs/Web/JavaScript/Reference/Global_Objects/String/length) —— 本批已核实可访问。用于支撑「`length` 是 UTF-16 码元长度，可能与字符实际数量不匹配」，即带表情那行的口径差异。
- [MDN · TextEncoder](https://developer.mozilla.org/zh-CN/docs/Web/API/TextEncoder) —— 本批已核实可访问，原文表述为「接受码位流作为输入，并提供 UTF-8 字节流作为输出」。用于支撑 A 组里"字节数怎么来的"，以及浏览器侧同样能算长度这件事。
- [第 1 章 LLM API 基础](/ai-apps/llm-api-basics) —— 无状态重发的增长算术、十二种失败分类、八项动手前核对清单的出处；本章只接它留下的第 2 项与第 8 项。
- [第 2 章 Prompt 工程](/ai-apps/prompt-engineering) —— 本章两处的"代价"来源：每条示例每次请求 21.8 个字符、`system` 必须每轮同一份。
- [Anthropic 官方文档入口](https://docs.anthropic.com/) 与 [OpenAI 平台文档入口](https://platform.openai.com/docs) —— **本批从本机访问失败**（前者 HTTP 200 但正文是「App unavailable in region」的区域不可用页，后者 HTTP 403）。本章没有从它们核实任何事实，列出仅作为你在可访问环境下的核对入口：窗口上限、分词与计数接口、单价与计价单位、缓存命中条件与价格、超限行为，全部以当期官方文档为准。

<Callout type="unverified" title="动手前必须自己核实的六件事">

本章刻意没有给数值，因为它们全部属于会变、且本批无法核实的类型。逐项列出，每项都要落到当期官方文档：

**一**，你在用的那个模型/服务的上下文窗口上限是多少，以及它是"输入上限"还是"输入加输出共同上限"。**二**，超限时的行为：返回错误，还是静默截断，截断时响应里用哪个字段告诉你。**三**，厂商是否提供 token 计数接口或用量回报字段，字段名叫什么、包含不包含系统段落。**四**，计价单位与两档单价（输入 / 输出分别是多少），以及被中断的生成怎么算。**五**，是否存在前缀缓存：命中条件、最小可缓存段落长度、有效期、写入与读取的价格倍率。**六**，限流是按请求数、输入量还是输出量。

前五项对应[第 1 章](/ai-apps/llm-api-basics)那份八项清单里的第 2、8 项与第 6 项。填完这六格，本章的每张表才能从"比值"变成"钱"。

</Callout>
