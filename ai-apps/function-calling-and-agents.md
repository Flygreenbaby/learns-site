# 模型只是提出请求，执行的是你的代码

**事故一**：退款工具第一次调用超时了，模型看到「没有结果」，于是又提了一次。两笔退款都到了客户账上。事后查日志，两次调用的 id 不同、参数完全相同——去重键用的是调用 id，等于没去重。

**事故二**：助手上线两周，运营反馈「它有时候翻来覆去查同一单」。翻代码发现循环里只有一个 `maxSteps = 25`。那 25 步里模型一次也没收敛，而每一步都要把整段历史重发一遍——这个乘法在[第 4 章](/ai-apps/context-and-cost)算过。

**事故三**：工单里写着「已为客户退款 88 元」，客服照着这句话回复了用户。那是模型自己产出的文本。审计表里那次调用的 `executed` 是 false——被授权层拦下了。**模型从来没有退款，是某人把「提出」当成了「发生」。**

**事故四**：`tool_error` 的回填文本写成「库存查询没能完成，稍后再试」。模型把这句话读成「操作已经做完，只是没有细节」，继续往下走。错误分类被自然语言糊掉了：在日志里它和成功长一个样。

四起事故没有一个发生在模型内部。它们全部发生在**你怎么定义工具、怎么校验参数、怎么执行、怎么把结果写回消息数组**这四段代码上。本章写这四段与它们之间那条循环，写到「模型能不能听懂你的工具」为止——那是[第 10 章](/ai-apps/security-and-abuse)与[第 2 章](/ai-apps/prompt-engineering)的地盘。

## 三种形状不是一条路上的三个里程牌

同一个「让模型帮你干活」的需求有三种实现，差别不在能力，在**谁决定下一步**。

| 形状 | 谁决定下一步 | 成本上界 | 出错时你能做什么 | 适合 |
| --- | --- | --- | --- | --- |
| 单次工具调用 | 你：一次提问、最多一次调用 | 两次生成 | 直接拒绝，回退到纯文本回答 | 提取参数、填表、把一句话变成一次查询 |
| 固定工作流 | 你：步骤写死，模型只填每一步的参数 | 步骤数 × 单步 | 精确重试失败的那一步 | 流程已知且不需要临场判断 |
| 自主循环（Agent） | 模型：它看结果，再决定调不调、调什么 | **没有天然上界**，靠你设的刹车 | 只能止损，不能精确重放 | 步数事先不知道、需要读中间结果 |

表里那一列「成本上界」是选择的真正依据。**自主循环是唯一一个默认没有上界的形状**，所以你要么给它上界（本章第七节），要么就别用它。前两种形状能解决的需求，不要用第三种：写死的工作流失败时你知道是哪一步坏了，自主循环失败时你只知道「没成」。

## 生命周期八段，每段有自己的失败形状和主人

一次工具调用不是「模型调用函数」，是八个阶段：

| # | 阶段 | 判什么 | 失败长什么样 | 归谁 |
| --- | --- | --- | --- | --- |
| 1 | 定义与暴露 | 模型能看到哪些工具、什么描述 | 你以为藏起来了，其实挂在白名单上 | 你 |
| 2 | 模型提出调用 | 产出一个「想调用」的结构 | 名字拼错、参数缺、一次提三个 | 模型 |
| 3 | 结构与语法 | 能不能解析成对象 | 坏 JSON、被截断 | 你（闸门在[第 5 章](/ai-apps/structured-output)） |
| 4 | 参数合法性 | 必填、类型、枚举、上限、未知字段 | 被拒，**工具一次都没执行** | 你 |
| 5 | 授权与确认 | 这个主体能不能碰这个对象、要不要人 | 拒绝或转人工 | 你（四层笼子实测在[第 10 章](/ai-apps/security-and-abuse)） |
| 6 | 执行 | 副作用真的发生 | 成功、报错、超时（状态未知） | 工具 |
| 7 | 结果封装与回填 | 把下场写成一条消息 | 写成自然语言糊掉分类 | 你 |
| 8 | 审计与观测 | 每一行同时有提出、执行、下场 | 「40 次失败在日志里全是成功」 | 你（口径归[第 9 章](/ai-apps/evaluation-and-observability)） |

三条要从表里单独记住的。**第 2 段到第 6 段之间全是你的代码**：模型对第 4、5 段没有任何投票权，它只能提出。**第 3 段的闸门复用[第 5 章](/ai-apps/structured-output)那四级**：工具调用同样是一段结构化文本，只是第四级判的不是字符串而是权限。**第 6 段是唯一一段「事情真的发生了」的阶段**，所以上面那三个布尔字段必须分开存。

## 提出、执行、结果可用是三个状态，不是一个

```text
  a1 orders.lookup     proposed=true executed=true  outcome=ok      ｜ {"orderId":"o1001","status":"shipped"}
  a2 orders.lookup     proposed=true executed=false outcome=invalid_request ｜ 参数：缺必填 orderId
  a3 orders.lookup     proposed=true executed=false outcome=denied  ｜ 授权：水平越权：对象不属于当前主体
  计数：提出 3，执行 1，拒绝 2，回填消息 3 条
```

同一轮里模型提出了三次，你的代码只执行了一次。**这 1 和那个 3 之间的差距，就是「模型不是执行者」这句话的全部含义。**把它们记成一个字段是本节开头事故三的来源：一句「我已经为你退款」在日志里找不到对应事实，因为它对应的是一次 `proposed=true / executed=false`。

一次调用的记录形状至少要有这些字段：

```json
{
  "step": 3, "callId": "c3", "tool": "refund.issue",
  "proposed": true, "validated": true, "authorized": true, "confirmed": true,
  "executed": true, "outcome": "timeout", "effectState": "unknown",
  "idempotencyKey": "refund:o1001:88", "backfilled": true, "stopReason": null
}
```

`effectState` 是给 `timeout` 准备的第三态：成功、失败、**不知道**。它不能省——省了它，超时就只能被写成前两者之一，而写错的方向一定是「当成没发生」，于是重试。`outcome` 用枚举不用自由文本，事故四就是把它拼成句子的结果。

## 工具定义与参数校验：能被拒绝才算写清楚

工具定义里你真正控制的是两件事：**暴露哪些**，以及**每个参数能不能被机器判合法**。下面是一个不含任何厂商字段名的形状（本站未核实任何厂商的定义字段，字段名以你的服务为准）：

```js
const tools = {
  'refund.issue': {
    description: '对已支付订单发起部分退款。一次只能针对一个订单，金额单位是分。',
    required: ['orderId', 'amount'],
    types: { orderId: 'string', amount: 'number' },
    enum: { reason: ['duplicate', 'damaged', 'other'] },
    max: { amount: 200 },
    strict: true,        // 未知字段报错，不是忽略
    needConfirm: true,   // 高风险：无人在场就不执行
    risk: 'write_high'
  }
}
```

`strict: true` 是这一节最想让你抄的一行。八个候选调用丢进去，看拦在哪一层：

```text
  b1 orders.lookup     executed=true  outcome=ok ｜ {"orderId":"o1001","status":"shipped"}
  b2 orders.lookup     executed=false outcome=invalid_request ｜ 参数：orderId 类型应为 string
  b3 customer.note.add executed=false outcome=invalid_request ｜ 参数：缺必填 note
  b4 customer.note.add executed=false outcome=invalid_request ｜ 参数：未知字段 sign
  b5 customer.note.add executed=false outcome=invalid_request ｜ 参数：note 长度超上限 200
  b6 refund.issue      executed=false outcome=invalid_request ｜ 参数：reason 不在枚举内
  b7 refund.issue      executed=false outcome=invalid_request ｜ 参数：amount 数值超上限 200
  b8 order.delete      executed=false outcome=invalid_request ｜ 注册表：工具存在但不在模型可见白名单内
  计数：提出 8，执行 1，拒绝 7
```

八个里只有一个是合法调用，七个被**你的代码**拦下，工具一次都没多跑。几个坑逐条对上：

**上限必须是数字。**「金额不要太大」拦不住任何东西，`max: { amount: 200 }` 拦得住——这跟第 10 章那条「上限要有数字，不能只有意图」是同一件事，只是这里拦的是模型能造成的影响范围。**枚举优先于自由文本**：b6 的 `reason: 'gift'` 若在枚举外被放过，它就会变成一条没人能聚合的脏数据。**未知字段要报错不要忽略**：b4 多带一个 `sign`，忽略它等于允许模型偷偷塞参数。**工具名不是权限**：b8 被拦在注册表层，连参数都没看；反过来说，只要它还在可见白名单里，你就已经在依赖第 4 层了。**描述要写「怎么填」而不是「这是什么」**：`description` 是模型唯一能读到的东西，写「退款」没用，写「一次只能针对一个订单，金额单位是分」才能减少 b2 那一类类型错。

## 失败有三种下场，其中一种是你不知道

```text
  c1 customer.note.add executed=true  outcome=ok              ｜ {"noteId":"n1"}
  c2 inventory.check   executed=true  outcome=tool_error       ｜ 库存服务连接被重置
  c3 refund.issue      executed=true  outcome=timeout          ｜ 假时钟 +40ms 超 25ms，副作用状态=未知
  c3 refund.issue      executed=false outcome=duplicate_delivery
  c4 orders.lookup     executed=false outcome=denied           ｜ 授权：水平越权：对象不属于当前主体
  副作用：notesAdded=1 refundsIssued=1（退款那次是超时，状态未知）
  迟到的返回值被丢弃计数=1
```

`c2` 是本节唯一一条「工具自己坏了」的路径：它通过了全部四道判定，`executed=true`，然后在执行阶段抛错。它必须被记成 `tool_error` 并原样回填成一条机器可判的失败，**不能把异常栈丢给模型**（错误原文的出口与脱敏在[第 10 章](/ai-apps/security-and-abuse)，回滚与降级在[发布与回滚](/devops/release-and-rollback)）。

`c3` 是事故一的机制：超时之后副作用计数**是 1**，也就是钱可能已经退了，而你不知道。所以超时之后带同一个调用 id 重发没有用——被识别成 `duplicate_delivery` 的那一行 `executed=false` 是**按 id 去重**的结果，不是「没有副作用」。

```text
  键=调用 id：d1=ok，d2=ok，副作用=2 次
  键=工具名+参数（业务幂等键）：e1=ok，e2=duplicate_delivery，副作用=1 次
```

两行的差别只在幂等键。**按调用 id 去重挡不住模型重复提出同一动作**，因为每次提出都是新 id；挡得住的是同一个 id 被回填两次。写操作要的是业务键：`refund:o1001:88` 这种由「工具名 + 决定性的业务参数」组成的键。这一条是本章里最容易做错的：你以为做了幂等，其实只做了去重。

`c4` 是顺带的一条纪律：查一个不存在的单号，被授权层拦成「水平越权」，**工具根本没跑，也就没告诉模型它不存在**。「不存在」和「不归你」在响应里区分开来，本身就是一次信息泄漏。

## 循环必须装五个刹车，而且要记是哪一个响的

多步循环的骨架只有十几行，全部工程量在刹车和刹车响过之后留下什么。

```text
  E1 步数上限 maxSteps=6，每步参数都不同 → steps=6 stop=步数上限
  E2 重复检测 repeatLimit=3，反复提交同一调用 → steps=3 stop=重复检测
  E3 预算刹车 tokenBudget=120 → steps=5 tokens=155 stop=预算上限
  E4 授权层先响（角色不足） → outcome=denied executed=false stop=收敛（给出最终回答）
  E5 人工接管闸门（有权限、无人在场） → outcome=needs_human executed=false stop=转人工
  E6 四道判定全过之后 → executed=true outcome=timeout 副作用计数=1
  E7 正常收敛 → steps=1 stop=收敛（给出最终回答） 工具执行 0 次
```

五个刹车分别是：**步数上限**（E1，本例 6 步）、**重复检测**（E2，键是工具名加参数的指纹，本例第 3 次响，比步数上限早三步）、**预算**（E3，按 token 计，本例停在第 5 步、累计 155——注意它停在步数上限之前）、**无进展检测**（连续几轮回填的内容没有任何变化就是原地打转，本例靠 E2 的指纹覆盖）、**人工接管**（E5：有权限但无人在场时不执行高风险动作，直接停）。

E4 那一行是本批跑出来的一个真实发现，值得单独说：授权拒绝之后循环**没有停**，`stop` 是「收敛」。这是对的——被拒的调用回填给模型，模型可以换一条合法路径再来一次。**但如果你希望「越权一次就终止整个会话」，那是另一条策略，必须自己写进刹车里**；默认行为是继续，而继续意味着攻击者可以靠被拒信息反复试探。这一条的取舍归[第 10 章](/ai-apps/security-and-abuse)。

停因必须写进日志的 `stopReason` 字段。它的价值在第 9 章：**「20 步停在步数上限」和「3 步停在重复检测」不是同一类失败，混在一个「Agent 未完成」里就统计不出该修哪一个。**

## 回填的形状：一次提出多个调用时，历史会长这样

```text
  B 组角色序列：system user assistant user user user user user user user user
  一次提出 8 个调用 → 连续 user 最长串=8，回填行数=8
  如果把回填行全部拿掉（模拟「提出后不回填就再发」）→ 末尾角色=assistant
```

三行对应三条纪律。**第一，回填必须成对**：提出多少个调用，就要回填多少条结果（本例 8 对 8，由断言逐行数出来）。少回填一条，模型就在信息不全的情况下决定下一步。**第二，一次多个调用会让消息数组出现连续同角色**——这正是[第 1 章](/ai-apps/llm-api-basics)那条「最后一条通常是 user」被破例的地方，也是它被设计成「警告而不是拒绝」的原因。**第三，不回填就再发的话末尾是 assistant**，第 1 章的校验会直接拒绝这次请求。

回填行也要能被数出来：本例 B 组 9 行审计 = 提出的 8 个调用 + 1 行收敛，`执行 1 + 拒绝 7 = 回填 8`。这三个数对不上，就说明有一条调用的下场被丢了。

## 要不要上编排框架：先看见机制，再谈框架

按通用原理给一个判断，本站没有评测过任何框架。

编排框架通常多给你四样东西：并行调用与依赖编排、中间状态的持久化与重放、人工介入队列、以及统一的观测面板。这四样都值钱，但它们都建立在**你已经有一套正确的单轮判定**之上。框架替你写的是循环，替不了你写的是本章第 4、5、6 段——参数校验、授权、幂等键。**先手写循环的理由不是省依赖，是刹车得由你按下去**：一个把 `maxSteps`、重复检测、人工接管都藏在默认配置里的框架，出问题时你会先怀疑模型，而真正缺的是上面那三段判定。

反过来，当你需要跨进程恢复（跑到第 9 步服务重启了）、需要重放同一条轨迹做调试、或者需要把「待人工确认」变成一张真实工单队列，手写那十几行就已经是负债了。这条判断与[第 11 章阶段项目](/ai-apps/project)不冲突：项目里先用最朴素的循环跑通，可观测与验收要求照样成立。

## 常见错误与排查

**1. 现象：用户说「已经退过款了」，系统又退一笔。** 原因：超时当成失败重试，或幂等键用了调用 id。怎么确认：把两次调用的 `tool + args` 指纹对一下，相同而 id 不同就是没幂等（本例 d1/d2 那组）。怎么修：写操作用业务幂等键，超时记 `effectState=unknown`，不记失败。

**2. 现象：日志里全是成功，用户投诉没生效。** 原因：`outcome` 被拼成自然语言，分类丢了。怎么确认：`grep` 你的审计表，看有没有一条独立的枚举列；再看「执行次数」和「回填条数」能不能对上。怎么修：字段先落，句子后生成。

**3. 现象：Agent 翻来覆去做同一件事，直到账单用完。** 原因：只有步数上限，没有重复检测。怎么确认：统计连续几步的调用指纹，相同即原地打转。怎么修：指纹计数到阈值就停，并把 `stopReason=repeat` 记下来。

**4. 现象：模型说「我调用了工具」，但审计里查不到任何调用。** 原因：它只是把调用意图写成了普通文本（或者你根本没执行那句文本）。怎么确认：文本里的工具名与真实审计行做联查。怎么修：一次生成只认结构化调用字段，正文里的自述一律不作为事实（本例 3 提出 1 执行就是这个差距）。

**5. 现象：加上校验之后，某些请求全被拒。** 原因：上限设得太死或者枚举没收全，把合法形状当非法。怎么确认：分被拒原因计数（本例七类各拦几次），看哪一类占绝对多数。怎么修：这是定义问题不是模型问题；对照真实流量分布放宽枚举，别关掉校验。

**6. 现象：换了一个模型，工具调用成功率从 90% 掉到 30%。** 原因：模型侧的遵从能力变了，而你的校验没变。怎么确认：同一份手填调用集分别喂给两个模型，比较 `proposed` 的形状合法率。怎么修：**这类结论本机测不出**——本批 0 次模型调用，只能给形状；真正的对照要你自己的评测集，判据与显著性在[第 9 章](/ai-apps/evaluation-and-observability)。

<Exercise title="故意把幂等键设成调用 id" difficulty="进阶">

本章 D 段有两组：键取调用 id 时两次都执行，键取「工具名 + 参数」时第二次被判重复。请回答：（1）为什么按 id 去重挡不住事故一？（2）业务键会不会带来新问题，给出一个具体的反例；（3）超时那次（`c3`）在这两种键下分别是什么下场？（4）用哪两个字段能不看代码就发现这个 bug？

<template #answer>

**（1）因为模型每次重新提出调用都会拿到一个新 id。** 按 id 去重只挡得住「同一个调用的结果被回填两次」这种重复，它挡不住「同一个业务动作被提出两次」。事故一正是后者。

**（3）两种键下 `c3` 第一次都是 `timeout`、副作用计数 +1。** 差别在第二次：按 id 时新 id 会真的再执行一次（于是退两笔），按业务键时 `executed=false / outcome=duplicate_delivery`。也就是**只有业务键能在超时这个未知态之后挡住重复扣款**。

**（4）`effectState` 与幂等键本身。** 报表里出现「timeout 之后紧跟一次同业务键的成功执行」就说明键不对；另一个信号是副作用计数（`refundsIssued`）比 `executed=true` 的行数多——那说明有你不知道的执行。

<Exercise title="给一个查库存再加购物车的助手设计笼子" difficulty="挑战">

场景：模型可以调用 `inventory.check`（读）、`cart.add`（写低风险）、`order.submit`（写高风险、要人确认），一次也可能提三个调用。请设计：（1）三个工具各自的参数校验规则（必填、类型、上限、枚举、未知字段策略）；（2）四道判定的顺序，并说明为什么顺序有意义；（3）五个刹车的取值与理由；（4）审计行的字段清单；（5）明确写出三处本机测不出来、必须接上真实模型或真实服务才能核实的东西。

<template #answer>

**（1）规则要写到能拒绝的程度。** 例：`inventory.check` 必填 `sku:string`，`strict:true`，无上限需求；`cart.add` 必填 `sku`、`qty:number`，`qty` 上限 20（这个数字来自你允许单次下的最大量，不是「别太大」），`sku` 必须在一次会话里被 `inventory.check` 查过——这条是语义校验，不是语法校验；`order.submit` 必填 `cartToken`、`amount`，金额上限取业务天花板，`reason` 之类自由文本一律不进必填。

**（2）注册表 → 参数 → 授权 → 确认，顺序有意义在两处。** 一是把注册表放最前，不可见工具连参数都不看（本例 b8），少暴露一层就少一层可被试探的面；二是把授权放执行前，「不存在」和「不归你」在同层拦下，不泄漏对象是否存在（本例 c4）。反过来（先授权后校验）会让脏参数走到带权限的代码里。

**（3）刹车取值要给理由。** 步数上限按最坏合法路径 + 1（本例三步能完成：查库存、加购、提交，那 `maxSteps` 取 4 到 6 就够，不是 25）；重复检测阈值 3（同工具同参数连续 3 次即停）；预算按会话额度换成 token 并在超限时**先止损再说明**；人工接管用「无人在场即拒绝」而不是「无人在场即挂起」，挂起的队列要有归属人与超时，否则它就是一个不可见的失败堆积。

**（4）审计字段清单**：`step`、`callId`、`tool`、`proposed`、`validated`、`authorized`、`confirmed`、`executed`、`outcome`（枚举）、`effectState`、`idempotencyKey`、`backfilled`、`stopReason`，再加 `tokens` 与 `rid`。前 13 个就是本章那张记录形状，`backfilled` 用来核对「执行数 + 拒绝数 = 回填数」那条等式；后两个是为了让第 9 章能按口径统计，并和第 10 章的请求关联起来。
