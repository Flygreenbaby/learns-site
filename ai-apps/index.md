## 这个领域解决什么问题

调用一个大模型 API 发一条消息、拿回一段文字，这件事三十分钟就能学会。但从「能调通 API」到「做出一个别人愿意用的 AI 功能」，中间隔着一连串具体的工程问题，这正是本领域要解决的：

- **模型输出不是你要的格式。** 你需要 JSON，它给你 JSON 外面裹了三层客套话和一对 markdown 代码块标记，`JSON.parse` 直接炸。你需要知道结构化输出的正确做法，以及为什么「在提示里求它只输出 JSON」是不够的、应用侧校验为什么不能省。
- **用户等了 20 秒，屏幕上什么都没有，然后全文一次性蹦出来。** 长回答必须流式渲染。这背后是 SSE 或 fetch stream 的传输机制（协议与生命周期在[实时通信](/realtime/)领域讲，第 10 章专讲这一段），以及与前端渲染的衔接——后者已经写成[第 3 章](/ai-apps/streaming)。
- **对话进行了十几轮之后，要么超出上下文窗口报错，要么账单开始吓人。** 你需要会估算 token、设计上下文裁剪策略、理解多轮对话为什么每次都把历史全量重发——以及厂商的 prompt 缓存机制能帮你省什么。
- **想让模型回答「我的文档里」的内容，它却开始编造。** 这是 RAG（Retrieval-Augmented Generation，检索增强生成）要解决的问题：文档分块、嵌入（embedding）、向量检索、把检索结果注入提示。每一环都有具体的质量与成本取舍，分块策略错了，后面全白搭。
- **改了提示词，感觉效果好了一点，又好像没有。** 没有评测集，你所有的「优化」都是玄学。AI 应用的评测与可观测不是锦上添花，是让你敢改东西的前提——这一章已写成[第 9 章](/ai-apps/evaluation-and-observability)，它讲的是分母、判据、样本构成与采样规则，而不是「多跑几条看看感觉」。
- **有人把你的 API 当成了免费提款机，或者用一段精心构造的输入让模型绕过了你所有的限制。** 提示注入（prompt injection）、速率限制、成本上限，这些防线要在上线前就设计好，而不是被薅了之后。

**一个必须先说清楚的诚实声明**：AI 领域是所有技术方向中 API 变化最快的——端点、参数名、模型名、定价、能力边界每隔几个月就会变。本站的做法是：**讲机制与取舍（这些相对稳定），凡是涉及具体厂商的参数名、端点、默认值，一律标注核实日期，并提示以该厂商官方文档为准。** 你在学习和开发时也应养成同样习惯：博客教程先看日期，动手前查官方文档。

## 前置知识

- [后端开发](/backend/)——AI 应用的主战场在服务端：调用上游 API、管理密钥、控制速率、拼装提示、处理流式转发。没有 Fastify/Node 的基本盘，本领域每一章都无法落地。
- [数据库](/database/)——RAG 的向量存储、会话与消息的持久化、评测数据的记录都在数据库里。本站主线用 PostgreSQL + pgvector 扩展，需要你已经会基本的 SQL 与 Prisma 使用。

软性依赖：[实时通信](/realtime/)的第 3 章（SSE 线格式）与第 10 章（与 AI 流式输出的关系）是第 3 章流式渲染的传输侧基础（三章互相引用，先学哪边都可以）；[TypeScript](/typescript/)的类型能力在结构化输出校验一章会派上用场。

## 学习顺序建议

**严格按 1 → 11 顺序学。** 依赖关系是链式的：第 2 章的提示能力是第 5 章结构化输出的前提；第 4 章的 token 概念是第 6 章分块策略「为什么块不能无限大」的答案；第 6 章的检索链路与第 7 章的检索质量判据，直接延续为第 9 章的系统化评测。

三个例外：

- **第 3 章流式渲染可以（也建议）尽早学。** 它是用户感知最强的功能，做完立刻有产品雏形，正反馈价值高。它自带一张「最小契约」表（消息数组、角色、无状态重发、密钥只能在服务端），所以**不读第 1 章也能独立读完**；[第 1 章](/ai-apps/llm-api-basics)现已上线，按 1 → 3 的顺序读更省力，那张表可以当它的摘要看。传输与取消传播那一半在 [实时通信第 10 章](/realtime/ai-streaming)，线格式细节在它的[第 3 章 SSE](/realtime/sse)。
- **第 10 章安全建议在你第一次把服务暴露到公网之前就通读一遍**，哪怕项目还没做到那里。密钥泄漏和被薅羊毛是新手最常付的学费，而且都不贵得离谱——但完全可以避免。
- **第 9 章可以插队读。** 它依赖的是第 1、2、4、5、10 章已经交出来的产物（字段集、请求哈希、成本口径、四级闸门、被拒请求日志），不需要 RAG 与 Agent 先行；只有「检索命中率」那一类判据要等第 6、7 章。读完第 5 章就把它读掉，你后面每一句「效果变好了」才有可检查的说法。

## 学习方法

**环境准备（Windows）**：

- Node.js LTS + TypeScript + 一个 Fastify 项目骨架（来自[后端开发](/backend/)领域的积累），前端用你熟悉的 Vue 3。
- **LLM API 密钥**：选择一到两家主流厂商注册并获取 API key，充值小额度即可（学习期消耗通常很低，但务必同时配置用量告警——这本身就是第 10 章的练习）。**具体选哪家、用什么模型，本站不锁定**：厂商格局变化太快，[第 1 章](/ai-apps/llm-api-basics)给的是动手前必须查清的八项核对清单（对话形状、长度上限、采样参数、流式形状、错误形状、限流规则、超时、计费口径），本站不复述任何一家的当期参数。国内环境需额外确认所选厂商的网络可达性与合规要求。
- **向量数据库**：直接用你已有的 PostgreSQL 加 pgvector 扩展，不引入新的基础设施。这符合本站「一个人能运维的东西才是好东西」的总原则。
- **密钥纪律**：所有 key 走环境变量，`.env` 进 `.gitignore`。AI 服务的密钥直接对应真金白银，泄漏成本比普通应用更高。

**练习原则**：

- 每章的示例都要在**至少两个不同厂商的 API** 上跑一遍（调用封装层保持不动，只换适配）。这是体会「本站为什么只讲机制不讲具体参数名」的最快方式。
- 保留一个 `prompts/` 目录存放所有提示模板并纳入 Git 版本管理。一个月后回看你的提示演化史，比读十篇文章都有收获。
- 遇到模型行为不符合预期，先分类：是提示问题、上下文问题、检索问题，还是模型能力边界问题？四者的修法完全不同，乱试只会引入更多变量。
