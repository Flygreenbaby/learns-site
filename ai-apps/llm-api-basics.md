# LLM API 基础：你以为发出去一句话，其实发出去的是整个对话

你做了一个问答功能，第 1 轮很快，第 5 轮还行，第 14 轮开始报错「超出上下文长度」。你以为是模型不行了，其实是**你第 14 次请求把前面 13 轮的问答原文又全发了一遍**。本站把这件事在本机算了一遍：到第 12 轮时单次请求的输入量已经是第 1 轮的 **61.0 倍**（A 组）——这不是厂商报价，是任何人都能复算的结构性质。

第二种症状不报错，只烧钱：账单比预估高一个数量级。代码里没有循环调用，只有一个很自然的写法「把用户那句话发给模型」，而它在无状态 API 上意味着每次重发整段历史，累计成本因此随轮次**平方**增长。

第三种最难看：同一段回答在界面上出现了两遍。你没写重试，是封装层里那句 `retry: 3` 写的——上游确实完成了两次生成，账单也是两次。生成没有幂等语义，第二次不是「补回丢失的那次」，是**又写了一篇**（D 组：400 个请求白付 63 次整段输入）。

第四种是安全事件而不是 bug：密钥写成构建期内联的环境变量，被构建工具替换进了产物 JS，任何人打开 DevTools 就能拿到，而它直接对应真金白银。

这四件事都不源于「你不会调 API」，而源于「你以为 API 的形状和你想象的一样」。本章把形状钉死：发出去的是什么、三种角色各管什么、一次调用会怎么失败、密钥能在哪、封装层的契约长什么样；增量怎么拼、前端怎么渲染、停止按钮要做完哪三件事，归[第 3 章](/ai-apps/streaming)。

## 无状态是部署形状，不是偷懒

先把最容易被误解的一条说清楚：**模型不认识你，也不认识这个会话**。每一次请求都完整、独立、自包含，必须自带全部上下文。这不是偷懒——无状态才能水平扩展，任何实例都能处理任何请求，扩容不必把会话粘在某台机器上，和[后端认证那一章](/backend/auth-session)的取舍同源。代价就是历史每次重发：

```text
=== A 无状态多轮：每轮把历史全量重发 ===
  假设：system 提示 26 字符，每轮用户输入 40 字符，每轮回答 320 字符
  第  1 轮：消息条数= 2，本次请求输入字符=   66（约为第 1 轮的 1.0 倍）
  第  2 轮：消息条数= 4，本次请求输入字符=  426（约为第 1 轮的 6.5 倍）
  第  3 轮：消息条数= 6，本次请求输入字符=  786（约为第 1 轮的 11.9 倍）
  第  5 轮：消息条数=10，本次请求输入字符= 1506（约为第 1 轮的 22.8 倍）
  第  8 轮：消息条数=16，本次请求输入字符= 2586（约为第 1 轮的 39.2 倍）
  第 12 轮：消息条数=24，本次请求输入字符= 4026（约为第 1 轮的 61.0 倍）
  上面六个采样点的输入字符之和 = 9396（注意：这不是 12 轮的真实累计，只是六个点的和）
  逐轮累加 k=1..12 的真实累计（每轮都全量重发）= 24552 字符
  逐轮累加 k=1..20 的真实累计 = 69720 字符；第 20 轮单次请求 = 6906 字符
  对照方案「把每轮回答存进数据库、每轮只发本轮那一句话」= 792 字符（12 轮）——**但那样模型看不见历史，不是同一件事**
  结论形状：输入 token 随轮次线性增长，累计成本随轮次平方增长（这条是算术，不是任何厂商的报价）
```

三句话读它。**一**，「只发本轮那句」省下的三十倍不是你的选项——那样模型看不见历史，产品就不成立；那一栏存在只为让「线性」与「平方」肉眼可见。**二**，同一段对话里**每一轮的边际成本都在涨**，所以「日活 × 平均一轮」必然偏低；摘要、滑动窗口、命中缓存这些手段归[第 4 章](/ai-apps/context-and-cost)。**三**，表里同时印着 9,396 与 24,552 两个数，口径不同却都对，相差 2.6 倍——**写进 README 的每个成本数字都要带口径**。

## 消息数组的不变量：封装层第一件事是拒绝

对话 API 收的是**消息数组**，不是字符串，而「听起来没什么」正是所有脏历史混进去的入口。B 组给一个只写了几十条规则的校验函数喂了 8 种形状：

```text
=== B 消息数组不变量：封装层该拒绝什么 ===
  通过｜正常一问一答                      （无警告）
  拒绝｜传了字符串而不是数组                  （不是非空数组（对话 API 收的是消息数组，不是字符串））
  拒绝｜role 写错                     （第 0 条 role="System" 不在 system/user/assistant 里）
  拒绝｜流式拼接后没填内容就回写                （第 1 条 content 是空字符串）
  拒绝｜把 system 放到了历史后面            （system 出现在第 1 条（位置不是最前））
  拒绝｜两条 system（每轮又追加分隔提示）        （出现多条 system）
  通过｜历史开头就是一条 assistant（没有先问的话）  （无警告）
  通过｜三条连续 user（把工具结果当 user 塞）    （第 2,3 条与前一条同角色（合法但要怀疑是不是历史拼接重复了））
```

分界线画在哪是这张表的全部要点：**拒绝的是「一定不对」，警告的是「可能不对但你可能有理由」**。画错它，轻则误杀合法请求，重则脏历史一路带到第 20 轮才炸。六条规则依次是：顶层非空数组、角色只取三值、每条 `content` 非空、`system` 至多一条且在最前、最后一条通常是 `user`、相邻同角色只警告。

倒数第二条在第 8 章会破例：工具循环里数组末尾可能是模型刚产出的「我要调某个工具」，你带着结果再发时末尾就不是 user，所以这条要写成「纯文本对话场景的检查」而不是硬约束。同理，「三条连续 user」和「历史开头就是 assistant」都被放过——**合法不等于正确**，这正是它们进日志而不进异常的原因。

最容易犯的是回写方向，F 组那段真实输出同时证明两条相反的纪律：

```text
=== F 一次调用换一整段：封装层的聚合形状（合成增量，不解析 SSE） ===
  增量数组长度=7，聚合后字符数=15，与逐字拼接期望一致=true
  回写历史后直接再发：{"ok":false,"why":"最后一条是 assistant（这轮没有要问的话）"}
  先带上本轮那句 user 再发：{"ok":true}
  形状结论：聚合结果是一条 assistant 消息（可回写），但回写之后的数组末尾是 assistant，它只能当历史，不能原样再发
  usage 记的是字符量（本站合成）：输入 35 / 输出 15——真实 token 数只能来自上游返回，本机没有 tokenizer 可核对
```

一边是**必须回写**：不存 assistant 消息，模型下一轮就不知道自己说过什么；另一边是**不能把回写后的数组当新请求发**：那等于替模型把话说完再问它「你说得对吗」。顺序永远是：assistant 存进历史 → 本轮 user 追加 → 发。

## 角色分工：三种角色不是三种语气

一句话钉死：**`system` 是「这次任务怎么干」，`user` 是「这次要处理什么」，`assistant` 是「模型说过的话」**。所有误用都能从这句话判出来。

`system` 的正确性质是**稳定**：不随轮次变，同一类产品里它应该和代码一起版本管理（模板写法归第 2 章）。三种误用：每轮追加一条（于是出现多条 system）；把用户数据塞进去，理由是「这里优先级高」——这是提示注入的主要攻击面，因为你把不可信内容放进了指令的位置；用它传「当前时间」「用户名」这类每轮都变的值，破坏了它的稳定性。

`user` 承载本轮输入，也包括你拼进去的检索片段、工具返回的 JSON、用户上传的文本。判据只有一个：**这里是数据不是指令**。哪怕它语义上像指令（「请参考以下规则：」），只要来自外部数据源，就必须假设它会试图改变模型行为。

`assistant` 是回写通道，也是最容易丢的一条：只在库里存了「给用户看的文本」，或存的是**清理过的版本**（展示时去掉 markdown、把表格转成列表）。下一轮模型看到的历史里没有它说过的话，或说的和当初不同，于是它开始不承认自己上一轮的结论。

**一处厂商差异必须提前说，但本章不给答案**：这套「三条消息数组」不是唯一形状，有的产品把 system 放在请求体**顶层参数**里，有的用独立消息类型承载工具结果。动手前要先核对的是「这家把 system 放哪、工具结果放哪、角色有哪几个」（清单第 1 项），而不是照抄本章的代码形状。

## 采样参数：概念只有一个，名字有 N 个

温度和 top-p 只做一件事：**改变下一个 token 的概率分布被截断和采样的方式**。它不是创意旋钮也不是质量旋钮——调高温度，模型更常选到概率低的候选，输出更分散，而分散既可能是你要的多样性，也可能是格式跑偏和事实漂移。默认值与取值范围本章不写（本批外部核对没成功），只给判据：下游是程序（抽取、分类、改写成 JSON）就取最低档**且仍然**留校验兜底，因为低档也偶发格式漂移；只有希望彼此不同的任务才值得调高，代价是越长越易跑偏。

两条纪律比判据值钱。**不要用「重抽到满意为止」代替改提示**：前者每次都在花整段输入的钱赌分布尾巴，后者改的是你发出去的内容，而且跑 20 次挑最好的会让第 9 章的评测无法复现。**温度调到最低不会让模型不胡说**：它只让输出可复现，而低温度下的错误是稳定的错误。

## 调用封装：一个函数、一个适配器、一条契约

本章的交付物是把上面所有规则收进一个模块。下面是**结构示意**：本批未安装依赖、未运行类型检查、未连接任何上游，它不承诺能编译，只承诺形状对。

```ts
export type Role = 'system' | 'user' | 'assistant'
export type ChatMessage = { role: Role; content: string }
export type LlmRequest = { messages: ChatMessage[]; purpose: string }
export type FailureClass =
  | 'auth' | 'quota' | 'rate-limit' | 'upstream' | 'transport'
  | 'timeout' | 'in-stream' | 'truncated' | 'empty-content'
export type LlmResult =
  | { ok: true; content: string; requestId: string }
  | { ok: false; class: FailureClass; retryable: boolean; producedContent: boolean; requestId: string }
export interface LlmAdapter { call(req: LlmRequest, signal: AbortSignal): Promise<LlmResult> }
export async function callLlm(req: LlmRequest, adapter: LlmAdapter): Promise<LlmResult> {
  const v = validate(req.messages)                              // 就是 B 组那个函数
  if (!v.ok) return { ok: false, class: 'empty-content', retryable: false, producedContent: false, requestId: '' }
  return adapter.call(req, AbortSignal.timeout(DEADLINE_MS))     // 超时必须显式，别信默认值
}
```

四个设计判断的理由。**一，判别联合而不是抛异常**：失败不是一个状态而是九个，其中三种（`truncated`、`empty-content`、`in-stream`）HTTP 层面是成功的；抛成异常就会用同一套 catch 处理「没权限」和「200 但内容为空」，这是[统一错误处理](/backend/error-handling)讲过的错法。**二，`producedContent` 必须存在**：它记录失败前你往屏幕上写了没有，这个布尔值决定 UI 显示「重试」还是「继续」，也决定这次能不能安全重试。**三，`retryable` 由封装层算**，不让上层猜状态码。**四，`requestId` 是链路钩子**：没有它，「第 8 轮回答重复了」无法定位到具体一次调用（日志字段取舍见[日志与监控](/backend/logging-and-monitoring)）。

适配器的边界是：**换厂商只换 `LlmAdapter` 实现，业务代码一行不动**。这条纪律只有在动手核对之前写下来才有意义，否则接口里全是某家特有字段。**八项核对清单**，每项都是「去查当期官方文档」，本站无法替你核实：对话形状（system 在数组里还是顶层参数、角色有几个叫什么）、长度上限（输入窗与输出窗各多少，超了报错还是静默截断）、采样参数（名称、范围、默认值、能否固定采样）、流式形状（用什么打开、增量字段叫什么、结束信号是什么、有无独立用量事件）、错误形状（状态码之外有无稳定错误类型字段，`retry-after` 在头里还是 body 里）、限流规则（按 RPM / TPM / 并发哪几个维度，配额耗尽与 429 是不是同一个码）、超时与最大连接时长（网关侧有无硬上限，长回答会不会被中间层掐掉，见[实时通信第 10 章](/realtime/ai-streaming)）、计费口径（输入/输出分别计价的比例、缓存命中怎么算、被中断的生成怎么算）。

## 失败分类：一个 200 不代表成功

最容易漏的不是网络错误，而是「状态码成功但结果不可用」。C 组把十二种失败喂给同一个分类器：

```text
=== C 失败分类：分类器是本站写的，输入是合成响应 ===
  401 密钥失效                 → 认证/权限｜自动重试=否（重试也不会有权限）｜日志=status、keyId、region（不记密钥本身）
  403 区域/权限                → 认证/权限｜自动重试=否（重试也不会有权限）｜日志=status、keyId、region（不记密钥本身）
  402 额度用尽                 → 配额/额度｜自动重试=否｜日志=status、quota 字段是否存在
  429 带 retry-after        → 限流｜自动重试=否（要等，不是要重试）｜日志=status、retryAfter、当时并发数
  429 不带 retry-after       → 限流｜自动重试=否（要等，不是要重试）｜日志=status、retryAfter、当时并发数
  500 上游炸                  → 上游故障｜自动重试=否（默认；见第 3 章那条纪律）｜日志=status、requestId、耗时
  503 发布窗口                 → 上游故障｜自动重试=否（默认；见第 3 章那条纪律）｜日志=status、requestId、耗时
  fetch 直接 reject          → 传输失败｜自动重试=否（交给用户点）｜日志=requestId、耗时、error.name
  200 之前一直没人写字节            → 超时｜自动重试=否｜日志=requestId、已等待毫秒、是否有首字节
  200 之后流里夹一个错误事件          → 流内错误｜自动重试=否｜日志=已生成长度、错误事件序号
  200 但收尾说被长度上限截断          → 长度上限截断｜自动重试=否｜日志=输入/输出量、finish 原因
  200 但内容长度为 0             → 内容为空｜自动重试=否（且必须显示而不是留白）｜日志=status=200、内容长度 0、finish 原因
```

**这张表的正确读法不是记状态码，是记「自动重试那一列全是「否」」。** 十二行没有一行建议自动重试，这是结论而不是脚本没写完：认证与额度类重试也不会有权限；限流类的正确动作是「等对方指定的时间」；生成类重试的代价见下一节。

后三行状态码都是 200，是本章最想让你记住的三行。**截断要在界面上明说**（「回答到上限被截断，要继续吗」）并记成独立指标——它是数据量问题不是故障，但若这篇回答本该是一段 JSON，截断等于给你坏 JSON，`JSON.parse` 会把它伪装成解析 bug；**空内容必须显示成可见失败**，留白会让用户重发，而重发就是一次全新计费；**流内错误要保留已产出内容并标注不完整**，「继续生成」是一次全新完整请求（见 A 组），不是续传。

## 重试的代价：生成没有幂等语义

D 组是本章唯一涉及随机的模拟，先说清形状：假设 15% 的响应在**回程丢了**——上游确实完成了生成，但你的服务没拿到结果（超时、连接断、网关掐掉都算）。固定种子 20261021，400 个用户请求：

```text
=== D 重试的代价：响应在回程丢了，重复的是整篇生成 ===
  失败形状：响应丢失率 15%，400 个请求，固定种子 20261021
  ① 自动重试 + 无幂等键：{"用户请求":400,"上游完成次数":463,"界面重复篇数":63,"幂等命中":0,"用户看到中断提示":0}
  ② 自动重试 + requestId 唯一索引：{"用户请求":400,"上游完成次数":400,"界面重复篇数":0,"幂等命中":63,"用户看到中断提示":0}
  ③ 不自动重试（用户点，40% 会点）+ 唯一索引：{"用户请求":400,"上游完成次数":400,"界面重复篇数":0,"幂等命中":22,"用户看到中断提示":64}
```

三行只差两个数：**上游完成次数**和**用户看到中断提示**。① 多付的 63 次是 63 段整输入和 63 篇整回答，换来的只是屏幕上 63 组重复，而用户全程不知道自己被重复服务了、错误率指标一路健康——「只涨账单不涨错误」的故障最难发现。② 与 ③ 都是 400：**幂等键把重复的代价从「两次生成」压成「一次生成加一次查表」**，两者区别只在 ③ 让用户知道「这次没成」（64 次中断提示）。

必须把幂等键的范围说准，否则会被误用成「加了 key 上游就会去重」：**幂等只做在你自己这一层**，形状是「同一个 requestId 在你的服务里只能产生一次向上游的转发」，靠数据库唯一约束——同键第二次进来直接返回第一次存好的结果。上游不认识你的键，也不会为你去重。完整表形态（唯一索引、状态列、失败态允许重试）在[会话、限流与幂等](/data-storage/session-rate-limit-idempotency)钉过；本章只补它的 AI 特殊性：重复一次是**整段输入重新计费 + 一整篇新内容**，而新内容还不一定和旧的一样（采样有随机性），连「重复」在语义层都守不住。

什么情况下重试才是对的？三条判据写成动作：请求**确定**没发出去（连接建立失败且从未收到第一个字节）；用户已经看到失败并且**由他点**；或者你重试的不是生成而是**校验**（输出不合式就带更强约束提示重发——那属于结构化输出的重试策略，且计入成本，不是免费兜底）。默认不自动重试听起来不高级，但它是本章唯一希望你抄下来的默认值。第三方 API 的重试取舍在[短信、邮件与第三方 API](/message-queue-cloud/sms-email-and-api)里以发信场景讲过，那个场景敢重投是因为厂商侧有去重，生成侧没有。

## 密钥：真正要防的是构建期内联

E 组的演示很短，但它打掉的是最常见的一个侥幸：

```text
=== E 密钥位置：构建期注入会进产物（字符串替换演示，不是真实打包器） ===
  前端直连厂商（构建期内联 env）         ：产物里能搜到密钥=true，产物里能看到厂商 URL=false
  前端只打自己服务端（不引用任何 env）      ：产物里能搜到密钥=false，产物里能看到厂商 URL=false
  正确形状只有一句：密钥只在服务端读，前端连「厂商地址」都不该知道
```

机制要说准：泄漏路径不是「前端代码被人看见」，而是**构建工具把被引用的环境变量当常量替换进了产物 JS**。所以判据不是「我有没有写进 `.env`」，而是「构建产物里能不能搜到那串字符」——前缀与内联规则在[环境变量与配置管理](/frontend-engineering/env-and-config)里讲得更细，本章的演示只是字符串替换，**不是真实打包器，本批未跑过任何构建**。

四条落法：密钥只在服务端进程里读（超时、裁剪阈值这类配置也一起走服务端环境变量）；前端只打你自己的后端，**连厂商地址都不该知道**；git 历史里的密钥删不掉只能**轮换**，并假设泄漏已经发生（[Web 安全](/backend/web-security)）；AI 的 key 直接对应账单，所以**用量告警和轮换要一起做**，只轮换不设告警等于月底才发现。最后一句关于日志：记 **keyId**（哪把 key、哪个区）而不是 key——C 组那张表里所有认证类失败都需要它，而这完全不需要把秘密写进日志。

## 常见错误与排查

**1. 现象：十几轮之后突然报「超出上下文长度」，或响应明显变慢。** 原因：每轮全量重发历史，输入随轮次线性增长（A 组第 12 轮是第 1 轮的 61.0 倍）。怎么确认：把每次请求的**消息条数**与**输入字符总量**打进日志，按轮次画线，它应该是直的；比直线陡说明历史里混进了重复片段。怎么修：先定位「陡」的来源（同一轮存了两遍？工具结果当 user 塞了几次？system 每轮追加？），再谈裁剪——裁剪归第 4 章，别用摘要掩盖拼接 bug。

**2. 现象：模型行为时好时坏，偶尔完全忽略你的规则。** 原因：多条 system 互相冲突，或 system 被挤到历史中间。怎么确认：打印发出去的角色序列，例如 `S U A U A U`；出现两个 `S` 或 `S` 不在第 0 位就是它。怎么修：一个进程里 system 提示只有一个**唯一来源**（模板文件 + 版本号），任何「临时加一句规则」都改成修改那个模板，而不是往数组里再塞一条。

**3. 现象：界面上是一条空白气泡，日志里 status 全是 200。** 原因：空内容被当成功渲染；或流式没拿到增量就回写了一条空 assistant，**下一轮的历史因此也脏了**。怎么确认：渲染前断言 `content.length > 0`，把违反次数记成独立指标；再查库里 `content` 为空字符串的 assistant 行数。怎么修：空内容显示成明确失败并提供重试，同时把空行从历史里清掉，别让脏历史继续发酵。

**4. 现象：用户投诉「同样的回答出现了两遍」，而错误率没有任何异常。** 原因：自动重试在「响应回程丢失」这一类失败上重做了整篇生成（D 组 ①：463 次上游完成、63 组重复）。怎么确认：统计同一个 `requestId`（或同一用户同一消息）产生的上游完成次数，比值大于 1 就是它。怎么修：默认改成不自动重试（③）并给幂等键加唯一索引（②），两条一起做才既不多付也不重复。

**5. 现象：429 之后你的服务成串失败，上游恢复后又自己好了。** 原因：把限流当普通失败立刻重试，或 `retry-after` 根本没读（清单第 5 项就是它）。怎么确认：看失败的时间分布是不是「越忙越炸、炸完更忙」的正反馈形状；再看日志里的`当时并发数`。怎么修：按对方给的时间等，同时给自己的服务加一层入口限流（[限流那一章](/data-storage/session-rate-limit-idempotency)），让队列等在你这边。

## 练习

<Exercise title="练习 1 · 把 A 组的算术外推到第 20 轮" difficulty="基础">

沿用 A 组假设（system 26 字符、每轮用户输入 40 字符、每轮回答 320 字符，纯追加式历史）。① 第 20 轮发出去多少条消息、输入字符多少？② 前 20 轮按「每轮全量重发」口径累计多少字符？③ 若回答长度从 320 变成 1,600，第 20 轮的输入量是多少？先写公式再算数，不要试。

<template #answer>

① 第 k 轮条数 = 1 条 system + k 条 user（含本轮）+ (k−1) 条 assistant = `2k`，与 A 组的 2/4/6/24 逐行吻合，故第 20 轮 = **40 条**。输入字符 = `26 + 40k + 320(k−1)`，k=20 → **6,906**，是第 1 轮（66）的 **104.6 倍**。用 k=12 复算得 4,026，与 A 组第 12 行逐字相同，公式成立。

② `Σ(k=1..20) [26 + 40k + 320(k−1)] = 20×26 + 40×210 + 320×190 =` **69,720 字符**，A 组倒数第二行印的正是这个数。顺带算清另一个口径：整段对话最终多长 = `26 + 40×20 + 320×19 =` 6,906，**恰好等于第 20 轮的单次输入**，因为在纯追加式历史里这两个量本来就是同一个东西。两个口径都对却差 10 倍——这就是「报数必须带口径」的来处。

③ 第 20 轮 = `26 + 800 + 1600×19 =` **31,226 字符**，是原假设的 4.5 倍。结论形状：**回答越长，历史膨胀越快**，输出上限与输入窗口不是独立参数，它们通过轮次互相放大。

</template>

</Exercise>

<Exercise title="练习 2 · 故意造出三条脏历史并解释报错原文" difficulty="进阶">

构造三条**能触发 B 组拒绝**的消息数组，写出报错原文里的关键词，并说明为什么「三条连续 user」只警告不拒绝。

<template #answer>

```ts
validate('请解释一下 this 的绑定规则')     // ① 报：不是非空数组（对话 API 收的是消息数组，不是字符串）；validate([]) 走同一条
validate([{ role: 'user', content: '上一轮的话' },
           { role: 'system', content: '请只输出 JSON' }])   // ② 报：system 出现在第 1 条（位置不是最前）
validate([{ role: 'system', content: '模板 A' },
           { role: 'system', content: '模板 B' },
           { role: 'user', content: '本轮提问' }])          // ③ 报：出现多条 system
```

② 的真实成因通常是「先拼历史，再 push 追加规则」；③ 的成因是每轮都追加一次规则，或两套模板各塞了一条。注意报错必须能定位：只说「多条 system」而说不出**在第几条**，排查时等于没报——B 组输出里那个下标才是它能用的原因。

至于三条连续 user：至少三种正常形状会产出它——工具结果作为 user 回填（第 8 章）、用户连发两条而前一条还没生成、把检索原文当独立一条注入。**硬拒绝会让这三种全发不出去**。但它确实是脏历史的强信号，最常见成因是同轮历史被拼了两遍，所以正确处理是「放行 + 把角色序列记进日志」，让常见错误 1 可查。**分界线画在「一定不对」而不是「我觉得可疑」**，这在[统一错误处理](/backend/error-handling)里是同一个原则。

</template>

</Exercise>

一次调用要能回答「谁发起的、发出去什么形状、结果是什么、失败属于哪一类、这次花了多少量」。① 列出日志字段；② 列出永远不能记的东西并说明原因；③ 输入量与输出量为什么要分别存成数字列。

<template #answer>

① 最小字段集（C 组那张表的「日志」列就是它的分配结果）：`requestId`、发起方 `purpose`（哪个功能/路由）、用户内部 id 或哈希、消息条数、**角色序列**（`SUAUAU` 这种字符串，不含正文）、输入字符总量、输出字符总量、`finish` 原因、耗时分段（发出→首字节→结束）、失败类、`retryable`、`producedContent`、`keyId` + region。角色序列那一行是排查常见错误 1 与 2 最省事的字段：一眼看出条数与拼接重复，又完全不涉及内容。至于要不要记正文，这是隐私判断而不是技术默认——记了省掉复现困难，代价是把用户输入长期留在日志里，这条边界归[第 9 章](/ai-apps/evaluation-and-observability)。

② 永远不能记：**密钥本体**（日志的读取权限通常远大于密钥的使用权限，一处日志外泄等于密钥外泄）；无脱敏策略下的**用户原文**；上游响应里可能带回的**其他租户数据**；以及完整的 system 模板正文——模板进 Git 版本管理，日志只记模板名与版本号，否则提示无法追溯也无法比对。

③ 因为单价不同、增长规律不同：输入随轮次线性膨胀（A 组那条 61.0 倍曲线），输出由回答长度与上限决定。分开存才能回答三个问题——钱花在哪一边（输入主导 → 该裁历史；输出主导 → 该看长度上限）、成本随产品怎么变（输入列的斜率会先暴露历史膨胀）、以及为什么「按平均一轮估的预算」必然偏低。F 组那行「输入 35 / 输出 15」给的是形状，真实 token 数只能来自上游返回，**本机没有 tokenizer 可核对**，这句要写进 README 而不是假装算过。

</template>

</Exercise>
