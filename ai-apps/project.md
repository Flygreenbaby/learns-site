# 阶段项目：个人知识库问答助手

第 7 章那份输出里最刺眼的一行不是哪个分数低，而是两行数字放在一起的样子：检索段 10/12，生成段 8/10，端到端 8/12。把两段乘回去，端到端还是那 8 条。也就是说检索确实变好了，用户看到的质量一点没动。这个项目存在的理由就是让「检索改好了」这句话不再能随便说出口——它把前十章的每一条承诺压成一次交付，每一条都配一个能跑的判据。

第二个动机来自一个更尴尬的形状：助手在只给自己用的 VPS 上跑了三天，然后准确复述出 `.env` 的内容。不是模型天生要泄密——那段文字被当作检索片段塞进提示，模型照抄，而出口没人拦。[第 10 章](/ai-apps/security-and-abuse)的四层笼子、[第 8 章](/ai-apps/function-calling-and-agents)的审计字段、[第 5 章](/ai-apps/structured-output)的四级闸门，到了项目里必须落在同一段代码的同一条执行路径上，否则就只是「读过」。

所以要验收的不是提示词写得多漂亮，而是五个问题：块进库之后来源坐标还在不在；库里查不到的时候它说不说「不知道」；流被掐断那一次算成功还是算失败；模型给回的 JSON 过了几级闸门；助手能碰的东西有没有上限。本批两条证据脚本在 Node v25.4.0 / Windows 上真跑（2026-10-22），38 条断言全过、**0 次模型 API 调用**、0 次外部网络请求、0 个依赖安装。凡涉及 PostgreSQL + pgvector、厂商 API、浏览器渲染、Nginx、VPS 的部分，本章只给命令形状、判据和本机替代方案，并逐条标注「需要真实账号/真实环境，本地可用替代方案验证」。**本批没有完成任何真实部署，也不声称完成。**

## 目标与范围

这个项目要证明的只有一件事：**一条完整的 RAG 链路里，每个环节都能被说清楚「在本机怎么验、在真机上怎么验」**。它不是要你造一个能上线的产品，而是要你把前十章散落的机制第一次组装成同一种语言——同一个 `doc_id`、同一条引用键、同一份审计表、同一套停因字段。纳入范围的五件事正好对应阶段 1–6：真实 Markdown 带坐标入库、三种排序在同一份库同一批查询上并排出数、流式消费的完整契约、出口一侧的闸门与脱敏、助手能做的动作有上限。

明确不做的事，一条都不加：

- **不做多 Agent 协作**。一个循环、一份白名单、一条审计表已经够处理本项目的所有失败模式；多 Agent 只会把「谁执行了哪一步」从十个字段变成三份日志。[第 8 章](/ai-apps/function-calling-and-agents)那条审计字段就是本章的上限形状。
- **不做微调，也不上编排框架**。本章没有任何一处需要权重可更新；框架替你藏起来的正是你需要先手写一遍的机制。
- **不做网页爬虫入库、不做多模态、不做用户系统与团队协作**。语料是你自己的 `.md`，来源可数、内容可读、哈希可复算；爬虫会把「来源坐标」变成不可复现的运行时依赖。认证直接复用[后端 · 授权与权限](/backend/authorization)，本项目只要求「只有你自己能用」。

范围控制的判据也写在纸上：如果你在阶段 2 里开始想「要不要加个重排模型」，先回答[第 7 章](/ai-apps/rag-quality)那个问题——现在这三张榜里，哪一张的天花板被证明了是瓶颈？答不出来就先别加。本项目的天花板有实测数字（148/175 块），阶段 2 会用到。

## 目录结构

一个目录树，一条实现线。阶段编号写在注释里，读者按阶段推进时只需要按顺序把文件从骨架填成实现。

```text
kb-assistant/
  package.json               # 只有 type: module，零运行时依赖
  .env.example               # 只放键名，不放值；真实 .env 进 .gitignore
  docs/
    scope.md                 # 阶段 0：一页纸边界，含「不做」清单
    threat-model.md          # 阶段 6：四层笼子各自的实现位置与演练记录
  scripts/
    ingest.mjs               # 阶段 1：读 md → 切块 → 写 SQLite（含来源坐标）
    eval.mjs                 # 阶段 2 + 5：三张榜、指标、评测集跑分
    ask.mjs                  # 阶段 3：检索 → 注入 → 流式消费 → 落库
  server/
    app.mjs                  # 阶段 3：POST /ask（SSE）与 GET /cite/:key
    gate.mjs                 # 阶段 4：四级闸门 + 出口脱敏
    tools.mjs                # 阶段 6：注册表 → 参数 → 授权 → 确认 → 幂等
    audit.mjs                # 阶段 6：一行一问，15 个字段
    db.mjs                   # 迁移：docs / chunks / messages / audit
  questions/
    golden.jsonl             # 阶段 5：≥20 条，一行一条，含手写相关集
  web/
    ask.html                 # 阶段 3：逐字渲染 + 停止按钮（本批未在浏览器运行）
  data/
    kb.sqlite                # 生成物，不进版本控制
```

三条组织原则决定了后面所有阶段能不能对齐。一，**来源坐标只有一个真相来源，就是 `db.mjs` 的建表语句**：`ingest.mjs` 写它、`eval.mjs` 读它、`gate.mjs` 查它、前端通过 `GET /cite/:key` 再查它。这条链上一旦出现两处各自拼 `doc_id` 的代码，「引用可溯」就会在两处给出不同答案。本项目里坐标长这样：`doc_id` 用短名（`nginx`），`path` 存真实相对路径，块键是 `nginx:24`，四者只在入库那一次绑定。二，**闸门与脱敏放在 `gate.mjs`，不写在 `ask.mjs` 里**：B4 那行实测说得很直白——成功出口调了脱敏、错误出口没调，等于把上游原文裸奔给客户端；两处出口共用一个函数，是本项目里最便宜的防「忘了调」结构。三，**评测集是数据文件不是代码**：`golden.jsonl` 每次改切分参数或注入预算后原样重跑，输出连参数与日期一起落盘，这样「hit@3 从 0.833 变成 0.750」这类话能被复算，而不是靠记忆。

## 分阶段实施

八个阶段是一条线，不是一份清单：阶段 0 定边界，1–2 造「文档到候选片段」，3–4 造「片段到用户眼前」，5 给前面所有决定打分，6 装上刹车，7 把本机验不了的半句搬到真机上。每阶段末尾的「真实环境限制」那一栏就是阶段 7 的目录。

### 阶段 0：把「不做什么」写成一页纸

**目标**：在写第一行代码之前，先把这个项目会失败的两个方向（范围膨胀、把模拟当真实）钉在纸上。

**涉及文件**：`docs/scope.md`、`docs/threat-model.md`（只写标题和四节占位）。

**实施步骤**：一，把上面「明确不做的事」逐条抄进 `scope.md`，每条后面补一句「为什么在本项目里它不解决问题」。二，在 `scope.md` 末尾写两列清单：左列是「本机可验」，右列是「需要真实账号/真实环境」，照需求清单那张表的第三列填。三，在 `threat-model.md` 里给四层笼子各留一节：注册表、参数、授权、确认，并写下「本项目的实现在哪个文件的哪个函数」。

**可核对产物**：一页边界表 + 一张威胁表骨架。

**验收方法**：找人只读这两页，问三个问题——这个项目做完是什么样、哪几件事它故意不做、上线前最坏能坏成什么样。三个问题都有答案就过。

**失败排查方向**：如果你的「要做的」条目数超过需求清单那九条，说明边界还没定下来，回到「不做」清单删。如果 `threat-model.md` 里某一笼子的「实现在哪」写成「以后再加」，那这一层等于没有——[第 10 章](/ai-apps/security-and-abuse)那九个工具九条请求的四层判定里，放行只有 1 条，靠的就是每层都有具体代码位置。

**真实环境限制**：无。这一阶段全在纸上。

### 阶段 1：真实笔记 → 块 → 来源坐标 → 库

**目标**：把磁盘上的 `.md` 变成带坐标、可版本化、能被查询回来的块表。这是整条链唯一「错了后面全错」的阶段。

**涉及文件**：`scripts/ingest.mjs`、`server/db.mjs`。

**实施步骤**：读文件 → 用内容哈希当版本号 → 按 H2 边界优先切 → 段落成组 → 超上限按句末标点切 → 仍无标点才硬切 → 写库。

```sql
CREATE TABLE docs(doc_id TEXT PRIMARY KEY, path TEXT NOT NULL,
                  bytes INTEGER NOT NULL, ver TEXT NOT NULL);
CREATE TABLE chunks(doc_id TEXT, chunk_no INTEGER, h1 TEXT, heading TEXT,
                    chars INTEGER, body TEXT,
                    PRIMARY KEY(doc_id, chunk_no),
                    FOREIGN KEY(doc_id) REFERENCES docs(doc_id));
-- 本机实测：这个库里 FTS5 可用，倒排由 SQLite 维护
CREATE VIRTUAL TABLE chunks_fts USING fts5(body, content='chunks', content_rowid='rowid');
INSERT INTO chunks_fts(rowid, body) SELECT rowid, body FROM chunks;
```

```js
// scripts/ingest.mjs 的核心形状（A 线脚本就是它的实现）
const MAX_CP = 280;                       // 上限单位：码点，不是字节、不是 UTF-16 长度
const ver = createHash('sha256').update(buf, 'utf8').digest('hex').slice(0, 12);
// 1) H2 边界优先，且必须跳过代码围栏里的 #，否则示例配置会被当成小节标题
// 2) 一个 H2 小节内按空行成组累积；超过 MAX_CP 才找句末标点（。！？。；）
// 3) 找不到句末标点才硬切，并给这次硬切计数：brokenHard++
// 4) 每条块必须带 (doc_id, chunk_no, heading, chars, body)，缺一个就整批拒绝入库
```

三个技术选择要能自答。**为什么上限用码点不用字节**：中文一字 3 字节，用字节当预算会让中文块的字符数只有英文的三分之一，而模型的上下文按 token 计，与码点的关系比与字节更近；[第 4 章](/ai-apps/context-and-cost)那三口径对照（比值 1.00–3.00）就是这个选择的依据。**为什么版本号是内容哈希而不是文件 mtime**：`mtime` 在你 clone、checkout、容器拷贝时全变，哈希只在内容真变时变；A 线里同一文件两次跑出的 `ver` 相同（`9930e1d64ea5`），这条就是可复现性的判据。**为什么把 `heading` 存进块而不是查询时再算**：来源展示要能说「第 24 块来自小节「反向代理：先搞清 Nginx 默认改了哪些头」」，这句话只有在切分时才知道——事后再算需要重读文件、重跑切分。

**可核对产物**：`data/kb.sqlite` 里 `docs` 5 行、`chunks` 467 行，每行坐标齐全。

**验收方法**：三条断言，A 线里全过——入库条数等于内存条数（真实写库，`SQLite 467 / 内存 467`）；逐块从库里读回正文与写进去的逐字相等（467 块全比）；最长块不超过上限（实测最长 280）。**再加一条本批没做的下限断言**：最短块不得低于某个值（比如 40 码点），低于就合并进邻块或整批拒绝。

**失败排查方向**：块数比预期少，先看围栏里的 `#` 被当成了标题；块数比预期多，看表格行是否被当正文；出现 1 码点的块，就是那个「只有标题的小节」；正文码点与源文档码点差值突然变大，看是不是把代码块整段吞进正文了。

**真实环境限制**：`node:sqlite` 是 Node 的实验内置模块，警告原文照抄在上面；它的行为不保证跨版本不变。**PostgreSQL + pgvector 本机没有**，Prisma 也没有安装，所以首页第 2 条承诺的「表结构经 Prisma 迁移管理」在本项目里只做到了 SQLite 版的建表语句，向量列、索引类型、维度上限全部未在本机验证。

### 阶段 2：三张榜放在同一份库、同一批查询上比

**目标**：不是「做一个向量检索」，而是**在同一份库、同一批查询上，让关键词排序和某种语义化排序并排出数**，然后用融合看两者的分歧能不能补上。

**涉及文件**：`scripts/eval.mjs`（本批就是 `project-kb-corpus.mjs`）。

**实施步骤**：分词 → 关键词榜（BM25，`k1=1.2`、`b=0.75`）→ 模拟排序榜 → RRF 融合 → 三张榜并排打印。

中文没有空格可切，本批的分词是「拉丁词与数字按词、汉字按相邻双字（bigram）」——它不是形态分析，「取消」与「取消了」会被当成两个词，这既够 BM25 工作，也够诚实。FTS5 在本机可用，倒排交给 SQLite，BM25 的评分公式仍在 JS 里实现。

模拟排序榜的做法必须交代清楚：把每块词集经 `sha256` 投到固定 32 维的词面签名向量上，再算余弦。**它是模拟**。它不含任何语义——不会因为「断线」和「连接中断」意思相近而给高分，只会因为字面同现而给分。它的存在价值只有一个：让「向量榜与关键词榜给出不同候选」这件事在本机以代码形状出现，而不用调任何 embedding API。[第 6 章](/ai-apps/rag-retrieval)那组 q1 结果（向量 0.976 / 0.970 / 0.891 而词面命中全 0）就是这个形状的语义版，本章不复制那个结论。

```text
=== A4 三张榜在真实语料上的算术结果 ===
  全 24 条：hit@1=0.667 hit@3=0.833 hit@5=0.833 MRR=0.743
  仅 normal 18 条：BM25 hit@1=0.833 hit@3=1.000｜模拟榜 hit@3=0.500｜RRF hit@3=0.889
  天花板（两榜并集覆盖到的相关块数 / 相关块总数）：并集覆盖=148 块可被检索，标注相关集共=175 块
  无答案/注入类 4 条：BM25 词面零命中=0 条，最高分分别=6.757 / 9.184 / 9.357 / 10.134
  recall@3 在这些条目上=NaN / NaN / NaN / NaN（空相关集：分母为 0，返回 NaN 而不是 0）
```

这五行是本项目的质量基线，读法有讲究。三行 hit@3 并排放着：**BM25 正常类 1.000、模拟榜 0.500、融合 0.889**。这里绝不能得出「embedding 不行」——那个「模拟榜」根本没有语义，输给词面是设计使然。能得到的结论只有两条：这份语料上词面已经把正常类问句兜住了（18/18 命中前三），因为问题里的术语（`limit_req`、`alias`、`sshd_config`）就是文档里的字；融合那 0.389 的抬升来自两张榜的名次分歧，不是理解。而一旦你要处理口语化提问「nginx 改完配置怎么没反应」，那个 1.000 立刻不成立——提问里没有 `location`、`proxy_pass` 这些字面词。**这就是真实环境里接 embedding 的理由**，写进 `scope.md` 比写在代码注释里有用。

第四行是天花板：**148/175 = 84.6%**。并集覆盖不到的那 27 块，任何重排都救不了，因为它们在检索段就没进候选——这是「要不要加模型」的唯一判据：正常类 hit@3 一旦贴着天花板，加什么都没用，得先改切分或元数据过滤（[第 6 章](/ai-apps/rag-retrieval)）。第五行是[第 7 章](/ai-apps/rag-quality)那条陷阱在真实语料上的复现：空相关集的 `recall@3` 返回 `NaN` 而不是 0，同一批查询的 `hit@3` 却记成 0——这就是全 24 条 0.833 低于正常类 1.000 的全部原因。**没有答案的问题绝不能进检索质量的分母**，本项目把它挪去另一条判据：库里没有的时候，系统有没有说「我不知道」。

第五行下面那条断言值得单独抄给你的实现：`正常类中位=21.03｜无答案类最高=9.18｜词面覆盖率 正常=1.00`。差距超过一倍，意味着「BM25 最高分低于某个远低于正常类中位的值」在本份语料上可以作为「查不到就降级」的触发条件。**但 9.18 和 21.03 都不是可移植阈值**——它们属于这 5 份文件、这 24 条查询、这套分词。做法是把阈值写成配置项，并在阶段 5 的评测集上验它的漏检与误伤。

**验收方法**：hit@1 / hit@3 / MRR 三个数能被只读输出复算；RRF 榜首分数等于手算的两榜名次倒数和（`k=60`，本批实跑一致）；融合榜引用 120 条全部能在库里解析（实测未解析 0 条）；空相关集的 `recall` 是 `NaN`，且汇总时把它排除而不是当 0。

**真实环境限制**：真实 embedding 模型需要厂商账号（需要真实账号/真实环境，本地可用替代方案验证：词面签名只验「两榜分歧 + 融合补集」这个形状）；pgvector 的索引类型、操作符、维度上限与 `ef_search` 一类参数**本机全部未验证**；本批对外部文档 0 次抓取。

### 阶段 3：流、取消、超时与会话历史

**目标**：把「一段不能重放的字节流」做成有终态的东西——要么完整收敛，要么被明确分类为取消或超时，且两者的记账不同。

**涉及文件**：`server/app.mjs`、`web/ask.html`、`db.mjs` 的 `messages` 表。

**实施步骤**：本机起一个只绑 `127.0.0.1`、端口由系统分配的假上游（B 线脚本就是这么做的），实现客户端消费契约：跨块缓冲、按空行切帧、`[DONE]` 判定、每帧重置的空闲计时器、`AbortController` 取消、结束后落库。

```js
// server/app.mjs 消费侧的核心形状（B 线脚本就是它的实现）
const ac = new AbortController();
let buf = '';
let last = Date.now();
const idle = setTimeoutOrDie;                 // 每收到一帧就重置，不是一次性总超时
for await (const chunk of res.body) {
  buf += decoder.decode(chunk, { stream: true });   // stream:true，别在字节边界 toString
  last = Date.now();
  let i;
  while ((i = buf.indexOf('\n\n')) >= 0) {           // 空行才是帧边界，不是每个 chunk 一条事件
    frames.push(parse(buf.slice(0, i)));
    buf = buf.slice(i + 2);
  }
  if (frames.some((f) => f.data === '[DONE]')) return 'converged';
}
// 走到这里只有两种结局：用户按了停止（cancel），或空闲计时器到点（timeout）
```

三个必须写清楚的取舍。**取消与超时不能共用一个终态**：取消是用户意图，`stop_reason='user_cancel'`、`effect_state='none'`（你已经知道上游只产了几块）；超时是系统故障，`stop_reason='timeout'`、`effect_state='unknown'`——你不知道上游那半截是否已经生成了副作用。B 线那两行就是这两条分支：取消那次客户端消费 3、上游实际产出 3、`sawClose=true`、[DONE]=false；超时那次消费 1、产出 1、半截 15 码点。

**半截文本不能当答案入库**。实测里超时那 15 码点确实被拿到了，但入库的是 `timeout` 这一行审计，不是那 15 个字；如果你顺手把 `answer` 写进 `messages`，下一轮模型就会把一句断在中间的话当完整前文接着编。**「停止按钮」至少要做完三件事**（这条与[实时通信 · AI 流式](/realtime/ai-streaming)是同一份契约的两半，那边管传输与生命周期，这里管消费与记账）：中止本地读取、告诉上游、把终态与已消费块数写下来。只做第一件的按钮，账单上不会给你任何回报。

会话历史的形状检查用得上[第 1 章](/ai-apps/llm-api-basics)那条实测：B 线里正常形状的角色序列是 `assistant user assistant user`，末尾是 `user`；把最后那条 `tool_result` 删掉（模拟「提出后不回填就再发」），末尾立刻变成 `assistant`。这条差别在你自己的库里同样可测，判据就是 `SELECT role FROM messages WHERE session_id=? ORDER BY id DESC LIMIT 1`。

**可核对产物**：`messages` 表里每个会话的角色序列合法；三种结局各一行审计。

**验收方法**：完整那次的 `[DONE]` 到达且客户端块数等于上游产出（8 = 8）；取消那次的上游产出严格小于完整那次，且上游观察到 `close`；取消那次没有 `[DONE]`，因而不能被记成成功收敛；超时那次文本码点数显著小于完整那次（15 / 89）；**脚本退出后没有任何进程还在监听**（B 线实测 `server.listening=false`，再次请求连不上）。

**失败排查方向**：取消后上游还在产 → 你把 `close` 挂在了错的对象上，或者写进了已销毁的 socket；[DONE] 永远收不到 → 按 chunk 而不是按空行解析；中文乱码 → 在字节边界上调了 `toString()` 而没有 `stream: true`；页面看起来「停了但还在扣」→ 你只关了本地读取，没传播取消，去看上游产出块数那一列。

**真实环境限制**：浏览器端逐字渲染与按钮交互**本批未在任何浏览器里运行过**（0 次页面加载），前端代码是结构示意；厂商 API 的流式事件名、结束信号、取消方式与重连语义**一律未在本机核实**，接入前查当期文档；经 Nginx 反代的 SSE 还需要真实 Nginx 验缓冲与空闲超时（阶段 7）。

### 阶段 4：结构化输出、引用展示、出口脱敏串成一条链

**目标**：让「模型给的文字」和「模型给的数据」在同一处出口上被同一套规则过一遍，并且引用点得开。

**涉及文件**：`server/gate.mjs`。

**实施步骤**：把四级闸门按[第 5 章](/ai-apps/structured-output)的顺序接成一条函数链：语法（能不能 `JSON.parse`）→ 结构（字段齐不齐、有没有多余键、数值范围）→ 语义（值在不在合法集合里）→ 出口（引用可溯 + 脱敏）。第四级在本项目里多了一个具体动作：**每个引用键都拿 SQL 去库里查一次**，查不到就降级。

```text
=== B3 四种上游形状过四级闸门（引用必须能查到才给引用）===
  干净 JSON      语法=true 结构=true 语义=true 引用可溯=1/2 不可溯=1 载荷标记=false → 接受并入库
  围栏包裹         语法=false 结构=false 语义=false 引用可溯=0/0 不可溯=0 载荷标记=false → 拒绝（记一次失败，不写终稿）
  尾随客套话        语法=false 结构=false 语义=false 引用可溯=0/0 不可溯=0 载荷标记=false → 拒绝
  夹带注入载荷       语法=true 结构=true 语义=false 引用可溯=0/1 不可溯=1 载荷标记=true → 拒绝
=== A5 来源追溯与降级（引用必须能查到，查不到就不给引用）===
  真实引用 nginx:24 → {"path":"linux/nginx.md","heading":"反向代理：先搞清 Nginx 默认改了哪些头","no":24,"head":"t_header Connection close;"}
  伪造引用 nginx:9999 → 查不到（必须降级，不得编造来源）
```

那行真实引用的 `head` 是从 `proxy_set_header Connection close;` 中间截开的——因为第 24 块的起点本身在句中（它是被硬切出来的 56 块之一）。这不是 bug，是**硬切的代价会在 UI 上现形**：来源预览可能从一个词的中间开始。要么给块补「所在句首」字段，要么在展示时向前扩展到最近的句末标点，二者都要写成断言，别让它只在人眼可见时才被发现。

第一行是四条里唯一的接受，也是本项目的关键结构：**接受不等于完美**。干净 JSON 的两个引用里只有一个可溯，另一个（`nginx:999`）库里没有，第四级把它判成不可溯——答案是接受的，引用列表被削成一条。这条分支必须有代码位置，否则「模型编了一个不存在的来源」会一路走到用户眼前。B 线里「入库答案数 = 被接受形状数 = 1」就是这条链的总数判据。

脱敏放在同一个 `gate.mjs` 里，且成功出口与错误出口共用：

```json
{"answer":"反代最少要补四个头","cites":["nginx:1","nginx:999"],"confidence":0.8,
 "gate":{"syntax":true,"shape":true,"semantic":true,"exit":"cites_resolved=1/2,masked=false"},
 "audit":{"step":2,"call_id":"c1","tool":"kb.search","proposed":1,"validated":1,"authorized":1,
 "confirmed":1,"executed":1,"outcome":"ok","effect_state":"committed","idem_key":"q:sha1",
 "backfilled":1,"stop_reason":"converged","tokens":135,"rid":"r-7"}}
```

`audit` 那十五个字段就是阶段 6 的表结构，一条回答一行审计，一条被拒调用也是一行。

**验收方法**：四种形状里恰好一种被当终稿，其余各自停在对应级别；伪造引用被第四级判为不可溯；夹带 `IGNORE_PREVIOUS` 那条既不入库也不污染会话；回显出口脱敏后密钥形态与内部端点片段同时为 false；错误响应出口也调用了同一个脱敏函数（B 线里这条以「未调就是裸奔」的提示出现，把它写成断言：错误分支返回的文本里 `sk-` 形态计数为 0）。

**失败排查方向**：所有形状都停在语法级 → 上游在 JSON 前后加了人话，这是最常见的一种，第 5 章那四个修复器就是为此存在；引用全不可溯 → `doc_id` 命名在入库和检索两处不一致；脱敏时有漏 → 只在成功出口调了；改完闸门成功率没变 → 你可能把语义级判据写宽了，去数失败分布而不是数成功数。

**真实环境限制**：「模型会不会真的输出围栏包裹的 JSON」「真实厂商的 JSON 模式错误返回什么形状」本机无法证明；B 线里四种形状是**由本批脚本自己喂给自己的**，用来证明你的代码会拒绝什么，不证明模型会给你什么。

### 阶段 5：不少于 20 条手工标注评测集

**目标**：给前四个阶段的每个决定一个分母，并且让「改坏了」这件事在 30 秒内可见。

**涉及文件**：`questions/golden.jsonl`、`scripts/eval.mjs`。

**实施步骤**：写查询 → 写相关集 → 跑指标 → 分类看漏检。本批的 24 条分布是 `normal=18 / noanswer=2 / ambiguous=1 / conflict=1 / injection=2`，四类非正常类各只有一条到两条是**下限而非配比**，你把条数抬到 20 以上时优先加 `noanswer` 和 `conflict`，因为这两类最能暴露结构缺陷（一条测「库里没有」的分支，一条测「多个版本并存」的分支）。

相关集怎么写才站得住：先打印库里的真实 H2 清单（A 线 A3 段就打了 64 个小节标题），然后按「`doc_id:chunk_no`」写，写完必须用一条断言验它指向的块真实存在——这条断言本批跑过（`手工标注的相关集全部指向库里真实存在的块` 通过）。少了这条，你打错一个标题字符，评测集会安静地给你一堆 0 分。

有两条标注规则值得直接抄进你的 `golden.jsonl` 说明：**注入类与无答案类的相关集必须为空，并且不进检索质量分母**（本批两条断言同时覆盖这两点）；**冲突类的相关集必须跨两个文档**，否则它测的是单点事实而不是版本冲突（本批实测跨文档数=2）。

```text
  全 24 条：hit@1=0.667 hit@3=0.833 hit@5=0.833 MRR=0.743
```

这行是**把六条空相关集当 0 分算进去**的结果，所以它比正常类的 1.000 低得多。两个数都对，含义完全不同——这句话就是[第 9 章](/ai-apps/evaluation-and-observability)「先补齐分母才能比较」在项目里的落地形态。别在项目文档里只留一行「hit@3 = 0.833」，那行数字无法被任何人复核。

**验收方法**：分类计数之和等于总条数（24 = 24，5 类）；标注全部指向真实块；有答案类相关集非空（本批 20 条）；空相关集的 `recall` 返回 `NaN` 且被排除出汇总；每次改 `MAX_CP`、overlap、top-k 或注入预算后重跑，输出文件名带上参数与日期。

**失败排查方向**：`hit@3=1.000` 但产品看起来很差 → 相关集标太宽（整章全标相关）；分数随重跑小幅抖动 → 检查排序的并列项是否按稳定键破平（RRF 的平票在第 7 章出现过）；「换了切分参数所有指标一起变好」 → 先看天花板 148/175 有没有动，没动就说明你只是在拟合自己写的标注。

**真实环境限制**：**这些数字不是回答质量**。全链 0 次模型调用，「答案是否正确」「是否真的引用了给的片段」这两列本机测不了；真实用户的问题分布需要真实日志（需要真实账号/真实环境）。本批没有做一次人工评测，也没安装任何指标库，`hit@k`/`MRR`/`recall` 全部是脚本内自写实现。

### 阶段 6：白名单、幂等、额度、停止条件

**目标**：把「助手能做什么」变成一份可以数出来的清单，并把每一次尝试（成功和被拒）都记成一行。

**涉及文件**：`server/tools.mjs`、`server/audit.mjs`、`docs/threat-model.md`。

**实施步骤**：工具走[第 8 章](/ai-apps/function-calling-and-agents)那五道顺序：注册表可见 → 参数校验 → 授权 → 确认 → 执行，副作用以业务键做幂等；调用与失败都写 `audit`；额度用令牌桶，步数与成本各一个上限，停因写进独立字段。

```text
  k1 kb.search   proposed=true executed=true  outcome=ok                ｜命中 0 块（真实 SQL）
  k2 kb.search   proposed=true executed=false outcome=invalid_request   ｜参数：topK 超上限 8
  k3 kb.search   proposed=true executed=false outcome=invalid_request   ｜参数：缺必填 query
  k4 kb.search   proposed=true executed=false outcome=invalid_request   ｜参数：未知字段 extra
  k5 admin.purge proposed=true executed=false outcome=invalid_request   ｜注册表：工具不在模型可见白名单内
  k6 kb.search   proposed=true executed=false outcome=duplicate_delivery｜命中 0 块（真实 SQL）
  计数：提出 6，执行 1，拒绝 5，回填 6 条
```

四件事值得解释，因为它们决定了这段代码为什么长这样。

第一，`k5` 落在注册表层、参数根本没看。顺序是有意义的：一个模型可见白名单之外的工具名，如果先进参数校验，你等于用报错告诉对方「这个名字存在、只是参数不对」。**先可见性、再形状**。

第二，`k2/k3/k4` 三类参数失败要能区分开（超上限、缺必填、未知字段），因为修法完全不同：上限是配置问题、必填是提示问题、未知字段通常是模型把上一轮响应的字段名回填了进来。第三，`k6` 那条 `duplicate_delivery` 认的是业务键而不是调用 id——重试会换 `call_id`，但「对同一订单发一次通知」只认订单号；本批最硬的证据不是它返回了错误，而是**副作用没有 +1**。第四，`命中 0 块（真实 SQL）` 是诚实的一行：B 线的 `kb.search` 走真实 SQL，夹具查询串没命中它自带的那 6 个块，于是命中 0——检索质量归 A 线，B 线只验通道、审计与回填。「outcome=ok 而命中 0」比「命中 3」更能提醒你**成功不等于有结果**，而「查到 0 条」正是阶段 2 那条降级分支的入口。

回填这件事必须数得出来。B 线那条断言是 `执行数 + 拒绝数 = 回填数`（1 + 5 = 6）。少了被拒那五条的回填，模型下一轮只会重提同一个调用，因为它的上下文里那条调用「没有下文」。

注入演练在本阶段收尾，B 线那两行是全项目最关键的一条诚实记录：

```text
  上游原文：含内部端点片段=true，含密钥形态=true
  出口脱敏后回显给用户：残留密钥=false，残留端点=false
```

这里的假上游**故意照做了注入**（脚本里那个模式直接把 system 提示连同内部端点与密钥形态的字符串一起吐出），因为「模型会不会被骗」本机证明不了，而「你的出口拦不拦得住」本机完全能证明。把演练做成可复跑的：注入样本进 `golden.jsonl` 的 `injection` 类，出口断言进 `eval.mjs`，演练记录写进 `docs/threat-model.md` 的四层笼子小节。

**可核对产物**：`audit` 表 15 列；本批一次运行落 10 行（工具 6 + 闸门失败 3 + 循环 1）；`stop_reason` 非空且取值落在合法集合里；额度实测「连发 9 次 → 放行 5，拒绝 4」；循环「步=3 tokens(估算)=135 stop=收敛（给出最终回答）」。

**验收方法**：四条判据——执行 + 拒绝 = 回填；白名单外的工具不进参数层；同业务键第二次不产生副作用；停因写在独立字段而不是拼在句子里。**再加一条**：审计行数 = 提出的调用数 + 循环数，少一行就说明有分支没被记录。

**真实环境限制**：`tokens=135` 的口径是本机字符数/4 的估算，**不是厂商计价**，真实账单、缓存命中折扣、限流响应头的语义全部需要真实账号；B5 那句「模拟时钟，未真实等待窗口」也照抄——令牌桶的算术是真跑的，墙钟行为不是。真实 Redis / 云端额度服务在本项目里不做。

## 常见翻车点

**一、把盘点时手算的总数写进断言，然后被真实数字打脸。** 本批真实发生：A 线第一条断言写成 `totalBytes === 160996`，跑出来是 `✘ A 语料是真实文件且字节数与磁盘一致 ｜ 合计 159045 B`。160,996 是我早先在另一处统计里抄来的数，磁盘上的真实值是 159,045。修法不是把常数改成新数字，而是**改成逐文件与磁盘 stat 大小对照**（`d.bytes === statSync(d.path).size`），从此这条断言在语料变动时仍然有意义。判据：任何写死在断言里的合计值，都必须能说出它是从哪次运行抄来的。

**二、重复变量声明让脚本连跑都跑不起来。** 本批真实报错原文：`SyntaxError: Identifier 'rows' has already been declared`（`project-kb-corpus.mjs:238`），原因是我改脚本时把 `const rows = [];` 粘了两遍。它的教训比报错本身值钱：**先让它跑起来，再谈断言内容**；而这类错误的修复必须是删除重复声明，不是把断言注释掉。

**三、切分器产出 1 码点的块。** 现象在 A1 那行：`最短块=1 码点`。原因：某个小节只有标题没有正文。危害：它进倒排索引占位、占一个 top-k 名额、进提示贡献 1 个字符的上下文。确认方法：`SELECT doc_id, chunk_no, chars FROM chunks ORDER BY chars LIMIT 10`。修法：加下限，短于阈值的块并进邻块或整批拒绝。

**四、把「取消」和「超时」记成同一个结局。** 现象：会话表里只有一列 `success`。原因：两者在客户端看起来都是「没收到 [DONE]」。后果：你无法回答「用户主动停止」占多少（那是正常行为，不该报警），也无法知道「超时那次的副作用状态未知」要不要重试——把 timeout 当 cancel 处理，重试可能重复扣费；把 cancel 当 timeout 处理，你开始给自己发告警。修法是两列：`stop_reason` + `effect_state`。

**五、只在成功出口做脱敏。** 现象：`gate` 之后一切正常，但上游报错时你把上游原文转述进了 500 响应的 `detail`，密钥就在那段原文里（B4 那行 `含密钥形态=true` 说的就是它）。确认方法：给错误分支单独写一条断言，检查响应体里 `sk-` 形态计数。修法：错误出口与成功出口调用同一个函数，且这个函数在 `gate.mjs` 里唯一。

**六、空相关集被当成 0 分进汇总。** 现象：全 24 条 `hit@3=0.833`，正常类单独算 1.000，于是有人写下「hit@3 从 1.000 掉到 0.833，回滚」。原因：无答案与注入类的分母为 0——[第 7 章](/ai-apps/rag-quality)那组 `NaN` 与 0 的三种记法（0.444 / 0.333 / 0.375）就是这个坑的形状。修法：空相关集返回 `NaN`、汇总前显式排除，并把这两类送去另一条判据：有没有正确说「我不知道」。

**七、由模拟排序的分数推导真实模型的预期。** 现象：模拟榜 `hit@3=0.500`，于是写下「向量检索在本语料上召回不佳」。原因：那个榜用的是词面哈希签名，**它没有任何语义**，输给 BM25 是设计使然。修法是命名纪律：代码、输出、文档三处都写「模拟」；任何要用于判断真实模型能力的结论，只能来自真实 API 调用，而那需要账号（需要真实账号/真实环境）。

**八、让被拒的调用没有下文。** 现象：模型反复提出同一个越权工具，步数一路撞到上限。原因：你在拒绝时没有把失败原因回填进消息数组。实测里这条被写成一条计数断言：`执行数 + 拒绝数 = 回填数`（1 + 5 = 6），审计总行数 10 = 工具 6 + 闸门失败 3 + 循环 1。少一行都有故事。
