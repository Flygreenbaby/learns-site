# 检索的上限在分块那一刻就定了

**事故一**：运维手册按固定 280 码点硬切成 3 块，「需要保留超过三十天的数据要先转成归档」被切成两半，检索命中前半句，模型照半句作答，读起来完全通顺。

## 先分清：RAG 解决什么，不保证什么

RAG（Retrieval-Augmented Generation，检索增强生成）只解决一个问题：**答案在你的文档里，而模型没读过它**。手段是把相关片段放进提示，让模型看着材料回答。它不保证四件事，每件都要别的机制兜底：材料本身正确（文档写错时，检索越准、错答越自信）；模型真的按材料回答（独立的一类失败，归第 7 章）；权限（写错过滤条件就把 private 片段交给 public 用户，边界归[第 10 章](/ai-apps/security-and-abuse)）；完整性（「库里确实没有」与「检索没找到」在候选集上是同一个形状——空集）。

四种手段按「答案存在哪里」和「要不要溯源」选：

| 手段 | 知识放在哪 | 更新一条知识要做什么 | 适合 | 不适合 |
| --- | --- | --- | --- | --- |
| 直接问模型 | 模型参数里 | 做不到 | 通用常识、解释概念 | 内部规则、任何会变的事实 |
| RAG | 你的文档 + 索引 | 重建那篇文档的块 | 文档多到写不进提示、持续变化、要引用来源 | 几十条固定规则、必须 100% 确定的判断 |
| 微调 | 模型参数里（重训进去） | 重新训练一轮 | 稳定的语气、格式、表达习惯 | 单纯「加知识」，成本换不来确定性 |
| 写死规则 / 查表 | 代码或 system 提示里 | 改代码 | 条数少、结构清楚、必须确定 | 条数多、说法多样、要模糊匹配 |

**三条判断问句**：① 答案是否存在于「你会持续更新的文档」里？② 用户是否需要点开看到原文？③ 规则条数是否多到写不进一条提示？三个都答「是」才轮到 RAG。**本站立场：先把它当成一个「带索引、带过滤的文本搜索」做对，再谈语义。**

## 链路九环：只有一环不在你的代码里，新手却只调那一环

| # | 环节 | 典型失效 | 后果出现在 |
| --- | --- | --- | --- |
| 1 | 来源与更新 | 旧版本或已下线文档还在索引里 | 两个版本同时进提示 |
| 2 | 解析与清洗 | 标题层级被压平、表格拉成流水句 | 切分没有边界可用 / 数字规则丢失 |
| 3 | 切分 | 句子被切断，或块过大 | 命中半句 / 预算爆炸 |
| 4 | 元数据 | acl 取值大小写不统一、字段由上传串决定 | 过滤直接空集 |
| 5 | 向量化 | 只嵌正文不带标题；换模型没重嵌 | 专有名词召不回 / 排序无意义 |
| 6 | 索引 | 写入与删除不同步、无版本与存在性字段 | 孤儿块 |
| 7 | 检索 | 用绝对分数当阈值 | 跑题查询照样进提示 |
| 8 | 组装 | 重复块、冲突片段被合并 | 花钱买重复 / 给两个答案 |
| 9 | 生成与溯源 | 引用的 id 其实不存在 | 假溯源 |

九环里只有第 5 和第 9 环由外部服务与模型决定，其余七环都能在你自己的代码里验证——这就是本章实验一个外部调用都不需要的原因。**最常见的错误是把第 5 环当成整条链路**：换 embedding 模型、调维度，而失效其实在第 3、4、6 环。第 2 环是切分质量的上游，一句话交代：清洗只做删除（页眉页脚）不做改写，摘要可以当粗筛用的附加字段，但**正文块必须在**。

## 切分：块大小、重叠与语义边界

同一份语料、两种切法，块大小都是 280 码点：

```text
问题句「哪些备份需要保留超过三十天？」在第 2 章
答案句「需要长期留存的备份要先转成归档并按月合并后再计费。」在第 3 章

定长硬切（maxLen=280，无重叠）   块数 3   每块 [280, 280, 149]   句子被切开 1 条
语义边界切（maxLen=280，无重叠）  块数 5   每块 [124, 152, 161, 133, 135]   句子被切开 0 条
被硬切切开的那句：「跨团队访问要先在工单…」；两种切法都没把问答放进同一块（块0/块1、块1/块2）

语义边界切的块大小扫描（无重叠）
  maxLen=140  块数  7  平均块长 100  切开 0  问答同块 否
  maxLen=280  块数  5  平均块长 141  切开 0  问答同块 否
  maxLen=560  块数  5  平均块长 141  切开 0  问答同块 否
```

- **硬切唯一确定的后果是切句子，而切在哪取决于编码口径**：按字符切与按 token 切给出不同切点，换一家服务，昨天「刚好没切到关键句」的参数今天就切到了。
- **语义切在任何块大小下都不切断句子**（句子不可分），代价是块长短不均、块数变多。
- **块大小不是连续可调的旋钮**：块数从 7 降到 5 就停住，因为 5 是章节数——语义切至少产生「每个边界一块」，maxLen 超过一整节后继续加大不再减少块数，只是让每块恰好等于一节。**主旋钮是选哪一层边界**（章 / 节 / 段 / 句）。
- **问答跨块在两种切法下都发生**：「检索不到答案」有时不是语义能力问题，而是答案与问题不在同一个可检索单元里。

```text
overlap=  0   注入总量  705 码点   重复字符   0（ 0.0%）   被重复句子  0 条
overlap= 40   注入总量  865 码点   重复字符 101（11.7%）   被重复句子  4 条
overlap= 80   注入总量 1025 码点   重复字符 266（26.0%）   被重复句子 10 条
overlap=140   注入总量 1249 码点   重复字符 466（37.3%）   被重复句子 18 条
（块数固定 5；问答同块在这四档下全是「否」）
```

**重叠加到 140 也没有让问答进同一块**，而注入总量已接近语料净字符的两倍。原因：重叠搬运的是「前一块的尾部」，而问题句在那一节的**开头**。它治「一句被边界切断、上下文缺半句」，治不了「问答隔着整整一节」——后者要靠整节入库或父文档检索，本章先把两种病分清。重叠还有个副作用：同一段文本以两个块 id 入库，见下一节。

## 嵌入与相似度：把「像」当成「对」的危险

Embedding 只做一件事：把文本映射成固定长度向量，使（在该模型的训练目标下）语义相近的文本夹角相近。三条工程后果：**① 查询与文档必须落在同一向量空间**，换模型 = 全库重嵌；新旧向量混在一列里排序没有含义，而它不报错、只会安静变差，所以模型版本要进元数据。**② 余弦对向量长度不敏感**，只衡量方向——「降级」一节会看到这条数学事实的工程后果。**③ 分数的绝对值不是概率**：0.976 不代表 97.6% 的把握，同一份手填向量下 24 个分数最小 0.070、最大 0.998、跨度 0.928，换一家模型这整段区间会平移或压缩。

选型时**必须自己去当期文档查清、本站一律未核实**的清单：维度、最大输入长度、中文与专有名词支持、是否区分查询侧与文档侧两种输入角色、批处理上限、计价口径（按 token，见[第 4 章](/ai-apps/context-and-cost)）。本章不写其中任何一项的数值或参数名。

同一批候选、两种排序口径的前三：

```text
q1 同义改写「线上库要长期留存的数据怎么处理才省钱」
  向量榜 c3:0.976  c4:0.970  c5:0.891 ｜ 关键词榜 c1:0 c2:0 c3:0（词面命中 0）
q2 专有名词「acme-backup-3 这个桶在哪个区域」
  向量榜 c5:0.995  c2:0.946  c3:0.933 ｜ 关键词榜 c5:1 c1:0 c2:0（命中 1）
q3 数字规则「备份到底留多久」
  向量榜 c3:0.998  c5:0.972  c2:0.935 ｜ 关键词榜 c3:1 c1:0 c2:0（命中 1）
```

**这两张榜只证明「两种口径给出的候选会不一样」**：向量是我手填的，任何关于「向量更懂语义」的结论在这里都不成立。但有一条结构性事实和向量内容无关，可以直接抄进代码审查清单：**关键词榜在全 0 命中时排序退化**——q1 三个候选都是 0 分，谁排第一完全取决于数组遍历顺序。用户换个说法、词面一个都不中时，关键词检索仍会信心满满返回三条无关块，而它们的顺序是随机的。**空命中必须显式判空，不能靠「分数低」体现。**

能给的适用结论只到这一层：关键词擅长专有名词、编号、精确字符串（q2、q3 两边命中同一条），向量擅长词面不重合的自然问法。**混合检索的分数怎么归一与融合、要不要重排本章不写**——那是第 7 章的主题，且它需要的真实评测数据本机造不出来。

## 存到哪里：pgvector 的形状与索引一致性

主线用 PostgreSQL + pgvector 的理由只有一个：**复用你已有的运维能力**。备份、权限、连接池、迁移、慢查询排查你都已经会了；块文本与向量在同一行，元数据过滤和向量近邻查找能在同一条 SQL 内完成，不用把 id 搬到第二个系统再搬回来。代价是一个库同时承担业务事务与向量检索，索引构建与写入放大抢同一套资源；扩展安装与索引选择归[数据库领域](/database/postgres-features)。**本章不写任何扩展的类型名写法、操作符名、索引类型名、参数名、维度上限或默认值**——本批 0 次外部核实成功，而这些恰好是它变化最快的部分。下面只给**形状**，且未在本机执行：

```sql
-- 形状示意，不含可照抄的扩展参数名。建表前按当期官方 README 逐项核对。
CREATE TABLE doc_chunk (
  id            bigserial PRIMARY KEY,
  doc_id        text      NOT NULL,   -- 哪篇文档
  chunk_no      int       NOT NULL,   -- 第几块
  ver           int       NOT NULL,   -- 版本，重建时递增
  section_title text,                 -- 所在章节，进提示时一起带
  char_start    int,                  -- 原文码点偏移，供「点开看原文」
  acl           text      NOT NULL,   -- 由代码写入，不接受上传路径原始串
  deleted_at    timestamptz,          -- 软删；检索必带存在性条件
  embedding     vector,               -- 类型名与维度写法刻意不写死
  text          text      NOT NULL
);
CREATE UNIQUE INDEX ON doc_chunk (doc_id, ver, chunk_no);
```

三个字段决定一致性事故能不能被发现：`doc_id + ver + chunk_no` 让「同一篇文档同时存在两个版本」变成一条可查询的记录，`deleted_at` 让孤儿块可查，`char_start` 让引用可核验。三类事故在同一份合成索引上的形状：

```text
索引里现存 5 条块（含 1 条来自已下线文档的孤儿块）
未做版本过滤：top-3 = c3@v1, c3@v2, c9@v1
   → 同一事实的两个版本同时进提示（三十天 / 九十天），第 3 名是孤儿块
加 ver=最大 的过滤后：top-3 里同一事实的版本数 = 1，但孤儿块仍在候选里
重叠带进来的完全相同文本：c2@v1 与 c4@v1，重复 26 码点
```

- **改版**：写入与删除必须在同一事务，或用「当前版本指针」原子切换。「先插新版、再删旧版」在两步之间崩溃就留下两个版本，而唯一约束里 ver 不同、**天然允许共存，所以它不报错**。
- **删除**：版本过滤挡不住孤儿块——c9 的 ver 也是它自己那篇的最大值，「只取最大 ver」对它完全无效。**存在性过滤与版本过滤是两件事**；缺「文档仍然存在」这条，删掉一篇文档后它的内容还会被检索到，而且排序可能很靠前。
- **重复**：同一段文本以两个 id 入库，两个候选名额被一段信息占掉、这一段被计费两次。按文本哈希去重是一种做法，但同一句话出现在两个上下文里本来有不同检索价值，去重会抹掉它——本批未测孰优。

## 检索：过滤、候选数与预算是三件不同的事

**过滤条件缩小候选集，而空集有两种完全不同的原因。**

```text
无过滤                        候选 8 / 8   c1,c2,c3,c4,c5,c6,c7,c8
acl='public'                  候选 4 / 8   c1,c2,c3,c4
acl in [public,staff]         候选 6 / 8   c1,c2,c3,c4,c5,c6
acl='public' 且 team='ops'     候选 2 / 8   c1,c3
acl='Public'（大小写写错）       候选 0 / 8   空集
acl='staff' 且 ver=1           候选 0 / 8   空集
```

两个 0 病因相反：`'Public'` 是**字段里根本没有这个取值**（写错），`acl='staff' 且 ver=1` 是**各条件单独都有解、交集为空**（库里真没有）。必须能区分，否则一个过滤 bug 会以「你的文档里没有这个问题的答案」的面目出现，然后降级分支把编造的机会交给模型。诊断形状：命中空集时**立刻用同一个字段去掉其余条件再数一次**——单独计数为 0 是取值问题（该报警），非 0 是交集为空（真实缺失，走降级）。纪律一条：`acl` 这类字段必须由代码以枚举常量写入，不能由上传路径的原始字符串决定（攻击面归第 10 章）。

**top-k 是候选池，不是「进提示的条数」**：先用较大的池加过滤拿到候选，再按预算与去重结果挑出进提示的几条。写成同一个 `topK` 变量的系统，没法在「多看几条」和「少花钱」之间做选择。重排能提升挑选质量，但要多一次模型调用，归第 7 章。

**块大小与 k 共同决定信噪比**（「有效占比」= 与问题直接相关的那两句字符 / 注入总量）：

```text
maxLen=140  块数  7  取 3 块注入  184 码点   有效占比 23.4%
maxLen=280  块数  5  取 3 块注入  446 码点   有效占比  9.6%
maxLen=560  块数  5  取 3 块注入  446 码点   有效占比  9.6%
top-k=1  注入  152 码点  有效占比 28.3%   ｜ top-k=3  注入 446  有效占比 9.6%   ｜ top-k=6  注入 581  有效占比 7.4%
```

这就是「块为什么不能无限大」的答案：**不是因为窗口装不下**（窗口与单价口径在[第 4 章](/ai-apps/context-and-cost)），而是每多带一块都在稀释——从 top-1 到 top-6 注入量涨到 3.8 倍而有效占比跌到约四分之一。同时注意 top-1 的 28.3%：信噪比最高的配置恰恰是**只带一条、答案错了毫无补救**的那个。这一拉一对是 RAG 的核心取舍，本章量化成比值，第 7 章教你用真实评测决定落在哪一端。另外，多轮对话里这一段每轮都要重发（[第 1 章](/ai-apps/llm-api-basics)那个「第 12 轮单次输入是第 1 轮的 61.0 倍」），**注入预算要乘轮数**；而检索片段通常是每轮里最大且最不变的一段，这也是它适合放在公共前缀位置的原因（前缀与缓存归第 4 章）。

## 组装上下文：来源信息必须和文本一起下去

进提示的每条片段带这六样：**稳定块 id、文档名、章节标题、块序号、版本号、原文定位**。id 让程序校验模型引用的到底存不存在，文档名与章节让用户判断来源可信不可信，版本号让一次回答能追溯到具体一版文档。缺一样，「可溯源」就降级成一句文案。第二条纪律：**这些是待引用的数据，不是要遵从的指令**——[第 10 章](/ai-apps/security-and-abuse)实测过「字符串里没有任何来源标记，信任级别必须带外保存」，而检索片段是别人写进你文档的内容，在提示里它和 system 提示是同一种东西（字符串）。资料区的分区写法与呈现格式归第 7 章，防注入实测归第 10 章，结构化消费的 schema 与四级闸门归[第 5 章](/ai-apps/structured-output)；本章只要求**引用 id 的合法性可以用代码判**（那个 id 在候选池里吗、它指向的片段里能不能找到那句话），判据做成指标归[第 9 章](/ai-apps/evaluation-and-observability)。

## 检索不足与片段冲突时的保守分支

**绝对阈值拦不住「库里没有相关内容」这件事。**

```text
q1 相关查询（权重与备份、计费同向）      top1=0.976  top2=0.970  最差候选=0.070
q4 跑题查询（四维都填 0.02~0.05）      top1=0.749  top2=0.718  最差候选=0.360
q5 对照查询（只填部署一维，库里确有部署内容） top1=0.995  top2=0.126  最差候选=0.000
设阈值 0.55：三条全部「不触发」，都直接进提示
```

q4 是故意造的「谁都不像」的查询，向量长度只有 q1 的几十分之一，但**余弦把长度除掉之后，它与最低权重候选仍有 0.749 的相似度**。「最高分低于阈值就拒答」在没有真实分数分布时可移植性为零：定在 0.55，跑题查询过得干干净净；定在 0.9，那 0.976 与 0.995 之间的差异又意味着什么？你无法回答，因为你不知道真实模型会产出什么分布。**本章不给任何建议阈值数值。** 能给的形状有两个：阈值按你自己的候选分数分布（分位数，而非绝对值）定；而 q5 那种 top1 与 top2 差 0.869 的形状和 q1 那种差 0.006 的形状是两种局面——前者可以放心取第一条，后者应该两条都带进上下文，因为它们实际上没拉开。

三条分支按候选集形状选。**① 候选为空**：先跑「去掉其余条件再数一次」区分病因；真实缺失时的正确输出是「文档里没有相关依据」，并落成可计数的事件，不要靠模型常识补全——那是把 RAG 变回裸问模型。**② 候选有但分布很扁**：带进提示但要求逐条引用，或转人工；判据用 top1-top2 差距与整池跨度。**③ 多条片段对同一事实给出不同取值**，这是唯一必须在合并之前处理的一条：

```text
retention：命中 2 条，不同取值 2 个 → 标记冲突，2 条全部带 id 与来源交给下游
bucket：  命中 1 条，不同取值 1 个 → 单值，可直接用
强行合并的话：按 id 取最新一条得到「九十天」，按候选顺序取第一条得到「三十天」
```

两条都极其合理的实现规则给出两个不同的确定答案，而这不是「哪个更对」——**正确的输出是「这里有冲突，需要人确认」**，因为「三十天 vs 九十天」背后通常是旧文档没清、或规则真改过而你没记录。做法是按事实 key 归组、比较取值、组内取值数大于 1 就整组标记冲突并全部保留。冲突片段进提示之后模型怎么办归第 7 章，做成可计数的指标归第 9 章。

## 端到端走一遍：从一份 markdown 到一次可溯源的回答

```text
入库（离线、可重跑且幂等）
  读文件 → 按标题层级解析章节与句子（保留结构，不改写）
  → 按语义边界切块（边界选哪一层 = 主旋钮，块大小 = 次级旋钮）
  → 每块产出 doc_id, ver, chunk_no, section_title, char_start, acl, text
  → 批量取向量（记录哪一版模型）
  → 一个事务内按 doc_id 删旧块 + 插新块（或原子切换当前版本指针）；删除走软删
问答（在线）
  查询 →（可选）改写 → 过滤（acl + 存在性 + 当前版本）先算候选集
  → 空集 → 诊断查询区分「取值错」与「真没有」→ 分支①
  → 近邻检索取候选池（k_pool > k_prompt）→ 文本去重 → 冲突检测 → 分支③
  → 按预算挑 k_prompt 条 → 组装带 id 的资料区 → 生成
  每次落一行：查询、候选 id 与分数、过滤前后条数、是否空集、是否降级、最终引用 id
```

最后那行日志是本章全部的「可观测」要求：它是**基本现象**，不是指标。「候选被过滤掉多少条」「空集走了哪条分支」「冲突发生过几次」是排查这条链路最先要看的三个数；它们的算法、分母口径、显著性与门禁归[第 9 章](/ai-apps/evaluation-and-observability)，本章不提前展开——判据要真实模型与真实语料才有意义，本机给不了。

## 常见错误与排查

**1. 现象：换了 embedding 模型，效果变差但没有任何报错。** 原因：新旧向量混在同一列，不在同一个空间，比较结果没有意义。怎么确认：按模型版本字段分组数向量列里有几个版本，多于一组就是它。怎么修：模型版本进元数据，切换时全库重嵌并原子替换，绝不增量混用。

**2. 现象：文档里明明有答案，回来的三条都不相干。** 原因：先查切分而不是查模型——答案可能与问题跨节（本章两种切法都同不了块），或结构在解析阶段被压平。怎么确认：打印命中块原文与「答案句在哪一块、邻居是谁」，再抽查 10 个块。怎么修：把切分层级从句子提到小节或整节，或让每块带章节标题参与嵌入。

**3. 现象：用户换个说法就查不到，用原文关键字能查到。** 原因：只有词面重合一条路，而关键词榜全 0 命中时仍返回候选（本例三个候选都 0 分），看着「有结果」其实是退化。怎么确认：打印词面命中数，为 0 时看排名是否由数组顺序决定。怎么修：显式判空而不是判分数；两种口径都要，融合归第 7 章。

**4. 现象：加了权限过滤后，一部分问题变成「文档里没有相关内容」。** 原因：过滤写错导致空集，而空集被当成真没有（本例 `'Public'` 返回 0 条）。怎么确认：跑「只带该字段、去掉其余条件」的诊断计数，0 是取值问题、非 0 是交集为空。怎么修：枚举常量由代码写入，两种空集分开报警。

**5. 现象：回答里出现两个矛盾数值，或一条已废止的规则。** 原因：旧版本块或已下线文档的块还在候选里（本例未过滤时 top-3 同时含 `c3@v1`、`c3@v2` 与孤儿块 `c9@v1`）。怎么确认：按 `doc_id` 数 `distinct ver`，按存在性数孤儿块条数。怎么修：版本与存在性是两条独立过滤条件，都要加；重建走单事务。（overlap 涨了账单却没换来效果，回「切分」一节看注入总量与净字符的比值。）

<template #answer>

**（3）** 用 `doc_id` 与 `ver`：`SELECT doc_id, count(DISTINCT ver) FROM doc_chunk GROUP BY doc_id HAVING count(DISTINCT ver) > 1`，结果集应恒为空，非空就是事故清单。再配一条存在性检查（`deleted_at` 非空却仍可被检索）。两条不能合并——**版本过滤挡不住孤儿块**。

**（4）** 两种：① 同一事务内删旧 + 插新；② 插入 `ver+1` 后用一条更新原子切换文档表上的「当前版本指针」，检索必须带该指针。两者要保证同一件事：**任何时刻都不存在两个都被视为「当前」的版本**，且这条不变量要能用一条 SQL 验证——不能验证的不变量就是没有不变量。
