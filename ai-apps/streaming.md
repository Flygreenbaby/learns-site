# 流式响应与前端渲染：模型还没说完，你就已经开始显示它了

你已经在请求里打开了流式开关，前端也用了 `fetch`，屏幕上还是那副老样子：**等了十七秒，一个字没有，然后整篇回答一次性蹦出来。** 你以为是模型没流式，其实是代码拿到流之后做的是 `await res.text()`——把流读完再开始渲染，等于花了流式的全部复杂度买了原来那个结果。

第二种更难查：中文回答里每隔几个字冒出一个替换字符方块（U+FFFD），或者半句话的最后一个字变成问号。同一个响应，复制到别处显示是好的，只有逐字渲染时坏。这是**一个汉字的三个字节被切在了两个数据块之间**，本批在本机复现出了它，三个替换字符，一次不落。

第三种是「偶尔少了最后一段」：回答明明生成完了，界面上少了尾巴，日志里没有任何错误。一条 SSE 消息必须由空行结尾才算派发完成（线格式在[实时通信第 3 章](/realtime/sse)已逐字段核实），而连接结束时你的缓冲区里还留着几个永远等不到那个空行的字节——本批实测到 **18 个字节**，刚好是一个没写完的事件。

第四种最贵：用户按了「停止」，界面干净了，但那半截回答消失了，而账单仍然按整篇计。

这四件事的共同点：都发生在「模型 API 的字节已经到你手里」之后。传输本身归[实时通信 · 与 AI 流式输出的关系](/realtime/ai-streaming)；**本章只管事件解析、前端消费、停止按钮的完整行为，以及应用层错误处理**，两份刻意不重复。

## 本章默认的最小契约（一句话版，展开见第 1 章）

流式建立在「一次调用长什么样」之上。调用封装、角色分工、密钥管理、失败分类归[本领域第 1 章](/ai-apps/llm-api-basics)，历史裁剪与成本归第 4 章，这里只用一张表把本章代码要用的那几条补到能读懂的程度：

| 事实 | 对流式的影响 |
| --- | --- |
| 对话 API 收的是**消息数组**，角色分 system / user / assistant | 增量拼出来的是一个 `assistant` 消息，它得原样回到数组里才能继续对话 |
| API 本身**无状态**，多轮靠客户端全量重发历史 | 「继续生成」不是续传，是新的一次完整请求：历史又发一遍、输入 token 又付一遍 |
| 一次调用换一整段响应，流式只是把这段拆成增量送达 | 「打开流式」不改请求结构，只改响应怎么读 |
| API Key 只能待在你的服务端，所以上游失败还要能分类（认证 / 限流 / 配额 / 超时 / 内容问题） | 前端不能直连厂商，链路必然多一段转发；分类错了就出现「429 被显示成一条空回答」，见错误处理一节 |

## 先把认知修正：流式买到的只有首字延迟

[实时通信第 10 章](/realtime/ai-streaming)量过这件事：同样 40 个 token、总耗时固定约 1.3 s，只改「几次产出一 `enqueue`」，首块时刻就从 30 ms 退到 263 ms 再退到 1294 ms，**总耗时一毫秒没变**。三个产品判断由此而来：**收益大**的是长回答（用户读三分钟而不是三秒）、可以中途止损、需要生成期间的进度感；**收益小甚至为负**的是短回答，以及**必须拿到完整结构才能渲染的东西**——表格卡片、一段 JSON、一组带编号的选项，逐字显示只会让它们在屏幕上畸变，这类需求该走结构化输出（本领域[第 5 章](/ai-apps/structured-output)）；**超时预算不能因为「流式了」就缩短**，改善的只是第一个字节的时刻，按总时长设的网关或前端超时照样会掐。

## 事件解析：三段流水线上最容易写错的一段

从字节到用户可见的文字，中间是三次转换，每一次都有自己的坑：数据块的切分点你控制不了、UTF-8 多字节字符会被切开、事件的结束标志是空行而不是块边界、而最后一个增量字段的名称是厂商相关的（本章不写）。

先看不负责任的写法为什么「在你机器上能用」。这是最常见的三行实现：每个数据块独立解码、独立按空行切、独立 `JSON.parse`：

```js
// 错的写法（但它经常看起来是对的）
for await (const chunk of resp.body) {
  const text = new TextDecoder().decode(chunk);          // ① 每个 chunk 独立解码
  for (const part of text.split('\n\n')) {               // ② 假设块边界就是事件边界
    if (!part.startsWith('data:')) continue;             // ③ 不以 data: 开头的碎片被静默丢掉
    const payload = part.slice(5).trim();
    if (payload === '[DONE]') continue;
    append(JSON.parse(payload).delta);                   // ④ 半截 JSON 直接抛
  }
}
```

本批把一条 554 字节、21 个事件的合成响应按三种不同边界切碎喂给它，实测结果（同一脚本，逐字输出）：

```text
[逐字节切分（最坏情况）] chunk 数=554
  朴素：还原 0/50 码元，派发 0 个事件，碎片被静默丢掉 554 段，parse 抛错 0 条
  状态机：还原 50/50 码元，与期望逐字一致，收尾残留 0 字节

[随机 1~40 字节切分] chunk 数=26
  朴素：还原 4/50 码元，派发 3 个事件，碎片被静默丢掉 28 段，parse 抛错 10 条 → 首条原文：
        SyntaxError: Expected ',' or '}' after property value in JSON at position 13 (line 1 column 14)
  状态机：还原 50/50 码元，与期望逐字一致，收尾残留 0 字节

[恰好按事件边界切分] chunk 数=22
  朴素：还原 50/50 码元，派发 21 个事件，碎片被静默丢掉 0 段，parse 抛错 0 条
```

最难堪的是第三行：**块边界恰好等于事件边界时它完全正确**，于是本机 loopback、响应体小、上游写得慢三个条件凑起来，就能让它稳定运行几周。那类报错说的也是 JSON 被截断，不是你的 JSON 写错了——看到 `Expected ',' or '}' after property value` 就该去看分块边界。

<Callout type="verified" title="本批实测环境与范围">

Node v25.4.0 / Windows，2026-10-21，命令 `node ai-apps/.scratch/stream-parser.cjs`，零依赖（只用 `TextDecoder`、`ReadableStream`、`AbortController` 等内置全局对象）。范围：验证的是「跨块解析与中止的形状」，样本是本站构造的合成流，**没有验证任何厂商的真实响应形状**。

</Callout>

正确的最小实现就是一个带缓冲区的状态机——跨块只有一份文本缓冲，只派发「以空行结尾」的事件，剩下的字节留在手里等下一块：

```js
// 实测过的实现（A/C 两组跑的就是它）；onEvent 收到的是 payload 字符串。
export function makeSseParser(onEvent) {
  const td = new TextDecoder();
  let buf = '';
  return {
    push(chunk) {
      buf += td.decode(chunk, { stream: true });        // 关键①：让半个多字节字符留在手里
      let idx;
      while ((idx = buf.indexOf('\n\n')) >= 0) {         // 关键②：只在空行处派发
        const raw = buf.slice(0, idx);
        buf = buf.slice(idx + 2);
        for (const line of raw.split('\n')) {
          if (!line.startsWith('data:')) continue;       // id:/event:/注释行都走这里
          const payload = line.slice(5).replace(/^ /, '');
          if (payload === '[DONE]') continue;            // 本站样本的结束哨兵；真实厂商以它文档为准
          onEvent(payload);
        }
      }
    },
    pending: () => buf.length,                           // 关键③：收尾时非零 = 有消息永远等不到空行
  };
}
```

三个关键点里最容易忘的是 `stream: true`。本批把「中文流式渲染」这六个字（18 字节）在第 4 个字节处切开——正好落在某个汉字的三个字节中间：

```text
=== B UTF-8 跨 chunk（"中文流式渲染" 在第 4 字节切开）===
  两次独立 decode："中〔U+FFFD〕〔U+FFFD〕〔U+FFFD〕流式渲染"  出现 U+FFFD 3 个
  带 stream:true："中文流式渲染"  还原=true
```

脚本在那一行原样打印的是三个不可显示的替换字符，上面用 `〔U+FFFD〕` 标出位置，数量与脚本自己统计的计数一致。`U+FFFD`（替换字符）一旦出现就**不可逆**：解码器当场已把它写进字符串，后面再拼回正确字节也补不回来——注意那行输出里「中」与「流式渲染」之间已经没有「文」了，**那个字整个丢了，不是显示成了方块**。所以这个 bug 只有一处可改：`decode(chunk, { stream: true })`，或者用 `TextDecoderStream` 把解码做成流的一环。

然后是被你忽略的那个收尾分支。本批把合成流在 60% 处硬切断，测到：

```text
=== C 连接在 60% 处被掐断 ===
  已派发文本 30 码元（以完整事件结尾），缓冲区残留 18 字节（永远等不到那个空行）
  朴素写法在这段上：还原 30 码元
```

**已派发的部分完全正常，18 字节静静躺在缓冲区里**——这就是「偶尔少了最后一段」的全部机制，而且它在客户端和「连接被中间层掐了」长得一模一样（第 10 章那条不等式）。所以读循环结束时必须问一句 `pending()` 非零吗：非零就是「有内容到了但没成事件」，要上报，不是正常收尾。

## 厂商差异放在哪一层：一张核对清单

各家都把增量装进 SSE 风格的 `data:` 里，但**具体形状各不相同**，而且变得比你想象的快。本批没有核对任何厂商文档，所以这里只给「动手前必须查清的七件事」和去处——查完这七项再写代码，比抄任何教程都便宜：

| 要查的事 | 为什么它决定代码形状 | 不查的后果 |
| --- | --- | --- |
| 怎么打开流式（参数名与取值） | 决定请求封装 | 「加了流式但没生效」，排查一天 |
| 增量文本的字段路径 | 决定 `onEvent` 里取什么 | `undefined` 被拼进文本，界面上出现 `undefined` |
| 结束信号是什么（哨兵字符串 / 具名事件 / 直接关流） | 决定 `pending()` 怎么判 | 把结束当异常，或把异常当结束 |
| 中途错误长什么样（流内事件 / 只有状态码） | 决定错误能否在流内分类 | 200 之后静默无内容，用户看到空回答 |
| 用量（token 数）在哪个事件、结束时还给不给 | 决定成本日志 | 只有估算，账单永远对不上 |
| 是否支持取消，取消是「关连接」还是「调另一个端点」 | 决定「停止」按钮的实现 | 以为停了，实际跑完（第 10 章那张成本表） |
| 事件有没有类型名（线格式里的 `event:` 字段） | 决定要不要按类型分发 | 收到却不处理，表现为「偶发丢事件」 |

核对入口是各厂商官方文档；本领域的做法是**不锁厂商**，所以本章到这一层为止。查完就把差异关进一层适配器：对外只暴露你自己的五种事件（`start` / `delta` / `usage` / `done` / `error`）。这不只是整洁——前端代码、日志字段、评测数据都建立在「事件种类」上，直接用厂商原始字段名，换厂商就等于重写渲染层。用 TypeScript 写这一层时判别联合最贴合（[联合类型与收窄](/typescript/unions-and-narrowing)）：`switch` 收窄后，漏写的分支编译器会替你指出来。

## 前端消费：一份骨架，和三个必须你自己决定的点

```js
// 结构示意（本批未在浏览器中运行）；节流与状态机取值按上面几组实测来定。
const ac = new AbortController();
const resp = await fetch('/api/generate', { method: 'POST', body: JSON.stringify({ requestId, prompt }), signal: ac.signal });
if (!resp.ok || !resp.body) throw await classifyHttpError(resp);   // 先判状态码，见「错误处理」一节
const parser = makeSseParser(handleEvent);
const reader = resp.body.getReader();
let dirty = false, text = '';                    // handleEvent 只做拼接（text += 增量），不碰 DOM
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  parser.push(value);
  dirty = true;
}
if (parser.pending() > 0) reportTruncated();     // ← 别忘了这个分支
requestAnimationFrame(() => { if (dirty) render(text); });   // 攒到帧，不做每片渲染
```

三个必须自己决定的点，按你踩到的顺序排：

**一、渲染节流。** 模型给增量的节奏比你屏幕刷新快，而每来一片就重渲染会随文本变长越来越贵。本批按「800 个增量、每片平均 2.38 码元、总长 1905 码元」算了两种做法的累计解析量：

```text
=== D 增量渲染的算术（800 个增量，每片平均 2.38 码元，总长 1905 码元）===
  每个增量各重解析一次全文：渲染/解析次数=800，累计解析字符量=762,857（约 400 倍全文）
  按帧节流（60fps、生成耗时 1.2s 的算术值）：次数≈72，累计解析字符量≈137,160
```

**每个增量各解析一次全文 = 累计 76 万字符，而全文只有 1905 字符。** 这就是「越到后面越卡」的来源：成本随已生成长度线性增长、再随增量数量线性叠加，合起来是平方；按帧攒一批就把平方项压回线性。**这两个数字是算术不是浏览器实测**，但结论不依赖具体数字：渲染频率要由帧决定，不由到达决定。框架侧对应 [Vue · 渲染性能](/vue/rendering-performance) 与 [React · 重渲染机制与性能](/react/re-render-performance)。

**二、Markdown 还没写完怎么办。** 逐字显示带代码块的回答，你会遇到「语言名刚出来、代码块还没闭合」的时刻。三种策略：

| 策略 | 屏幕表现 | 什么时候选它 |
| --- | --- | --- |
| 每片都按完整 markdown 解析 | 代码块边框闪烁、表格抖动、未闭合的星号原样露出 | 不介意抖动，且文本短 |
| 把未闭合标记当已闭合解析 | 视觉稳定，但解析器要处理残缺结构，实现复杂 | 长文本且要求不闪 |
| **流式期间只显示纯文本，结束后一次性渲染完整结构** | 过程中没有排版，结束后排版出现 | 默认推荐：把「逐字」和「结构」解耦，代价只是最后多一次解析 |

第三行是本站建议，理由不是审美而是复杂度：一边做增量渲染、一边让解析器猜未完成的语法结构，bug 面很大，而用户在这个阶段真正想要的是「它在说话」，不是「排版精确」。

**三、自动滚动。** 跟随最新内容会把用户的阅读位置顶掉。规则只有一条：用户自己向上滚（或光标落在文本里）就停止跟随，并显示「有新内容，跳到底部」的入口——别用「3 秒没滚动就算他没在看」这种猜测。「停止」与关页为什么共用一条路径，是下一节的主题。

## 「停止」按钮到底要做完哪三件事

`AbortController` 是这件事的入口。本批实测过中止之后链路的两种反应（上游共 40 个 token，读者消费到第 12 个时中止）：

```text
  上游不检查 signal：读者消费 12 个后中止；中止瞬间上游已产 12 个，上游走完后累计 40 个（中止后又白产 28 个，跑满 40 才收尾）；读者侧拿到的异常名=AbortError
  上游检查 signal：读者消费 12 个后中止；中止瞬间上游已产 12 个，上游走完后累计 13 个（第 13 次迭代检到中止，主动停住）；读者侧拿到的异常名=AbortError
```

两种情况读者侧都干净地拿到了 `AbortError`，**A 段的断开一模一样，差别全在你看不见的上游那一段**。链路与账单的算法在[实时通信第 10 章](/realtime/ai-streaming)，本章只把「点停止之后要做完的三件事」列全：

1. **停传输**：`ac.abort()`，并把 `signal` 真的传进 `fetch`。少了 `signal`，你只是不再读，请求仍然在跑——就是上面那组「不检查 signal」的形态。
2. **保存已生成的内容**：把当前拼好的文本写库，并**带一个不完整标记**。这一步必须在服务端，不能只写在按钮回调里（下面马上解释为什么）。
3. **切出「生成中」状态**：UI 从 `streaming` 进 `stopped`，输入框可用、按钮变「继续」。停在 `streaming` 是最常见的收尾漏洞，表现是「按了停止但转圈还在转」。

**为什么落库不能在按钮回调里做？** 因为「停止」有四个入口，只有第一个是你写的：点按钮、切后台、刷新、网络断。后三个你的代码里没有按钮，服务端只能从连接的 `close` 发现它们。所以分工是：前端只传 `signal`，**服务端在任何来源断开时把残缺文本连同不完整标记落库**——这条分工同时堵上常见错误④。

用户回来应该看到：带「已中断」标记的残缺文本 + 一个「继续」按钮。**别把「继续」实现成续传**——API 无状态，继续就是把已有文本当前缀再发一次完整请求，**新的一次生成、新的一次计费**。诚实地当新请求写，比假装能续传少一堆边界 bug。

## 应用层错误处理：200 之后才是错误的高发区

先钉住一条本批核实过的事实：MDN 的 Fetch API 页明确说 `fetch()` 在收到响应头时就 resolve，**即使状态码是 HTTP 错误**（2026-10-21）。翻到流式上是一句必须照做的纪律：**碰 body 之前先判 `resp.ok` 与 `resp.status`。** 429 时你照样能拿到一个「可读的 body」，不判就进解析循环，用户看到的是一条空回答——这是本类问题里最典型的误诊。

按「什么时候被发现」分五类，每类都要有自己的出口：

| 类别 | 例子 | 怎么发现 | 用户看到什么 | 日志记什么 |
| --- | --- | --- | --- | --- |
| 请求前 | 401 密钥、429 限流、5xx、DNS/断网 | `!resp.ok` 或 `fetch` reject | 明确失败提示 + 显式重试入口 | 状态码、`requestId`、耗时 |
| 流内 | 上游在增量里夹一个错误事件 | 解析器分发到一个 `error` 事件 | 已有内容保留 + 尾部错误说明 | 事件原文（脱敏）、已生成长度 |
| 传输 | 连接被掐（超时、发布、网络） | `done` 但没有结束事件，或 `pending()` 非零 | 「生成中断」+ 继续按钮 | 断开时刻、已生成长度、残留字节数 |
| 语义 | 长度上限截断、安全策略停住、内容为空 | 结束事件里的收尾信息（厂商相关，本批未核对） | 说明原因，而不是「回答结束」 | 结束原因、输入/输出量 |
| 渲染 | markdown 解析抛错、脏数据把界面写坏 | 渲染函数抛错但流仍在收 | 降级成纯文本继续显示，别让一片脏内容终止整条回答 | 出错片段的序号与长度，不记全文 |

第三类要专门强调：它在**你自己的服务端**也会发生——响应头早发出去了、状态码已经是 200，此后上游出错你**改不了状态码**，只能在自己的事件信封里定义一个错误类型下发（这就是适配器必须有 `error` 那一档的原因）。

还有一条纪律：**不要自动重试一次生成**——重试 = 重新计费 + 内容不一样，要重试就让用户点。如果转发链路里已经有一个「为了稳定性」的自动重试，删掉它，然后去[会话、限流与幂等](/data-storage/session-rate-limit-idempotency)把 `requestId` 唯一索引那套补上；限流与配额的正确出口是 429 加清晰的等待提示，不是偷偷重试。日志字段见[日志与监控](/backend/logging-and-monitoring)：记输入输出的**长度与量**，不要记全文，用户对话内容进日志是一份合规债务。

## 常见错误与排查

**① 开了流式，界面上仍然整段蹦出来。** → 你 `await resp.text()`，或者解析完之后一次性 setState。→ 在 `read()` 返回处打一行日志，看它被调用几次、每次几字节，再看渲染被调用几次。→ 拿到 `resp.body` 就进解析循环，渲染攒到帧。

**② 中文里出现 U+FFFD 方块，或某个字直接丢失。** → `TextDecoder` 没带 `{ stream: true }`，多字节字符被切在两块之间（本批实测：第 4 字节切开后出现 3 个替换字符、「文」字整个丢掉）。→ 拿一段确定的中文，把响应体强制按 1 字节喂进解码函数，看是否复现。→ 加 `{ stream: true }` 或改用 `TextDecoderStream`。

**③ 偶发少最后一段，日志无任何错误。** → 最后一条消息没以空行结束，或连接结束时缓冲区还有字节（本批实测残留 18 字节）。→ 读循环结束后打印 `parser.pending()`。→ 非零就上报「被截断」，并让服务端保证结束事件写完再关流。

**④ 按了停止，半截回答消失。** → 落库只写在成功分支或按钮回调里。→ 刷新页面看库里有没有那行。→ 落库移到「任何来源的断开」统一处理（服务端 `close`）。

**⑤ 一条空回答，没有任何提示。** → 429/5xx 被当成正常响应进了解析循环（`fetch` 不因状态码 reject，本批核实）。→ 打印 `resp.status` 再决定走不走解析。→ 先判 `resp.ok`，把状态码分类成「可重试 / 需等待 / 致命」。如果同一句话还出现了两遍，那是重放问题，归[第 10 章练习 2](/realtime/ai-streaming)。
