# 模型只负责写字，结构化输出是你在自己这边把字变成数据

事故一：`JSON.parse` 抛 `SyntaxError`，消息里那句 `Unexpected token` 后面跟着的是一个反引号。你去看了原始响应，模型给的是三行客套话加一对 ```json 围栏，里面那段确实是合法 JSON。你的代码没有错，你的假设错了——你假设「要求它输出 JSON」等于「它输出的就是 JSON」。

事故二：程序不报错了，但下游开始静默做错事。`paid` 字段的值是字符串 `"false"`，而 JS 里非空字符串永远是真，于是 `if (order.paid)` 走进「已支付」分支；`confidence` 是 `"0.91"`，`confidence > 0.8` 因为类型转换侥幸能用，直到某一天它变成 `"9"`。没有任何一行代码抛异常。

事故三：字段齐全、类型正确，`category` 的值是 `"其他"`——一个你的枚举里没有的值。你的程序接受了它，而「其他」不触发任何通知。两周后你从客服工单里发现这批单子根本没人处理。

事故四最贵：你把模型抽出来的 `buyer` 字段拼进了 SQL 的字符串里。这段合规文字里带了 `' OR '1'='1`，查询返回了别人的订单。OWASP 在 2025 版清单里给这类问题留了独立条目（LLM05:2025 Improper Output Handling），指的就是「输出没有经过足够的校验与消毒就进了下游执行上下文」。

四件事的共同点：**模型输出的永远是文本**。文本要变成程序能放心消费的数据，中间的闸门全在你这一侧，而且是四道不同的闸门——本章把它们分开算。

## 第一道墙是语法，它只管「能不能被 parse」

`JSON.parse` 的判据只有一条：这段字符串是否符合 JSON 语法。MDN 的 `JSON.parse()` 页（本批核实原文）说得很直：不符合语法就抛 `SyntaxError`，数组和对象**不能有尾逗号**，字符串**必须用双引号**。这三句就是第一级闸门的全部内涵。把 13 条合成响应丢进去，卡点分布是这样（真跑输出，节选）：

```text
  1   合规整段      前三级全过        可交给下游
  2   围栏包裹      第1级 语法不过     SyntaxError Unexpected token '`'
  3   客套话前缀     第1级 语法不过     SyntaxError Unexpected token '好'
  4   单引号       第1级 语法不过      SyntaxError Expected property name or '}'
  5   尾逗号       第1级 语法不过      SyntaxError Expected double-quoted property name
  6   类型错       第2级 结构不过      confidence 类型应为 number，实际 string
  7   缺字段       第2级 结构不过      confidence 必填但缺失
  8   枚举外       第3级 语义不过      枚举外值 "其他"
  9   额外字段      前三级全过        可交给下游
  10  被截断       第1级 语法不过      SyntaxError Expected ',' or ']' after array element
  11  空响应       第1级 语法不过      空响应/非字符串
  12  载荷样本      前三级全过        前三级全过，但 note 进 html 上下文会改变语法
  13  原型键       前三级全过        前三级全过，但 键 __proto__ 会改写对象自身
  计数：语法=6 结构=2 语义=1 前三级全过=4 / 13
```

读法有两条。**一，第 10 行和第 11 行的成因不在语法**：截断来自输出长度上限（[第 4 章](/ai-apps/context-and-cost)算过这笔预算，被截断的响应在 HTTP 层是成功的），空响应属于第 1 章那三行「状态码 200 的失败」。只在语法层面排查，你会去改提示词，而真正该改的是长度预算和空内容处理。**二，第 1 级通过之后没有任何结论是免费的**——它只证明「这是一段 JSON」，不证明是你要的那段。

## 契约判结构，业务判语义：三段代码不能互相代替

第一级 `JSON.parse` 就够了，第二级开始要你自己写清「要什么」。示例用一张声明式字段表加一个手写校验器，零依赖（校验库的 API 名与行为差异本站不写，立场同 [TypeScript 的取舍章](/typescript/tradeoffs)）：

```js
export const FIELDS = {
  category:   { required: true,  type: 'string', enum: ['退款', '咨询', '投诉'] },
  confidence: { required: true,  type: 'number', min: 0, max: 1 },
  note:       { required: false, type: 'string', maxLength: 40 },
}

export function check(value) {
  const problems = [], unknown = []
  if (value === null || typeof value !== 'object' || Array.isArray(value))
    return { ok: false, problems: ['顶层不是对象'], unknown }
  for (const k of Object.keys(value))
    if (!Object.prototype.hasOwnProperty.call(FIELDS, k)) unknown.push(k)
  for (const [k, rule] of Object.entries(FIELDS)) {
    if (!(k in value)) { if (rule.required) problems.push(`${k} 必填但缺失`); continue }
    const val = value[k]
    if (val === null) { problems.push(`${k} 为 null（契约未声明可空）`); continue }
    if (typeof val !== rule.type) problems.push(`${k} 应为 ${rule.type}，实际 ${typeof val}`)
    else if (rule.maxLength && val.length > rule.maxLength) problems.push(`${k} 长度 ${val.length} > ${rule.maxLength}`)
    else if (rule.min !== undefined && (val < rule.min || val > rule.max)) problems.push(`${k} 越界 ${val}`)
  }
  return { ok: problems.length === 0, problems, unknown }   // 未知字段：先记录，不直接判失败
}
```

四道闸门的分工就此定死：

| 级 | 判据 | 谁来判 | 典型坏样本 | 失败时的正确动作 |
| --- | --- | --- | --- | --- |
| 一 语法 | 能否 parse | `JSON.parse` | 围栏、客套话、单引号、尾逗号、截断、空 | 先分类再决定修不修（下一节） |
| 二 结构 | 必填、类型、长度、可空 | 你的契约 | 缺 `confidence`、类型 string | 拒绝或带更强约束重试一次 |
| 三 语义 | 枚举闭集、取值关系、业务规则 | 你的业务规则 | `category: "其他"` | 拒绝并转人工，重试无用 |
| 四 出口 | 这段字符串要进哪个执行上下文 | 出口侧代码 | `<img onerror>`、`' OR '1'='1` | 转义/参数化，或改走安全通道 |

第三级是「枚举外值」那一行的来源，也是本章最想让你加代码的一层。枚举必须写成闭集，且**默认分支不能是「接受并继续」**。13 条里第 8 条只被第三级拦住——如果你的 `switch` 用 `default:` 兜底成一个不发消息的分类，它就从「结构失败」悄悄变成了「成功但没人处理」。

## 契约要写到「能拒绝」的程度，否则它只是文档

字段设计六问，每一问都要有答案，缺一个就有一个静默失败：必填还是可空？类型是什么（数字还是字符串）？取值是闭集还是自由文本？数值有没有范围与单位？字符串要不要格式（日期、ID、正则）？数组有没有长度上限、嵌套最深几层？

可空值要区分三态，这三态在本机是三个不同结果：

```text
  字段缺失      stringify={}              'note' in o=false  ??兜底="D"  ||兜底="D"
  显式 null     stringify={"note":null}   'note' in o=true   ??兜底="D"  ||兜底="D"
  空字符串      stringify={"note":""}     'note' in o=true   ??兜底=""   ||兜底="D"
  值是 undefined stringify={}             'note' in o=true   ??兜底="D"  ||兜底="D"
  额外：{count:0} → count||10 = 10；count??10 = 0
        {paid:false} → paid||'未支付' = 未支付
```

三条结论，全部能写成代码规则。一，`||` 会把 `0`、`''`、`false`、`null` 一律换成默认值——用 `??`，或者更好：**让缺失和 null 在契约层就分别失败**，而不是在取值层兜底。二，`undefined` 会被 `JSON.stringify` 整个丢掉键，但 `'b' in obj` 仍是 `true`——「我以为发出去了的那个字段」可以在序列化那步静默蒸发，所以发送前也要跑一次契约。三，`"false"` 与 `false` 在类型检查之前长得一样，布尔字段必须由校验器判类型，别靠 `Boolean()`。

JSON 语法本身还有两个坑，厂商帮不了你，因为它们是实现行为而不是模型行为。

```text
  重名键：{"category":"退款","category":"咨询"} → 本机解析后 category=咨询
  1e400 → Infinity（本机：range 检查 max=1 能拦住它）
  19 位整数 id 12345678901234567890 → 12345678901234567000（尾数被吃掉）
  30 位小数 → 3.141592653589793
  回写：JSON.stringify({confidence: Infinity}) = {"confidence":null}（不报错）
```

RFC 8259 §4 对本机现象只有一句概括，且明确说实现之间不统一（本批抓取原文）：对象内的名字 `SHOULD` 唯一；不唯一时**接收方行为不可预测**——许多实现只保留最后一个名字/值对，有些报错，有些全部保留。§6 建议只发送双精度可表达的数字，并举 `1E400` 与三十位小数为「可能出现互操作问题」的例子。两条硬规则由此落下：**ID、金额、精度敏感的量一律按字符串传**（模型写数字很容易丢位，而你的 `number` 检查拦不住一个已经丢到位的值）；**重名字段不能靠 parse 结果判对错**——要判就得在文本级数键出现的次数，这条检查通常没人做，那就接受「最后一个赢」并在日志里留原始文本。

未知字段策略要显式写出来。默认「忽略并记录」，严格模式在你能承担失败率时再开；但**忽略不等于无害**：`priority`、`sla_days` 这些没声明的键一旦进了你的对象，就可能被后续合并、写库、回显带进别的地方。这里有个本机踩出来的真实缺陷：

```text
  用 k in FIELDS 判未知字段：'__proto__' in FIELDS = true  → 未知字段列表为空
  改用 hasOwnProperty：     Object.prototype.hasOwnProperty.call(FIELDS, '__proto__') = false → 正确报未知
```

原型链上的键会被 `in` 认成「我声明过的」，于是这一条既没进未知字段也没被拒绝。判存在性用 `Object.prototype.hasOwnProperty` 或 `Object.keys` 白名单。

## 模型为什么给你坏 JSON，以及厂商那一层能替你到哪

机制只有一句：**模型是在逐 token 续写文本，不是在序列化一个对象**。它见过大量「JSON 写在 ```json 围栏里、前面带一句说明」的样例，就按那个分布写；你要求「只输出 JSON」是在给分布加权，不是在下命令。由此推出三件工程侧能做的事，都不涉及厂商参数：

一，把格式要求写成可检查断言而不是愿望。「输出 JSON」不可检查，「能被 `JSON.parse` 解析，顶层有 `category` 与 `confidence`，且 `category` ∈ 三个值」可检查（[第 2 章](/ai-apps/prompt-engineering)第一层那条纪律在这里落地）。二，**安排字段顺序**：必填的短字段放前面，长文本和数组放后面。上面第 10 行那条截断样本就是顺序的代价——被截掉的是数组尾巴，前面的短字段全留着，你的程序因此能识别「这是半成品」而不是「这是完整的」。三，给数组和嵌套设上限并在契约里判，否则一条被截断的数组会伪装成一条恰好只有一项的数组。

还有一条反直觉但极实用的判断：**能不用 JSON 就别用**。分类任务要的是三个值之一，让它输出 `退款` 一行比输出一个对象更短、更省（第 4 章的口径）也更难写错；需要结构的地方可以退到「按行分隔的定长字段」这种你能逐行检查的形状。用 JSON 的成本是每次请求多几十到几百字符的格式说明和更长的回答，值不值得取决于下游是不是真的需要一个对象。

厂商层的机制本章不写名称。你该向自己选定的厂商核对这六个问题，答案决定了你代码里要不要那层兜底：

1. 能否强制语法合法？强制后失败以什么形式出现——报错，还是给你一段不合规文本？
2. 枚举、类型、必填、可空能不能在参数里声明？声明之后是「保证」还是「强烈倾向」？
3. 约束与温度之类的采样参数如何互相影响？谁优先？
4. 流式期间约束在什么时候生效？部分结果如何暴露（第 3 章那个「必须拿到完整结构才渲染」的判断依赖这一答案）？
5. 长度上限截断时，约束机制给你一个完整但被剪掉的结构，还是一个坏 JSON？
6. 校验不通过时，账单怎么算？

## 失败处置有四种，代价完全不同

拿到坏输出你只有四个动作，选错的代价分别是：白付一次账单、写进脏数据、把可见故障变成静默故障、把攻击载荷放进下游。

**拒绝**是默认动作：不合式就当失败处理，走第 1 章那个判别联合，把「内容不合规」记成独立失败类。**修补**只适用于「已证明原文属于某个包装形状」的那一类。本机把四个常见修复器丢在四条语法失败样本上：

```text
  剥围栏        √ × × ×   通过 1/4
  截取大括号段    √ √ × ×   通过 2/4
  补齐括号        × × × √   通过 1/4
  单引号换双引号    × × √ ×   通过 1/4
```

「截取大括号段」看起来收益最大。但截断样本（第 10 行）被补齐括号之后：

```text
  parse=true → 第一级通过
  修后对象 = {"category":"退款","confidence":0.91,"tasks":[{"title":"退款审核"}]}
  第二级 ok=true（tasks 记为未知字段） 第三级 ok=true 第四级=tasks 是数组，长度上限未声明
  完整版应是 tasks 条数=3，修补版=1（少 2 条）；sha12 aa53bdfe232d vs b3d0fd86582c
```

修补成功、前三级一路绿灯、少掉的两条任务不会报错，它只是不存在了。反方向也成立：`单引号换双引号` 用在一条本来合法的响应（内含英文撇号 `it's fine`）上，修前能 parse、修后直接抛 `SyntaxError`——修补器对合法内容同样下手。**所以修补的判据不是「能不能让它 parse」，而是「有没有证据表明原文完整、只是被包了一层」**：剥围栏有证据（首尾标记成对），补括号没有。修过就必须在日志里留标记。

**重试**只对第一、二级失败开放，上限一次，第二次带更强约束。代价可以算准（全是构造参数，本机没有 API）：

```text
  输入 1200 字符 / 输出 320 字符；输出按 4 倍输入计价（第 4 章的 r 口径）；更强约束提示多 22 字符（第 2 章实测增量）
  重试上限 1 次：失败率 0.10 → 成本 1.101×；0.25 → 1.252×；0.40 → 1.404×
  重试上限 2 次：0.10 → 1.111×；0.25 → 1.316×；0.40 → 1.565×
  最坏情况（每次必失败、上限 1 次）：上游完成次数 2000，成本 2.009× —— 与失败率无关
```

最后一行是本节的全部要义：**重试上限就是成本上界**。所以预算检查必须放在发送之前，事后统计不叫熔断。第三级（语义）失败不给重试——同一提示同一分布，重试最可能重复同一个错误；至于它会不会变好，本机无法测，任何给你的百分比都是编的。

**降级**要提前设计，且默认值不得触发副作用。三条路按产品选：把原文直接显示给用户并明说「没能自动分类」；转人工队列；或用保守默认值继续走——但「保守」的定义必须是**不执行任何动作**，不能是「按最常见的分类填一个」。`category` 拿不准时填「咨询」看起来无害，如果下游对「咨询」的处理是自动关单，那就是用一次解析失败换来一批错误关单。报错信息必须带**字段路径 + 期望 + 实际**（`confidence: 应为 number，实际 string`），只说「解析失败」等于没报；同时原文片段要脱敏，边界见[第 10 章](/ai-apps/security-and-abuse)。

## 校验通过的字符串，仍然不是可信数据

这是本章最重要的一节，也是前面所有闸门共同的天花板。本机把一条语法合法、结构合式、语义合规的响应喂给四种下游：

```js
const payload = JSON.parse('{"category":"退款","confidence":0.91,"__proto__":{"paid":true}}')
// parse 之后：原型没被改，__proto__ 是一个普通自有键（MDN 注明这是 JSON 与对象字面量唯一的差异处）
const merged = {}
for (const k of Object.keys(payload)) merged[k] = payload[k]
// 逐键赋值之后：merged 的原型被换掉，凭空多出 merged.paid === true
({}).paid   // 仍是 undefined —— 被污染的是这一个对象，不是全局
```

`JSON.parse` 本身在这里是安全的（MDN 明确说 `__proto__` 是 JSON 文本与等价 JS 表达式唯一的不同之处），出事的是你后面那行看起来很无辜的赋值。**同一份契约在 `in` 判据下还把这键当成「我声明过的字段」放过去了**（上一节那个缺陷），所以这条载荷在真实代码里能一路走到合并那一步。修法三层：判存在用 `hasOwnProperty`、拒绝未知键、或用 `Object.create(null)` 承载外部数据。

另外三个上下文，本机只做字符串层面的断言（没有数据库、没有浏览器、没有执行任何命令）：

```text
  SQL 拼接：SELECT * FROM orders WHERE buyer = 'x' OR '1'='1'
            → 恒真片段是否进了语法位置 = true
            参数化形态：["SELECT * FROM orders WHERE buyer = ?", ["x' OR '1'='1"]]
  HTML：     note=<img src=x onerror=alert(1)> → 可执行标签原样保留 = true
            转义后 = &lt;img src=x onerror=alert(1)&gt;（残留 < = false）
  Shell：    note=a; rm -rf / → 命令分隔符是否仍在 = true
```

四条载荷在第 2 节的表里全部落在「前三级全过」那一档：13 条里 4 条通过前三级，其中 2 条是载荷或半成品。**schema 判得出形状，判不出这段合规字符串接下来进谁的手。**所以第四级不属于校验器，属于出口：SQL 走占位符、只绑值不绑标识符（[Web 安全](/backend/web-security)与[原生 SQL](/data-storage/raw-sql-and-drizzle)各实测过一次），HTML 按上下文转义而不是「看起来无害就塞进 `v-html`」（[Vue 模板语法](/vue/template-syntax)讲过 `v-html`），Shell 走参数数组形式。写进 CSV、回显给用户、存库再读出来，都是出口，都要各走一遍。

## 常见错误与排查

**1. 现象：`JSON.parse` 报错，你开始在提示里加「务必只输出 JSON，不要任何解释」。** 原因：把第一级失败当成提示问题。怎么确认：把原始响应头 40 字符、尾 40 字符打进日志（脱敏后）——围栏、客套话、半截结构，三种修法完全不同。怎么修：成对标记的剥掉并记 `repaired=unwrap_fence`；半截的是长度预算问题，回头改第 4 章那套；空内容是第 1 章的独立失败类，不要重试。

**2. 现象：程序不报错，但 `if (x.paid)` 永远为真。** 原因：`"false"` 是非空字符串，而契约没声明类型或校验器没判类型。怎么确认：打印 `typeof` 而不是打印值。怎么修：布尔、数字一律在第二级判 `typeof`，契约里为每个字段写类型；任何地方都不要用 `Boolean(外部值)`。

**3. 现象：字段偶发变少，日志里没有任何失败。** 原因两条，本机都能复现：`undefined` 在 `stringify` 时把键整个吃掉；截断样本被「补齐括号」修好后数组少一项。怎么确认：比较修补前后对象的哈希——本机那条截断样本是 `aa53bdfe232d` vs `b3d0fd86582c`。怎么修：发送前也跑契约，修补必须留标记，数组字段声明长度上限。

**4. 现象：兜底默认值上线后，一批单子被自动关掉。** 原因：解析失败时用了「最常见的分类」而不是「不执行动作」。怎么确认：搜代码里所有 `catch`/`fallback`/`??` 附近有没有会触发写操作的分支。怎么修：默认值只能取「不产生副作用」的状态，并把降级事件记成独立指标（第 9 章要用它）。

**5. 现象：未知字段没被记录，`__proto__` 进了你的对象。** 原因：用 `k in SCHEMA` 判未知字段，原型链上的键被认成已声明。怎么确认：本机跑一句 `console.log('__proto__' in {})`——它就是 `true`。怎么修：`Object.prototype.hasOwnProperty.call` 或 `Object.keys` 白名单，外部数据落到 `Object.create(null)`，能拒就拒（机制同[接口文档](/backend/api-docs)那章的批量赋值事故）。

1. 把 `if (!(k in value))` 那行改成 `if (value[k] === undefined)`。
2. 把必填字段缺失的分支从「记问题」改成「填默认值」：`category` 填 `'咨询'`。

<template #answer>

**改动 1**：`{ note: undefined }` 里 `'note' in value` 为真而 `value.note === undefined`，两种写法对「键存在但值是 undefined」的判定相反（本机在可空三态那张表里跑出过这一对：`stringify` 把键吃掉、`in` 仍报告存在）。用 `=== undefined` 会把「模型真的没给这个字段」和「代码某处把值覆盖成 undefined」并成同一个失败形态，报错定位能力直接下降。
