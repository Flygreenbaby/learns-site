# 认出模式比手写十种算法有用：二分、分治、遍历与 DP 的前提

你在写一个「按时间范围筛选日志」的功能。数据已经在内存里，按时间排好了序。你顺手写了 `for (const row of logs) if (row.ts >= from && row.ts <= to) out.push(row)`，跑通了，提交了。三个月后日志涨到 200 万条，这个接口每次请求都要扫完整份数组，而它其实只需要一个起点下标——**因为数据是有序的，二分查找能在 21 步之内定位它。** 你当时不是不会二分，而是没认出「有序 + 可以按下标跳」这个场景就是二分的入口。

这是第三种失败模式，和前两种不一样：第一种是没学过（第 1–2 章给了结构清单，第 3 章给了估量级的方法），第二种是学过但忘了，第三种是**学的是「算法」这个名词，用的是「模式」这个信号**——教科书教你写二分，是因为题目说「用二分」；真实项目里没人告诉你该用哪个，只有一个形状：输入有序、要找一个边界、每步能排除一半。所以本章不讲「怎么手写十种排序」（那种训练的目标是通过筛选考试，与本站定位不符），讲的是**每组模式成立所需的前提，和前提不成立时的后果**。前提记住了，模式本身就记住了。

有一条纪律贯穿全章：所有数字都是**操作计数**，没有一毫秒（理由见第 3 章：个别运行结果不能冒充普遍结论）。哪些是真跑的、哪些是推演，下面这个框说清了。

<Callout type="info">

**本章证据的三类，读之前先分清。**

- **本机真跑**：以下三组数字来自本批写的 `computer-science/.scratch/op-counts.cjs`，Node v25.4.0 / Windows，2026-10-21，脚本零依赖、不联网、不含计时。二分步数与答对答错（D 组）、图的遍历顺序与跳数（E 组）、递归调用次数与 DP 内层循环次数（F 组）。

## 二分查找：两个前提，一个中点约定

先给真跑的数字，因为它把「快」这件事说得很直白：

```text
在有序数组里找目标，统计「取中点并比较」的执行次数（本机真跑）

  n =       1 000   → 10 步    （log₂ 1000 = 10.0）
  n =   1 000 000   → 20 步    （log₂ 1e6  = 19.9）
  n = 1 000 000 000 → 30 步    （log₂ 1e9  = 29.9）
  n =   1 000 000   找一个不存在的值 → 19 步，结论「没有」
```

30 步是什么概念：10 亿个元素，从头线性扫要 10 亿次比较；二分 30 次。而且**「找不到」和「找到」一样快**——最后一行也是几十步内给出结论，这一点决定了二分能不能用在「校验这个 id 存不存在」的场景上。

但这两个前提缺一个，二分就是错的：

**前提一：数据有序。** 这不是「性能优化」问题，是**正确性**问题。脚本拿一个未排序数组 `[3, 1, 4, 1, 5, 9, 2, 6]` 跑二分，四个目标值的结果是：

```text
  找 1 → 命中（第 3 位，1 步）  判断错误 = false
  找 9 → 命中（第 5 位，2 步）  判断错误 = false
  找 2 → 未命中（3 步）          判断错误 = true   ← 数组里明明有 2
  找 6 → 未命中（3 步）          判断错误 = true   ← 数组里明明有 6
```

注意最阴的地方：**它不报错，而且一半情况下还真给正确答案。** 找 1 和找 9 都对了，因为那两次比较的走向恰好符合有序假设。所以「测了两个用例都通过」完全不能证明二分正确。

**前提二：能按下标随机访问，且访问是 O(1)。** 这是第 1 章那条「连续内存」兑现的地方。数组上 `arr[mid]` 一次拿到；链表上想拿第 mid 个得从头走 mid 步，二分的每一步都退化成 O(n)，整体 O(n log n)，比直接扫一遍还慢。**「有序链表能不能二分」的正确答案是不能**，这个判断不依赖任何性能测试。

第三个坑属于工程层面，也是真跑出来的：

```text
边界收敛实验（本机真跑；200 是脚本设定的迭代上界，不是算法固有次数）

  正确写法（hi = mid - 1）  → ok = true，3 步得到答案
  陷阱：hi = mid（不减 1）  → ok = false，跑到 200 步上界仍未给出答案
  陷阱：命中后只改 lo = mid、不动 hi  → ok = false，同样撞上上界
```

写成 `hi = mid` 时，如果 `mid` 恰好等于 `hi`，区间不再缩小，循环原地踏步。这类 bug 的表现不是「答案差一个」而是**整段请求挂住**，所以在生产里比一般的 off-by-one 更贵。规避方法只有一条：**固定一个区间约定并写进注释**——本站用闭区间 `[lo, hi]`，因此收缩必须是 `hi = mid - 1` 和 `lo = mid + 1`，循环条件 `lo <= hi`。改成左闭右开 `[lo, hi)` 就全配套换一套写法，两种都对，混用必错。**不要凭记忆现场推导边界**，这是二分的真实难点，不是它的时间复杂度。

顺带一个高频用法：不是「找等于」而是「找第一个 ≥ x 的位置」（也就是范围筛选的起点）。它和标准二分的区别只在收缩方向，前提完全一样，同样要求有序。日志那个例子真正需要的就是这个函数，代价约 21 步。

## 排序：记住默认行为和承诺，不背实现

`array.sort()` 是本站见过的用得最多、误解也最多的一个方法。四条已核实的规范事实，每条对应一类真实故障：

**不传比较函数时，元素被转成字符串按 UTF-16 码元顺序比较。** 于是 `[1970, 1980, 2024, 2000].sort()` 得到的不是数值序，而是在比较 `"1970"` `"1980"` `"2000"` `"2024"` 这样的字符串。中文按码元序排也不等于拼音序或笔画序。

**它就地修改原数组，并返回同一个数组的引用。** `const b = a.sort()` 之后 `a` 也被排了——这是「我没改原数组啊」这类 bug 的全部原因。需要保留原序就先 `[...a].sort()`。

**自 ECMAScript 2019（第 10 版）起规范要求排序稳定。** 稳定意味着相等元素保持原相对顺序，这让「先按 A 排再按 B 排」等价于「按 B 为主、A 为辅」，多字段排序可以放心地分步做。

**规范不承诺时间复杂度和空间复杂度**（这是 MDN 中文页面的原话）。所以：**不要在你的代码注释或技术选型文档里写「`Array#sort` 是 O(n log n) 所以没问题」**。你可以合理期待主流引擎的实现是 n log n 级别的，但那是实现事实，不是规范承诺。真要判断你的排序调用是不是瓶颈，用第 3 章的计数思路在真实数据上测。

至于排序算法本身，够用档只需要三句话：

- **比较型排序有个下界：Ω(n log n)。** 你写不出一个通用的、基于比较的、最坏 o(n log n) 的排序。这就是「为什么语言内置的排序是 n log n 而不是更快」。
- **常数因子和低阶项由实现决定，由输入形状兑现。** 第 3 章那张真跑表已经演示过反差：已排序输入上，「更优量级」的归并反而比插入排序多做了 5 倍比较。**所以「数据本来就基本有序」是真实可利用的信息**，工业级排序实现正是靠它（本站没有核实过任何引擎的具体实现，这一句只作为解释方向）。
- **不该在内存里排序的场景，排序就不该在内存里做。** 数据库 `ORDER BY` 有索引可以直接给出顺序，Redis 的有序集合维护着顺序。**「把 10 万行拉到 Node 进程里再 sort」通常是错的**，因为它同时付了传输、内存和 CPU 三份钱，而其中一份本来可以省掉。

## 递归与分治：写下「拆成几份」和「拆多深」

递归代码的正确性审查看两个量，它们对应两种不同的故障。第 3 章真跑过的 Fibonacci 计数表可以直接搬来用：暴力 fib(35) 调用 29 860 703 次，记忆化只要 37 次；暴力的调用次数按斐波那契数列本身增长（核对式 2·F(21) − 1 = 21 891 与 fib(20) 的实测值逐字吻合），记忆化后是 2n + 2。

**调用次数**决定要等多久：暴力版每层分裂成两个子问题、深度为 n，所以是指数级；记忆化后每个不同的 n 只真正计算一次，所以是线性。**栈深度**决定会不会崩：暴力 fib(35) 有 2 986 万次调用，但栈上任何时刻只有约 35 层，所以它慢而不炸；反过来，线性递归遍历 20 万元素的数组会撞上栈上限（第 3 章练习 3 要求你自己跑一次确认），因为它调用次数只有 20 万而栈深度也是 20 万。**这两个量必须分开估，混起来会得出完全相反的风险判断。**

分治的读法就是这两个量的乘与和：把「拆成几份 × 每份规模 × 合并代价」写出来，就能认出四个常见形状——

- 每层拆 2 份、每份规模减半、合并 O(1) → O(n)（如二分）
- 每层拆 2 份、每份规模减半、合并 O(n) → O(n log n)（如归并、快排的平均情况）
- 每层拆 2 份、但每份规模只减 1、合并 O(1) → 指数（如暴力 fib）
- 每层拆 1 份、规模减 1 → 线性时间 + 线性栈深（如线性递归）

**为什么快排「平均 O(n log n) 但最坏 O(n²)」？** 因为「拆成两半」这件事依赖基准选得是否均衡：每次都能把数组分成两半就是 log n 层；每次最差地分出 0 和 n−1 就退化成 n 层、每层线性扫描。这也是第 3 章「最坏情况对应什么输入分布」那条纪律的具体化——**当分区基准由外部输入决定（比如取第一个元素，而用户恰好传了个有序数组），你就把最坏情况交给别人生产了。**

## 双指针与滑动窗口：两个前提，都不是性能技巧

**双指针成立的前提：数据有序，或者问题对「顺序」有可单调推理的结构。** 经典的两数之和中，数组排序后用 `lo`/`hi` 从两端向中间逼近，依据是「和偏大就收右、偏小就放左，被排除的那一侧不可能有更优解」——这个推理**只在有序数组上成立**。数组无序时先排序，而排序把原下标信息抹掉了，所以「返回下标」的题目必须另存原索引。所以双指针的第一步不是写代码，是问：**我能不能让数据变成有序的？变成有序后我丢掉了什么？**

**滑动窗口成立的前提有两个，缺一个就退化成暴力：**

一，**窗口内的统计量能增量维护。** 右端进一个元素、左端出一个元素时，你要能在 O(1) 内更新那个统计量（子数组和、最长无重复子串里的字符计数）。如果每次移动窗口都要重扫整个窗口来得到统计量，那你写的就是 O(n × 窗口长度)，比外层套循环没有更好。

二，**窗口收缩的判据满足单调性。** 「窗口越大越可能违反条件」，因此违规时缩左端是安全的。典型破坏者是**存在负数的子数组和**——加上一个负数可能让和变小，于是「右端扩张不一定让和变大、左端收缩不一定让和变小」，滑动窗口的判据失效，必须换成前缀和 + 哈希表这类思路。**「子数组和为 K」的题有负数时能不能用滑窗，答案是不能**，这一条比任何一个实现细节都更值得记。

本站对「无重复最长子串」这类经典实现没有跑计数，所以这里不给性能结论。用法上的判断标准是：如果你发现自己在窗口里做 `includes` 或重算，就停下来回到前提一。

## BFS 与 DFS：同一张图给出两种答案，只有一种是「最短」

先看图怎么存，因为它决定了遍历成本。脚本用同一张 6 个节点、7 条边的无向图（边：0-1、0-2、1-3、2-3、2-4、3-4、4-5）跑了两种表示：

```text
E 组（本机真跑）

  邻接矩阵：6×6 = 36 个格子；存 7 条无向边要写 14 次；「u 和 v 相邻吗」查 1 次
  邻接表：  7 条无向边存成 14 条表项；遍历全部邻居要走 14 步；「u 和 v 相邻吗」最坏查 3 次（度数最大是 3）

  BFS 访问顺序：0 1 2 3 4 5
  DFS 访问顺序：0 1 3 2 4 5
  无权最短路（跳数）：{0:0, 1:1, 2:1, 3:2, 4:2, 5:3}
```

矩阵和表的选择依据就是这两行：**「判断两点是否相邻」多 → 矩阵 O(1)；「遍历一个点的所有邻居」多 → 表 O(度数)。** 而空间上矩阵永远占 V²，即使图只有几条边——36 个格子对 7 条边，浪费得很典型。实际项目里几乎都用邻接表（`Map<Node, Node[]>`），因为真实关系图通常是稀疏的。

现在到本章最重要的一行结论：

```text
  从 0 走到 5：DFS 找到的路径 0 → 1 → 3 → 2 → 4 → 5，共 5 跳
              BFS 算出的最短距离，3 跳
              （同一条边集，两种答案差 2 跳）
```

**DFS 给你的是「一条能走通的路」，不是「最短的那条」。** 它按深度优先一头扎进去，走到 5 就返回，路上经过的弯完全取决于邻接表里邻居的**存储顺序**——换一下数组里边的顺序，路径就变了，但最短跳数不变。BFS 之所以对无权图给出最短跳数，是因为它按「跳数」一层层扩展，第一次碰到某个节点时用的层数就是它的最小跳数。**这不是「BFS 更快」**——两者都要访问一遍可达节点，工作量同为 O(V + E)；区别是**语义**：一个给「可达性/一条路径」，一个给「最短距离」。

选谁的判断标准也由此而来：

- 问「能不能到」「有没有环」「拓扑顺序」「所有解/回溯」→ DFS（栈或递归，空间 O(深度)）。
- 问「最少几步」「最近的」「按层扩散」（好友二度关系、迷宫最短步数、地图格子、依赖传播层级）→ BFS（队列，空间 O(最宽一层的宽度)，可能很大）。
- **边有权重时两者都不对**，那是 Dijkstra 的领域，本站不在够用档展开；你只需要记住「BFS 只在边权相等时给最短路」。

还有一条必写的东西：**`visited` 集合。** 图上「0-1-0-1…」这种来回是合法的边，不记访问状态就是无限递归或死循环。这是第 2 章「图与树用同一种存储，区别只在有没有环」的兑现点：**树不需要 visited 因为它无环。** 不加访问标记的带环遍历，就是生产里「CPU 打满且日志一条没有」那类 bug。

## 动态规划：只要求你认出它

够用档对 DP 的要求写在领域首页里：**「只到认出这是 DP 问题的程度」**。不需要你构造状态转移方程，需要你能判断「这个需求该不该按 DP 处理、该不该找人帮忙」，因为 DP 的代价在**存储与依赖顺序**上，不在代码行书上。

认它的两个信号，加上一次真跑的数字：

**信号一：暴力递归里有大量重复子问题。** 「递归与分治」一节引用的 fib 计数就是它——暴力 fib(35) 把同一个子问题整份重算了很多很多次，而真正不同取值的 n 只有 35 个。凑钱问题（用 1/2/5 三种面值凑出目标金额，问有几种方案）同一份脚本给了对照：

```text
凑钱：暴力递归调用次数 vs DP 内层循环次数，方案数两边核对（本机真跑）

  目标 10 → 暴力    544 次  vs DP    30 次   方案数 128 = 128 ✓
  目标 20 → 暴力 112 981 次 vs DP    60 次   方案数 26 547 = 26 547 ✓
  目标 30 → 暴力 23 442 475 次 vs DP    90 次   方案数 5 508 222 = 5 508 222 ✓
```

三个金额上两边的**方案数完全一致**——这是 DP 改写的验收标准：**必须证明「少了 26 万倍的操作、答案还是同一个」**，而不是「跑得快了」。DP 那一列计数正好是 3 × 金额（3 种面值 × n 个金额），也就是 O(面值数 × 目标值)，与暴力的指数增长形成鲜明对照。

**信号二：答案可以由「更小的同类问题」拼出来，而这类子问题的总数是多项式有界的。** 「凑 30 分的方案数」可以拆成「凑 29、28、27、25 分的方案数」的组合，而「凑 X 分」只有 31 种取值——**问题总数有限，就值得把结果存下来复用**。这就是记忆化/DP 的本质：**用 O(子问题个数 × 每个的合并代价) 换掉指数级重算。**

于是你需要的判断清单很短：

1. 我先写暴力递归（它最容易想对），**并且用真跑的小数据核对答案**。
2. 打印调用次数。如果「调用次数 ≫ 不同子问题的个数」，那就有重复计算 → 加记忆化，再核对一次方案数一致。
3. 记忆化后仍然太慢，且子问题规模是「区间」「二维网格」这类 → 这时候已经不是「自己改改」的范围，要正式建模状态转移，属于需要专门投入的工作。
4. 内存也要算：记忆化表的大小就是「不同子问题个数」，凑钱是 O(目标金额)，网格是 O(行×列)。**「DP 把指数变线性」这句话后面永远要跟一句「用 O(子问题数) 的空间换来的」**，这是第 3 章空间复杂度的直接兑现。

本站不做的事：不训练你在 20 分钟内现场造出一个 DP。那是刷题档的目标，与你「独立做产品、需要技术判断」的目标函数不一致。

## 从需求形状到模式：一张对照表

| 需求信号 | 先检查的前提 | 模式 |
| --- | --- | --- |
| 「数据按时间/序号排的，要找一个边界」 | 有序、能随机访问、边界约定固定 | 二分（找第一个 ≥ x） |
| 「这个 id 存不存在」 | 同上；否则用 `Set` | 二分 / 哈希 |
| 「列表要按某个字段展示」 | 该字段有没有索引；要不要在内存里排 | 内置排序 / `ORDER BY` / 有序集合 |
| 「两个来源匹配去重，两边都有顺序」 | 能否排序、排序后丢了什么 | 双指针 |
| 「连续区间里满足某条件的最长/最短一段」 | 统计量能增量维护；无负数破坏单调性 | 滑动窗口 |
| 「最少几步能到」「二度关系」 | 无权图；必须带 visited | BFS |
| 「能不能走通 / 有没有环 / 所有组合」 | 递归深度可控；必须带 visited | DFS |
| 「有多少种方案 / 最优拆法」 | 先写暴力并用小数据核对 | 记忆化 → DP |

每一格对应的实测数字与失败后果，在上面的小节里都标了「本机真跑」或「未跑实验」；用这张表做筛选，不要因为它是三列就以为结论也是三条并列。

## 常见错误与排查

**1. 现象：二分「有时对有时错」，测试还过了两轮。**

原因：数组根本无序。真跑的四个目标值里，找 1 和找 9 命中，找 2 和 6 报「未命中」——而数组里两个都有。

怎么确认：断言输入有序再跑一遍（`arr.every((x, i) => i === 0 || arr[i-1] <= x)`），或临时改成线性扫描对比结果。

怎么修：先排序（并确认它不破坏你需要的其他信息），或改用 `Set`/`Map`。**永远不要用「多测几个用例」来确认二分正确**，它依赖的输入分布假设不是靠采样能验证的。

**2. 现象：接口整段挂住，CPU 打满，没有报错也没有超时日志。**

原因：二分的区间不收缩（`hi = mid` 不 -1，或命中后不动 `hi`），或图上遍历没加 `visited` 形成环内死循环。真跑实验里前者撞到了脚本设定的 200 步上界才被发现。

怎么确认：在循环里打印 `lo`/`hi`（或当前节点）；发现区间宽度不再变，就是它。

怎么修：闭区间 `[lo, hi]` 配 `hi = mid - 1` / `lo = mid + 1` / 条件 `lo <= hi`，三件套一起改；图遍历统一用 `Set` 记访问状态。生产代码里给任何 while 循环加迭代上限并在越界时抛错，是这类 bug 的通用止血手段，参见[后端错误处理](/backend/error-handling)。

**3. 现象：`sort()` 之后数字顺序诡异（`10` 排在 `9` 前面），中文列表顺序像乱码。**

原因：不传比较函数时按字符串的 UTF-16 码元顺序比较，这是本批在 MDN 核实到的规范行为。

怎么确认：把元素显式转成字符串跑一遍，看是否得到同样顺序——得到就说明你踩的是默认比较。

怎么修：传比较函数 `(a, b) => a.n - b.n`（数值差只对有限安全数值可靠）；带地区语言的文本用 `localeCompare`（其结果依赖运行环境的 ICU 与语言标签，本站未验证）。

**4. 现象：改动一个字段后「先按 A 排再按 B 排」的顺序不稳定，或复制数组时把原数组一起改了。**

原因：后者是 `sort()` **就地修改并返回同一数组**这条已核实行为；前者涉及相等元素的相对顺序，规范自 ECMAScript 2019 起要求稳定，但你的判断可能落在更老的行为预期上。

怎么确认：`const a = [1,2,3]; const b = a.sort(() => -1); console.log(a === b)` —— 打印 `true` 就是同一个数组。多字段顺序问题：把两次排序换成一次带复合比较的排序，看结果是否变化。

怎么修：需要保留原序就 `[...a].sort(...)`；多字段就用一个比较函数把所有键写全（稳定性让你可以偷懒，但不该依赖它作为语义保证）。

**5. 现象：「用了 DFS 找最短路」，小规模测试看着对，线上路径明显绕远。**

原因：把「能找到一条路」当成了「能找到最短的路」。真跑数据：同一张图上 DFS 到目标 5 跳，BFS 最短 3 跳。

怎么确认：把图的邻接表顺序打乱再跑 DFS，得到的路径会变，而最短路答案不该变——会变就说明你的答案依赖存储顺序，那就是 DFS 而非 BFS。

怎么修：无权图最短路一律 BFS；带权重就要上 Dijkstra 或把计算交给已有的服务/数据库能力，不要自己现场发明。

```ts

function findFirst(arr: number[], target: number): number {
  let lo = 0
  let hi = arr.length - 1
  while (lo <= hi) {
    const mid = (lo + hi) >> 1
    if (arr[mid] < target) lo = mid + 1
    else hi = mid - 1
  }
  return lo
}
```

1. 先跑 `findFirst(data, 55)`，记下返回值；再跑 `data.sort()`（注意它就地修改）之后跑同一个调用，记下返回值和「你调用前保存的那份数组」的状态。

<template #answer>

1. `data.sort()` 之后数组变成 **字符串序**（已核实的规范行为）：`[10, 100, 20, 30, 40, 50, 60, 70, 80, 90]`，**不再有序**（100 排在 20 前面破坏了单调性）。又因为 `sort` 就地修改，你调用前保存的引用指向的也是改过的数组——两个坑一次踩完。此后 `findFirst` 不报错，但行为不可预期。
