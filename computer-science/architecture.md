# 拆不拆服务不是信仰问题，是一道有判据的算术题

「要不要上微服务」这个问题之所以把人卡住，是因为它被当成身份题在答：回答它的人要么在表忠心（「单体就是落后」），要么在复述招聘市场（「我们规模不够，不需要拆」）。两种回答都不能帮你在凌晨两点决定该改哪一处。

把问题换成三个能算的问句，它立刻降回工程尺度：第一，**这次改动要打开几个文件、跨几个目录**——这是结构问题，跟服务数量无关。第二，**如果这一段出问题，我会连带失去什么**——这是故障隔离问题。第三，**如果这一段要单独扩容，我现在能只重启它吗**——这是伸缩单元问题。这三个问句的答案，加上「拆了以后我要新增哪些常驻成本」的清单，就是本章的全部内容。

一个具体的失败现场：订单导出功能同步跑在请求里，一千行 CSV 要转十秒；需求加了一句「导出要能下到一百万行」，于是有人提议把它拆成独立服务。三周后系统里多了第二个进程、一套内部鉴权、一张任务状态表、一条「前端轮询直到完成」的链路，以及一类新故障：任务被领取两次、文件写了一半没人管。**导出慢这件事没解决**，因为它从来不是进程数量问题，而是「到达速率与服务速率不匹配」——那个模式叫队列，第五节算它的账。

**本机实测**（Node v25.4.0 / win32，2026-10-22，脚本 `computer-science/.scratch/arch-boundaries.cjs`，逐字输出留在同目录）：两个互相 `require` 的模块在循环点读到 `undefined` 的导出值、Node 在 stderr 上主动给出的循环依赖警告原文、加载完成后同一对象的键数补齐到 3、正向调用链仍然算出正确金额；ES 模块跨环继承抛出 `ReferenceError` 及栈帧指向的文件与行列；把边界改成「域不认识出口、出口由入口注入」后同一份域代码得到两种货币格式。6 条断言全过，退出码 0。

## 分层回答「谁能调用谁」，分域回答「什么东西一起变」

这两件事经常被混成一个「目录结构问题」，它们是正交的，而且各自防止不同的腐烂。

**层（layer）**是一组权限规则：表现层可以调用业务层，业务层可以调用数据访问层，反向不允许。它防的是「任何东西碰任何东西」——没有它，一个路由处理函数里既拼 SQL 又发 HTTP 又格式化货币，三个月后没人能改动任何一处而不牵动全局。**域（domain/feature）**是一组归属规则：订单相关的路由、校验、状态查询放在一起。它防的是「一起变的东西散在五个地方」。

一个仓库可以同时用这两条规则，而且是本站推荐的形状：**一级目录按域，域内保留固定三层**。

```text
src/
  orders/                 # 域：一次需求几乎只落在这里
    routes.ts             # 层 1：认识 HTTP，不认识 SQL
    service.ts            # 层 2：业务规则，不认识 HTTP，也不认识具体数据库
    repository.ts         # 层 3：唯一会写 SQL 的地方
  exports/                # 另一个域，同样的三层
    routes.ts
    service.ts
    worker.ts             # 域内特有：异步任务的领取与状态
  shared/                 # 只允许放无业务状态的纯函数与类型
    money.ts
    clock.ts
  main.ts                 # 组合根：把 repository 交给 service，只有这里知道全部名字
```

纯按技术分层的形状是 `src/controllers/*`、`src/services/*`、`src/repositories/*` 三堆。它的代价有一个可数的度量：**改一个需求要打开的文件数**（以及这些文件落在几个顶层目录里）。[工程工具与部署 · 代码规范](/devops/code-standards)从写规范的那一侧给出的是同一个判据——「改一个需求要打开的文件数比任何架构名词都更能反映结构好坏」，两侧口径必须一致，否则你会在一边纠正另一边。

这个数不需要工具就能量：翻最近三次真实提交，写下每次涉及的文件数与顶层目录数（Git 仓库里是 `git log -5 --name-only --pretty=format:'%h %s'`，**未在本机验证，需要你自己的项目**）。判读方式本站给得出，你的数字给不出：**同一个需求跨三个以上顶层目录、而那些目录之间只有转发关系，就不是分层的问题，是分域分错了。**反过来，域目录之间大量互相 import，那是缺依赖规则（下一节），不是缺目录。

## 依赖方向是要写下来的东西，不然循环会替你决定行为

「模块之间不许互相知道」这句话太软，能被检查的版本是：**允许 import 的方向表**，加一条能跑的检查。方向表本身可以只有三行：`routes → service → repository`，`shared` 谁都不许向上指，`main` 例外（它是唯一知道所有实现的名字的地方）。

不写下来会怎样，这一节是本章唯一能在本机跑干净的部分。两个模块互相依赖时，加载顺序决定谁看到空壳：

```js
// prices.cjs —— 第一行就进入循环
const fmt = require('./formatters.cjs');
exports.taxRate = 0.06;
exports.net = (gross) => gross / (1 + exports.taxRate);
exports.label = (gross) => fmt.money(exports.net(gross));

// formatters.cjs —— 此刻 prices 的 exports 还是空对象
const { taxRate } = require('./prices.cjs');
exports.rateSnapshot = taxRate;
exports.money = (v) => '¥' + v.toFixed(2);
```

本机跑 `require('./prices.cjs')` 之后的真实输出（临时目录名已抹去）：

```text
=== S1 CommonJS 循环：加载顺序决定谁看到空壳 ===
  prices 完整导出键数=3（taxRate/net/label 都填上了）
  formatters 在循环点抄到的 rateSnapshot=undefined
  调用 prices.label(106) → ¥100.00
(node:21924) Warning: Accessing non-existent property 'taxRate' of module exports inside circular dependency
=== S2 ESM 循环：跨环继承报的是哪一行 ===
  抛错：ReferenceError: Cannot access 'Base' before initialization
  栈里指向的文件：at file:///C:/Users/.../Temp/cs-arch-XXXXXX/derived.mjs:2:30
=== S3 无环版：同一个域代码 + 两个出口 ===
  同一域代码两次注入：净价 ¥100.00 / 净价 100,84 €
```

三行输出里有三个值得记住的事实。第一，**Node 会警告，但警告在 stderr 上，而且不中断执行**——如果你的进程输出没人看，它就等于没有。第二，**症状只在循环点，不在最终形状**：加载完成后 `prices` 的三个键都补齐了，`prices.label(106)` 照样算出 `¥100.00`；坏掉的只有那个「在加载时抄了一份值」的 `rateSnapshot`。这就是循环依赖最难查的原因——**它的调用链大部分时候是对的**。第三，换到 ES 模块，同一类错误变成运行时 `ReferenceError: Cannot access 'Base' before initialization`，栈帧直接指到那一行；两种模块系统给的是不同形状的同一个病因。

把边界改成域不认识出口，环就消失了。不是靠「少用 import」这种自律，而是靠一条机械可查的形状：

```ts
// orders/service.ts —— 域内：只声明「我需要能把金额变字符串的东西」
export const makeOrderView = (money: (v: number) => string, taxRate: number) => ({
  label: (gross: number) => '净价 ' + money(gross / (1 + taxRate)),
});

// main.ts —— 组合根：唯一同时知道域和出口名字的地方
// import { makeOrderView } from './orders/service';
// const view = makeOrderView(cnMoney, 0.06);
```

`repository` 同一形状：`service` 接一个「有 `findOrderById` 方法的东西」，而不是 `import` 一个具体的库连接。这样做的直接收益在本章别处：换出口不用改域文件（本机那次两次注入给出两种货币格式）、测试不用起库、以及最重要的一条——**当某天你要把这一段搬到另一个进程时，需要改的只有组合根**。

## 三种「拆开」是不同的动作，只有第二种开始才改变故障语义

「拆」这个字在架构讨论里同时指三件事，它们的账单完全不同。分开写：

| 边界 | 你在换掉什么 | 立刻得到 | 必须付 |
| --- | --- | --- | --- |
| 模块边界（同进程，函数调用） | 一堆互相 import 的文件 → 有方向的几个模块 | 可测、可替换、改动面可数 | 只是纪律成本；调用失败还是异常，栈是完整的 |
| 进程边界（同机多进程） | 一个进程 → 几个进程（如多进程部署） | 单进程崩溃不全军覆没、CPU 密集与 IO 密集分开 | 进程间通信、共享状态失效、端口与生命周期管理 |
| 网络边界（跨机） | 一次函数调用 → 一次请求 | 独立部署、独立伸缩、团队边界 | 超时 + **未知状态**：调用失败时你不知道对方做没做，于是要重试 + 幂等键 |
| 数据边界 | 一张表 → 各模块自己的真相源 | 各自演进 schema、不被别人的一次改表拖住 | 跨边界查询没有了；「一次业务动作」需要 saga 或最终一致 |

这张表的关键在第三行的**未知状态**。函数调用不会「执行了一半就网络断了」；请求会。你在[操作系统：内存与 IO 模型](/computer-science/os-memory-io)里量过等待的位置，在网络边界上多出来的是「等待结束后对方那边发生了什么仍然不知道」。这条语义变化是所有分布式难点的来源，也是本站对「拆服务」最保守的理由：**引入网络边界，你付的不是运维麻烦，是正确性模型的改变。**

于是「订单导出」那个案例的正确读法就出来了：它需要的是**时间上的解耦**（队列）而不是**空间上的解耦**（新服务 + 新网络边界）。前者在同一个进程里就能做，后者一旦做了就回不去。

## 五种风格：各自解决哪一类瓶颈，各自签什么账

**客户端-服务器**是本站默认形状（[网络：HTTP 演进与 CDN](/computer-science/network-http)讲过它的版本演进）。它解决的问题是「一份业务逻辑，多个前端」；它不解决伸缩与部署耦合，所以别把它当成架构决策的终点。

**单体**：一次构建、一次部署、一个进程内跑完整个业务。它解决的问题是**改动便宜**——跨功能的重构是编译期错误而不是跨服务协议谈判；事务是语言级的；本地调试一条栈就够。它付的是：伸缩单元等于整体（[操作系统：进程与线程](/computer-science/os-process-thread)里那台机器上，一个吃满 CPU 的报表任务会拖慢所有接口），故障共享（一个内存泄漏拖死全部），部署互相阻塞（两个功能的发布排同一条队）。

**模块化单体**：单体的部署形状 + 上面两节的模块边界与依赖方向。它解决的问题是**把「以后能拆」买成期权**——因为拆分成本几乎全部落在「边界有没有」上，而边界是可以在一个进程里维持的。它付的是纪律：边界要靠检查守住，不靠自觉。对一个人维护的产品，这是本站默认推荐。

**微服务**：按业务能力切开的、可独立部署的服务，边界是网络。它真正解决的只有四件事：独立部署频率不同、伸缩单元不同、故障隔离要求高、团队边界与代码边界对齐（这一条对个人项目不存在）。它付的账本单独列在下一小节。

**事件驱动**：动作之间不直接调用，而是写下「发生了什么」，别人自己订阅。它解决的问题是「同一件事有多个后续动作，而且你不想让发起者知道都有谁」，以及「瞬时到达速率高于处理速率」。它付的是最终一致（用户提交后看到的列表可能滞后）、重复投递（所以要幂等）、以及**调试跨时间**——一次错误的原因可能在八分钟前的一条消息里。投递机制的详细账归[消息队列与云服务](/message-queue-cloud/reliable-delivery)，本章只保留「它买的是时间，不是正确性」这个判断。

## 缓存、队列、读写分离：三个模式都在买时间

这三个模式经常被并列成「性能优化三件套」，但它们各自对应上面那张边界表里不同的瓶颈，而且**都不解决正确性**。

**缓存买的是「重复计算的次数」。**瓶颈是同一份昂贵结果被反复要：数据库重复查询、上游接口重复调用、页面重复渲染。它在本站已有三个真实层级：浏览器与 CDN 边缘（[网络：HTTP 演进与 CDN](/computer-science/network-http)）、进程内对象缓存、操作系统页缓存（[操作系统：内存与 IO 模型](/computer-science/os-memory-io)）。账有四笔：失效（什么时候算旧）、击穿（同一 key 过期瞬间被并发打穿）、穿透（根本不存在的 key 每次都回源）、雪崩（一批 key 同一秒集体过期）。判据是一句乘法：**命中率 × 每次省下的成本，是否大于一次错误数据造成的成本**。把缓存当真相源是本节最贵的一类错误，因为它的症状跟本章那个循环依赖一样——**大部分时候是对的**。

它的代码形状小到不必写：一个 `Map` 存「值 + 写入时间」，命中是一行减法，过期就回源；`Map` 的键值语义与代价见[数据结构（二）：哈希、树与图](/computer-science/data-structures-hash-tree-graph)。**真正需要设计的是那四笔账**，尤其是击穿——同一 key 过期瞬间要只放一个请求回源，做法是让并发请求共用同一个进行中的 Promise，而不是各自算。

**队列买的是「时间」：把到达速率与处理速率解耦。**瓶颈是瞬时峰值超过服务能力，或者一个动作要等一件慢事。账：至少一次投递带来的重复（于是需要业务幂等键）、顺序不再自然、排队本身增加延迟（用户等得更久）、失败变得不容易看见（错误落在 worker 日志里而不是接口响应里）。**用它之前必须先量出服务速率**——如果瓶颈是「每单本来就慢」，队列只是把慢变成排长队。

**读写分离买的是「读放大不拖累写」。**瓶颈是报表类长查询占住写路径需要的资源。账：复制延迟导致「刚写完读不到自己刚写的」（这一条会直接变成产品问题，需要「主库读」的例外通道）、故障转移变复杂、路由与连接池管理多一份。

一句话总纲：三个模式的共同形状是**用一层中介换一个瓶颈**。所以每次引入之前问两句话——「它替我挡住的那一段，现在到底排不排？」和「中介坏了以后，我这份数据还能不能算出来？」

## 把「要不要拆」写成一张判据表

信号分三组。值得拆的信号：**部署互相阻塞**（A 功能的紧急修复被 B 功能的未完成测试拖着）、**伸缩单元不同**（CPU 密集的批处理与 IO 密集的接口抢同一台机器）、**故障隔离要求**（一段代码历史上多次把整个进程拖死）。不该拆的信号：只有一个人维护、边界还没稳定（这块逻辑三个月改一次形状）、真正的瓶颈是速率而不是耦合、以及「拆」在提案里的理由只是一个名词。

拆一次的真实常驻成本，列全才有得算（每一项都是长期付，不是一次性）：

- 服务间鉴权与内部凭据轮换
- 每个服务自己的部署、回滚与配置（对照[部署到 VPS](/devops/deploy-to-vps)那一章的一次部署工作量，乘以 N）
- 版本兼容：调用方与被调方的字段演进要能共存两个版本
- 可观测：请求跨进程的关联 id、每个服务各自的日志与告警
- 容量：多份进程常驻内存、多份连接池
- 数据：跨边界查询的替代方案（要么冗余字段，要么一次额外调用）
- 故障：超时 + 未知状态的语义（本节第三节的账）、重试与幂等
- 本地开发：一套能起全部东西的编排（对照 [Docker Compose](/devops/docker-compose)）

一个成本半天、两头都不亏的折中：**先不拆，但把最可能被拆的那块改成「只能通过一个接口被调用」**。真要拆时边界已经在代码里；不拆时你只多了一个接口文件——而这一个接口天然成为观测点，它的调用参数与失败率就是「值不值得独立部署」的证据。

## 决策按可逆性分级，别按难度分级

难度是主观的，可逆性是客观的：改回来的代价。三档：

**高可逆**：内部函数结构、私有模块划分、有适配层时的库选择。当天决定，当天做，不需要论证。**中可逆**：模块边界、进程边界、缓存策略。写一段话，说明触发重看的条件。**低可逆**：数据模型与迁移路径、对外契约（API 字段、消息格式、文件格式）、身份与权限模型。这些必须留决策记录，必须写「我们当时知道什么、否决了什么、什么信号出现时重看」。

这一档的完整评估维度（成熟度、社区、运维成本、与现有栈契合、退出成本）在[下一章](/computer-science/domain-modeling)讲；本章只留一条形状：**低可逆的决策，要把它对外的表面收窄到一个文件**。你的产品与数据库之间隔一层 repository，与隔十层调用同样安全——差别只在改动落点有几个。

```json
{
  "decision": "订单导出走进程内队列，不新建服务",
  "status": "accepted",
  "date": "2026-10-22",
  "reversibility": "中：worker 与接口同进程，改为独立进程需新增生命周期管理",
  "context": ["单次导出中位 12s", "峰值同时 4 单", "机器只有一台"],
  "options_rejected": [
    { "option": "同步导出 + 网关超时放宽", "why": "超时不等式无法守住" },
    { "option": "独立导出服务", "why": "付网络边界与数据边界，收益只有一条部署频率" }
  ],
  "revisit_signals": ["同时导出数持续 > 20", "worker 一次崩溃导致接口不可用"]
}
```

## 常见错误与排查

**一、纯按技术分层，一个需求跨五个目录。**症状：改「订单加上税种」要在 `controllers/`、`services/`、`repositories/`、`validators/`、`types/` 各开一个文件；新手最容易被它骗，因为每个目录看起来都「很整洁」。原因是分域缺失。改法：一级目录按域，域内保留层，`shared` 只收无业务状态的东西。判据回到那个数：改动面里的顶层目录数。

**二、循环依赖，偶发的 `undefined`。**症状：某些路径拿到的值是 `undefined` 或 `NaN`，另一些完全正常；换一下 import 顺序现象就移动。排查：本章那段本机输出就是模板——`Accessing non-existent property ... inside circular dependency` 这条 warning 一旦出现在你的 stderr 上，病因已经确定了。改法：把共同依赖抽到第三个模块，或者改成注入；不要在循环点上「读一次值」，改成「调用时再读」。

**三、把缓存当真相源。**症状：「重启就好了」；「用户说他的余额不对，过一会儿自己对了」。原因是把可变的唯一事实放进了带 TTL 的介质。改法：缓存只放能重算出来的派生结果；状态与金额一类读出来必须准确的字段，走带约束的读路径（对照[数据库](/database/)的事务与隔离级别）。

**四、用队列掩盖容量问题。**症状：接口不报错了，但「处理中」的平均时间从 15 秒涨到 4 分钟；队列长度单调上升。原因是没量服务速率就引入缓冲。改法：先测「一个 worker 一小时能吃多少单」，再决定要几个 worker；队列长度要变成被监控的指标，而不是一个隐藏的水位。

**五、过早微服务。**症状：一次「下单」跨四个服务，测试必须在集成环境跑；本地开发要起 11 个容器；一个字段改名要协调三次发布。原因是把部署单元切在了还没稳定的边界上。改法：退回模块化单体，把边界做成接口；只有本节那张判据表里的信号出现，才逐个搬出去。

**六、`utils` 变成垃圾场。**症状：`helpers.ts` 一千二百行，谁都在改它，改它等于改全仓库。原因是共享的诱惑压过了归属。改法：`shared` 里只允许无状态纯函数与类型；带业务规则的「公共逻辑」必须属于某个域，由那个域对外提供。

**七、抽象早于第二个实现。**症状：为了「将来可能换数据库」写了一个只有 PostgreSQL 实现的接口，读代码时要在四个文件间跳。改法：接口留给低可逆的对外契约；内部的「将来可能」先不做，等第二次出现再抽。这条与上一节不冲突：**边界要早画，抽象要晚做**——边界是「谁能调用谁」，抽象是「用一个泛化名字代替具体实现」。

**八、决策没有记录。**症状：半年后有人问「为什么导出不是服务」，答案只剩「一直是这样」。改法：上面那份 ADR JSON，一年写十份，每份半页。
