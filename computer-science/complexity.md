# 大 O 不是速度，是数据量涨起来之后的形状

一段处理函数在测试环境跑得很顺：几百条记录，几十毫秒。生产上某个租户的数据涨到五万条，接口没有变慢，直接卡死——前端转圈三十秒后超时，Node 进程那段时间 CPU 占满，日志里没有任何错误。排查的人翻遍了依赖和数据库，最后发现问题是函数里一个循环套着一个循环，而且内层那个循环用的是 `Array.prototype.includes`。这是本章要训练的能力：**在写代码的那一刻，就能看出这段逻辑在数据量涨 100 倍之后会怎样。**

另一个常见场面是两个人对同一段代码估出不同结论。甲说「这是 O(n log n)」，乙说「你这里递归调用了两次，是 O(2ⁿ)」，吵完之后各自去查资料，谁也没被说服。原因往往不在于谁算错了，而在于他们把大 O 当成了某种精确的耗时公式。大 O 是一组约定清晰的记号：**它系统性地忽略了决定实际速度的两类东西——常数因子和低阶项。** 所以「O(n log n) 比 O(n²) 快」这句话只有在数据量足够大、且两个算法的常数因子在同一量级时才成立。理解它忽略了什么，比记住一堆量级名字重要得多。

还有一个必须提前说清的偏差：网上大多数复杂度教程会顺手给你一组毫秒数字，「n = 100 000 时冒泡排序用了 4.2 秒，快排用了 0.03 秒」。这类数字看着最有说服力，实际上最不能作为结论——它测的是那一台机器、那一次运行、那一份输入。本章一个毫秒都不会测，所有数字都是**操作计数**：搬移了几次、比较了几次、递归调用了几个函数帧。计数是确定的，同一份脚本同一份输入必然得到同一个数字，你可以逐字核对。

本章的定位是「够用档」：不要求你会证明主定理，不要求你手推递归式，只要求你拿到一段陌生代码能在半分钟内说出量级、拿到一个陌生场景能说出「数据涨 100 倍谁先出问题」。这两件事做到了，第 4 章的算法模式和你才接得上。

## 大 O 是三条约定的合称，不是一个数

把「O(n²)」读成一个数是最常见的误解。它其实是一串省略的结果，三条约定决定了省略了什么。

**约定一：忽略常数因子。** 一个算法每处理一个元素做 50 次操作，另一个只做 1 次，两者都是 O(n)。在 n = 200 这个规模上，前者可能比后者慢 50 倍——这是真实的、可感知的慢。大 O 不管它。

**约定二：忽略低阶项。** n² + 500n + 10⁶ 是 O(n²)。当 n 足够大时前一项压过一切；但 n = 100 时，n² 只有 10 000，那个 10⁶ 的常数项才是主角。

**约定三：它给的是上界。** 严格地说大 O 描述「不超过这个增长速度」，所以一个 O(n) 的算法同时也是 O(n²) 的——这句在数学上没错，日常交流中却会让讨论变得没有信息量。工程上大家默认说的是「紧确的那个上界」，也就是 Θ(n) 的意思，只是口头仍叫大 O。你读别人的分析时按这个默认理解即可。

现在用真跑的计数看这三条约定在现实里意味着什么。同一份脚本里对 n = 2000 的数组跑两种排序，统计的是**比较次数**（这份实现只数比较，不测时间，也不数搬移）：

```text
输入 n = 2000，三种输入形状，两种排序算法，统计比较次数（本机真跑）

  已排序   插入排序    1 999 次   归并排序  10 864 次
  逆序     插入排序 1 999 000 次   归并排序  11 088 次
  锯齿     插入排序 1 001 498 次   归并排序  16 447 次

  三种形状下归并的结果与插入一致 = true
```

这张表值得反复看，因为它一次性推翻了三个粗糙结论。

第一，**「O(n²) 一定比 O(n log n) 慢」是错的**。已排序输入上，插入排序只比较了 1 999 次（正好是 n − 1，它只需要每个元素比较一次），归并排序比较了 10 864 次——**那个「更差的量级」反而少做 5.4 倍**。第二，**逆序输入上两者差 180 倍，锯齿输入上差 61 倍**，同一对算法、同一个 n，差距完全由输入形状决定。第三，归并三档都在 1.0–1.6 万这个区间，波动很小；插入从 1 999 跳到 1 999 000，三个数量级。这就是「最坏情况」和「平均情况」在实际代码里的样子。

那什么时候可以理直气壮地用大 O 做决策？答案是：**当 n 已经大到低阶项和常数项被压过去的时候。** n = 10⁵ 时，插入排序最坏是 5 × 10⁹ 次操作，归并是约 1.7 × 10⁶ 次，差三个数量级，常数因子怎么翻盘都不够。你的产品里「用户能上传多少行 CSV」「列表最多渲染多少条」「一次批量任务处理多少记录」——这些量到了千、万级，大 O 的判断就开始兑现；只有几十条时，选错量级的代价你可能根本感觉不到。**这也是为什么第 1 章反复强调「先问 n 有多大」。**

## 为什么本章不用毫秒当证据

这不是为了省事，是因为用计时下结论这件事本身方法上不成立。一次 `performance.now()` 的差值里混着这些东西：CPU 当前频率与调度、同一台机器上其他进程的干扰、JIT 是否已经预热（前几千次调用和之后是两份代码）、垃圾回收在哪一刻插入、数据是否还在 L3 缓存里。更麻烦的是**缓存效应会随 n 变化而突变**：n = 5 000 时数组整个在 L1/L2 里，n = 500 000 时装不进，于是你会测出一条不是任何公式能拟合的曲线。把「我本机跑出来 4.2 秒」写进结论，读者拿去指导自己的部署，这就是用个别运行结果冒充普遍结论。

操作计数没有这些问题：它不依赖机器、不依赖时钟、不依赖 JIT 状态，同一份输入永远同一个数字。所以本站的示例代码统一按这个原则设计——**每段用于说明复杂度的代码，都自带一个计数器并把总数打印出来。**

代价也必须说清楚：计数只反映你数的那个实现。`op-counts.cjs` 里的插入排序是比较交换的朴素写法，真实引擎里的排序是另一份高度优化的实现；本章从 MDN `Array.prototype.sort()` 中文页面核实到的原文明确写着，该方法**「无法保证排序的时间和空间复杂度」**，也说明了实现细节不在规范承诺范围内。所以本章能带走的是数量级的直觉，不是具体数字。**要测真实性能，正确做法是：固定数据集、重复多次、只比同一指标（操作数或耗时）、用 profiler 看火焰图**——这属于工程实践，本站不在这里展开，也不给未经执行的基准结论。

## 最好、最坏、平均说的是输入分布，不是运气

本章开头那张表里，插入排序在三种输入下的比较次数分别是 1 999、1 999 000、1 001 498。把它们和公式对上：

```text
n = 2000
  已排序 → 1 999      = n − 1
  逆序   → 1 999 000  = n(n − 1) / 2
  锯齿   → 1 001 498  ≈ 介于两者之间（略高于 n(n−1)/4 = 500 000）
```

前两个和公式逐字吻合，这不是巧合：插入排序每插入一个元素，要把它和前面比到不再更大为止。已排序时每个元素只比一次就停，共 n − 1 次；逆序时第 i 个元素要比 i 次，共 1 + 2 + … + (n−1) = n(n−1)/2。**所以「最好 O(n)、最坏 O(n²)」讲的从来不是运气，而是「在什么样的输入分布下」。**

平均情况之所以在教科书里难算，是因为它需要先假设输入服从某个分布（通常是所有排列等概率），再对分布求期望。工程上你会碰到三种更实用的处理办法：

**只看最坏，当输入由外部决定时。** 用户上传一个 CSV、爬虫抓回来一段文本、别人调用你的接口传一个列表——这些输入的**形状**不受你控制，而攻击者和坏运气都恰好会生产最坏形状。第 2 章真跑过的那个坏哈希实验就是这类：同样 100 000 个整数键、同样 100 000 个桶（负载因子 1.0），均匀哈希时平均比较 0.00 次；把哈希函数换成「只看 key 的后几位」，平均比较变成 49.50 次、最长链 100、空桶 99 000。同一个数据结构、同一份数据规模，只是分布变了，性能就退化成链表。

**只看最好，当输入由你自己生产时。** 你的列表已经被数据库 `ORDER BY` 排过序，你往一个几乎有序的数组里插几条记录——这时候「最坏 O(n²)」的担忧是多余的。

**两者都算不出来时，退而求其次看「这个操作会不会被外部输入放大」。** 这个判断不依赖任何精确计算，但它决定了你要不要在代码评审里拦住那个嵌套循环。

## 目测一段代码的复杂度：四种读法

下面四种模式覆盖了你实际会写的绝大多数逻辑。每种给一段可以真跑的代码和一个计数锚点。

**读法一：嵌套循环，看内层次数是否依赖外层。**

```ts
// A：内层固定 n 次 → n × n，O(n²)
for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) work()
}

// B：内层从 i 开始 → n(n-1)/2 次，仍是 O(n²)（常数 1/2 被约定一吃掉）
for (let i = 0; i < n; i++) {
  for (let j = i + 1; j < n; j++) work()
}

// C：内层翻倍增长 → 总共约 2n 次，O(n)
for (let i = 1; i <= n; i *= 2) {
  for (let j = 0; j < i; j++) work()
}
```

C 是最容易看错的一个：循环套循环，看起来 O(n²)，实际内层次数是 1 + 2 + 4 + … + n ≈ 2n。判断依据只有一条——**把内层次数当成 i 的函数加起来。**

**读法二：递归，用「每层工作量 × 层数」；分支数决定是否爆炸。**

同一份脚本里对 Fibonacci 的两种写法计数（函数调用次数，含第一次调用）：

```text
        暴力递归    记忆化
 fib(10)     177        12
 fib(20)  21 891        22
 fib(30) 2 692 537      32
 fib(35) 29 860 703     37

 核对：暴力 fib(20) 的调用次数 21 891 与 2·F(21) − 1 = 21 891 逐字吻合
```

暴力的调用次数随 n 按斐波那契数列本身增长，也就是指数级（比值约 1.618，即黄金比例）。记忆化那一列更值得看：10 → 12、20 → 22、30 → 32、35 → 37，**这条关系是 2n + 2，是线性的**——每个不同的 n 只计算一次，再加上「从记忆里读出来」的那一层调用。同一份逻辑、同一个正确结果，量级从指数掉到线性，这就是第 4 章要讲 DP 的动机。

递归还有一条隐藏成本：调用次数不等于**栈深度**。fib(35) 需要 2 986 万次调用，但任何时刻栈上最多只有约 35 层（因为它是先一路走到 n=0 再返回的）。深度决定「会不会栈溢出」，次数决定「要等多久」，两者分开评估。

**读法三：摊还，看这个操作是不是把代价推迟了。** `push` 一次算 O(1)，见下一节。

**读法四：藏起来的循环。** 这一类是真实事故的主要来源，因为代码里没有第二个 `for`。

```ts
const seen: string[] = []
for (const row of rows) {          // n 行
  if (!seen.includes(row.id)) seen.push(row.id)  // includes 是 O(已收集个数)
}
```

看起来是 O(n)，实际是 O(n²)——`seen` 每加一个元素，后续每次 `includes` 就多比一次。**把 `seen` 换成 `Set` 才回到 O(n)**（第 2 章讲过哈希表为什么能按 O(1) 查找，以及它的前提）。

其余需要条件反射般认出来的隐藏循环：数组的 `includes` / `indexOf` / `filter` / `map` / `reduce`（每个都是完整 O(n)，链式调用几个就是几趟）、`Object.keys(obj)` 与 `{ ...obj }`（O(键数)）、`JSON.stringify`（O(序列化内容大小)）、字符串 `+` 拼接（每次生成新字符串，累计 O(n²)）、数组的 `shift` / `unshift` / `splice`（搬移，见第 1 章）。

## 摊还复杂度：push 凭什么记成常数

第 1 章说过，数组要连续存放，容量不够时只能找一块更大的地方把全部旧数据搬过去。按 doubling（容量不足就翻倍）这条最常见的策略推演一下：

```text
按「容量翻倍」规则推演（本站未核实具体引擎的扩容策略，这是数学上界）

  搬移总量  = n + n/2 + n/4 + … < 2n
  摊还代价  = 2n / n < 2  →  每次 push 记作 O(1)
```

关键在于「翻倍」让扩容次数极少：从 1 涨到 n，只需 log₂n 次扩容，而每次只搬当时的全部数据。几何级数求和压不过末项的两倍，所以总搬移是 O(n)，摊到每次 push 就是常数。

**但摊还有严格的适用条件，两个最容易踩的：**

一，**摊还说的是总代价，不是单次延迟。** 那一次扩容要连续搬 n 个元素，这一次调用的耗时可能是平时的几十倍。在浏览器里的表现就是你我都见过的「页面平时顺，某一下突然卡住」；在服务端表现为 P99 远高于 P50。**「平均 O(1)」永远不能拿来回答「这一笔会不会超时」**，这个区别在实时通信领域里直接决定用户体验，参见[实时通信的断线与补拉](/realtime/)里的延迟尖刺处理。

二，**摊还是要各操作自己算，不能传递。** 第 1 章真跑过：`shift` 一次要搬 n − 1 个元素（n = 100 000 时 99 999 次），而且**每一次都搬**，不存在「偶尔贵一次」——所以队列里用 `shift` 处理 n 条消息就是实打实的 O(n²)，摊还救不了它。对比记忆化后的 `push`：贵的那一次极少。这就是「摊还 O(1)」和「最坏 O(n) 且每次都 O(n)」的分界。

本站对引擎实际扩容策略没有核实，所以「翻倍」「2n 上界」都按推演读。但结论不依赖具体策略：**只要容量是几何增长的，摊就是常数；只要每次插入都要搬一半以上数据，摊就无效。**

## 空间复杂度：被大多数人忽略的那一半

时间复杂度决定「用户等多久」，空间复杂度决定「进程还在不在」。四个必须计入的地方：

**递归栈深度。** 上节说过，fib(35) 的栈深度只有约 35。但换一个问题：用递归对一个 10 万元素的数组求和，栈深度就是 10 万，直接撞上引擎的栈上限并抛出 `RangeError`。栈空间是**每个调用帧**占的，无法靠「反正很快返回」糊弄过去。

**分治算法的额外数组。** 上面真跑的归并排序，额外空间是 O(n)：每一层合并都需要临时容器。（本站没有测内存占用，这一条按算法定义推演。）对比插入排序的原地做法，省下的就是这 n 个位置的分配与回收。

**为加速而建的索引结构。** 这是最典型的「空间换时间」：`Set` 去重是 O(n) 额外空间换 O(1) 查找；把列表按某字段建 `Map` 分组是 O(n) 空间换「每次查询不用重扫」；数据库索引同理——第 2 章讲过 B 树家族的直觉，[数据库索引那一章](/database/indexes)讲了工业实现和写放大代价。索引不是免费的：它占内存、占磁盘、每次写入都要维护。**「加个索引就好了」这句话的成本项是空间复杂度，不是时间。**

**被保留的中间结果。** `map` + `filter` + `sort` 一条链子跑完，内存里同时存在好几个和 n 成正比的数组；`JSON.stringify` 出来的一整串文本也占内存。数据量小的时候无所谓，大的时候这是 Node 进程 RSS 涨上去的常见原因之一——JS 堆与进程内存的差异在[操作系统的内存与 IO 模型](/computer-science/)第 9 章讲。

估算法则和时间几乎一样：**问「最大的那个容器里有几个元素」，问「递归最深几层」。** 如果两个都不超过 n 的常数倍，空间就是 O(n)；如果建了哈希表或排序副本，仍然是 O(n) 但常数很大；只有原地双指针那类才是 O(1)。

## 一张对照表：数据量涨 100 倍会发生什么

脚本对若干 n 打印了两个公式值（`n·log₂n` 取整、`n²`），`2ⁿ` 只在 n = 10 那一档打印：

```text
        n      n·log₂n        n²       2ⁿ
       10          33        100    1 024
      100         664     10 000
    1 000       9 966  1 000 000
   10 000     132 877 100 000 000
  100 000   1 660 964 10 000 000 000
```

把 n 放大 100 倍（1 000 → 100 000），三列各自涨了多少：

```text
  线性 n        → 涨    100 倍
  n·log₂n      → 涨    167 倍（9 966 → 1 660 964）
  n²           → 涨 10 000 倍（1 000 000 → 10 000 000 000）
```

这张表的用法不是预测毫秒——**它预测不了**，因为你不知道每次操作要多少纳秒、不知道常数因子。它的用法是回答一个产品问题：**「这个逻辑能撑到多大数据量？」**

具体做法就两步。第一步，把可疑逻辑的操作数写成 n 的函数。第二步，代入你产品里 n 的**上限**（不是当前值），只看这个数是不是越过了一个数量级红线。粗略锚点（**这是推演，不是本站测过的耗时**）：一个纯 JS 循环体内的操作在「每元素几次到几十次基本操作」这个尺度上，10⁸ 次量级会让人感到「卡一下」，10⁹–10¹⁰ 会到「页面失去响应 / 请求超时」的量级。所以：

- n = 10⁵、O(n²) → 10¹⁰ 次 → **必死**，没有侥幸。
- n = 10⁵、O(n log n) → 约 1.7 × 10⁶ 次 → 毫无压力。
- n = 10³、O(n²) → 10⁶ 次 → 完全没问题，**别为了这个改架构**。

第三条那一句同样重要：够用档的目标是拦住会出事的写法，不是把所有代码都优化到理论最优。**n 的上限拿不准时，先把上限问出来再决定要不要动代码**——这是技术判断，不是算法能力。

## 常见错误与排查

**1. 现象：把「O(n log n)」当成「更快」的保证，替换后线上反而更慢。**

原因：大 O 忽略了常数因子，而小 n 时低阶项和常数项才是主角。本章开头那张 n = 2000 的表里，已排序输入上「更优量级」的归并比较了 10 864 次，插入只比较了 1 999 次。

怎么确认：把两种实现都放进计数器跑同一份真实数据（不是随机数据），比操作总数；操作数接近时，量级之争就不重要，改法方向应该是**减少总工作量**而不是换算法。

怎么修：先在代码评审里问「n 有多大」，只有当 n 大到你的量级差能压过常数时才换。

**2. 现象：一段没有嵌套 `for` 的代码，数据一多就卡死。**

原因：隐藏循环。最常见的是循环体里的 `includes` / `indexOf` / `find` / `filter`，以及 `Object.keys`、`{ ...obj }`、`JSON.stringify`、字符串 `+=`。每次调用都是完整的一趟。

怎么确认：在循环体里放一个全局计数器，累加被隐藏循环扫过的元素个数，跑完打印——上一节那个 `seen.includes` 的例子就是靠这个方法现形的。

怎么修：把「存在性判断」换成 `Set`，把「按 key 找」换成 `Map`，字符串拼接换成 `push` 到数组最后 `join('')`。第 1、2 章给了对应的结构选择判据。

**3. 现象：本地压测「n = 5 000 用时 12ms」，线上 n = 5 000 却超时。**

原因：你测的是「平均输入」，线上是「最坏形状」。同一个数据结构同一个规模，分布不同可以差出数量级——第 2 章坏哈希实验里平均探测从 0.00 变成 49.50，最长链 100。

怎么确认：把压测数据集换成线上真实数据（脱敏后），并额外构造几种「恶意形状」：全重复、全相同 key、完全逆序、超长字符串。

怎么修：对**外部可控的输入**按最坏情况评估；能约束形状的地方就约束（排序后再处理、要求哈希分布均匀、限制字段长度）。

**4. 现象：内存告警，但代码里没有新建大数组。**

原因：递归栈深度，或者链式 `map`/`filter` 同时留下的多份中间数组；也可能是扩容瞬间新旧两份数组并存。

怎么确认：把递归改成显式循环试一次（如果内存回落，问题是栈）；把链式调用拆成带名字的中转变量，看哪一个的 `length` 最大。

怎么修：深度可能很大的递归改循环或改分片；中间数组用完立刻断开引用；数据量再大就该在数据库侧做聚合而不是全量拉到进程里，参见[连接池与慢查询](/data-storage/connection-pool-and-slow-query)。

**5. 现象：讨论「这是 O(n) 还是 O(n²)」吵了半小时，没有结论。**

原因：在争常数而不是争量级，或者没先约定 n 的范围与输入分布。大 O 本身不区分 2n 和 100n，这类争论在记号体系里没有答案。

怎么确认：要求双方各写一句话——「我认为在 n = ___、输入形状为 ___ 时，操作数约为 ___」。填不出来说明还没到讨论大 O 的时候。

怎么修：把讨论降级为「这个操作会不会被外部输入放大」，先决定要不要加保护（限流、分页、上限校验），再谈优化。

## 练习

<Exercise title="四段代码，各是什么量级" difficulty="基础">

下面四段代码各自的时间复杂度是什么？写出你的推导过程，特别标注哪一段有「藏起来的循环」。

```ts
// 1
const ids = orders.map((o) => o.id)
for (const u of users) total += ids.includes(u.id) ? 1 : 0

// 2
for (let i = 1; i <= n; i *= 3) work(i)

// 3
for (const tag of post.tags) {
  for (const other of relatedPosts) {
    if (other.tags.includes(tag)) hits++
  }
}

// 4
let text = ''
for (const line of lines) text += line + '\n'
```

<template #answer>

1. **O(|orders| + |users| × |orders|)**，也就是双线性/平方级。`map` 走一趟建 `ids`，然后每个 user 都在 `ids` 上做一趟 `includes`——这就是藏起来的循环。改法：`const idSet = new Set(orders.map(o => o.id))`，之后每次判断 O(1)，整体回到 O(|orders| + |users|)。
2. **O(log n)**。`i` 按 3 的幂增长，循环次数是 ⌊log₃ n⌋ + 1。注意「循环体里只有 O(1) 工作」这个前提：如果 `work(i)` 内部遍历 `i` 个元素，就变成 1 + 3 + 9 + … + n = O(n)，和本章读法一里的 C 段同理。
3. **O(|tags| × |relatedPosts| × |other.tags|)**，三段相乘，最外层还有一层 `for (const post of posts)` 的话就是四段。这里 `other.tags.includes(tag)` 是第三个隐藏循环。改法：先把 tag 到帖子的倒排关系建成 `Map<string, Post[]>`（一次 O(总标签数)），再按 tag 直接取。
4. **O(n × 平均行长) 甚至更差**。每次 `+=` 都生成一个全新的字符串，把已有的整份复制一遍，n 次之后累计复制量与 n² 成正比。改法：`const parts: string[] = []; parts.push(line)`，最后 `parts.join('\n')`——`push` 是摊还 O(1)，`join` 只走一趟。

</template>

</Exercise>

<Exercise title="用计数器把一段代码的量级现形" difficulty="进阶">

你打算写一个「按 id 去重并保持首次出现顺序」的函数。有两个版本：A 用 `Array` + `includes`，B 用 `Set` + `add`。

请为两个版本各加一个「扫描元素个数」的计数器，对 n = 1 000 和 n = 10 000 的**全不重复**数据各跑一次，打印四个数字。然后回答：

1. 按你数到的数字，A 的增长形状接近 n 的哪一次函数？（提示：全不重复时第 i 次 `includes` 要比较 i 次，总量是 n(n+1)/2）
2. 把数据换成「全部同一个 id」（极端重复），A 的数字会怎么变？为什么？
3. 这个实验为什么不能用「本机跑了多少毫秒」来替代？

<template #answer>

1. 接近 **n²**。全不重复时第 i 次 `includes` 要把已有的 i 个元素比完才返回 false，累加是 1 + 2 + … + n = n(n+1)/2。按这个公式推演（不是本站实测值）：n = 1 000 → 500 500，n = 10 000 → 50 005 000，n 涨 10 倍计数涨约 100 倍。**n 涨 100 倍就是涨 10 000 倍**——这正是本章「数据量涨 100 倍」那张放大表讲的规律。B 版本每个元素只做一次 `Set.has` + 一次 `add`，计数是 n 的常数倍，所以 10 000 → 十几万量级。
2. **变小**。`includes` 一旦在第一个位置命中就立刻返回 true，不再往后比，所以每个元素只比较 1 次，总量退化成 O(n)。这条很关键：**同一份代码，操作数由输入分布决定**，最好情况和最坏情况差一个数量级。第 2 章坏哈希实验是同一现象的另一面（分布变坏，平均探测次数从 0.00 涨到 49.50）。
3. 因为毫秒数字里混着机器状态、JIT 预热、GC 时机和缓存命中，跑两次不一定一样，换台机器结论可能反过来——**它是个别运行结果，不是普遍结论**。计数是确定的，可以逐字核对，还能同时给出「最好/最坏/平均」三组数字（换三份输入即可）。要判断真实耗时还得做基准测试，那是另一套方法：固定数据集、重复多次、同指标对比、用 profiler。

</template>

</Exercise>

<Exercise title="故意制造一次栈溢出，并解释报错" difficulty="挑战">

写一个递归函数 `sum(arr)`：基准情形是空数组返回 0，递归情形是 `arr[0] + sum(arr.slice(1))`。然后用 `Array.from({ length: 200_000 }, (_, i) => i)` 造一个 20 万元素的数组，调用它。

1. 预期会看到什么？把报错原文和你的判断写下来。
2. 这个错误的时间复杂度问题和空间复杂度问题分别是什么？
3. 改成循环之后还有同样的问题吗？

<template #answer>

1. 预期抛出 `RangeError`，Node 里的典型信息是 `Maximum call stack size exceeded`（浏览器措辞略有不同，但同样是 RangeError）。**本站没有执行这个实验，所以不把它当作已核实结论**——请你自己跑一次，把真实报错文本记下来。触发原因是递归深度达到了引擎栈上限（这个上限由引擎设定，随平台与版本变化，本站未核实具体数值，也不建议依赖它）。
2. 时间上 O(n)，但有个更阴的坑：`arr.slice(1)` 每次都复制一份新数组，总复制量是 n(n+1)/2 = **O(n²)**，这是「藏起来的循环 + 中间数组」双料案例。空间上是 O(n) 栈深度，外加同时存在的 n 份 slice 副本——两者叠加，20 万这个规模既撑爆栈也撑爆堆。
3. 循环版本没有栈深度问题：`let total = 0; for (const x of arr) total += x`，时间 O(n)、额外空间 O(1)。顺带一提，`arr.reduce((a, b) => a + b, 0)` 也是 O(n) + O(1)，两种都对。这道题的真正结论是：**能写成循环的深度不可控的递归，就别写成递归**；真的需要递归时，用分治（深度 log n）而不是线性递归（深度 n）。

</template>

</Exercise>
