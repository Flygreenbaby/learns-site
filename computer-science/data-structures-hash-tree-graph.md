# 哈希、树与图：把「找」变成一次算术，把顺序交给树

你有一个 5 万条的用户表，代码里写着 `users.find((u) => u.id === target)`。单次查找在循环里看起来无害，一轮批处理跑下来它执行了 5 万次——每次平均扫完半个数组。换成 `Map` 之后同样这段逻辑「突然不慢了」，但你要知道**为什么**：哈希表把「比较」变成了「算术」。

第二种恰好相反：你把一个计数逻辑从数组改成 `Map`，压测确实快了，但产品里那段「按分数排名」的输出乱了序。`Map` 不替你的数据排序，它只保证你自己的插入顺序；要「按 key 的范围查」「要第 k 小的全部」「要 Top-K」，需要的是树和堆，这是两种完全不同的形状。

第三种最常见，而且和数据结构无关，只和语言细节有关：拿普通对象当字典用，键是用户传进来的字符串——`obj['toString']` 一开始就「已经存在」了；`obj[1]` 和 `obj['1']` 是同一个键；`JSON.parse` 出来的对象带着 `Object.prototype`。这些不是哈希表慢，是**你在用错的那个哈希表**。

第四种是关系：评论里有用户、用户有标签、标签互相引用，你把它们存成层层嵌套的数组，于是「这两个人是不是朋友」变成一次嵌套遍历。那是一件图的问题，而图有它自己的表示法。

本章讲四件事：哈希表的代价与它的失效条件、树替你保住的到底是什么顺序、堆只保证什么、以及图的两种存法各自的账单。遍历算法（BFS/DFS）在[第 4 章](/computer-science/algorithms)，大 O 记号本身在[第 3 章](/computer-science/complexity)。

## 哈希表把「找」变成一次算术

先看没有哈希表时你在做什么：`find` 是逐个比较，平均比较 n/2 次。哈希表做的事只有一步——**用 key 算出一个位置**，然后只看那个位置。

```text
=== B 哈希表：桶数、负载因子与链长（本站手写链地址法，键为整数） ===
  n=100,000 键，均匀哈希：
    桶数 100000（负载因子 1.0）→ 平均比较 0.00 次，最长链 1，空桶 0
    桶数  10000（负载因子 10.0）→ 平均比较 4.50 次，最长链 10，空桶 0
    桶数    500（负载因子 200.0）→ 平均比较 99.50 次，最长链 200，空桶 0
  同样 100,000 键，换成只看低位的坏哈希：
    桶数 100000 → 平均比较 49.50 次，最长链 100，空桶 99000
    桶数  10000 → 平均比较 49.50 次，最长链 100，空桶 9000
```

B 组的构造值得说清，否则它会被读成「哈希表慢」的证据。本站实现的是**链地址法**：`m` 个桶，每个桶是一条链表；插入第 k 个键时，先按哈希值定位桶，然后**把这条桶里已有的元素数一遍**（这就是 `probes`）。于是：

- 均匀哈希那三行说明的是**负载因子**（n / m）的作用：桶够多（负载因子 1.0）时平均比较接近 0，桶缩到 1/10 就变成 4.5 次，缩到 1/200 就变成 99.5 次。**注意它不是线性跟着负载因子走的**：负载因子 10 时平均 4.50 ≈ 10/2，负载因子 200 时 99.50 ≈ 200/2——平均链长就是负载因子的一半，这是算术，不是实测发现。
- 坏哈希那两行说明的是**分布**的作用：桶数从 10,000 加到 100,000（多十倍），平均比较一次没降，仍是 49.50，最长链仍是 100，因为哈希函数只看低位，而键的低位每 1,000 个循环一次。空桶从 9,000 涨到 99,000——**桶多了一堆，全是空的**。

这两组合起来就是本章的主结论：**哈希表 O(1) 的前提不是「它是哈希表」，而是「哈希函数把键散得开」且「桶数与键数同量级」。** 前者坏掉时你得到的是「一堆几乎全同的链」，后者坏掉时你得到的是「一条很长的链」。

## 扩容、稳定性，以及为什么「遍历顺序」不能依赖它

桶数不够时表要长大：重新给每个键算一次位置，把全部元素搬到新桶里——这叫 rehash，代价是**与元素数成正比**的一次性动作。所以「往 `Map` 里塞 100 万个键」的总成本里，绝大部分其实花在一次次扩容搬家上，形状和[第 1 章](/computer-science/data-structures-linear)里 `push` 的整块复制同源：单次贵，摊还下来能接受。

一个更实用推论：**如果你的键数量有可预见的上界（比如「这个批处理最多 20 万条」），预先给足容量比让它一路扩容便宜。** 具体能不能预设在 JS 里有限制——`Map` 的构造函数并不接受容量参数，这一点本站按「不写具体 API」处理，只把结论留在「知道扩容是线性动作」这一层。

哈希表本身不保证顺序：桶的位置由哈希值决定，与插入先后无关。JS 的 `Map` 在此之上**另外**记了一份插入顺序（这是语言规范给的保证，本批在 MDN 核实到原文），所以遍历 `Map` 是稳定的；但这个保证是「你插入的顺序」，**不是「键的顺序」**：

```ts
const m = new Map<string, number>();
m.set('banana', 2); m.set('apple', 1); m.set('cherry', 3);
[...m.keys()];        // 预期：['banana','apple','cherry'] —— 插入顺序，不是字母序
[...m.keys()].sort();  // 想要字典序必须自己排，而排序是另一笔成本（见第 4 章）
```

这就是「范围查询」为什么哈希表做不了：`apple` 到 `cherry` 之间的键，在哈希表里散落在互不相邻的桶中，你无法从一个位置「顺着走下去」拿到下一个。要范围，需要下面那种结构。

## JS 里有三种「键值」：Object、Map、Set，选错的那类最容易出事

```ts
// 用普通对象当计数表：三个真实陷阱
const counts: Record<string, number> = {};
counts['1'] = 1; counts[1] = 2;                 // 同一个键：属性名最终都是字符串 ⟹ counts['1'] === 2
counts['NaN'] = 3; counts[NaN] = 4;             // 还是同一个键（NaN 被转成字符串 'NaN'）
counts['toString'] = 5;                          // 危险：这个键一开始就「存在」（原型链上有）

// 换成 Map：键保留类型，且判等语义是零值相等
const c = new Map<unknown, number>();
c.set(1, 1); c.set('1', 2);                      // 两个不同的键
c.set(NaN, 3); c.has(NaN);                        // true —— NaN 能当自己的键
c.set(0, 'a'); c.get(-0);                          // 'a' —— +0 与 -0 视为同一个键
```

三条判据：

1. **键要保留类型，或者键来自外部输入** → 用 `Map`/`Set`。外部字符串作键时用 `Object` 有原型污染风险（`__proto__` 也是一个可以写进去的键），退一步的写法是 `Object.create(null)`，但它没有 `Map` 的 `size` 与迭代接口。
2. **要判重、要「在场集合」** → `Set`，别用数组 + `includes`（那是[第 1 章](/computer-science/data-structures-linear)常见错误 4 那条线性扫描）。
3. **要序列化、要字面量可读、键确定是安全的短字符串** → `Record`/对象够用，这是它的主场（配置文件、DTO）。

顺带一个高频 bug：`Map` 的键**按引用比**（对象作键时），所以两个字段完全一样的 `{ id: 7 }` 是两个不同键；想按内容去重就要先把 id 取出来。这条在第 1 章练习 3 也出现过，因为它是缓存不命中最常见的原因之一。

## 树保住的顺序，正是哈希表丢掉的那件

二叉搜索树的规则只有一句：左子树全部小于根，右子树全部大于根。于是「中序遍历」自动给出升序，「找第 k 小」「查一个范围」「找前一个/后一个」这些操作都有路可走——这些是哈希表结构上做不到的。

代价写在形状上：查找沿路往下走，走的高度是多少？**取决于插入顺序。** 按升序插入 5 个键，得到的树是一条向右的链：

```ts
// 结构示意（本站没跑过；这是构造出来的退化形状）
// 依次插入 1,2,3,4,5 ⟹ 每个新键都比当前所有键大，一路向右
// root=1 → right=2 → right=3 → right=4 → right=5
// 高度 5，查找第 5 个要走 5 步 ⟹ 这棵树已经退化成一个链表
```

n 个键按序插入就得到高度 n，查找从 O(log n) 变成 O(n)——**而且它是个更差的链表**（每个节点还要带两个指针）。所谓「自平衡」（AVL、红黑树、B 树这一族）就是给树加一条维护规则：每次改动后付一点常数级的旋转代价，把高度锁在 O(log n)。本站不写平衡树的实现（那是刷题档的活，本领域[首页](/computer-science/)明确说了不训练手写红黑树），你要建立的是这个判断：**「树慢」从来不是树的问题，是它没平衡、高度失控。**

数据库索引用的是 B 树家族，而理由和内存里的平衡树**不一样**，这一层很多文章会混过去：磁盘读的是「页」，一次几十 KB，所以结构要**矮而且宽**——一个节点里放很多键和很多子指针，一次 IO 换一大片信息。于是你会看到这些真实结论：索引扫描适合「按前缀过滤 + 排序」，不适合「随便哪个字段都加索引」（每个索引都是一份额外的写入放大，插入要同时改多棵树）；`EXPLAIN` 里走位表扫描意味着索引没被这个查询条件命中。**本站没有 PostgreSQL 环境，这一段的每条具体行为都属于「按官方文档核对后自己 `EXPLAIN` 验证」**，权威说法见延伸阅读的索引文档链接与[数据库领域的索引一章](/database/indexes)。

## 堆：它只保证「顶上那个最小」，其余一概不管

堆是一条**偏序**：父节点不大于子节点（最小堆）。它保证的只有堆顶是极值；第二小的可能是根的任一子树里任意一个，堆里其余部分完全没有顺序。

```ts
// 结构示意：堆的真实用法在 JS 里通常是「自己维护一个数组 + 上浮下沉」
// 或者交给第三方库（本站没有安装过任何依赖，不推荐具体包名）。
// 你能确证的性质只有：
//   取极值 = 常数（读堆顶）
//   插入 / 取出后重排 = O(log n)（沿一条路上浮下沉）
// 你不能确证的性质：堆里其他元素的相对顺序。
```

「只要一个极值」和「要全序」的账单完全不同：`sort()` 之后取第一个是 O(n log n) 加一整份新数组，而堆的做法是 O(n) 建堆 + 常数次取顶。当这个操作在循环里、而 n 是几万时，这就是那种「改一行、批处理时间砍掉一大截」的优化。

两种典型形状：

- **Top-K**：维护一个大小为 K 的**最小堆**，新元素与堆顶比，比堆顶大才替换——这样 K 个元素就是目前最大的 K 个。整个流只需一遍，内存只占 K。
- **优先队列 / 定时任务**：入队时给优先级，出队永远取最高的那个。这是[消息队列](/message-queue-cloud/)和限流场景里真实存在的结构，Redis 的有序集合就是这类需求的产品兑现（本站未在本机验证其内部实现，它是否用跳表请以 Redis 官方文档为准）。

## 图：两种存法，各自的账单写在两个不同的操作上

图没有新的复杂度魔法，它首先是一个**存储决策**：边怎么放。E 组把这张 6 节点 7 条边的无向图两种存法的计数打了出来：

```text
  邻接矩阵：6×6 = 36 个格子，存了 7 条边（无向 → 写 14 次），查「u-v 有没有边」= 1 次
  邻接表：14 条表项，遍历全部邻居 = 14 步，查「u-v 有没有边」最坏 = 度数 3 次
  形状结论：矩阵用 n² 空间换 O(1) 查边；表用 2m 空间换 O(deg) 遍历——「遍历邻居」才是应用里最常见的那个操作，所以表几乎总是赢
```

对应到实际写码：矩阵的空间是 n²，1 万个用户的关系图要 1 亿个格子，而真实关系往往只有几万条——**存了 99.99% 的「没有」**。所以绝大多数应用场景用邻接表，也就是 `Map<节点, 邻居[]>`（或对象字典 + 数组）；只有「边很密且要反复问两点是否有边」才轮到矩阵。

还有一条常被忽略：**「图」和「树」是同一个存储的两种语义**。树是没有环、有根的图，所以树的遍历（父往下）比图的遍历（任意方向）少一件事——**标记已访问**。你在图上不加 visited 集合就会沿同一条边来回弹，这是无限递归的第一号成因（第 4 章有对应的计数与修法）。

## 需求到结构：一张表

| 你要做的事 | 正确的结构 | 会被误用成 |
| --- | --- | --- |
| 按 id 取值 / 判重 / 计数 | `Map` / `Set` | 数组 + `find` / `includes`（线性） |
| 「这个范围内的所有键」、「第 k 小」、「前一个/后一个」 | 平衡树家族（或数据库索引） | 排序后 `slice`，每次重新排 |
| 只要最大或最小那一个 / Top-K | 堆 | 每次 `sort()` 取第一个 |
| 后进先出 / 先进先出 | 栈 / 队列（接口，[第 1 章](/computer-science/data-structures-linear)） | `shift()` 做队列 |
| 任意两点是否有边 | 邻接矩阵 | 嵌套数组 + `some` |
| 遍历邻居、可达性、最短跳数 | 邻接表 + BFS/DFS | 递归嵌套 `filter` |
| 键来自外部输入 | `Map`/`Set`，或 `Object.create(null)` | 普通对象字面量（原型污染） |

## 常见错误与排查

**1. 现象：换成 `Map` 之后逻辑快了，但输出顺序变了。** 原因：`Map` 保的是**插入顺序**，不是键的顺序；你原来的代码顺序来自「数组本来就是排好的」。怎么确认：打印 `[...m.keys()]`，和排序后的结果比一次。怎么修：显式排序，或把「需要顺序」这件事交给能保序的操作（`Array.sort` 一次、或索引扫描），不要指望哈希表维持顺序。

**2. 现象：缓存命中率莫名其妙地低。** 原因：用对象作 `Map` 键，或每次重建一个内容相同但引用不同的对象。`Map` 的对象键按引用比。怎么确认：`m.has(k)` 为 false 而 `m.size` 一直涨，就是这个；把键打出来看引用是否同一个。怎么修：键取原始值（id、拼接出的稳定字符串），或者按内容生成 key 后再放进 `Map`。

**3. 现象：字典里凭空多出一个键，或者查 `hasOwnProperty` 意外为真。** 原因：普通对象的键可以撞上原型链上的名字（`toString`、`constructor`、`__proto__`）。怎么确认：`Object.keys(obj)` 的长度与你自己 `set` 的次数不一致，或 `for...in` 里出现了没写过的键。怎么修：`Object.create(null)`，或直接用 `Map`；来自外部输入的键**绝不**直接写进普通对象。

**4. 现象：加了索引之后插入明显变慢，或者索引根本没被走。** 原因：每个索引是一棵要同步维护的树（写放大），以及查询条件不匹配索引前缀（函数包裹、隐式类型转换、前导通配符）。怎么确认：`EXPLAIN`（本站无数据库环境，这一步必须在你的实例上做）看是否走 Index Scan，以及 `Seq Scan` 的 rows 估计数。怎么修：按真实查询条件建复合索引并遵守前缀顺序，删掉从没被走的索引；**不要靠「感觉」加索引**。

**5. 现象：递归遍历用户关系时栈溢出。** 原因：把图当成树处理，没有 visited 集合，沿边来回弹。怎么确认：把访问路径打出来，出现 `0 → 1 → 0` 这种回头边就是它。怎么修：加 `Set` 标记已访问（判据用零值相等，原始值 id 最稳），并给递归深度设上界；改写成显式栈/队列见第 4 章。

<template #answer>

① 负载因子 = n / m。n = 200,000 时：m = 200,000 → 负载因子 1 → 平均比较约 **0.5 次**（B 组第一行是 0.00，因为本站的计数只算「同桶已有元素数」，第一个进桶的元素比较 0 次；两者说的是同一件事的不同口径，写结论要带口径）；m = 20,000 → 负载因子 10 → 约 **5 次**（B 组第二行给的是 4.50）；m = 2,000 → 负载因子 100 → 约 **50 次**。

② 桶不动、键涨十倍：负载因子变成 10 → 平均约 **5 次**，与①的第二行同一个数。这条推论的实际含义是**哈希表的性能由「键数与桶数的比值」决定**，而不是由键数决定——扩容（把比值打回去）与哈希函数（把分布弄均匀）是仅有的两条出路。

③ 估算失效的三种情况：哈希函数差（键散不开，链长由聚集而不是比值决定，B 组坏哈希那两行就是这个——平均 49.50 与负载因子 1.0 完全不符）；键的高度相似（如全是同一前缀的字符串且哈希只看低位）；以及**分布不均的极端**，此时最长链远大于平均，一次落在长链上的查询就会拖尾。所以平均比较次数不能单独当结论，要和最长链一起看。

</template>

</Exercise>

<Exercise title="练习 2 · 故意造出一个「缓存永不命中」的 Map 并解释" difficulty="进阶">

写一段用 `Map` 做缓存的代码，让它在逻辑正确的前提下**每次都不命中**，解释为什么不命中，并给出两种修法。

<template #answer>

```ts
// 会失效的形状：键是对象
const cache = new Map();
const load = (key: { userId: number }) => {
  if (cache.has(key)) return cache.get(key);   // 永远 false
  const v = { rows: [] };
  cache.set(key, v);
  return v;
};
load({ userId: 7 });
load({ userId: 7 });   // ← 字面量新建的对象，与第一次那个不是同一个引用
```

原因：`Map` 的对象键**按引用**判等。`{ userId: 7 }` 每次求值都创建一个新对象，两次调用的键是两个不同对象，于是 `has` 永远 false，`size` 一路涨（这同时是一个内存增长源）。这条判据来自本站本批核实到的 `Map` 键语义，不是推演。

修法一（首选）：**把键降成原始值**——`cache.set(key.userId, v)`，数字/字符串按值比较，第二次调用就命中了。修法二：**把键规范化成稳定字符串**——`const k = JSON.stringify(key)`（或字段拼接），并用同一个规范化函数负责读写；如果调用方传的对象字段顺序可能不同，`JSON.stringify` 就不稳定，此时必须改成显式拼接固定字段。修法三（结构性）：让调用方传同一份 id 而不是每次造对象，即在入口做 interning（`Map` 把 id 映射到唯一实例）。

排查方向也一并给出：`cache.size` 单调增长而业务并发数不变，就是这类「键的引用不稳定」问题；先打 `size` 与一次 `has` 的结果，比读代码快得多。

</template>

</Exercise>

<Exercise title="练习 3 · 给三个真实需求选结构，并说明它替谁省掉了什么" difficulty="挑战">

① 从 2,000 万行日志里取访问次数最多的前 20 个 URL；② 一个后台列表页要「按创建时间翻页，且能跳到某个时间点附近」；③ 一个风控规则要问「这两个账号之间是否存在不超过 4 层的关联」。分别选结构，说清每个选择省掉了什么，以及它的前提条件。

<template #answer>

① **固定大小的最小堆（Top-K）**，或退一步的两段式：一遍扫描用 `Map` 计数，然后把计数数组做 O(n) 的部分选择。选它的理由是内存与顺序：全量排序是 O(n log n) 且要处理全部条目，而大小为 20 的堆只占 20 个槽，每来一个与堆顶比一次。前提条件是**计数阶段必须先有 `Map`**（B 组那套：桶数要与 URL 种类数同量级，否则每次计数都在长链上比较）；如果 URL 种类本身就有几百万，内存里放不下的方案是外部聚合（数据库或流式统计），那就不是这道题的结构了。

② **平衡树的语义，兑现成数据库索引**（B 树家族）。关键在「跳到某个时间点附近」= **范围查询 + 有序遍历**，这两件事哈希结构做不到：`Map` 里没有「下一个」，只有「同一个桶里的下一个」。具体做法是在创建时间上建索引（若过滤条件常带租户 id，则复合索引按前缀顺序 `(tenantId, createdAt)`）。前提条件与代价：这是**读快写慢**的取舍，每次插入都要维护树；本站无数据库环境，索引是否真的被走必须用你的 `EXPLAIN` 确认，不能引用本章下结论。

③ **邻接表 + 限深 BFS**。这是可达性问题（层数限制 = 深度限制），E 组那张图的邻接表形状就是它的最小版：`Map<账号, 邻居[]>`，从起点按层扩展，`Set` 记已访问，深度到 4 停。选它的理由：「不超过 4 层」这个约束在 BFS 里就是「队列扩四层」，而 DFS 要么走完一整条深路才发现超限，要么需要额外剪枝。**不要用邻接矩阵**：账号数 n 的矩阵是 n² 空间，而关系数 m 通常远小于 n²，查边用 `O(deg)` 完全够用。前提是关系数据要能一次性载入内存；如果关系表在数据库里且要实时问，正确做法是限制深度地递归查询或引入图存储，那是另一个规模的问题。

</template>

</Exercise>
