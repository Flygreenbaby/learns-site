# 线性结构：一次 shift 搬走的是它后面的全部元素

你写了一个日志面板，新日志往头部插：`list.unshift(entry)`。几十条的时候没有任何感觉，到两万条时滚动开始掉帧。你去查性能，得到的解释是「数组慢，链表快」，于是写了双向链表，结果**更慢**——因为每次要在中间插入前，你得先走过去，而走过去这件事从来没被算进那句「O(1) 插入」。

第二种更普遍：`arr.shift()` 被当成队列的出队操作，一天调十万次。本站把这件事在本机数了一遍：一个数组式表在 n = 100,000 时**一次 shift 就搬移 99,999 个元素**（A 组）。不是「内存不够」，不是「V8 不行」，是那句话的字面意思：每出队一个元素，后面每一个都得挪一次位置。

第三种是判据用错地方：`arr.includes(x)` 写在一个循环里，看起来一行，实际是隐藏的一层循环；`new Array(50000)` 之后 length 是 50,000 而可迭代元素是 0 个，`map` 回调一次都不执行。这些都源于同一个误会——**把 JS 的 `Array` 当成教科书里那个「数组」**。它一半是数组，一半是带整数键的对象，两种身份之间的切换就是本章要讲的代价。

本章把四种线性结构的**成本形状**钉死：数组把成本放在「写中间」，链表把成本放在「读第 k 个」，栈和队列是接口而不是结构，JS 数组的真实行为要用实验而不是直觉判断。记号的严格定义与大 O 推演归[第 3 章](/computer-science/complexity)，这些结构上的算法（反转、遍历、二分）归[第 4 章](/computer-science/algorithms)，本章只管「选哪一个」。

## 数组买到的只有一件事：不看内容就能跳到第 k 个

连续内存的含义是「第 k 个元素的地址可以直接算出来」：起点地址 + k × 元素宽度。这一步不看任何前面元素的内容，所以随机访问是常数。代价写在同一句话的另一半——**位置本身就是信息**，你要在第 3 位插一个元素，第 3 位及之后每个元素的位置都变了，而位置就是它们「是谁的第几个」这个信息，必须逐个改写。

```text
=== A 线性结构的代价：本站实现里显式的搬移计数（不是 V8 内部 memmove） ===
  数组式表：n=1,000 一次 shift 搬移 999 次；n=100,000 一次 shift 搬移 99999 次（等于 n-1，逐行吻合）
  数组式表：在中间插入（k=n/2）搬移次数 = n-k；n=100,000、k=50,000 → 50000 次
  链表式：头部删除改指针 1 次（本站计数 1 次操作）；但随机访问第 50,000 个要走 50000 步（计数与下标逐字相等）
  形状结论：数组把成本放在「写中间」，链表把成本放在「读第 k 个」；两者都只有一个 O(1) 的端点操作
```

读 A 组要带着一个限制：那两个「数组式表」的数字来自本站手写的 `ArrayList`，它用一个显式计数器模拟了搬移；真实的 `Array.prototype.shift` 底层是一次内存块移动，比逐元素赋值快得多，**但次数是同一个**。所以本章说 shift 贵，说的是「与 n 成正比」这个形状，不是「它比链表慢多少倍」——后者本站没测，也不该由你猜。

还有一个容易被漏掉的性质：数组的连续内存对 CPU 缓存友好（顺序访问时预取有效），链表每个节点在堆上独立分配，遍历时是指针追逐。这是「链表在教科书复杂度里赢、在真实机器上经常输」的**唯一可靠解释方向**；具体到某个引擎、某个数据量谁赢，取决于缓存层级与分配器，本站不做这种断言。

## push 和 shift 不对称：尾部摊还，头部全额

数组在一端操作是常数的，另一端是线性的，而这个不对称经常被打平理解。「两端都叫队列」是接口层的事，实现层要分清三件事：

```ts
// ① 尾部：追加 + 偶尔整块搬家（摊还下来每次算常数，第 3 章讲这套记法）
arr.push(x);

// ② 头部：每次全额线性，没有摊还可言
arr.shift();                     // n-1 次搬移（A 组第一行）
arr.unshift(x);                  // 同样是 n 次搬移

// ③ 中间：先走过去（② 和 ③ 的隐藏前提），再搬后面全部
arr.splice(k, 0, x);
arr.indexOf(x);                  // 找不到时把整个数组走一遍
```

头部出队的正确做法不是换链表，而是**别再真的删**。三种形状按侵入性从低到高：

```ts
// 形状一：头指针法。不搬元素，只把「有效起点」前移；代价是数组永久占着已出队的格子
class QueueByHead<T> {
  private a: T[] = [];
  private head = 0;
  enqueue(v: T) { this.a.push(v); }
  dequeue(): T | undefined {
    if (this.head >= this.a.length) return undefined;
    const v = this.a[this.head];
    this.head++;
    if (this.head === this.a.length) { this.a = []; this.head = 0; }  // 空了才清零，否则前段永不释放
    return v;
  }
  get size() { return this.a.length - this.head; }
}

// 形状二：环形缓冲。固定容量 + 两个下标回绕，出队进队都是常数且不搬移。
// 适合「同时在场的元素数量有上限」的场景：缓冲区、滑动窗口、限流计数。
```

形状一的 `if (this.head === this.a.length)` 那一行是新手最容易漏的：**头指针法不清空的话，出队过的元素引用还留在数组里**，小对象攒成内存泄漏，大对象（比如你缓存的响应体）根本释放不掉。这是「结构选择」直接变成「线上问题」的典型一条。

## 链表的 O(1) 有个前提，而真实代码常常不满足它

链表那一端确实只改指针。但请把「改指针」的调用写全：

```ts
class ListNode<T> { constructor(public v: T, public next: ListNode<T> | null = null) {} }

function insertAfter<T>(node: ListNode<T>, v: T) {   // ← 前提：你手里已经有 node
  node.next = new ListNode<T>(v, node.next);
}

function find<T>(head: ListNode<T> | null, pred: (v: T) => boolean): ListNode<T> | null {
  let c = head;
  while (c) { if (pred(c.v)) return c; c = c.next; }  // ← 走到那个节点，线性
  return null;
}
```

`insertAfter` 是常数，但它要一个**已经在场**的节点引用。真实代码里你手里通常只有「一个 id」「一个下标」「一个排序键」，于是必须先 `find` 走过去——A 组数了：走到第 50,000 个要 50,000 步。链表真正赚的场景是**引用本来就握着**的那些：

- 你已经在遍历这条链，顺手摘掉当前节点（例如 LRU 缓存里命中后把节点移到队首——那种场景下每个节点的引用存在哈希表里，这才是「哈希 + 双向链表」这个组合为什么是 LRU 的答案）。
- 你需要 O(1) 合并两个序列（拼接两端），或者你根本不知道最终长度、且总是从两端进出。

反过来说，只要你的操作里有「第 k 个」「按位置插入」「按下标遍历」，链表的常数就一笔笔还回去了。**链表是「你已经站在节点上」时的最优解，不是「你怕数组搬移」时的最优解。**

## 栈和队列是接口，不是结构

这句话决定了你能不能看懂别人代码里的容器。栈是「后进先出」这一组操作（push / pop / peek），队列是「先进先出」（enqueue / dequeue）——两者的**语义**由接口规定，实现可以用数组、链表、环形缓冲，甚至两个栈。

```ts
// 用两个数组实现队列：in 只进，out 只出；out 空了才把 in 整块倒过来。
// 倒块这件事是线性的，但每个元素一生只被倒一次 ⟹ 摊还下来每次进出算常数。
class QueueByTwoStacks<T> {
  private inn: T[] = [];
  private out: T[] = [];
  enqueue(v: T) { this.inn.push(v); }
  dequeue(): T | undefined {
    if (this.out.length === 0) { while (this.inn.length) this.out.push(this.inn.pop()!); }
    return this.out.pop();
  }
}
```

要判断一段代码需要哪个接口，看它有没有这些语义要求：

| 需求信号 | 真正需要的接口 | 常见误用 |
| --- | --- | --- |
| 撤销、返回上一页、括号匹配、深度优先穷举 | 栈（LIFO） | 用 `slice().reverse()` 每次重建顺序 |
| 任务派发、消息缓冲、按到达顺序处理 | 队列（FIFO） | 用 `shift()`，把出队变成搬移 |
| 「谁最急给谁」而不是「谁先来给谁」 | 优先队列（堆，[第 2 章](/computer-science/data-structures-hash-tree-graph)） | 每次 `sort()` 后取第一个 |
| 只关心「在场的是哪些」 | 集合（`Set`） | 用数组 + `includes` 判重 |

第三行值得停一下：「每次排序取第一个」是最常见的隐形 O(n log n)。如果你只要最小的那一个，那是优先队列的职责；如果你要的是「第 k 小的全部」，那才是排序。这两件事经常被写成同一个 `sort`。

## JS 的 Array 不是教科书数组：length、空洞与身份切换

三个真实行为，每一个都能制造一类线上问题（下面三段是**结构示意**，本站没在浏览器或 Node 里跑过它们，预期结果按 MDN 语义推得）：

```ts
// ① 稀疏：length 与「可迭代元素个数」不是一回事
const holes = new Array(3);          // 3 个空洞，不是 3 个 undefined
holes.map((x) => x ?? 0);            // 预期：回调一次都不执行，仍得到 [empty × 3]
const real = Array.from({ length: 3 }, () => 0);  // 预期：真正填满的 [0,0,0]
real.length = 10;                    // 变长：追加 7 个空洞，length 与内容再次分家

// ② 键的形状：负数、超大整数、小数都不算「数组索引」
const weird: any[] = [];
weird[-1] = 'a';                     // 挂成属性，length 不变，for...of 看不见它
weird[2 ** 32 - 1] = 'b';             // 超出数组索引上限 ⟹ 退化成对象键
weird[1.5] = 'c';                    // 同上，不是索引

// ③ 大下标赋值：length 瞬间变成下标 + 1，中间全是洞
const far: any[] = [];
far[1_000_000] = 'x';                // length = 1000001，但只有 1 个元素
far.includes('x');                   // 预期 true；但这是一次完整扫描，不是查表
```

①那条是本页最容易踩的：`new Array(n)` 造出的是**空洞（holes）**，`map`/`forEach`/`filter` 会跳过空洞，而 `indexOf(undefined)`、展开运算符又把空洞当成 `undefined`——**同一个数组，两种遍历语义**。要用「长度为 n 的空数组」就写 `Array.from({ length: n }, fn)`，它保证每个位置都有真元素。

②③说的是引擎层面「这不是数组索引」的语言事实：一旦键不是 0 到 2^32−2 的整数，它就不在元素区里，而是挂在对象属性上；大量稀疏同样会改变内部表示。引擎具体切成哪种形态、阈值多少，**本站没有核实到官方资料**，你只需要记住结论的形状：稀疏数组与混类型数组在遍历语义和性能上都会跟紧凑数组不一样，别把 `Array` 当 `Map` 用。

## 选择判据：三个问题按顺序问

结构选择不是背诵，是三次判断。按这个顺序问，四章里所有例子都能落地：

1. **你的操作里有「第 k 个」或「按下标遍历」吗？** 有 → 数组（或环形缓冲）。链表在这个问题上没有任何优势，它的每次随机访问都是线性。
2. **你的高频操作在端点上吗？** 只在尾部追加/弹出 → 数组直接用，别加抽象。头出尾进（FIFO）→ 环形缓冲、头指针法或两个栈，**不要用 `shift`**。要按优先级取 → 那是堆，不是线性结构的事。
3. **你要的是「找得到」还是「排得前」？** 找（按 key 取值、判重、计数）→ `Map`/`Set`，见第 2 章；排（顺序、范围、Top-K）→ 树或堆，也在第 2 章。这一问是分水岭：绝大多数「我是不是该换个数据结构」的问题，答的是「我要的其实不是顺序」。

问完这三句，通常已经不需要第四个方案。剩下的才是特例：需要在中间频繁插入**且**你本来就一直握着节点引用，才轮到链表。

## 常见错误与排查

**1. 现象：列表越长越卡，且卡顿随条目数线性变差，不是突然崩。** 原因：每次渲染/处理都在头部 `unshift` 或 `shift`，把 n 次搬移乘上了操作次数。怎么确认：在浏览器 Performance 面板录一段火焰图，看自底向上里 `Array.shift` / `splice` 的占比；或把数组长度按 2 倍、4 倍喂进去，看总耗时是不是近似乘 4（那就是 n² 的形状，A 组那个 99,999 次搬移的乘积效应）。怎么修：改成尾部追加 + 渲染时反转顺序，或用头指针队列；**先别上链表**。

**2. 现象：`map` 出来的数组还是空的/带 undefined，但 length 正确。** 原因：数组是稀疏的，回调对空洞不执行。怎么确认：`arr.filter(() => true).length` 与 `arr.length` 一比，不相等就是有洞；`Object.keys(arr).length` 更能看出真实元素数。怎么修：用 `Array.from({ length: n }, fn)` 或先 `fill(0)` 再 `map`；如果是 `delete arr[i]` 造出来的洞，改用 `splice(i, 1)` 或重建成紧凑数组。

**3. 现象：内存一直在涨，但代码里明明 `shift()` 出队了。** 原因：头指针法的 `head` 前移不释放引用，或缓存数组只 `push` 不清理。怎么确认：拍两次堆快照，看那个数组对象上仍被引用的旧元素；再检查 `size` 是按 `length` 还是按 `length - head` 报的。怎么修：出队后把让出的槽位显式置 `undefined`（或直接 `null`），并在队空时重置数组，如上一节形状一那行代码。

**4. 现象：判重逻辑正确但极慢，或反过来「明明加过了又加一遍」。** 原因：`includes` 是线性扫描（隐藏循环），而用普通对象当集合时键被转成字符串——`obj[1]` 和 `obj['1']` 是同一个键，`obj[NaN]` 和 `obj['NaN']` 也是。怎么确认：把待判重的值类型打出来，看是否有数字/字符串混用；再数一下判重调用次数。怎么修：换 `Set`，它按零值相等比较键（`NaN` 能与 `NaN` 相等，`+0` 与 `-0` 视为同一个键），语义直接对上「判重」。

**5. 现象：代码换了链表实现之后整体更慢。** 原因：把「走到那个节点」的成本从复杂度里漏掉了，加上指针追逐对缓存不友好。怎么确认：在链表实现里给遍历加一个步数计数器（A 组就是这么数的），看每个业务操作实际走了多少步；再对照原来数组版本的搬移次数。怎么修：把「握着引用」这件事补上——用 `Map` 存 key → 节点，才是真正的 O(1)；否则退回数组 + 头指针/环形缓冲。

| --- | --- |
| `map` / `forEach` / `filter` | 跳过空洞，回调不执行 ⟹ 结果仍是稀疏的 |
| `indexOf(undefined)` | 找不到空洞（空洞不是 `undefined` 值） |
| `[...a]` / `Array.from(a)` | 空洞被读成 `undefined` ⟹ 得到长度正确的**紧凑**数组 |
| `JSON.stringify(a)` | 空洞序列化成 `null` ⟹ `[null,null,null]` |

最难查的是最后两行的组合：展开之后「看起来没问题」，`map` 却「一次都没跑」。修成紧凑数组的两种办法：`Array.from(a)` 或 `[...a]`（把洞转成值，再自己填）；或干脆重建 `Array.from({ length: n }, fn)`。写 `fill(0)` 之后再 `map` 也行，因为 `fill` 会把空洞变成真元素。

</template>

</Exercise>

<Exercise title="练习 3 · 给一个真实需求选结构并说清前提" difficulty="挑战">

需求：处理任务队列，要求「新任务从尾部进；取任务时优先取尚未处理最久的，但如果某个任务已被取过一次就永远不再重复取」，同时在任意时刻能回答「这个任务在不在队列里」。① 选出结构与辅助结构；② 指出这个方案里哪一步是线性的，怎么变成常数；③ 说明「已取过不再取」应该存在哪里、用什么判据。

<template #answer>

① 主体是队列（FIFO），辅助是集合。队列**不能用 `shift` 实现**——那是 A 组那条线性搬移。方案：环形缓冲或头指针法做队列；再用一个 `Set` 记「已经出过队的任务 id」，或者干脆把「在场/已取过」合并成同一份 `Map<id, 任务>` 加一个只存 id 的出队游标数组。判重这一问必须走 `Set`/`Map`，因为需求里含「任意时刻能回答在不在」，而数组只能靠扫描。

② 线性的是「判断是否重复出队」和「取出后从队列里消失」。前者由 `Set.has` 变成常数；后者由头指针/环形下标变成常数——**出队不需要移动任何元素，只需要承认起点变了**。如果实现里出现 `splice(0, 1)` 或 `filter(x => x !== t)`，那就是在用全量扫描做一件改两个下标就能完成的事。

③ 「已取过」不能靠从数组里删元素来表达（删就是搬移），要靠**状态**表达：一个 `Set<id>`（或 `Map` 上的一个状态字段）。判据要说清：`Set` 的键按零值相等比较，所以 `NaN` 能与 `NaN` 相等、`+0` 与 `-0` 是同一个键；但**对象键是按引用比的**，两个字段完全相同的 `{ id: 7 }` 是两个不同的键——所以这里必须存 id 这种原始值，不能存对象。这一条是本站在 MDN `Map` 页面核实到的原文语义，不是推演。

</template>

</Exercise>
