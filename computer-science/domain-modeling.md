# 选型题的正确答案，多半在你还没碰技术之前就定了

「用什么数据库」「要不要上 Elasticsearch」「要不要换 Postgres」——这类问题之所以难，不是因为选项难懂，而是因为**提问的顺序错了**。技术之间少有绝对优劣，多数差异要被你的数据形状、写入形态和运维人手压一遍才显出来。顺序错了，你就只能拿别人的结论当自己的答案，而别人的结论背后有一套你没有的前提。

现场大致是这样的三种之一。第一种，**同一个规则被写了四遍**：「退款金额不能超过实付」出现在前端校验、接口的 `if`、服务层的检查、数据库的一个约束里，其中两处口径不一致，于是有一类订单能退两次。第二种，**表结构是界面形状的**：页面上有一张宽表，数据库里就有一百二十列的宽表，两个月后加一个「部分退款」，谁都不敢动。第三种，**选型只比了 star 数**：换了新数据库，迁移做完才发现真正省下的那项本来可以用现有库的一条索引解决。

这三种现场对应本章的三块内容：**建模**（把规则收到一处）、**关系与约束**（把形状画对）、**选型方法论**（把决策依据从名词换成维度）。它们有先后：模型不清楚时，选型题无解。

## 建模的目的不是画图，是让每条规则只写一遍

先给一个不需要任何术语的判据：**同一件事的规则，在你代码里出现几次？**出现两次以上，就已经有人在两个地方维护同一个真相，不一致只是时间问题。

「订单」这个词在产品里和你库里很可能指两种东西。你说「订单」时指的是客户看到的那一张单（含状态、金额、地址快照、发票状态）；代码里的 `orders` 表指的是交易记录。「领域建模」这四年做的第一件事，就是强迫你把这两个名字对齐：写代码的人、写需求的人、看数据库的人用同一份词表，每个词只许有一个意思。这份词表不用长，半页足够，但它必须存在——否则「退款」在客服后台指部分退，在报表里指全额退，两个都对，两份代码都写。

有了词，再谈三个够用档的概念。**实体**是有身份、会变化的东西：两张 `id` 不同的订单即使字段完全一样也是两笔交易。**值对象**没有身份、只有值：金额 100.00 元与 100.00 元是同一个值，它不该有 `id`，也不该被「更新」，只能被替换。**聚合**是一组必须一起保持一致的对象，以及它们外面那道门：想改订单项，只能通过订单这个入口改，不能绕过订单直接改订单项那一行——因为「总额等于各项之和」这条规则只有订单能检查。

这三个概念的用处全在落点上。规则要写在域里，不是写在控制器或界面里：

```ts
// 反例：规则住在接口里，脚本导入与后台操作各写一遍，口径迟早不一致
app.post('/refunds', async (req, res) => {
  const order = await orders.byId(req.body.orderId);
  if (req.body.amount > order.paidAmount) return res.status(400).json({ error: '超出实付' });
  // ...还有 40 行同样属于「订单」的事
});

// 正例：规则住在域对象上，任何入口都只能经它走
export class Order {
  constructor(readonly id: string, readonly paid: Money, private refunds: Money[]) {}
  refund(amount: Money, today: Date): Order {
    const total = [...this.refunds, amount].reduce((a, b) => a.plus(b), Money.zero);
    if (total.gt(this.paid)) throw new DomainError('退款累计超过实付', { orderId: this.id, paid: this.paid.toString(), want: total.toString() });
    return new Order(this.id, this.paid, [...this.refunds, amount]);
  }
}
```

第二段比第一段「难读」，这是真的代价，本章不粉饰。它换来的是：**当第三个入口出现（定时任务、后台工单、CLI 脚本）时，你不需要再写一遍规则**。上一个项目里那个能退两次的 bug，出现的位置正是「后台工单那条路没走接口校验」。

## 从需求里挖对象：名词、动词、约束扫三遍

「建模」听起来要求你画 UML，实际动作比这朴素：拿一页真实需求（或十张工单），扫三遍，每遍只找一类东西。

第一遍只找**名词**，写下每个名词被提到的次数与它的修饰语。第二遍找**动词**，也就是要发生的事，把每个动词写成一句「谁对什么做了什么，结果必须怎样」——注意结果那半句，它是下一遍的材料。第三遍找**约束**，也就是需求里那些「不能」「必须」「同一时间最多」「超过就」的句子。第三遍最值钱，因为它找出来的是不变量。

| 需求原句 | 第一遍（对象） | 第二遍（行为） | 第三遍（不变量） |
| --- | --- | --- | --- |
| 「一本书同一时间只能被一个读者借走，逾期不能再借」 | 书、副本、读者、借阅 | 借出、归还、续借 | 同一副本最多一条未归还记录；有逾期则借出被拒 |
| 「退款金额不能超过实付，部分退款可多次」 | 订单、支付、退款 | 退款 | 累计退款 ≤ 实付 |
| 「导出超过 1 万行转后台任务，任务最多同时跑 3 个」 | 导出请求、任务 | 提交导出、执行、下载 | 未完成任务数 ≤ 3；行数阈值 10000 |
| 「同一邮箱只能注册一次，可用手机号找回」 | 账号、邮箱、手机号 | 注册、找回 | 邮箱唯一；手机号可复用还是唯一需要确认 |

产出物就是一张这样的表加半页词表，**不要更多**。画到第四页时你已经在编需求了。这张表真正的用处出现在两处：写数据库 schema 之前（第三列直接是约束和索引的依据），和选型之前（第二列的行为数量与第一列的对象数量决定了你的系统值不值得多一层中介）。

有一处必须提醒：这张表第三列里如果有你**判断不了真假**的句子，那是需求缺口，立刻回去问，不要靠猜补全。「手机号能不能被两个账号用」这种问题，猜错一次就要跑一次数据迁移。

## 不变量是模型的骨头，落点要分三层

不变量就是「任何时刻都必须为真」的那句话。它和「校验」的区别是：校验可以失败重来，不变量被破坏时数据已经坏了。

同一条不变量在三个位置各有一份工作，不是三份重复：

**域内断言**负责唯一性表达，也就是「这条规则是什么」——上一节那个 `throw new DomainError`。**数据库约束**负责兜住所有绕过代码的路径——`UNIQUE`、外键、`CHECK`、以及在并发下真正生效的那道锁。**入口提示**负责体验——让表单提前报错，不必等一次往返。只写第三层的项目一定会出事，因为「后台直接调 API」和「脚本批量导入」都不经过表单；只写第一层也一样，因为你无法用应用代码阻止两个并发事务同时插同一行。

```sql
-- 并发下真正拦住重复的那道，是数据库约束，不是代码里的 if
CREATE UNIQUE INDEX one_open_loan_per_copy
  ON loans (copy_id) WHERE returned_at IS NULL;

ALTER TABLE refunds
  ADD CONSTRAINT refund_within_paid CHECK (false);  -- 跨表累计无法用 CHECK 表达，见下
```

那句 `CHECK (false)` 是故意写的：PostgreSQL 的 `CHECK` 只能看本行，看不到「累计退款」这种跨行事实，所以这条不变量在数据库层要靠另一种落点——触发器、或者把累计值物化到订单行上并给它加约束。**「代码里写了规则」和「数据库里能验证规则」之间有一道能力边界**，认不出它的人会以为加了约束就安全了。这道边界的具体机制归[数据库](/database/)领域，本章只负责让你认出一道边界存在。

```text
借出这条流程，缺一个副本级并发保护时的典型时序（两请求同时通过 if 检查）：
  t0  读者A 请求借 copy#7 ── 代码查：无未归还记录 → 允许
  t1  读者B 请求借 copy#7 ── 代码查：无未归还记录 → 允许（A 的插入还没落）
  t2  A 插入 loans 行 → 成功
  t3  B 插入 loans 行 → 也成功，不变量已被破坏，且没有任何报错
```

`t3` 那一步是本节最重要的地方：**破坏不变量通常不给你异常**，它只给你一份坏数据，等你两个月后对账才发现。所以判据不是「有没有报错」，而是「有没有一条数据库约束会在这一刻拒绝第二次插入」。

## 关系与基数：画错一处，后面每次改表都在还

三种基数，各自的代价：

**一对多**（订单 → 订单项）最常见，做法是「多」的那一侧放外键。**一对一**（订单 → 发票）看起来像「把它合成一列更省事」，除非两边生命周期与访问模式一致，否则合成一列会让「发票状态」的更新去锁订单行。**多对多**（书 ↔ 标签）必须有一张中间表，把数组塞进一列 JSON 的做法不是不行，而是它会逐步拿走你的能力：按标签查书变成全表扫、统计「用过某标签的书数」变复杂、约束「同一标签不许重复挂」没地方放。

一个更准的判断口径：**别按界面形状设计表，按写入形态设计表。**页面要「一屏显示订单和全部退款」，不代表它们该在同一张表里；决定表怎么切的是「什么动作会改动什么数据、并发度多高、谁负责一致性」。多对多的那张中间表常常是「业务上的事实发生在这里」的地方（借阅表既是关系也是事实），这种时候它不该被叫作「连接表」，它有它自己的属性：借出时间、归还时间、经办人。

还有一条与选型直接相关的推论：**基数决定你能不能换存储**。如果你的多对多其实是「关系即事实」，那么任何不支持关系约束的存储都会让你把这件事写回代码——这条比「哪个库更快」重要得多。

## 技术选型的五个维度，以及每一维怎么查

这五维不是打分表，是**五个必须写下证据的问题**。填不满的那格就是你的风险位置。规则只有一条：**查到的东西要带日期和链接，查不到的写「未核实」，不要拿别人的结论当自己的前提。**

| 维度 | 要回答的问题 | 怎么查（可执行动作） | 常见自欺 |
| --- | --- | --- | --- |
| 成熟度 | 它在你这类用法上是否已经稳定 | 读它的 issue 列表里与你场景同名的条目；看破坏性变更频率与升级指南有没有写过「迁移脚本」 | 把「下载量大」当「在你这个用法上成熟」 |
| 社区与支持 | 出问题时多快能找到答案 | 数一下你能真正读懂的相关回答的数量与时间新旧；看维护者最近一次响应日期 | 只看 star 数，不看 issue 关闭时长 |
| 运维成本 | 谁来备份、升级、扩容，夜间出事怎么办 | 把「一次小版本升级」「一次备份恢复」写成两步命令试一遍；数你需要的常驻进程与人肉配置项 | 把「有 Docker 镜像」当「运维成本低」 |
| 与现有栈契合 | 是否复用你已有的连接池、鉴权、可观测 | 列出你已有的横切能力，逐项问「新组件要不要再造一遍」 | 忽略团队语言与生态带来的隐性成本 |
| 退出成本 | 三年后要换掉它，要走的路径是什么 | 写出「数据怎么导出」「依赖它的代码有几个文件」「哪些用法是不可移植的方言」 | 以为「用标准 SQL」就等于可退出 |

第三维和第五维对个人项目权重最高。理由很直接：一个人维护时，多一套需要备份与升级的东西，就是多一份永远排不到队里的运维债；而退出成本决定你不会在某个下午发现「换不掉，只能忍」。

## 用可逆性给决策分级：先做能改的，把不能改的推后有证据时

[上一章](/computer-science/architecture)给了分级的形状，这里给填法。判断一档决策是不是低可逆，只看一个问题：**改回来要动几个地方，以及动那些地方的成本是多少**。

**高可逆**（内部函数拆分、日志格式）：当场决定，不写记录。**中可逆**（缓存策略、模块边界、用哪个 ORM）：半页说明，写清重看信号。**低可逆**（数据模型与主键选择、对外字段名与消息格式、身份模型、以及「把业务真相存进某个专有格式」这类锁定）：必须留记录，必须写清「改回来的动作」。

三条个人项目最常用的经验：把低可逆的决定收窄到**一个文件**（你的对外契约只在一处拼装，改起来才只有一处）；能在有真实数据之后再定的，就不要在写第一行代码之前定（「先猜 schema 再迁数据」是新手最常见的返工来源）；把「将来可能要换」写成一条能观察的重看信号，而不是写成注释里的 TODO。

## 一个完整走一遍的例子：站内搜索选 SQL、全文索引还是专业引擎

需求取自本站真实存在的东西：五份已上线的运维文档，合计 159,045 B，切成 467 块，要支持中文查询「超时怎么排查」这类问题，并且要能给出可点开看原文的来源坐标。

**第一步，把问题写成形状清楚的问句**（不是「用什么引擎」）：数据量级多大、写入形态是什么、查询是词面匹配还是语义、要不要分面聚合与高亮、能不能接受多一个常驻进程。本站这份语料的答案是：静态文档、批量重灌、量级在千块而不是千万块、中文查询、需要来源坐标、单人维护、一台机器。

**第二步，按五维填表**。这里只能用本机实测的那半，其余老实标未核实：


那份记录里 `not_verified` 一栏不是装饰：它把「我没测过」这件事写在了决策旁边，半年后别人（或你）重看时，不会把你的保守当成结论。**如果只留三条结论不留那条限制，这份文档就变成了错误的来源。**

## 常见错误与排查

**一、把 ORM 实体当领域模型。**症状：`Order` 类只有字段和 getter，所有规则散在 service 里；加一个入口就要重写一遍规则。原因：表形状直接映射成了类。改法：先写不变量清单（第三节），再决定哪些规则必须在类里；表可以为查询服务，类必须为规则服务，两者不必同形。

**二、为不存在的需求建模。**症状：第一版就有七个抽象基类和一套「插件化」扩展点，而实际入口只有一个。改法：等第二个真实用例出现再抽；「边界早画、抽象晚做」在上一章写过，在这里同样成立。

**三、词表没对齐。**症状：产品说「客户」，代码叫 `user`，报表里是 `member`，三者口径其实不同。排查方式：拿那半页词表去搜代码，一个概念对应超过两个名字的，全都记下来。改法：改名一次到位（低可逆的对外字段除外），并把口径写进词表。

**四、不变量只写在界面层。**症状：手动操作没问题，脚本导入或并发一过就坏，而且没有报错（第三节那个 `t3`）。改法：数据库层加约束；并发窗口内的重复插入靠唯一索引，不靠代码里的 `if`。

**五、多对多用 JSON 数组塞一列。**症状：一开始很顺，半年后所有查询变成全表扫、约束加不上。改法：中间表；如果那份「关系」本身有属性，它本来就该是一张有主键的事实表。

**六、选型只比维度表的第一维。**症状：换成「更流行」的方案以后，运维成本项没减，代码里多出三处适配。原因：只看了成熟度，没看运维与退出成本。改法：五维每格都要有证据或写「未核实」，空着的格子就是风险位置。

**七、把别人的基准数字当自己的前提。**症状：照抄「某引擎 QPS 是某引擎三倍」的结论，上线后你的负载形态完全不同。原因：基准数字属于别人的数据形状、查询分布与机器。改法：用你自己的十份真实样本，在你能搭起来的最小环境里量一次；量不了就写未核实（第三节那 4 条无答案查询就是「自己数据才有自己结论」的例子）。

**八、决策不留记录。**症状：一年后「为什么不用专业搜索」无人能答，有人重提已被否决的方案，团队再花两周吵一遍。改法：五段结构（决定 / 可逆性 / 为什么 / 未核实 / 重看信号），半页，存在仓库里。

## 练习

<Exercise title="给一段真实需求扫三遍，交出词表、行为清单和不变量清单" difficulty="基础">

拿你自己项目（或本站任意一个领域）的一页真实需求，做三遍扫描：名词、动词（写成「谁对什么做了什么，结果必须怎样」）、约束（所有「不能」「必须」「同一时间最多」的句子）。交三样东西：不超过十个词的词表、按对象分组的行为清单、以及一份**能判断真假**的不变量清单。最后标出不变量清单里你自己判断不了的那几条——它们就是需求缺口。

<template #answer>

自查三个最容易失真的点。① 词表里出现同义词（「客户 / 用户 / 会员」并存）说明概念还没对齐，先合并再往下写。② 行为清单里若某个动词找不到对应的对象，通常意味着缺了一个实体（「续借」需要「借阅」和「借阅期限」两个对象）。③ 不变量必须是能判断真假的句子——「退款要合规」不是不变量，「累计退款金额不超过实付金额」是。判断不了真假的那几条要单列一栏，那才是这一遍扫描的真正产出：它给你的是三个必须回去问的问题，而不是看起来完整的设计。

</template>

</Exercise>

<Exercise title="故意只把不变量写在界面层，然后用并发把它打穿" difficulty="进阶">

选一条真实不变量（「同一副本同时只能有一条未归还借阅」「同一邮箱只能注册一次」）。第一步，只在表单校验里实现它，数据库不加任何约束。第二步，用两个几乎同时发出的请求（脚本、并发工具或两次连点）打同一个资源。第三步，查表并回答：有没有重复行？有没有任何错误返回？然后加一条约束重跑一次，比较两次 `t3` 时刻的行为差别。

<template #answer>

第一次的典型结果是：两行都进去了，两个请求都返回 2xx，**没有任何异常**——这就是为什么「跑了一遍没报错」不能证明不变量成立。第二次加上唯一约束后，其中一个请求会拿到数据库层的唯一冲突（错误形状取决于你的库与驱动），而且这条约束对你所有入口同时生效，包括你以后写的脚本和后台操作。要带走的两句话：**并发窗口内的唯一性只能由存储层保证**；**验证不变量的测试必须自己制造那个窗口**（两个并发请求、或同一批数据导入两次），单线程顺序测一百遍都测不出来。如果你在项目里做不到制造并发，退而求其次：把约束加上，再写一条「故意插入重复行」的测试，期望它失败——它失败了就证明约束在。

</template>

</Exercise>

<Exercise title="用五个维度给你现在项目里最贵的一次选型补一份证据表" difficulty="进阶">

挑一个你已经在用的技术（数据库、消息方案、某个第三方服务都行），按本章那张五维表把每格填成「一句结论 + 证据（链接或日期）」，填不满的格子写「未核实」。然后针对「退出成本」那一格，写出具体动作：数据怎么导出、有几个文件依赖它的专有语法、哪些用法换不掉。

<template #answer>

这一题的产出通常是一句让人不太舒服的话：**大部分格子的证据是别人的结论，而退出成本那一格从来没被查过**。三个检查点。① 成熟度与社区两格如果只有 star 数和「很流行」，把它们换成你在 issue 列表里读到的与你场景同名的条目编号与日期——查不到就写未核实，这本身就是信息。② 运维成本要落到两条能跑的命令上：一次小版本升级、一次从备份恢复。写不出恢复步骤的格子，风险是真实存在的。③ 退出成本那一格如果答案是「导出应该可以吧」，就现在做一次：真的导 100 行出来，看它们在下一个存储里能不能落地。专有方言（某种查询语法、某种索引类型、某种事务语义）用 grep 数一下出现次数，那个数字就是你未来的迁移工作量。

</template>

</Exercise>
