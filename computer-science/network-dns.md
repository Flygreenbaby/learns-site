# 域名解析不是一次查询，而是一串各自过期的缓存

「网站打不开」这句话里藏着四个完全不同的故障：名字解析不到、解析到一个没人监听的地址、连上了但 TLS 证书不对、连接通了而应用层返回错误。要区分它们，先要有把链路切段的标准语言——这就是分层模型要解决的事。本章把最上面那一段（名字到地址）讲透：一条 DNS 报文里有哪些字段真的值得记，谁在替你回答，以及**为什么「TTL 300 秒」不等于「5 分钟后所有人都看到新地址」**。

一个具体故障形状：你把域名从旧服务器迁到新服务器，A 记录改了，`nslookup` 已经返回新 IP，但你自己写的应用还在连旧地址，甚至有几个用户一整天都在连旧地址。这不是「DNS 没生效」，而是**解析路径上有好几层缓存，每层各自决定什么时候过期**，还有一层长连接把「已经建好的连接」钉在旧地址上。把它们逐个拆开，你才能回答「还要等多久」和「怎么现在就验证」。

本章的每个数字都要标明它从哪来、边界在哪：

<Callout type="verified">

**本章标为「本机实测」的内容**：Node v25.4.0 / Windows、2026 年 10 月 21 日，用 `.scratch/dns-wire.cjs` 直接向 1.1.1.1、8.8.8.8、根服务器和 example.com 的权威服务器发手工构造的 UDP DNS 查询，并从应答字节里解出标志位与每条记录的 TTL；另有 `nslookup`、PowerShell `Resolve-DnsName`、`node:dns` 三个入口的对照结果。脚本与完整输出留在 `computer-science/.scratch/`。

**边界**：这是**一台机器、一个网络出口、一次时间**的采样。TTL 数值会随查询时刻变化，IP 会变，权威服务器的 TTL 由域名所有者设定。本章用它们演示「字段读法」，不用它们断言任何普遍数值。

</Callout>

## 分层模型是给排障用的，不是给考试用的

**分层存在的理由只有一个：让「谁负责什么」变成可以指认的对象。** 如果一次访问是一整块，故障就只能说「不通」；切成段之后，每段有自己的名字、自己的错误形状、自己能观测的工具。

你日常写的 JavaScript 其实一直站在最上面一层。往下依次是：HTTP（消息与语义）→ TLS（加密与身份）→ TCP 或 UDP（端到端可靠/不可靠字节流或报文）→ IP（把包送到地址）→ 链路。DNS 不在这条栈里，它是**进入这条栈之前的查号台**：把一个人类可读的名字换成 IP，同时顺手告诉你这个答案的保质期。

两个概念要一次钉死：**IP 回答「哪台机器」，端口回答「这台机器上的哪个服务」**——同一台服务器上 nginx 监听 80/443、Node 监听 3000 就靠端口区分，所以「IP 通了但请求失败」完全可能（练习 3 专门制造一次）；**域名与 IP 是多对多**——实测 `developer.mozilla.org` 一条 CNAME 后面挂 4 个 A 记录，`example.com` 挂 2 个，而一个 IP 上可以托管几十个域名，这正是下一章 SNI 存在的原因。

| 这一段坏了 | 你看到的症状 | 能观察它的手段 | 本站对应章节 |
| --- | --- | --- | --- |
| 名字解析 | 报域名错误、`ENOTFOUND`、解析要几秒 | 本章的报文/记录/TTL 读法 | 本章 |
| 路由可达 | 一直转圈、超时、没有任何应用层错误 | `ping`（ICMP，另一个协议）、运营商路由 | 本章 + [网络诊断与防火墙](/linux/networking) |
| 端口/连接 | `ECONNREFUSED`、RST、SYN 重传后超时 | 下一章的握手与状态机 | [TCP、UDP 与 TLS](/computer-science/network-tcp-tls) |
| 身份与加密 | 证书警告、`unable to verify the first certificate` | 下一章的证书链字段 | 同上 |
| 应用语义 | 状态码、慢、缓存不更新 | 第七章的头字段读法 | [HTTP 演进与 CDN](/computer-science/network-http) |

## 一条报文里只有六个字段值得记

DNS 查询与应答共用一个格式。头部 12 字节，你真正需要会读的只有这些：

| 字段 | 含义 | 为什么值得记 |
| --- | --- | --- |
| 事务 ID | 16 位随机数，应答原样带回 | 客户端靠它把应答配对了查询；配不上就丢弃（这也是为什么 DNS 曾被用来做反射攻击） |
| QR | 0 是查询，1 是应答 | 抓包时唯一的「谁在说话」判据 |
| **AA** | 应答服务器**是该名字的权威** | 区分「官方答案」与「二手答案」的唯一标记 |
| **RD / RA** | 请求方要求递归 / 应答方支持递归 | 决定你是拿到答案，还是拿到「去问别人」的指引 |
| **TC** | 应答被截断 | 置位时要换更大的传输通道重问 |
| 四个计数 | 问题 / 答案 / 权威 / 附加各多少条记录 | 判断应答形状：答案在哪一段全靠它 |

规范里的原话值得直接引用（RFC 1035 第 4.1.1 节，[原文可访问](https://www.rfc-editor.org/rfc/rfc1035.txt)，核实时间 2026 年 10 月）：AA 位「specifies that the responding name server is an authority for the domain name in question section」；RD「directs the name server to pursue the query recursively. **Recursive query support is optional**」；RA「denotes whether recursive query support is available in the name server」。

**「递归支持是可选的」这一句是整个 DNS 拓扑的根。** 它意味着同一个查询发给不同服务器，你拿到的东西性质不同：给递归解析器（1.1.1.1、8.8.8.8、你 broadband 运营商给的地址）会拿到答案；给根服务器会拿到「去问顶级域」。下面就是本机读到的真实字段。

```text
向 1.1.1.1 问 example.com 的 A 记录（本机手工报文，实测 2026-10-21）

QR=1 AA=0 RA=1 TC=0 rcode=0 计数[问题,答案,权威,附加]=[1,2,0,0]
    答案段 example.com  A  TTL=151  172.66.147.243
    答案段 example.com  A  TTL=151  104.20.23.154

向权威服务器 hera.ns.cloudflare.com（解析到 108.162.192.162）问同一个名字

QR=1 AA=1 RA=0 TC=0 rcode=0 计数=[1,2,0,0]
    答案段 example.com  A  TTL=300  104.20.23.154
    答案段 example.com  A  TTL=300  172.66.147.243
```

两个结论直接从字段里读出来，不需要相信任何人：**AA=1 且 RA=0 的那台才是权威服务器**（递归解析器不是权威，AA 必须为 0；它支持递归，所以 RA=1）；**权威给出的 TTL 是 300，二手答案给的是 151**，同一个答案在传递过程中 TTL 正在倒计时。这条比「哪个工具更准」可靠得多——工具的输出没有这些位，报文里有。

## 递归解析器、权威服务器与 referral：谁在替你回答

「解析一个域名」在教学里常被画成一步，实际是一条链。两种模式的形状由 RD/RA 两个位决定，必须分清：

```text
递归：你的应用 ──问题──> 递归解析器 ──> 根 / .com / 权威（这三跳由解析器代跑）
                                     └── 只把最终答案返回给你的应用
迭代：你的应用 ──> 根（回「去问这 13 台」）──> gtld（回权威的名字与粘附地址）──> 权威（回 A，AA=1）
```

本机实测正好把这两条各钉了一次死。向 `a.root-servers.net` 问 `example.com` 的 A，应答是：

```text
QR=1 AA=0 RA=0 TC=1 rcode=0 计数[问题,答案,权威,附加]=[1,0,13,11]
    权威段 com  NS  TTL=172800  l.gtld-servers.net
    权威段 com  NS  TTL=172800  j.gtld-servers.net   …（共 13 条）
```

**答案段是 0 条，权威段 13 条，RA=0**——根服务器明确告诉你「我不递归，去问这 13 台」。这就是 referral（转介）。看到「计数[1,0,13,*] + RA=0」，你就知道自己在跟权威层级说话，而不是在跟解析器说话。

而递归解析器替你把上面几跳做完，代价是：**答案的权威程度降一层（AA=0），并且它会缓存。** 缓存本身不是问题，各自独立缓存才是问题。本机对同一个名字问 1.1.1.1 与 8.8.8.8，两条记录的 IP 完全相同，返回的 TTL 分别是 **151** 与 **137**，而权威服务器给的是 **300**——同一个答案同时在三个地方按三个时钟倒计时。

**还有一个更容易踩空的入口：你的程序查 DNS 有两条路径，其中一条根本拿不到 TTL。** Node 的 `node:dns` 模块：`dns.resolve*()` 自己发 UDP 报文去问 `dns.getServers()` 里的服务器；`dns.lookup()` 调系统 `getaddrinfo`，走操作系统解析路径（含 hosts 文件、系统缓存，且**不返回 TTL**）。本机实测把两者的差别暴露得很干净：

```text
dns.getServers() = ["127.0.0.1"]

dns.resolve("nodejs.org", "A")          → ECONNREFUSED
dns.resolve("example.com", "A")         → ECONNREFUSED（A/AAAA/CNAME/NS/SOA/MX/TXT 六种类型全部 ECONNREFUSED，一次 ETIMEOUT）
dns.lookup("nodejs.org", {all:true})    → 2606:4700::6810:d483(family 6)、2606:4700::6810:d583(6)、104.16.212.131(4)、104.16.213.131(4)

换成 resolver.setServers(["1.1.1.1","8.8.8.8"]) 后
dns.promises.Resolver 问 developer.mozilla.org A → 151.101.193.91 等 4 条，成功
```

这台机器上 `dns.resolve` 全线失败而 `dns.lookup` 完全正常，原因不是「DNS 坏了」：本机 DNS 服务器被设成了 `127.0.0.1`（某个本地软件在接管系统解析路径），而那个地址不接 UDP/53 的直连查询。把服务器换成公共解析器之后 `resolve` 立刻成功。

这条实测值得抄下来的不是结论，是**方法**：同一份数据从四个入口各问一遍（`dns.lookup`、`dns.resolve`、`nslookup`/`Resolve-DnsName`、手工报文），结果两两不同就能定位到哪一层在骗你——**工具没给你某个字段，不代表协议里没有**。

## 记录类型回答的是不同问题

类型不是要背的名词，每个类型对应一个具体问题。全部取自本机实测应答：

| 类型 | 回答的问题 | 本机实测的样子 |
| --- | --- | --- |
| A / AAAA | 这个名字的 IPv4 / IPv6 地址 | `nodejs.org` A 两条（104.16.212.131 / 104.16.213.131，TTL=32）；`lookup` 同时拿到 2 条 v6 + 2 条 v4 |
| CNAME | 这个别名的**规范名**是谁 | `www.github.com` → `github.com`；`developer.mozilla.org` → `mozilla.map.fastly.net` |
| NS | 谁能权威回答这个zone | `example.com` 两条 NS：`hera.ns` / `elliott.ns.cloudflare.com`，TTL=64257 |
| A（粘附记录 glue） | 那台 NS 自己怎么连上 | `hera.ns.cloudflare.com` 三条 A，TTL=86353 |
| SOA | 这个 zone 的负责人与刷新参数 | 见下面那段实测 |
| MX / TXT | 邮件投递到哪 / 给这个挂任意文本（域名验证、SPF） | 本机对 `example.com` 未取到 MX 内容（类型查询成功但答案为空） |

注意 A 与 AAAA 是两条独立记录，各自有 TTL（`nodejs.org` 的 A 实测 TTL=32）。**IPv6 与 IPv4 的有效期可以不同，所以「双栈」在解析层是两个独立问题**：v6 配错而 v4 正常、或反之，症状就是「部分网络能上部分不能」。

CNAME 链最该记住的一件事：**链上每一环的 TTL 各自独立，决定你多久必须重问的是最短的那个。** 本机对 `www.github.com` 的一次查询里同时出现：

```text
答案段 www.github.com  CNAME  TTL=3598  → github.com
答案段 github.com      A      TTL=58    → 20.205.243.166
```

别名几乎不变（3598 秒 ≈ 1 小时），而目标地址故意设成 58 秒。于是「`www.github.com` 这个名字要不要重问」几乎总是否，「它最终指向哪个 IP」每分钟都要重问。看到「同一个应答里两个 TTL 差几十倍」不要以为读错了，那是设计意图：**缓存链上最短的那个 TTL 决定你的恢复时间**，而不是你在后台改的那个数字。

SOA 是唯一同时告诉你「怎么刷新」和「错了要记多久」的记录，本机实测：

```text
example.com  SOA  TTL=1800
  mname   = elliott.ns.cloudflare.com        （主权威）
  rname   = dns.cloudflare.com               （负责人，邮件地址用点代替 @）
  serial  = 2418004112                       （区域序号：从旧权威刷新到新权威靠它判断有没有变）
  refresh = 10000                            （二级服务器 2 小时 46 分问一次有没有更新）
  retry   = 2400                             （刷新失败后 40 分钟重试）
  expire  = 604800                           （7 天联系不上主权威就放弃应答）
  minimum = 1800                             （否定答案的缓存上限）
```

这台机器上另一个入口给出的数字与此逐字相同（`nslookup -type=SOA example.com 1.1.1.1` 打印 `serial = 2418004112`、`refresh = 10000 (2 hours 46 mins 40 secs)`、`default TTL = 1800 (30 mins)`）。**两套独立实现给同一组字节 → 手工解析没读错字段**，这个交叉核对方式比相信任何一个工具更值得学。

`minimum` 那个字段是最后一节的入口：它管的是**否定答案**的缓存期限。

## TTL 是一条链的上限，不是所有人的义务

先钉一个容易被误解的事实：TTL 不是「服务器命令你缓存多久」，而是「我最多允许你缓存多久」。规范原话（[RFC 2181 第 8 节](https://www.rfc-editor.org/rfc/rfc2181.txt)，已核实）：TTL 是无符号数，最大 `2^31 - 1`；实现「are always free to place an upper bound on any TTL received, and treat any larger values as if they were that upper bound. **The TTL specifies a maximum time to live, not a mandatory time to live.**」

也就是说：任何一层都可以**提前**丢弃缓存（内存不够、进程重启、服务发现主动失效），但**不能延后**。这条不对称就是你迁移域名时看到「部分用户还在旧 IP、部分已经到新 IP」的根源。

一次域名变更之后，答案沿这条链逐层过期：

| 哪一层在缓存 | 期限由谁决定，怎么让它立刻失效 |
| --- | --- |
| 应用的连接池 / 长连接 | 与 TTL 无关：连接建好就不再查 DNS。只能重启进程或等空闲回收（这是连接池配置项，见[连接池与慢查询](/data-storage/connection-pool-and-slow-query)） |
| 浏览器 / HTTP 客户端 | DNS 缓存归 OS，页面缓存归 HTTP（第七章）；硬刷新不清系统缓存 |
| 操作系统的解析器缓存 | OS 自己的策略，部分实现会自己封顶；刷新命令各家不同，以本机文档为准 |
| 递归解析器 | 权威给的 TTL 倒计时，**没有办法提前失效**，只能等（本章实测剩余 151/137） |
| 权威服务器之间 | SOA 的 refresh 与 serial：递增 serial 让二级服务器拉新 |

**「还要等多久」的正确答案是：从「最长的那条缓存链」算，不是从你设的 TTL 算。** 实践上按这三步走，不需要任何特权工具：

1. 变更**前**提前把 TTL 调低（常见做法：从 86400 调到 300，等待一个旧 TTL 周期再改），这样变更时刻已经在缓存里的答案最多只能再活 300 秒。**必须在变更前做**——改完记录之后再调 TTL，救不了已经按 86400 缓存出去的解析器。
2. 变更后用多个互不相干的递归解析器验证，而不是只问本机。像本章那样向 1.1.1.1 与 8.8.8.8 各问一次，看剩余 TTL：数值接近权威给出的原始 TTL 说明刚拉新，明显偏小说明还在吃缓存。
3. 保留旧服务器可用一段时间（旧 IP 上继续服务，或让它 301 到新址）。**长连接不受 TTL 控制**，所以「旧服务器还能响应」这段时间要按业务最坏情况留够，判据在下一章的 TIME-WAIT 与[发布与回滚](/devops/release-and-rollback)。

否定答案同样有缓存，机制不同：名字不存在时（rcode 表示 NXDOMAIN），解析器缓存的期限取 **SOA 的 minimum 与 SOA 自身 TTL 中较小的那个**（[RFC 2308 第 5 节](https://www.rfc-editor.org/rfc/rfc2308.txt)，已核实）。所以「刚加上的记录查不到」也会持续一段时间，而且这段时间你从记录本身读不出来——它写在区域的 SOA 里。本机读到的 `minimum = 1800` 就是这个数。

这里必须如实报告一个**与教科书不一致的本机观察**：向 1.1.1.1 查询一个必然不存在的名字（`this-should-not-exist-20261021.example.com`），本机收到的是 `rcode=0`（NOERROR）、`计数[1,0,1,0]`、权威段带 SOA（TTL=1800），**而不是 NXDOMAIN(3)**。本站没有查明原因（可能是本地网络路径对 DNS 报文的处理，也可能是解析器行为），不编造解释。它教的是一条更重要的判断：**同一个查询在不同网络里可能拿到不同的 rcode，出现这种不一致时先怀疑中间有人在改写你的包，再怀疑域名配置。** 复现方法就是本章那三个入口对照着问。

## 常见错误与排查

**1. 现象：`nslookup` 已经返回新 IP，但我的 Node 服务还在连旧地址。**

原因：你的服务不通过 `nslookup` 那条路径。常见的是两类：连接池里已建立的长连接根本不再查 DNS；或者应用走系统 `getaddrinfo`（`dns.lookup`），而系统缓存仍给旧值——实测显示这台机器上 `dns.resolve` 与 `dns.lookup` 的行为完全不同（前者 ECONNREFUSED，后者返回 4 条地址）。

怎么确认：在应用侧打印每次建立连接时实际使用的目标 IP（不要打印域名），与 `Resolve-DnsName` 的返回对比。若 IP 一直是旧的而系统查询已是新的，问题在连接池；若两者一致地旧，问题在系统/解析器缓存。

怎么修：连接池要有最大存活时间或空闲回收（这是连接池配置项，不是 DNS 配置项）；对高频外部服务，让客户端定期重建连接而不是永久复用。

**2. 现象：TTL 设成 300，迁移后仍有用户长时间打到旧 IP。**

原因：三层叠加——旧答案在某个递归解析器里按更早的长 TTL 缓存着；某些实现有自定的 TTL 上限/下限；长连接不受 TTL 约束（见上一节表格第 1 行）。

怎么确认：向多个不同递归解析器问同一个名字，把各自返回的剩余 TTL 记下来。数值分布很散说明缓存链上有多个独立计时器，此时任何单点验证都会给你假的成功。

怎么修：变更前降 TTL + 旧 IP 继续服务一段时间 + 监控旧服务器流量归零后才下线。**判断「什么时候能下线」用流量指标，不用时钟。**

**3. 现象：记录改了，`Resolve-DnsName` 的 TTL 列却是空的（本机就是这样）。**

原因：工具没有展示该字段，或该查询命中了不给 TTL 的缓存路径。协议里 TTL 一定存在（应答的资源记录第 9–12 字节），只是这个工具没解出来给你看。

怎么确认：换一个能读到字节的入口。本章的 `.scratch/dns-wire.cjs` 直接把应答字节切出来，151 和 137 就是这么读到的；`nslookup -type=SOA` 能拿到 `default TTL`。

怎么修：排查 DNS 问题时不要依赖单一工具的字段可用性；需要 TTL 就明确用它存在的地方（报文），并像本章那样拿第二个工具交叉核对 SOA。

**4. 现象：加了 CNAME，邮件或域名验证就配不上，配置页报冲突。**

原因：CNAME 表示「这个名字只是别名」，同一名字上再挂 MX/TXT 与它语义冲突，多数服务商会在配置页直接拦住。

怎么确认：把冲突提示原文记下来，并查该服务商文档确认它是否提供 ALIAS/ANAME/CNAME flattening 这类「在 apex 上伪装 CNAME」的记录类型。本站未在任一服务商控制台验证各家行为，以你所在服务商文档为准。

怎么修：需要同时是别名又要有其他记录的名字，改用服务商的 flattening 类型，或把邮件与验证记录挪到一个不带 CNAME 的名字上。

**5. 现象：DNS 查询偶发超时，重试之后正常，业务把它报成「第三方服务不稳定」。**

原因：UDP 上的 DNS 本来就允许丢包（本章第二次连续查询实测 `timeout 5s`）；应答过长时 TC 置 1，需要换 TCP 重问；部分网络对 UDP/53 限速。

怎么确认：看失败率的分布——如果超时集中出现在某个时段或某类查询（返回记录很多的名字），截断与限速的嫌疑大于服务器故障。

怎么修：客户端给解析设**有限**超时和**幂等**的重试，并把「解析失败」与「连接失败」分开上报，否则 DNS 抖动会被计到别人的服务上（上报方法见[日志与监控](/backend/logging-and-monitoring)）。

## 练习

<Exercise title="四个入口问同一个名字，把差异写下来" difficulty="基础">

在你自己的机器上，对同一个域名（建议就用 `example.com`，与本章实测可对照）分别用四个入口查询，逐个记录**真实输出**，包括失败：

1. Node 的 `dns.lookup(name, {all: true})`；
2. Node 的 `dns.resolve(name, "A")`（不要改 `setServers`，先看默认行为）；
3. 系统工具（Windows 用 `Resolve-DnsName -Name example.com -Type A -DnsOnly`，macOS/Linux 用 `dig A example.com`）；
4. 本章的 `computer-science/.scratch/dns-wire.cjs`（`node computer-science/.scratch/dns-wire.cjs`）。

然后回答：哪两个入口给了 TTL、哪两个没给？哪两个结果与 `1.1.1.1` 那份不完全一致，为什么？

<template #answer>

字段可用性是这道题的收获，不是数字一致。

1. `dns.lookup` 走系统 `getaddrinfo`，返回地址与 family，**没有 TTL**——本机它返回 4 条地址（2 条 v6 + 2 条 v4）。
2. `dns.resolve` 自己发 UDP 报文问 `dns.getServers()`。本机它对六种类型全线 `ECONNREFUSED`（这台机器把系统 DNS 设成了 `127.0.0.1`，而那个地址不接直连查询）。你的机器很可能正常返回——**这一步的作用是证明「同一份 API 在不同机器上行为可以完全不同」**。
3. 系统工具：`Resolve-DnsName` 本机 `TimeToLive` 列为空；`dig` 会打印每行 TTL 与 `flags: qr rd ra`，可与第 4 步逐字对照。
4. 手工报文同时给出标志位与 TTL，是四者里信息最全的。

出现不一致时按可能性排序解释：各解析器缓存的剩余期限本来就不同（本章 151 与 137 就是同一答案的两个计时器）、`resolve` 与 `lookup` 是两条路径、本地有中间件改写。判断顺序固定：先用 AA/RA 确认被问者身份，再比 TTL。

</template>

</Exercise>

<Exercise title="读出一条记录的 TTL，并判断它有没有在倒计时" difficulty="进阶">

写一个最小的 DNS 客户端（可以照抄 `.scratch/dns-wire.cjs` 的 `buildQuery` 和 `parse`，它们加起来不到 60 行），完成三件事：

1. 向 `1.1.1.1` 查 `nodejs.org` 的 A，打印每条记录的 TTL 与 `AA`/`RA` 位；
2. 立刻再查一次同一名字，比较两次的 TTL；
3. 从应答的 NS 记录里取一个权威服务器名字，解析出它的 A，直接问它同一名字，比较 TTL 与 `AA`。

前提说明：这道题需要能出网的 UDP/53，**任何一步失败都算正常结果**（本章就遇到一次 5 秒超时）。把失败原样写进记录，不要改成「预期应该」。

<template #answer>

1. 实测形状：`AA=0 RA=1`，两条 A 记录 `TTL=32`（这个值很短，是 CDN/云厂商常用做法，便于快速换 IP）。标志位说明你在跟递归解析器说话。
2. 两次之间 TTL **相等或减少**：减少说明第二次命中了同一份缓存并正在倒计时；相等说明间隔小于计时粒度或两次都刚从权威拉回。变多则说明被问的不是同一份缓存（或你换了一台解析器）。**不要期望看到某个具体数字**，本节本机数据是 151/137/300，权威值由域名所有者设定，与你的机器、你的时刻有关。
3. 问权威时应答的 `AA=1`、`RA=0`，TTL 等于该记录的原始设定值（`example.com` 上是 300）。这一步是「原始值 vs 剩余值」的唯一可靠区分法：**只有权威服务器能给原始 TTL**。

如果你把这三步的数字排成一行：`权威=300 → 1.1.1.1=151 → 8.8.8.8=137`，你已经用报文同时证明了「TTL 是倒计时」和「各解析器独立计时」。结论里不要写「DNS 缓存 5 分钟」——权威给的是上限，各层实际留多久无法从单点观察得出。

</template>

</Exercise>

<Exercise title="故意让「解析正常」和「服务不可用」同时成立" difficulty="挑战">

构造一个 DNS 成功但请求失败的现场，并证明故障**不在**本章这一段。两种做法任选：

- 把某个你可控的子域名的 A 记录改成一个「地址合法但没有任何服务」的 IP（比如同网段一个未使用的地址；不要指向别人的机器）；
- 或者不改域名，直接对目标 IP 用一个未开放的端口发请求（`http://那个IP:8099/`，本机没监听即可）。

记录三件事：解析有没有报错、TCP 连接的错误码原文、以及 `ping` 同一地址的结果。然后回答：为什么 `ping` 成功而 HTTP 失败时，说「DNS 有问题」是错的？

<template #answer>

预期分层（请按你机器上的真实输出改写，本站未在网络环境上跑完这个实验）：

1. 解析阶段**没有任何异常**：`Resolve-DnsName` 与手工报文都正常返回 AA/RA 与 TTL。DNS 的职责到「交出地址」为止就已完成。
2. 连接阶段报错来自传输层：端口无人监听通常是立即 `ECONNREFUSED`（对端回 RST）；地址不存在于路由可达范围则是 SYN 重传直到超时，表现为「转圈几十秒」。**两种失败在 DNS 层看不出任何区别**，但在耗时形状上完全不同：一个快死、一个慢死。为什么是这个次数，下一章讲。
3. `ping` 用的是 ICMP，既不碰 DNS 也不碰端口。所以「`ping` 通 + HTTP 失败」的组合恰好说明前两段都好、坏在端口/服务；反过来「`ping` 不通 + HTTP 失败」也不等于 DNS 坏了，ICMP 常被防火墙单独丢弃（见[网络诊断与防火墙](/linux/networking)）。

这题只要求你会做一件事：**把「打不开」翻译成「哪一段坏了」**，并且每段用各自的证据回答。可用的检查顺序：报文里读标志位（解析对不对）→ 用错误码区分 RST 与超时（连上不连上）→ 才有资格谈证书与应用层。下一章给第二段的完整判据，第七章把第三段的头字段读法补上。

</template>

</Exercise>

## 官方文档与延伸阅读

- [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.txt) —— 核实「六个字段」一节：AA、RD、RA 与 RCODE 的定义原文（第 4.1.1 节），包括「递归支持是可选的」这句决定整个拓扑的话。
- [RFC 2181](https://www.rfc-editor.org/rfc/rfc2181.txt) —— 核实第 8 节「TTL 是最大存活时间，不是强制存活时间」与 TTL 上限 `2^31 - 1`，以及第 9 节 TC 置位后改用更大通道重问。
- [RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.txt) —— 核实否定答案的缓存期限取 SOA MINIMUM 与 SOA 自身 TTL 的较小值（第 5 节），支撑「刚加的记录查不到也要等一段时间」。
- [MDN · DNS 术语条目](https://developer.mozilla.org/zh-CN/docs/Glossary/DNS) —— 读者速查入口（2026 年 10 月核实可访问，状态码 200）。

三个 RFC 链接都由本站于 2026 年 10 月直接下载正文并从中引用原句，不是二手转述；引用只给结论与原句，未复制整段。

- 站内相关：[复杂度分析](/computer-science/complexity)（为什么本章不测毫秒）、[TCP、UDP 与 TLS](/computer-science/network-tcp-tls)（下一章）、[网络诊断与防火墙](/linux/networking)、[HTTP 演进与 CDN](/computer-science/network-http)。
