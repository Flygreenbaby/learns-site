# 阻塞的意思不是没返回，而是那根线程也被占住了

磁盘告警的现场通常是这样的：日志明明按轮转策略删掉了，`df` 的数字一动不动；重启那个 Node 进程，可用空间瞬间回来。没有人写错删除代码，只是有一份文件被删掉了名字，却还被一个没关的句柄握着。

内存告警的形状更迷惑。监控面板上进程 `rss` 涨到 800 MB，同时间打印 `process.memoryUsage().heapUsed` 只有 60 MB，于是有人认定「指标坏了」或者「Node 不报真实内存」。两个数都没坏，它们量的不是同一件事：一个是这个进程在物理内存里占的位置，一个是 V8 堆里还留着引用的对象。中间那一大段是 Buffer、C++ 侧对象和运行时自己。

第三种现场最难看：接口 p99 抖得厉害，CPU 曲线却很平。真相往往是这台机器上有四类工作在抢同一批稀缺位置——不是 CPU，而是文件系统与部分加密操作共用的那几条线程。这类任务不看 CPU，看队列。

<Callout type="verified">

**本机实测**（Node v25.4.0 / Windows，2026-10-21，脚本 `computer-science/.scratch/os-mem-probe.cjs`、`os-io-probe.cjs`，后者分别用未设置与 `UV_THREADPOOL_SIZE=8` 各跑一次）：`process.memoryUsage()` 五个字段在「持有 40 万个对象 / 强制回收 / 分配 32 MB Buffer」三种状态下的读数；`--max-old-space-size=64` 的子进程 OOM 崩溃文本与退出码；同步读与异步读期间每 20 ms 心跳的执行次数；8 个等量 `crypto.pbkdf2` 的完成批次分布；线程池排满时 50 个 loopback TCP 请求的完成情况；连续 `openSync` 不关撞到的错误码；持有句柄删除文件后可用空间的变化。

## 一个进程的内存有好几个口径，别把它们当一个数

先给定义，全部来自 Node 官方文档对 `process.memoryUsage()` 的说明：`heapTotal` 与 `heapUsed` 指的是 V8 的内存使用；`external` 指的是绑定在 V8 所管理的 JavaScript 对象上的 C++ 对象内存；`rss`（Resident Set Size）是「进程在主存设备上占用的空间，即已分配内存的一个子集，包含所有 C++ 与 JavaScript 对象和代码」；`arrayBuffers` 是 `ArrayBuffer` 与 `SharedArrayBuffer` 分配的内存，**包含所有 Node `Buffer`**，并且这一项也被计入 `external`。

这四句话已经把两台监控面板对不上的原因写完了：`rss` 是最大的那个口径，`heapUsed` 只管 JS 对象，`Buffer` 走的是另一条路。本机一轮实测（`--expose-gc`，单位 MB）：

| 状态 | rss | heapTotal | heapUsed | external | arrayBuffers |
| --- | --- | --- | --- | --- | --- |
| 刚启动 | 35.0 | 5.4 | 4.3 | 1.6 | 0.0 |
| 持有 40 万个对象 | 123.1 | 87.1 | 62.1 | 1.6 | 0.0 |
| 放开引用并强制回收后 | 113.7 | 38.1 | 4.0 | 1.6 | 0.0 |
| 再分配 8 个 4 MB `Buffer` | 141.8 | 38.1 | 4.0 | 33.6 | 32.0 |

三行数字对应三个判据，比任何形容词都直接。

**`heapUsed` 跟着「还留着的引用」走。** 40 万个对象挂在一个变量上，`heapUsed` 从 4.3 涨到 62.1（+57.8）；把变量置空再 `global.gc()`，它回到 4.0（回落 58.2）。这一项是 JS 层最好用的信号。

**回落不等于还给操作系统。** 同一次操作里 `rss` 只从 123.1 降到 113.7（变化 −9.4），远远小于 `heapUsed` 回落的 58.2。回收意味着「这块空间 V8 认为自己可以复用」，不意味着「操作系统拿回了这些物理页」。所以「内存一直涨」和「内存涨上去不再降」是两类不同的问题：前者看 `heapUsed` 的走势，后者要看 `rss` 与 `heapTotal` 是否一起涨——只把前者当后者用，就会得出「有泄漏」的错误结论。至于运行时什么时候真正把内存还给系统，取决于分配器与平台，本机无法稳定观测，本章不做断言。

**`Buffer` 不进 `heapUsed`。** 8 个 4 MB 的 `Buffer`（32 MB）之后：`heapUsed` 增量是 **0.0 MB**，而 `arrayBuffers` +32.0、`external` +32.0、`rss` +28.1。只看堆的告警会完全漏掉这一类——处理上传文件、做压缩、批量导出的服务正是这一类。

## 堆上限是每个进程一份，而且它管不到 Buffer

`--max-old-space-size` 是 V8 老生代堆的上限，也就是「JS 对象最多用多少」。本机两个子进程实验把它能管什么、不能管什么划得很清楚。

```text
子进程（堆上限 64 MB，试图放 400 万个对象）：status=134 signal=null
它的 stderr：FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
父进程（发起这个子进程的一方）还活着：heapUsed=4.1 MB

同一个 64 MB 堆上限里分配 128 MB 的 Buffer：status=0
输出：arrayBuffers=134228203（约 128 MB）、heapUsed=3515072（约 3.4 MB）
```

第二组数字值得读三遍：**堆上限是 64 MB 的进程，成功分配了 128 MB 的 `Buffer`**，因为 `Buffer` 的内存不在 V8 堆里（`arrayBuffers`，属于 `external`）。也就是说，遇到 `rss` 一路涨却完全没有 `FATAL ERROR: Reached heap limit` 的进程，把启动参数改成 `--max-old-space-size=8192` 一点用都没有——那条旋钮只管 JS 对象。

第一组数字给出另一半信息：堆炸掉的是那一个进程，退出码 134，父进程照常在跑。这就是第八章说的「进程边界」在内存上的体现，也是为什么「一个 worker 崩了主进程没事」在真实故障里比听起来更重要。

由此可以列一张读告警的顺序表：先看崩溃文本属于哪一类（`Reached heap limit` 是 V8 堆；`EMFILE` 是句柄数量；被外部信号杀掉要看 signal，Linux 上常见的是 OOM killer，本机没有环境、未验证）；再看是哪个口径在涨（`heapUsed` / `external`+`arrayBuffers` / `rss` 三者关系）；最后才谈参数。

还有一层容易被搞混：`os.totalmem()` 与 `os.freemem()` 是**整机**数字，不是你这个进程的。本机 `totalmem` 是 16291.7 MB；这一段脚本多占 64 MB 期间，`freemem` 从 3162.3 MB 变成 3115.1 MB（差 47.2）——方向对，但幅度不会精确等于你的分配量，因为同一时刻别的进程也在动。顺带一个平台差异：`os.vmStats()` 在本机（win32）读到的是 `undefined`，它只在部分 Unix 平台有值，所以同一份监控代码在不同镜像里取不到数，常常不是 bug 而是这个 API 本来就不存在。

## 「阻塞」的准确含义：等的位置不同，代价完全不同

阻塞（blocking）不是「没有立刻返回」，而是**这条等待期间，那根执行流被占着，什么都推进不了**。非阻塞的意思也不是更快，而是等待期间那根线程可以去干别的。

本机用同一个 32 MB 文件、每 20 ms 一次的心跳来量这件事：

```text
同步：6 次 readFileSync 共 201326592 字节，占住主线程 89 ms
      进入同步读之前最后一次心跳在 -16 ms，之后第一次在 +89 ms；这 89 ms 之内心跳次数 = 0

异步：6 次 fs.promises.readFile 共 201326592 字节，47 ms 完成
      这 47 ms 内心跳执行了 2 次
      请求刚发出、还没回来时 process.getActiveResourcesInfo() = ["FSReqPromise","Timeout"]
```

注意这两个数字：同步那轮把主线程押住了 89 ms，异步那轮同样搬了 192 MB 数据、47 ms 完成，而这 47 ms 里心跳照常在走。**异步并不让读盘本身变快**，它做的是把「等」这件事从 JS 执行流上挪走，代价是要在完成后回到主线程继续处理。

最后一行是这件事唯一可读的现场证据。官方文档对 `process.getActiveResourcesInfo()` 的定义是：返回一个字符串数组，内容是**当前让事件循环保持活跃的资源类型**。它有三个用处：判断进程为什么不退出（还挂着哪些句柄/请求）、区分句柄与请求、以及在压测时看某一类资源有没有堆积。本机这一轮里，一个未完成的 `fs` 承诺读显示为 `FSReqPromise`，一个定时器显示为 `Timeout`；而 D 段那批连接期间统计到的是 `{"TCPServerWrap":1,"TCPSocketWrap":100}`（100 正好是 50 条连接的两端）。

按「等在哪里」把常见操作分三堆，判据就够用了：

```text
事件循环自己等        net / http 的 socket、定时器、子进程信号 —— 不占用线程池，成千上万个也没人排队
线程池里等            fs.* 全部、部分 crypto（pbkdf2、randomBytes 等）、DNS 解析 —— 位置有限，会排队
JS 执行流上「等」     任何同步 API（readFileSync、crypto.pbkdf2Sync）、任何同步循环 —— 把第一条那一堆全挡在门外
```

第三行才是「一个同步调用拖垮整台服务」的机制：它不只是慢，它顺手把第一行那批本来不占资源的 socket 也一起挡住了。

## 线程池只有几张桌子，而且桌子数量要启动前定

libuv 的线程池大小在源码里写死了默认值：`static uv_thread_t default_threads[4];`，初始化时 `nthreads = ARRAY_SIZE(default_threads);`，随后读环境变量 `UV_THREADPOOL_SIZE` 覆盖它，上限 `#define MAX_THREADPOOL_SIZE 1024`。关键性质是这次读取发生在池子初始化时——**进程跑起来之后再改环境变量没有用**，所以本机的对照实验是把同一个脚本用不同环境变量各启动一次。

```text
未设置（默认 4）：8 个等量 pbkdf2 → 第1批 4 个（292~322 ms），第2批 4 个（600~624 ms）
UV_THREADPOOL_SIZE=8：同样 8 个 → 第1批 8 个（632~685 ms）
```

第一轮那个「4 个一批、4 个一批」的形状，比任何解释都清楚：8 个任务同时发出，但同时被服务的只有 4 个，后 4 个只能等前 4 个腾出位置。两轮之间的毫秒不可直接比较（脚本按机器速度重新校准了每轮的迭代数），能比的是**分了几批**——这就是判据：把一批等量的线程池任务同时丢进去，数它分几批回来。

还有一条官方提醒容易踩：Node 的 `fs` 文档明确写着，因为回调版与 Promise 版的操作「由底层线程池异步执行，两者之间没有保证的执行顺序」。同一段代码里先 `fs.rename()` 再 `fs.stat()`（都用异步），后者的线程完全可能先被调度到。顺序有意义时要么用 `await` 串起来，要么用同一线程串行执行的同步版本。

那网络呢？本机最漂亮的一组对照是这个：

```text
50 个 loopback TCP 请求在 50 ms 内完成 50 个（失败 0 个），而 16 个 pbkdf2 此刻还没跑完
16 个 pbkdf2 全部完成是在发起后 1334 ms
```

线程池排满的时候，socket 一点都没被拖住——它根本不在那条队列上。这正是「Node 为什么能扛很多连接」的真实来源：不是单线程快，而是**大多数连接只是在等，而等不占桌位**。反过来也一样成立：如果你的服务慢的是文件与加密哈希，那再多的连接能力也救不了它。50 ms 这个数只说明本机那一次没被拖住，不能当吞吐指标用。

## 文件、句柄，以及「删了但空间没回来」

句柄是有配额的资源，而且它数的是「现在占着多少」，不是「总共打开过多少」。本机把 `fs.openSync` 循环开下去，不关：

```text
连续 openSync 不关（上限 8192）：成功 8189 个，第 8190 个失败：EMFILE: too many open files
关闭 100 个之后能重新开成功（fd=8092）
```

撞到 `EMFILE` 时文件本身没问题——关掉 100 个立刻就能再开。这一条排障判据是普适的：报 `EMFILE` 就去找「谁还没关」，而不是去改文件权限。至于 8189 这个数字属于本机（Windows + 这个运行时），Linux 上常见的是 `ulimit -n`（默认值随发行版与容器配置差别很大），两者不能互推；Linux 侧的核对路径未在本机验证。

然后是那个磁盘告警的机制本体。同一份脚本里：打开一个 32 MB 文件的读句柄，持有句柄的情况下删掉它，再分别看名字、内容和可用空间。

```js
const fd = fs.openSync(target, 'r');
fs.unlinkSync(target);           // 名字删掉
fs.statSync(target);             // 立刻 ENOENT
const buf = Buffer.alloc(8);
fs.readSync(fd, buf, 0, 8, 0);   // 内容还在
fs.closeSync(fd);                // 到这里最后一个引用才消失
```

```text
持有 fd 的情况下删文件：unlink 成功；statSync 抛 ENOENT（目录项已经没了）
删完之后从旧 fd 还能读回 8 字节（前 4 字节 = 07070707）
本盘可用空间：删之前 135446.2 MB → 删之后（fd 仍开着） 135446.2 MB → 关闭 fd 之后 135478.2 MB
```

**删除操作删的是名字，数据要等最后一个引用关闭才真正释放**——本机这轮表现为：名字消失、旧句柄仍读到 `07 07 07 07`、可用空间在删的那一刻一动不动，直到 `closeSync` 才多出 32 MB。POSIX 对这件事的措辞是规范级的：「当一个或数个进程在最后一个链接被移除时仍打开着该文件，链接会在 `unlink()` 返回之前被移除，但文件内容的移除将被推迟到所有对该文件的引用被关闭之后」。这不是 Windows 的特性，也不是 Linux 的 bug，而是引用计数在文件系统上的直接后果。

Linux 上的现场核对命令（本机没有环境，**未在本机验证**，命令与预期来自通用运维实践）：

```bash
df -h /var                       # 已用量比 du 统计的大，且差距稳定存在
du -sh /var                      # 与 df 对不上，说明有「已经没名字但还在被占着」的数据
lsof +L1                         # 列出链接数小于 1（已删除）但仍被打开的文件，重点看日志与临时文件
ls -l /proc/<pid>/fd             # 顺着持有者找到那个没关的句柄，比 name 对应到具体代码路径
kill -USR1 <pid>                 # 常见日志轮转信号：让进程重开日志而不是继续写旧句柄
```

最后一件事是页缓存，也是本章唯一刻意**不做测量**的一条。页缓存的意思是：读文件时数据可能已经在内存里（上一次读或写留下的），所以命中与否会让「同样的读」耗时差很多；写也通常先落到页缓存、之后异步回写。本机没法可靠证明这件事——唯一能拿出的证据是「第二次比第一次快」这类单次耗时对比，而这类对比既受缓存影响也受调度、磁盘状态、其它进程影响，不足以支撑任何普遍结论。要知道页缓存的实际状况，Linux 上看 `/proc/meminfo` 里的 `Cached`、`Dirty`、`Writeback`，配合 `vmstat` 的 `bi`/`bo` 看是否在真正落盘；本机没有对应接口。概念上需要记住的只有一句：**「读文件很快」很多时候不是磁盘快，是根本没走到磁盘。**

## 常见错误与排查

**只监控 `heapUsed`，于是看不见 Buffer 造成的增长。** 现象是面板一切正常但 `rss` 一路上涨。原因如实测：32 MB Buffer 让 `heapUsed` 增量是 0.0，而 `external` 与 `arrayBuffers` 各 +32.0。确认方法是把 `process.memoryUsage()` 的五个字段一起打出来做时间序列。修法是按口径分别设阈值，`external`/`arrayBuffers` 的异常单独告警，尤其是文件与压缩相关的路径。

**一遇到 OOM 就调 `--max-old-space-size`。** 现象是调到 8 GB 之后照样崩。原因是那条旋钮只管 V8 堆（实测：64 MB 堆上限的进程成功分配了 128 MB Buffer）。确认方法是读崩溃文本，`Reached heap limit` 才属于堆；否则要看是被系统杀（signal）、还是句柄/网络资源耗尽。修法是按口径找源头：堆是对象留存问题，堆外是 Buffer/流未释放问题，句柄是关闭问题。

**日志删了但磁盘没回来，于是去删更多文件。** 原因是删除只减名字，最后一个句柄还开着。确认方法是 `lsof +L1` 或对比 `df` 与 `du`（本机以可用空间读数直接复现：删掉 32 MB 之后数字不动，关句柄才 +32 MB）。修法是让写日志的一方关闭并重新打开（信号轮转、或 logrotate 的 `copytruncate`/`postrotate`），不是继续在磁盘上删。

**「CPU 很闲，所以不是性能问题」。** 现象是 p99 很差而 CPU 曲线平。原因是 `fs` 与部分 `crypto` 在等只有几张桌子的线程池，等待不烧 CPU。确认方法是数队列：同量任务同时发出，看它们分几批回来；或看 `getActiveResourcesInfo()` 里请求类的数量。修法是减少走线程池的调用（缓存、批量、放到子进程），或者按官方建议把文件读改成分块的流——文档同时提醒这样事件循环能在块之间转、减轻线程池压力，但读完整个文件的总时间会更长。

**「用了异步，就不会挡别人」。** 前半句对，后半句只在「不等的那段时间」成立。异步读 192 MB 数据时，本机那 47 ms 里事件循环确实转了两格，但数据是一次性整块进内存的（`readFile`），并且它占了一个线程池位置。确认方法是在这条路径上做并发压测，同时看 `rss` 峰值与排队批次数。修法是大文件用流、限制并发数、把不能变快的部分挪出请求路径。

四句话：`heapUsed` 量的是 V8 堆里还活着的 JS 对象；`heapTotal` 是 V8 已经拿到手的堆空间，回收后不必缩小；`external`/`arrayBuffers` 量的是堆外的 C++ 与 Buffer 内存，`Buffer` 全在这里；`rss` 是这个进程在物理内存里占的位置，包含上面全部。所以「`heapUsed` 回落」**不能**当作内存已还给操作系统——它只说明 V8 认为那段空间可复用了；要看是否还给系统得看 `rss` 的长期走势，而且本机也测不出归还的确切时机（取决于分配器与平台）。

</template>

</Exercise>

<Exercise title="量出你自己机器上的线程池批次数" difficulty="进阶">

用 `crypto.pbkdf2`（异步版）先测一次 20000 迭代的耗时，把迭代数换算成「单次约 200 ms」，然后同时发出 8 个这样的任务，记录每个任务的完成时刻。再分别在 `UV_THREADPOOL_SIZE` 未设置与设为 8 的两种环境下各跑一次。报告：两种环境下各分了几批完成、每批几个。最后回答：为什么不能拿这两轮的毫秒数互相比较来证明「调大线程池就快一倍」？

<template #answer>

本机结果：未设置时 8 个任务分成两批，第 1 批 4 个（292~322 ms）、第 2 批 4 个（600~624 ms）；设为 8 时一批 8 个（632~685 ms）。默认值 4 来自 libuv 源码里的 `default_threads[4]`，`UV_THREADPOOL_SIZE` 可以覆盖，上限 1024，而且只在池初始化时读一次——所以必须在启动进程前设。

不能比毫秒的理由有三条：脚本每轮按当轮机器速度重新校准迭代数，两轮任务的绝对耗时本来就不等价；同一台机器重跑本身有波动，单次样本没有区间估计；完成时刻还受同一时刻其它进程、电源状态影响。能比的是**批次数与每批的大小**，它反映的是并发位置数而不是性能。真要判断调优收益，得固定输入、重复多轮、比较分布（这已经超出本章范围）。

<Exercise title="亲手制造一次 EMFILE 和一次「删了但空间没回来」" difficulty="挑战">

写一段脚本：(1) 循环 `fs.openSync(someFile, 'r')` 且**不调用 close**，直到抛错，记录成功打开了多少个、错误码是什么；然后关掉 100 个句柄，再试着开一个，看是否恢复。(2) 新建一个 32 MB 文件，打开它的读句柄，然后 `fs.unlinkSync` 删掉它，依次回答：`fs.statSync` 还看得见吗？从旧句柄还读得到内容吗？用 `fs.statfsSync` 在删除前后、关闭句柄前后各取一次可用空间，四个数分别是什么？解释两个现象的共同原因。

<template #answer>

本机 (1)：成功 8189 个，第 8190 个抛 `EMFILE: too many open files`；关掉 100 个之后能重新开成功。说明失败与文件本身无关，纯粹是「当前占着的数量」到了上限——排障时该找的是没关的句柄，不是权限。

本机 (2)：`unlinkSync` 成功；`statSync` 立刻抛 `ENOENT`（目录项已经没了）；从旧句柄仍能读回请求的 8 个字节；可用空间在删除那一刻**没有变化**，直到 `closeSync` 之后才多出 32 MB。

共同原因是引用计数：名字（链接）和数据是两件事。目录项被删只是让「按名字找」这条路断了，只要还有打开的句柄指向它，内核就必须保留内容，空间自然也就回不来。`EMFILE` 与磁盘不降其实是同一枚硬币的两面——句柄是一种有限的资源，而它绑定的数据又是另一笔要等它释放才回收的资源。日志轮转的所有正确做法（信号重开、`copytruncate`）本质都是在处理这个「删了但还被开着」。

## 官方文档与延伸阅读

- [Node.js `process.memoryUsage()`](https://nodejs.org/docs/latest/api/process.html) —— 核实 `heapTotal`/`heapUsed` 属于 V8、`external` 是绑定到 V8 管理对象的 C++ 内存、`rss` 包含所有 C++ 与 JS 对象和代码、`arrayBuffers` 包含所有 `Buffer` 且已计入 `external`，对应第一节表格的读法。
- [Node.js `process.getActiveResourcesInfo()`](https://nodejs.org/docs/latest/api/process.html) —— 核实它的定义（当前让事件循环保持活跃的资源类型字符串数组）与稳定性历史，对应第三节的现场证据。
- [Node.js `os` 文档](https://nodejs.org/docs/latest/api/os.html) —— 核实 `totalmem`/`freemem` 是整机口径、`vmStats()` 的平台限制，以及 `availableParallelism()` 与 `os.cpus().length` 的取舍（第八章也引用了）。
- [Node.js `fs` 文档](https://nodejs.org/docs/latest/api/fs.html) —— 核实「回调与 Promise 版由底层线程池异步执行，因此没有保证的顺序」，以及分块读可以减轻线程池压力但读完整个文件更慢的说法，对应第四、五节。
- [libuv 源码 `src/threadpool.c`](https://github.com/libuv/libuv) —— 默认 `default_threads[4]`、环境变量 `UV_THREADPOOL_SIZE`、`MAX_THREADPOOL_SIZE 1024`，对应第四节的批次实验解释。
- [POSIX `unlink()` 规范](https://pubs.opengroup.org/onlinepubs/9699919799/functions/unlink.html) —— 核实「最后一个链接被移除时若仍有进程打开该文件，链接先被删但内容移除推迟到所有引用关闭」，对应第五节本机复现的机制。
- 站内：[第八章 操作系统：进程与线程](/computer-science/os-process-thread) —— 「进程边界」与「执行流边界」那两件事；[第七章 网络：HTTP 演进](/computer-science/network-http) —— 多路复用在应用层解排队，本章讲的是同一条队列在操作系统层的形成。
