# 阶段项目：全链路诊断演练

本领域前十一章给的都是**判据**：复杂度怎么估（第 3 章）、一次请求在网络上要付几段等待（第 5–7 章）、进程线程与内存口径（第 8–9 章）、边界与模式各自解决什么（第 10 章）、模型与选型怎么留证据（第 11 章）。判据有个共同的问题：**它们在别人的例子里都讲得通，在你自己的机器上还没兑现过。**

这一章就是把那十一把尺子挂到你自己那台真实运行的机器上，产出一份**诊断报告**。它不写新功能、不重构、不迁移，只做一件事：把你的产品在 2026 年这一天是什么样，量清楚、写清楚、并把「哪些是我量的、哪些是我猜的」分开。

一份合格的报告长这样：一句话结论在前面，随后是每条主张配一段命令输出或一段代码引用；每个数字带单位与口径；凡是没有证据的句子要么删掉，要么明写「未验证，需要在有真实环境时补测」。不合格的报告显示为三种典型形状：**只有截图没有口径**（「首页 1.2 秒」——哪一段？冷启动还是热连接？）、**只有名词没有判据**（「微服务能提升可维护性」）、**把别人机器的数字当自己的**（某博客上的 QPS 结论）。

本站能陪你走到哪一步要说在前面：阶段 0、3、4 的绝大部分动作在任意一台开发机上就能做完，阶段 1、2、5、6 里凡涉及公网、你的域名与你的 VPS 的部分，需要你自己在真实环境里跑——那部分本章给出命令、字段口径、预期形状与验收方法，**不提供本站跑过的数字**，因为本站没有你的部署。

## 目标与范围

**做**：一份 Markdown 报告 + 一个证据目录，回答四个问题——一次真实请求经过哪些段、每段花多少、哪段最先随数据量崩、你当前的结构在什么信号出现时才值得改。

**明确不做三件事**，每条给判据，否则这一章会变成第二个重构项目：

- **不优化任何东西**。判据：报告里出现「已经改成 X 所以变快了」就越界了。允许写的只有「改法建议」，且必须附「未实施」。
- **不搭新环境**。判据：为了让某个指标能测而专门去装一套监控栈，属于下一阶段。本阶段只允许使用你已有的命令行与浏览器开发者工具。
- **不给「要不要拆微服务」的结论**。判据：第 10 章那张判据表要的是**信号**，你报告里该出现的是「三个部署阻塞事件的具体日期与耗时」，不是结论。

**成功判据一句话**：一个没有参与这个项目的工程师，只看你的报告，能够复现其中任意一条数字（照抄命令、换自己的参数），并且能一眼分辨出哪些句子是主张、哪些是证据。

## 分阶段实施

### 阶段 0：选定对象与基线，把证据目录建起来

**目标**：让后面六个阶段的每次测量都落在同一个对象、同一份代码版本上。**涉及文件**：`diagnosis/report.md` 的方法一节、`evidence/` 目录。**实施步骤**：一，写下被测 URL、被测部署的 commit 号或镜像 tag、机器规格（几核几 G、系统版本、你的 Node 版本）；二，创建上面那棵目录树；三，约定「测量口径三句话」——同一请求重复 5 次取哪一数、是否清缓存、冷连接还是复用连接；四，把这三句话直接写进报告开头，作为后面所有数字的前提。**可核对产物**：报告第一节的「被测对象卡」，含 commit 号与机器规格。**验收方法**：任选报告里一个数字，看它能不能被你写下的口径唯一确定；不能确定就是口径缺项。**失败排查方向**：最常见的坑是测量期间代码变了（你在同一周里既上线了新功能又做了诊断），对策是给报告钉一个 commit 号并在每张证据文件顶部重述它。**真实环境限制**：本阶段全部在你自己的仓库与笔记里完成，无需公网；但 commit 号必须来自真实部署的那一次，不是本地未发布的提交。

### 阶段 1：把一次请求拆成段，并给每段找到核对方法

**目标**：产出一张别人可以照着核对的路径表，而不是凭印象的一句话。**涉及文件**：`evidence/01-path-table.md`、`report.md` 的第一节。**实施步骤**：按你真实部署的形状，把「浏览器输入域名 → 页面出现内容」拆成 DNS、TCP、TLS、HTTP 语义层、边缘/CDN、反向代理、容器或进程、应用处理、数据访问这几段；每段填三列：发生在哪台机器、用了本领域哪一章、**你怎么核对这一段真的存在**。第三列是本阶段的真正产出，形如：DNS 用 `dig` 看返回链路与 TTL；TCP/TLS 用阶段 2 的 `curl -w` 差值；Nginx 看它的 access log 里那条请求的 `request_time` 与 `upstream_response_time` 两个字段；容器用 `docker stats` 的一次读数；应用处理看你自己打的日志时间戳；数据访问看慢查询日志有没有那条。**可核对产物**：七到九行的表，每行三列齐备。**验收方法**：随机挑两行，照第三列的命令做一次，能在你的日志或输出里找到对应记录。**失败排查方向**：最常见的是「表里有一段时间线对不上」——比如 Nginx 记录的 800 ms 比你从浏览器看到的 300 ms 还大，这通常意味着你测的不是同一次请求（缓存命中与未命中混在一起），或者浏览器计时里包含并发复用。**真实环境限制**：全部需要你的 VPS 与域名；本节未在本机验证，本站无对应部署。

### 阶段 2：分段计时实测，把「慢」落到某一段

**目标**：用一条命令把 DNS / TCP / TLS / 首字节 / 总耗时五个数分开，并证明它们可重复。**涉及文件**：`evidence/02-cold.txt`、`02-warm.txt`。**实施步骤**：先测冷连接（不复用连接、DNS 结果不缓存的形态），再测复用连接，各重复 5 次；保留 `-w` 的**原始输出**，然后自己做相减。

```bash
# 需要你的真实域名；未在本机验证（本批 0 次外网请求）
for i in 1 2 3 4 5; do
  curl -s -o /dev/null \
    -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} prep=%{time_pretransfer} ttfb=%{time_starttransfer} total=%{time_total}\n' \
    "https://<你的域名>/"
done
```

字段的口径（这一段按通用原理与官方文档陈述，本站不替你验证）：`time_namelookup` 到 DNS 解析完成；`time_connect` 到 TCP 连接建立，所以 **TCP 段 = time_connect − time_namelookup**；`time_appconnect` 到 TLS 握手完成，所以 **TLS 段 = time_appconnect − time_connect**；`time_pretransfer` 是准备发出请求；`time_starttransfer` 就是通常说的 TTFB，**服务端处理到首字节 = time_starttransfer − time_appconnect**（复用连接时基线不同，要减 `time_pretransfer`）；`time_total` 是整个响应体收完。**首字节时间不是 `time_total`**，这是本阶段最常见的一处口径错误。

**可核对产物**：两张表（冷/热），每张五行原始输出加一张相减后的分段表，以及一句「哪一段最贵、为什么」。**验收方法**：五次的 DNS 段读数应该在同一量级；如果其中几次等于 0，说明缓存生效了——这不是错误，但你必须在报告里写明哪几次被缓存遮蔽。**失败排查方向**：TLS 段为 0 通常是连接复用（会话恢复）；总耗时波动大而各段都稳定，多半是响应体下载段（带宽/体积）；冷连接每次都慢得离谱，先检查 `dig` 的 TTL 和你的 CDN 边缘节点位置。**真实环境限制**：需要公网与你的域名；本批未执行；`curl` 版本影响可用变量，写报告时把 `curl --version` 一并留存。

### 阶段 3：复杂度审计，挑出「数据量 ×100」时第一个崩的

**目标**：把三段真实逻辑从「跑得动」变成「能说出它什么时候跑不动」。**涉及文件**：`evidence/03-complexity.md`。**实施步骤**：挑三类各一段——一个应用内的循环（或嵌套循环）、一条数据库查询、一个前端渲染或聚合计算；对每段写四件事：当前数据规模（真实条数，从你的库里 `count` 出来）、时间复杂度、`×100` 后的操作量比值、以及改法（只要方案，不要求实施）。

```ts
// 典型形状：外层订单列表，内层每次线性扫全量用户找归属——O(n·m)
// n=8,000 单 × m=3,000 用户 ≈ 2.4e7 次比较；两个维度各 ×100 → 2.4e11
// 改法方向：先把用户按 id 建成 Map（O(n+m)），或把这次聚合下推到数据库
const rows = orders.map((o) => ({ ...o, user: users.find((u) => u.id === o.userId) }));
```

放大倍数只用算术，不需要跑：`n·m` 双双 ×100 是 ×10,000；`n log n` 是约 ×100 再多一点；纯 `n` 是 ×100。**可核对产物**：三段各一条「当前条数 → 复杂度 → ×100 推导 → 改法」的四行块，外加一句结论：第一个出问题的是哪段。**验收方法**：把你推导出的比值交给别人复算；三段里至少有一段能说出「它崩之前会先出现什么症状」（接口 p99 抬升、慢查询日志出现某条语句、页面掉帧）。**失败排查方向**：最常见的错误是把 `find` 藏在循环里只算成 O(n)；第二个是把数据库的索引当作理所当然，先跑一次 `EXPLAIN` 再写复杂度（需要你的真实数据库）。**真实环境限制**：读代码与算术本机可做；`count` 与 `EXPLAIN` 要连你的真实库，本站没有。

### 阶段 4：内存与线程观察，把「进程占了多少」说清是哪个口径

**目标**：能解释一个具体差额从哪来。**涉及文件**：`evidence/04-mem-node.txt`、`04-mem-server.txt`。**实施步骤**：先在开发机上拿一条本机可读的口径基线（这一步本批真跑过，命令与原始输出）：

```bash
node -p "JSON.stringify(process.memoryUsage())"
```

```text
本批 2026-10-22 在 Node v25.4.0 / win32 x64 的原始输出（空载进程）：
{"rss":33570816,"heapTotal":4591616,"heapUsed":3736704,"external":1369639,"arrayBuffers":10511}
换算（除以 1048576）：rss 32.01 MB｜heapTotal 4.38 MB｜heapUsed 3.56 MB｜external 1.31 MB｜arrayBuffers 0.01 MB
rss − heapUsed = 29,834,112 B ≈ 28.45 MB ← 这一份就是你报告要解释的对象
```

一个刚起来的空载进程，`rss` 是 `heapUsed` 的九倍。差额不是指标坏了：`heapUsed` 只管 V8 堆里还有引用的 JS 对象，`external` 与 `arrayBuffers` 走的是 C++ 侧与 Buffer，其余是运行时自身与代码段。然后到服务器上做同一件事（需要你的 VPS）：同一进程打印 `memoryUsage()` 一次，`ps -o rss= -p <pid>` 读一次，两者相减；再读容器或系统给的限额（`docker stats` 的 MEM USAGE，或 cgroup 的 `memory.max`）。**可核对产物**：两组数字 + 一段「差额住在哪儿」的解释 + 一句「哪个口径会触发 OOM，哪个会触发容器被杀」。**验收方法**：你能用一句话区分「堆 OOM」与「容器被 OOMKilled」的症状差别（前者抛 `RangeError: Heap allocation failed` 类错误并留下 JS 栈，后者由内核记录、你的日志里往往只有一行 exit code 137）。**失败排查方向**：`rss` 高但 `heapUsed` 低，先看 Buffer 与大字符串；`heapUsed` 持续增长且强制回收后不降，才是引用没断；`ps` 与 `memoryUsage` 差得离谱时先确认你读的是同一个 PID（多进程部署下每个 worker 一个）。**真实环境限制**：开发机部分本机可做且本批已做；服务器、容器、cgroup 三处**未在本机验证**。

### 阶段 5：架构与模型复盘，把名词换成信号与日期

**目标**：用第 10 章与第 11 章的两张表，各做一次「有证据的填空」。**涉及文件**：`evidence/05-architecture.md`、`06-invariants.md`。**实施步骤**分三小步。

一，**部署单元清点**：列出你现在有几个可独立部署的东西（应用进程、worker、数据库、静态资源），以及一次改动要发几个东西。二，**判据表填写**：把第 10 章「值得拆 / 不该拆」两组信号逐条填，**每条只能填真实发生过的事件与日期**——「上周那次紧急修复被未完成测试拖了一天」算一条，「微服务更灵活」不算。三，**不变量落点核查**（第 11 章第三节的兑现）：把代码里所有 `if` 式业务校验列出来，逐条问「数据库层有没有对应约束」，没有的标成风险并写清它能被哪条路径绕过（脚本导入、后台直调接口、并发窗口）。

```bash
# 一条能真正开始的检查：把所有校验式失败点列出来，逐条去库里找对应约束
grep -rnE "throw new (Domain|Business)Error|res\.status\(400\)" src/ | head -50
```

**可核对产物**：三样东西——部署单元清单（含「发一次要动几个东西」）、填好且每条带事件的判据表、不变量落点表（每条不变量：规则原文 / 域内在哪个文件 / 库内有没有约束 / 能被哪条路径绕过）。**验收方法**：随便挑一条「拆分信号」，能说出发生日期、耗时与影响面；随便挑一条不变量，能指出库里那条约束的名字。**失败排查方向**：如果你的判据表三条信号全是抽象句，说明你还没攒够经验，那就写「暂无信号」——**这是本章允许的合格答案**，比编一个强。绕不过来的另一种情况是不变量清单为空，那通常意味着你的业务规则其实只活在表单里，回去读第 11 章第四节。**真实环境限制**：读代码与列清单本机可做；核对库内约束要连你的真实数据库。

### 阶段 6：成稿、标注与三个月后的复核

**目标**：把六个阶段的产物装配成一份别人能照着重跑的报告，并给未来留一把尺子。**涉及文件**：`report.md` 全文、`decisions/`。**实施步骤**：一，按「结论 → 证据 → 方法 → 未验证清单」四段装配；二，逐句加标注：每条数字后面写 `［证据：evidence/02-cold.txt 第 3 行］`，每条没有证据的句子改成 `［未验证：需要在 XXX 条件下测］`；三，写一份「未验证清单」集中收拢所有需要真实账号/真实环境才能补的部分（首页那条「点开可看原文」类的需求同理，做不到的就写做不到）；四，公开前做真实信息替换（域名、IP、路径、用户名）；五，写下三个月后的复核动作：哪几个数字要重测、怎么保证同口径（把阶段 0 的三句话再抄一次）。**可核对产物**：报告本身 + 未验证清单 + 复核计划一行。**验收方法**：找一位没参与项目的工程师（或三个月后的你自己），让他只看报告复现阶段 2 或阶段 4 的任意一个数字；他能复现，报告就合格。**失败排查方向**：复现失败九成是口径没写全（冷/热连接、清没清缓存、第几次取哪一数）；另一种是证据文件与报告正文版本不一致（代码改了、报告没改）。**真实环境限制**：装配与标注本机可做；「能复现」这一步需要报告里的数字本来就来自真实环境，缺的那半要在你有部署时补齐。

## 常见翻车点

**一、把 `time_total` 当首字节时间。**症状：报告写「首页 1.2 秒」，别人以为服务端处理 1.2 秒，实际那 1.2 秒里绝大部分是响应体下载。对策：报告里只允许出现五个段名各自的数，`total` 单独一行并注明它不是 TTFB。

**二、测了个「缓存全生效」的链路却当成真实链路。**症状：DNS 段 0、TLS 段 0、`time_starttransfer` 稳定得可疑。原因：浏览器/系统 DNS 缓存、连接复用、CDN 命中三层里有任意一层在替你干活。对策：冷热各测一组，两组的差值本身就是要写进报告的结论。

**三、只看 CPU 找瓶颈。**症状：p99 抖动而 CPU 曲线很平，于是判断「不是资源问题」。原因：等待不占 CPU（第 9 章那节的线程池排队实验就是这件事）。对策：把「等在哪里」写进报告：等 DNS、等连接、等数据库、等线程池、等下游服务，各有对应证据。

**四、把别人的基准数字当自己的前提。**症状：报告里出现「PostgreSQL 单机能撑 X 万 QPS，所以现在没问题」。对策：任何比较必须来自你自己的数据规模与查询形状，量不了就写未验证（第 11 章那七条错误里的第七条）。

**五、复杂度审计漏掉「藏在方法里的那次线性扫」。**症状：`orders.map(... users.find ...)` 被算成 O(n)。对策：凡是被调用的方法都要展开一层再算；数据库那侧要跑一次 `EXPLAIN` 才知道有没有走索引。

**六、报告里没有一次失败样本。**症状：所有读数都很漂亮。原因：只测了成功路径。对策：阶段 2 里刻意测一次「服务在维护中」「DNS 指错」的形态（可控地做，别影响真实用户），把它们的时间形状记下来——这类样本比五个正常样本有用。

**七、混淆本机与真实环境。**症状：把开发机 `node -p` 的 `rss` 写进「服务器内存分析」。对策：每条数字前面标测量地点（开发机 / 容器内 / VPS 宿主 / 浏览器），本批那组本机数字之所以写了口径，就是为了示范这个标注形状。

**八、把架构章的名词抄进报告当结论。**症状：出现「我们应该采用事件驱动架构」。对策：报告只允许出现「信号 + 事件 + 日期」，结论留给第 10 章那张判据表去推；名词出现在报告里时必须带它替你解决的那一段瓶颈。

**九、不变量核查表全部填「有约束」。**症状：一条数据库约束的名字都说不出。对策：逐条去 `\d 表名` 或等价命令里找，找不到就是没有——这一格空着写「无」比填「有」有用得多。

<template #answer>
