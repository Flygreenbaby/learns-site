# 选择器与特异性：怎么算，以及为什么越低越好

## 先看两个都会猜错的例子

### 例子一：12 个类能不能打败 1 个 id

```html
<style>
  #a { color: rgb(10, 10, 10); }
  .k1.k2.k3.k4.k5.k6.k7.k8.k9.k10.k11.k12 { color: rgb(0, 240, 0); }
</style>

<p id="a" class="k1 k2 k3 k4 k5 k6 k7 k8 k9 k10 k11 k12">A</p>
```

流传很广的说法是「特异性可以靠数量堆」，所以这里该是绿色。**实测是 `rgb(10, 10, 10)`，id 赢。** 12 个类打不过 1 个 id，100 个也打不过。

### 例子二：匹配不到的分支要不要计数

```html
<style>
  #e :is(.xx, #nopeE) { color: rgb(111, 11, 11); }
  #e .xx { color: rgb(0, 200, 0); }
</style>

<div id="e"><span class="xx">E</span></div>
```

文档里根本不存在 `id="nopeE"` 的元素，`:is()` 的那一支永远匹配不到任何东西，直觉上它应该「不算」。第二条规则写在后面，`.xx` 也确实在元素身上命中了。**实测是 `rgb(111, 11, 11)`，带假分支的第一条赢。**

两个例子指向同一件事：特异性不是分数累加，而是一次性排出三个数字、逐位比较；而且**计数发生在选择器「写法」层面，跟它能不能匹配上没有关系**。理解这两点，本章几乎所有结论都能自己推导出来。

<Callout type="verified" title="本章实测说明">

- 方法与第 1 章相同：把用例写成静态页面，用 `getComputedStyle()` 读浏览器最终结果。环境是 Qoder 内置浏览器（`Chrome/150.0.7871.114` + `Electron/43.1.1`）、Windows 10 x64、`devicePixelRatio = 1.25`、视口宽度 638px，核实时间 2026 年 10 月 16 日。
- 每个用例的选择器都挂在唯一的 id 或类上，避免其他规则串味。**测出与规范不符的结果时，我改的是用例而不是结论**——上一版草稿里「7 个类打败 1 个 id」就是被实测推翻的。
- **本章未能实测的部分**：现有环境无法调整浏览器窗口宽度，所有 ≥960px 视口下才会激活的规则冲突只能按规范推导，会在对应位置明确标注。

</Callout>

## 特异性的三位记法：(a, b, c)

给任意一个选择器数三个数字，从左到右：

| 位 | 记号 | 数什么 | 例子 |
| --- | --- | --- | --- |
| a | id 数 | `#foo` 形式的 id 选择器个数 | `#main` → `(1,0,0)` |
| b | 类/属性/伪类数 | `.foo`、`[href]`、`:hover`、`:nth-child()`、`:not()` 的参数 | `.a[href]:hover` → `(0,3,0)` |
| c | 类型/伪元素数 | `div`、`p` 这类元素名、`::before`、`::first-line` | `div::before` → `(0,0,2)` |

**完全不参与计数的**：

- 通配符 `*`
- 组合器：空格、`>`、`+`、`~`
- `:where()` 整个函数（内部无论写什么都算 0）
- 伪类 `:hover` 与 `:nth-child(2n+1)` 一样只算 1 个 b 位，参数复杂度不影响

比较规则是**逐位、从左到右、不进位**：先比 a，a 大的赢；a 相同再比 b；b 也相同才比 c；三位全同就是平局，交给源码顺序。

## 第一组实测：高位碾压，数量无用

```html
<style>
  #z { color: rgb(10, 10, 10); }
  .m1.m2.m3.m4.m5.m6.m7.m8.m9.m10.m11.m12 { color: rgb(0, 240, 0); }

  #y span { color: rgb(20, 20, 20); }
  .m1.m2.m3.m4.m5.m6.m7.m8.m9.m10.m11.m12 span { color: rgb(0, 230, 0); }
</style>

<p id="z" class="m1 m2 m3 m4 m5 m6 m7 m8 m9 m10 m11 m12">Z</p>
<div id="y" class="m1 m2 m3 m4 m5 m6 m7 m8 m9 m10 m11 m12"><span>Y</span></div>
```

| 用例 | 竞争双方 | 特异性 | 实测结果 |
| --- | --- | --- | --- |
| Z | `#z` vs 12 个类 | `(1,0,0)` vs `(0,12,0)` | `rgb(10, 10, 10)`，**id 赢** |
| Y 里的 span | `#y span` vs `12 类 + span` | `(1,0,1)` vs `(0,12,1)` | `rgb(20, 20, 20)`，**id 赢** |

第二个用例专门加了类型选择器，说明「补几位低权重也追不上高权重」这件事与总数字无关，只与最高位有关。把两串数字连起来读成 `120 > 100` 是错的，正确读法是「`(0,12,0)` 的 a 位是 0，比不过 a 位为 1 的任何规则」。

这解释了老项目里最难缠的一个现象：**一旦某条规则用了 id，你在它外面做什么都没有意义**——加类、加层级、加十个类都不行，只能：① 自己也用 id 并且写在后面；② 用 `!important`；③ 用层叠层改变比较范围（见第 1 章）。所以「不要用 id 选择器」这条惯例的真正理由是：**它给后来的人留下的唯一出口是 `!important`**。

## 第二组实测：同一档内部怎么分胜负

```html
<style>
  #b[data-x] { color: rgb(1, 1, 1); }
  #b.kb { color: rgb(111, 111, 111); }
</style>

<p id="b" data-x class="kb">B</p>
```

| 选择器 | 特异性 | 说明 |
| --- | --- | --- |
| `#b[data-x]` | `(1,1,0)` | id + 属性选择器 |
| `#b.kb` | `(1,1,0)` | id + 类选择器 |

实测 `rgb(111, 111, 111)`：**属性选择器和类选择器完全同档**，平局后由源码顺序决定，后写的赢。同一条规则内部谁先写毫无意义——`color` 在同一声明块里也是后写覆盖先写（第 1 章的 `#a` 例子）。

再看组合器：

```css
#h > span { color: rgb(70, 70, 70); }   /* (1,0,1) */
#h span { color: rgb(7, 7, 7); }        /* (1,0,1)，写在后面 */
```

实测 `rgb(7, 7, 7)`。加号 `>` 一个数字都不加，两条规则同为 `(1,0,1)`，于是源码顺序接管。**「写得更具体」在 CSS 里不增加任何权重**，层级深度只在它引入了更多类或 id 时才起作用。

条件规则同理：

```css
#i { color: rgb(0, 180, 0); }
@media screen { #i { color: rgb(99, 99, 99); } }
```

实测 `rgb(99, 99, 99)`。`@media` 不给里面的规则加权重，它只决定这条规则**这一轮有没有参加层叠**。参加之后仍然按同样的规则比。

<Callout type="unverified" title="`@import` 的顺序：规范推导，未实测">

`@import` 引入的样式表，其规则的源码顺序算在 `@import` 语句所在的位置，而不是文件末尾。因此 `A.css` 里 `@import` 放在最前面时，`B.css` 的规则其实排在 `A.css` 后续规则之前——这是很多「明明 import 的库样式却被本地样式意外覆盖」问题的来源。这条结论来自规范对样式表顺序的定义，**本章没有在本地环境实测**（需要两个独立样式表文件配合，本地预览的服务端拼接顺序与真实项目不一致）。

</Callout>

## 第三组实测：函数型选择器按「最高的那支」算，且不看能否匹配

这是最容易踩的一组，四个用例放在一起：

```html
<style>
  /* C：:not() 的参数计入 */
  #c span:not(.nope) { color: rgb(55, 55, 55); }   /* (1,1,1) */
  #c .kc { color: rgb(5, 5, 5); }                  /* (1,1,0)，写在后面 */

  /* D：:where() 贡献 0 */
  #d .wc { color: rgb(44, 44, 44); }               /* (1,1,0)，写在前面 */
  :where(#d) .wc { color: rgb(200, 0, 0); }        /* (0,1,0) */

  /* E：:is() 里匹配不到的 id 照样计数 */
  #e :is(.xx, #nopeE) { color: rgb(111, 11, 11); } /* (2,0,0) */
  #e .xx { color: rgb(0, 200, 0); }                /* (1,1,0)，写在后面 */

  /* F：:not() 里匹配不到的 id 也计数 */
  #f :not(#nopeF) { color: rgb(222, 22, 22); }     /* (2,0,0) */
  #f .xf2 { color: rgb(0, 180, 0); }               /* (1,1,0)，写在后面 */
</style>

<div id="c"><span class="kc">C</span></div>
<div id="d"><span class="wc">D</span></div>
<div id="e"><span class="xx">E</span></div>
<div id="f"><span class="xf2">F</span></div>
```

每个用例我都故意把「你以为会赢的那条」写在前面，把「符合直觉的那条」写在后面，这样源码顺序无法替结果背书，只有特异性差异能解释胜负。

| 用例 | 实测 | 结论 |
| --- | --- | --- |
| C | `rgb(55, 55, 55)` | `:not(.nope)` 里的 `.nope` **算一个 b 位**，`(1,1,1)` 压过后写的 `(1,1,0)` |
| D | `rgb(44, 44, 44)` | `:where(#d)` 整个函数贡献 `0`，`(1,1,0)` 打赢写在后面的 `(0,1,0)` |
| E | `rgb(111, 11, 11)` | `:is(.xx, #nopeE)` 取参数中最高的一支 → id 级，即使 `#nopeE` 在文档里根本不存在 |
| F | `rgb(222, 22, 22)` | `:not()` 同样按参数的最高特异性计数，与能否匹配无关 |

四个函数摆在一起对比：

| 函数 | 对特异性的贡献 | 适合的用法 |
| --- | --- | --- |
| `:is()` | 参数里**最高**的一支 | 合并同义选择器，缩短写法；**注意它会把权重抬到最高档** |
| `:where()` | **0**，参数无论写什么都不算 | 想合并写法但完全不想加权重，例如组件库的样式重置、主题覆盖层 |
| `:not()` | 参数里最高的一支 | 排除性选择，`a:not([disabled])` 与 `a[disabled]` 同档 |
| `:has()` | 参数里最高的一支（规范规定，**本章未实测**） | 父选择器、状态判断，权重风险与 `:is()` 相同 |

<Callout type="warn" title="`:is()` 的隐性代价">

`:is()` 让你少打字，同时把整条规则的权重抬到参数最高档。写成 `:is(#app, .app, .card) .title` 时，这条规则是 id 级的——将来想在别处覆盖它，只有 `!important` 一条路。**惯例：`:is()` 的参数列表里只放同一档的选择器**（全是类，或全是元素名）。需要「批量给一段样式但不加权重」时，直接用 `:where()` 包整条：`:where(.btn, .chip, .tag) { ... }` 权重是 `(0,0,0)`，谁都能轻松覆盖它。

</Callout>

<Callout type="unverified" title="伪元素与 `:has()` 的计数：规范原文，未逐项实测">

[选择器 Level 4](https://www.w3.org/TR/selectors-4/) 规定伪元素（`::before`、`::first-line` 等）按一个类型选择器计入 c 位，`:has()` 与 `:is()`/`:not()` 用同一套「取参数最高值」规则。本章没有为这两条单独构造用例（伪元素的计算结果无法用 `getComputedStyle()` 直接读到，需要截图比对，成本高且易受字体渲染干扰），所以按规范引用。

</Callout>

## 特异性不是第一道关卡

第 1 章的层叠排序有五个阶段，特异性只是第三道：

1. 来源与重要性（UA / 用户 / 作者 / 行内，各自再分普通与 `!important`）
2. 层叠层（`@layer` 的顺序；未分层声明在普通档里最大、在 `!important` 档里最小）
3. **特异性**
4. 源码顺序
5. 元素上的顺序（同一声明块内后写覆盖先写）

实测已经证明过高位可以碾压特异性：第 1 章里 `.imp-low !important`（`(0,1,0)`）打败了 `#id` 的普通声明（`(1,0,0)`），结果 `rgb(155, 155, 155)`。所以「特异性越高越优先」这句话必须加限定：**只在同一个来源、同一个档位、同一个层的范围内成立**。

由此得到一条实际排查准则：**覆盖第三方框架样式之前，先确认它有没有用 `@layer`。** 本站构建产物里可以直接验证这一点——遍历 `document.styleSheets` 的全部规则对象，没有任何 `CSSLayerBlockRule` 或 `CSSLayerStatementRule`（实测于 2026-10-16），说明 VitePress 主题全部是未分层样式。因此主题规则天然压在「未分层普通声明」这一最高档里，靠 `@layer` 赢它行不通，只剩三条路：补特异性、抢源码顺序、用 `!important`（而它一旦用了就再也退不回去）。

## 本站源码的真实审计：两处 `!important` 到底该不该留

`D:\work\learns\.vitepress\theme\style.css` 里有且只有两处 `!important`，两处都针对主题内部元素：

```css
:root { --vp-doc-max-width: 62rem; }

.VPDoc .container .content {
  max-width: var(--vp-doc-max-width) !important;   /* 第 26 行 */
}

@media (max-width: 768px) {
  .VPDoc .container .content {
    padding: 0 20px !important;                    /* 第 128 行 */
  }
}
```

审计结果比「能用就行」有意思得多：**第一条 `!important` 管的属性根本不决定正文宽度，第二条只在窄视口生效，两条都属于「看起来在承重、实际是噪声」**——但结论不是「删掉」，理由在下面。

先看特异性。主题的规则来自 Vue 单文件组件的 `<style>`，编译时会给每条选择器补一个 scoped 属性（实测从构建产物的样式表里读到的原文）：

| 规则 | 特异性 | 怎么数 |
| --- | --- | --- |
| `.content[data-v-e6f2a212]`（主题） | `(0,2,0)` | 1 个类 + 1 个属性选择器 |
| `.VPDoc.has-aside .content-container[data-v-e6f2a212]`（主题） | `(0,4,0)` | `.VPDoc`、`.has-aside`、`.content-container` 三个类 + 1 个属性 |
| `.VPDoc:not(.has-sidebar) .content[data-v-e6f2a212]`（主题） | `(0,4,0)` | 三个类（`:not()` 取参数最高值）+ 1 个属性 |
| `.VPDoc .container .content`（本站） | `(0,3,0)` | 3 个类；全局样式表没有 scoped 属性 |

这里有个值得记住的反直觉点：**框架的 scoped 样式自带一个属性选择器，特异性比肉眼看到的要高一级。** 很多人以为「组件样式很好覆盖」，实际遇到的是这种带属性的选择器。

由此得到两条实测结论：

1. **本站这条比主题的 `.content` 基础规则高，本来就赢。** 实测做法：在浏览器里用 CSSOM 把这条规则的 `important` 优先级撤掉，`getComputedStyle(...).maxWidth` 仍是 `992px`（`62rem × 16px`）。但它**在另一类页面上是承重的**：主题的 `.VPDoc:not(.has-sidebar) .content` 是 `(0,4,0)`，专治没有侧边栏的文档页。本站目前每个文档路径都配了侧边栏，所以这条规则一次都没被触发过；哪天新增一个不带侧边栏的文档页，`!important` 就是唯一能赢它的方式（否则你得在自己的选择器里也凑到 4 个 b 位）。**保留它，并把这个理由写进注释，比删掉它更负责。**
2. **但 `max-width: 992px` 并没有加宽正文。** 有大纲侧栏时真正约束文字宽度的是主题的 `.content-container`（`(0,4,0)`，`max-width: 688px`）。实测在 `/html/` 这个文档页上：`.content` 的 computed max-width 是 `992px`，它内部的 `.content-container` 是 `688px`，正文实际渲染宽度 535px（视口 638px）。也就是说，第 26 行的 `!important` 一直在一个不生效的属性上较劲。

要真正加宽正文，正确做法是拿 `.content-container` 开刀，并且**用同等特异性 + 靠后的源码顺序**，而不是加 `!important`：

```css
/* (0,4,0)，与主题规则同档，且本站样式表在主题之后加载 → 源码顺序接管胜负 */
.VPDoc .container .content .content-container {
  max-width: var(--vp-doc-max-width);
}
```

实测对比（同一页面、同一视口，用注入样式表逐个试）：

| 注入的规则 | 特异性 | 能否覆盖主题的 `688px` | 实测 computed |
| --- | --- | --- | --- |
| `.VPDoc .content-container` | `(0,3,0)` | 不能 | `688px` |
| `.VPDoc .container .content .content-container` | `(0,4,0)` | **能**（平局，本站样式表在后） | `992px` |

一条 `(0,3,0)` 输给 `(0,4,0)`，另一条 `(0,4,0)` 靠源码顺序赢，全程没有 `!important`。**这就是本章想要的效果：用选择器的形状解决问题，而不是用音量。**

<Callout type="info" title="为什么这条改宽方案最终没有应用到本站">

上面那条 `(0,4,0)` 规则实测有效，但它会把正文行宽从 688px 抬到 992px——这是阅读体验参数，必须目视验收。**当前环境能用的浏览器视口只有 638px 宽，我无法把窗口调宽**（尝试过用脚本开新窗口，被环境拒绝）。没有验收手段的布局改动不该提交，所以本站保留了原状，只把这个结论写进 `style.css` 的注释里（第 9–20 行），供以后在宽屏幕上验证时直接采用。

审计中另一处无法实测的点在第 128 行：`padding: 0 20px !important` 只在 ≤768px 生效，而主题的 `.content { padding: 0 32px 128px }` 在 `@media (min-width: 960px)` 里，两者不会同时激活。按特异性推导（`(0,3,0)` > `(0,2,0)`）这个 `!important` 同样多余，但这条只有推导没有实测，所以保守保留，并在源码注释里写明了未验证的原因。

</Callout>

## 怎么写出不需要 `!important` 的选择器

按代价从低到高排序，四条路：

| 手段 | 什么时候用 | 代价 |
| --- | --- | --- |
| **调整选择器形状 + 源码顺序** | 对手是普通声明，特异性可以够到 | 需要知道对方规则的确切特异性（DevTools 里能直接看到） |
| **`:where()` 把自己的权重归零** | 你在写重置层、主题层，希望任何人都能轻松覆盖你 | 只能让自己变弱，不能让你变强 |
| **`@layer` 把自己的层排在后面** | 项目里所有样式都由你控制，或对方也在分层 | 若对手是**未分层**样式，未分层在普通档里最大，`@layer` 反而赢不了（第 1 章实测） |
| **改结构 / 加语义钩子** | 对手用了 id，或者用了 `!important` | 要动 HTML，成本最高但最彻底 |

最后一条值得展开：当你发现自己的选择器长度在往上卷（`#a .b .c > d:nth-child(2)` 这种），正确反应不是继续加，而是**给目标元素加一个稳定的类名钩子**（`.price-row--discounted`），把比较拉回 `(0,2,0)` 这一档。选择器长度是负债，不是资产。

## 常见错误与排查

### 症状：加了类、加了层级，样式还是不生效

**先看 DevTools 里那条赢的规则的选择器。** 只要里面有一个 `#id`，你加多少类都没用（本章第一组实测）。三条出路：让 HTML 里那个 id 变成类（如果你是作者）、用 `!important`（临时）、把整份覆盖放进 `@layer`（只有对方也用层或你不在乎层时才有效——对方未分层时未分层最大）。

### 症状：明明写在后面的规则被前面的压住了

检查前面那条规则里有没有 `:is()`、`:not()`、`:has()`。**一个匹配不到的假分支也在计数**（本章 E、F 用例实测）。这类规则肉眼看着「比我短」，实际权重高一档。

### 症状：用 `:not()` 排除一类元素，结果把整条规则废掉了

`a:not(.disabled)` 的特异性是 `(0,1,1)`，而 `a.disabled { ... }` 也是 `(0,1,1)` —— 平局看顺序，写在后面的赢。这类「看起来是包含关系、实际是平级关系」的冲突，最省事的解法是把状态写成两个互斥类（`.is-disabled` / `.is-enabled`）而不是靠 `:not()` 兜底。

### 症状：框架的组件样式覆盖不掉，加 `!important` 后越加越多

先遍历一次它的样式表，把候选规则的选择器抄下来数特异性（本章审计一节的做法）。带 `[data-v-...]`、`[class*="..."]`、`.x.y.z` 的框架规则实际档位通常比肉眼估计高 1–2 档。**补特异性 → 抢顺序 → 才考虑 `!important`**，顺序不要倒过来。

### 症状：DevTools 里样式被划掉了但找不到是谁压的

被划掉只说明「有别的声明赢了」，不告诉你赢家。做法：在 Styles 面板里逐条勾掉候选（取消勾选等于临时删除该声明），或者反过来，用 `element.style.setProperty('color', 'red', 'important')` 从最高档试起——行内 `!important` 是实测过的最高档（第 1 章），它若还不生效，问题就不在层叠而在选择器没命中，去 `document.querySelector` 验证元素选对了没有。

## 练习

<Exercise title="练习 1 · 数特异性并预测赢家" difficulty="基础">

下面六个规则全部命中同一个元素 `<a class="active">`（位于 `#main > nav.nav > ul.menu > li.item` 内）。写出每条的特异性，预测最终颜色。

```css
.nav .menu .item a          { color: rgb(2, 200, 2); }   /* ② */
#main .menu a.active        { color: rgb(4, 240, 4); }   /* ④ */
:where(#main) .menu a.active{ color: rgb(6, 60, 6); }    /* ⑥ */
nav ul li a                 { color: rgb(8, 80, 8); }    /* ① */
#main a                     { color: rgb(3, 30, 3); }    /* ③ */
:is(#main, .nav) a          { color: rgb(5, 50, 5); }    /* ⑤ */
```

<template #answer>

| 编号 | 选择器 | a | b | c | 特异性 |
| --- | --- | --- | --- | --- | --- |
| ① | `nav ul li a` | 0 | 0 | 4 | `(0,0,4)` |
| ② | `.nav .menu .item a` | 0 | 3 | 1 | `(0,3,1)` |
| ③ | `#main a` | 1 | 0 | 1 | `(1,0,1)` |
| ④ | `#main .menu a.active` | 1 | 2 | 1 | `(1,2,1)` |
| ⑤ | `:is(#main, .nav) a` | 1 | 0 | 1 | `(1,0,1)`（`:is` 取最高的 `#main`） |
| ⑥ | `:where(#main) .menu a.active` | 0 | 2 | 1 | `(0,2,1)`（`:where` 贡献 0） |

赢家是 **④，`rgb(4, 240, 4)`** —— 实测结果与之一致（该用例就是本章构造的探针页面之一，六条规则按 ②④⑥①③⑤ 的顺序书写，赢家并不在最后）。

两个附带结论：

- ③ 与 ⑤ 特异性完全相同（`(1,0,1)`），因为 `:is()` 只取最高的参数，`.nav` 那一支等于没写。若 ④ 不存在，⑤ 会因源码顺序在后而胜出。
- ⑥ 是 ④ 的「去权重版」：内容一模一样，只因 `#main` 被包进 `:where()`，权重从 `(1,2,1)` 掉到 `(0,2,1)`，于是它输给 ②（b 位 3 > 2）、输给 ③⑤④（a 位 1 > 0），只赢 ①。**这就是给主题层、重置层用的写法。**

**自查**：如果你的答案是 ① 或 ②，说明你按总数字或层级深度在比大小；回到「逐位比较、不进位」一节。

</template>

</Exercise>

<Exercise title="练习 2 · 把 !important 全部去掉" difficulty="进阶">

你在维护一个用了第三方组件库的页面。组件库的样式是普通全局样式表（未分层），你的样式表在它之后加载。下面这段业务代码里有三处 `!important`，请给出不用 `!important` 的等价写法，并说明每一处靠什么取胜。

```css
/* 组件库内部（不可修改） */
#widget .panel .title span      { color: #333; }
.w-card .w-head .w-desc         { color: #666; font-size: 13px; }
.w-btn[disabled]                { opacity: 1 !important; }

/* 你的样式（可修改） */
.hdr .title span  { color: #0a7 !important; }
.card .desc      { color: #999 !important; font-size: 14px !important; }
.btn:disabled    { opacity: 0.5 !important; }
```

<template #answer>

三处的性质完全不同，得分开处理。

**第一处：能干净解决，但要付出耦合代价。** 组件库那条 `#widget .panel .title span` 是 `(1,2,1)`；你写的 `.hdr .title span` 是 `(0,2,1)`，a 位差 1，**加多少个类都追不上**（本章第一组实测）。可行的纯特异性解只有一种：把那个 id 借用进你的选择器——`#widget .hdr .title span` 也是 `(1,2,1)`，平局，你的样式表在后加载 → 你赢，`!important` 可以去掉。代价是你的样式从此依赖组件库内部的一个 id 字符串，它一改就静默失效，所以必须在注释里写清「依赖 `#widget` 这个 id 与加载顺序」。如果那个 id 不在目标元素的祖先链上（借用不了），就没有不靠 `!important` 的出路，此时保留它并写注释，比强行凑一条五层级的选择器诚实得多。

**第二处：干净解决。** `.w-card .w-head .w-desc` = `(0,3,0)`，你的 `.card .desc` = `(0,2,0)`，低一档。把中间那层补上即可——给容器加上你自己的类，写成 `.card .wrap .desc { color: #999 }`（`(0,3,0)`），与对方平局，由源码顺序接管，你的表在后 → 赢（这正是本章第二组实测的机制）。**注意这条胜利完全依赖加载顺序**，所以要在代码里注释一句「依赖本表在组件库之后加载」，否则将来有人调整了 CSS 合并顺序就会静默失效。`font-size` 那条同理。

**第三处：必须用 `!important`，或者绕开属性层。** 组件库自己已经用了 `opacity: 1 !important`。`!important` 之间仍然比特异性再比顺序：`[disabled]` 是 `(0,2,0)`，`:disabled` 也是 `(0,2,0)`（伪类与属性选择器同档，本章实测），你写在后面 → 但**只有在你也加 `!important` 的前提下**才成立，因为 `!important` 档位永远压过普通声明。想彻底摆脱它，只有两条路：① 用 `@layer` 把自己的 `!important` 放进排序更靠后的层（第 1 章实测：分层 `!important` > 未分层 `!important`）；② 不用 `opacity` 表达禁用态，改用一个对方没占用的属性，例如 `filter: grayscale(1)`——不同属性之间不存在层叠竞争。

**评分标准**：三处都答对「靠什么赢」才算通过。只写「加更高特异性」而说不出具体数字的，按未作答处理。

</template>

</Exercise>

<Exercise title="练习 3 · 阅读一段真实样式表并做审计" difficulty="进阶">

打开你正在维护的任意一份 CSS（本站可以直接审计 `.vitepress/theme/style.css`，本章审计一节就是它的样例结论），完成四件事：

1. 数出每条规则的选择器特异性，列出最高的一条。
2. 找出所有 `!important`，逐条判断：它压住的是谁？把 `!important` 去掉，DevTools 里 computed 值会不会变？
3. 找出所有 id 选择器，标注它们是「定位用」还是「样式用」。
4. 给出一份改写方案：哪些可以改成类 + 顺序，哪些必须保留。

<template #answer>

以本站 `.vitepress/theme/style.css` 为例，一份合格的审计结论长这样（其中带「实测」标记的条目在本项目里已经用浏览器验证过）：

- **覆盖时要当天花板算的规则**：`.VPDoc.has-aside .content-container[data-v-e6f2a212]` 与 `.VPDoc:not(.has-sidebar) .content[data-v-e6f2a212]`，都是 `(0,4,0)`——它们来自框架编译后的 scoped 样式，**不在你写的文件里**，但你所有覆盖都得按这个档位来算。
- **两处 `!important`（第 26、128 行）性质不同**（实测）：第 26 行的 `max-width` 撤掉 `!important` 后 computed 值不变（`(0,3,0)` 本就压过主题的 `(0,2,0)`），但**它管的属性不是决定正文宽度的那个**——真正生效的是 `.content-container` 的 `688px`；它在「无侧边栏的文档页」上才会承重（主题的 `:not(.has-sidebar)` 规则是 `(0,4,0)`），而本站目前没有这种页面。第 128 行的 `padding` 与主题的 padding 规则受互斥的媒体查询保护，不会同时激活，冗余但无害，且因无法在 ≥960px 视口实测而保留。
- **id 选择器：0 处。**（实测方式：在整个 `style.css` 里搜 `#`，零命中。）全站样式没有一处用 id 定位元素——这是刻意的：id 选择器让覆盖方只剩 `!important` 一条路（本章第一组实测）。定位靠的是组件类名（`.VPDoc`、`.vp-doc`）与自定义属性（`--vp-doc-max-width`）。
- **改写方案**：把宽度覆盖从 `.content` 挪到 `.content-container` 并补足特异性到 `(0,4,0)`，`!important` 可以去掉；padding 那条保留原样并写注释说明「与主题 ≥960px 规则互斥，未实测，保守保留」。本站采纳了第二条，**没有采纳第一条**——因为它改变正文行宽，而可用环境里没有宽视口可做目视验收。审计的产出因此是「注释里的结论 + 一条待验证的改法」，不是「改了但没人看过」。

**做这道题的关键不在改写方案本身，而在第 2 步：`!important` 去掉之后 computed 到底变不变。** 变了，说明它在承重；没变，说明它只是历史噪声——而噪声会诱导下一个维护者继续加。如果你们的构建没有 CI 检查，这类审计建议每半年做一次，一次 30 分钟。

</template>

</Exercise>

## 官方文档与延伸阅读

- [Selectors Level 4（W3C）](https://www.w3.org/TR/selectors-4/) —— 特异性计算（§9 Specificity）与 `:is()`/`:where()`/`:not()`/`:has()` 的计数规则的规范原文。本章「函数型选择器按最高参数计」的结论以此为准。
- [MDN · Specificity（特异性）](https://developer.mozilla.org/en-US/docs/Web/CSS/Specificity) —— 英文，含计算器与常见误区；[中文版本](https://developer.mozilla.org/zh-CN/docs/Web/CSS/Specificity) 已同步。
- [MDN · `:is()`](https://developer.mozilla.org/en-US/docs/Web/CSS/:is) 与 [MDN · `:where()`](https://developer.mozilla.org/en-US/docs/Web/CSS/:where) —— 两者对特异性的贡献差异就是本章 E、D 两个用例的结论。
- [MDN · `:has()`](https://developer.mozilla.org/en-US/docs/Web/CSS/:has) —— 父选择器；计数规则与 `:is()` 相同，本章未实测。
- [MDN · `@layer`](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer) —— 用层替代特异性战争，见第 1 章的实测表。
- 下一章：[盒模型：宽度、百分比基准与外边距折叠](/css/box-model) —— 选择器决定「谁的声明生效」，盒模型决定「生效后元素占多大地方」，而后者才是布局 bug 的大头。
