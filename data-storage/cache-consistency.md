# 缓存一致性：先删还是后删不是玄学，是两条长度不同的脏数据窗口

用户在 App 里改了昵称，刷新三次还是旧的。你检查了接口、检查了前端，最后发现列表页读的是缓存——而缓存里那条记录是修改之前回填进去的。这类故障的现场描述永远是同一句：「数据不一致」。但「不一致」在缓存这一层有两个来源完全不同、修法也完全不同的病：一个是**新鲜度滞后**（缓存里还是旧值，因为它压根还没被通知过），另一个是**脏回填**（并发读写互相踩了一脚，把旧值当成新值塞回了缓存）。前者加失效机制就能压小，后者加不加失效都会发生——它恰恰是失效机制自己造成的。

最常见的两种「修复」都是有害的。第一种是把缓存改成「写库时顺手把新值写进缓存」：看起来更聪明，实际把双写失败、并发写顺序反转、计算型字段三份新问题引进来了。第二种是把 TTL 缩到 30 秒「保证最终一致」：脏读的时间窗从不可控变成可控，但代价是全库的缓存命中率被人为压低，而且用户在 30 秒内改两次名字，第二次还是能读到第一次的值。

这一章把顺序问题算清楚：给定读写耗时与失效时机，脏数据能活多久、能被多少次读到。下面所有的表格数字都是本机跑出来的（同目录 `.scratch/ds-consistency.mjs`），Redis 命令一律是预期结果。看完你应该能做三个决定：**写路径用哪种顺序、兜底 TTL 留多长、哪些字段干脆不该进缓存**。

## 两种不一致必须分开算

**新鲜度滞后**：写发生在 t=0，缓存里的旧值要等到失效动作或 TTL 到期才走。这段时间内的读全部返回旧值——这是缓存的定义，不是 bug。你能控制的只有「多久」，所以这一类的唯一命题是**把失效动作从业务代码里可靠地触发一次**。

**脏回填**：写请求删了缓存，与此同时一个读请求正在查数据库。读拿到的是提交前的旧值，但它写回缓存的动作发生在删除**之后**——于是缓存里出现了一个「比库还旧、且刚刚被写入、TTL 从此刻重新起算」的值。这一类不是滞后，是**失效机制自己把旧值塞回去了**，最坏情况把新鲜度重置成一整个 TTL。

两者的判定方式不同。滞后可以从「写成功」到「缓存失效」打点量出来；脏回填只能靠读侧发现：缓存命中时返回的版本号比库里当前版本号旧，且缓存条目的写入时间晚于最近一次失效时间。所以下面所有表格都只算脏回填——把「读到旧值」的场景计数，按脏值存活时长折算成脏读次数。

## 六种做法的实测对照：脏值能活多久

跑出来的两张表，第一张是 4ms 的快读（主键点查，缓存 miss 后最常见的形态），第二张是 20ms 的慢读（带 join 的查询、或走了延迟一点的从库）。

```text
== 快读 4ms（主键点查） ==
策略                          脏回填场景  活满TTL的场景  该场景δ区间           平均存活ms  最长存活ms  累计脏读
A 先写库后删缓存               104        8            8..11.5ms(4ms宽)      253.2      3000       1053
B 先删缓存后写库               104        34           -5..11.5ms(17ms宽)    992.7      3000       4130
C 先删+写库+延迟双删            104        0            无                   48.5       120        202
D 写库+把缓存更新为新值          104        8            8..11.5ms(4ms宽)     253.2      3000       1053
E 删除失败，只靠 TTL 兜底        104        104          -40..11.5ms(52ms宽)  3000.0     3000       12480
F binlog 订阅异步失效           104        0            无                   81.3       107        338

== 慢读 20ms（复杂查询/从库延迟） ==
A 先写库后删缓存               104        40           -8..11.5ms(20ms宽)    1163.8     3000       4842
B 先删缓存后写库               104        66           -21..11.5ms(33ms宽)   1907.4     3000       7935
C 先删+写库+延迟双删            104        0            无                   69.4       120        289
D 写库+把缓存更新为新值          104        8            8..11.5ms(4ms宽)     253.2      3000       4842
E 删除失败，只靠 TTL 兜底        104        104          -40..11.5ms(52ms宽)  3000.0     3000       12480
F binlog 订阅异步失效           104        0            无                   65.3       91         271
```

「场景数」那一列全是 104，因为「读到旧值」只取决于读的起始时刻是否早于提交（12ms），与各策略无关。真正区分优劣的是第三列往后：**有多少个 δ 位置会让脏值一路活满整个 TTL**，以及**最坏情况下脏值能活多久**。

四条能直接抄进设计的结论：

1. **先删缓存再写库（B）比反过来（A）差一个量级**：快读下活满 TTL 的场景是 34 对 8，累计脏读 4130 对 1053。原因是 B 的删除动作发生在写之前，之后的回填**没有任何后续事件会来清理它**；而 A 的删除动作排在提交之后，回填只要早于删除一步，就会被这次删除顺手清掉。
2. **A 的安全是有条件的**：它只在「读耗时 < 提交 + 缓存操作 = 13ms」时几乎免疫。快读 4ms 只剩 8 个坏位置（窗口 4ms 宽），慢读 20ms 立刻涨到 40 个（窗口 20ms 宽，累计脏读 4842）。所以「先写库后删缓存」是对的，但它防不住慢读——**读越慢，A 越像 B**。
3. **延迟双删（C）与 binlog 订阅（F）都没有活满 TTL 的场景**，最长存活被压到 120ms 与 107ms 这个量级，累计脏读只有 202/338。代价分别是「要维护一个延迟任务」和「要多一套订阅链路」。
4. **只靠 TTL 兜底（E）是唯一会让全部 104 个场景都活满 3000ms 的做法**，累计脏读 12480——它是别的策略失败之后的保底，不是策略本身。

## 为什么删除要排在提交之后

把 A 与 B 的时序摊开看，差别只是那 1ms 的缓存操作排在提交前还是提交后：

```text
B 先删缓存，再写库
  t=0     DEL cache           ← 此刻起，任何 miss 的读都会去查库
  t=0..12 读：查库拿到旧值
  t=12    提交 DB
  t=13    读：回填 cache = 旧值   ← 没有下一次删除了，旧值开始计 TTL
  结果：脏值存活 = 一整个 TTL

A 先写库，再删缓存
  t=0..12 读：查库拿到旧值
  t=12    提交 DB
  t=13    DEL cache           ← 若回填发生在 t<13，脏值被这次删除清掉
  结果：只有「回填时刻 > 13」的读会留下脏值，即 δ + 读耗时 > 13 且 δ < 12
```

A 的坏窗口宽度是 `读耗时 - (提交耗时 + 缓存操作耗时)`。这个式子解释了两件事：为什么快读时它几乎不出现（4 - 13 < 0，窗口为负，只剩「读在提交前 4ms 内才刚开始」的边界情况）；为什么一旦你的查询变慢、或者读走了延迟从库，它就重新打开——**慢读等价于把窗口宽度直接加到读耗时上**。

工程含义是三条：写路径的顺序选 A；把「读耗时 P99」当作缓存失效设计的输入参数；别让 miss 的读走从库（从库延迟是叠加在读耗时上的，会让 A 的窗口宽度和 B 一样难收拾）。

## 延迟双删救的是窗口宽度，不是概率

```js
// A + 延迟双删：第二次删除必须晚于「最慢的那次回填」
async function updateWithDoubleDelete(key, writeFn, { firstDel = true, secondDelMs = 120 } = {}) {
  if (firstDel) await cache.del(key);          // 可选：先删一次，缩短后面的脏窗口
  const row = await writeFn();                 // 提交数据库
  await cache.del(key);                        // ① 主删除，紧跟提交
  setTimeout(() => cache.del(key), secondDelMs); // ② 兜底删除，等慢读回填完
  return row;
}
```

第二次删除的延时要怎么定？答案是**比一次读的最坏耗时（查库 + 回填）更长，比 TTL 短得多的那个数**。我这次模型里第二次删除排在 120ms，慢读的回填最晚发生在 δ + 21ms（δ < 12 → 最晚约 32.5ms），120 足够盖住，所以最长存活只有 120ms；如果我把它设在 50ms，慢读的一部分回填会排在它之后，那部分就又只能等 TTL。所以别抄 120 这个数，去量你自己的读耗时 P99 再加一点余量。

延迟双删的三个真实缺陷要知道：`setTimeout` 在进程被杀时不会执行（优雅关闭期正好撞上就丢了，见[优雅关闭](/backend/docker-and-shutdown)），所以它必须配合「删除失败可被发现」；它删第二次的时候并不知道别人在它之后又回填了没有；分布式环境下每台机器都会排自己的定时器，重复删除本身无害但会放大监控噪声。**它是补丁，不是主方案**——主方案永远是「写成功之后一定有一次删除发生」，兜底删除只是补那一次可能没发生。

## 兜底 TTL 不能省，但要能发现删除失败

E 那一行（12480 次脏读）不是假设，它就是「`cache.del()` 抛了异常但你没看返回值」的线上形态。两种写法区别在这一处：

```js
// 错：删除失败静默
try { await db.update(...); await cache.del(key); } catch (e) { log.error(e); }

// 对：把提交与失效分开处理，失效失败必须留下可查证据
await db.update(...);                        // 提交失败就直接抛，不动缓存
try {
  const n = await cache.del(key);            // n=0 也算失败：键可能刚被别人回填
  if (n === 0) metrics.inc('cache.invalidate.miss');
} catch (e) {
  metrics.inc('cache.invalidate.error');
  await queue.add('cache:invalidate', { key, at: Date.now() }); // 补偿队列，不是 setTimeout
}
```

`n === 0` 这一条很值得单独打点。删除返回 0 意味着「我以为我要删的东西不在那里」：要么键本来就不存在（正常，冷键），要么它已经被别人删过，要么**它在删除之后又被回填了旧值**。最后一种是脏回填的直接信号，配合读侧版本号就能定位到「哪条链路在回填旧值」。

TTL 的定位是「所有一致性机制都失败之后的最长脏读时间」。它应该是你按业务能容忍的最坏新鲜度倒推的数（比如商品详情接受 10 分钟，就设 10 分钟上下，再随机抖动防雪崩——雪崩那部分在[缓存三大问题](/data-storage/cache-penetration-breakdown-avalanche)），而不是「默认一小时」抄来的数。

## 更新缓存和删除缓存不是一回事

把新值直接 `SET` 进缓存（表里的 D）在这套模型下和 A 的数字完全一样——因为它同样依赖「事件发生在回填之后」才能清理。差别出现在另外两处，而且都是只有 D 才有的：

**并发写顺序反转**。两次写 W1、W2，W1 提交早但写缓存晚（网络重试、GC 停顿都可能），W2 的缓存写入排在前面，最后缓存里是 W1 的旧值而库里是 W2 的新值，且没有任何删除会来救。删除缓存不会出这个问题：删两次都是空。

**双写不原子**。库提交成功、缓存写入失败（或者反过来），两边就分叉了。删除缓存失败只是「暂时读到旧值」，更新缓存失败是「读到旧值 + 你以为已经写了新的」。

**计算型字段**。列表缓存、聚合值、拼音排序键这类不能由单行数据推出的东西，写入路径根本没有「新值」可 set，只能失效。

结论：默认用删除（invalidate），只有当值与库一对一、写路径单点、且你能给缓存写入带单调版本时才用更新。要更新就带上版本比较：

```text
-- 预期行为：仅当新版本更大时才覆盖（这段脚本在 Redis 单线程模型里整体执行，未在本机验证）
-- KEYS[1] = 缓存键, ARGV[1] = 新值, ARGV[2] = 新版本号, ARGV[3] = TTL 秒
local cur = tonumber(redis.call('HGET', KEYS[1], 'ver') or '-1')
if cur < tonumber(ARGV[2]) then
  redis.call('HSET', KEYS[1], 'ver', ARGV[2], 'val', ARGV[1])
  redis.call('EXPIRE', KEYS[1], ARGV[3])
  return 1
end
return 0
```

## binlog 订阅把失效从业务代码里搬出去

A 的失效写在业务代码里，意味着每一条写路径都要记得调、每次改数据都要评估有没有漏掉的缓存键、批量修数据时没人通知缓存。把失效搬到 binlog 侧（PostgreSQL 的逻辑复制 / MySQL binlog + Canal、Debezium 这类消费者）之后，**只要库里的行真的变了，失效就一定发生一次**，业务代码不再负责正确性，只负责性能。表里 F 那一行的最长存活 107ms 就是这个方案的实际代价：端到端滞后（我按 60ms 建模，实际取决于你的复制与消费延迟）。

需要真实服务、本机没跑的部分，说清楚边界：

- 复制槽、`wal_level=logical`、发布订阅表、Debezium/Canal 部署、消费者重放与位点保存——**未在本机验证**，PostgreSQL 的部分请对着 [PostgreSQL 官方文档](https://www.postgresql.org/docs/current/index.html) 的复制章节做，Redis 侧的复制与失效关系见 [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)。
- 值得在本地先验证的是**语义**而不是链路：在[数据库阶段项目](/database/project)那套表上手写一条「更新后立刻读缓存」的断言，把消费者换成一个进程内的函数，看最长存活时长能不能压到你的目标值。链路与语义分开验证，比一上来就搭 Debezium 快得多。
- 这个方案的两条新失败模式：消费者挂了（失效停摆，只剩 TTL）与消费者积压（滞后从毫秒级跳到分钟级）。两者都要有告警，且**TTL 兜底照旧保留**。

## 一致性要求高于缓存能力时，别让读走缓存

「改完必须立刻读到自己的改动」这类要求（下单后的订单详情、支付结果页、后台审核状态）不是靠调顺序解决的。三种做法按侵入性从小到大：

1. **写后读走主库并绕过缓存**：请求带上写之后返回的版本号或 `seen` 标记，读接口对这类请求直查库。实现最轻，代价是这部分流量没有缓存收益。
2. **读侧版本号 read-repair**：缓存里存版本号，读的时候若「库版本 > 缓存版本」就地修缓存。这需要读路径多打一次库（可用抽样或按租户做），换来的正是本章表格里所有策略都躲不掉的那一段——回填旧值的读被当场纠正。
3. **把并发写串行化**：真正需要「同一资源同一时刻只有一个写」的场景是[分布式锁](/data-storage/distributed-lock)的范围，本章不展开；但要注意锁只保证写互斥，**不保证缓存与库一致**——锁内的写仍然要有失效动作。

这三条的选择依据是业务能否容忍滞后，而不是「缓存命中率多少」。命中率是性能指标，一致性是正确性指标，别拿前者决定后者。

## 常见错误与排查

**1）改完数据读到旧值，先把锅甩给「缓存没删」。** 现象：写接口返回成功，读接口 3 秒内仍返回旧值。原因可能是三种之一——TTL 未到且根本没有失效动作、脏回填（本章的主题）、读走了延迟从库。确认：让读接口返回时附带缓存条目的写入时间与版本号，对比库里的 `updated_at`；如果缓存条目的写入时间**晚于**你的写时间，那是脏回填；早于则是失效没发生。修法：前者按本章调顺序 + 兜底 TTL，后者把失效动作接进写路径或 binlog。

**2）失效动作写在事务里，事务回滚了缓存已经删了。** 现象：偶发「缓存被删但没有对应写」，读侧大量回源，数据库瞬时压力上升。原因：`cache.del()` 在 `BEGIN ... COMMIT` 之间执行，回滚时删不掉已经发生的删除。确认：在事务里抛异常，看监控有没有 `cache.invalidate` 计数。修法：失效永远排在提交之后（这就是 A 的字面意义），或者排到 binlog 侧。

**3）批量改数据不经过写接口，缓存没收到通知。** 现象：运营在后台执行一条 `UPDATE ... WHERE category = ?`，或者跑了[迁移脚本](/database/migrations)，用户端长时间读到旧值。原因：失效只挂在单一接口的成功路径上。确认：把一次批量改数据放进预发，抽查三个受影响键的缓存写入时间。修法：批量写必须显式失效（或者用按前缀维护的键集合），且这类失效要有「删了多少个键」的日志。

**4）延迟双删的第二次删除用 `setTimeout`，进程重启就没了。** 现象：发版窗口之后出现一批长期不一致的键，且只在旧版本数据上出现。原因：定时器不持久。确认：看发版时刻附近有没有 `cache.invalidate.miss` 尖峰。修法：把第二次删除放进可重放的队列或 binlog 消费者，重试由队列负责。

**5）用「更新缓存」代替「删除缓存」，出现缓存比库旧但库里更新。** 现象：并发写之后缓存值与库值不一致，且再也不会自愈（除非 TTL）。原因：两次写的缓存落地顺序与提交顺序反了。确认：对同一键做两次并发写（第二次带可识别的值），读缓存看是哪个版本。修法：改回删除；坚持更新就带单调版本比较，像上面那段 Lua 一样把比较和写入放在同一个原子操作里。

**6）缓存键里带了不该带的东西，失效时算不出那个键。** 现象：写路径删的键和读路径用的键对不上，删除永远返回 0。原因：键由「租户 + 语言 + 页码 + 排序 + 用户等级」拼成，写侧拿不到全部维度。确认：打印一次删除的完整键名与一次读取的键名做字符串比较。修法：给可变维度建反向索引（按实体维护键集合，或用 `SCAN` 按前缀清理，别用 `KEYS`），并在设计时就把「能被失效」当作键设计的约束——这一条与[数据访问层设计](/database/data-access-design)是同一个问题。

## 练习

<Exercise title="练习 1 · 用你自己的耗时参数复算脏窗口" difficulty="进阶">

本章模型里 A 策略的坏窗口宽度是「读耗时 - (提交耗时 + 缓存操作耗时)」。假设你量到：主键点查 3ms、带 join 的详情查询 45ms、写库提交 20ms、缓存删除 1ms、TTL 3600 秒。请回答：哪条读路径会让「先写库后删缓存」打开脏窗口，窗口多宽；另一个策略「先删缓存后写库」在这两条读路径下的窗口各是多少。

<template #answer>

A：详情查询 45 - (20 + 1) = **24ms 宽的窗口**；点查 3 - 21 < 0，窗口不存在（只剩「读恰好在提交前 21ms 内开始」的边界，本章表里把它算作 4ms 宽的 8 个位置）。B：删除在提交之前，回填只要发生在删除之后就没人清理，窗口宽度约等于提交耗时 + 读耗时——点查 23ms、详情 65ms，且**这些场景全都活满一整个 TTL（3600 秒）**。

所以两条读路径的结论不同：详情查询是 A 的主要风险来源（24ms 窗口 × 高 TTL = 大量脏读），而 B 对两条路径同样糟。这解释了为什么「慢查询多的详情缓存」特别容易出事，以及为什么修 A 的关键是量准慢读而不是换顺序。

把这三个数换成你线上 `EXPLAIN ANALYZE` 与 `PTTL` 实测出来的值再做一次，比引用本章数字有意义。

</template>

</Exercise>

<Exercise title="练习 2 · 故意制造一次脏回填并解释现场" difficulty="挑战">

设计一个能稳定复现「先删缓存后写库」脏回填的最小实验：只有你一个进程、一台 Redis（或本地 Map 替身）、一张表。给出步骤、要让哪两步重叠、以及用什么现象确认脏值确实进了缓存而不是仅仅读到旧值。

<template #answer>

**最小复现**（不需要并发，只要能把时钟暂停）：

1. 库里放一行 `name='old'`，缓存里放同一个值，TTL 设成 300 秒（故意设长，好观察）。
2. 手工把缓存置为「不存在」——模拟删除已经发生（这一步就是 `DEL` 之后的世界）。
3. 发起一个读，**在它查库之后、回填之前停住**：真做的话给读路径加一个可开关的延迟点（`await pauseBeforeFill()`），替身实现里就是在 `cache.set` 前 `await barrier.wait()`。
4. 停住期间执行写：`UPDATE ... SET name='new'` 并提交，按 B 的顺序不再动缓存。
5. 放行第 3 步的读，它把 `old` 回填进缓存。

**确认脏值真的进了缓存**，只看「读到旧值」不够——那可能只是滞后。要拿两条硬证据：一是缓存条目的写入时间**晚于**第 4 步的提交时间（说明回填发生在写之后）；二是此刻直接查库返回 `new`，查缓存返回 `old`（两边都有值且不一致）。再加一条：把 TTL 缩短到 5 秒重跑，脏值 5 秒后消失，这确认了「只有 TTL 能救」这个判定，而不是你的失效逻辑漏了。

反向实验同样必要：把第 4 步改成 A 顺序（提交后 `DEL`）再跑一次，同一条读路径下这次读到的是 `new`——因为回填被第 5 步之前的删除清掉了。**两个顺序在同一份数据上一好一坏，才是这个机制的证据**，只跑一次说明不了什么。

</template>

</Exercise>

<Exercise title="练习 3 · 给失效动作补上可观测性" difficulty="基础">

本章「常见错误 3、6」都指向同一个缺口：删除发生了没有、删掉的是不是该删的键。请给出三个必须存在的指标和它们的告警判据（不要写「监控缓存」这种没法落地的答案）。

<template #answer>

**① `cache.invalidate.count{entity}`**：按实体统计失效调用次数，分母是写接口成功次数。判据：`invalidate.count / write.success < 0.95` 持续 5 分钟 → 说明有写路径漏挂失效（批量改数据、迁移脚本、后台直改库都算写）。这一条抓「常见错误 3」。

**② `cache.invalidate.deleted{entity}`**：删除返回 0 次数的占比。判据：突增到写量的 30% 以上 → 键算错了、或者刚被别人回填（常见错误 6 的直接信号）。注意冷键的正常 miss 也会返回 0，所以要与「读回填计数」一起做比值，不要设绝对阈值。

**③ `cache.staleness.detected{entity}`**：读侧版本号不一致的次数（缓存版本 < 库版本，或缓存条目写入时间 > 最近失效时间）。判据：任意非零持续增长就要查——这是脏回填唯一能被发现的形态，也是本章所有表格最后一列那种「累计脏读」在线上的真实计量单位。

实现上 ③ 别全量做：按 1% 抽样比对，或者只对刚写过的键在 TTL 前半段做一次校验读。全量校验等于给每个读加一次库查询，那就不是缓存了。

</template>

</Exercise>
