# 缓存模式：读别人写好的模式，选自己唯一能用上的那一种

线上有个接口 RT 从 12 ms 涨到 180 ms，DB 的 CPU 贴着 100%。第一反应是"加缓存"，第二反应是从某篇英文博客里抄来了五个名词：Cache-Aside、Read-Through、Write-Through、Write-Behind、Refresh-Ahead。然后团队的讨论就变成了"我们是 Write-Behind 架构比较先进"，一周后上线的方案却是"先更 Redis 再更 MySQL"——这已经不是 Write-Behind，这是丢数据预备役。又过一周，缓存层重启，Redis 里还没落库的半小时订单状态没了，MySQL 里永远停在旧值，因为没有任何一方"负责"把它们对齐。

事故复盘会开完后能得出本章的核心结论：**这五种模式描述的是"缓存与后端之间谁负责读、谁负责写、谁负责回源"的分工契约**，而 Redis 本身对这套分工**一无所知**——它没有"后端"概念，没有回源钩子，不会替你写 MySQL。所以绝大多数团队真正能落地的只有应用层自己实现的 Cache-Aside，其余模式要么需要你能改造缓存中间件（平台团队才做），要么风险根本不可接受。模式名不高级，也不提供任何保证；它只回答三个问题：**未命中谁去读库、写的时候谁更新库、没落盘的写丢了多少**。

前置：[Redis 过期与内存淘汰](/data-storage/expiry-and-eviction)（缓存键的 TTL 与淘汰行为决定了本章所有模式"失效"的确切语义）；[后端分层架构](/backend/layered-architecture)（这些代码到底写在服务的哪一层）。

## 五种模式放一张表：分工、回源者、丢数据窗口

| 模式 | 读路径 | 写路径 | 谁负责回源/落库 | 数据丢失窗口 | 真实存在形式 |
| --- | --- | --- | --- | --- | --- |
| Cache-Aside（旁路缓存） | 应用查缓存，未命中查库并**由应用**回填 | 应用写库，成功后应用失效缓存 | **应用自己** | 无（库是唯一事实源） | 各语言手写，最常见 |
| Read-Through（读穿透） | 应用只问缓存层；缓存层内部未命中自动读库回填 | 缓存库/代理 | 缓存组件 | 无 | 需要缓存 SDK/代理支持 |
| Write-Through（写穿透） | 同 Read-Through | 应用只写缓存层；缓存层**同步**写库再返回 | 缓存组件同步落库 | 无（返回即已落库） | 需要缓存组件持有库写权限 |
| Write-Behind / Write-Back（写回） | 同 Read-Through | 应用写缓存即返回；缓存组件**异步批量**落库 | 缓存组件异步落库 | **有**：两次刷新之间进程/实例崩溃，写永久丢失 | 数据库自己的脏页机制、部分商业缓存代理 |
| Refresh-Ahead（读前刷新） | 未命中读库；**逻辑临近过期**时后台异步刷新，前台几乎总能命中 | 应用/缓存库 | 读路径顺便续命 | 无，但读到的是旧值的概率上升 | Cache-Aside 的增强变体 |

两条必须掰开的区分。第一，**Write-Through 和 Write-Behind 只差一个字，差的是整个数据完整性**：前者是"我替你写，写完才回你"；后者是"我先收下，回头再写"——后者把数据库的持久性承诺替换成了缓存组件的刷盘策略，而 Redis 侧的对应物你已经见过：[AOF everysec 的 1 秒窗口](/data-storage/redis-persistence)。把订单状态、余额这类写放进 Write-Behind，等价于自愿接受"最后 N 秒可能全丢"。第二，**Refresh-Ahead 依赖"逻辑过期"**——键里存 `refreshAt` 而不是物理 TTL 一刀切，这与[缓存三大问题](/data-storage/cache-penetration-breakdown-avalanche)里击穿的解法是同一个机制，那里会给出实测数据。

## Redis 没有回源钩子，所以大多数团队只有 Cache-Aside 一个真选项

Read/Write-Through 听起来更干净——应用层不用写那三段式样板——但它要求**存在一个既认识缓存又认识数据库、还能在你所有语言栈里运行的中间件**。现实里只有三种情况凑得齐：云厂商托管缓存服务自带回源（你买的是"缓存+源站"套餐）、公司有平台团队统一封装了缓存 SDK、或者你整个服务只用一种语言且愿意把 SQL 写进这个 SDK。缺了这些条件，"Read-Through"就退化成一句口号：回源逻辑（查哪张表、怎么带权限过滤、要不要 join）本来就是业务，塞进通用缓存组件就是把业务逻辑劈成两半。

所以选型决策其实很短：

```text
有平台级缓存代理/统一 SDK 吗？
├─ 有 → 读多写少用 Read-Through；写可容忍"缓存代写库"再考虑 Write-Through
└─ 没有 → Cache-Aside（+ 热点读叠加 Refresh-Ahead）
          只有你愿意自建持久队列 + 回放 + 对账时，才碰 Write-Behind
```

代价要说清楚：Cache-Aside 把回源、回填、失效三件事全压在你身上，**每一个都够写出 bug**——失效时机是本章后面"事务时序"一节，失效与更新的竞态是[缓存一致性](/data-storage/cache-consistency)，回源风暴是下一章。模式没有银弹，只是选择由谁来背复杂度。

## Cache-Aside 的骨架代码：三段式，缺一个都不算会

```js
// getWithCache：查缓存 → 未命中查库 → 回填。注意三个细节全在注释里
async function getWithCache(key, loadFromDb, { ttlMs, cache, db }) {
  const hit = await cache.get(key);
  if (hit !== null) return JSON.parse(hit);        // 细节 1：空值缓存让 hit 可能是 "null" 字符串
  const row = await db.query(loadFromDb);          // 细节 2：并发未命中会一起打到这里 → singleflight，下一章
  if (row === null) {
    await cache.set(key, 'null', 'EX', 60);        // 细节 3：不存在也要缓存，短 TTL
    return null;
  }
  await cache.set(key, JSON.stringify(row), 'PX', ttlMs);
  return row;
}

// 写路径：改库成功之后才失效，且是"删缓存"而不是"写新值进缓存"
async function updateAndInvalidate(id, patch, { db, cache }) {
  await db.update(id, patch);                      // 事实源只有库
  await cache.del(`v2:product:${id}`);             // 失效，不是更新；时序问题见下文"事务"一节
}
```

预期行为：首次读一次 DB 一次缓存写，二次读零 DB；`updateAndInvalidate` 后首次读回到一次 DB。`del` 失败（网络抖动）意味着缓存里留旧值，处理方案是重试队列/延迟双删，属于[缓存一致性](/data-storage/cache-consistency)的主题。**为什么是"删"不是"写新值"**：两个并发写各自往缓存里"更新"，落笔顺序和数据库提交顺序没有任何同步关系，缓存会永久停在先提交、后写入的那个旧值上；删除则把决定权交给下一个读请求，最多慢一次、不会错到底。

## 缓存键设计：版本前缀、租户维度、序列化变更的灰度

键名是这套系统里最便宜的演进手段，也是最多人省掉的东西。规范按四段：

```text
v{schema}:{domain}:{entity}:{id}
v2:shop:product:9527
```

- **`v2` 版本段是给序列化格式用的**。缓存值从 JSON 换成 MessagePack、字段从 `{ { name } }` 重排成 `{ { title } }`（形状变了但类没变）——老键没人来通知你，读到就炸或者读出半成品。带版本前缀时换格式 = 换前缀，老键自然过期，读写互不干扰。
- **租户/权限维度必须进键**。`v2:tenant:42:user:7:profile` 而不是 `v2:user:7:profile`——同一份数据在不同租户下的可见字段不同，把过滤后的视图作为缓存对象，键里带上租户；否则 A 租户实例缓存了脱敏版，B 租户读到脱敏版（业务错误），或者反过来串数据（安全事故）。
- **别把用户输入原样拼进键**：基数失控（搜索词全进键空间，LRU 被一次性查询洗劫，对应上一章的扫描污染）+ 注入面（见 [Web 安全](/backend/web-security)）。要缓存搜索结果就缓存"查询指纹"而不是原文。
- **格式变更的灰度序列**：先发"双写读旧"（写 v2:v3 两个前缀，读只读旧）→ 观察新前缀命中率 → 切"读新兜底读旧"（读 v3 miss 则读 v2 并回填 v3）→ 全量后停写旧前缀。每一步都能秒级回退。

## 命中率与读放大：定义不清，指标全白测

**定义**：`h = 命中 / (命中 + 未命中)`。**读放大**：缓存层总读 QPS 与数据库实际承接的回源 QPS 之比 = `1/(1-h)`：

| 命中率 h | 回源比例 | 读放大 | 含义 |
| --- | --- | --- | --- |
| 90% | 10% | 10× | 10 万 QPS 的读，DB 仍有 1 万 QPS |
| 99% | 1% | 100× | 同上场景 DB 降到 1 千 |
| 99.9% | 0.1% | 1000× | 高流量下 DB 依然是三位数，别以为高枕无忧 |

这张表反过来读才是重点：**h 每加一个 9，DB 负载减一个数量级；但 99.9% 在 50 万 QPS 下仍是每秒 500 次回源**——命中率是个百分比，回源量是个绝对值，容量规划看后者。

**测量口径的三个坑**。第一，Redis 服务端 `INFO keyspace` 的 `keyspace_hits/misses` 只统计**到 Redis 的**请求，进程内 L1 命中和 singleflight 合并的等待者根本不经过它——数字与业务真实命中率对不上（各计数器的关系见下文两级缓存）。第二，**空值缓存会把命中率刷得很好看**：缓存"不存在"也是命中，但那是一次业务失败。分开统计"有效命中/空值命中/回源"三类，混一个数是自欺。第三，分 key 类型统计：商品详情 99% 和推荐位 30% 平均出来的数字没有任何决策价值。

Redis 侧的读数方法（预期输出，未在本机验证）：

```bash
redis-cli INFO keyspace    # 每个 db 的 keys/expires/avg_ttl
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses"
# 命中率 = hits / (hits + misses)，两次采样做差得"区间命中率"，别用开机累计值
```

## 两级缓存：进程内 L1 与分布式 L2，快的那级不一致

```text
请求 → L1（进程内存，µs 级，无网络无序列化，但每个实例一份、互相看不见）
     → L2（Redis，ms 级往返，全实例共享）
     → DB（唯一事实源）
```

L1 的存在理由不是省那零点几毫秒往返，是**省 L2 的带宽与连接数**：热点键每秒几十万次读，L2 单实例扛得住 QPS 但网卡先扛不住（对照上一章大 value 的内存账）。典型策略：L1 只缓存"小而热"的值（上限几 KB），容量按"热集 ÷ 实例数"估，实例扩容后 L1 总量会超 L2——这是两级结构最常见的容量误算。

代价是**一致性问题被乘上了实例数**：L2 的键被删被换，L1 里每个实例还各自揣着一份。三条基本纪律：**L1 的 TTL 必须显著短于 L2**（秒级，比如 1~10 s，用新鲜度换掉跨实例广播的复杂度）；**权限/会话这类强敏感数据不进 L1**（登出无法即时触达每个进程）；确实需要即时失效时，用**版本号键**——L1 的键里拼一个来自 L2 的全局版本 `product:9527@v17`，写路径 bump 版本，各实例 L1 里的旧版本键自然成为孤儿等 TTL 收走，比 pub/sub 广播可靠（广播会丢，版本丢失只是多读一次 L2）。部署/重启后所有实例的 L1 同时清空，冷启动回源量 = 实例数 × 冷读量，配合限流与预热，这是下一章雪崩的伏笔。

L1 的最小实现不需要库（可直接在本机 Node 跑）：

```js
class L1 {
  constructor(max) { this.max = max; this.m = new Map(); } // Map 保持插入序 → 廉价近似 LRU
  get(k) {
    const e = this.m.get(k);
    if (!e) return undefined;
    if (e.at + e.ttl < Date.now()) { this.m.delete(k); return undefined; }
    return e.v;
  }
  set(k, v, ttl) {
    if (this.m.size >= this.max) this.m.delete(this.m.keys().next().value);
    this.m.set(k, { v, at: Date.now(), ttl });
  }
}
```

预期行为：容量满时最旧的键先出（插入序≠访问序，这是"近似 LRU 的近似"——别把它当本章 LRU 讨论的替代品，只配给短 TTL 的 L1 用）。

## 缓存失效要等事务提交：一个交错就能把旧值写回来

写路径最阴的不是"忘删缓存"（那只是读到旧值到下次失效为止），而是**时序错了会被并发读者把旧值永久回填**。两个坏序列：

```text
序列 A：T1 BEGIN → UPDATE db → DELETE cache → T1 回滚
  结果：缓存被删了、库没改成。危害小（下次读回填到旧库值），
  但它证明"删缓存"不受事务管辖——缓存操作不是事务资源。

序列 B：DELETE cache →（尚未 UPDATE db）→ T2 读：未命中 → 读库旧值 → 回填旧值 → T1 UPDATE db 提交
  结果：库里已是新值，缓存里是旧值，且没有任何事件会再删它 → 旧值活到 TTL 自然过期。
```

序列 B 的窗口只有毫秒级，但在高 QPS 热键上必中。修法是纪律不是技巧：**数据库提交成功之后**才失效缓存——事务回调（afterCommit 钩子）、或把"待失效键"写进 outbox 表随事务提交、由后台投递，服务层落点见[分层架构](/backend/layered-architecture)，事务边界的通用原理在[事务与并发](/database/transactions)里已经讲透（"读和写不在同一事务里"就是丢失更新的根因，这里是同族问题：删缓存和提交不在同一时序里）。**绝不要在事务内写缓存新值**——缓存不是事务资源，回滚不掉。outbox 方案还顺带解决"删缓存失败"：删除动作和库更新原子落库，投递失败可重试。失效与更新的更多竞态（延迟双删、binlog 订阅失效）归[缓存一致性](/data-storage/cache-consistency)。

## 什么数据不该缓存

给缓存层列一份否决清单，每条都能在事故报告里找到对应段落：

- **强一致读**：支付前余额校验、库存扣减判定。缓存里的"够"不等于此刻够，这类读要么走库要么走带条件的原子写（`update ... where stock >= n` 思路见[事务与并发](/database/transactions)）。
- **一次性读**：搜索长尾词、用户历史列表翻页——命中率接近零，纯粹给淘汰器送燃料（扫描污染，上一章）。
- **超大 value 低复用**：整页 HTML、大对象序列化。放对象存储走 CDN（[对象存储与 CDN](/data-storage/object-storage-and-cdn)），别让 Redis 当文件系统。
- **写多读少**：计数器、状态位。缓存删失或淘汰的概率高于收益，直接库内原子更新。
- **上游已有缓存**：CDN/网关已挡住的静态内容，再加一层只增加两套失效逻辑的相互推诿。
- **合规敏感数据明文外溢**：手机号身份证这类进缓存，等于多 copies 一份到攻击面更大的地方，先回答脱敏与加密归谁管。

## 常见错误与排查

**1. 命中率 99%，数据库照样被打挂。** 现象：大盘一片绿，DB CPU 100%。原因：绝对回源量没算过（50 万 QPS × 1% = 5000），或其中 1 个热键被空值/失效风暴击穿（下一章）。确认：把回源 QPS 打点出来并按 key 聚合，看 top-N。修法：热键 singleflight/逻辑过期 + 给回源本身限流。

**2. 更新接口"删了缓存"，用户还是长期读到旧值。** 现象：偶发，重启后又"自己好了"。原因：本章序列 B 的交错——删缓存发生在提交前/并发读回填旧值。确认：在删除与提交两处打时间戳日志，与读请求的回填日志对齐。修法：afterCommit 失效；上延迟双删前先把提交时序修对，双删只是补丁。

**3. 换了序列化格式后缓存读取批量报错。** 现象：发布后 `JSON parse` 异常刷屏或字段读空。原因：键没有版本段，新代码读旧键。确认：抓一条缓存值看结构。修法：本节的双写切前缀灰度流程；长期靠"格式版本写进 payload + 读方向后兼容"兜底。

**4. 登出后另一用户在同实例读到上一用户的数据。** 现象：多实例偶发。原因：进程内 L1 的键没带用户/租户维度，或 L1 TTL 设了分钟级。确认：复现时固定打到同一实例。修法：键加维度；强敏感数据退出 L1；即时失效用版本号键而不是广播。

**5. 把 Redis 配置成 Read-Through 的"精神版"**：以为 `SET` 了个 key Redis 就会自己去 MySQL 拉数据。现象：缓存 miss 直接返回空，前端显示默认值。原因：Redis 没有后端概念（本节核心）。修法：应用层三段式，或者承认需要自建缓存代理再立项。

**6. Write-Behind 用 Redis 裸做**：先写 Redis 返回、异步任务刷库，Redis 重启丢一批。现象：缓存与库出现永久分叉且无对账。确认：对照[持久化](/data-storage/redis-persistence)章确认丢失窗口。修法：业务关键写不用这个模式；确需写回语义就换持久队列 + 幂等 + 对账（见[可靠投递](/message-queue-cloud/reliable-delivery)）。

四个场景：(a) 商品详情页，读 10 万 QPS，写每天几十次；(b) 用户改昵称，要求其他用户最迟 1 秒后看到新值，且写不可丢；(c) 报表系统每次查询都是新的组合条件；(d) 某内部服务只有 Go 一种栈，公司有统一缓存代理中间件，读远大于写。各选一种模式（Cache-Aside / Read-Through / Write-Through / Write-Behind / Refresh-Ahead 及其组合），各写一句理由。

<template #answer>

(a) Cache-Aside + Refresh-Ahead：写极少，热键临近过期异步刷新，避免 TTL 到点被击穿；不可用 Write-Behind（没有写路径需求，白担丢数据风险）。(b) Cache-Aside：写走"库事务提交后失效缓存"，1 秒新鲜度靠短 TTL + 失效；Write-Through 看似满足但要代理具备库写能力，裸 Redis 做不到——这正是(b)该拒绝时髦词的地方。(c) 不缓存（本章否决清单"一次性读"），或只缓存底层聚合结果而非查询组合。(d) Read-Through：条件凑齐（单一语言栈+现成代理），读大、源稳定；写仍旁路。判分点：理由里要出现"谁负责回源/有没有代理"，只答名词不得分。

</template>

</Exercise>

<Exercise title="练习 2 · 给序列化变更设计灰度" difficulty="进阶">

线上 `v1:shop:product:*` 存的是 JSON，要切换成字段重排后的紧凑格式。给出你的键策略与切换时间线（精确到"哪些请求什么时候读哪个前缀"），并回答：为什么不能直接"代码发布瞬间全体改读新格式但沿用旧键"？

<template #answer>

正确序列：阶段 0，键 `v1:shop:product:{id}` 存旧格式；阶段 1 发布"双写读旧"——写路径同时写 `v1` 与 `v2`（新格式），读路径只读 `v1`；观察 `v2` 回填量与写放大可接受后进入阶段 2"读新兜底旧"——读 `v2`，miss 读 `v1` 并按新格式回填 `v2`；命中率恢复后阶段 3 停写 `v1`，其靠 TTL 自然消亡。任何阶段回退 = 把读切回上一前缀。不能直接改读旧键的原因：缓存里躺着的是**按旧格式序列化的字节**，新代码按新格式解析它们——要么解析异常刷屏，要么静默读出 undefined 字段渲染成默认值；且旧键由历史写入产生、数量巨大，没有任何一次性迁移路径，缓存层也没有版本号可以协商。键前缀版本化就是为这一刻准备的。

</template>

</Exercise>

<Exercise title="练习 3 · 故意构造一次旧值回填并解释日志" difficulty="进阶">

写一个本地实验：用内存 Map 当缓存、一个 sleep 50ms 的假 DB（`get` 返回全局变量 `dbVal`）。开两个异步任务：T1 执行 `cache.del → sleep(10) → dbVal=新值`（模拟先删库后提交）；T2 在 20ms 时刻执行标准三段式读（miss 则读假 DB 并回填）。观察最终 `cache` 里的值与 `dbVal` 是否一致。然后按本章修法调整 T1 的时序再跑一次。写出两次实验各自你看到的值。

<template #answer>

第一次：T2 在 20ms 读到的仍是旧 `dbVal`（T1 还没改），并把**旧值回填**进缓存；40ms 后 `dbVal` 变新，但缓存里是旧的，直到 TTL 才自愈——这正是序列 B 的日志现场："删除时刻 < 回填读时刻 < 提交时刻"三个时间戳排成这个顺序即坐实。第二次修法是 T1 改为 `dbVal=新值（提交）→ 再 cache.del`，重跑后缓存要么 miss 要么装新值。这个实验在本机 Node 可复现（纯内存模型，不涉及 Redis）。注意它暴露的残余窗口：T2 的"读库→回填"不是原子的，若 T1 的删除恰好夹在读与回填之间，旧值照样能写回去——这个竞态的完整解法（版本比较/延迟双删/订阅 binlog）在[缓存一致性](/data-storage/cache-consistency)展开，本练习只要求你抓到"时序错了"这一种错法。

</template>

</Exercise>

<Exercise title="练习 4 · 设计三层命中率打点" difficulty="挑战">

一个采用 L1+L2 Cache-Aside 且回源带 singleflight 的商品接口，要求你设计打点与看板：统计哪些计数器、用哪两个公式算 L1/L2/整体命中率、看板上哪个指标用来判断"该把某个键放进 L1"、哪个用来发现"回源在涨但命中率没跌"的隐患。

<template #answer>

计数器至少六个：`l1_hit / l1_miss`、`l2_hit / l2_miss`（仅统计穿过 L1 到达 L2 的请求）、`origin_calls / origin_joined`（回源执行与合并等待数）。公式：`h1 = l1_hit/(l1_hit+l1_miss)`，`h2 = l2_hit/(l2_hit+l2_miss)`，整体 `h = 1 - origin_calls/l1_requests`——**必须用 origin_calls 而不是 l2_miss 做分母**，因为 singleflight 把 N 个 l2_miss 合成 1 次回源，直接拿 INFO 的 hits/misses 算会和业务口径对不上（Redis 侧 hits/misses 只是参考）。"放进 L1"的判据：按 key 聚合的 `l2_hit 速率 × value 字节` top-N，热且小才进。"回源涨、命中率没跌"的隐患通常是**空值命中在膨胀**（穿透前兆）或 L1 失效风暴（部署导致全体冷启动）——把有效命中/空值命中/回源三条曲线分开画就能 5 分钟内分辨。判分点：知道合并等待不进 L2 统计、知道空值必须单列。

</template>

</Exercise>

## 官方文档与延伸阅读

- [Redis 官方文档入口](https://redis.io/docs/) —— 用于核实本章引用的服务端观测面：`INFO stats` 里 `keyspace_hits/keyspace_misses` 的确切统计口径（是否包含空值返回、是否包含内部过期删除），动手前对着你实例的 `INFO` 实测一遍。
- [Redis 过期与内存淘汰](/data-storage/expiry-and-eviction) —— 站内前置：本章"失效语义"（TTL 不精确、淘汰随机删键）全部建立在那一章上。
- [Fastify 文档](https://fastify.dev/) —— 服务端钩子生命周期（请求级/onSend 等）是 afterCommit 失效逻辑在框架层的挂载点参考，具体钩子名以官方文档当前版本为准。
- [事务与并发](/database/transactions) —— 站内前置：为什么"读和写不在同一事务里就没有一致性"，本章把它推广到"删缓存和提交不在同一时序里"。
