# 分布式锁的四个陷阱：提前过期、误删他人锁、无主释放，以及锁本身救不了的那次脏写

定时任务在两台机器上同时跑了一遍，同一个客户收到两封催款邮件。代码里明明有锁——它是个模块级的 `Map`，在单实例压测里表现完美，一次都没重入。加机器之后，互斥域跟着缩小成了「每个进程自己的地址空间」，两台机器各自持有各自认为独一无二的锁，谁也没拦谁。

第二个现场更贵：库存扣减超卖。加锁之后确实不超了，但一周后日志里出现一条「锁获取失败但业务执行成功」的记录。往前翻，是一次 8 秒的慢查询：锁的 TTL 是 5 秒，业务第 6 秒还在跑，第 5 秒锁已经不属于它了，等待者从这一刻起就进来了——而在第 8 秒，那个「早就失去锁」的旧持有者照常把结果写进了库，写得干干净净，因为它写的是一条 `UPDATE`，没有人问过它「你现在还持有锁吗」。

第三个现场是解锁。老代码 `DEL lock:xxx`，一行,干净。它删掉的键可能不是自己那把锁：你的业务超了 TTL，别人已经拿到锁，你收尾时把别人的锁删了，第三个等待者立刻进入。三个临界区叠在一起，日志里却只有三条「加锁成功、解锁成功」，全都符合预期。

这三件事不是三个 bug，是同一件事的三面：**分布式锁给的是带租约的、概率性的互斥，不是「进不来就是没执行」的硬保证**。本章把这层区别算清楚：什么时候锁会失效、失效之后谁能替你挡住脏写、以及什么时候你根本不该用锁。下面所有数字都是本机跑出来的真库与确定性模拟结果，脚本在 `.scratch/ds-lock.mjs` 与 `.scratch/ds-lock2.mjs`。

<Callout type="verified" title="锁表、唯一约束、原生报错都是真的；「并发」是虚拟时钟编排的">

Windows 10 x64 + **Node v25.4.0**，2026-10-19 运行。锁表 `locks(res PRIMARY KEY, owner, token, expires_at)`、资源表 `resource(id, amount, last_token)`、序号表 `seq` 都是真实 `node:sqlite` 建出来的，`UNIQUE constraint failed: locks.res` 那行是驱动返回的原文，`amount` 与 `last_token` 是查询出来的。

但**「并发」不是真多线程**：交错顺序由一个虚拟时钟 `NOW` 编排（比如把「A 还在业务里、锁已到期」写成 `NOW = 1000` 后再让 B 尝试 acquire）。它证明的是**时序规则**——哪种交错会让两个人同时在临界区里、fencing 在哪一步把谁的写挡掉——不是「实测吞吐能到多少」或「Redis 的 SET NX 有多快」。

互斥违反的判定口径是「两个临界区时间区间重叠」：记录每个持有者进入与离开时刻，两两比较。**重叠一次不等于业务出一次事故**，它度量的是「锁没能提供互斥」的次数。

一处诚实交代：`.scratch/ds-lock.mjs` 的 S5 段把四个耗时的任务排在同一条锁上顺序执行，W2 超时后锁被第三方抢走，导致 W3、W4 的 `acquire` 其实是被拒的——它们从未持有过锁，那两行「可被抢时刻」读的是别人的锁行，会被误读。因此本章的看门狗对照用的是修订版 `ds-lock2.mjs`：**每个场景独立建库，只有一个持有者 A 和一个每 100ms 抢一次的等待者 B**，每个 tick 都断言「这行现在是不是 A 的」。原脚本作为发现过程保留，没有改动。

## 先分清你要的是哪一类：互斥、防重、还是选主

拿锁之前先问一句要什么，因为三种需求的正确机制完全不同，用错的那一种会同时失去性能和正确性。

| 你要的东西 | 常见误用 | 更合适的机制 | 依据 |
| --- | --- | --- | --- |
| 一件事只做一次（下单、发信、扣款） | 加分布式锁包住「查一下有没有做过」 | 幂等键 + 唯一索引 | 上一章真库实测：无索引重放得到 3 行，有 `UNIQUE(user_id, idem_key)` 得到 1 行。锁保护「查再插」仍然有竞态，约束没有 |
| 同一时刻只有一个写者改同一行 | 应用层锁 + 各自 `UPDATE` | 库内行锁 / 条件更新（CAS） | 本章 S4 里那条 `WHERE last_token < ?` 就是它：判断和写发生在同一条语句内 |
| 一段长流程串行化（跑批、迁移、导报表） | 进程内 `Map` 当锁 | 外置带 TTL 的锁 + 看门狗 + 幂等兜底 | 见下面四个陷阱，全部来自这格 |
| 长期只有一个实例活着（leader） | 用短 TTL 锁不断续 | 租约与选主机制 | 锁的续期失败被当成普通错误重试时，会出现「两个 leader」 |

第二行值得多说一句：**能用一条 SQL 解决的，别用一把锁**。`UPDATE stock SET amount = amount - ? WHERE id = ? AND amount >= ?` 把判断和写入压进一个原子语句，比「先加锁读、再改、再解锁」少两次网络往返，也不存在「锁过期了但业务还在跑」这个整类问题。分布式锁适合的是**无法压成一条原子操作的那一段**——跨多个服务、多次外部调用、或者你压根改不动那条写路径。

## 一把可用的锁最少需要四件事

数据库形态（本章实测的就是它）与 Redis 形态（预期，未执行）对照着看，缺一条都会退化成上面某一个陷阱：

```sql
-- 实测用的表：res 是主键，这是「同一条目只有一个持有者」的真正防线
CREATE TABLE locks (
  res        TEXT PRIMARY KEY,
  owner      TEXT NOT NULL,      -- 每次获取的唯一身份，不是进程名
  token      INTEGER NOT NULL,   -- 单调递增，fencing 用
  expires_at INTEGER NOT NULL    -- 租约到期时刻，必须有
);
```

获取要**一个原子步骤做完**「判断没被人持有 + 写入自己」。数据库里就是靠主键或唯一约束的插入冲突：

```text
# 预期语义，本机无 Redis：一条命令完成「不存在才写」，并自带过期
SET lock:acct-1 <随机 owner 串> NX PX 5000
```

写成「先 `GET` 判空、再 `SET`」的两次往返，就是竞态。本章测了这个现场：

```text
=== S7 加锁与判断必须是两步时的竞态（单机内存里也照样发生）===
   两个客户端各自先查（都查到空）、再插：插入成功次数=1，锁表行数=1
   被主键挡住的一方，驱动报错原文: B: UNIQUE constraint failed: locks.res
```

两个客户端都做了「查一下，空的」这一步，然后各自插入。这个脚本是串行跑的，所以第二次插入被 `res` 主键挡下——它给你两个结论：**救你的是约束，不是那个判断**；以及那条冲突错误必须被实现成正常分支（「我没抢到，去等待」），如果它冒成 500，客户端会重试、监控会出现和真实故障混在一起的错误率。这与上一章幂等里那条冲突是同一种代码写法。

释放必须**校验 owner**；过期时间必须**能续**（或者写侧有版本校验，见第四节）。这四条里最常被省掉的是第三、第四条——省掉它们的代码在单实例上永远不出问题。

`owner` 用什么值有讲究：不能是进程名或 IP（同一台机器上多个 worker 会重名），必须每次获取时新生成（随机串或 UUID），并且要在你「拿到锁」的那一刻就记进本地变量——否则你连自己该删哪一行都不知道。

## 陷阱一：锁提前过期，而业务还没跑完

第一个数字是 S1 基线：业务 300ms、TTL 1000ms，一切正常，互斥违反为 0。

```text
=== S1 正常互斥：业务 300ms < TTL 1000ms ===
A acquire={"ok":true,"token":1} | B acquire(在 A 释放后)={"ok":true,"token":2} | B 等待 0ms
互斥违反：{"v":0,"pairs":[]}
```

然后是同一个模型，只把业务耗时改成 1500ms——比 TTL 长 500ms：

```text
=== S2 锁提前过期：业务 1500ms > TTL 1000ms，无续期 ===
A={"ok":true,"token":1} B={"ok":true,"token":2} | 写库结果 A:接受 B:接受
互斥违反：{"v":1,"pairs":["A×B@1000ms"]}
```

注意这一行里**没有任何一步是异常**：A 拿到锁，B 在第 1000ms 也拿到锁（因为租约到期，判断合法），两边的写都被接受，日志里两条都写着「加锁成功 / 解锁成功」。互斥只在「业务耗时小于 TTL」这个前提下成立，而这个前提不是代码保证的——**你的业务耗时分布有多长，取决于 GC 停顿、慢查询、下游抖动、虚拟机的 steal time、甚至一次容器热迁移**，而这些都不在你写 `TTL = 5000` 时的那张桌子上。

修法是续期（看门狗）。下面这张表就是「有 vs 没有」的对照，口径是每个 tick 都断言锁行是否仍属于 A，并让等待者 B 每 100ms 抢一次：

```text
=== S5 修订：TTL=1000ms，业务耗时分档；等待者 B 每 100ms 抢一次 ===
无看门狗：
   W1(150ms) A拿到=true 失去所有权=never B抢入=never B的token=- 续期=0次/失败0次 收尾删除行数=1
   W2(1200ms) A拿到=true 失去所有权=1000 B抢入=1000 B的token=2 续期=0次/失败0次 收尾删除行数=0
   W3(900ms) A拿到=true 失去所有权=never B抢入=never B的token=- 续期=0次/失败0次 收尾删除行数=1
   W4(2000ms) A拿到=true 失去所有权=1000 B抢入=1000 B的token=2 续期=0次/失败0次 收尾删除行数=0
有看门狗（每 TTL/3 续期，带 owner 校验）：
   W1(150ms) A拿到=true 失去所有权=never B抢入=never B的token=- 续期=0次/失败0次 收尾删除行数=1
   W2(1200ms) A拿到=true 失去所有权=never B抢入=never B的token=- 续期=3次/失败0次 收尾删除行数=1
   W3(900ms) A拿到=true 失去所有权=never B抢入=never B的token=- 续期=2次/失败0次 收尾删除行数=1
   W4(2000ms) A拿到=true 失去所有权=never B抢入=never B的token=- 续期=5次/失败0次 收尾删除行数=1

=== S5b 重叠判定：B 抢入时刻 早于 A 业务结束 = 两个临界区重叠 ===
   无看门狗：重叠场景数=2/4  1200ms→B@1000, 2000ms→B@1000
   有看门狗：重叠场景数=0/4  （无）
```

四条值得从这张表里读出来、而不是只读「0/4 打赢 2/4」的东西：

**「失去所有权」和「B 抢入」是同一毫秒。**在这两个模型里，锁一旦到期，等待者下一次探测就进来了。所以判断「有没有出事」不需要等事故日志，看失去所有权时刻是否早于业务结束就够了——这也是为什么续期失败的计数比任何日志都有用。

**`收尾删除行数=0` 是一次真实故障的指纹。**无看门狗的 W2、W4 里，A 结束时执行了带 owner 校验的 release，删掉 0 行：因为那一行此刻写着 `B`。有 owner 校验，这只是「你的解锁是空操作」；没有校验，它就是下一章那个误删。**如果 `changes` 这个数字没有被打点出来，你在线上永远看不见这件事。**

**续期次数本身是成本。**W4 那 2 秒业务续了 5 次（每 TTL/3，即约 333ms 一次）。把 TTL 设成 30 秒就不用续期了吗？不行，见下一条。

**「干脆把 TTL 设很大」不是看门狗的替代品。**TTL 很大时，持有者被 `kill -9`、掉电、OOM 的情况下，锁要等 TTL 走完才被释放，这段时间所有等待者全部阻塞——你会得到一个「偶发但持续几十秒的全局停摆」。看门狗的意义正是把这两件事解耦：TTL 短（崩溃后很快能被接管），但只要进程还活着就一直续（不会中途失去所有权）。它的**残余风险**也要写进设计文档：续期依赖一个定时器，事件循环被长任务卡住、GC 停顿比 TTL 还长、续期请求本身超时，都会让「以为自己还持有」与「实际已失去」脱钩——这就是为什么第四节仍然必须存在。

TTL 取值可以这样定：`TTL 至少是业务耗时 P99 的若干倍`这句话不够，要问的是**尾延迟的成因能不能被你的续期间隔覆盖**。看门狗间隔取 `TTL/3` 是经验做法，它给出两次失败机会；间隔取 TTL/2 时一次抖动就丢锁。

## 陷阱二：unlock 不带 owner，删掉的是别人的锁

在 S2 的时序上继续加一个条件——解锁时不做 owner 校验（`DEL lock:acct-1` 这一行 Redis 命令、或 `DELETE FROM locks WHERE res = ?` 这一条 SQL）：

```text
=== S3 在 S2 之上加上「不带 owner 的 unlock」= 误删他人锁 ===
A 的 unlock 删掉了 1 行（那行其实是 B 的）| C 立刻拿到锁：{"ok":true,"token":3}
互斥违反：{"v":2,"pairs":["A×B@1000ms","B×C@1501ms"]}
```

完整链条读一遍，它比任何一句「要带 owner」都有说服力：A 在第 0ms 拿锁，TTL 1000ms；A 的业务跑到 1500ms；第 1000ms 锁到期被 B 拿走；第 1500ms A 收尾，执行无条件删除——**删掉 1 行，那行是 B 的**；第 1501ms C 立刻拿到锁。于是 A、B、C 三段的临界区两两重叠，违反数从 1 涨到 2。一次误删不会只影响一次，它把锁服务变成了「谁的收尾晚谁就有清场权」。

Redis 侧的对应写法是「先比较 value 再删」，而这**必须是服务端原子的**（Lua 脚本或等价机制；具体命令与脚本形态请按官方文档核实，本章未在本机执行）。写成两次往返：

```js
// 错的：比较与删除之间有窗口，和 S7 那个先查后插同型
const cur = await redis.get(key);
if (cur === owner) await redis.del(key);   // 上一行返回后，这把锁可能已经换了主人
```

它出错的方式非常隐蔽：多数时候 `cur === owner` 成立、删除也确实是自己的键，**只有在刚好过期的那一次**你会删掉别人的。所以判据不是「跑一周没出事」，而是 release 的返回值：`DEL` 返回 1 但你并没有持有、或 `changes` 为 0 却记录成「解锁成功」，都是可观测性缺口。数据库形态里这条最容易实现，因为它就是一次带 `WHERE owner = ?` 的删除，配合 `changes` 打点，S5 表里那两行的 0 就是它在工作。

## 陷阱三：锁的键决定互斥域，锁不住所有写路径就等于没锁

**键的粒度就是边界。**锁 `lock:acct-1` 只互斥这一个账户；锁 `lock:orders` 会串行掉整条下单链路，吞吐直接塌。反过来，如果你在分片表上锁 `lock:acct-{shard}`，而两个分片的请求实际改的是同一行汇总数据，那两把不同的锁彼此不认识——这跟把会话存在两台机器内存里是同一个形状的错误。写锁之前先能回答：**所有会改这份数据的入口，是不是都会经过这一个键？**把这一行的写入点机械列出来（`UPDATE` 语句、批量任务、脚本、别人的服务、消费者重投），逐条问它有没有拿锁；列不全，就把防线挪到资源侧，也就是下一节的办法。

**能用库内锁就不要用外置锁。**`SELECT ... FOR UPDATE`、行锁、advisory lock 把互斥交给已经在保护数据的那个组件，代价是连接与事务生命周期（长事务占着连接池，见 [连接池与慢查询](/data-storage/connection-pool-and-slow-query)）。PostgreSQL 的相关语义请查[官方文档当前版本](https://www.postgresql.org/docs/current/)再决定，本章没有在本机跑过。

## 陷阱四：失去锁的一方照样写成功，锁救不回来时靠什么

这是最反直觉也最值钱的一节。把 S3 的时序原封不动重跑一遍，唯一改动是：**每次写库都带上自己拿锁时得到的单调 token，资源侧拒绝不大于已应用版本的写**。

```js
// 资源侧的判断与写入在同一条语句里：小于 last_token 的写直接被条件挡住
function writeResource(db, token, delta) {
  const r = db.prepare(
    'UPDATE resource SET amount = amount + ?, last_token = ? WHERE id = ? AND last_token < ?'
  ).run(delta, token, 'acct-1', token);
  return r.changes ? '接受' : '拒绝(过期写)';
}
```

跑出来的结果：

```text
=== S4 fencing token：同样的 S3 时序，资源侧拒绝过期写 ===
token A=1 B=2 C=3 | B 写:接受 | A 写(过期持有者):拒绝(过期写) | C 写:接受
最终余额={"amount":120,"last_token":3}（期望只有两个有效写进入）
临界区仍重叠（锁本身没救回来）：{"v":2,"pairs":["A×B@1000ms","B×C@1501ms"]} —— 但脏写被资源侧挡住了
```

读这张表的关键是最后两行**互相不打脸**：临界区仍然重叠两次——A 在第 1600ms 写的时候，B 已经在临界区里了，锁确实没救回来；但 A 那次写被拒绝了，因为它手里的 token 是 1，而资源上的 `last_token` 已经被 B 推到 2。起始余额 100，最终 120，只有两次有效写入进入，正是 B 和 C 那两个当前持有者。

这就是 fencing token 的全部思想：**互斥的正解不在锁侧，在资源侧**。锁只能给你一个「大概没人跟我抢」的窗口，窗口会破；资源侧记得「我接受过最大的版本号」，破窗口里挤进来的旧持有者就写不动。任何声称「绝对互斥」的分布式锁描述都经不起 S2 这条时序，加一个单调版本号比加一层锁可靠得多。

代价也写在明面上，别装作没有：

- 资源必须**能存一个单调整数并参与写判断**。有版本列的表（乐观锁）天然可以；没有的表要么加列，要么改造写 SQL。
- token 必须由**锁服务在获取时发出且单调递增**，不能是客户端时间戳（机器时钟会倒退，也不满足单调）。本章用一张 `seq` 表自增取号。
- **改不动的资源用不了这一招**：发一封邮件、调一次第三方接口、推一条消息，都没有「拒绝过期写」的地方。这时只剩三层：短 TTL + 看门狗把重叠概率压小；把不可逆动作放进事务性 Outbox 或消息队列里、由单分区消费者串行执行（去 [可靠投递](/message-queue-cloud/reliable-delivery) 看这条链路），以及给这些动作本身配幂等键（上一章那条真库结论在这里第二次起作用）。

## 惊群与退避：锁释放的那一瞬间是另一个故障点

50 个等待者轮询一把被持有 500ms 的锁，三种等待策略的实测：

```text
=== S6 惊群：锁被持有 500ms，50 个等待者轮询，有无随机退避的差别 ===
   固定 10ms 轮询：探测查询总数=2500｜同一时刻发现锁空出来的最多人数=50（这些人在同一刻同时发起 acquire）
   固定 200ms 轮询：探测查询总数=150｜同一时刻发现锁空出来的最多人数=50（这些人在同一刻同时发起 acquire）
   指数退避 + jitter：探测查询总数=233｜同一时刻发现锁空出来的最多人数=2（这些人在同一刻同时发起 acquire）
```

两列各自说明一件事。探测总数是**锁服务的负载**：10ms 轮询把 500ms 变成了 2500 次查询，这是纯粹为「问一下有没有」支付的开销，而它正好砸在最需要锁服务活着的时候。同刻发现人数是**故障的形状**：固定间隔（无论 10ms 还是 200ms）让 50 个人在同一毫秒一起发起获取请求，只有一个是赢家，其余 49 次都要被拒——加上随机抖动之后同刻最多 2 人，锁服务看到的是一条平滑的到达曲线而不是尖峰。

注意 150 与 233 这一对：加大固定间隔确实省了 8.7 倍查询量，但对惊群**一点用都没有**（两种固定间隔都是 50 人同刻）。退避加抖动的查询数 233，比 200ms 间隔多，却同时解决了两件事——这就是它存在的理由。**间隔再大也不解决同刻问题，同刻只由随机性解决。**这一条对重试、对限流后的 429 回退、对锁等待者是同一个道理，可以在上一章那句「429 之后系统更卡了」里看到同一张脸。

诚实边界：S6 统计的是探测次数与同刻发现人数，用的是虚拟时钟，**没有测真实网络往返与锁服务的实际吞吐**。它给的是「为什么要有 jitter」的机制证据，不是「设成多少毫秒」的调参答案。

真正的解法在退避之上：**别让人问，让他们被通知**。等待者订阅锁释放事件（发布订阅、或库内的等待唤醒），只在被通知时抢一次，本地再加一层 jitter。这个方案的额外代价是多一个订阅通道与「通知丢失」的兜底（超时后自己重试），要在设计里写明。

## 常见错误与排查

**单实例压测全绿，双实例重复执行。** 原因：锁在进程内存里，互斥域只覆盖一个进程。怎么确认：同一份输入并发打到两台实例，比对执行次数与主机名（每次执行都记 `hostname` + `pid`，一行日志就够）；只看一台的日志永远看不出问题。怎么修：外置锁，并且顺手问一句「这是不是防重需求」——如果是，唯一索引比锁便宜且没有过期问题（见陷阱表第一行）。

**日志里出现「加锁成功」也出现「解锁成功」，业务却重复执行了。** 原因：TTL 提前过期，锁在业务中途中途易主（S2 的 `A×B@1000ms`）。怎么确认：把业务耗时分布与 TTL 画在同一张图上，看 P99.9 而不是 P99；再看锁的获取次数是否明显大于业务次数（失去后重取会产生额外获取）。怎么修：看门狗 + owner 校验 + 缩短临界区（把外部调用挪出锁范围），最后再问写侧能不能加 fencing。

**`release` 的删除行数长期是 0。** 原因：你释放的从来不是你的锁行——业务普遍超 TTL，锁早已易主；或者你的 owner 每次都没写对。怎么确认：就是打点 `changes` / `DEL` 返回值，S5 表里那列 0 与 1 的区别。怎么修：先修 TTL 与续期，别去「让 unlock 忽略返回值把日志打得漂亮」。

**解锁后另一个等待者立刻拿到锁，而你的业务还没结束。** 原因：unlock 没校验 owner，删了别人的键（S3 里那句「A 的 unlock 删掉了 1 行（那行其实是 B 的）」）。怎么确认：人为复现——把 TTL 设 1s、让业务睡 1.5s、第三个客户端在等待，看它是否在你解锁后瞬间成功。怎么修：owner 校验 + 比较与删除必须在服务端原子完成（Redis 侧脚本形态按官方文档核实，本章未执行）。

**进程被 `kill -9` 之后，锁很久都没被释放，而加了锁仍然超卖。** 前者原因：只有显式释放、没有 TTL，或 TTL 设得极大——`finally` 里的解锁在 OOM、掉电、容器强杀下根本不执行（`SIGKILL` 连钩子都不给）。怎么确认：测试环境 `kill -9` 一次，观察等待者恢复时间。怎么修：租约必须有 TTL，把「快速接管」交给短 TTL、把「不误伤自己」交给看门狗。后者（超卖）原因：锁没覆盖全部写路径——补偿任务、后台直接改数、缓存回写、消费者重投都在锁外。怎么确认：机械枚举这一行所有 `UPDATE` 来源，逐条核对是否经过同一个键。怎么修：把判断压进同一条条件更新（`WHERE amount >= ?`），或给资源加 `last_token` 做 fencing——S4 那张表演示的就是这个「锁失效但脏写被挡」的兜底。

## 练习

<Exercise title="练习 1 · 为什么 P99 不够用来定 TTL" difficulty="基础">

某临界区业务耗时：P50 200ms、P95 900ms、P99 1.6s、P99.9 9s。你按「TTL 至少是 P99 的 3 倍」把 TTL 设成 5s，看门狗间隔 TTL/3。回答：(1) 这个 TTL 会不会出事，什么时候出事；(2) 看门狗间隔设成 2s 与设成 1.6s，哪个更危险，为什么；(3) 如果一次 Full GC 停顿 6s，你的服务在锁服务眼里发生了什么。

<template #answer>

(1) 会。P99 是 1.6s，但 P99.9 是 9s，超过 5s TTL——按每万次约一次的频率，你的「绝对互斥」每万次破一次。定 TTL 要看尾延迟的**成因清单**（GC、慢查询、下游超时上限之和、容器热迁移），不是看一个分位数。(2) 2s 更危险。间隔 TTL/3 给的是「两次续期都失败才丢锁」的容错；间隔 2s 时 TTL 5s 只剩两次机会，一次超时加一次调度延迟就丢；1.6s 有三次余量。原则是**间隔必须小于 TTL 减去你的最坏续期耗时**。(3) 停顿 6s 期间没人续期，锁在第 5s 过期被 B 拿走；停顿结束后你的进程继续执行原来的业务代码，它**不知道自己已经不是持有者**。此时若写路径没有 fencing 条件，就是你线上那条「两个实例都执行成功」。看门狗的续期失败计数是这类事故唯一会提前暴露的信号，所以它必须打点并告警，而不是被 catch 掉。

</template>

</Exercise>

<Exercise title="练习 2 · 亲手做出误删他人锁并解释现场" difficulty="挑战">

用任一个真库（`node:sqlite` 或 PostgreSQL）复现 S3：TTL 1s，A 拿锁后睡 1.5s，B 在第 1.1s 成功拿锁，C 在等待。要求 (1) A 收尾执行不带 owner 的删除，B 之后能否被 C 抢走；(2) 把删除改成带 `WHERE owner = ?` 的版本再跑一次，两次分别报告删除行数；(3) 说明为什么「删除行数 = 0」不是失败而是保护，什么情况下它反过来才是事故；(4) 给出你在这个实验里看到的原生报错或返回值原文。

<template #answer>

判分点是**你有没有真跑并给出两边的数字**，不是结论对不对。预期与本章实测一致：不带 owner 时删除 1 行（那行是 B 的），C 立刻拿到锁，临界区重叠数从 1 涨到 2；带 owner 时 A 的删除影响 0 行，B 的锁完整，C 抢不进去。「删除行数 0 是保护」的含义是：你已经失去所有权，此时什么都不删才是正确行为。它反过来成为事故的情形有两个——你的 owner 每次都没写对（比如用了进程名而不是本次获取生成的随机串），或者你根本没拿到锁却调用了解锁（这时 0 是正常但日志会骗你，因为你的日志写着「解锁成功」）。所以第三问的答案是打点：把 `changes` 与「本次 acquire 是否成功」一起记下来，两者比值长期偏离 1 就说明 TTL 或 owner 有问题。原生报错那一格，本章在同类约束上看到的是 `UNIQUE constraint failed: locks.res`（S7 抓到的是主键冲突；PostgreSQL 报 `duplicate key value violates unique constraint "locks_pkey"`），它出现在「查过是空的、然后插」的第二次插入上。延伸要求（能做出来算加分）：给这张表加 `last_token`，把 S3 的时序再跑一次，证明重叠仍是 2 但脏写被拒绝——这正是 S4 的输出，也说明修 unlock 不够，fencing 才是那一层保险。

</template>

</Exercise>

<template #answer>

SET stock = stock - ? WHERE id = ? AND stock >= ?`，靠影响行数判断成败；压力更大时用队列把同一个 SKU 串行化。用锁会坏在：热点 SKU 上锁服务变成串行瓶颈（S6 那种惊群还会放大），而且锁过期时超卖照旧——本章 S4 里那条 `WHERE last_token < ?` 就是「把判断交给写语句」的同一个思路。(b) 是三者中唯一真正适合外置锁的，因为它必须靠一个不在事务里的长流程。
