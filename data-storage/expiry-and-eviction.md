# 过期与淘汰：Redis 删你数据的两种方式，都没有精确时间

监控群里先炸的是第一条：「用户隔三差五掉登录，session 查不到」。排查半天，最后定位到 Redis 实例内存打满、`maxmemory-policy` 是 `allkeys-lru`——淘汰器把一部分 session 键当普通缓存删了，而且删得毫无规律，谁最"冷"谁先走，那个"冷"可能只是用户睡了个午觉。第二天又爆第二条：一批 key 明明设置了 1 天过期，过期都两天了，`used_memory` 却纹丝不动，内存顶到上限后淘汰器照样在删**还没过期**的活跃键。

这两类事故对应本章的两个机制：**过期（expiration）**——你告诉 Redis 某个键什么时候该死，但 Redis 并不保证它按时死，也不保证它死得体面（内存回收时机、主从一致性都是另一回事）；**淘汰（eviction）**——内存顶到 `maxmemory` 时，Redis 为了自保主动删键，这个删除不看业务语义、不报错、不进你的错误日志。搞不清这两件事，Redis 就从一个加速器变成"数据源黑洞"：键没了，业务读到的不是异常，而是一个看起来合法的默认值。

前置：[Redis 持久化](/data-storage/redis-persistence) 管的是"重启之后数据还在不在"，本章管的是"运行期间谁先离开、什么时候离开"。两者在 fork 重写 AOF/RDB 时要额外内存这件事上还会互相咬一口，最后会讲到。

## 过期键的三种删除路径：没有一条叫「准时」

`SET k v EX 60` 之后，这个键在 60 秒后**逻辑上**就死了——从这一刻到它**物理上**被释放，中间隔着三条互不承诺的删除路径：

| 路径 | 触发时机 | 开销 | 保证 |
| --- | --- | --- | --- |
| 惰性删除 lazy expiration | 任意命令**访问**到这个键时，先查 TTL，过期则删除并返回"不存在" | 只在访问时付删除成本；永远不被访问的键永不释放 | 读到结果一定正确（不会把过期键当活的） |
| 定期删除 active expiration | 后台周期任务（默认每秒 10 次量级）随机抽一批设了 TTL 的键，删掉其中过期的；过期占比高于阈值就再来一轮，直到超预算 | 采样是概率性的，删除是限时的 | **不保证删完**，也不保证删的速度 |
| 主从传播 | 从库**不自己判过期**，等主库在复制流里发删除事件；主库惰性删除、定期删除或淘汰时产生的删除，才算数 | 从库的删除延迟跟随主库 | 从库可能读到"逻辑已过期、物理还在"的键 |

第三条路径值得单独强调：这意味着**过期语义在读写分离场景是二次延迟的**。你在主库上等到键消失了，去从库查它可能还在；主从切换后，新主上残留过期键继续活一段时间。Redis 官方把过期描述为"尽力而为"，这不是实现瑕疵而是设计：精确删除要求对每个键定时，代价高到不可接受，所以用"读时修正 + 概率清扫 + 复制对齐"的组合兜底。

复现「过期 ≠ 消失」的最小配方（本机没有 Redis 服务，以下步骤未执行，需要 Docker 或 WSL2 起实例后自验）：

```bash
# 1. 设一个 2 秒过期的键
redis-cli SET probe v EX 2
# 2. 等 5 秒后读：应返回 (nil)
sleep 5 && redis-cli GET probe
# 3. 看过期计数：只有被访问或被扫到，expired_keys 才会 +1
redis-cli INFO stats | grep expired_keys
# 4. 对照实验：设 1 个 EX 1 的键，等 10 秒，**不访问它**，
#    查 INFO memory 的 used_memory 是否回落、INFO keyspace 的 keys 数是否变化
```

### TTL 的精度到底是什么

- `EXPIRE`/`SET EX` 是秒粒度，`PEXPIRE`/`SET PX` 是毫秒粒度；内部存储统一是**毫秒级绝对时间戳**。
- `TTL` 命令返回秒，且是向上取整：还剩 1 毫秒时 `TTL` 返回 1，别用 `TTL==0` 判"刚过期"。
- 逻辑过期是精确的（绝对时间戳比对，纳秒级比较无所谓），**物理消失是模糊的**：惰性路径取决于谁来访问，定期路径取决于随机抽样。
- 推论：**任何把"键消失"当业务信号的设计都不安全**——令牌吊销、分布式锁释放、按时间扣费，只要依赖"到点就没人能读到它"，就必须在读侧自己再校验一次时间戳，把 TTL 塞进值里。锁的坑展开见[分布式锁及其陷阱](/data-storage/distributed-lock)。

### 过期键遇上大 key：删除成本在后脑勺爆开

惰性删除的账要按对象大小付。一个装了 100 万个 field 的 Hash 过期后，第一个访问它的请求（哪怕是 `EXISTS`）会触发同步删除，逐个释放百万个内部对象——主线程在这一刻卡住，量级可以到几十甚至几百毫秒（未在本机验证，可用 `redis-cli --latency` 或 latency monitor 观察毛刺是否与 `expired_keys` 跳变同时发生）。配套缓解：`UNLINK` 代替 `DEL` 把释放交给后台线程、`lazyfree-lazy-expire` 等配置让过期删除也走异步（默认值各版本有差异，`CONFIG GET lazyfree-lazy-expire` 自查）。

定期删除路径同样怕大 key：一轮抽样的时间预算是有限的，删一个百万成员的大 key 就能吃完整轮预算，导致**这一轮其他该删的键没删掉**。更难受的组合是"大 key 带 TTL + 没人访问"：逻辑上早过期了，物理上一直占内存，`used_memory` 不降，然后 eviction 开始删那些**还活着的小键**。现象看起来就是"Redis 在随机删我的正常数据"，根因却是过期键在占位。排查动作：`redis-cli INFO stats` 看 `expired_keys` 与 `evicted_keys` 的增长是否脱钩（前者不动、后者疯涨），再用 `redis-cli --bigkeys` 找占位者。

## maxmemory-policy 八种策略：先分清「候选集」和「淘汰依据」

`maxmemory` 是软上限，**只在写命令要突破它时触发淘汰**（纯读流量顶到上限不会开始删，但也不会报错——这是另一个常见误解）。淘汰行为由两个维度决定：从哪些键里选（候选集），按什么标准选（淘汰依据）。八种策略就是这两个维度的组合：

| 策略 | 候选集 | 淘汰依据 | 无候选可淘汰时写命令 | 适用 |
| --- | --- | --- | --- | --- |
| noeviction（通称默认值） | 不淘汰 | — | 直接报 OOM 错误，写全挂 | 数据即业务本体（锁、队列状态、会话兜底） |
| allkeys-lru | 全部键 | 近似 LRU，最近最久未访问 | — | 纯缓存 |
| allkeys-lfu | 全部键 | 近似 LFU，访问频率 | — | 纯缓存 + 有扫描型访问 |
| allkeys-random | 全部键 | 随机 | — | 键基本等概率被再访问 |
| volatile-lru | 只有 TTL 的键 | 近似 LRU | 报 OOM（退化成 noeviction） | 同实例混放"可丢的带 TTL 缓存 + 不可丢的持久键" |
| volatile-lfu | 只有 TTL 的键 | 近似 LFU | 报 OOM | 同上，访问不均 |
| volatile-random | 只有 TTL 的键 | 随机 | 报 OOM | 同上 |
| volatile-ttl | 只有 TTL 的键 | 谁先过期先删 | 报 OOM | 想让"快过期的"提前腾位；实践中几乎不用 |

三条容易理解错的规则：**任意策略下，淘汰候选里如果有"已逻辑过期"的键，会优先直接回收它们**（这不算淘汰，算清理）；`volatile-*` 家族一旦带 TTL 的键被删光，剩余内存压力全部砸回写命令，表现与 `noeviction` 无异，报错原文通常是 `OOM command not allowed when used memory > 'maxmemory'.`（预期文案，未实测）；八种取值、默认值以你的版本的 `CONFIG GET maxmemory-policy` 为准——通行说法是默认 `noeviction`，本文无法在本机验证，标 unverified。

## 近似 LRU：Redis 的「偷懒」和你的直觉差多远

真 LRU 需要一条全局双向链表维护访问顺序：每个键每次被访问都要摘链、插到头——每键额外几十指针字节、每次读写多两次指针操作。Redis 是单线程模型，这笔账太贵。它的替代方案：**要腾位置时，随机抽 `maxmemory-samples` 个键，淘汰其中"最近访问时间最旧"的那个**。每次访问只更新对象头里的一个时间字段，O(1)。

采样算法有个可量化的问题：抽样可能全抽到"其实挺新"的键，导致错杀；也可能永远抽不到某些冷键。samples 越大越接近真 LRU，但淘汰本身是同步在主线程里做的，CPU 开销随 samples 线性涨。我在本机用 Node 复刻了这个采样思路做离散模拟（10 万键空间、容量 5000、100 万次访问、zipf 偏度 0.75、确定性种子），跑出的对照如下：

```js
// 近似 LRU 的核心：淘汰时随机采样 samples 个键，淘汰其中最近访问最旧者
function approxLRU(trace, samples, span) {
  const inCache = new Set();
  const last = new Float64Array(span); // 每个键的最近访问时间，含已淘汰键
  // ... 访问 k：命中则 last[k] = t；未命中且已满：采样若干轮，
  //     victim = 采样命中且在缓存中的键里 last[] 最小者，删除后放入 k
}
```

| 淘汰算法 | 稳定热点流量命中率 | 掺入 10% 一次性扫描流量后 |
| --- | --- | --- |
| 真 LRU | 33.77% | 28.94% |
| 近似 LRU samples=3 | 30.81% | — |
| 近似 LRU samples=5 | 30.94% | 26.29% |
| 近似 LRU samples=10 | 31.19% | 26.41% |
| 随机淘汰（对照 allkeys-random） | 30.80% | 26.23% |

<Callout type="verified" title="以上命中率是本机算法模拟，不是 Redis 实测">

Windows 10 x64 + Node v25.4.0，2026-10-18 运行。这是对 maxmemory-samples **采样思路的自行复刻**，不是 Redis 二进制（Redis 的淘汰池维护细节、访问时钟精度都比这简化）。表内数字只能说明**方向**：samples 越大越接近真 LRU、收益递减（3→10 在这组负载里只换回约 0.4 个百分点命中率）；近似与真 LRU 的差距在这组模型里是 2~3 个百分点量级。别把它们当 Redis 的承诺值。

</Callout>

两个可以从表里读出的结论。第一，**别为那 2~3 个百分点把 samples 拉满**：采样 10 已经基本榨干收益，继续加大只增加主线程负担（samples=100 这类配置基本是给心理安慰付费）。第二，**LRU 的死穴不是"近似"，是"最近"**：第二列里掺入 10% 只访问一次的扫描流量（报表爬虫、批量对账），真 LRU 自己就从 33.77% 掉到 28.94%，近似版跟着塌——扫描键个个"刚刚访问过"，把热键挤出缓存。**这才是 LFU 存在的理由**，不是为了让近似更准。

## LFU：8 bit 计数器和它的衰减

Redis 4.0 起提供 `allkeys-lfu` / `volatile-lfu`（通用说法）。它在对象头里塞了一个 **8 bit 访问计数器（0~255）**，配两个参数改写它的增减曲线：

- `lfu-log-factor`：计数器**不是**每访问加一，而是按对数概率递增——factor 越大，低频段涨得越慢、高频段越能分层。255 饱和不代表"255 次访问"，代表"热到不用区分"。
- `lfu-decay-time`：计数器随时间**递减**（按经过的时间单位扣减，饱和的老键也要不断被新热度供养），默认值与单位口径以你版本的 redis.conf 注释为准（本机无法验证，通行说法默认为 1）。衰减是 LFU 不变成"历史热度纪念碑"的关键：上周爆款的热度会按时间退场，不会永生。
- 新键进门带着一个初始小计数（通行说法为 5，即先给一点保护免得刚写入就被当成最冷淘汰掉），这个门槛决定了缓存预热期的行为。

诚实声明：我同样在本机写了个"计数 + 周期衰减"的玩具 LFU 放进上面的模拟里，结果它**没有**跑出对 LRU 的优势（扫描负载下 26.02%，与近似 LRU 相当）。原因是参数曲线和 Redis 的真实实现差得远——所以对"LFU 抗扫描污染"这条结论，请以上方机制描述和官方文档为准，别引用我那行数字。选型口径：访问分布平稳、有明显长期热点 → `allkeys-lfu`；短窗口爆发型热点、要求快速跟随 → `allkeys-lru`。

## 淘汰与业务错配：缓存变成「数据源黑洞」

最恶性的一类事故不是 OOM 报错——报错至少诚实。是 `allkeys-lru` 的实例里混放了**不可丢的键**，键被删后系统不报错，而是**自圆其说**：

- 会话/令牌：查不到 session 的接口如果写成"查不到就当未登录，重定向登录页"，被淘汰的用户表现为"随机掉线"，日志里一条异常都没有。
- 幂等键：幂等记录被当缓存淘汰，重复请求开始生效，赞数加两次、券发两张。
- 限流/计数键：计数器被删后归零，限流形同虚设，业务还以为防住了。
- 回源逻辑写错：`GET` 不到就返回默认值而不是回源查库——键消失被解释成"数据不存在"，缓存替数据库撒了谎。

这就是"数据源黑洞"：**淘汰是 Redis 语义里的正常操作，却是业务语义里的静默数据丢失**。修复方向按优先级排：一个实例只承担一种身份（纯缓存实例开 `allkeys-*`，存储型实例 `noeviction` + 容量规划 + 告警）；会话类数据必须能在缓存全丢时从[数据库](/database/)完整重建；黑洞式回源代码改成"读不到 = 异常，去查库"，而不是"读不到 = 不存在"。混合放置时 `volatile-*` 只是止痛药（带 TTL 的键被删光照样全挂），别把它当架构。

## 内存预算：每键固定开销、对象头、碎片，一个都不能漏

`maxmemory` 不是实例内存，是 Redis **逻辑用量**上限；进程真实 RSS 还要乘上碎片系数，另外 fork 重写（RDB/AOF，见[持久化](/data-storage/redis-persistence)）时的写时复制要额外留空间。预算从下往上拼：

**单键成本**。一个键占用的内存大致是：key 字符串本体 + 内部字符串头的对齐开销 + 字典节点 + 值对象头（引用计数、类型、lru/lfu 时钟这些元数据就塞在这里，这也是近似 LRU 不用链表的原因）+ 值本体 + 若带 TTL 则过期字典再登记一次。`SET k 1234567890` 这种 10 字节的值，实际落账是它的好几倍——数量级通常是几十字节/键（通行说法，未在本机验证，用下面的方法实测你自己的）。**键越多、值越小，单位成本越离谱**：5000 万个 10 字节小值，光每键开销就可能占掉数 GB。

**测量方法**（比任何公式都可靠）：

```bash
redis-cli CONFIG RESETSTAT
# 灌入 1 万个与线上同构的键（真实 key 长度、真实值大小、真实 TTL 比例）
redis-cli INFO memory | grep used_memory_dataset
# 单键平均成本 = used_memory_dataset 差值 / 10000
redis-cli MEMORY USAGE some:real:key
```

拿到单键均值后：**预算 = 键数 ×（元数据 + 平均对象字节）÷ 0.7**（0.7 是给碎片、突发增长、复制积压缓冲的余数），再把 `maxmemory` 设成容器/主机可用内存的六到七成——剩下的给 fork（未在本机验证，原理与观察方法见持久化章）。

**jemalloc 碎片**。Redis 用 jemalloc 按大小级（size class）分配，删掉大对象后页内可能只剩零头，RSS 还给不了操作系统。看这个比值：

```bash
redis-cli INFO memory | grep mem_fragmentation_ratio
# 预期：1.0~1.5 之间属正常；> 1.5 持续走高，考虑 activedefrag（需编译支持，默认值未在本机验证）
```

`mem_fragmentation_ratio` **低于 1** 是另一个方向的红线：说明部分内存被换页出去了，Redis 响应会偶发地慢到秒级——这比淘汰恶性得多，立刻去看 swap 配置，别调 Redis。

## 监控哪些指标能提前发现「要爆内存」

淘汰和过期不产生错误日志，只能靠指标趋势。按"离爆炸的时间"排序：

| 指标（来自 INFO） | 含义 | 告警姿势 |
| --- | --- | --- |
| used_memory / maxmemory | 逻辑用量占比 | 80% 预警；这是最基础也最滞后的 |
| used_memory_peak 增速 | 历史最高与斜率 | 按增速线性外推"几小时后触顶"，排值班 |
| mem_fragmentation_ratio | RSS/逻辑用量 | 持续 > 1.5 报警；< 1 红色报警（在换页） |
| evicted_keys | 已被淘汰的键总数 | **斜率非零即事故**，说明已经在爆；接业务损失评估 |
| current_eviction_exceeded_time | 当前处于"超限持续淘汰"的时长 | 非零说明此刻就在淘汰风暴中 |
| expired_keys vs used_memory | 过期清理与内存释放是否对得上 | 前者猛涨、后者不降 → 大 key 碎片或同步删除拖累 |
| 命中率（keyspace_hits / misses） | 缓慢阴跌 = 热数据正被错杀 | 环比下跌 5% 就该查 evicted_keys，别等客诉 |
| 容器 RSS vs limit | 进程真实内存 vs cgroup 上限 | 到 90% 就接近 OOMKiller——它不看你的 maxmemory |

最后一行点破一个常见盲区：**杀死 Redis 的往往不是 maxmemory，是 OOMKiller**。`maxmemory` 只管 Redis 自己的数据账，复制缓冲、AOF rewrite buffer、碎片都在账外。所以"used_memory/maxmemory = 60%"的实例照样可能被容器杀掉——监控必须同时盯进程 RSS 与容器 limit，两者的余量才是真实余量。

## 常见错误与排查

**1. 容器里的 Redis 被 OOMKiller 杀掉，日志最后一条是正常操作。** 现象：实例重启，`maxmemory` 明明没到。原因：RSS = 逻辑用量 × 碎片系数 + fork 写时复制 + 缓冲，账外部分先撞上 cgroup 上限。确认：宿主机 `dmesg | grep oom`（Linux 侧，未在本机验证）、对比 killed 时刻的 RSS 曲线与 `used_memory` 曲线是否分叉。修法：`maxmemory` 只设可用内存的六到七成，盯 RSS/limit 告警，碎片高就 `activedefrag` 或计划内重启。

**2. 设了 volatile-lru，写命令还是报 OOM。** 现象：内存满、报错文案像 noeviction。原因：实例里的键大多**没带 TTL**，volatile 候选集是空的，策略名不副实。确认：抽样 `TTL key` 返回值分布，`-1` 占比一目了然。修法：缓存键要么统一带 TTL（并接受 TTL 章的"不精确"），要么改 `allkeys-lru` 并接受数据被删——或者最干净的：拆实例。

**3. 「键过期了内存就该降」的错觉。** 现象：`expired_keys` 猛涨，`used_memory` 不动，随后 `evicted_keys` 开始涨，删的全是活键。原因：过期键没被惰性（无人访问）也没被定期（预算被大 key 吃掉）回收，占着位置。确认：`--bigkeys` 找过期的大集合键。修法：给大 key 拆桶；评估开 lazyfree 异步过期删除；别让单键超过千级成员。

**4. 把 TTL 当业务定时器用。** 现象：定时对账依赖"到期键消失"，偶发读到旧值或从库上更旧。原因：过期是尽力而为 + 从库二次延迟。确认：读写分离链路上复测同一个键在主从的消失时刻差。修法：时间判断写进值里由读方校验；需要"到点执行"的语义用[延迟消息](/message-queue-cloud/dlq-delay-order)，不要用键过期。

**5. maxmemory-samples 调到 100 追求"真 LRU"。** 现象：命中率没肉眼变化，P99 变差、CPU 上升。原因：淘汰是同步采样，开销线性于 samples；而模拟显示 3→10 收益只有零点几个百分点，再多基本是噪声。确认：分别设 5/10 观察一天命中率与延迟。修法：回到默认附近，把精力花在选 LRU 还是 LFU 上（看你的流量里有没有扫描污染）。

**6. 掉线/重复发放类故障先查了三天应用代码。** 教训对应"数据源黑洞"一节：现象随机、日志干净。确认动作永远是同一步——先拉 `evicted_keys` 时间轴与故障时间轴对齐，再谈其他。修法见上文：拆实例、noeviction + 告警、回源代码改"查不到 = 查库"。
