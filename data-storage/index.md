## 这个领域解决什么问题

前面的[数据库领域](/database/)让你把数据「存对、查对、不丢」。但在真实产品里，还有一大类问题**只有当用户量、并发量上来之后才会显现**——本地开发和几十个用户时一切正常，一旦上了量，性能和一致性问题集中爆发：

- 首页每次都从数据库重算一大堆数据，明明内容几小时才变一次 —— 因为你没上缓存，数据库被重复的读请求压垮。
- 加了缓存之后，用户改了数据，页面却还显示旧值 —— 因为你没处理好缓存和数据库的一致性。
- 一个热点 key 突然过期，成千上万的请求瞬间全部打到数据库，数据库当场被击穿 —— 这就是缓存击穿；如果大批 key 在同一时刻集体过期，就是缓存雪崩。
- 有人用不存在的 id 疯狂查询，每次都穿过缓存直接打到数据库 —— 缓存穿透。
- 你的服务部署了两个实例，用户在这个实例登录、下个请求落到另一个实例就掉线了 —— 因为会话存在了单机内存里，没做分布式会话。
- 一个「点赞」接口被快速点两次，赞数加了 2 —— 因为你没做幂等，也没考虑并发下的竞态。
- 数据库连接数被耗尽，新请求全部超时 —— 因为连接池没配好，或者某处忘了释放连接。
- 一条查询在测试库（几百行）飞快，在生产库（几百万行）要十几秒 —— 因为你没做过慢查询定位。

这个领域就是专门收拾这些「上量之后才出现」的问题。它围绕两条主线：**一是 Redis 与缓存**（数据结构、持久化、各种缓存模式与三大经典问题、分布式会话/限流/锁），**二是 ORM 的深入与数据访问性能**（Prisma 的关系查询与事务、原始 SQL、连接池、慢查询）。因为它解决的问题都建立在「你已经有一个能跑的数据库后端」之上，所以被放在**第二期**——先让产品能上线，再让它扛得住量。

## 前置知识

- [数据库](/database/) —— 你必须先懂 SQL、索引、事务和 PostgreSQL 的基本运维，才能理解缓存是在给什么加速、连接池在管理什么、慢查询为什么慢。
- [后端开发](/backend/) —— 缓存、限流、分布式会话都挂在后端的请求处理链路上；你需要先理解 Fastify 的钩子、分层架构和认证机制，才知道这些东西该插在哪一层。

这两个前置是硬依赖。没有它们，本领域的内容会变成一堆背下来的名词，而不是能落地的能力。

## 学习顺序建议

**按 1 → 14 顺序学，Redis 与缓存这条线（第 2～9 章）建议连着走完。**

第 1 章先建立「为什么」——这个领域的每一个技术都是在解决一个具体的、上量后才出现的问题。跳过它直接学 Redis 命令，你会不知道这些能力该在什么时候用、值不值得引入（**过早引入缓存和分布式锁，是给自己凭空增加故障点**）。

第 2～4 章是 Redis 的基础能力（结构、持久化、过期淘汰），第 5～7 章是在这个基础上讲缓存怎么用对、怎么不出一致性问题，第 6 章的三大问题是第 5 章模式的补充防护。第 8、9 章（会话/限流/幂等、分布式锁）是并发场景下的进阶，依赖前面对 Redis 的理解。

第 10～12 章是另一条主线——ORM 深入与数据访问性能，它更靠近[数据库领域](/database/)，其中第 11 章的「类型安全边界」和第 12 章的「慢查询定位」直接呼应第 10 章的 N+1 问题。第 13 章对象存储与 CDN 相对独立。**第 14 章是阶段项目：它把前 13 章压在同一条热路径上，用改造前后的数字回答「这一层到底值不值得上线」，前面各章单独验证过的能力只有在它那里才会互相暴露冲突，所以不要跳到最后才做它。**

不能跳过的是第 1 章（建立判断力）和第 6、7 章（缓存最容易出事的地方）。

## 学习方法

**这一领域尤其要「先造出问题，再解决问题」。** 光读缓存三大问题的定义没用——你要在本地用一个脚本把并发打上去，亲眼看到数据库被击穿，再动手加防护，观察它如何被挡住。判断学会的标准：给你一个性能症状，你能推断出可能的原因并设计出验证方法。

**本地环境准备（Windows）：**

- **Redis**：Redis 官方**不提供原生 Windows 版本**，Windows 下有两条现实可行的路：
  - **Docker（推荐）**：装好 Docker Desktop for Windows 后，用容器运行 Redis，配套 `redis-cli` 也在容器里，练完即删。这与项目后续的容器化路线一致，可参考 [Docker Compose 文档](https://docs.docker.com/compose/)。
  - **WSL2**：在 Windows 的 Linux 子系统里安装 Redis，得到一个接近生产的 Linux 环境。
  - （也有第三方把 Redis 移植到 Windows 的产品，但为贴近真实部署，建议优先用上面两种方式。）
- **PostgreSQL**：沿用[数据库领域](/database/)已经装好的实例即可，本领域会在它之上做连接池和慢查询实验。
- **压测工具**：准备一个能发并发请求的工具（脚本或命令行压测工具均可），用来复现击穿、雪崩、限流这些并发问题——没有并发，这些问题你根本触发不出来。
- **ORM**：Prisma 主线、Drizzle 对照，均已在数据库领域安装。

## 阶段项目

**为一个已上线的产品加一层「扛得住量」的数据层**：延续[后端](/backend/)与[数据库](/database/)阶段项目，针对其中一条读多写少的热路径做缓存与性能改造。验收标准：

- 选一条高频读接口，用 **Cache-Aside** 模式加缓存，并能测出缓存命中率；写操作发生时缓存被正确失效，读取到的不再是旧值（一致性）。
- 针对缓存三大问题各有防护：对不存在的查询有防穿透手段、热点 key 失效有防击穿手段、过期时间有防雪崩的打散处理，并能说明各自是怎么做的。
- 至少一个「写」接口做了**幂等**（用幂等键，重复提交不产生重复效果），并有一个限流器保护它。
- 数据库连接池经过配置，能说明连接数设置的理由；用慢查询定位手段找出至少一条慢查询并通过加索引或改写优化它，给出前后对比数据。
- 用压测工具给出改造前后的对比（延迟或吞吐），**用数字证明这层改造确实有用**——如果证明不了，说明当前规模还不需要它，这本身也是一个正确结论。

上面每一条落在哪个阶段、用什么动作判真假、在本机跑出了什么数字，见[第 14 章 阶段项目](/data-storage/project)。

## 版本说明

本领域内容以 **Redis 官方文档** 与 **Prisma / Drizzle 官方文档的最新稳定版** 为准编写，核实时间为 2026 年 10 月。Redis 的核心数据结构与持久化机制（RDB / AOF）非常稳定，跨版本变化小；缓存模式、三大问题、分布式锁的陷阱这些属于**设计模式层面的知识，基本不会过时**。

容易过时、需重点核对的部分：

- **Redis 的具体命令与新特性**：Redis 会在新版本里增加数据类型和命令（例如较新的流、搜索等能力），涉及具体命令参数时请以 [Redis 官方文档](https://redis.io/docs/) 你实际运行的版本为准。
- **ORM 的 API**：Prisma、Drizzle 迭代较快，第 10、11 章的关系查询、事务、原始 SQL 写法请以官方最新文档核对，本站不锁定其小版本号。
- **对象存储与 CDN**：第 13 章涉及的具体云厂商产品与配置差异大、更新快，正文只讲通用思路，落地时以对应厂商的最新文档为准。
