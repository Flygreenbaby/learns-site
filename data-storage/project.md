# 阶段项目：加一层扛得住量的数据层——先用数字证明它值这一层，再决定要不要上线

后端阶段项目交付了一个能测、能拒、能优雅关掉的 API，数据库阶段项目把它的存储换成了真库。接下来的第一反应通常是「上量了，加个缓存吧」。于是你得到：命中率没人测过；用户改了数据页面还是旧值；有人拿不存在的 id 每秒刷一百次；一个热点 key 过期的一瞬间，数据库连接被打满。你以为加了一层保护，实际上是给自己凭空加了一个故障点——这正是[第 1 章](/data-storage/why-this-layer)反复警告的那件事。

前 13 章各自答了一遍机制问题，但**分章验证有个天然缺陷：每章只测自己那一格**。缓存章测了命中率，没测它和索引改造叠加之后还剩多少收益；连接池章测了排队分位数，没测那个排队其实是慢查询伪装的；三大问题章测了防护，没测防护的代价。把它们拼到同一条热路径上，最先坏掉的不是功能，是「值不值得」这个问题本身。

本章的交付物就是逼你回答它。我在本机把改造做完并测了，结论先摆出来，因为它可能和你想的相反：**同一条负载上，只加索引把总耗时从 1293ms 砍到 93ms（降 92.8%），在此之上再加缓存只再砍掉 47ms（降 3.6%）**。按这个形状，缓存不该上线。但这条结论有它严格的适用边界（阶段 ⑧ 拆给你看），本机数字给的是**方法与形状，不是你的结论**——你要在自己的环境里重跑一遍，才有资格说这一层值不值。

## 不做什么

- **不做多实例。** 会话、限流桶、幂等表、缓存都在单进程或单文件库里。多实例下的一致性是[第 8、9 章](/data-storage/session-rate-limit-idempotency)的问题，不是本项目的范围。
- **不上 Redis 服务。** 缓存层用进程内替身，目的是把「命中率、三防、失效」这些机制的因果先测清楚。换成 Redis 的改造要点在参考答案要点 1，那是你接下去做的事。
- **不引入 ORM。** 全部手写 SQL，才看得见执行计划与查询条数。ORM 侧的 N+1 与关系查询在[第 10 章](/data-storage/prisma-deep-dive)已单独验证。
- **不做前端、不做 CI/CD、不写监控大盘。** 日志只要一行 JSON 里带上本章要看的字段（`hit` / `dbQueries` / `waitMs`），够判真假就行。
- **不重设计业务模型。** 沿用后端阶段项目那个多用户资源管理 API 的路由与校验；这里只加数据层。

## 数据层：一张主表、一张幂等表、一条索引

```sql
CREATE TABLE resources (
  id         INTEGER PRIMARY KEY,
  owner      INTEGER NOT NULL,
  name       TEXT    NOT NULL,
  amount     INTEGER NOT NULL,
  version    INTEGER NOT NULL DEFAULT 1,
  updated_at INTEGER NOT NULL
);
CREATE INDEX idx_owner ON resources(owner);          -- 阶段 ③ 之前先不要建，留着测前后

CREATE TABLE idem (
  k          TEXT PRIMARY KEY,                        -- 幂等键，UNIQUE 就是防线本身
  result     TEXT    NOT NULL,
  created_at INTEGER NOT NULL
);
```

主查询接口读的是「某个 owner 的资源列表」：

```sql
SELECT id, name, amount FROM resources WHERE owner = ? ORDER BY id LIMIT 20;
```

## 负载形状：先把「上量」造出来

没有负载形状，后面每一条数字都没有意义。两件事必须先定下来：**数据规模**和**流量分布**。

数据规模用 20 万行。这个数不是随手挑的：几百行的表里 `SCAN` 和 `SEARCH` 都是亚毫秒，索引改造的收益测不出来（[第 12 章](/data-storage/connection-pool-and-slow-query)的 P5 就是这个现象）。建库耗时本机实测：

```text
B0 建库 200000 行耗时 511ms   journal_mode=wal
```

流量分布必须有热点。真实读流量几乎不是均匀的，而是少数 key 承担大头（zipf 形状）。如果你的压测把 key 均匀打出去，命中率会假低、击穿与雪崩也打不出来。本章的形状写成一句话：**40% 的流量落在 3 个 owner 上，其余 60% 摊到 800 个 owner**：

```js
// 决定第 i 次请求读哪个 owner：前 40% 落在 3 个热 key 上，其余摊到 800 个
function pickHot(i) {
  const r = (i * 2654435761) % 1000;      // 确定性伪随机，重跑数字才可比
  return r < 400 ? 1 + (i % 3) : 1 + (i % 800);
}
```

注意 `pickHot` 是**确定性**的：同一个 `i` 永远得到同一个 key。这样阶段 ⑧ 的三臂才是在比同一份负载；否则你会拿两次不同形状的流量互相比大小。

## 阶段 ① 基线：什么改造都不做，先测一次

产出：**一条未改造的总耗时**。这一步最容易跳过，跳过之后你所有「提升了 X%」都是无根的话。

基线臂故意用一条没走的 SQL（把列包进函数，索引直接失效），这是[第 3 章数据库领域](/database/indexes)讲过的形状：

```sql
SELECT id, name, amount FROM resources WHERE owner + 0 = ? ORDER BY id LIMIT 20;
```

跑 1500 次，记总耗时。本机结果在阶段 ⑧ 的三臂表里（A 臂：1293ms）。

## 阶段 ② 连接池：容量算式和真实排队

产出：**一张 poolMax → 等待分位数的表 + 一个写得出理由的连接数**。

先算，再配。单条查询占用连接多久（含网络往返与事务持有），乘以目标 QPS，就是稳态需要几条：

```text
容量算式：目标 120 QPS × 每条占用 12ms = 稳态 1.44 条连接，留 2 倍余量 → poolMax=4
```

这个算式的两项都必须是你测出来的，不是猜的。「每条占用 12ms」在本机是「一次真查询 + 一段人为持有」，对应事务里那段时间（[第 10 章](/data-storage/prisma-deep-dive)的结论：交互式事务把连接按住到整个 handler 结束）。然后把 40 个并发任务分别灌进 poolMax = 1 / 2 / 8 三个池，量每个任务的等待时间（`n` 是等到过时间的任务数，为 0 的直接不记）：

```text
poolMax=1 40 个任务：n=39 p50=330.7ms p95=626.4ms p99=642.0ms max=642.0ms   总耗时=658ms
poolMax=2 40 个任务：n=38 p50=156.6ms p95=298.5ms p99=298.7ms max=298.7ms   总耗时=314ms
poolMax=8 40 个任务：n=32 p50=32.5ms  p95=79.6ms  p99=79.6ms  max=79.6ms    总耗时=95ms
```

读法：**排队时间等于「你前面还排着几个任务」乘以单任务持有连接的时长**。把三个 `max` 除一下就对上：poolMax=1 时 40 个任务串成一队，642ms ÷ 40 ≈ 16ms；poolMax=2 时两队各 20 个，298.7ms ÷ 20 ≈ 15ms；poolMax=8 时八队各 5 个，79.6ms ÷ 5 ≈ 16ms——**每个任务持有连接约 15～16ms**（那 12ms 人为持有加一次真查询），这正是上面算式里「每条占用 12ms」在真实排队下的样子。这就是你写「为什么是 4」的依据，而不是「网上说设 10」。（[第 12 章](/data-storage/connection-pool-and-slow-query)的 P3 还测了泄漏的样子：`Timed out acquiring a connection after 127ms (pool=2, leaked=1)`；池配大只是把泄漏的下一次故障推迟。）

## 阶段 ③ 慢查询：先让执行计划说话

产出：**改造前后的计划文本 + 分位数对比**。这条必须走在加缓存前面，原因见阶段 ⑧。

```text
改造前计划： [SCAN resources]
改造前 n=30 p50=0.7ms p95=0.9ms p99=1.1ms max=1.1ms
加 idx_owner 后计划： [SEARCH resources USING INDEX idx_owner (owner=?)]
改造后 n=30 p50=0.1ms p95=0.1ms p99=0.2ms max=0.2ms   p95 对比：0.9ms → 0.1ms
函数包住列：[SCAN resources USING COVERING INDEX idx_owner]
覆盖索引：[SEARCH resources USING COVERING INDEX idx_owner (owner=?)]
同一条 SQL 把列包进函数（索引已在）：n=30 p50=0.7ms p95=1.0ms p99=1.1ms max=1.1ms
```

三个可复用的判读结论：

1. **只认计划文本，不认「我加了索引」。** 最后一行是故意制造的坑：索引已经在表上了，但 `WHERE owner + 0 = ?` 仍然全表扫（`SCAN`），耗时回到 0.7ms。**列一旦被函数包住，索引就用不上**——这也是为什么 `date(created_at) = ?` 要改写成范围条件。
2. `LIMIT 20` 命中索引后 p50 从 0.7ms 掉到 0.1ms，量级差是 7 倍，但绝对值只有 0.6ms。别为此写一篇战报：在本机这种同进程库里，它值不了几个钱；它的意义在于**扫描行数从 20 万降到 20**，这在生产库上换回的是缓冲池压力与锁竞争。
3. 覆盖索引那一行说明「计划文本里的 `USING COVERING INDEX`」是可见的优化信号——查询只需要 `owner` 一列时不必回表。

## 阶段 ④ Cache-Aside：命中率与省下多少条 SQL

产出：**命中率数字 + DB 查询条数**，以及一份能对着第 5 章流程画的读写时序。

Cache-Aside 的四步（读时先看缓存、没命中查库并回填、写时先落库再**删**缓存）在[第 5 章](/data-storage/caching-patterns)已经论证过为什么是「删」不是「改」。这里只补判据：命中率不是感觉，是 `(请求数 - DB 查询数) / 请求数`。

```text
B3 3000 次读：DB 查询 800 条 命中率=73.3% n=3000 p50=0.0ms p95=0.1ms p99=0.2ms max=3.1ms
```

`max=3.1ms` 那一次就是首个未命中的回源，别把它当异常——它是命中率的代价本身。

写侧的失效与四种读写时序的实测在[第 7 章](/data-storage/cache-consistency)，本章沿用它的结论：**先写库、再删缓存、给删除加一次重试或延迟双删**，且必须接受「删失败就短暂不一致」这个残差，因为它无法原子消除。

## 阶段 ⑤ 三防：穿透、击穿、雪崩

产出：**每个问题一组「无防护 / 有防护」的条数对比**。这一节的三条数字来自同一份代码，只差防护开没开。

穿透（不存在的 id 疯狂查）：

```text
B4 无防护（miss 不写缓存）：400 次请求 50 个不存在的 id → DB 查询 400 条
B4 空值缓存：400 次同样请求 → DB 查询 50 条（=不同 key 的个数 50）
B4 入参白名单先挡掉的形状：5 / 5 条不该打到 DB
```

空值缓存把 400 条压到 50 条，即「每个不存在的 key 只让库回答一次」。但要写清两个代价：**空值的 TTL 必须短**（本机用 30s，避免真实体出现后长期读不到），以及**入参先校验**——`id=0`、负数、超长字符串这类形状，第一道闸在校验层，轮不到缓存。

击穿（热点 key 失效的一瞬间）：

```text
B5 无 single-flight：回源 60 次，全部完成 1829ms
B5 有 single-flight：回源 1 次，全部完成 30ms（等待者共用同一次查询的结果）
```

一次回源约 30ms（这是本机一条真查询的耗时），60 个并发若无 single-flight 就把这 30ms 排了 60 遍。有 single-flight 之后，只有一个请求去查库，其余等待者共享同一个 Promise。它的两个坑必须在代码里处理：**失败也要广播**（否则等待者永久挂起）、**只合并同一个 key**（跨 key 合并就是把 A 的数据给 B）。

雪崩（大批 key 同一时刻过期）：

```text
B6 固定 TTL：900ms 观察窗内回源=3200（覆盖 400 个 key）分布在 8 个 25ms 窗口，最挤的窗口=400 次
B6 TTL 打散 0～400ms：回源=1371（覆盖 400 个 key）分布在 36 个窗口，最挤的窗口=68 次
```

看的是**最挤窗口的峰值**：400 次 → 68 次，5.9 倍落差；两个臂覆盖的 key 数相同（400），说明打散没改变「有多少 key 要回源」，只改变了「它们挤在哪一刻」。**两个臂的回源总数不同（3200 / 1371）是因为固定 900ms 观察窗内跑出来的总请求数不同，这一列不可比**——别抄它当结论，能比的是峰值分布。这是本章刻意留下的一个诚实标注：一个指标只有在同一总量下才有意义。

## 阶段 ⑥ 写侧：幂等键与限流器

产出：**同一幂等键提交多次，库里只有一条**；**突发流量下放行条数等于桶容量**。

幂等交给数据库约束，不要交给应用层的「先查再插」——后者在并发下是两个请求同时查不到、同时插入。

```sql
INSERT INTO idem (k, result, created_at) VALUES (?, ?, ?)
  ON CONFLICT(k) DO NOTHING;
```

```text
B7 同一幂等键提交 5 次：changes 依次=[1,0,0,0,0]，库里落库 1 条
B7 去掉 ON CONFLICT 后的真实报错：UNIQUE constraint failed: idem.k
```

`changes` 是这条语句真正影响的行数：**1 表示这次是首次执行，0 表示命中已有记录**，业务分支据此决定「执行」还是「重放上次结果」。第二条是故意去掉 `ON CONFLICT` 制造出来的报错原文——幂等表的作用就是让并发落在约束上而不是落在 if 判断上。

限流（本机跑的是令牌桶）：

```text
B7 令牌桶 capacity=10 rate=5/s，瞬间打 200 个请求：放行 10 拒绝 190
```

`capacity=10` 决定能扛多大的突发，`rate=5/s` 决定长期Throughput。被拒的 190 个必须返回 `429` 并带 `Retry-After`，且只对**这个写接口**生效——把全局限流打开，你的健康检查也会被限掉。幂等键要有时效并定期清理，否则 `idem` 表只增不减；限流只数请求条数，超体积、超并发的代价它管不了（那属于[后端阶段项目](/backend/project)的 `maxBody` 与排空）。

## 阶段 ⑦ 大响应：把导出从内存里搬出去

产出：**同一个 20 万行导出，两种写法的 rss 峰值对比**。

这条路径的典型写法是「查出来 → 拼成一个字符串 → 一次发出」。本机实测：

```text
[服务端] memory 全量物化 行数=200000 字符串=7.8MB 发完前耗时=671ms 此刻rss=337.0MB
memory   请求数=1 传输=7.8MB 状态=200 Content-Length=8128722 总耗时=744ms 起始rss=61.8MB 峰值rss=345.3MB 峰值增量=283.5MB
memory   请求数=4 传输=31.0MB 状态=200 Content-Length=8128722 总耗时=2670ms 起始rss=61.8MB 峰值rss=619.9MB 峰值增量=558.1MB
```

**7.8MB 的导出把进程推高到 283MB。** 这不是夸张，是三层成本叠在一起：`all()` 物化 20 万个对象、`csv += line` 每次拼接产生新串、发完之前整个串不能释放。并发 4 个请求就 558MB。注意服务端那行日志的位置——它打在 `res.end()` **之前**，此时 rss 已经到 337.0MB（基线 61.8MB），所以**这 275MB 与客户端无关，纯粹是物化过程自己吃掉的**；峰值增量里属于接收侧的那一小部分是本机测量同进程带来的（服务端与客户端在同一进程内），下面那张对比表读的是量级差，不是精确归因。

改成从库里逐行流出，同一个查询、同一个响应体：

```text
[服务端] stream 逐行流出 行数=200000 首块=2ms 发完前耗时=1440ms 此刻rss=103.8MB
stream   请求数=1 传输=7.8MB 状态=200 Content-Length=null 总耗时=1459ms 起始rss=61.8MB 峰值rss=103.9MB 峰值增量=42.0MB
stream   请求数=4 传输=31.0MB 状态=200 Content-Length=null 总耗时=5384ms 起始rss=61.7MB 峰值rss=194.7MB 峰值增量=133.0MB
```

对比要读三处，不能只读一处：

| 指标 | memory 写法 | stream 写法 | 读法 |
| --- | --- | --- | --- |
| 峰值 rss 增量（单请求） | 283.5MB | 42.0MB | 6.8 倍落差，这才是能不能扛住并发的关键 |
| 首块到达 | 671ms | 2ms | 流式的**第一个字节**几乎立刻出来 |
| 总耗时（单请求） | 744ms | 1459ms | 流式**更慢**：背压 + 分块写入的代价 |
| `Content-Length` | 8128722 | 缺失（分块传输） | 客户端拿不到总长，进度条只能显示已下载字节 |

最后一行是有官方依据的：MDN 对 `Content-Length` 的说明里写着，在 HTTP/1.1 下分块发出的响应可以用 `Transfer-Encoding: chunked` 替代它，因为长度是边算边得到的。所以「要进度百分比」和「要低内存」在导出这件事上是真实的取舍——想要两者都有，就别边查边发：异步生成文件、落对象存储、回一个带长度的地址（[第 13 章](/data-storage/object-storage-and-cdn)的三条上传/下载路径之一）。

## 阶段 ⑧ 收口：三种改造放在同一负载上比

产出：**三臂对比表**，以及一句「这一层到底要不要」的判断。

同一份 1500 次读、同一个 `pickHot` 分布，跑三个臂：

```text
A 未优化的 SQL（列被函数包住，计划是 SCAN）：n=1500 p50=0.8ms p95=1.3ms p99=2.3ms max=9.3ms 总耗时=1293ms DB 往返=1500
B 只改 SQL/加索引（计划是 SEARCH）：n=1500 p50=0.1ms p95=0.1ms p99=0.1ms max=1.9ms 总耗时=93ms DB 往返=1500
C 在 B 之上加 Cache-Aside：n=1500 p50=0.0ms p95=0.1ms p99=0.1ms max=1.9ms 总耗时=46ms DB 往返=621 命中率=58.6%
相对 A 的总耗时下降：B=92.8%  C=96.4%
缓存相对 B 的额外收益：47ms（B 已经是一条 seek 的成本，命中率再高也只是省掉 0.0ms 量级的本地调用）
```

**这张表是本章最有用的东西，因为它把「顺序」量化了**：先改 SQL 与索引拿到 92.8%，再加缓存只再拿 3.6%。如果你的项目按反序做（先上缓存掩盖慢查询），你会得到「缓存一失效就雪崩」的系统，而且永远不知道自己本来可以只加一条索引。

但这条结论有两个必须写进交付说明的边界：

1. **本机 DB 是同进程调用。** 从 1293ms 到 93ms 之后，剩下的 93ms 里每次查询只有 0.06ms，缓存命中省下的就是这 0.06ms——所以额外收益必然是个位数毫秒。生产的库在另一台机器上：一次往返是网络 RTT + 驱动排队 + 服务端解析，命中省下的是整个往返，还要加上「并发时连接池不被占满」这层收益。
2. **真正会带崩系统的是 DB 往返条数，不是本地毫秒。** 同一张表里 C 臂把往返从 1500 降到 621（-59%）。在远端库上，往返数直接连着连接池占用（阶段 ② 的算式里那 12ms 就是它），所以缓存的价值要按「省下多少条往返 × 每条往返的真实成本」算，而不是按本机的 47ms 算。

**上线判据**（把它写成一句话放进你的交付文档）：

```text
值得加这一层：  命中节省成本 × 命中次数 > 一致性残差成本 + 运维成本 + 三防的实现成本
不值得：        慢查询本身没解决、命中率靠猜、写多读少、或者数据规模还不需要
```

首页那条「如果证明不了，说明当前规模还不需要它，这本身也是一个正确结论」，说的就是这张表读出来的结论可以是「不加」。

## 常见翻车点

**1）先上缓存，慢查询照旧。** 现象：缓存命中率很高，但数据库 CPU 仍然被打满，且每隔 N 分钟出现一次尖刺。原因：回源那条 SQL 本身是全表扫，缓存只是把它的出现频率降低了。确认：看阶段 ⑧ 的 C 臂，把 `pickHot` 换成你的真实分布，比对「回源次数 × 单次回源耗时」。修法：把阶段 ③ 提到阶段 ④ 前面——顺序错了，整层的成本结构就错了。

**2）命中率算的是请求数，不是 key 数。** 现象：「命中率 95%」但 DB 查询条数没降多少。原因：分母用了总请求，而热点集中在少数 key 上；或者只统计了读路径的一小段。确认：同时打印 `请求数 / DB 查询数 / 不同 key 数`，三个数一起看。修法：命中率定义写成 `(请求数 - DB 查询数) / 请求数`，与本章 B3 同一口径。

**3）空值缓存把真实体也挡掉了。** 现象：数据刚创建好，接口仍返回「不存在」，直到很久之后才恢复。原因：空值 TTL 太长。确认：查那条 key 的剩余时间（Redis 上是 `PTTL`）。修法：空值 TTL 显著短于正常值（本章用 30s vs 5s～9s 的打散窗口），并且创建成功后主动删掉对应的空值 key。

**4）single-flight 的等待者永久挂起。** 现象：一批请求既不返回成功也不返回错误，超时才醒。原因：回源那次查询抛异常，但合并的 Promise 没有被 reject 广播出去。确认：把回源故意改成抛错，看等待者是否也拿到错误。修法：`try/finally` 里清掉 inflight 记录，并让失败也 resolve 成同一个 rejected Promise；记住「失败不写缓存」，否则一次抖动会被缓存五分钟。

**5）幂等键由客户端随机生成，每次都不一样。** 现象：加了幂等表，重复提交仍然产生两条业务数据。原因：键取的是请求体哈希（内容里带了时间戳），或每次重试都重新 `uuid()`。确认：把两次提交的 `k` 打出来比对。修法：幂等键必须表达「**这次业务动作**」而不是「这次 HTTP 请求」——用订单号、用用户动作 ID，由发起方在重试间保持不变；服务端只负责把它撞在 UNIQUE 上。

**6）限流阈值拍脑袋。** 现象：上线后正常用户被 429，压测却一切正常。原因：桶按压测 QPS 设的，没算真实突发（用户连点、前端重试风暴）。确认：分位数看真实分布，而不是平均值。修法：`capacity` 按可容忍突发定、`rate` 按后端能扛的长期吞吐定，且**只对写接口生效**；两个数都要能说出来源，像阶段 ② 的连接池那样。

**7）导出接口把内存问题伪装成缓存问题。** 现象：加缓存后偶发 OOM，怀疑缓存没淘汰。原因：导出用了全量物化，一个请求 283MB（阶段 ⑦ 的实测）。确认：翻 OOM 前那条请求日志的 path，看它是不是导出。修法：流式写出 + 有上限的行数 + 大文件走「异步生成、落对象存储、回地址」。别用「把缓存关掉」来验证你的内存假设，那是两个变量一起动。

回应「必须上 Redis」时，别讲道理，给三个数：

1. **DB 往返条数**：改造前后各多少条（本章是 1500 → 621，你的分布会给出你的数）；
2. **一条往返的真实成本**：在**你的**库上测，含网络与连接排队，不是本机的 0.06ms；
3. **一致性残差的代价**：写后到读之间的最长不一致窗口是多少毫秒，你能不能接受，以及你的产品里哪些路径不能接受。

三个数都拿到，「上不上」就是一个算式而不是一个立场。拿不到第 2 个数（没在真实往返上测过）的时候，诚实的结论是[首页](/data-storage/)那句：当前规模还不需要它，本身也是正确结论。

</template>

</Exercise>

## 参考答案要点

<Exercise title="参考答案要点 · 把进程内替身换成 Redis 要改哪些地方" difficulty="进阶">

本章所有数字都来自一个进程内的 `Map` 缓存替身。写出把它换成 Redis 的最小改造清单，并说明哪些结论在换完之后**必须重测**、为什么。

<template #answer>

改造面只有四处，但每一处都会改变数字的量级：

1. **数据结构选型**：读路径的值是一段行数组，`String` 存 JSON 就够；如果只想失效某一行、或要给列表加字段，才用 `Hash`。选型判据在[第 2 章](/data-storage/redis-data-structures)，别为了「像生产」而用复杂结构。
2. **两个原子动作要落到服务端**：`single-flight` 从「本进程共享一个 Promise」变成「跨进程也要只回源一次」，靠的是 Redis 上的一个 `SET ... NX PX` 标记；空值缓存与 TTL 打散变成写 `EX`/`PX` 时带上随机项。这两处的**命令参数与返回值语义本章未在本机验证过**，一律按[命令参考](https://redis.io/docs/latest/commands/)核对。
3. **序列化与体积**：替身里存的是 JS 对象，Redis 里存的是字节。`LIMIT 20` 的行数组很小，但导出或大字段会瞬间让你为序列化付钱，还会顶到 `maxmemory`（[第 4 章](/data-storage/expiry-and-eviction)）。
4. **失败路径**：Redis 连不上时读路径必须能直接走库（降级），而不是 500。替身没有这个分支，加上它之后要故意 kill 掉 Redis 验一次。

换完必须重测的三项：**命中率**（key 分布不变，但 TTL 精度与淘汰策略会变）、**命中延迟**（本机 0.0ms 的 Map 查找变成本地回环的网络往返，量级跳一到两个数量级，你的分位数表形状会完全不同）、**回源条数**（跨进程 single-flight 生效后才是真的合并）。最容易被忽略的是第二项：**「缓存命中」在你的架构里从来不是零成本，它是用一次网络往返换掉一次数据库往返**——只有当数据库那条更贵（慢查询、连接池排队）时，这笔交换才划算。

</template>

</Exercise>

<Exercise title="参考答案要点 · 怎么证明限流器真的保护了那个写接口" difficulty="基础">

给出一个能在本机跑出来的判定脚本骨架（伪码即可），要求结论是一句「放行 X、拒绝 Y」，并且要能证明被拒的请求没有落库。

<template #answer>

要点是**把「被拒」和「没落库」两件事分别断言**，只断言其一都会被反驳：

```text
1. 建一张只写不读的观测表：每次业务写入前，先记一条 attempt 日志（带幂等键）
2. 瞬间发 200 个请求（不要 await 串起来，要 Promise.all 打并发）
3. 断言 A：状态码分布 = {200: 放行数, 429: 拒绝数}，放行数 == capacity
4. 断言 B：SELECT count(*) FROM idem  == 放行数（拒绝的没进幂等表）
5. 断言 C：过了 rate 的时间窗后再发一轮，放行数跟着 rate 走，不是 capacity
6. 打印三行数字，不接受「看起来是对的」
```

本章 B7 只跑了断言 A 的那一半（放行 10 / 拒绝 190），B、C 两条要你在自己的接口上补——尤其是 B：**限流器如果把请求吞在中间件里而没有短路，业务函数照样跑了一次**，这是「加了限流但仍重复扣款」的经典成因。第三条（rate 与 capacity 分开验）防止你把「桶容量」当成「每秒速率」配错单位：`capacity=10` 只保证瞬时突发不超 10，`rate=5/s` 才决定长期能通过多少。

</template>

</Exercise>

<Exercise title="参考答案要点 · 这一层的上线与回滚开关怎么写" difficulty="进阶">

缓存、限流、幂等三层能力都上线了。给出一个「能一键退回不加这层的状态」的实现要点，并说明为什么回滚开关本身也要被测试过。

<template #answer>

三条：

1. **开关在入口，不在各处 if。** 一个 `FLAGS` 配置对象（`cache` / `rateLimit` / `idempotency` 三个布尔），读路径与写路径各自在入口决定走哪条分支。散落各处的判断会出现「缓存关了但 single-flight 还在等一个永不写入的 key」这种组合状态。
2. **关闭路径也要能测。** 把 `cache=false` 跑一遍阶段 ⑧ 的 B 臂，确认它就是 B 臂的数字（回源条数回到 1500、总耗时接近 93ms）；这一步的意义是**证明开关真的把那一层摘掉了**，而不是只让代码少跑了一段。你从没执行过的分支，不能假定它正确。
3. **回滚有状态残留。** 关缓存后 Redis 里那些 key 还在（靠 TTL 自己走），关幂等后 `idem` 表里的旧键还会挡住重放——所以幂等表要有清理任务，且**开关改变的是「读不读」而不是「数据在不在」**。

回滚开关本身必须测的原因很直：故障时你只有几分钟，那时没人会去读代码确认「关掉 cache 到底影响哪些分支」。判据只有一条——**在生产上开过一次、也关过一次**，并且两次都有数字落进日志。只在预发验证过的开关，等于没有开关。

</template>

</Exercise>
