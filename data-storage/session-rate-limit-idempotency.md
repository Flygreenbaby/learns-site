# 分布式会话、限流与幂等：机器一翻倍，进程内状态就变成三份互不相认的私有账

服务从 1 台加到 2 台，CPU 曲线立刻好看，一小时后客服开始转来「反复要求登录」的反馈。它的三个特征很容易被误判成别的问题：只有一部分用户受影响；停掉其中一台反而正常；两台同时重启（版本一致）也正常。真正的原因是新实例的进程内存里没有那半张会话表——它从来不知道的 token，会被判定成未登录。

第二个现场：接口限流明明配的 10 次/秒，压测脚本照样在某个 1 秒里打进 19 个成功请求；反过来也有限流上线后同事集体被误伤的事故。前者是算法在时间边界上的固有放大，后者是限流键选错了维度。这两个错误都不会在日志里自称是 bug——按代码写的逻辑，它们都「正确执行」了。

第三个现场最贵：用户点提交，前端转圈超时，他又点一次；网关自己也重试了一次。于是两张订单、两次扣款。日志里两条记录相差三秒，`user_id` 和参数完全一致。这不是并发撞车的巧合——超时重试是网络请求的正常结局，它早晚会发生，所以你要么让重复请求无害，要么就等着它发生。

这三件事共用同一个隐含假设：**进程内存里的东西就是全局状态**，以及**一次请求 = 一次执行**。本章把这两个假设拆开，脚本在同目录 `.scratch/ds-ratelimit-idem.mjs`，下面每一张表都是它打印出来的原文。

## 会话在扩容后丢失，是因为登录态被写进了「每台一份」的地方

先看实测的对照数字，负载模型是两台实例、6 次登录、60 次带 token 的请求，请求按无粘性轮询派发，并且刻意让同一用户的新请求落到另一台（`target = (u + 轮次) % 2`）：

```text
=== C. 多实例会话：进程内存态 vs 共享存储（真库计数）===
每台各存自己内存：{"需要重新登录":30,"总请求":60,"SQL条数":0}
共享存储（会话表）：{"需要重新登录":0,"总请求":60,"SQL条数":66}
```

`30/60` 就是 50%，来源很直白：登录只写进了一台实例的 `Map`，请求被派到另一台时查不到。**但「一半」不是常数**，这才是它难查的原因。N 台实例、无粘性轮询时，命中概率约 `1/N`；实例数一变，比例就变；发布期间新旧实例并存，比例随流量在两个值之间漂移。所以用户体感是「时好时坏」，而不是「一直坏」。日志里也不会有错误——查不到会话是合法分支，返回 401 是完全正确的行为。

`0/60` 那一行的代价写在同一行里：`SQL条数=66`（6 次登录写 + 60 次请求读）。共享存储不是免费的，它把每个请求变成一次网络往返；当有人说「加个 Redis 放会话就好了」，你要能立刻报出这笔账——命中率换成了每请求一次调用，然后才开始谈能不能接受。

### 「用 ip_hash 把用户粘在原实例上」为什么不成立

nginx 对 `ip_hash` 的承诺是明确的（官方文档原文，已核实）：

> The method ensures that requests from the same client will always be passed to the same server except when this server is unavailable.

以及一条容易漏掉的操作约束：

> If one of the servers needs to be temporarily removed, it should be marked with the `down` parameter in order to preserve the current hashing of client IP addresses.

两句引述恰好判死这个方案：`except when this server is unavailable` 说故障或下线时映射必然改变；`to preserve the current hashing` 反过来说明**不加 `down` 就直接摘服务器会重排全部映射**，而弹性伸缩与滚动发布恰恰就是这么干的。再叠上客户端 IP 本身不稳定（移动网络换出口、公司 NAT 后几百人共用一个 IP），ip_hash 只能降低发生率，不能作为正确性手段；同一页还写明 `sticky` cookie 与 `ip_hash` 是互斥的分发策略，不能拿 sticky 去补它。结论只有一句：**要么登录态不在进程里，要么就接受随机掉线**。

## 登录态的三种落点：能立刻注销与不依赖中心存储不可兼得

| 落点 | 状态存在哪 | 每请求代价 | 能否立刻注销 | 进程重启后 | 典型翻车 |
| --- | --- | --- | --- | --- | --- |
| 进程内存 Map | 单机 | 0 | 能 | 全丢 | 扩容/发布即掉线（上面 30/60 就是它） |
| 服务端会话（Redis 或库里的会话表） | 中心 | 一次读 | 能，删键即生效 | 不丢 | 会话实例被 `allkeys-lru` 淘汰 → 又变成随机掉线 |
| 自包含 token（JWT 一类） | 客户端 | 0（验签） | **不能**，只能等过期 | 不丢 | 把敏感信息放进 payload；过期设 7 天且无吊销列表 |

第三条常被当成「免存储的正确答案」，它免掉的其实只有中心读，代价是把注销能力换成「等自然过期」——要做的是**明说这笔交换**，而不是以为两个好处都能拿到。

服务端会话通常就是一个带 TTL 的 hash（键 `session:<token>`，字段记 `userId / role / loginAt`，吊销即 `DEL`；自包含 token 要兜底就另配一个短命的 `revoked:<jti>`），但它有两个必须处理的细节。一是**每请求续期 = 每请求一次写**，量大时这里的写压力会先于容量成为瓶颈，所以通行做法是条件续期（`PTTL` 余量低于阈值才写），把续期频率压到每分钟级。二是**空闲超时与绝对寿命是两条独立规则**：只实现「空闲 30 分钟失效」，一个被盗用的 token 可以永远续下去，所以还要有「无论多活跃 12 小时后必须重登」。同理，签名密钥泄露时自包含 token 召不回来，要能吊销就得维护吊销列表——它本身又是一份中心状态，等于绕回第二种方案的一半。

## 限流算法的差别不在聪明程度，在你愿意为精度存多少状态、允许多大突发

```text
=== A. 限流算法对照（限速 10/s，负载 105 请求：基线 8/s + 第 5 秒跨边界突发 25）===
算法                      通过     拒绝     任意1s内通过峰值        任意200ms内峰值       状态量(每键)
固定窗口计数              84       21       19                    13                    10
滑动窗口日志              82       23       10                    4                     8
滑动窗口计数(加权近似)        67       38       10                    4                     20
令牌桶(cap=10)         89       16       18                    11                    2
GCRA(突发=10)         89       16       18                    11                    1
```

逐列读，别只看「通过」那一列。

**「任意 1s 内通过峰值」才是下游真正感受到的速率。**固定窗口的限速是 10/s，实测峰值 19——接近两倍。机制没有玄学：突发跨在 5.000s 边界上，`4900..4999` 落进窗口 4，`5000..5092` 落进窗口 5，两个窗口各自都没超过 10，于是全部放行。写这个代码的人没有犯错，他实现的就是「每整秒最多 10 次」。

它有一个可推导的上界：最坏情况是上一窗口末尾用满额度、这一窗口开头再用满，`瞬时通过 ≤ 2 × LIMIT`。实测 19 没超过 20，与推导一致。**这条上界本身就是体检项**：压测出的瞬时峰值若超过 2 倍限额，那不是算法特性，是实现有 bug（窗口键算错、或每个实例各有一份计数）。

**滑动窗口日志**把每个请求的时间戳存进队列，判定写成「现在 - 队列头 小于 1000」，所以任意 1 秒窗口内恰好 10 次。代价在状态量的**增长方式**：队列按请求数增长，限速越高、突发越久，单键状态越大（脚本那次突发 25 个被 10 的额度截住，`mem` 报的是队列峰值长度 8）。

**加权近似**用「上一窗口总数 × 本窗口已过时间比例 + 本窗口已计数」估计滑窗，状态只要两个计数器——但 `mem` 报 20，因为**每键两个 × 10 个窗口**都留在表里，这正是它最常见的浪费：历史窗口不清理。它的实测结果最值得警惕：峰值同样精确到 10，通过率却只有 67/105，比日志法多拒 15 个。**同一条限速规则，近似版比精确版凶 18%**，因为折算假设上一窗口的请求均匀到达，而真实突发完全不均匀——用户看到的是「没到额度就被限」。

**令牌桶与 GCRA**给出完全相同的曲线（89 / 16 / 18 / 11），在本脚本参数下（桶容量 = 突发额度 = 限速 = 10，补充 10/s；GCRA 的 emission 100ms、burst 10）两者是同一约束的两种表述，差别只在存储：桶要记令牌数与上次补充时刻（`mem` 2），GCRA 只记一个理论通过时刻（`mem` 1）。脚本里的 GCRA 是单键虚拟调度的自实现写法，只体现核心思想，参数含义以你选用的库为准。它们那 18 次峰值是**设计意图而非缺陷**：桶攒下的令牌允许突发。于是「该选哪个」变成能说清的问题——你要保护**下游平均速率**（允许突发，选桶类），还是**任意瞬间不得超限**（选日志类），把答案写进评审记录比争论算法名字有用。

## 计数器一搬到共享存储，就要同时处理原子性、TTL 和键维度

单机内存计数器在多实例下天然是 N 份独立额度：每台限 10/s，两台就是 20/s。把它搬到 Redis 才有全局语义，但接着遇到两个新问题。

第一个是竞态。朴素写法有四步：读计数、判断是否超限、`INCR`、首次时 `EXPIRE`。前两步之间完全没有互斥，两个并发请求都读到 9，都判定「还能过」，实际放行 11；`INCR` 成功但那次 `EXPIRE` 因为异常没跟上，键就**永不过期**——这正好是 [过期与淘汰](/data-storage/expiry-and-eviction) 里那条「漏设 TTL 的键永生」的成因，只不过这次是限流键在批量制造它。

通行解法是把这几步合成一个服务端原子操作。以下是**未在本机执行**的示意（`EVAL` 与 Lua 脚本在现代版本里的推荐替代方案，动手前核对官方脚本文档）：

```text
# 预期语义，非实测：一次往返内完成「计数 + 首次设置过期」
EVAL "local n = redis.call('INCR', KEYS[1])
      if n == 1 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end
      return n" 1 rate:u42:POST:/api/orders 1000
```

即使不用脚本，也有「一条命令搞定窗口」的做法：把窗口编号写进键名，只依赖计数器自带的过期语义。要点不在挑哪一种，而在**过期与计数必须在同一个服务端步骤里落定**，否则故障形态就变成内存持续上涨而不是限流不准。集群部署下还有一条：同一次判定涉及的键要用 hash tag 落到同一分片，否则跨节点谈不上原子。

第二个是键的维度。三层缺一不可：

```text
全局层    rate:global:<route>        保护下游与数据库连接池，阈值 = 容量压测结果
主体层    rate:uid:<userId>:<route>  公平性与抗刷，阈值 = 单用户合理上限
敏感层    rate:uid:<userId>:<action> 登录、发码、下单，阈值最低、拒绝码最明确
```

只配主体层，一个共享出口 IP 后面的所有人合计起来照样打爆下游；只配全局层，一个慢接口吃光全站额度。MDN 对 429 的描述正好点出这件事（已核实原文）：限制「可能是服务范围的，也可能是针对具体资源的」，且「通常基于客户端 IP，但如果请求已认证或带 cookie，也可以是特定用户或授权应用」。以 IP 为唯一维度就是那句话里的「通常」，而它在公司 NAT、校园网、运营商大内网下会一次误伤一整栋楼——判断依据很简单：**被限流的 distinct IP 数远小于被拒请求数时，几乎一定是键选错了**。

## 被拒绝也是接口契约的一部分

限流拒绝的响应必须自带「什么时候再来」。MDN 的原文（已核实，页面例子写作 `Retry-After: 3600`）：

> A Retry-After header may be included to this response to indicate how long a client should wait before making the request again.

三个细节决定它能否真救你：`Retry-After` 用整数秒而不是毫秒；客户端必须**指数退避 + 抖动**，固定间隔会让所有被限流的客户端在同一时刻齐刷刷回来，把系统打成震荡；429 不要与 5xx 混用同一个错误码，否则正常限流会污染「服务错误率」，真故障被掩盖。最后一条最便宜也最常被违反：被限流时**不要**执行任何业务写——先落一条「待处理」订单再返回 429，客户端重试就留下一堆僵尸记录。

## 幂等：一次「用户意图」在库里只应该留下一个结果

```text
=== B. 幂等键：真库 node:sqlite 对照（同一请求重放 3 次）===
无唯一索引（只靠应用层先查后插）：最终行数=3
   #1 新建
   #2 新建
   #3 新建
有 UNIQUE(user_id, idem_key)：最终行数=1
   #1 新建
   #2 重放返回已有 id=010bd0f9 payload一致=true
   #3 重放返回已有 id=010bd0f9 payload一致=false
```

先把这一组的语义说准，别让结论超出它证明的范围。**三次请求是串行发出的**，所以这里没有并发竞态参与：无索引那一行演示的是「库里没有任何唯一约束时，重放的下界就是三行」；有索引那一行演示的是「唯一约束 + 命中即返回」能把行数钉在 1。并发下的「先查后插」为什么照样双写，那是 TOCTOU，需要你真正并发才能观察——本章不声称演示过它，练习 2 会让你自己做出来。

真正值钱的是最后一行：`payload一致=false`。第三次请求带的是同一个幂等键 `K-1`，但请求体变成了 `{"title":"CHANGED"}`。唯一约束保证了库里只有一行，**它不保证这一行是你这次想要的内容**。如果你的代码只查键、命中就返回已有结果，用户会收到一个成功响应，而实际执行的是他第一次提交的内容。所以幂等实现必须是两件事：唯一约束防重，请求体摘要比对防「同键不同体」，后者不一致时明确拒绝（409/422 一类），而不是假装完成。

幂等键的四个设计决定，每一个都有对应的翻车形态：

**谁生成。**由客户端（或网关）在「一次用户意图」开始时生成一次，重试复用同一个。服务端不能凭请求体哈希推导：用户改了地址再下一单，哈希变了，于是系统认为这是新意图——但如果用户是「点了提交没反应、又点一次且内容没变」，哈希相同反而挡住了正常的第二次尝试。UUID 适合「动作即意图」（下单、扣款），内容哈希适合「内容即意图」（整体覆盖式保存）。

**作用域。**实测就是 `UNIQUE(user_id, idem_key)`。建成全局唯一会出两类问题：A 用户猜到一个键就能让 B 用户的请求被当成重放丢弃（越权 + 拒绝服务）；跨租户复用序号时误伤。唯一索引列必须是「谁 + 哪个动作」。

**保留期。**至少覆盖最长的重试链路：客户端超时 + 网关重试 + 消息重投 + 人工兜底，通常是分钟到天级。到期之后的重放会被当成新单，这是设计的必然结果，不是 bug——但很多人不知道，所以要写在接口文档里。

**存哪。**首选与业务记录同库同事务，实测就是这个形态：那张 `jobs` 表的一行**既是业务记录又是幂等记录**，插入成功与业务成功是同一个原子事实，不存在「扣款成功但幂等记录没写」的缝隙。

```sql
-- 实测用到的表结构（node:sqlite，内存库）
CREATE TABLE jobs (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL,
  payload    TEXT NOT NULL,
  idem_key   TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX ux_idem ON jobs(user_id, idem_key);
```

把幂等记录放到独立缓存（`SETNX` 那类）要清楚自己在赌什么：缓存重启或被淘汰，键就消失，重放立刻变成第二笔。这不是理论风险，它就是 `allkeys-*` 策略下会发生的事，取舍逻辑与 [过期与淘汰](/data-storage/expiry-and-eviction) 里「会话与幂等键该放哪个实例」完全一致。

还有一个常被忽略的返回语义问题：命中重放时，你是返回「库里那一行的现状」，还是返回「首次执行时的响应」？两者在优惠、库存、状态机场景下不同。若业务要求重放得到与首次完全相同的响应，就必须把首次响应体一并存下来；只存 id 的实现做不到这一点。

## 把「进程内有我」当成一条 bug 来搜

上面三节的病根是同一个。检查动作很机械：把可疑写法捞出来（`grep -rn --include='*.ts' -e 'new Map(' -e 'globalThis' -e 'setInterval' src/`），逐条问「如果这个进程复制一份会怎样」——进程内会话表变随机掉线，限流桶变「集群实际额度 = 单台额度 × 实例数」，幂等表变重启后重放全成新单，`setInterval` 里的定时任务变每台跑一遍、N 倍重复发送，进程内文件写变「落到哪台决定文件在哪」，本地缓存变「每台一个 TTL 且互不知情」（这条要连着读 [缓存一致性](/data-storage/cache-consistency)）。验证不需要监控平台：**同一份流量并排打两台实例，看结果是不是恰好两倍**，两个进程就够了。

## 常见错误与排查

**部分用户随机掉线，或发布之后集中掉线；停掉其中一台反而正常。** 原因：登录态在进程内存，实例数决定命中比例；发布时新实例没有旧会话，或 upstream 摘除没标 `down` 导致映射整体重排。怎么确认：分别统计两台实例的鉴权失败率（失败集中在一台），或拿同一个 token 各打两台一次，一边 200 一边 401；再把掉线时间点与实例启动时间对齐。怎么修：会话外置。临时把流量收敛到一台只是止血，下一次扩容就复发。

**限流阈值 10/s，压测某个 1 秒里过了 19 次。** 原因：固定窗口的边界放大，实测就是这个数。怎么确认：把请求按小于窗口长度打满并**跨边界**（本脚本的突发刻意压在 4.900–5.092s），统计任意 1s 与任意 200ms 的通过峰值，而不是只看总通过数。怎么修：改滑动日志（硬上限语义）或令牌桶（允许突发，并写明允许多大）；若峰值超过 2 倍限额，先怀疑实现而不是算法。

**限流上线后整个公司的同事一起被拒。** 原因：键选成 IP，而出口是 NAT。怎么确认：聚合被拒请求的 distinct IP 数与总请求数，一个 IP 承担成百上千次即可疑；或看被拒 IP 是否落在同一段。怎么修：主体维度做默认层，IP 只作辅助信号并放宽阈值。给内部网段开白名单前，先确认转发层会清掉客户端自带的 `X-Forwarded-For`，否则这个白名单是可以伪造的。

**Redis 内存缓慢上涨，`SCAN` 出来一堆限流键的 TTL 是 -1。** 原因：`INCR` 成功而 `EXPIRE` 因异常没跟上；或只在「首次创建」时设 TTL，而那次判断错了。怎么确认：对可疑键读 `PTTL`（预期 `-1` 表示永不过期），比对键名里的窗口编号是否还在增长。怎么修：把计数与过期合成一个服务端原子步骤、统一兜底 TTL，并按 [过期与淘汰](/data-storage/expiry-and-eviction) 给这类键选对 `maxmemory-policy`。

**幂等表里同一个键出现了两行，或重放返回 200 但业务按旧内容执行了。** 前者原因：只有「先查后插」、没有唯一索引，并发下两次读都为空；后者原因：只比键不比请求体（见实测的 `payload一致=false`）。怎么确认：查索引是否存在（`PRAGMA index_list('jobs')`，PostgreSQL 用 `\d jobs`），再用 20 个并发同键请求压一次看行数，并主动构造一次同键不同体。怎么修：加复合唯一索引、把插入冲突实现成正常分支（捕获 → 读已有行返回）、摘要不一致时返回 409 而不是 200。反向错误也要防：索引建在单列 `idem_key` 上会让不同用户互相顶掉，表现为随机「订单号重复」。

**429 之后系统更卡了。** 原因：客户端固定间隔重试，被限流的一批在同一时刻齐刷刷回来。怎么确认：把服务端收到的请求时间按 10ms 分桶，看是否呈与退避间隔同周期的尖峰。怎么修：服务端必须回 `Retry-After`，客户端退避加抖动——这与下一章锁等待者「同一时刻一起抢」是同一个病，可以对照阅读。

<Exercise title="练习 1 · 复算限流表的每一格" difficulty="基础">

A 组负载是 8 次/秒基线加 25 次跨边界突发，合计 105 个请求，限速 10 次/秒。固定窗口通过 84、拒绝 21。请推算：基线部分被拒了多少、突发部分被拒了多少，以及为什么「任意 1 秒峰值」是 19 而不是 20。再解释滑动窗口计数（加权近似）为什么同样精确却多拒了 15 个请求。

<template #answer>

10 秒窗口、限速 10，固定窗口最多放行 100 个，实测 84，缺口全部来自突发。基线 8/s 在每个整秒窗口内都是 8 个，低于 10，80 个全过；突发被 5.000s 边界劈开，窗口 4 里剩余额度只有 2，窗口 5 里 8 个基线加突发后半段共 16 个可用——于是 25 个突发被拒约 21 个。峰值 19 而不是 20：20 是「上一窗口末尾用满 + 本窗口开头用满」的理论上界，本负载的基线占掉了开头几个名额，凑不满最坏值。加权近似把上一窗口的 8 个按剩余时间比例折算成已用额度，突发落在窗口靠后位置时被扣的估计值仍偏高，于是拒掉了一些本可放行的请求——**近似算法的偏差方向不是随机的，是偏严**，这是它最常见的线上投诉来源。

</template>

</Exercise>

<template #answer>

判分点是**你有没有真的跑并把报错原文贴出来**，而不是给出符合直觉的答案。典型结果：(1) 最终 1 行，其余请求在同一条唯一约束上失败，报错形如 `UNIQUE constraint failed: jobs.user_id, jobs.idem_key`（Postgres 是 `duplicate key value violates unique constraint "ux_idem"`，Detail 里带已有键值）。(2) 无索引 + 先查后插：多数实现得到 2 到 20 行，取决于并发交错——两次读都为空是合法的，因为读之间没有互斥，这就是 TOCTOU；它说明「应用层判重」在没有唯一索引时不构成任何保证。(3) 必须当正常分支：约束冲突正是「这次执行已经在别处成功了」的信号，统一映射成 500 会让客户端重试、让监控错误率与真实故障混在一起，而库里其实一行不多。(4) 正确做法是捕获约束错误 → 按 `(user_id, idem_key)` 读那一行 → 比对请求体摘要 → 一致则返回首次结果，不一致则 409。抛给客户端的表现是「用户点了两次提交，第二次报错，于是不确定有没有下单」，那正是幂等要消灭的焦虑。

</template>

</Exercise>

<template #answer>

限流三层：`rate:uid:<userId>:POST:/orders` 主体公平层，阈值来自「一个正常人 1 分钟内可能提交几单」加上客服工单里的历史分布，通常远低于下游容量；`rate:global:POST:/orders` 保护下游，阈值来自该接口压测出的安全 QPS 除以实例数再留余量；IP/设备维度只作辅助信号，阈值宽、命中时加验证而不是直接拒。三层都回 429 加 `Retry-After`，但主体层的文案要区分「你太快了」与「活动刚开始」——语义相同、措辞不同。幂等键：客户端在点击提交那一刻生成 UUID，作用域 `UNIQUE(user_id, idem_key)`，保留期覆盖最长重试链路并写进接口文档，存储与订单同库同事务，就是本章实测那张表的形态：一行既是订单又是幂等记录。为什么不能互相替代：限流按「速率」判断，挡不住相隔 3 秒的两次点击；幂等按「是否同一意图」判断，挡不住每秒 50 次的不同意图刷单（每换一个键就绕过）。一个管量，一个管重复，缺一层就是另一个漏洞。

</template>

## 官方文档与延伸阅读

[MDN：429 Too Many Requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/429) —— 用于核实本章两条结论：429 的语义是「单位时间内请求过多、要求放慢速率」，以及限流「可以是服务范围或针对具体资源」「通常基于 IP，认证后可基于用户或应用」；同页给出 `Retry-After: 3600` 的例子与「该响应可带 Retry-After 头告知客户端等多久」。注意该页近期从 `Web/HTTP/Status/429` 迁到 `Web/HTTP/Reference/Status/429`，深层路径不可靠，请以站内检索为准。

[nginx：http upstream 模块](https://nginx.org/en/docs/http/ngx_http_upstream_module.html) —— 用于核实 `ip_hash` 的承诺原文（同一客户端总是到同一台，除非该服务器不可用）与「临时摘除服务器要标 `down` 才能保持现有哈希」，这两条共同支撑「粘性会话不能作为正确性手段」。同页 `hash` / `least_conn` / `sticky` 的适用范围一并核对。

[Redis 文档主入口](https://redis.io/docs/) 与 [命令参考](https://redis.io/docs/latest/commands/) —— 用于核实 `INCR`、`PEXPIRE`、`PTTL`、`SET ... NX EX` 的参数与返回值，以及 `EVAL` 的现代替代写法。本章未在本机执行任何 Redis 命令；我尝试抓取 Lua 脚本文档的深层路径时得到 404，所以只留主入口。

[Node.js 官方文档](https://nodejs.org/api/) —— 用于核实 `node:sqlite` 的 `DatabaseSync` 属实验特性（运行时打印 ExperimentalWarning）；本章 B、C 两组真库数字来自本机 Node v25.4.0。
