# 性能指标与 Core Web Vitals：数字好看而体验仍差，中间漏掉了什么

你跑了一次 Lighthouse，移动端 96 分，绿色的。你把截图发到群里，然后同一周有两个人说「这站卡」。你不确定他们在矫情还是自己在骗自己，因为你没有证据——只有一个分数和一堆「预计可节省 0.4 秒」的建议。这是第一种错位：**实验室分数是你在自己机器上、用一种人为设定的节流条件跑出来的一个数，而用户的卡发生在他的中端安卓机、4G、后台挂着二十个标签页的时候。**

第二种错位更具体。你把 LCP 从 4.2 秒优化到 2.1 秒，手段是给首屏那张大图加 `loading="lazy"`。首屏截图刷新了，指标变绿了。然后你发现真实用户的首屏**白屏时间变长了**——因为你把 LCP 候选元素本身变成了「等它滚动到视口附近才下载」的资源，浏览器要先建好布局、判断它在不在视口内，才开始请求它。**你优化掉的不是加载时间，是「什么时候开始加载」这个问题。**

第三种：你为了把 TBT 压好看，把一个 300 毫秒的大任务切成六十个 5 毫秒的小任务，中间用 `setTimeout` 隔开。TBT 归零（因为 TBT 只统计超过 50 毫秒的部分），Lighthouse 里那个红色长任务不见了。但用户的点击变得更难受了——六十个任务照样把主线程排满，每次输入还是要排队等在前面那个任务后面。**长任务的「长度」消失了，长任务的「总量」一丁点没少，而 INP 看的是总量。**

第四种最容易被忽略：你写了二十个 `transition` 让交互「有反馈感」，其中一个用 `width` 做动画。Lighthouse 不会告诉你这件事，因为实验室里没有连续交互；但 CLS 会，因为 `width` 变化的元素把下面的内容一路往下推，每次偏移都被计入。

这四种错位有一个共同根源：**指标是体验的一个投影，不是体验本身。** 你需要的能力是两件事——① 知道每个指标到底在测哪个物理过程，这样「这个数字变好了」才能翻译成「用户那边少了哪一段等待」；② 给自己定一条能被机器判定的预算，这样「够不够快」不再取决于谁的情绪。下面按这个顺序来。

## 三个核心指标各自测什么：一张对照表

Core Web Vitals 是 Google 定义的一组以**真实用户数据**衡量页面体验的指标，当前三项是 LCP、INP、CLS，各自对应体验的一个维度（加载、响应、视觉稳定）。

| 指标 | 英文原名 | 测哪个物理过程 | 单位 | 检索到的一致阈值 |
| --- | --- | --- | --- | --- |
| LCP | Largest Contentful Paint | 从导航开始，到视口内**最大那块内容**首次绘制完成 | 秒 | 良好 ≤ 2.5s，需改进 ≤ 4s |
| INP | Interaction to Next Paint | 整次访问里，**响应最差的一次**「用户操作 → 界面画出新状态」的耗时 | 毫秒 | 良好 ≤ 200ms，需改进 ≤ 500ms |
| CLS | Cumulative Layout Shift | 整次访问里**意外布局偏移**的累计分值 | 无量纲分值 | 良好 ≤ 0.1，需改进 ≤ 0.25 |

三点必须在读这张表时就建立的认知：

**一、它们的取值对象各不相同，且都不「完整」。** LCP 只关心一个元素（最大的那个），FCP/TTI 之类不在核心三项里；CLS 只统计**意外**的偏移（用户点击后你主动展开的面板不计入，前提是偏移与交互在时间上足够接近且被判定为用户意图所致）；INP 只报最差的那次交互（准确说是接近最差的统计量），所以一个页面上只要有一个按钮是卡的，INP 就是卡的——**这项指标不能靠「大部分交互还行」刷分**。

**二、它们都要求「视口内 / 用户可见」。** 视口外的图片、`display: none` 的元素、被 `overflow: hidden` 裁掉的内容，都不参与 LCP 的候选。这直接影响你的优化对象选择：首屏那张不在 HTML 里、靠 JS 插入的图，才是真正的 LCP 元素，而不是 hero 区的标题文字。

**三、阈值会随定义演进，别背数字。** 本站给出的这组阈值来自 2026-10-17 检索到的多处一致表述。

## 为什么 FID 被 INP 取代：首次交互不足以描述响应性

FID（First Input Delay）测的是「页面加载期间，用户**第一次**尝试交互（点击、按键）到浏览器能够开始处理该事件之间的延迟」。它被 INP 替代（检索到的一致说法是 2024 年 3 月），原因很实在：

| | FID | INP |
| --- | --- | --- |
| 覆盖的交互范围 | 只测**首次**一次 | 整次访问的**所有**交互 |
| 测的时间段 | 加载期间（首次交互往往发生在还没稳定可交互时） | 加载后全程，包括用户真正在用的那几分钟 |
| 结束点 | 事件处理**开始**（handler 被调用） | 界面**画出新状态**（下一帧绘制完成） |
| 漏掉了什么 | 处理耗时、渲染耗时；也漏掉加载完成后的一切卡顿 | 几乎不漏——但代价是必须真的有人交互才有值 |

FID 有个致命的结构性缺陷：**它测的是「开始处理」而不是「看到结果」。** 一个 handler 可以在 8 毫秒内被调用（FID 漂亮），然后同步跑 400 毫秒再让画面更新——用户等到的是半秒空白，FID 完全不知道。INP 把终点挪到了绘制，于是必须把处理耗时和渲染耗时都算进去，这才是用户实际感受到的那段时间。

同时 INP 也不是「最慢那一次交互的裸值」，它取的是一个接近最差的统计量（交互很少的访问取最大值，交互很多时取高分位数）。**结论层面你只需要记住一句：一个交互卡的地方就足以让 INP 变红。**

## INP 的三段构成：卡在哪一段，修法完全不同

一次交互的总延迟被官方拆成三段，你在 Performance 面板录制里能直接看到这三段各自占多少。

| 段 | 英文 | 是什么 | 典型病因 | 对应修法 |
| --- | --- | --- | --- | --- |
| 输入延迟 | input delay | 事件已发生，但主线程正忙，handler 还没被调用 | 前面有长任务（> 50ms）压着；首屏 JS 还没跑完 | 拆长任务、延后非关键 JS、`content-visibility` 减少布局量 |
| 处理时长 | processing duration | 你的事件 handler 同步执行的总时长 | 大列表同步过滤/排序、在 click 里做复杂计算、Vue 里同一 tick 触发巨型重渲染 | 把计算挪出关键路径（预计算/缓存/`computed`）、分批渲染、用 `requestIdleCallback` 之类延后 |
| 展示延迟 | presentation delay | 处理完之后，浏览器计算样式、布局、绘制到屏幕的时间 | 单帧里改太多 DOM、动画走的是布局属性（`width`/`top`/`height`）、图片解码 | 只动 `transform`/`opacity`（见 [过渡与动画](/css/transitions-and-animations)）、给图片声明尺寸、减少同时变更的节点数 |

这张表的价值在于**诊断顺序**：INP 变红时，先确定是这三段里哪一段占大头，再决定动哪里。而这三段的修法互相冲突——比如「把 handler 拆成异步分片」只对处理时长有效，对输入延迟一点用没有（输入延迟要减少**别的**任务）。

## 首屏 JS 体积为什么同时伤 TBT 和 INP

浏览器为一份 JavaScript 付三次钱：**下载**（受第 7 章缓存策略与压缩影响）、**解析与编译**（正比于代码量）、**执行**（跑顶层代码、挂载应用）。只有第一项能被缓存救回来，后两项每次都要重付（`immutable` 长缓存省的是网络，不省 CPU）。

TBT（Total Blocking Time，总计阻塞时间）是 Lighthouse 里的**实验室指标**，定义是：从 FCP 到 TTI 之间，每一个执行时长超过 50 毫秒的任务，把「超出 50 毫秒的那部分」加起来。50 毫秒是人眼能感知到「界面没反应」的经验阈值。所以：

```text
一个 320ms 的任务  →  TBT 贡献 270ms
拆成 7 个 45ms 的任务 → TBT 贡献 0ms（每个都没超过 50ms）
```

**这就是上面那个「拆任务把 TBT 归零」的手法为什么是作弊**：TBT 只惩罚超出部分，不惩罚总量。而 INP 是现场指标，它看真实交互那一刻主线程上排着多少活。要真正改善响应性，方向是**减少主线程总工作量**，而不是把同样的工作量切成好看的段：删依赖（第 4 章的产物分析与代码分割）、把首屏不需要的逻辑延后（路由级懒加载）、把计算挪到 Web Worker 或挪到服务端。

一条经验关系（**这是量级直觉，不是你站点的实测值**）：首屏必须执行的 JS 从约 50 KB 涨到 300 KB 再到 1.5 MB，中端移动设备上主线程被占住的时间大致从几十毫秒涨到数百毫秒、再到数秒量级，表现依次是「首屏能看能点」→「点下去有可感知的停顿」→「页面像坏了」。要把这个直觉变成证据，用下面那一节自己读一次数。

## CLS 是怎么算出来的：为什么「抖一下」值 0.2

CLS 不是「偏移了几次」，而是每次偏移的**分值累加**。单次布局偏移分值的两个因子：

```text
影响分数（impact fraction）= 偏移前后两块区域合并后，占视口面积的比例
距离分数（distance fraction）= 移动距离 / 视口在移动方向上的较短边
单次偏移分值 = 影响分数 × 距离分数
```

浏览器把偏移按时间窗口分组（检索到的官方描述是：窗口内相邻偏移间隔不超过 250 毫秒、窗口最长 500 毫秒），CLS 取**所有组里分值最高的那一组的总和**——不是整个访问的简单累加。

由此得到两条判断力：

**一、一个占满视口的元素整体下移，最坏接近 1 分；而它只是自己动、不推开别人，也可能被计入。** 真正让 CLS 崩掉的组合是「大块内容 + 推开下方内容」，最常见的两个来源是：**没声明宽高的图片**（浏览器先按占位算布局，图到位后撑开一切）和**后插入的内容**（cookie 横幅、骨架屏换成真实内容时高度变了、懒加载广告位）。

**二、修 CLS 的手段是「预留空间」，不是「去掉动画」。** 给 `img` 写 `width`/`height`（或用 `aspect-ratio`，见 [盒模型](/css/box-model) 之后的值与单位那一章）、给横幅留固定占位、用 `transform` 而不是布局属性做位移、字体替换时用 `size-adjust` / `ascent-override` 让兜底字体与目标字体的度量尽量一致。

字体是 CLS 里最隐蔽的一项：`font-display: swap` 会让文字先用兜底字体绘制，真字体到位后**同一段文字变宽变高**，整段重排。中文段落因为字形宽度差异大，这个偏移尤其明显（下一节讲字体）。

## 实验室数据与真实用户数据：两套不可互替的数

| | 实验室数据（lab） | 现场数据（field / RUM） |
| --- | --- | --- |
| 来源 | Lighthouse、DevTools Performance 面板、CI 里的 Lighthouse CI | Chrome CrUX（真实用户的 Chrome 上报聚合）、你自己埋点上报 |
| 环境 | 一台设定机型 + 人为网络/CPU 节流，**跑一次** | 真实设备与网络的混合分布 |
| 统计方式 | 单次运行的值 | **p75**（第 75 百分位）：即 25% 的用户比你看到的数字更差 |
| 能测 INP 吗 | **不能**（INP 需要真实交互）；Lighthouse 用 TBT 作为它的实验室代理 | 能，这是 INP 唯一可靠来源 |
| 什么时候用 | 复现问题、验证某次改动有没有效、CI 里防回归 | 判断「到底有没有变好」、看长尾设备 |

两个必须记住的推论：

**第一，p75 意味着你不是在优化平均分。** 如果你的 p75 LCP 是 2.4 秒，那么有四分之一的用户比这更慢。想让 p75 达标，靠的是消除最坏路径（首屏 JS 总量、第三方脚本、图片未按尺寸下发），不是把平均情况抹平。

**第二，个人项目大概率拿不到 CrUX 数据。** CrUX 要求该页面/来源有足量的真实 Chrome 流量，本站这种个人站点在 PageSpeed Insights 上通常显示「CrUX 数据不可用」。这意味着：**你的现场数据只能自己造**——要么埋点用 `web-vitals` 库上报（下一节），要么至少用「在真实中端机上、用真机浏览器手测一遍」替代。别把 Lighthouse 的分数当成唯一证据。

## 用 PerformanceObserver 读出自己的数

标准做法是用 `web-vitals` 这个官方维护的库（它在 npm 上；检索到该包已把 FID 标注为弃用、并导出 `onINP`）。下面的写法是**为站内演示手写的、未在本机运行**，接口名请以该包与 MDN 当前文档为准。

```js
// main.js —— 只用于本地调试：把三项指标打到控制台
// 生产环境应改为 sendBeacon 上报到你自己的接口（本站没有后端，见第 9 章练习）
import { onLCP, onINP, onCLS } from 'web-vitals'

function report(metric) {
  // rating 由库按官方阈值算好：good / needs-improvement / poor
  const row = {
    name: metric.name,
    value: Math.round(metric.value),
    rating: metric.rating,
    // LCP 才有：哪个元素是最大内容
    element: metric.entries?.at(-1)?.element?.outerHTML?.slice(0, 60),
  }
  console.table([row])
}

onLCP(report)
onINP(report)   // 会在交互过程中多次触发，取当前最差值
onCLS(report)
```

在浏览器里跑通之后，**预期输出**（不是实测，数值取决于你这台机器与网络）长这样：

```text
┌─────────┬───────┬───────┬────────────────────┬────────────────────────────┐
│ (index) │ name  │ value │ rating             │ element                    │
├─────────┼───────┼───────┼────────────────────┼────────────────────────────┤
│ 0       │ 'LCP' │ 1843  │ 'good'             │ '<img src="/assets/hero…"' │
│ 0       │ 'CLS' │ 0     │ 'good'             │ undefined                  │
│ 0       │ 'INP' │ 76    │ 'good'             │ undefined                  │
└─────────┴───────┴───────┴────────────────────┴────────────────────────────┘
```

不装库、直接用 PerformanceObserver 读 LCP 与偏移的最小版本：

```js
new PerformanceObserver((list) => {
  const entries = list.getEntries()
  const last = entries.at(-1)
  console.log('LCP 元素:', last.element?.tagName, '时刻:', Math.round(last.startTime))
}).observe({ type: 'largest-contentful-paint', buffered: true })

new PerformanceObserver((list) => {
  let total = 0
  for (const e of list.getEntries()) {
    if (e.hadRecentInput) continue   // 与近期输入关联的偏移不计入 CLS
    total += e.value
    console.log('一次偏移:', e.value.toFixed(4), '来源节点:', e.sources?.[0]?.node?.nodeName)
  }
  console.log('当前累计 CLS:', total.toFixed(4))
}).observe({ type: 'layout-shift', buffered: true })
```

`buffered: true` 是关键——它让 observer 能拿到「注册之前」就已经发生的条目，否则你在应用挂载后才 import 这段代码，LCP 早已完成，什么都读不到。**预期输出**形如 `LCP 元素: IMG 时刻: 1843` 与 `当前累计 CLS: 0.0000`。

配合 DevTools 的另外两个入口：Application → Metrics 面板可以勾选模拟 CPU/网络节流；Performance 面板录制里点 Timeline 上的红色角标就是长任务，下方 Main 轨道展开能看到「这段任务里跑的是哪个函数」——**这是把 INP 的三段拆开的唯一可靠手段**，别靠猜。

## 图片与字体：两个最稳的拖慢点

图片的问题永远是这几条，且每条都可验证：

| 拖慢点 | 为什么慢 | 怎么确认 | 怎么修 |
| --- | --- | --- | --- |
| 渲染尺寸远小于资源固有尺寸 | 下载了几千像素宽的图，只为显示 320 像素 | Network 里该图传输大小 vs 元素实际渲染尺寸 | `srcset` + `sizes` 按视口下发；或用响应式 CDN 参数 |
| 首屏图被 `loading="lazy"` 拖住 | 要等布局算完才知道它是否在视口内 | Performance 里图片请求开始时间晚于布局完成 | **首屏/LCP 图片不要用 lazy**；lazy 是给折叠以下的图用的 |
| 没有 `width`/`height` 或 `aspect-ratio` | 先按占位布局，图到了再撑开 | CLS 非零且 `sources` 指向那个 img | 声明固有尺寸（[渲染性能](/vue/rendering-performance) 里同理） |
| 格式落后 | JPEG/PNG 体积是 AVIF/WebP 的数倍 | Network 面板逐条看体积 | 现代格式 + `source` 回退；SVG 用于图标 |
| 靠 CSS 背景图承载 LCP 内容 | 浏览器要等 CSSOM 才知道要下载它 | LCP 元素是 DIV 而不是 IMG；请求起始时间很晚 | 用 `preload` 提早（第 7 章）或改成真正的 `img` |

字体的问题只有两条主线，但中文站对第一条特别敏感：

**一、体积。** 一套完整中文字体是几兆起步，「字体子集化」不是可选项而是必需项——按实际用到的字符裁剪（本站正文里出现的字符集），或用系统的中文字体栈兜底。字体体积直接压在 LCP 上：文字要等字体到位才能绘制，这是最典型的「加载完但看不见内容」。

<Callout type="warn" title="别用 font-display 的 block 值">

`block` 会在阻塞期内让文字**完全不显示**（FOIT），中文长文页面的观感就是「白屏了两秒，然后突然全是字」。可考虑 `optional`（首次访问可能直接用兜底字体，换来零延迟与零偏移）或 `swap`（先兜底、后替换，代价是替换那一刻的偏移）。这三档的精确时间线请务必对照 MDN 的 `font-display` 页面核实——本章未逐一核对其行为区间。

</Callout>

**二、度量替换造成的偏移。** 兜底字体与目标字体的 x-height / 行宽不同，替换那一刻整段重排。修法是 `@font-face` 的度量描述符（`size-adjust`、`ascent-override`、`descent-override`、`line-gap-override`）把兜底字体的度量校到接近目标字体。这些属性名请在动手前对照 MDN 核实（**本章未逐一核实**）。

另外回指第 7 章：字体是 CORS 取用的资源，`preload` 漏 `crossorigin` 会导致下载两次——那才是真正让 LCP 变慢的坑，而不是「没加 preload」。

## 性能预算：写成能被机器判定的句子

「把这个站优化一下」不是预算。预算是**一条带数值、带来源、带失败动作的规则**。四步定出来：

1. **先取基线**：用上一节的 `web-vitals` 代码在你的目标设备档位上读一次；拿不到现场数据就明确写「基线来源=实验室，1 台桌面 + 模拟 4x CPU 节流」。没有基线的预算一定是拍脑袋。
2. **写下现场指标目标**（面向用户，允许有噪声）：例如「p75 LCP ≤ 2.5s；p75 INP ≤ 200ms；p75 CLS ≤ 0.1」。
3. **写下构建期预算**（面向工程，可被 CI 硬失败判定）：这是个人项目最实用的一条，因为它不需要任何真实用户就能执行。

| 预算项 | 本站可用形式 | 判据来源 | 超了怎么办 |
| --- | --- | --- | --- |
| 首屏 JS 传输体积 | 入口 chunk gzip 后 ≤ N KB | 构建产物体积（第 4 章） | 拆路由、换依赖、按需引入 |
| 单个依赖体积 | 任一依赖 gzip 后 > 80 KB 需写明理由 | 产物分析报告 | 记录理由或替换 |
| 首屏请求数 | 关键路径请求 ≤ 12 | Network 面板首轮加载计数 | 合并、内联小资源、去掉第三方脚本 |
| 图片总量 | 首屏图片 ≤ 400 KB | Network 按类型汇总 | 压格式、按尺寸下发 |
| 字体 | 每档 ≤ 100 KB 且已子集化 | 产物目录 | 子集化 / 改用系统字体栈 |
| LCP / INP / CLS | 见上，指向现场数据 | `web-vitals` 上报 | 回到三段归因表定位 |

**关键纪律：预算要挂在会失败的环节上。** 一条写在文档里、没人读的预算等于没有。可行的做法是在构建脚本后加一步体积检查，超阈值就让 `npm run build` 退出码非 0（工具选型与具体参数以官方文档为准，别照抄本站措辞；如何接进流水线见 [/devops/ci-cd](/devops/ci-cd)）。

## 常见错误与排查

1. **Lighthouse 96 分但用户说卡，且你不确定谁对** —— 实验室数据只跑一次、只测加载、用人为节流；INP 在实验室里**根本测不出来**（Lighthouse 用 TBT 代理）。确认：用 `web-vitals` 上报或至少在中端真机上做连续点击手测，看 INP 是否 > 200ms。修：把决策依据从「Lighthouse 分数」换成「三项指标的现场 p75」，Lighthouse 只用于复现与回归检查。
2. **加了 `loading="lazy"` 之后首屏白屏更久** —— 你把 LCP 候选元素变成了延迟加载资源，请求起始时间被推到布局之后。确认：Performance 录制里看该图片请求的起始时刻是否晚于首次布局；LCP 元素的时刻是否变大。修：首屏图不加 lazy，只给折叠以下的图加。
3. **CLS 是 0.18 但你在开发机上「看不出任何跳动」** —— 偏移来自字体替换或图片到达，这两者都依赖网络时序，本地缓存秒回就看不到。确认：PerformanceObserver 打印 `layout-shift` 条目、看 `sources` 指向哪个节点；或用 DevTools 的 Performance → 布局偏移轨道。修：给图片声明尺寸、给字体度量做 override、避免在已渲染内容上方插入东西。
4. **主线程长任务红色块很多，点开发现是「（匿名）」或一堆无关帧** —— 常见于第三方脚本与未压缩的生产构建。确认：切到生产构建再录一次（开发模式有未压缩代码与 HMR 运行时，长任务数字完全不可比）。修：先在 `npm run build` + 预览模式下测；第三方脚本考虑延后加载或移除。
5. **把大任务拆成小任务后 TBT 降了、INP 没降甚至更高** —— TBT 只统计超过 50 毫秒的部分，拆分能「藏」指标；INP 看的是真实交互时主线程上排了多少活。确认：对比「拆分前后主线程总忙碌时间」，而不是红色块数量。修：减少总工作量（删依赖、延后非必要逻辑、把计算移出主线程），别只调形状。
6. **每次发版 LCP 都变差一点点，没人知道是谁** —— 没有构建期预算，回归只能靠肉眼。确认：把入口 chunk 的 gzip 体积记在 CI 日志里，与上一次对比。修：给体积加硬门槛（超阈值即失败），并把「哪个依赖涨了多少」写进 PR 检查。
7. **CrUX / PageSpeed Insights 显示「没有数据」，于是你觉得没法衡量** —— 现场数据需要足量真实 Chrome 流量，个人站通常不够。确认：该工具是否明说数据量不足。修：自建上报（`web-vitals` + 你自己的接口 + `sendBeacon`），或者退回「实验室基线 + 真机抽查」这条可执行路线；**不要因为拿不到现场数据就退回只看分数**。

## 练习

<Exercise title="练习 1 · 给自己的站点读出三项数字" difficulty="基础">

用本章的 `web-vitals` 代码（或 PerformanceObserver 版本）在你的项目上跑一次：先正常加载，然后**刻意做五次交互**（点开一个折叠内容、切一次暗色模式、输入一段搜索、跳一个路由、回来）。抄下三个 `value` 与 `rating`。回答：① 你的 INP 出现在哪一次交互上？② 你的 LCP 元素是什么标签，它的 `element` 是 `img` 还是 `div`？③ 如果你的 CLS 非零，`layout-shift` 条目的 `sources` 指向哪个节点？

<template #answer>

这题的答案必须由你读出来才有效，这里给判读方法：① INP 是「最差那次」，所以你要找的是**你点下去之后画面最晚响应的那一下**——通常是「点开折叠内容」或「切换路由」这种会触发较大渲染的动作。确认它属于三段中的哪一段：如果输入后要等一帧才开始，是输入延迟（主线程被别的任务占着）；如果立刻开始但画面半天不更新，是处理时长或展示延迟。② `div` 意味着你的 LCP 内容承载在 CSS 背景图或纯文本块上，第 7 章讲的「浏览器要等 CSSOM 才发现资源」就会命中你——这是最容易改好的一个 LCP 病因。③ 指向 `img` 就是缺固有尺寸；指向文本节点通常是字体替换；指向某个容器的位移则是后插入内容。

顺带一条纪律：**每次读数都记下环境**（设备档位、是否首访（有缓存）、是否开了 DevTools 的 Disable cache）。同一份代码在有缓存时 LCP 会好看一大截，你如果拿有缓存的数字当基线，之后所有优化都无从判断。

</template>

</Exercise>

<Exercise title="练习 2 · 四个动作分别影响哪个指标，哪个可能反向" difficulty="进阶">

判断下列每个动作主要影响 LCP / INP / CLS / TBT 中的哪一项，以及**有没有可能让某一项变差**：A 把入口文件里一个只在详情页用的大依赖改成动态导入；B 给首屏 hero 图加 `loading="lazy"`；C 给所有 `transition` 换成 `transform` 动画；D 把 300 毫秒的同步过滤拆成七个 `setTimeout(0)` 的分片。

<template #answer>

A：主要减 LCP 与 TBT（首屏要执行的 JS 变少），也减 INP 的输入延迟；副作用是**用户第一次点进详情页时会多一次下载与等待**——你把成本从「所有人」转移给了「访问详情页的人」。这正是为什么需要路由级预取或至少 `modulepreload`（回指[第 4 章](/frontend-engineering/vite-build)与第 7 章）。B：**反向**。LCP 变差（请求开始得更晚），白屏期变长，其他指标基本不动。首屏图永远不加 lazy。C：改善 INP 的展示延迟段与 CLS（不再因尺寸变化推开内容）；副作用几乎为零，是收益稳定的一条——但注意它救不了「内容本身太多导致布局很慢」的情况。D：**作弊型**。TBT 变好看（每片都不超过 50 毫秒），但主线程总忙碌时间没变，INP 不会改善甚至更差（分片本身有调度开销，且输入更可能落在某个分片中间要等它做完）；而且拆完之后过滤结果**更晚出现**，处理时长之外的等待时间被拉长了。正确的做法是减少总计算量（预计算、缓存、把排序交给索引化的数据结构）或移出主线程。

这题的结论：任何一个「让某个数字变好」的动作，都要问一句「这个物理过程本身变短了吗」。答不上来就是 Goodhart。

</template>

</Exercise>

<Exercise title="练习 3 · 故意制造一次 CLS 并解释它的量级" difficulty="挑战">

在一个页面顶部放一个 `img`（不写 `width`/`height`，也不写 `aspect-ratio`），图片本身 1200×800，CSS 里只给它 `width: 100%`；图片下方紧跟三段正文。用 PerformanceObserver 打印 `layout-shift` 条目并观察 CLS。① 预测偏移发生在哪一时刻、偏移分值的两个因子分别大概是多少（假设视口宽 1200、高 800，图片渲染后高 800）；② 如果同一段文字在图片上方而不是下方，CLS 会怎么变？③ 加上 `aspect-ratio: 3 / 2` 之后为什么偏移消失？④ 如果换成 `font-display: swap` 的中文段落，偏移来源与修法有什么不同？

<template #answer>

① 偏移发生在**图片解码完成、开始占位绘制**那一刻（不是请求开始）。在此之前，图片元素的固有高度未知，布局给它的高度接近 0；图到位后按 100% 宽 × 3:2 高撑到 800 像素，下方三段正文整体下移 800 像素。距离分数 = 800 / min(1200, 800) = 800 / 800 = **1**（取视口较短边）；影响分数 ≈ 偏移前后被移动内容占据的联合区域 / 视口面积，正文三段加图片新区域很可能覆盖大半个视口，量级 0.5–0.9。单次分值量级 **0.5–0.9**，一次就足以让 CLS 远超 0.25 的「差」线。**这个数不是估出来的漂亮故事——它说明 CLS 崩掉往往只需要一张没写尺寸的大图。**② 文字在上方则不会被推开，只有图片自身「从无到有」，而 LCP/绘制不算偏移；此时 CLS 明显变小甚至接近 0——这告诉你：**同样一张图，放在首屏之上与首屏之下，CLS 命运完全不同。**③ `aspect-ratio` 让浏览器在下载完成前就能算出高度（宽度 × 比例），首帧布局已留好 800 像素的坑，图到位只填充像素、不改变任何元素的盒位置 → 没有布局位移 → 不产生 `layout-shift` 条目。这是「预留空间」类修法的共同原理，也是为什么 `width`/`height` 属性同样有效（浏览器会据此推算固有比例）。④ 字体替换的偏移来源是**文本自身度量变了**：兜底字体与目标字体的字宽/x-height 不同，替换后每行文字变宽或变高，下方内容级联下移；给图片写尺寸救不了它，要用 `size-adjust` / `ascent-override` 把兜底字体度量校准，或者干脆用系统字体栈（牺牲一点一致性换零偏移，中文站常见且合理的取舍）。

诚实提示：本练习未在本机执行；①里的具体分值依赖实际文本行数与视口，请以你自己打印出来的数字为准。

</template>

</Exercise>

本站是一个 VitePress 静态文档站：纯静态产物、无后端、内容以中文长文为主、暗色模式、本地搜索、图片很少。给这个站写出四条可被机器判定的预算（含数值、判据来源、超标动作），并说明：为什么这个站的预算里**不该**出现「首屏图片 ≤ 400 KB」？哪一项指标在这个站上其实天然健康，哪一项是真正的风险？

<template #answer>

建议的四条：① **入口 JS（含主题、搜索运行时）gzip 后 ≤ 120 KB**，判据来自 `dist/assets/` 产物体积（第 4 章的分析方法），超标动作=把搜索索引或代码高亮改成按需加载；② **构建产物中不得出现完整中文字体文件（任一字体资源 ≤ 150 KB）**，判据=产物目录逐文件体积，超标动作=子集化或改系统字体栈；③ **本地搜索索引的加载不得阻塞首屏渲染**，判据=Performance 录制里索引请求的发起时机与首次绘制关系，超标动作=改为首次交互时再取（这直接改善 INP 的输入延迟与 LCP）；④ **p75（或实验室基线）CLS ≤ 0.05**，判据=`web-vitals` 打印值，超标动作=排查 `layout-shift` 的 `sources`。

为什么不该有「首屏图片 ≤ 400 KB」：这个站几乎没有图片，写一条用不到的预算只是让文档变长——**预算必须挂在这个站点真实的瓶颈上**。天然健康的项：LCP（文本为主的静态页、无大资源，只要没有把文字压到字体后面绘制就很快）与 INP 的加载期部分（没有复杂首屏逻辑）。真正的风险项：**CLS 与 INP**——前者来自自定义中文字体的 swap 替换与主题切换时图片/代码块重排，后者来自「点击搜索后同步构建索引或做全文匹配」这类主线程长任务。这也解释了为什么性能预算要按站点定制：一份通用清单套到一个文档站和一个电商站上，产出的都是废话。

</template>
