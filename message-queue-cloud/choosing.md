# 三者选型对照：把「哪个更好」换成「我需要哪种保证」

选型失败几乎从来不是因为不懂某个产品，而是因为问错了问题。「RabbitMQ 和 Kafka 哪个更快」这类问题没有答案，因为它没说要快在哪一段；「我已经有 Redis 了，那就用 Stream 吧」也不算决策，它只是把「顺手」当成了「合适」。真实的翻车都长这样：有人用 Kafka 做「注册后发欢迎邮件」，功能是通了，代价是一个人维护一套为百万级事件设计的分布式日志，并且要为它的运维水平负责；有人用 Redis Stream 做「报表重算」，三个月后一次修剪把要回放的历史剪掉了，因为条数上限从来不是时间承诺；有人用 RabbitMQ 做审计事件流，然后发现「上周这笔订单的完整事件序列」查不出来——消息确认后就没有了，路由拓扑再漂亮也不给你日志。三个案例里，产品都没选错功能，选错的是**它提供的保证类型与你业务需要的保证类型不匹配**。

这一章把前三章的模型知识转成判据。做法是两段：先做**概念清障**——四组经常被混为一谈的东西（投递语义、持久化、吞吐、顺序），它们各自和谁不是同一件事；再做**维度对照**——八个维度逐项回答「这个维度上三者各自给你什么、代价是什么」。最后给出第四种选项（不引入中间件）和三条迁移线，因为对个人项目最常被忽略的事实是：**选型包含「现在还不需要选」这个答案。**

<Callout type="info" title="这一章的判据来源与用法">

本章不引入新的产品事实，只做映射：模型细节与已核实/未核实的边界分别写在 [RabbitMQ](/message-queue-cloud/rabbitmq)、[Redis Stream](/message-queue-cloud/redis-stream)、[Kafka](/message-queue-cloud/kafka) 三章开头的核实说明里。凡涉及具体配置项、命令参数、版本行为，请以各章的核对提示为准，不要把本章的对照表当成参数表用——它回答「选哪个、为什么」，不回答「怎么写配置」。另外本章的判据全部以「个人项目 + 一到两个人运维」为默认规模；团队规模、合规要求、既有技术栈都会改变结论，本章末的练习里有这种改写。

## 四组必须分清的概念：它们都不是同一件事

**投递语义不是消费确认。** 前者是系统层面的承诺类型（至多一次 / 至少一次 / 恰好一次），描述「一条消息最多与最少被处理几次」；后者是某个客户端 API 上的一个动作（`ack` / `XACK` / 提交偏移量），描述「我把进度告诉谁、什么时候告诉」。混了会怎样：你以为「消费者配置里写了手动确认」就等于「至少一次」——但如果没有失败重认领机制（RabbitMQ 的连接断开归还、Stream 的 `XAUTOCLAIM`、Kafka 的不提交偏移量），确认动作只会把消息**确认掉**，处理失败的消息照样消失。判据很简单：**先说出你要哪一档语义，再问这个产品的哪个动作组合能兑现它。**语义是组合行为的结果，不是某个开关的名字。

**消息持久化不是高可用。** 持久化回答「重启后数据还在吗」，高可用回答「一个节点没了服务还可用吗、数据还全吗」。RabbitMQ 里这两件事隔得很开：持久化消息 + 持久化队列是「与」运算，而跨节点冗余要仲裁队列；Redis Stream 的数据随 RDB/AOF 落盘，但单实例宕机期间队列就是不可用；Kafka 的副本机制把两者绑得最紧，可副本因子不等于端到端不丢（生产端确认程度、消费端提交时机仍在链上）。混了会怎样：你在配置里勾了「持久化」，然后在一场单节点故障里丢掉了勾选项之外的东西——磁盘上没写、或者副本数一。判据：**分别回答「进程重启」和「整机消失」两个问题，每个答案要能指出兑现它的具体机制。**

**吞吐量不是延迟。** 吞吐是「单位时间能处理多少条」，延迟是「单条从发出到被处理花多久」，而且两者通常互相拉扯：批处理、刷盘策略、分区并行都靠攒着换吞吐。Kafka 的高吞吐来自顺序写盘与批量拉取，它不承诺单条低延迟；RabbitMQ 在传统队列上的单条投递延迟表现很好，但把它的吞吐拉到日志级别要拿设计换路线；Redis Stream 的延迟取决于你 `BLOCK` 多久和 `COUNT` 多大。混了会怎样：你看「Kafka 每秒百万条」的规格上了它，然后抱怨「用户点注册到邮件送达要好几秒」；或者反过来，为了压延迟选了逐条推送，结果消费者被压垮。判据：**写下你的两个数字**——峰值每秒条数，以及可接受的最大送达延迟。给不出这两个数，吞吐与延迟的取舍无法判断。

**顺序保证不是业务幂等。** 顺序处理的是「先后」，幂等处理的是「重复」。它们在故障场景里各解一类问题：顺序错乱表现为「先收到取消再收到下单」；重复处理表现为「发两封邮件、扣两次库存」。混了会怎样：你用单分区换来了全局有序，然后仍然在同一条消息重投时给用户发了两封邮件——顺序机制对重复一点作用都没有；反过来你做了幂等表，也救不了错序的状态机。判据：分别列出「乱序会造成什么」和「重复会造成什么」两张清单，再决定优先设计哪个。这两张清单在第 4 章和第 5 章各自有对应的设计手段。

这四个判断合起来是一条通用方法：**任何中间件宣传的「保证」，都要先问它属于哪一层**。理论保证（语义档位）、具体产品配置（持久化、副本、确认模式）、客户端行为（重投、认领、提交时机）、业务层保证（幂等键、状态机、补偿）是四层，跨层引用永远是 bug 的来源。

## 八个维度逐项对照

下表把「要回答的问题」写在了维度旁边——用它当清单，别用它当结论。

| 维度 | 要回答的问题 | RabbitMQ | Redis Stream | Kafka |
| --- | --- | --- | --- | --- |
| 业务语义 | 这条东西是「待办」还是「发生过的事」 | 待办（确认后消失） | 两者都能，默认像待办（但条目可留） | 发生过的事（日志，消费不删） |
| 投递与确认 | 哪一档语义、由哪些动作组合兑现 | 手动 ack + nack + 断线归还，配合幂等可到至少一次 | 组 + `XACK` + 认领三件套，兑现 at-least-once | 提交偏移量决定丢或重；产品另有事务型能力（条件请查官方） |
| 顺序 | 顺序承诺的粒度是什么 | 单队列内大致有序，多消费者并发即失效 | 单流内 ID 有序，跨流不承诺 | **分区内**有序，键决定归属 |
| 吞吐量 | 单位时间能扛多少 | 中小量级绰绰有余，海量要调拓扑 | 受单实例内存与命令吞吐限制 | 设计目标就是高写入吞吐 |
| 积压恢复 | 堆了几百万条之后怎么办 | 队列会涨，内存/磁盘报警，消费者按 prefetch 慢慢吃 | 内存是硬上限，积压到一定量先炸缓存 | 积压只是 lag 变大，磁盘扛着，追平即可 |
| 数据保留 | 处理完还能不能翻出来 | 不能（确认后删除） | 能，但受 RAM 与修剪策略约束 | 能，保留时长由你定 |
| 运维复杂度 | 多这一个组件要长期做什么 | 中等：单节点简单，集群/仲裁队列复杂 | 最低（已有 Redis 时接近零新增） | 最高：集群、分区、副本、磁盘 |
| 成本 | 谁付钱——机器、你的时间、还是账单 | 机器 + 学习曲线 | 复用现有实例，但要划内存预算 | 机器 + 运维时间，或托管账单 |

三个需要额外说明的维度：

**业务语义排在第一位，因为它是唯一不能靠配置改变的维度。** 其余七个维度都能在换产品或改参数后调整，语义不行。你要做的事情如果是「把这些任务处理完，处理完就结束」，日志模型会强迫你自己维护「哪些还没做」；你要做的事情如果是「保留事实，允许多个下游各自重放」，队列模型会强迫你自己往另一个存储抄一份副本。这一维选错，后面七维的对错都救不回来。

**积压恢复这一维最容易被人低估，因为它在没出事时完全不可见。** RabbitMQ 的积压吃的是 broker 的内存与磁盘配额；Redis Stream 的积压吃的是整个实例的内存池，会牵连你的缓存；Kafka 的积压只是 lag 变大——这正是它的舒适区。反过来说，如果你把「积压能扛」当成优点提前上 Kafka，那你其实是在为一件还没发生的事付运维账。诚实的判断顺序：先看你的数据保留与语义需求，再看积压。

**运维复杂度这一维对个人项目是硬约束，不是软偏好。** 每多一个有状态组件，你就多承担一份升级、监控、备份、故障排查和夜间告警。第 6 章那句「单节点四件套够用」、第 7 章「我已经有一个 Redis」是决定性理由、第 8 章「一个人不该为想象中的规模引入分布式日志」，三条都是同一个判断在不同产品上的表达。

## 第四个选项：先问要不要引入中间件

选型表上一直被忽略的一行是「不引入队列」。对个人项目它有三种常见形态：

| 形态 | 怎么做 | 适合 | 什么时候坏掉 |
| --- | --- | --- | --- |
| 同步做 + 超时兜底 | 请求里直接调用，失败返回可重试 | 操作快、必须立刻成功、无第三方依赖 | 一出现「慢」「会挂」「会失败重试」就必须异步 |
| 进程内异步（`setImmediate` / 不 await） | 主链路返回，后台继续跑 | 单实例、可容忍丢、量小 | 进程重启即丢；多实例无法协调 |
| 任务表 + 轮询 | 写一张 `jobs` 表，定时任务扫并处理 | 需要「不丢 + 可查状态」但量很小 | 并发处理、退避重试、优先级、多实例都要自己实现 |

第 3 种是多数个人项目**真正的第一个正确答案**：任务表天然持久化、天然可查（`SELECT count(*) WHERE status='pending'`）、天然幂等友好（状态字段就是去重表）。你缺的只是重试退避、并发消费、优先级这几个机制，而它们在你需要之前不值得实现。第 1 章讲的「异步换来的四样债」在这里全部适用：一旦你引入队列，你就欠下了确认、重投、死信、幂等四笔账——**不引入就一笔都不欠。**

从任务表升级到队列的信号是具体的：同一批任务需要多个消费者并发（任务表要写锁和抢占逻辑，开始变复杂）；重试退避需要按时间投递；你需要把慢任务从数据库连接池里搬走；或者出现第二个进程要独立消费同一批事件。反过来，「听说队列更专业」不是信号。

## 三条迁移线：换组件的信号要能观测

**Stream → RabbitMQ。** 出现任一：需要按内容/多维条件分发（不想让路由逻辑长在自己代码里）；需要 broker 侧的自动归还与更成熟的死信/延迟生态；消息体变大、开始挤占你的缓存内存预算；消费者需要「推给我活」而不是自己拉。迁移成本主要在代码：生产者要从「往一个 key 追加」变成「声明拓扑 + 发消息到交换机」；消费端幂等不用改，但认领定时任务可以删掉。

**Stream 或 RabbitMQ → Kafka。** 需要同一份事件流被多个独立下游各自重放；需要历史回放（重算、审计、补数据）；峰值写入让单实例扛不住；积压恢复成为常态需求而不是意外。迁移成本最高的一段是**语义反转**：你从「消费即消失」换到「消费只是移游标」，所有依赖「消息还在不在」来推断「任务做没做」的代码都要重写，改成按业务状态判断。顺序设计也要重做（键与分区数是一对长期承诺）。

**Kafka → 退回去。** 这也是真实方向。信号：你在为「只有一个下游、不需要回放」的主题维护分区规划；运维时间超过了功能开发时间；每次发布都在观察再平衡； lag 曲线的告警比你产品的用户数还先响。退回 RabbitMQ 或 Stream 的代价是丢掉回放能力——所以要先把「历史真相」落到业务库或对象存储，再退。

第 13 章会把这三条线和「自托管还是上云」叠在一起判断；这里先给一条独立结论：**迁移成本的主要部分永远是语义，而不是代码行数。**

## 常见错误与排查

**1. 按「规模应该会长大」选型。** 现象：项目第一天上了 Kafka，一年后日活几十，你仍在维护分区规划。原因：把容量当成概率，把未来的想象当成需求。怎么确认：写下当前真实数字（峰值条数/秒、可接受延迟、保留时长），三件里有一件写不出来就说明需求还没成型。怎么修：先按今天的数字选，并把「什么信号出现时重新评估」写进 README；迁移线在上面那一节。

**2. 把三个产品当同类的三档。** 现象：你在对照表里逐行比较功能，得出「Kafka 比 RabbitMQ 高级」。原因：没先看业务语义。怎么确认：问自己「消息被处理完之后应该还在吗」——这个问题只有一个答案，而三个产品给你的是两类答案。怎么修：回到本章第一张表的「业务语义」行；第 2 章的「队列与日志」是关键概念底座。

**3. 用「我们用了手动确认 + 持久化」来回答投递语义问题。** 现象：出了重复扣款或消息消失，复盘时无法定位是哪一层失守。原因：跨层引用（见四组混淆）。怎么确认：能否分别指出兑现「不丢」和「不重」的具体机制与代码位置。怎么修：按第 5 章的三个计数器思路（投递/执行/副作用）在你的系统里各打一条日志，用数字回答语义。

**4. 只看吞吐指标做延迟敏感场景的选型。** 现象：通知送达慢到用户投诉，但监控显示「吞吐正常」。原因：批处理与拉取节奏换吞吐，延迟被牺牲。怎么确认：测 P95/P99 端到端延迟，不是平均值。怎么修：给出延迟预算并据此选拉取参数或换推送模型；吞吐达标不能替代延迟达标。

**5. 让一个 Redis 实例同时承担缓存、会话和只增不减的队列。** 现象：内存告警先出现，随后大面积缓存失效，用户掉线，你从队列代码里查不出来。原因：共享内存池，驱逐策略不分青红皂白。怎么确认：`maxmemory` 减去缓存正常工作集，就是你的队列上限；对照 `XLEN` 增长曲线。怎么修：要么给队列划出明确预算并加修剪策略，要么承认这个实例不该同时干这两件事——这条边界在第 7 章的三条硬边界里排第一。

**6. 把运维成本算成零。** 现象：组件装完三个月后，一次小版本升级把你周末搭进去两天。原因：只算了功能，没算升级、监控、备份、告警响应。怎么确认：问一句「这个组件出事时，我有没有一个能看的地方（管理界面/日志/指标）」。怎么修：每引入一个组件就同时引入它的健康检查与一条告警，做不到的先别引。

(a) 第 1 项：运维复杂度这一维的约束松了（三人轮值，夜间告警不再压在一个人的周末上），Stream 与 RabbitMQ 的选择差异从「组件数量」变成「可观测性成熟度」——需要管理界面、积压指标、死信可见性时，RabbitMQ 的优势才真正兑现（第 6 章那句「能看见没有绑定」在这里有意义）。第 3 项：仍不引队列，但要给它加一条监控（任务表里 pending 的年龄上限告警），因为「15 分钟定位」对第四种选项同样成立。(b) 第 2 项没变：需要重算 30 天是语义与保留决定的，跟团队规模无关。团队规模改变的是「你能维护什么」，不改变「什么模型能满足需求」。(c) 落在**可观测性与运维复杂度**这一维，不在投递语义那一维。三件事：为每条链路建立三个计数器（投递/执行/副作用，第 5 章）并做差值告警；给积压设阈值（队列长度或 lag）；给死信/失败任务设一个能被查到的地方并有 owner。

这题真正要练的是：**分清哪些判据来自业务需求（不随团队变），哪些来自你的运维能力（会变）。**选型结论要写清每个理由属于哪一类，未来条件变了才知道该重算哪一条。

<Exercise title="为「注册后发邮件」写一份完整选型说明，包含一次自我反驳" difficulty="挑战">

这是阶段项目的正式交付物。需求：注册后发欢迎邮件，日均 2 万件，峰值 10 倍；必须至少送达一次；同一用户绝不能收到两封；失败要重试 3 次后有人看得见；产品只有一个维护者，一台 VPS，Redis 已在跑。请写：(a) 选择与三行理由（必须引用语义、投递与确认、运维复杂度三个维度）；(b) 你放弃的两个方案，各写一句「它在什么信号出现时变成正确答案」；(c) 一段自我反驳：这个方案最早会在什么地方坏掉，你怎么提前知道；(d) 上线后要盯的三个数字，以及各自的阈值来源。

<template #answer>

(a) 选 Redis Stream。语义：待办（处理完就该消失），不是事件流。投递与确认：组 + `XACK` + `XAUTOCLAIM` 三件套即可构成 at-least-once，配合以用户 ID 为幂等键的去重表满足「绝不两封」。运维复杂度：复用已有实例，不新增有状态组件，这对一个人是决定性理由（第 7 章）。

(b) 放弃 RabbitMQ：当出现多维路由需求（不同类型通知要按规则分给不同 worker 组）、或需要 broker 侧成熟死信与延迟生态、或队列消息开始挤占缓存内存预算时，它变成正确答案。放弃 Kafka：当出现第二个真正独立的下游要各自重放、或需要历史回放（重算/审计）时，它变成正确答案。两条都以「信号」表述而不是「规模变大」——规模本身不是信号。

(c) 最早坏掉的地方是**共享内存池**：未确认条目 + 保留中的条目 + 缓存抢同一个 `maxmemory`。提前知道的办法是把三条曲线放一起看：`XLEN` 增长、各组 `XPENDING` 总数、`evicted_keys`。任一持续上升就说明预算划错了，不用等到用户掉线。第二早坏掉的是 `min-idle-time` 与发信 P99 的关系设置错误，症状是重复送达，而幂等表挡住了——所以要看「执行次数」而不是只看「投诉数」。

(d) 三个数字：**送达延迟 P95**（阈值来自产品要求，不是来自默认值——邮件这类需求通常几分钟级可接受）；**pending 总数与最老条目年龄**（阈值来自重试窗口：3 次重试 × 退避上限 + 认领间隔，超这个年龄就是真卡住）；**队列占用的内存字节数**（阈值来自 `maxmemory` 减缓存工作集，第 7 章的预算法）。每条阈值都要能说出它是从哪条业务约束推出来的——说不出就是抄来的数字。
