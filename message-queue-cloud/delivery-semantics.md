# 「不丢」和「不重」是一笔交易，而 exactly-once 说的从来不是你以为那件事

三个词被用得最随意的地方就是投递语义。产品页写「exactly-once 投递」，架构评审里有人说「我们用 Kafka 所以是恰好一次」，代码里有人把 `at-least-once` 当成注释写上去然后继续 `autoAck`。

先把话说到底：**投递（delivery）是一次网络交互，效果（effect）是这个交互之后世界变了没有。**这两个东西分属不同的层，而三种语义的保证对象其实不一样——at-most-once 和 at-least-once 说的是「投递」，exactly-once 说的是「效果」。把这三条摆在同一句话里比较，误解就从这里开始。

这一章不打算给你一个新的规则，只给你一组能自己数的数字，然后你会得到判断力：看见任何一句「我们保证恰好一次」，你能问出该问的那三个问题。

<Callout type="verified">

本章主证据是 `bench` 模式里的 M9：100 条消息的同一份负载，三档语义各跑一遍，注入**确定比例**的故障（不是随机数），最后数三个计数器。环境 Windows 10 x64 + Node v25.4.0，2026-10-19：

```bash
node message-queue-cloud/.scratch/mq-core.mjs bench    # M9 三档语义；M6 幂等键四臂
node message-queue-cloud/.scratch/mq-core.mjs crash    # M0 确认时机的三臂
```

模型是 SQLite 任务表 + 独立 worker，不是真实代理。**故障是人为注入的固定比例，所以「丢失=5」「重复=7」这两个数是由注入规则算出来的，不是概率估出来的**——这一点让它可以当反例用，不能当容量规划用。真实代理的语义表述单独一节，标明文档依据与未核实项。

</Callout>

## 三条保证各自放弃什么

| 保证 | 一句话定义 | 崩溃时的选择 | 你放弃了 |
| --- | --- | --- | --- |
| **at-most-once** 至多一次 | 消息可能丢，但绝不会重复 | 宁可丢掉，不再投第二次 | **不丢** |
| **at-least-once** 至少一次 | 消息一定被处理，但可能被处理多次 | 宁可重投，也不放过 | **不重** |
| **exactly-once** 恰好一次 | 每条消息的效果如同只发生一次 | —— | 这条不是「更好的前两档」，它要求在前面两条之外另做一件事（见下文） |

前两条的取舍结构是完全对称的：**它们回答的是同一个问题的两个答案——「你不确定时，赌哪一边？」**

- 赌「已经做完了」→ 至多一次 → 丢。
- 赌「还没做」→ 至少一次 → 重。

这个「不确定」来自哪里？来自**确认本身也是一条消息，也会丢**。这就是下一节那个死结。

## 为什么传输层给不出第三条路

```text
消费者做完副作用 ──▶ 发「我做完了」──▶ 代理
                                    │
                        如果这个确认在路上丢了：
                        代理认为没做完 → 重投 → 重复
                        消费者认为已做完 → 不再处理
                        两边都「没说错」，但没有共识
```

想消除重复，消费者需要知道「代理有没有收到我的确认」——那就要代理回一个「我收到了」。而这个回执也可能丢，于是需要一个确认的确认。**这是一个有限步数解决不了的通信问题**（分布式里通常叫两军问题）：在会丢包的信道上，双方无法对「某一件事是否已被双方知道」达成一致。

工程上唯一能终止这个递归的办法，是让某一方**在不确定时按一个固定方向赌**：

- 代理不确定 → 重投 → at-least-once。
- 代理不确定 → 丢弃 → at-most-once。

**任何声称「恰好一次投递」的系统，要么它的信道不会丢（不可能），要么它偷偷用了 at-least-once 加上某种去重。**后者才是真实发生的事情，也是「效果恰好一次」这个说法的全部内容。

## 同一份负载上的三个计数器

100 条消息，三档各跑一遍（原文）：

```text
=== M9 三档投递语义在同一份负载上的计数（100 条，注入确定比例的故障） ===
   at-most-once：投递=100 执行=95 副作用=95 丢失=5 重复=0（每 20 条注入 1 次「确认后才崩」）
   at-least-once：投递=107 执行=107 副作用=107 丢失=0 重复=7（每 13 条注入 1 次「确认丢失」）
   at-least-once + 幂等：投递=107 执行=107 副作用=100（=库里 100 行，不同 job=100）丢失=0 重复副作用=0 ← 这就是「效果恰好一次」
```

三个计数器分别是什么，必须先分清，否则这六列数字读不出任何东西：

- **投递**：这条消息被交到消费者手上的次数。
- **执行**：消费者代码被进入的次数（函数被调用了）。
- **副作用**：真的改了世界的次数（邮件发了、库存扣了、`effects` 表里多了一行）。

**语义承诺的对象是「副作用」，不是前两个。**逐条看：

**第一档（at-most-once）**：投 100、执行 95。5 条在「已投但没执行完」的缝里蒸发，因为这一档的策略是「领走就算交出去了，崩了不重投」。**丢失=5 正是那个不确定的赌局被结算成丢的 5 次。**重复=0 不是因为它安全，是因为它从不重试——不重试当然不重复，代价全在丢失那一列。

**第二档（at-least-once）**：投 107、执行 107、副作用 107、丢失 0。多出来的 7 来自每 13 条注入一次的「确认丢失」——`13, 26, 39, 52, 65, 78, 91` 正好 7 条，所以 `100 + 7 = 107`。这些数字不是测量结果，是注入规则的算术，**这正是它能当反例用、却不能当容量规划用的原因**。

**第三档（at-least-once + 幂等）**：**投递和执行一列没变，还是 107**。变的只有副作用：107 → 100，库里正好 100 行、去重后 100 个 job。

第三行是本章的全部论点。**幂等没有减少一次执行，也没有减少一次投递**——你的 CPU、你的下游调用次数、你的日志条数，全都还是 107。它减少的是「世界被改了两次」。所以：

<Callout type="info">

「exactly-once」在工程上唯一可实现的形式是：**传输层接受 at-least-once，效果层用幂等把重复结算成 1。**

它不是一个更高级的投递保证，而是「投递语义」和「业务语义」两层合作的结果。任何只在传输层做的努力，最后都会撞上上一节那个递归。

</Callout>

## 幂等这一环上仍有三个洞

第 3 章已经给过幂等键的粒度问题（消息 id vs 业务动作，实测 2 次副作用 vs 1 次）。这里补三个直接决定「你的 exactly-once 能撑多久」的洞。

**洞一：去重记录有保留期，窗口外的重复挡不住。**

```sql
-- dedup 表会长大，你一定会想清理；清理之后，一条被延迟重投超过保留期的消息就会二次生效
DELETE FROM dedup WHERE done_at < ?;
```

保留期取多长，取决于你能容忍「多久以前的重复」：**至少要大于你最长的重试跨度加上最坏情况下队列的滞留时间**。一个常见事故形状是：大促期间积压了 3 天的消息，在你按 48 小时清理幂等表之后被消费——重复副作用回来了，而且这时所有告警看起来都正常。

**洞二：幂等表的写与副作用的完成不原子。**

```js
// ✗ 危险顺序：先插幂等，再做外部调用；中间崩 → 幂等说做过，其实一次都没做
await insertDedup(key);
await mailApi.send(payload);

// ✓ 至少要做成两态：进行中 → 已成功，且「进行中超时」要能被重投
await insertDedup(key, 'pending');
const ok = await mailApi.send(payload);
await markDedup(key, ok ? 'done' : 'failed');
```

单布尔幂等表解决的是「别做第二次」，两态幂等表解决的是「别因为怕做第二次而永远不做」。**第 3 章「幂等挡不住的那一半」里的第 1 条就是这个洞**：外部调用发出去了、响应丢了，你的记录既不该算成功也不该算失败，需要一个明确的「结果未知」状态和一条对它的处理路径（查询对端、或人工），否则它就成了永远不可查的丢失。

**洞三：跨系统时，你的键对方不认。**

幂等只有在「所有会重复的路径都用同一个键」时成立。链路上有第三方 API 时，重复可能来自它对同一请求的重试，而它用的是自己的标识。**做法是把你的键作为请求参数带过去**（很多 API 有 idempotency key / request id 一类的字段，字段名以你所用服务的文档为准），让两边共享同一个键。做不到时，语义就只覆盖到你自己的边界——**这必须是设计文档里写明的边界，不是留给以后的人去发现的。**

## 语义是每条链路的属性，不是整个系统的属性

一个真实系统里，不同消息该用不同档。别在架构文档里写「我们全站 at-least-once」，那种写法等于没写。

| 链路 | 重复的代价 | 丢失的代价 | 该选 |
| --- | --- | --- | --- |
| 欢迎邮件 | 低（用户烦） | 低（可补发） | at-least-once，幂等键=用户+模板 |
| 扣库存 | **高**（超卖） | 高（少卖） | at-least-once + **唯一条件更新**（库存行的状态机） |
| 支付回调后的状态更新 | 中（重复通知） | **高**（收了钱没发货） | **必须** at-least-once + 幂等，且幂等键=商户订单号而不是回调 id |
| 风控评分刷新 | 低 | 低 | at-most-once 完全可以——**丢一条比重一条便宜** |
| 埋点统计 | 低（多算一次） | 中（少算） | at-least-once + 可交换写入（`SET` 型），或干脆接受误差 |
| 短信验证码 | **高**（费用 + 用户困惑） | 高（登不进） | at-least-once + 带时间窗的幂等（同一手机号同一模板 60 秒内只发一条） |

看第 4 行：**存在应当主动选 at-most-once 的链路**，条件是「丢了不心疼、重了很贵」。这是判断力而不是偏好——选它时你要在评审里说出「这里的丢失是可接受的，因为 X 会补」。

第 6 行给了另一种形态：**当重复的代价是钱，幂等键要带时间窗**。60 秒内只发一条这件事，用「手机号+模板」做永久唯一键是错的（用户第二天再也收不到验证码），用无键是错的（重复计费）。正确形状是键里带窗口，例如 `code:13800000000:A:2026-10-19T14:03`，保留期刚好覆盖窗口。

## 怎么向别人解释你放弃了什么

三条保证各自需要一句能被检验的话。写不出这句话，说明你还没真的选定：

- 选 **at-most-once**：「最多可能丢 N 条，N 由 ___ 决定；丢了之后由 ___ 补。」（填不出来就不要选它。）
- 选 **at-least-once**：「重复率大约 ___，因为幂等键是 ___，所以重复的副作用是 0；**但执行次数不降，所以我的下游 QPS 要按含重复的量算**。」
- 声称 **exactly-once**：「传输层是 at-least-once，效果层靠 ___ 这个键去重，去重记录的保留期是 ___，跨系统那一段靠 ___。」三个空都填上，才配这三个词。

中间那句「下游 QPS 要按含重复的量算」是 M9 那行数字最实用的推论：投递 107、执行 107、副作用 100——**你的幂等让你能对用户承诺 100，但它没让你少打 7 次下游。**容量规划按 107，用户承诺按 100，这两个数必须同时出现在你的文档里。

## 常见错误与排查

**1. 现象：文档写着 exactly-once，用户却收到两封一样的邮件。**
原因：把 at-least-once 当成了 exactly-once，或者幂等键的粒度错了（用了消息 id）。
怎么确认：`SELECT job_id, count(*) FROM effects GROUP BY job_id HAVING count(*) > 1`——有行就说明副作用重复了；再看 dedup 表里这两次的键值是否相同。
怎么修：先确认投递确实是 at-least-once（不丢的一侧），再把键换成业务动作（第 3 章 M6 第三、四臂就是这个改动，2 次 → 1 次）。

**2. 现象：加了幂等表，某些消息变成永远不再被处理。**
原因：幂等记录写成单布尔、且写在副作用之前（洞二）。第一次尝试崩在外部调用中间，记录显示「做过」，之后所有重投都被挡住。
怎么确认：找 dedup 里有记录、但 `effects` 里没有对应行的 job——这批就是被自己的幂等设计杀掉的。**这个查询是本章我最希望你写进巡检的一条。**
怎么修：两态（`pending` / `done` / `failed`），并且给 `pending` 且超时的那批一条重投路径；`pending` 超时窗口必须大于最长合法处理时间。

**3. 现象：清理过一次历史数据之后，很久以前的重复动作又出现了。**
原因：洞一。去重记录的保留期短于消息可能的最大滞留时间。
怎么确认：比对「dedup 表最早一行」与「队列里最老一条消息的投递时刻」；后者更早，就已经暴露在窗口外。
怎么修：保留期 ≥ 重试跨度 + 最坏积压时长；或者不要让去重记录被时间清掉，而是把去重下沉到**业务键的唯一约束**上（订单表里那个「已退款」标记本来就该是唯一的），让它的生命周期跟着业务对象而不是运维脚本。

**4. 现象：压测时一切正常，真实故障当天重复量远超预期。**
原因：你的注入比例只覆盖了「确认丢失」，真实故障时是**恢复扫描把大量 `claimed` 一次性退回**，重复率呈尖峰而不是均匀的 7%。
怎么确认：看重复是不是均匀分布——`SELECT substr(done_at, 1, 13), count(*) FROM effects GROUP BY 1` 若在某个小时集中，就是批量回收。
怎么修：给回收路径也做退避与分批；监控里把「单位时间回收条数」作为独立指标，而不是混在积压里。M0 那三臂里 `after` 臂的 `重复=1` 是单条的形状，别把它当成整体重复率。

**5. 现象：所有消息都选了 at-least-once，下游限流天天被打爆。**
原因：没读 M9 第三行——执行次数等于投递次数，不降。**选 at-least-once 就是把重复流量转给了下游。**
怎么确认：下游调用量 ÷ 业务副作用量，这个比值就是放大倍数（M9 里是 107/100）。真实链路里这个数在故障当天可能是 2、5、20。
怎么修：能丢的链路主动降到 at-most-once（上文表格第 4 行）；不能丢的链路把去重放到**调用下游之前**（dedup 挡住就根本不发请求），这样幂等同时保护了你的预算。

**6. 现象：跨了三个服务之后，没人说得清这条链路是哪一档语义。**
原因：每个服务各自选了默认，语义是各自对「自己的投递」的承诺，串起来没有含义。
怎么确认：画一条链路，在每个跨界处标注「这里的重复会不会带来第二次副作用」「这里的丢失谁来补」。
怎么修：把键与语义作为**契约**传递（同一个 idempotency key 从入口带到出口），并在契约里写明谁负责补丢。这一条与[接口文档那一章](/backend/api-docs)里的版本约定是同一件事的不同面。

四处错，按严重程度排：

1. **「手动确认」与「持久化」都推不出 exactly-once。**手动确认只保证消息不会在你没 ack 时被抹掉（第 3 章核实的文档事实：`autoAck` 默认为 `false`，且未确认消息在通道或连接关闭时回到队列）——回到队列的意思恰恰就是**会重投**，也就是 at-least-once。
2. **持久化管的是「代理重启不丢」，不管「消费者崩溃不重复」。**这两件事属于不同故障域：一个在代理侧，一个在消费者侧。第 3 章 M0 的崩溃发生在消费者侧，持久化对此毫无帮助。
3. **「不需要做幂等」等于放弃了对重复的处置权。**传输层无法消除重复（那个两军递归），所以「不需要」只在一种情况下成立：重复没有代价（本文表格里的风控刷新）。
4. 结论应当是：「传输层 at-least-once，效果层用业务动作做幂等键，键的保留期覆盖最长重试跨度，外部调用段用两态记录」——**这一整句才是 exactly-once 的全部内容**，而不是某个产品开关。

顺带一个诚实声明：RabbitMQ 官方是否在某处使用「exactly-once」这个措辞、以及它的限定条件，**本章没有核实**，因此这里只对「这三项设置能推出什么」做逻辑判断，不引用它的宣传语。核实入口见文末。

## 下一章

本章用一个 100 条消息的负载把三条保证钉成了六个可数的数字：至多一次是 `投递=100 执行=95 丢失=5 重复=0`，至少一次是 `投递=107 执行=107 丢失=0 重复=7`，而加上幂等之后**投递与执行一列不动，只有副作用从 107 降到 100**。从这三个计数器出发，「exactly-once」被拆成了它真实的构成——传输层至少一次，加上效果层按业务键去重，加上一个说得清保留期的去重记录；同时它有三个会被漏掉的洞：窗口外的重复、单布尔幂等造成的永久不做、以及跨系统时对方不认你的键。

通用概念到这里讲完了：第 1 章的动机、第 2 章的模型、第 3～5 章的可靠性。接下来看具体产品——而第一个要看的不是 Kafka，是那种你多半真的会用的：灵活路由、任务队列、单机就能跑起来的那一个。第 6 章回答它在个人项目里值不值得装，以及它的「手动确认 + 死信交换」如何逐字对应本章与第 4 章讲过的机制，见[RabbitMQ：定位与适用场景](/message-queue-cloud/rabbitmq)。
