# 处理不了的消息要有去处，晚点做的事要有闹钟，有先后的事要有一条不许打乱的线

第 3 章解决了「消息不丢」和「重复无害」。但有三类问题它管不了，而且它们出事时比丢消息更难查。

第一类：**有一条消息永远处理失败**。载荷里有个字段是 `null`，任何 worker 拿到它都会抛异常。你的重投策略很健康——失败了就退避重试。于是这条消息在队列头部循环，**每一轮都占住一个 worker**，而它身后 5 条完全正常的消息一直等到超时。用户看到的是「队列没堵塞，接口也不报错，但任务就是不完成」。

第二类：**用户下单 30 分钟未支付，要发一条提醒**。这条逻辑不难，难的是「30 分钟」这个信息活在哪里——活在 `setTimeout` 里，一次部署就全没了；活在数据库的一列里，重启后照样能被领到。

第三类：**事件顺序倒了**。支付服务先发「已支付」再发「已取消」，两个消息被两个 worker 并行拿到，「已支付」那条恰好慢了一点，后落地。于是订单状态从「已取消」被改成「已支付」，而货物发了出去。

这三类分别对应死信队列、延迟消息、顺序性。它们看起来是三个功能，实际上是同一个问题的三面：**你的系统能不能表达「这条我不做，交给别人」「这条要到某个时刻才做」「这两条之间有先后」**。

```bash
node message-queue-cloud/.scratch/mq-core.mjs bench    # M4 毒丸三臂、M5 延迟闸门
node message-queue-cloud/.scratch/mq-core.mjs models   # M8 顺序性四种消费者配置
```

模型边界照旧：任务表 + 轮询不是 RabbitMQ / Kafka / Redis Stream 的实现。涉及真实代理机制的部分（死信交换、投递次数上限、原生延迟能力）单独立节，标明文档依据与核实日期，未验证的一律写进「未验证」清单。

## 死信：不止要有理由，还要有去处、有告警、能被重放

第 3 章 M3 那条消息用完上限之后落成的行（原文）：

```json
{ "id": 1, "state": "dead", "attempts": 3, "reason": "max attempts reached" }
```

一行死信记录至少要有四样东西，缺一样就少一种能力：

| 要有 | 缺了会怎样 | 用来回答 |
| --- | --- | --- |
| 终态（`dead`） | 恢复扫描把它当 `ready` 复活，永久循环 | 「这条为什么不再被消费了」 |
| 完整载荷（不能只存 id） | 修好 bug 也重放不了 | 「当时到底投了什么」 |
| `attempts` 与失败原因 | 只能靠翻日志，日志早已滚掉 | 「它试过几次、每次错在哪」 |
| 落到与主队列**分开**的地方 | 混在主队列里被反复捞，积压数字失真 | 「现在有多少条在等人处理」 |

最后一行是「死信队列」这个独立结构存在的真正原因——不是为了分类好看，是为了**让主队列的积压指标仍然可信**。死信混进主队列，你的告警面板上「积压 500 条」就再也不知道其中有 480 条是永远做不成的。

死信之后必须有人处理。三种重放方式，按代价从低到高：

```sql
-- ① 修好代码后，把行退回可消费状态（最常用：批量 bug 已修）
UPDATE jobs SET state='ready', next_at=0, reason='requeued after fix' WHERE id IN (?, ?);

-- ② 载荷本身要改（例如缺字段），改完再退——这一步要有审计，别在页面上裸改数据
UPDATE jobs SET payload=?, state='ready', next_at=0 WHERE id=?;

-- ③ 人工执行副作用，只标记为 done 并留下处理人
UPDATE jobs SET state='done', reason='handled manually by <who>, <when>' WHERE id=?;
```

**②是危险的**，因为它把「消息内容」变成了可编辑的运维数据，很容易改出第二条不存在的订单。能只用 ① 就别用 ②；必须用时，改完的载荷要作为新消息重新投递（保留原始那条不动），让链路里始终有一份不可篡改的现场记录。

真实代理侧（**文档依据，2026-10-19 通过 RabbitMQ 死信交换文档核对**）：一条消息成为死信的条件是那四项——被 `reject` 或 `nack` 且 `requeue` 为 `false`；消息 TTL 过期；队列 TTL 过期；队列长度达到上限被丢弃。配置项是队列参数 `x-dead-letter-exchange` 与 `x-dead-letter-routing-key`。文档同时把「投递次数达到上限」列为死信来源之一——**这意味着「重试上限 + 死信」在现代版本里可以是代理原生行为，不必全靠应用层实现**；具体到你要用的那个版本是否支持、参数叫什么，动手前核对官方文档。

## 毒丸：上限很重要，但「回队尾还是回队头」更重要

一条必定失败的消息 + 五条正常消息，三种重投策略，在 700 毫秒观察窗内的实测（原文）：

```text
=== M4 毒丸消息：有没有重投上限、重投回到哪里，决定后面 5 条正常消息能不能被处理 ===
   无上限 + 退避             700ms 观察窗内总投递=12 次，其中毒丸那条被投=7 次；毒丸状态=ready，后面 5 条正常消息完成=5/5
   无上限 + 立刻回队头          700ms 观察窗内总投递=41 次，其中毒丸那条被投=41 次；毒丸状态=ready，后面 5 条正常消息完成=0/5
   上限 3 次 + 退避          700ms 观察窗内总投递=8 次，其中毒丸那条被投=3 次；毒丸状态=dead，后面 5 条正常消息完成=5/5
```

三行读数：

- **41 次对 12 次**：同样的失败、同样的一个观察窗，「失败立刻回队头」把毒丸的重投频率放大了 3 倍以上，因为退避闸门（`next_at`）被绕过了。
- **0/5 对 5/5**：这是全章最该记住的两个数字。**毒丸自己完不成不是最坏的，最坏的是它把后面五条正常消息饿死。**队头阻塞的成本永远由无辜的消息承担。
- **总投递=8、毒丸=3、状态=dead、正常 5/5**：有上限 + 有去处，一条毒丸的代价被限制成「3 次无用执行」，而不是整条队列的瘫痪。

所以顺序是：**先设上限，再设去处，最后才是调退避参数**。反过来做（先精调退避曲线）的系统，第一次遇到必失败的消息就会全线卡住。

上限取几次不是风格问题，是「下游多久能恢复」的问题：

| 失败原因 | 重试能解决吗 | 上限怎么定 |
| --- | --- | --- |
| 网络抖动、连接重置 | 能，秒级 | 3～5 次、指数退避足够 |
| 下游限流（429） | 能，但要尊重它的窗口 | 退避下限 = 它给的 `Retry-After` |
| 下游业务校验失败（400，字段不合法） | **永远不能** | 1 次就够，立刻进死信——重试它是纯粹的浪费 |
| 代码 bug（空指针、解析异常） | 不能，直到你发版 | 上限之后进死信 + 告警，靠人 |
| 你的依赖服务挂了 20 分钟 | 能，但很慢 | 上限要按总退避时长算，不是按次数算 |

倒数第二条常被做错：很多人给所有失败统一 3 次。**把 4xx 业务校验失败也重试 3 次，等于给每条坏消息 3 次毒丸机会**。按错误类别分档，比调一个全局数字有用得多。

按总退避时长算这件事要给个算式（**算式，不是实测**）：base=1s、指数 2、上限 5 次 → 累计等待约 `1+2+4+8+16 = 31` 秒，覆盖不了 20 分钟的下游故障；要覆盖 20 分钟，base 得取到分钟级或直接落到死信 + 延迟重放（下一节）。**「重投上限 × 退避曲线」合起来定义了你对下游故障的容忍时长**，这个数字要写进设计文档，因为它决定了运维要不要在半夜起来。

## 延迟消息：到期时间必须是数据，不能是定时器

实测（原文）：

```text
=== M5 延迟消息：没到期时领不到，到期后第一次轮询就领到 ===
   到期前轮询 6 次全部返回空（下一次可领取时间写在行里，不是靠 sleep），到期后第 7 次领到，距投递请求 355ms，配置延迟=298ms
```

355 对 298 的 57 毫秒差就是轮询粒度加上领取与插入耗时——**延迟精度受限于轮询间隔**，和退避是同一个道理（第 3 章 M3 那 43 毫秒同源）。

三种实现，只有一种活得过重启：

```js
// ✗ 一：定时器。部署一次，所有待提醒全部消失，且没有任何记录证明它们存在过
setTimeout(() => notify(orderId), 30 * 60 * 1000);

// △ 二：定时器 + 落库。重启后还得自己扫描「哪些还没触发」，那定时器就是多余的
// ✓ 三：把到期时刻写进行，由消费者按闸门取（本章实测的形状）
db.prepare(
  "SELECT id FROM jobs WHERE state='ready' AND next_at <= ? ORDER BY id LIMIT 1",
).get(Date.now());
```

第三个做法有三个额外的好处，都是延迟消息场景里真正会用到的：

- **能改期**。用户提前支付了，你要做的不是取消定时器（`clearTimeout` 只在本进程有效），而是 `UPDATE jobs SET state='done' WHERE id=? AND state='ready'`——改不动就说明已经触发了。
- **能查到**。运营问「为什么他没收到提醒」，一条 SELECT 回答。
- **与重试共用同一个闸门**。退避重投本质就是「延迟一点点」，一列 `next_at` 同时服务两件事，不需要两套机制。

**一个必须写进代码的纪律**：延迟消息只是闹钟，不是事实。到期时**一定要回查当前状态**，不能把消息里的内容当作现状：

```js
// 到期后不要直接发提醒，先确认这件事还成立
const order = db.prepare('SELECT status FROM orders WHERE id = ?').get(orderId);
if (order.status !== 'unpaid') return;   // 已支付 / 已取消，闹钟到点但事过境迁
await sendPaymentReminder(orderId);
```

不写这一句的必然事故：用户 5 分钟就付了款，30 分钟后仍然收到「您有一笔订单未支付」。这不是假设——**消息里带的是「当时的事实快照」，而你需要的是「现在的事实」**，两者之间的时间差正是延迟消息的用途。

真实产品侧（**边界说明**）：任务表加闸门列是我验证过的机制形状；RabbitMQ 用什么实现延迟（TTL + 死信的组合、或专门的延迟插件）、Kafka 是否原生支持按投递时间延迟、Redis 侧有没有等价能力，本站**未在本机验证、也不在这里给结论**。落地时按你选定的产品核对官方文档；判据本章可以给：**能否做到「重启后仍然会在到点时被领到」，以及「到期时刻能不能被查询和修改」**。这两条不满足，你实现的就只是一个定时器。

## 顺序性：先确认要不要，再决定要多细

「订单已创建 → 已支付 → 已发货」这三条消息如果乱序落地，最坏的形状是**状态机倒挂**：「已创建」最后到，把状态从「已发货」改回「待支付」。

第 2 章的 M8 实测把顺序与并行之间的交易摊开（原文）：

```text
=== M8 顺序性：串行 / 全局并行 / 按 key 分区，四种消费者配置（6 条，其中 id 1 与 4 是 250ms 的慢活，其余 40ms） ===
   单 worker 串行                   完成顺序=1,2,3,4,5,6 总耗时=751ms 同 key 内乱序次数=0
   3 worker 全局并行（不分 key）     完成顺序=2,3,5,6,1,4 总耗时=327ms 同 key 内乱序次数=2
   2 worker 按 key 分区（1 key 1 worker） 完成顺序=2,1,4,3,6,5 总耗时=375ms 同 key 内乱序次数=0
   3 worker 按 key 分区（两个 worker 撞进同一个 key） 完成顺序=2,6,1,4,3,5 总耗时=370ms 同 key 内乱序次数=1
```

把它翻译成业务语言：

- `2,3,5,6,1,4` 这一行就是事故现场。id 1（订单已创建）是慢活，id 2（支付回调）是快活，两者并行后**支付先落地、创建后落地**。
- `同 key 内乱序次数=2` 意味着两条本应有先后的事件被倒过来了。**并行度换来 2.3 倍速度（751→327 毫秒），代价是这两次倒置。**
- 第三行 `2,1,4,3,6,5` 是解法：同一订单的事件串行处理，不同订单之间并行。375 毫秒，比全并行慢 48 毫秒，乱序 0。
- 第四行是解法被破坏的时刻：多塞一个 worker 让它和另一个 worker 落进同一个 key，`6` 排到了 `4` 前面，乱序 1。**分区保序的前提是「一个分区同一时刻只有一个消费者」，不是「我配了分区」。**

顺序性只有三种正确姿势，按代价排序：

| 姿势 | 保证什么 | 代价 | 什么时候用 |
| --- | --- | --- | --- |
| 单消费者串行 | 全局有序 | 吞吐上限 = 1 ÷ 单条处理时间 | 量小；或顺序是硬要求（账务流水） |
| 按业务 key 分区 | 同一实体内有序 | 并行度上限 = key 的个数；扩容时有序窗口会被打破 | **绝大多数业务事件流的正解** |
| 全局并行，不保证顺序 | 什么都不保证 | —— | 消息本身无序语义（审计流水、统计计数） |

**还有第四种姿势，很多人以为自己用的是它：「我加了单调条件更新，所以顺序乱也没关系」。**

```sql
-- 只有比当前更新的事件才允许落地：version 是事件序号 / 状态优先级 / 时间戳
UPDATE orders SET status = ?, version = ? WHERE id = ? AND version < ?;
```

`changes=0` 就说明这条是过期事件，丢弃它。这确实是**最便宜、也最能扛重平衡窗口的兜底**，因为它把顺序性下沉到了数据层，不依赖消费者的分配。但它有三个限制：① 它只能丢弃，**不能补做**被丢掉的那步的副作用（比如那条被丢的事件本来还要发消息）；② `version` 必须由生产侧保证单调，跨服务时钟不可信，用序号或状态优先级而不是时间戳；③ 它救不了「两个 worker 同时读到旧状态再各自写回」这类丢失更新——那要靠[事务与隔离级别](/database/transactions)。

最后一条要诚实说：**顺序性与「不丢」在机制上是有冲突的**。重投会让一条消息晚于它后面的消息被处理；要严格保序就不能重投，而「不重投 + 失败」就必然丢。真实系统里常见的解耦办法是「**保序靠分区、失败靠死信、恢复靠人工或延迟重放**」——不要在同一个队列上同时要求自动重试和严格有序，那两条各要各的。

## 三件事的共同前提：看得见

死信、延迟、乱序有一个共同的失效模式：**它们发生时，你的面板上一切正常**。所以先把观测的形状定下来。

```sql
-- 每个状态各有多少条（积压不等于有问题，claimed 长期不减才是）
SELECT state, count(*) FROM jobs GROUP BY state;

-- 最老一条等了多久 —— 这个比「积压条数」有用得多
SELECT (strftime('%s','now')*1000 - MIN(created_at)) AS oldest_ms FROM jobs WHERE state='ready';

-- 谁在反复失败：毒丸与超时回收都会在这里现形
SELECT id, kind, attempts, reason FROM jobs WHERE attempts > 1 ORDER BY attempts DESC LIMIT 20;

-- 未来 5 分钟会执行多少延迟任务：这是延迟消息的「预计负载」
SELECT count(*) FROM jobs WHERE state='ready' AND next_at BETWEEN ? AND ?;
```

**「积压 500 条」和「最老一条已经等了 40 分钟」是两个完全不同的告警。**前者可能只是峰值，后者意味着有东西出不去（毒丸、worker 死在 `claimed`、或者闸门配错了）。第三个查询里那个 `oldest_ms` 是本领域我最希望你带走的一个指标——所有关于「不丢」的自信，最后都会在这里被检验。

## 常见错误与排查

**1. 现象：队列没有积压，但任务完成速度明显变慢，个别任务永不完成。**
原因：毒丸在队头循环。因为每次都被领走（`claimed`）又退回（`ready`），队列长度基本不变。
怎么确认：`SELECT id, attempts FROM jobs ORDER BY attempts DESC LIMIT 5`——有一条 `attempts` 远大于其余，就是它；再看它身后消息的 `created_at` 是否集中在近几分钟。
怎么修：上限 + 死信（M4 第三臂，代价 3 次无用执行、正常 5/5 完成）。**先加去处，再考虑优化重试曲线。**

**2. 现象：一条消息一直重试，但面板显示「失败率 0」。**
原因：你的重试逻辑吞掉了异常（`catch` 里只打日志、不改状态、不写 `reason`），从 worker 角度看是「处理完了」。
怎么确认：`SELECT count(*) FROM jobs WHERE state='ready' AND attempts > 1` 是否长期不为 0；如果 `attempts` 停在 1，那说明连计数都没记，问题更严重。
怎么修：失败必须落成状态。至少要有 `attempts` 自增 + `next_at` 推后 + `reason` 写入三件事；只有日志不算处理过。

**3. 现象：用户在 5 分钟内就完成了支付，仍然在 30 分钟后收到「未支付」提醒。**
原因：到期后直接执行消息里的内容，没有回查当前状态。
怎么确认：看提醒逻辑有没有一条「状态是否仍成立」的判断；或者构造一个「提前完成」的用例跑一遍。
怎么修：延迟消息只当闹钟。到点先查现状（本章那段 `status !== 'unpaid'` 的判断），或让业务写操作能取消未触发的行（`UPDATE ... SET state='done' WHERE state='ready'`，`changes=0` 表示已经触发过）。

**4. 现象：延迟消息在开发机上准点，在生产上晚一大截，且抖动很大。**
原因：轮询间隔太大，或者闸门列没有索引——每次轮询都在扫全表，队列越大越慢。
怎么确认：`EXPLAIN QUERY PLAN SELECT id FROM jobs WHERE state='ready' AND next_at <= ? ORDER BY id LIMIT 1`，看到 `SCAN` 就是没走索引（这个判据与[索引一章](/database/indexes)里那条一致，我在 data-storage 领域实测过 `SCAN` 与 `SEARCH ... USING INDEX` 的分位差）。
怎么修：给 `(state, next_at, id)` 建索引；把轮询间隔按「可接受的延迟精度」定，别两边各配一个不相干的数。

**5. 现象：订单状态被一个旧事件改回去了，而且日志里看不出错。**
原因：多消费者并行处理同一订单的事件，且没有单调条件。
怎么确认：把这条订单的所有事件按 `created_at` 与 `done_at` 两列并排查出来，看 `done_at` 顺序和 `created_at` 顺序是否不一致（M8 里 `2,3,5,6,1,4` 那个形状）。
怎么修：短期兜底用单调条件更新（`WHERE version < ?`，靠 `changes` 判断丢弃）；根治是按 key 分区消费，并确认消费者与分区的对应关系在扩缩容后没有重叠（M8 第四行那个 1 次乱序就是重叠的代价）。

**6. 现象：加了死信队列之后，故障反而更难发现了。**
原因：只做了「搬进死信」，没做「有人看」。死信队列安静地长到 3000 条，没有任何告警。
怎么确认：死信表有没有独立的告警阈值；有没有一个查询能告诉你「最早一条死信等了多久」。
怎么修：死信必须配三件事——一个独立的告警指标、一个能被重放的入口（本章那三条 UPDATE）、以及**每次处理死信都留下处理人**。第三条听起来像流程负担，但它是唯一能让你一年后看懂当年为什么这条被人工做过的东西。

结构与本章 M5 一致：投递时写 `next_at = now() + 30*60*1000`，消费者只取 `state='ready' AND next_at <= now()`。到期回查现状：

```sql
-- (a)(b) 的判据：任务行必须存在且到期时刻正确

UPDATE jobs SET state='done', reason='order paid before due' WHERE kind='pay-reminder' AND biz_key=? AND state='ready';
```

修法一（结构性）：按 `biz_key` 分区，同一订单只由一个消费者串行处理。代价是并行度上限等于 key 的个数——实测 `2 worker 按 key 分区` 那行：375 毫秒、乱序 0，比全并行的 327 毫秒慢约 15%，而比单串行（751 毫秒）快一半。**只有一个订单在动时，分区给不了任何并行。**

修法二（数据层兜底）：单调条件更新。

```sql
UPDATE orders SET status='paid', version=2 WHERE id=7 AND version < 2;
```

创建事件后到时 `changes=0`，直接丢弃。代价：0（并发度不变），但**只能丢弃，不能补做**——如果创建事件本来还要顺带发消息、扣库存，丢弃它就等于丢副作用。这时必须让副作用与状态写同事务（第 3 章 M2 的形状），或者被丢弃的事件也要进一条「已忽略」的记录里供人复核。

## 下一章

本章给了三组可复现的数字：毒丸在「失败立刻回队头」下把重投放大到 41 次、正常消息 0/5 完成，加上限落到 `dead` 之后投放大到 8 次、正常 5/5；延迟闸门在 298 毫秒配置下 355 毫秒被领到，且到期前 6 次轮询全部返回空——**这就是「闹钟写在数据里」与「写在定时器里」的区别**；顺序性那一档用 48 毫秒的代价换来同订单事件不乱，而多塞一个 worker 撞进同一分区时，保序立刻失效（乱序 1 次）。

这三件事共享一个底层事实：**投递次数、执行次数、以及「做成功」是三件不同的事**，你的状态机必须能把它们分开记账。下一章把这个直觉推到它的极限——at-most-once、at-least-once、exactly-once 这三种保证为什么在「不丢」和「不重」之间必然取舍，以及「效果恰好一次」到底是谁的承诺，见[投递语义：不丢、不重与取舍](/message-queue-cloud/delivery-semantics)。
