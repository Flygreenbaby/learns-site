# 生产者、消费者、主题、分区：四个词各自解决哪一个问题

你打开 RabbitMQ 的教程，看到 exchange、queue、binding、routing key 四个词；换到 Kafka 的文档，是 topic、partition、consumer group、offset；再换到 Redis，是 stream、consumer group、pending list。**三套词都在描述同一件事——把活儿从一个进程交给另一个进程——但它们的默认行为不一样，而默认行为才是决定你能不能睡好觉的那部分。**

最常见的误解不是「不懂术语」，而是**以为术语可以互换**。把 Kafka 的 topic 理解成「一个队列」，你会以为消费完就没了；把 RabbitMQ 的 queue 理解成「一个主题」，你会以为多挂几个消费者就能各自收到全量消息。这两处误解的代价都不是文档里的读错，而是线上的重复消费和消息丢失。

这一章只做一件事：**把消息系统的四个动作拆开，说清每个动作在不同模型里由谁负责、什么时候负责。**术语表放在最后，是因为它应该只是这套结构的产物，而不是记忆材料。

再次明确边界：脚本里的「队列」是 SQLite 的一张任务表 + 若干异步循环 / 真子进程，**它是用来演示机制的模型，不是 RabbitMQ、Kafka、Redis Stream 的实现或性能代表**。凡是从真实产品文档里来的结论（默认值、参数名、能力有无），本章一律标为文档依据并注明核实日期；没核实的就不写具体值。

## 四个动作，不是三个

任何消息系统都在做这四件事，把它们分开，术语就不再可怕：

```text
投（publish）    生产者把一条消息交给系统。这一步只保证「交出去了」。
存（persist）    系统把它放在某个能活过进程重启的地方。放在哪、放多久，是产品差异最大的地方。
取（deliver）    消费者拿到这条消息的一份副本。注意：是副本，不是把原对象搬走。
确认（ack）      消费者告诉系统「这条我处理完了，你可以按你的规则处置它」。
```

**「取」和「确认」是两个动作，把它们混成一步是所有可靠性问题的起点。**HTTP 请求没有这个区分——连接断了就是失败了；进程内函数调用也没有——抛异常就是没做成。跨进程交付必须区分「我拿到了」和「我做完了」，因为这两者之间可以夹着一次崩溃。

第 1 章的 M0 实测就是这个夹缝：worker 子进程在「已标完成、副作用还没写」时被杀，与在「副作用已落库、还没确认」时被杀，结果完全不同——前者丢，后者重。

```text
before      崩溃前：done里没副作用=1 条（丢），已领未确认=0 条（可重投）
after       崩溃前：done里没副作用=0 条（丢），已领未确认=1 条（可重投）
```

这四个动作各自在不同产品里叫什么，见本章末尾的对照表。

## 一条消息应该带什么：把身份、载荷、投递历史分开

任务表的真实 DDL（就是脚本里跑的这一份）：

```sql
CREATE TABLE jobs (
  id INTEGER PRIMARY KEY,          -- 消息身份：投递方生成，永不变化
  kind TEXT NOT NULL,              -- 干什么（mail / report / index）
  biz_key TEXT,                    -- 业务对象：哪一笔订单、哪一个用户
  seq INTEGER,                     -- 同一 biz_key 内的序号，顺序性靠它
  state TEXT NOT NULL DEFAULT 'ready',   -- 生命周期：ready / claimed / done / dead
  attempts INTEGER NOT NULL DEFAULT 0,   -- 投递历史：这是第几次尝试
  next_at INTEGER NOT NULL DEFAULT 0,    -- 时间闸门：不到这个时刻不许被取（延迟消息）
  reason TEXT,                             -- 为什么走到这个状态（排查用）
  done_at INTEGER, created_at INTEGER NOT NULL
);

-- 副作用表：自增主键，同一条消息做两次就是两行，「重复」必须是能数出来的东西
CREATE TABLE effects (id INTEGER PRIMARY KEY, job_id INTEGER NOT NULL, made_at INTEGER NOT NULL);

-- 幂等表：主键就是幂等键，插不进去就说明这件事已经做过
CREATE TABLE dedup (mid TEXT PRIMARY KEY, job_id INTEGER NOT NULL, done_at INTEGER NOT NULL);
```

三个必须分清的东西：

- **消息身份（`id`）**：这条投递是哪一个。它在重试中**不变**——同一条消息被投 3 次，`id` 还是那个。
- **业务身份（`biz_key`）**：这件事关于哪笔订单。它在用户重复点击时**不变**——点了 2 次是 2 条消息、同一个 `biz_key`。
- **投递历史（`attempts`、`next_at`、`reason`）**：系统对这条消息做过什么。**这部分绝不能放进业务载荷**，因为载荷是业务语义，重试了 3 次不会让「订单 7 要发货」这句话变。

第 1 章练习里那个「两封欢迎邮件」的坑，本质就是把消息身份当成了幂等键。实测的四臂对照在第 3 章。

这条消息最终死掉时的真实行内容（M3 的输出，原文）：

```json
{ "id": 1, "state": "dead", "attempts": 3, "reason": "max attempts reached" }
```

有这四列，「为什么这封邮件没发出去」是一个查询能回答的问题；没有，它是一次代码走读。

## 竞争消费与发布订阅：一次副作用，还是 N 份拷贝

这是两个**语义完全不同**的模型，大多数「该用队列还是该用总线」的争论其实是没分清这两个词。

同一份 6 条消息，两种模型各跑一遍（原文）：

```text
=== M7 竞争消费 vs 发布订阅（同一份 6 条消息） ===
   竞争消费：三个 worker 分掉 6 条 → A=2 B=2 C=2 副作用总数=6（每条只做一次）
   发布订阅：每条消息给每个订阅者一份拷贝 → audit=6 mail=6 search=6，投递总次数=18（6 条消息 × 3 个订阅者）
```

| | 竞争消费 | 发布订阅 |
| --- | --- | --- |
| 一条消息的命运 | 被某个消费者拿到**一次** | 被每个订阅者各拿**一份** |
| 加消费者的效果 | 分摊同一批工作（吞吐 ↑） | 增加拷贝份数（投递总量 ↑） |
| 适合什么 | 任务分发：发货、生成报表、发信 | 事件通知：审计、缓存失效、索引更新、实时展示 |
| 新增一个下游时你要做什么 | 什么都不用做（它自己来抢） | 新增一个订阅者即可，**生产者一行不改** |
| 典型坑 | 以为「多挂几个就能各收全量」 | 以为「加消费者能加速处理」，结果副作用做了 N 遍 |

`A=2 B=2 C=2` 这三个数字里藏着一个必须知道的限制：竞争消费的分发**不是均分的**，那是这一轮恰好均匀。真实系统里谁快谁抢得多，所以「三个 worker 各处理 2 条」不是配置出来的，是竞争出来的结果。**你不能依赖竞争消费来做「按用户轮流分配」这类需要确定性的路由**——那需要分区（见下一节）。

判断该用哪个只问一句：**这件事的副作用应该发生几次？** 一次 → 竞争消费；每个关心它的模块都要知道 → 发布订阅。两者常常同时存在：「订单已支付」用发布订阅通知多方，其中「扣库存」这一路只有一个消费者组在处理。

这个区别在真实产品上的落法（文档依据，2026-10-19 通过 RabbitMQ 文档入口核对其模型描述，未在本机验证任何代理行为）：RabbitMQ 用一个 exchange 把一条消息路由到多个 queue，每个 queue 内部是竞争消费——**发布订阅与竞争消费是可以在同一张拓扑里叠起来的**；Kafka 的 topic-partition 天生是「多个消费者组各自读到全量、组内按分区分摊」，也就是把这两个模型同时给你。具体到 RabbitMQ 的 exchange 类型名称与各版本配置项，请以官方文档为准，本章不复述参数。

## 队列与日志：消费完是不是就没了

第二个必须分清的模型差异，也是 Kafka 和 RabbitMQ 不是一类东西的根本原因（第 8 章正面讲）。

**摘除式（传统队列）**：确认之后，这条消息从队列里消失。你的「已处理到哪」这个问题没有答案，因为历史被删了。

**游标式（日志）**：消息只追加、不删除；每个消费者自己记一个「我读到第几条了」的游标（offset）。读它不会消耗它，所以**同一段历史可以被重放**。

同一张任务表，两种取法只差一行代码：

```js
// 摘除式：取到就把状态改掉，这条消息对后来的消费者不再可见
const row = db.prepare("SELECT id FROM jobs WHERE state = 'ready' ORDER BY id LIMIT 1").get();
db.prepare("UPDATE jobs SET state='claimed' WHERE id=? AND state='ready'").run(row.id);

// 游标式：不动原行，只推进自己的进度；换个新消费者组从 0 开始能重放全部历史
const cursor = db.prepare('SELECT last_id FROM offsets WHERE grp = ?').get('search-index').last_id;
const rows = db.prepare('SELECT id, payload FROM jobs WHERE id > ? ORDER BY id LIMIT 50').all(cursor);
db.prepare('UPDATE offsets SET last_id = ? WHERE grp = ?').run(rows.at(-1).id, 'search-index');
```

**这两行的差别不是风格，是能力**：

| | 摘除式 | 游标式 |
| --- | --- | --- |
| 新下游上线能不能补历史 | **不能**，消息早被消费走了 | 能，把它的游标设回 0 |
| 消费者挂了怎么恢复 | 靠代理把它没确认的消息重投 | 靠它自己的游标没推进，从游标处继续 |
| 存储会不会自己长大 | 不会（消费即释放） | **会**，必须靠保留策略裁剪（按时间或条数） |
| 积压的度量 | 「队列里还有多少条」 | 「每个消费者组的游标落后多少」（lag） |
| 代价 | 历史不可追，出错难复盘 | 游标与副作用不原子时会重复（第 5 章） |

需要说清的诚实边界：**上面这段游标式代码我在本机没有单独跑出结果**，它是与本章 M7/M8 同一套表结构的另一种读法，用来把「摘除 vs 游标」的差别落到可对照的代码形状上；`offsets` 表是示意。真实代理里 offset 的提交时机、粒度与失败语义以各产品官方文档为准（本站第 5、8 章会分别处理）。

## 分区：并行度从哪来，顺序性又从哪来

如果只有一个队列，你怎么加消费者都不会改变「一条消息只能被一个 worker 拿到」这个事实带来的串行上限。**并行度的来源是分区**：把一个主题切成若干分区，每个分区内部严格有序，分区之间互不相干。

M8 实测四种消费者配置（6 条消息，id 1 与 4 是 250 毫秒的慢活，其余 40 毫秒；两个业务 key A、B，奇数属 A、偶数属 B），原文：

```text
=== M8 顺序性：串行 / 全局并行 / 按 key 分区，四种消费者配置（6 条，其中 id 1 与 4 是 250ms 的慢活，其余 40ms） ===
   单 worker 串行                   完成顺序=1,2,3,4,5,6 总耗时=751ms 同 key 内乱序次数=0
   3 worker 全局并行（不分 key）     完成顺序=2,3,5,6,1,4 总耗时=327ms 同 key 内乱序次数=2
   2 worker 按 key 分区（1 key 1 worker） 完成顺序=2,1,4,3,6,5 总耗时=375ms 同 key 内乱序次数=0
   3 worker 按 key 分区（两个 worker 撞进同一个 key） 完成顺序=2,6,1,4,3,5 总耗时=370ms 同 key 内乱序次数=1
```

这四行来自同一次运行。重跑时墙钟有几十毫秒的抖动（另一次是 730 / 332 / 381 / 377），但**完成顺序的形状和乱序次数没变**——要看的是这个形状，不是那几个毫秒。

四行读数：

1. **串行**是唯一保证全局有序的档位，代价是墙钟最长（751 毫秒）。
2. **全局并行**把 751 压到 327（2.3 倍），代价是同 key 内乱序 2 次。注意 `2,3,5,6,1,4` 这个顺序——慢活排在前面，后到的先完成了，这就是「订单已创建」比「订单已支付」后落地的那种事故。
3. **按 key 分区**：375 毫秒、乱序 0。**并行度的上限就是 key 的个数**：2 个 key 只能开 2 个消费者，第 3 个消费者无事可做。这是分区模型最常被忽略的一条硬约束。
4. **第三档的前提被破坏一次，保序立刻失效**：3 个 worker 映射到 2 个 key 时，两个 worker 撞进了同一个 key（`w % 2` 把 0 号和 2 号都派给了 B），完成顺序变成 `2,6,1,4,3,5`，`6` 排在 `4` 前面 → 乱序 1 次。**保序不是配置出来的性质，是「一个分区同一时刻只有一个消费者」这个不变量的产物**；破坏它的常见时刻是扩容/缩容时的重分配，而真实产品里的重平衡机制本章不描述，见第 8 章并核对官方文档。

这一节和 M9 的语义数字合起来看，你会得到第 4、5 章的骨架：并行与顺序是同一笔预算的两端，而不变量守不住时，语义退化是静默的。

## 生命周期：一条消息的状态机

把这章的概念串成一条消息实际走的路：

```text
        投                取（CAS）            成功
  ┌─────────┐   ┌─────────┐   ┌──────────┐   ┌────────┐
  │ pending │──▶│  ready  │──▶│ claimed  │──▶│  done  │  ← 确认之后才进这里
  └─────────┘   └────┬────┘   └────┬─────┘   └────────┘
       ▲             │ 未到时间     │ 失败
       │ 重投（退避） │ next_at 闸门 │
       │             ▼             ▼
       │        [ 不许被取 ]   retrying ──超过上限──▶ dead / 死信
       └───────────────────────────┘
```

三条要从图上读出来的东西：

- **`ready → claimed` 这一步必须是原子的**。脚本里靠一条带条件的 UPDATE 做比较交换（CAS）：

```js
const claim = (db, due) => {
  const row = db
    .prepare("SELECT id FROM jobs WHERE state = 'ready' AND next_at <= ? ORDER BY id LIMIT 1")
    .get(due ?? now());
  if (!row) return 0;
  const r = db.prepare("UPDATE jobs SET state='claimed', attempts = attempts + 1 WHERE id = ? AND state = 'ready'").run(row.id);
  return r.changes ? row.id : -1; // -1 = 被别人抢先（CAS 失败）
};
```

  先 SELECT 再 UPDATE 是两个动作，两个 worker 可以同时选中同一行。真正的守卫在第二句的 `AND state = 'ready'` 上——`changes` 是 0 就说明被别人抢了，必须放弃这条去取下一条。**「我读到了这行，所以它是我的」是竞争消费里第一号的错误假设。**这个假设的真实代价我实测过：把那句带条件的 UPDATE 换成无条件版本，同一份 6 条消息、同样三个并发消费者，结果是 `投递=18 副作用行数=18 不同 job=6 重复=12`（代码与复现见本章练习 2）。

- **`claimed` 是一个必须能被回收的状态**。worker 死在 `claimed` 上，如果没有恢复扫描，这条消息永远卡在那里。第 1 章 M0 里那行「已领未确认=1 条（可重投）」指的就是它。
- **没有 `dead` 状态的系统，故障是隐形的**。`reason` 那一列存在的唯一理由是：三个月后你要能在不读代码的情况下回答「为什么这条没做完」。

## 术语对照：同一个动作在各家叫什么

**这张表只用于读文档时对号入座，不代表你在本机验证过任何代理。**具体参数名与默认值请以对应产品官方文档当前版本为准，动手前核对（入口链接在文末）。

| 本章的说法 | RabbitMQ | Kafka | Redis Stream |
| --- | --- | --- | --- |
| 投 | publish / `basic.publish` | produce | `XADD` |
| 消息存放的地方 | queue | topic（由 partition 组成） | stream（一个 key，只追加） |
| 路由 | exchange + binding + routing key | partition 选择（常按 key 哈希） | 无路由层，一个 stream 一个目的地 |
| 取 | `basic.deliver`（代理推给消费者） | poll（消费者主动拉） | `XREADGROUP` |
| 确认 | `basic.ack` / `nack` / `reject` | 提交 offset | `XACK` |
| 一组竞争消费者 | 挂同一 queue 的多个 consumer | consumer group | consumer group |
| 单个消费者未确认的消息 | unacked 状态（在 channel 上） | 由 poll 会话与 offset 决定 | pending entries list（PEL） |
| 处理不了的消息去哪 | dead-letter exchange | 自己写到另一个 topic | 自己搬到另一个 stream |

最后一行值得停一下：**「失败的消息去哪」只有 RabbitMQ 给了开箱机制，Kafka 和 Redis 都指望你自己实现。**这不是优劣，是设计重心不同——日志型系统假设你会重放，所以不替你做丢弃后的安置。

## 常见错误与排查

**1. 现象：消息有时候谁都没处理，但队列看起来是空的。**
原因：把「取到了」当成「处理完了」——消费者拿到消息后进程崩了，而系统按取走即删除来记账。
怎么确认：查 `SELECT count(*) FROM jobs WHERE state='claimed'` 是否长期大于 worker 数；真实代理上看 unacked / pending 计数（PEL 长度、Kafka 的 lag 与 in-flight 都要看，不能只看积压）。
怎么修：确认动作放在副作用之后（第 3 章），并且让未确认的消息能被回收（超时重投或认领）。

**2. 现象：加了第二个消费者，同一条消息被处理了两遍。**
原因：你以为挂两个消费者是「加速」，实际上那是一条消息被投递给了两个订阅者——这是发布订阅语义。
怎么确认：`SELECT count(*) FROM effects WHERE job_id = ?`；如果是 2，说明两者是各自一份拷贝而不是竞争。
怎么修：竞争消费要让多个消费者加入**同一组**（RabbitMQ 里挂同一个 queue；Kafka / Redis 里同一个 consumer group）。跨组就是各收全量。

**3. 现象：改了消费者数量之后，出现历史数据被重新处理或某段被跳过。**
原因：把分区当成队列，同时又把 offset / 消费进度存在消费者本地。消费者重分配后，新接手的人用了自己的进度。
怎么确认：比对各分区的进度是不是存在共享的地方；如果进度在消费者内存里，重分配必然丢。
怎么修：进度必须由组共享（真实产品都有组级进度存储），并且**进度的提交与副作用的落库要么原子、要么幂等**（第 5 章的核心命题）。

**4. 现象：某个消费者的耗时正常，但整条链路都在等它。**
原因：一个慢消费者占住了分区，而这个分区里的其他消息（不同业务对象）也在等它——**队头阻塞**在分区模型里的表现。
怎么确认：按分区看 lag，而不是只看总量。只有 1 个分区滞后 = 那个 key 有慢活。
怎么修：把慢的 key 拆出去单独处理，或者提高分区粒度；不要靠「加消费者」解决，分区数不变时加消费者不增加并行度（本章第 3 档 375 毫秒那一行就是它的度量）。

**5. 现象：本地一切正常，到线上消息顺序乱了。**
原因：本地只有一个分区 / 一个 worker，顺序性是靠环境而不是靠设计得来的。
怎么确认：在测试里刻意开两个消费者、把消息带同一个 key 打进去，看是否出现「后到的先完成」（M8 的 `2,3,5,6,1,4` 就是这个形状）。
怎么修：把顺序性要求写成测试，而不是写成文档里的一句话。顺序性怎么保证、代价多大，第 4 章正面讲。

**6. 现象：一条消息的载荷里既有业务字段又有 `retryCount`，业务代码开始读重试次数走不同分支。**
原因：把投递历史塞进了业务载荷。系统的重投策略一改，业务逻辑跟着变。
怎么确认：搜业务代码里对重试次数的引用；如果它有分支，你已经把传输层的偶然事件变成了业务语义。
怎么修：重试信息作为**元数据**（`attempts`、`reason` 这些列/头）传递，载荷只描述「要做什么」。这也是 outbox 表要把消息体和投递状态分列的原因。

<Exercise title="给一张任务表补齐四个动作需要的列" difficulty="基础">

从只有 `id / payload / created_at` 的最小表开始，写出能支持「投、存、取、确认」四个动作的最小表结构，并说明每一列去掉之后会失去什么能力。

<template #answer>

```sql
CREATE TABLE jobs (
  id INTEGER PRIMARY KEY,
  payload TEXT NOT NULL,
  state TEXT NOT NULL DEFAULT 'ready',   -- 去掉：无法区分「没人拿」和「有人正在做」
  attempts INTEGER NOT NULL DEFAULT 0,   -- 去掉：无法限重投上限，毒丸会永远循环（第 4 章 M4）

  reason TEXT,                           -- 去掉：故障不可解释，只能读代码复盘

);
```

关键在 `state` 与 `next_at` 的组合：「不许被取」有两种原因（别人正在做 / 还没到时间），它们都要能被同一条取任务的查询表达出来：

```sql
SELECT id FROM jobs WHERE state = 'ready' AND next_at <= ? ORDER BY id LIMIT 1;
```

这条就是脚本里 `claim()` 用的那条，实测能被两个 worker 同时执行而不重复取到，靠的是随后那句带 `AND state = 'ready'` 的 UPDATE 与 `changes` 检查。

<Exercise title="故意制造一次重复领取，把看到的报错或错误结果解释清楚" difficulty="进阶">

把取任务的代码改成只有 SELECT、去掉那句带条件的 UPDATE（也就是不做 CAS），然后开 3 个并发循环消费 6 条消息，记录 `effects` 表的行数与 `count(DISTINCT job_id)`。

再回答：为什么这个 bug 在单线程测试里永远复现不出来？

<template #answer>

去掉 CAS 后的实测输出（本机 2026-10-19，`node message-queue-cloud/.scratch/mq-core.mjs models` 里的 M7b 段）：


对照带 CAS 的 M7 竞争消费臂：同样三个并发 worker、同样 6 条消息，副作用总数正好是 6，每条只做一次。**同一段数据、同一个并发度，18 与 6 的差别只在那句 `AND state='ready'`。**

为什么单线程测不出来：没有交错就没有竞争。单进程里 SELECT 与 UPDATE 之间不会被别的执行流插入，这个 bug 需要**两个真实的取任务者在时间上重叠**——并发的 worker 循环、多个进程、或者一次重平衡后的短暂重叠。

正确的复现方式（本脚本就是这么做的）：并发跑、把每次副作用写成独立行（`effects` 用自增主键而不是 `job_id` 主键），然后要求「行数等于去重后的数」。如果副作用表以 `job_id` 为主键，重复插入直接被唯一约束挡住，你会误测出「没有重复」——**表结构本身可以掩盖这个 bug**，这是本章最阴的一个坑。

要求：逐条指出它需要竞争消费还是发布订阅、需要摘除式还是游标式，以及哪一条会让你必须重选方案。

<template #answer>

<Exercise title="把 M8 的第四档改造成能稳定保序的配置" difficulty="挑战">

第四档（3 worker 按 key 分区）因为 `w % 2` 的映射让两个 worker 撞进同一个 key，乱序 1 次。给出至少两种修法，并说明每种修法的**并行度上限**由什么决定。

<template #answer>

修法一：让消费者数等于分区数（2 个 worker 各管一个 key）。实测第三档就是这个配置：完成顺序 `2,1,4,3,6,5`，乱序 0，总耗时 375 毫秒。**并行度上限 = key 的个数 = 2**；即使你有 8 核也只跑 2 路。

修法二：把 key 拆细，让分区数追上你需要的并行度。比如按 `biz_key + 哈希到 N 个分区`，同一个实体的事件永远落进同一个分区（保序），而不同实体散开（并行）。**并行度上限 = 分区数**，所以分区数是你为「保序粒度」和「吞吐」定价的那个旋钮。

修法三（工程上最常见）：分区数固定且大于消费者数，让消费者在重平衡时各自领若干个分区。**这时不变量变成「一个分区同一时刻只属于组里一个消费者」**——Redis Stream 的消费者组与 Kafka 的消费者组都靠这条不变量提供分区内有序，各自的重平衡机制本站不在这里描述，动手前核对官方文档（见文末链接）。

诚实的补充：修法二/三在这个脚本里都只需要改分区分配函数，但**真实代理的重平衡窗口内可能出现两个消费者短暂同持一个分区**，那会带来重复或乱序——这个风险不能靠本章的模拟排除，它是第 5 章「为什么必须幂等」的一部分理由。

</template>
