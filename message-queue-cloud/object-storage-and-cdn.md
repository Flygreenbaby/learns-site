# 云服务基础：对象存储与 CDN：桶不是目录树，CDN 不替你决定「什么时候算新」

第一条事故线：一个 VPS 上的应用，头像和附件都存在项目目录里。某天磁盘写满，`df` 一看，`/` 用了 97%——里面 20 GB 是用户三年攒下的上传文件，而你的备份脚本把整个项目目录 `tar` 了一份，所以备份盘也在同一天写满。真正致命的不是空间，是那台机器再也起不来了：你加了一台新机器部署，用户头像全 404，因为**文件不是「应用的输出」，是你唯一没有备份的输入**。

第二条正好相反。你把文件挪进对象存储，勾选了「公有读」，页面一切正常。两个月后账单里的外网下行流量是平时的四十倍——有人写了个脚本，按 `列表接口能返回的顺序` 把你的桶整个拉了一遍，而桶是公读的，一个请求都没被拒。对象存储没有「目录列不出来」这层保护，只要前缀可猜、权限放开，它就是可枚举的。

第三条是 CDN。接完之后用户还是说「图片没换」，你手动刷新缓存，五分钟后再看还有一批人是旧的；而你的接口日志里，来源 IP 全部变成了同一个网段的十几个地址，你按 IP 做的限流一夜之间把所有用户限死了——因为**站在你面前的不再是用户，是边缘节点**。

这三条事故的共同点：它们都不是「云产品不好用」，而是**文件搬出你的进程之后，四条边界同时变了**——数据的语义变了（桶不是目录）、访问面变了（谁能读、怎么读）、时间的语义变了（什么算最新版本）、账单的构成变了。这一章把这四条边界讲清。至于是哪家厂商、控制台在哪个二级菜单、单价多少钱，本章一律不写：本机没有云账号，写了就是编造。

## 文件住在哪：先看清四种位置各自欠什么

同一个「用户上传的头像」，可以有四种放法。它们的区别不是「贵不贵」，是**扩容、故障和备份这三件事分别落在谁身上**。

| 放法 | 谁把文件发给用户 | 多实例时 | 备份是什么 | 被刷时谁吃亏 |
| --- | --- | --- | --- | --- |
| 应用所在磁盘（项目目录里） | 你的应用进程 | **不成立**：两台机器的目录是两份文件 | 常被漏掉（「备份代码」不等于备份数据） | 你的进程：内存、带宽、磁盘 IO 全在你身上 |
| 独立挂载盘（云厂商的块存储） | 你的应用进程 | 多数形态不能同时挂给两台读写，仍不成立 | 要你自己做快照策略并验证能恢复 | 同上，只是磁盘容量与 IO 变成分开的一项 |
| 对象存储桶 | 存储服务（或它前面的 CDN） | 成立：桶是共享的，与你的实例数量无关 | 版本控制 + 跨区域复制或导出任务，仍要验证 | 账单：出网流量按量计费，被刷等于被扣钱 |
| 对象存储 + CDN | 边缘节点 | 成立 | 同上 | 两层都可能吃亏：CDN 挡掉的部分帮你省，挡不住的回源照样花钱 |

第三行是这一章的核心结论：**只要你打算跑第二个实例，「文件放本地磁盘」这个选项就自动作废了**。[后端开发](/backend/uploads-and-jobs)里已经讲过怎么收文件，[部署到 VPS](/devops/deploy-to-vps)讲过怎么把一台机器跑起来；把它们拼起来的那一刻，你必然撞上「状态在哪」这个问题。上传文件放桶，是把应用变成无状态的第一块拼图——另一块是会话与缓存，见[数据存储进阶](/data-storage/session-rate-limit-idempotency)。

## 桶不是目录树：四条语义决定了你能拿它做什么

对象存储的接口只有三个动作的变体：放一个对象、取一个对象、按前缀列一批对象。从这里推出四条规则，它们和文件系统不一样，也决定了「什么不该放桶里」。

| 你以为的 | 桶的实际行为 | 后果 |
| --- | --- | --- |
| 目录 = 一层容器 | `key` 是一个扁平字符串，`a/b/c.png` 里的 `/` 只是字符 | 「文件夹改名」是逐个对象复制再删原对象，量大时不是一次操作，也不会原子完成 |
| 可以在文件末尾追加 | 一次 `PUT` 写入一个完整对象；分段上传是「先传碎片、最后合并成一个对象」，不是追加 | 实时增长的日志不适合直接写对象；要么本地攒够再传，要么用别的服务 |
| 覆盖写和改权限类似 | 后写覆盖先写（旧内容可能以版本形式存在，取决于是否开了版本控制） | 「同名的图片永远不变」这个假设不成立；要不变就得靠内容寻址命名 |
| 能锁文件、能给可执行位、能 `rename` | 没有 POSIX 语义、没有文件锁、没有权限位 | 数据库的数据目录、Git 工作区、需要随机读写的文件——都不该放桶里 |

第四条最值钱，因为它替你排掉了一批「看起来能省钱」的方案：把 SQLite 数据库文件放桶里、把构建缓存放桶里、把需要 `rename` 语义的临时目录放桶里，都是把对象存储当文件系统用，最后要么坏要么慢。桶擅长的是「一次写完、反复整读、按 key 定位」的东西：图片、附件、导出的报表、备份归档、前端构建产物。

关于「列」还有两点必须自己核对：列表接口通常有单次返回条数上限、按 key 字典序返回、要靠上一页返回的标记继续翻，所以「一个前缀下几百万个对象」的遍历是你自己的责任；而**列不出来的前缀不等于不存在**，这也是公读桶被枚举的前提。

## 只增不减：版本、生命周期与「谁负责删」

桶的默认物理规律是**只增不减**：写入不会触发任何删除，读取不会触发任何清理。所以三年的头像就是三年的存储费，加上版本控制之后可能变成六年的量。三种控制手段，各自解决不同的问题：

- **版本控制**解决「覆盖写和误删」：旧版本还在，能回滚。代价是每个版本都算存储量，而它**不是备份**——桶被删空的脚本同样会带走版本（各家的删除保护、保留策略与解锁条件不同，属厂商私有语义，必须核对）。
- **生命周期规则**解决「只增不减」：按前缀或标签匹配对象，按「创建后多少天」执行转储、降级或删除，也常能单独设置「非当前版本保留多久」。没写规则，就等于决定不删。
- **不可变/保留锁**类能力解决「合规上不能删」，是反方向的需求；不是个人项目的默认选项，用到时先看条款能不能真的做到，再看厂商能不能做到。

判断该开哪个，问一句就够：**这份数据如果永远不删，三年后的账单和恢复时间能不能接受**。头像原图可以（转储到更少访问的存储类型即可），导出报表和临时文件不行（直接过期删除），备份归档两者都要（保留 + 定期验证能恢复）。备份的验证方法在[备份与恢复](/database/backup-and-restore)里讲过同一套原则：**没恢复过的备份不是备份**，桶里的备份也一样要真恢复一次。

## 访问面：谁能读、谁能写，以及公读桶那两个月

读写两侧各有两三种做法，选错主要出在读取侧。

**读**有三档：整桶公读、单个对象公读、私有 + 带有效期的签名 URL。签名 URL 的服务端语义（它签的是什么、过期后是什么表现）在[数据存储那章](/data-storage/object-storage-and-cdn)有实测；这里只补云服务视角的两条判断：一是**粒度**，公读把「知道 key」变成唯一的门槛，私有 + 签名让有效期成为你的控制权，代价是链接不能长期外发（贴在文章里的永久链接做不到）；二是**混合方案是常态**——头像和封面公读、原始文件和发票私有，用两套前缀切开，而不是给整个桶设一个权限。最常见的事故就是为了让一个页面显示图片，把整桶设成公读。

**写**有三档：后端代传（文件过你的进程一次，实现简单，代价见[后端：文件上传、定时任务与后台作业](/backend/uploads-and-jobs)）、预签名直传（浏览器直接传给存储，你的后端只签一张条，那章已讲清换来什么、丢掉什么）、表单类直传（限制条件写在签名里）。选直传时有一条与厂商无关的前置：**跨源**。浏览器从你的页面所在域名去请求另一个域名的存储，需要存储侧配置允许这个源的 `PUT`/`POST` 以及暴露必要的响应头，配错的表现是控制台里一条跨源错误、网络面板里请求「存在但失败」。**直传失败先查跨源配置和签名有效期，再怀疑桶权限。**

还有一条常被忽略的写侧风险：**上传文件的类型判定不会因为换了存储就自动变安全**。桶不会替你检查内容、不会替你重编码、不会替你限制大小，那三件事的判断标准在后端那章。挪进桶只是把「存」搬走了，「收」的校验还是你的。

## S3 兼容：为什么「能不能换厂商」在这里有技术答案

对象存储是唯一一个**接口比产品更稳定**的云能力。多家云厂商的文档把自己的兼容实现描述为「S3 兼容」，开源实现也以此为基本定位——这意味着三件很实际的事：绝大多数语言的客户端库、备份工具、命令行工具都能指向任意一个实现；自托管与云服务之间可以互换；迁移时代码里主要改的是访问端点与密钥，而不是数据读写逻辑。

这是本章唯一带强可核实性的判断，它对「自托管 vs 云服务」的意义直接接[第 13 章](/message-queue-cloud/self-host-vs-cloud)：**能被兼容层接住的能力，锁定天然弱**。

但兼容只覆盖「对象读写」这一层。真正会产生锁定的，是你顺手用了只有它有的那部分——生命周期规则的表达能力、事件通知的消息格式（这一项对本领域特别重要：存储事件触发后台任务是常见架构，格式各家私有，换厂商等于重写消费端）、权限策略语言、跨区域复制、图片处理类的服务端变换。判断方法一句话：**把厂商私有 API 的调用行数除以总代码行数**。接近 0，你随时能搬；每处业务逻辑都要问「这个特性哪家也有」，你就已经在锁定里了。

## CDN 站在链路哪一段：命中、回源，以及「刷新」到底刷新了什么

先把请求路径画清楚，后面每个结论都能从这张图推出来。

```text
用户
  ↓ DNS 解析（你的域名指向 CNAME，实际把用户带到离他较近的边缘节点）
边缘节点
  ├─ 命中：直接返回缓存副本，你的服务完全不知道这次请求发生过
  └─ 未命中：向源站取 → 源站（对象存储桶，或你的服务器）→ 返回给用户，并在边缘留存一份
              这一段叫「回源」，消耗的是源站的出口带宽与请求次数
```

四条由此可推的判断：

**命中率同时是性能变量和账单变量。** 命中的请求用户拿到的是边缘的快响应、你一分钱源站流量不付；未命中的请求用户等一次回源、你付一次源站的出口流量。而命中率不是配置出来的，是 URL 设计出来的——同一个内容被打成不同 URL，每个 URL 各自缓存一份，收益归零。**带随机查询参数的 URL 等于关掉 CDN**，这一层的缓存键规则、`Vary` 拆碎的实际后果，[数据存储那章](/data-storage/object-storage-and-cdn)用本机服务实测过，结论在云产品上同样成立。

**「刷新」和「预热」是两件事，都不能当兜底。** 刷新是让边缘丢掉已有副本（下一次请求被迫回源），预热是让边缘提前回源一次。两者生效到全部节点的时间通常没有保证，节点数量大或缓存层级多时你会观察到「一部分人新、一部分人旧」——这不是故障，是分布式缓存的物理表现。让内容「一定是新的」的正确手段是**换 URL**（内容寻址命名），不是刷缓存。

**证书要装在 CDN 上。** 域名指向边缘后，TLS 握手是和你选的终止点完成的：没配好这一层，浏览器告警的是你的域名，而你能改的只有 CDN 侧的配置。域名解析、放行、监听、证书这四层怎么逐层验证，[部署到 VPS](/devops/deploy-to-vps)有完整的排查顺序，接 CDN 之后那套顺序仍然适用，只是多了一跳。

**接了 CDN，日志里的客户端 IP 就变了。** 你会看到大量边缘节点的地址，于是按 IP 的限流、封禁、风控全部失真。解法是让源站从请求头里取真实客户端地址再记录——但**这个头只能在你确认请求确实来自 CDN 之后才能信**，否则任何人都能伪造它来绕过你的封禁。各家的头名与取法不同，属必须核对项，本章不写名字。

## 要不要上 CDN：四条判据，其中一条通常是否决项

值得上的信号：用户分散在多个地域或跨国；资源是静态的、能被内容寻址命名、因此命中率高；你的成本结构里源站出口流量是明显的一项（构成项与低估原因在[那一章](/data-storage/object-storage-and-cdn)已列，单价请以价格页为准）；或者你的源站带宽本身很小，需要有人替你挡第一层。

不值得上的信号，按杀伤力排序：**内容主要是动态且每用户不同**（命中率低时你只是在自己的响应路径前面插了一跳）；**你还没解决命名与缓存键**（先修 URL 再谈加速，否则接完只会多一个「刷新了但不生效」的排障项）；**用户就在一个城市、量也小**（收益是几十毫秒，代价是失效不可控与调试链路变长）；**你还没上 HTTPS**（先把证书做对，那才是真问题）。

还有一类与厂商无关的额外前置：在某些地区，对境内用户做加速分发会牵涉域名与备案层面的要求，各厂商流程不同、政策会变，落地前以你所选厂商与主管部门的现行要求为准，不要照抄本站或任何博客的步骤。

## 自托管对照：MinIO 与「一台 VPS 的磁盘」各自欠什么

三条路的真实账本要算四笔，而不是只看月费。

| | 云对象存储桶 | 自托管 MinIO（S3 兼容） | VPS 磁盘 + Nginx 直发 |
| --- | --- | --- | --- |
| 你要运维什么 | 权限、生命周期、账单告警 | 上面这些 **加**：安装升级、磁盘与扩容、副本或纠删码、备份恢复、证书、进程守护 | 上面这些 **加**：容量、发文件的内存代价、目录共享问题 |
| 多实例共享 | 天然成立 | 成立（一个集群，多个应用连它） | 不成立，需要额外方案 |
| 被刷时的暴露面 | 按量账单，需自己设告警与访问面 | 你的带宽上限被打满，邻居是你自己的服务 | 同左，且直接影响你的应用延迟 |
| 换厂商成本 | 低（兼容层）+ 私有特性部分 | 与桶之间基本只是端点与密钥 | 高：文件迁移要重新设计访问方式 |

选自托管 MinIO 的真实理由通常不是「省钱」，而是这三条：数据必须留在你自己控制的位置、需要在无外网的内网环境跑、或者你要在本地开发里得到一个和线上同语义的存储（这一点很值钱：本地有一个 S3 兼容端点，跨源、签名、前缀这些坑能在开发阶段暴露）。它付出的代价也很具体：**存储故障从「打一个工单」变成「你凌晨起来看磁盘」**，而副本、坏盘、扩容这些运维知识是必须真会的，不是装上就有。

选「VPS 磁盘 + Nginx 直发」只在一种情况下是最优解：文件量小、增长可预测、你只跑一台机器、并且**你有明确的备份计划并且演练过恢复**。发文件本身的内存与带宽代价是能被量化的，那部分实测在[数据存储那章](/data-storage/object-storage-and-cdn)——它给出的判据是「要不要让这个进程来发」，而不是「要不要上云」。

## 常见错误与排查

1. **为了让一张图显示，把整桶设为公读。** 症状：账单里外网流量异常，或有人反馈能猜到别人的文件名。确认：把桶权限收回后用签名 URL 试同一张图能不能显示；用列表接口在你的本地权限下试能不能枚举。判据：换个不相干的文件名去请求，应该失败。
2. **把需要修改或随机读写的东西放桶里。** 症状：数据库损坏、日志要重写整个对象、改名脚本跑半小时还留了一半。这是语义错配，不是性能调优问题——回到上面那张四条语义表重选位置。
3. **开了版本控制却不清理旧版本。** 症状：存储量莫名翻倍。确认：按前缀统计各版本数量与占用；判据：设置「非当前版本保留 N 天」后，账单项在下一个周期回落。
4. **接 CDN 后日志与限流失真。** 症状：来源 IP 集中在少数网段，误封误限。确认：取到的客户端地址是否与用户实际网络相符，且只在确认请求来自 CDN 的前提下采信。
5. **用随机查询参数「强制刷新」。** 症状：命中率掉到接近 0、回源请求数几乎等于用户请求数。正确做法是内容寻址命名；缓存键那层的规则见[实测那章](/data-storage/object-storage-and-cdn)。
6. **直传失败先怀疑桶。** 排查顺序固定四问：跨源配置允许这个源和这个方法吗；签名过期或时钟偏差多少；方法名（`PUT`/`POST`）与签名时约定一致吗；桶或前缀权限真的给了写吗。四问按序做，多数情况第一问就有答案。

<Exercise title="五种文件各放哪：位置、发送方与清理规则" difficulty="基础">

一个跑在单台 VPS 上的小产品有这些文件：(a) 用户头像，约 2 万个，公开可见；(b) 用户上传的原始素材（发票、合同），只有本人可读；(c) 后台任务生成的导出报表，用户下载后即失去价值；(d) 应用日志，每天约 200 MB，只偶尔回看；(e) 前端构建产物，每次发版一批新文件。

请为每一项回答：放在应用磁盘还是桶；由谁发给用户（应用进程、存储直出、还是存储加 CDN）；是否要公读；有没有清理规则；以及「再跑一个实例」时它会不会成为障碍。

<template #answer>

关键判据是**增长是否可预测、访问是否需要授权、多实例是否共享**。

(a) 头像进桶、公读、按内容或 ID 命名，前缀与私有文件切开；(b) 原始素材进桶但私有，读取走带有效期的签名 URL，绝不能为了显示方便设公读；(c) 报表进桶并设「创建后 N 天删除」的清理规则，因为它有价值的时间只有一次下载；(d) 日志不适合「每次追加就重写整个对象」，正确做法是本地按时间滚动、攒够一段再整体上传（或直接交给日志服务），并保留期与清理；(e) 构建产物进桶或静态托管并挂 CDN，靠**文件名里带内容哈希**让它天生可长期缓存。

(a)(b)(c)(e) 放进桶之后，「再加一个实例」就不再是障碍；(d) 若继续留在本地磁盘，就是新实例各有一份日志、你查不到全量的原因。最后一项容易被忽略：只要你想跑第二个实例，(a)(b) 留在本地磁盘的方案就直接作废。

<Exercise title="三条事故记录：定位到语义、访问面还是 CDN" difficulty="进阶">

以下三段来自同一个产品的三个月，各自判断问题在哪一层、用什么确认、判据是什么。注意：本领域常见的错误是把这三层混成「云存储有问题」。

```text
记录 1  某月流量费是上月 41 倍。访问日志显示大量请求命中不同前缀下的图片，
        每个 key 只请求一次，来源 IP 集中且请求间隔均匀。
记录 2  运营改了 banner 图，文件名不变。自己无痕窗口看到新图，同事那边还是旧图。
        刷新缓存后一半用户新了一半还是旧的。
记录 3  前端直传素材，浏览器控制台一条跨源相关报错，网络面板里请求有响应但被拒。
        同一份签名换成后端代传就能成功。
```

<template #answer>

**记录 1 在访问面层**：均匀间隔、每 key 一次、IP 集中，是被枚举抓取的形状而不是真实用户行为——公读加上前缀可猜就等于可枚举。确认方式：用你自己的凭据按同样的前缀调列表接口，看能不能拿到那批 key。判据：桶权限收回后，同一脚本的批量请求应当失败；同时加流量与请求数告警，因为「事后从账单发现」不是防护。

**记录 2 在命名与时间语义层**：文件名不变而内容变了，就要求所有缓存层都被通知到，而边缘节点数量多时刷新到全部节点的时间没有保证——所以「一部分新一部分旧」是预期行为。确认方式：看响应里表示缓存命中与来源的头部（各产品字段名不同，需核对文档），对比新旧用户拿到的是哪一份。判据：改成文件名带内容哈希、URL 随内容变，新链接天然没有旧副本，问题一次性消失，且不再需要靠刷新兜底。缓存键与 `Vary` 那层的实测结论见[数据存储那章](/data-storage/object-storage-and-cdn)。

**记录 3 在跨源配置层**：后端代传成功证明桶权限与签名本身没问题，差别只在于「请求由浏览器跨源发出」。确认方式：核对存储侧允许的源、允许的方法、以及是否暴露了浏览器需要的响应头。判据：把允许的源精确加到你的页面域名后，同一份预签名 URL 能传成功——仍然不要放宽成允许任意源。

三题的共同方法：**先判断问题属于语义、访问面、时间语义还是网络配置，再去翻对应那一层的文档**。直接怀疑「产品不行」会让你在四份文档之间来回浪费半天。

</template>

</Exercise>

<Exercise title="设计：分享链接有有效期的素材站" difficulty="挑战">

你要做一个小工具：用户上传设计稿（原始文件私有），系统生成若干预览图，用户可以把预览图的链接分享给别人，**链接必须能设 7 天或 30 天有效期，也能提前手动失效**。同时你希望将来能把存储从当前厂商换掉而不重写业务代码。

请给出：桶与前缀怎么切；对象命名规则；三种读取分别用什么方式（公读 / 签名 / 经过你的服务）；预览图的生成时机放在哪里（同步还是异步，并说明理由，可参考[为什么需要异步解耦](/message-queue-cloud/why-async)与[可靠投递](/message-queue-cloud/reliable-delivery)）；「提前失效」在物理上怎么做到；生命周期规则怎么写；以及三条「必须回到厂商文档核对、本站不能替你做决定」的点。

<template #answer>

一个可辩护的方案：**一个桶、三个前缀**（`raw/` 私有、`preview/` 私有、`share/` 结构另议），或用两个桶把「公开面」物理隔离——后者更稳，因为权限设置的作用域就是桶，误操作的爆炸半径小。命名一律带内容哈希，让预览图可长期缓存，同时让「同一份内容、不同分享」和「内容更新」都能被 URL 表达。

读取分三种：原始文件永远不公开，本人读取走签名 URL；预览图给分享者时**不要让分享链接等于对象地址**——让链接指向你的服务，服务校验 token 的有效期与是否被撤销后再给出一个短时效的签名地址。原因很直接：如果分享链接就是对象的公读地址，「提前失效」在物理上做不到，你只能等缓存过期。失效的实现因此是**你的元数据表里那个 token 状态**，而不是删除对象；删除只用于清理。这一条是本设计题的核心判据：**能不能撤销，取决于控制点是不是在你手里**。

预览图生成必须异步：原图可能很大，同步转换会把请求链路拖长并让失败影响上传本身（这正是[第 1 章](/message-queue-cloud/why-async)的动机）。上传成功后落一条待处理记录并发消息，worker 负责转换、写回 `preview/`、更新状态；转换失败重试有上限后进死信，用户侧表现为「预览还没生成」而不是「上传失败」——语义参考[死信队列、延迟消息与顺序性](/message-queue-cloud/dlq-delay-order)。清理写两条：原始文件按「用户删除即清理 + 长期不活跃转储」；临时分享对象按创建天数过期，避免只增不减。

三条必须自己核对、本站不能替你决定的：签名 URL 的最长有效期与是否支持主动撤销（各家差异大，直接影响上面的设计是否成立）；跨源与直传的允许项怎么配、签名对 HTTP 方法的约束叫什么；生命周期规则的匹配能力（按前缀还是标签、能表达哪些条件、执行延迟多久）与图片处理类服务端变换是不是私有 API——最后这项决定你换厂商时要不要自带一层转换 worker。

会被反驳的地方也应写明：让所有读取都过你的服务，等于把带宽与延迟重新请回进程，与本章「别让应用进程发文件」的结论冲突。所以取舍点是**只让「需要撤销的入口」过服务，实际文件字节交给短时效签名或边缘**——这也是本设计里唯一需要认真权衡的一刀。

</template>

</Exercise>
