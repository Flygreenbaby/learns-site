# 阶段项目：把慢操作异步化：这一章不给你数字，只保证你测出来的数字能拿去做决定

先说三个真实的翻车形状，它们都是这个项目的验收点被跳过之后发生的。

第一个：某人把「注册后发欢迎邮件」改成异步，改造完在 README 里写「接口延迟从 1300ms 降到 20ms，提升 65 倍」。三个月后他才发现那 65 倍里有 60 倍是他自己造出来的——改造前的数字是压测机上并发打到 200 时取的 p95，改造后的数字是他本地单请求手工点几次取的 p50。两个数根本不在同一个口径上，而真正的结论（慢操作从主链路里拿走之后，长尾不再决定接口延迟）本来不需要造假就能讲清楚。

第二个：异步化上线两周，用户投诉「收不到欢迎邮件」。查下去发现 worker 半夜 OOM 被杀，消息堆积了两千条，而系统的唯一信号是「接口成功率 100%」——因为主链路确实全程正常，坏掉的是没人盯的那一半。**把慢操作扔出主链路，不等于把它扔出了你的责任范围**；它只是把故障从「用户立刻骂你」变成了「你三天后自己发现」。

第三个：有人为了「保证不丢」，在消费者里写了「先查一下有没有发过，再发」。重复投递一来，两封邮件照样发出去了——因为两条投递在几毫秒内同时到达，两次「查」都读到「没发过」。这是[第 3 章](/message-queue-cloud/reliable-delivery)钉过的先查后写窗口，本项目里它会以真金白银的形式回来找你（一封邮件是一次真实的厂商调用，可能要钱）。

这个项目要做的，就是把上面三件事变成你亲手做过、亲手验证过、并且能写出结论的一次改造。

## 目标与范围

**一句话目标**：从前面的产品里挑一个又慢又非核心的副作用（注册后发欢迎邮件、下单后生成报表、发布后通知一批人），把它从请求主链路里拿走，改成由独立进程通过消息队列处理，并且证明四件事：主链路确实快了、消息确实没丢、重复确实没造成重复副作用、失败确实有地方可查。

交付物：一个能一键起的 Compose 编排、一段带幂等与确认的生产/消费者代码、五组故障注入记录、一张改造前后的延迟对照表、一页纸的「值不值得」结论。

**明确不做什么**（这一栏不是客套，是这个项目最容易越界的地方）：

- 不引入 Kafka，不做多集群、不做镜像队列、不谈跨可用区。你现在的量不需要（判据见[第 9 章](/message-queue-cloud/choosing)与[第 13 章](/message-queue-cloud/self-host-vs-cloud)）。
- 不做微服务拆分。worker 是一个独立进程，不是一个新架构。
- 不上云、不用 Serverless 承载 worker。云上的取舍是[第 12 章](/message-queue-cloud/serverless-and-cloud-services)的判断，不是本项目的验收项。
- 不做「通用任务平台」。你只需要跑这一类任务。

**挑哪一段来做**，三条入选判据：它在主链路上（现在正被用户等）、它可以晚几秒到几分钟、它失败时不需要回滚主业务。两条否决：它是鉴权/支付/写库这类必须马上有结果的操作；或者它慢但是**它的结果就是接口要返回的内容**——那不是异步化，那是换需求。**如果这三条判据你一条都对不上，那这个项目对你就不该做**，正确结论是「我当前没有该异步化的东西」，这同样是合格交付。动机层面的判断方法在[第 1 章](/message-queue-cloud/why-async)。

## 目录结构与进程拓扑

```text
app/                      现有后端
  src/
    jobs/
      outbox.ts           业务事务里写一条待投递记录
      publish-worker.ts   把 outbox 里的记录投进队列（可选，见阶段 1）
  src/plugins/notify.ts   唯一允许调用发信厂商的模块
worker/                   独立进程，不在 app 里
  src/index.ts            订阅、拉取、调用 handler、ack/nack
  src/handlers/welcome.ts 具体副作用
  src/idempotency.ts      幂等表读写
infra/
  compose.yaml            app + 队列 + worker + 数据库
sql/
  001_outbox.sql
  002_idempotency.sql
scripts/
  fault-kill.mjs          故障注入：在指定时刻杀掉 worker
  dup-publish.mjs         故障注入：把同一条消息投两次
docs/
  before-after.md         延迟对照表（阶段 0 建表，阶段 4 填完）
  decision.md             值不值得：一页纸结论
```

「谁在哪个进程里」这张表比代码更重要，因为它决定了故障半径：

| 东西 | 在哪个进程 | 它挂了会怎样 | 谁负责重启它 |
| --- | --- | --- | --- |
| HTTP 请求处理 | app | 用户直接看到错误 | 编排层 |
| 投消息 | app（或 outbox 搬运进程） | 消息暂留在数据库里，不丢 | 编排层 |
| 消费与执行副作用 | worker | 消息不丢，积压开始增长 | 编排层 + 积压告警 |
| 队列本体 | 队列容器 | 生产与消费都失败 | 编排层；数据是否丢取决于持久化 |
| 幂等表 | 数据库 | 副作用可能重复 | 数据库备份策略 |

**为什么 worker 必须是独立进程而不是 `setTimeout`**：进程内异步不解决任何一件事——它不抗重启（进程没了任务就没了）、不隔离资源（同一份内存里长任务会挤死请求处理）、不能单独扩（你只能整体复制应用）。这条论证在[第 1 章](/message-queue-cloud/why-async)，[后端作业的落法](/backend/uploads-and-jobs)给了进程内的边界在哪。

## 阶段 0：改造前先量基线（跳过这步，整个项目作废）

这一步不写任何队列代码。这一步的唯一产出是一张**空表**和一段**测量口径定义**，两者必须在改造前就写好。

### 先把六个定义钉死

1. **测哪一段**：从服务端收到请求开始，到**响应写完**为止。不是数据库那段，不是加个平均的前端时间。
2. **谁在等**：用户在等的是「请求返回」；异步化之后没人等的是「副作用完成」。这两个必须分开报（见下面第 5 条）。
3. **统计量**：p50、p95、p99 加最大值，四个都要。**不许报平均值**——副作用有长尾时，平均值告诉你的是「大多数时候没事」，而事故都发生在尾巴上。
4. **样本量与时间窗**：改造前后各取**同一星期、同一小时段、同样的流量形状**，样本不少于 1,000 次请求。拿「改造前本地手点五次」对「改造后压测两小时」是最常见的作弊，往往不是故意的。
5. **两个延迟都要报**：请求延迟（用户视角，异步化后必然下降）与副作用完成延迟（业务视角，异步化后**必然上升**，因为多了一段排队）。只报前者就是营销。
6. **错误口径**：分别记「用户可见失败」与「副作用最终失败」。异步化会把第一类降下去，如果你没盯第二类，你只是把失败藏起来了。

### 一个可以在现有环境做的机制模型

不需要中间件，你就能看清「为什么长尾会决定你的 p99」和「积压什么时候排不完」。下面是本站跑过的模型（参数：数据库 12+0–8ms；入队 0.4+0–6ms；发信 900+0–700ms，其中 5% 追加 4,000ms、3% 可重试失败；同步路径失败重试 1 次；消费者单条 250ms；常态到达 8 条/秒，第 30–45 秒峰值 60 条/秒；观测窗 180 秒；重复投递率 18%，其中四分之一并发到达；永久失败率 1.5%，重试上限 5）：

```text
=== A 主链路延迟（ms，模拟 2000 次请求）===
同步串联       p50=1295.4 p95=1845.1 p99=5407.2 max=6135.7
异步拆分       p50=16.8   p95=20.3   p99=20.7   max=20.9
用户可见失败：同步 2 / 2000（0.10%），异步 0 / 2000
p95 降幅：90.8 倍；p50 降幅：77.2 倍

=== B 积压与排空（服务时间 250ms/条）===
worker=1 能力=4/s 峰值积压=1500 条 未排空，结束剩 1500 条，最新一条已等待约 375.0s
worker=2 能力=8/s 峰值积压=780 条 未排空，结束剩 780 条，最新一条已等待约 97.5s
worker=4 能力=16/s 峰值积压=660 条 排空于第 127s
worker=8 能力=32/s 峰值积压=420 条 排空于第 62s

=== C 重复投递（模拟 2000 条业务消息，18% 遭遇重复投递）===
策略=none                处理次数=2350 副作用次数=2350 多做的=350
策略=select_then_update  处理次数=2350 副作用次数=2089 多做的=89
策略=unique_key          处理次数=2350 副作用次数=2000 多做的=0

=== D 重试上限与死信（模拟 4000 条，毒药消息比例 0.015）===
上限=null  死信队列=否 总投递=3953 毒药=47 进死信=0 空转后被放弃的投递=0 到窗口结束仍未终止=47
上限=5     死信队列=否 总投递=4264 毒药=66 进死信=0 空转后被放弃的投递=330 到窗口结束仍未终止=0
上限=5     死信队列=是 总投递=4200 毒药=50 进死信=50 空转后被放弃的投递=0 到窗口结束仍未终止=0
```

这四组数字里只有三句话值得记住，而且全都是**结构性**的：

第一句，A 组：同步串联的 p99 是 5,407ms，而它的中位数只有 1,295ms。**决定你 p99 的从来不是慢操作的平均耗时，是它的长尾比例**。异步拆分后 p99 只有 20.7ms，不是因为变快了，是因为那条长尾被从「用户在等」的那段路径里挪走了。挪到哪儿，见 B。

第二句，B 组：能力必须**大于**峰值到达率，否则积压永远排不完。4 条/秒的单个 worker 面对 60 条/秒的 15 秒峰值，180 秒观测窗结束时还剩 1,500 条、最新一条已经等了 375 秒——**这就是表二里那个「副作用完成延迟」的来源**。把 worker 从 1 加到 2，积压只从 1,500 降到 780 且仍然排不完；加到 4 才在 127 秒排空。异步化不是免费的，它把「等待」从用户身上转移到队列里，而**队列里的等待会以更难看的形式在某个时刻回来找你**。

第三句，C 组：「先查后写」在 2,000 条里仍然多做了 89 次副作用（无幂等时是 350 次）。原因不是查询写错了，而是两次投递都在对方写下来之前读到了「没做过」。**这条 89 是本章最想让你亲眼看到的一个数字**，它出现在你自认为已经做了幂等之后。唯一键那条路做到 0，是因为拒绝的权力交给了数据库约束，不是交给你的判断。

D 组的读法要小心：三种配置消耗的随机数不同，「毒药」条数本身在 47–66 间波动，**所以这里要读的是形状**——不设上限时毒药消息永远占着消费者（模拟里到窗口结束仍有 47 条没终止）；设上限 5 但不接死信，则有 330 次投递纯粹是空转后被丢弃（这些消息从消费者的视野里消失了，也就是丢了）；接上死信，50 条全部有地方可查、空转为 0。死信的价值不在「不丢」，在**「可查」**。

## 阶段 1：投出去

顺序上先只做一件事：让主链路里那段时间消失。**先不碰可靠性**，投不到、丢了都别管——那是阶段 3 的功课。这一阶段唯一目标是把表一的「改造后」那一行量出来。

```sql
CREATE TABLE outbox (
  id            BIGSERIAL PRIMARY KEY,
  kind          TEXT        NOT NULL,   -- welcome_mail / report_export
  biz_key       TEXT        NOT NULL,   -- 业务幂等键，例如 user:42:welcome
  payload       JSONB       NOT NULL,
  status        TEXT        NOT NULL DEFAULT 'new',   -- new / sent / failed
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  sent_at       TIMESTAMPTZ,
  UNIQUE (biz_key)
);
```

为什么消息要先进数据库再搬进队列：**因为「写库成功、投队列失败」是最容易发生的组合**（进程在两行代码之间被杀）。outbox 把「要不要做这件事」变成一条持久记录，投递变成一个可以反复重试的动作——数据库写成功就等于意图被记住了。第 3 章讲清了这套语义，本章只给落法。

搬运有两种做法：

```ts
// 做法一：请求里顺手投，失败也当成功（简单，但会有短暂不一致）
await db.tx(async (t) => {
  await t.insert(users, row);
  await t.insert(outbox, { kind: 'welcome_mail', bizKey: 'user:' + id + ':welcome', payload });
});
void publishPending().catch(() => {});   // 投失败没关系，下一条会带着它

// 做法二：独立搬运进程（多一个进程，但主链路完全不碰队列）
// while (true) { 取 status=new 的一批 → 投队列 → 标 sent }
```

**判据**：主链路里能不能出现「等队列」？如果你的请求路径里有 `await queue.add()`，那么队列不可用时你的接口就 500——你只是把第三方故障从「发信服务」换成了「队列服务」，而后者是你自己运维的，更该由你负责。做法二多花一个进程，换来的是「队列挂了业务照样能注册」。**个人项目选哪个都合理，但必须写清代价**，这是 R3 的真正验收点。

产出与验证：表一的「改造后」行开始有数；`select count(*) from outbox where status='new'` 在常态下应当是 0 或很快归零。

## 阶段 2：吃下来（消费者与幂等）

worker 的骨架。**下面的 API 名按「订阅 → 处理 → 确认」的通用形状写，不是你所用产品的真实方法名——各产品的确认接口差别很大，动手前对齐[第 6 章](/message-queue-cloud/rabbitmq)或[第 7 章](/message-queue-cloud/redis-stream)，本站没有环境去核对具体方法名**。

```ts
async function handleOne(msg: Envelope) {
  const claimed = await markRunning(msg.bizKey);      // 唯一约束在这里发力
  if (!claimed) return 'ack';                          // 已有人做过或正在做 ⇒ 什么都不做
  try {
    await deps.sendWelcome(msg.payload);               // 真正的副作用，只在唯一约束通过之后
    await markDone(msg.bizKey);
    return 'ack';
  } catch (err) {
    await markFailed(msg.bizKey, err);                 // 留痕，供死信与人工排查
    return 'nack';                                     // 交给代理重投
  }
}

async function markRunning(bizKey: string): Promise<boolean> {
  try {
    await db.insert(idempotency, { bizKey, state: 'running' });   // 表上有 UNIQUE(bizKey)
    return true;
  } catch (e) {
    if (isUniqueViolation(e)) return false;                       // 冲突 ⇒ 这条已经有人在处理
    throw e;
  }
}
```

三条不许的写法，直接对应 C 组那个 89：

- 不许 `先 SELECT 再决定`——这是那 89 次重复的来源。
- 不许「成功后才插入」——两条并发都成功，还是两封邮件。占位必须**在副作用之前**，用约束拒绝。
- 不许把 `msg.id`（代理给的消息 ID）当幂等键——重投或换一条通道时它可能变；键必须是业务含义（`user:42:welcome`）。这条在[第 3 章](/message-queue-cloud/reliable-delivery)论证过，[数据存储的幂等与限流](/data-storage/session-rate-limit-idempotency)给了表的完整形态。

还有一个容易漏的：**worker 也会抢数据库连接**。N 个 worker × 每个的连接池大小，加上线上的 app，很容易顶到数据库的连接上限（这个乘法在[连接池那章](/data-storage/connection-pool-and-slow-query)钉过）。给 worker 的池设一个小值，比给它加 CPU 有用。

产出与验证：R4 的验收——把同一条消息**手工投两次**（自己写个 `dup-publish.mjs`，或者直接重放一条真实消息），然后拿证据说明副作用只发生一次。证据必须是外部可查的那种（发信厂商侧的发送记录、或数据库里的行数），不是「我看了日志没报错」。

## 阶段 3：故意制造故障

这一步是这个项目的本体。前面所有「我做了幂等」「我做了确认」的自述，只有在这里被证实或推翻。**每个实验都要写清「怎么制造 → 预期看到什么 → 实际看到什么 → 通过与否」**，实际那一栏不许留空，留空就是没做。

| 实验 | 怎么制造 | 通过标准 |
| --- | --- | --- |
| F1 确认前崩溃 | 处理成功后、ack 之前杀进程（`scripts/fault-kill.mjs` 在延时点 `process.kill(process.pid)`） | 同一条被重新投递；副作用不再发生第二次（靠幂等表拒绝） |
| F2 永久失败 | 让 handler 对某条固定抛错 | 重试到上限后停止，进死信；死信里能看到消息体与最后一次错误 |
| F3 重复投递 | 手工把同一条投两次，间隔 0（并发）与间隔 1 分钟各一次 | 两次都只发生一个副作用；并发那次尤其要看住 |
| F4 消费者全停 | 停 worker 120 秒再恢复 | 期间积压增长、恢复后自动排空；主接口不受影响 |
| F5 代理重启 | 重启队列容器 | 已确认的不重投；未确认的仍在；**注意持久化是「与」运算，任一侧没落盘都可能丢**（第 6 章） |

**F5 是唯一一个可能给你「丢了几条」的实验，而那正是它的价值**。[投递语义](/message-queue-cloud/delivery-semantics)那句结论在这里必须被你自己撞一次：不丢和不重不能同时免费拿到。如果你的 F5 结果是「一条没丢、也没重」，先怀疑是不是测试窗口太小，而不是怀疑理论错了。

重试上限的取值要有理由，而不是抄一个数：把它当成**「你愿意为同一条消息花多少次真实厂商调用」**。上限 5 就是最坏情况多花 4 次；上限太大是让毒药消息长期占着消费者（D 组那 47 条），太小是让本来一次网络抖动就能救回来的消息过早进死信。

死信不是终点，是**队列**。验收要求你写一小段处理流程：谁来看、看什么字段、怎么修（修数据还是修代码）、修完怎么重放、重放时幂等键怎么处理（**同键重放会被幂等表拒绝——这是设计正确的表现，也是最常见的「死信重放不动」的原因**；解法是让幂等记录带状态，失败态允许重试或显式清除）。

产出与验证：五张故障记录 + 一次真实的重放成功。

## 阶段 4：可观测、回退与结论

三个指标，缺一不可：

- **积压条数**：现在有多少条待处理。
- **最老消息年龄**：积压 500 条但最老的是 3 秒前，和积压 500 条但最老的是昨天，是两个世界。**只看条数会漏掉「消费者活着但极慢」这种形态**。
- **死信速率**：单位时间进死信多少条。它是「你的幂等或数据有系统性问题」的探测器。

阈值要写成数字并说明依据；如果告警从来没响过，做一次「故意把它触发」的测试，**确认它真的会通知你**。没验证过的告警等于没有告警——这条纪律在[devops 的测试章](/devops/testing)里以另一种形式讲过。

**回退触发条件**（R11 的一部分，必须写成动作，不是「量大了再说」）：写清楚出现哪三个信号时你会重算方案，以及重算时往哪儿退。典型的一条是：如果队列故障会连带让你的核心接口变慢，那就把直投改成纯 outbox + 定时搬运，用副作用延迟换接口稳定性。选型对照见[第 9 章](/message-queue-cloud/choosing)，自托管与云的账见[第 13 章](/message-queue-cloud/self-host-vs-cloud)，那一页纸十问的第 9、10 问就是这里要交的东西。

**顺手做的那个可选扩展**——处理完成后通知在线用户——是本批和实时通信领域的接缝，也是很多人会踩错的地方：

- worker 处理完消息，持有用户长连接的却是 app 进程（甚至另一个实例）。这属于**发布订阅**，不属于竞争消费：每个 app 实例都必须知道这条消息，否则用户能不能收到取决于运气。
- 竞争消费和发布订阅的差别在[第 2 章](/message-queue-cloud/mq-concepts)用实测数字钉过（6 条消息：竞争消费 6 次副作用，发布订阅 18 份拷贝）。**在同一个进程里两种语义并存时，最贵的两个错误是：把广播当竞争消费（用户随机收不到），把竞争消费当广播（副作用重复执行）**。
- 跨实例怎么广播、以及总线为什么补不上「离线的人」，见[扩展性：多实例的广播问题](/realtime/scaling-out)；断线期间的消息怎么补、为什么不能只靠重连，见[心跳与断线重连](/realtime/heartbeat-and-reconnect)。这里的结论只有一句：**队列负责「不在的人」，长连接负责「现在在线的人」，两者不是替代关系。**

## 常见翻车点

1. **现象：README 写「延迟降低 65 倍」，但改造后本地手工点几次是 p50，改造前压测是 p95。** 原因：两个数不同口径。怎么确认：把两个数字的采样窗口、样本量、统计量各自写出来，一眼就能看出对不上。怎么修：同窗口同统计量重测，并在表里把窗口写死。
2. **现象：接口快了，但邮件三天没发出去。** 原因：worker 挂了而没有任何积压指标；主链路指标一片健康。怎么确认：看队列的积压与最老消息年龄，而不是看接口成功率。怎么修：R8 那三个指标 + 一次告警触发测试。
3. **现象：同一条消息发了两封邮件，而你确定自己写了幂等。** 原因：先查后写的窗口（C 组那 89 次）。怎么确认：把重复投递的间隔压到 0 再试一次；单次串行重投是测不出这个 bug 的。怎么修：把判断换成唯一约束，让数据库替你拒绝。
4. **现象：死信里的消息重放不动，或者一重放就报「已处理」。** 原因：幂等记录只在成功时写入且没有状态。怎么确认：查那条 `biz_key` 在幂等表里的状态。怎么修：幂等记录带状态，失败态允许重试；重放走「清除该键的失败态」这条明确动作。
5. **现象：加了 worker 之后数据库报错连接数超限。** 原因：连接数是实例数 × 池大小的乘法，而你把 worker 当无成本的东西复制了。怎么确认：把实例数与池大小分别写出来算一次。怎么修：worker 用小池；上限来自数据库侧配置，见[连接池与慢查询](/data-storage/connection-pool-and-slow-query)。
6. **现象：队列一挂，注册接口跟着 500。** 原因：主链路里 `await` 了队列。怎么确认：停掉队列容器，打一次注册请求。怎么修：改纯 outbox + 独立搬运，或至少给投递一个短超时并且失败不抛出到请求层。
7. **现象：重试次数越加越多，失败还是失败，厂商账单也在涨。** 原因：没有把「数据错误」和「暂时错误」分开（第 11 章那条硬退/软退之别的同款问题）。怎么确认：把失败样本按原因分两堆，看重试对哪一堆有效。怎么修：数据类错误直接进死信，不重试。
8. **现象：F5 之后「一条都没丢」，于是写下「我们做到了 exactly-once」。** 原因：样本小、时间窗短、或者根本没检查重复。怎么确认：同时统计「丢失数」和「重复数」两个数，缺一个都不算结论。怎么修：写「我们在这个场景下接受 at-least-once + 幂等」，这是诚实且正确的表述（[第 5 章](/message-queue-cloud/delivery-semantics)）。

## 下一章

`message-queue-cloud` 这个领域到这儿走完：第 1 章的动机、第 2 章的模型、第 3–5 章的可靠性语义、第 6–9 章的三个产品与选型、第 10–13 章的云服务取舍，最后由本项目把它们压成一次可验证的改造。如果你把 F1–F5 五组故障真的做出来并且写出了那张两组数字并存的对照表，你手里就不只是「会用队列」，而是「知道一个异步系统要怎么被证明」。

下一个要还的债在实时通信那边：这个项目里那个可选扩展——把处理结果推给正在线的用户——会逼你面对一条和队列完全不同的链路：**HTTP 的请求-响应模型里，服务器不能主动说话**。如果你还没读过那一边，从[实时通信领域首页](/realtime/)的四章基础开始；如果你已经读过，本批刚上线的[心跳与断线重连](/realtime/heartbeat-and-reconnect)是它与本项目共用可靠性语义最密的一章——它讲的「断线期间的消息怎么补、补了会不会重复」，和你刚在 F3 里对付的「重复投递会不会双发」，本质上是同一个问题在两个方向上的投影。
