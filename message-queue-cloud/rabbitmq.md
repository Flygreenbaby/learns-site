# RabbitMQ：你设计的不是消息，是一张路由拓扑

「消息发出去了，队列长度一直是 0。」这是 RabbitMQ 最经典的一类事故，而且它**不报错**。原因几乎总是同一个：生产者把消息交给了交换机，交换机手上没有任何一条绑定能接住这个路由键，于是消息按规则被静默丢弃了。RabbitMQ 不会替你把「发给了一个没人订阅的地址」当成错误——因为在自己的设计里，这是正常情况。

第二个常见事故是「测试时一切正常，压测时 worker 内存打满」：消费端开着自动确认（投递即算成功），又没有设置在途上限，broker 就把整条队列一股脑推给了那个慢得要死的消费者。第三个是「队列声明了 durable，重启后消息还是没了」：持久化是两个条件的与运算，少一半等于没做。

前五个章节把通用概念立完了——[生产者消费者与分区](/message-queue-cloud/mq-concepts)、[确认与幂等](/message-queue-cloud/reliable-delivery)、[死信与顺序](/message-queue-cloud/dlq-delay-order)、[投递语义](/message-queue-cloud/delivery-semantics)。本章不再讲那些原理，只做一件事：**把通用概念翻译成 RabbitMQ 的具体对象，并说清它的模型擅长什么、从哪儿开始不擅长**。RabbitMQ 的定位一句话：它是以 broker 为中心的**任务分发器**，核心抽象是路由拓扑与逐条确认，消息一旦被确认消费就消失，积压能力是它的短板。

## 设计对象是拓扑：交换机、绑定、队列、路由键各管一件事

RabbitMQ 的模型里，生产者**永远不直接往队列发消息**，它把消息交给一个交换机（exchange），交换机照着绑定（binding）的规则决定这条消息进哪几个队列。这一层间接是 RabbitMQ 全部灵活性的来源，也是它全部踩坑的来源。

| 交换机类型 | 匹配规则 | 典型用法 | 什么时候别用 |
| --- | --- | --- | --- |
| direct | 路由键**精确**相等 | 按任务类型分派：`email.send`、`report.build` | 需要「一类」而不是「一个」匹配时 |
| fanout | 完全忽略路由键，广播给所有绑定的队列 | 一份事件发给多个互不相干的下游（审计、缓存失效） | 下游只想收一部分时，它会收到全部 |
| topic | 路由键按点分词，`*` 恰好一个词，`#` 零个或多个词 | 多维筛选：`order.eu.high`、`*.eu.*`、`order.#` | 规则复杂到需要几十条绑定时，先想清楚是不是该拆服务 |
| headers | 不看路由键，按消息头部属性以 any/all 匹配 | 需要按元数据（租户、版本）路由且路由键已被业务占用 | 需要可读性与可调试性时——headers 匹配最难肉眼排查 |

已核实的三条语义要记牢，因为它们决定了故障表现：绑定是**应用创建的**（不是你「以为存在就存在」，声明队列不等于建立绑定）；fanout 会**忽略路由键**（所以你以为的分级在它面前完全无效）；topic 的 `#` 可以匹配**零个**词（`order.#` 能匹配 `order` 本身）。

最该背下来的一条是：**无法路由的消息会被丢弃，除非发布者设了相应标记让它被退回**（已核实）。默认行为是静默丢，这在生产上等价于「消息消失但没有错误」。可操作的对策有两条，选一条即可：给交换机挂一个备用交换机（alternate exchange）把没路由上的消息接到一个「黑洞队列」，或者在客户端打开 returned message 回调并**把它当错误上报**。没做这两件事的团队，第一次遇到「路由键拼错」时是查不出来的。

一条队列可以同时被多个交换机绑定（这在官方模型页里没有明确表述，动手前用管理界面验证一条给你看），反过来一个交换机可以绑多条队列。这两个方向合起来就是 RabbitMQ 的核心能力：**路由是数据，不是代码**。你的业务代码只说「这是 `order.eu.high`」，谁收、收几份，由运维时建立的绑定决定，改路由不用改代码、不用重新发布。这在第 1 章「解耦」的意义上是真实解耦，代价是你必须在某处（IaC、部署脚本或一份登记表）维护这张拓扑图，否则半年后没人知道为什么这条消息进了那个队列。

## 三段确认各管一段：生产侧、broker 侧、消费侧

第 3 章说过「可靠性由确认写在哪一行决定」。在 RabbitMQ 里这句话拆成三段，各自有独立开关，缺一段就是一个具体的丢消息点。

```js
// 示例（未在本机运行）：Node.js amqplib 风格的三段确认
// 客户端库与 API 名以官方文档与你所用库的当前版本为准
const ch = await conn.createConfirmChannel();     // ① 生产侧：开启发布确认

await ch.assertQueue('jobs', { durable: true });  // ② broker 侧：队列必须持久
await ch.publish(
  '', 'jobs',
  Buffer.from(JSON.stringify({ id: 42 })),
  { persistent: true, messageId: '42', expiration: '60000' }   // ② 消息也要持久（delivery_mode=2）
);
await ch.waitForConfirms();                       // ① 等到 broker 承认收到，才算「发出去了」

await ch.prefetch(10);                            // ③ 消费侧：在途未确认消息的上限
await ch.consume('jobs', async (msg, { ack, nack }) => {
  try {
    await handle(JSON.parse(msg.content.toString()));
    ack(msg);                                     // ③ 处理成功才确认（消息此刻才被删除）
  } catch (err) {
    nack(msg, { all: false, requeue: false });    // ③ 不重回队头，交给死信链路（见第五节）
  }
}, { noAck: false });                             // ③ 绝对不能开自动确认
```

三段各自的意义：`waitForConfirms` 解决「消息有没有到 broker」——它是异步的批量确认，不等就等于把「发出去了」当成已核实事实；队列与消息的持久性解决「broker 重启后还在不在」；消费端手动 ack 解决「有没有真的处理完」，而**消息只有在 broker 收到确认后才从队列移除（已核实）**，这一条正是 at-least-once 的机制来源：确认前你崩了，消息会重新投递给别的消费者。

`prefetch`（QoS）那一行是压测事故的直接解药。它限制「已投递但未确认」的消息数量，不设的话，broker 会把能推的全推给消费者，快生产者 + 慢消费者 = 你的进程内存里躺着十万条待处理消息，而 broker 以为它们都在「处理中」。这同时也是并发控制手段：`prefetch(1)` 就是逐条串行，`prefetch(20)` 允许 20 条并发处理，这个数字与你的 worker 数量、单条处理时长直接相关，取法见第 1 章的吞吐算术。

`noAck: true`（自动确认）要理解为**投递即删除 = at-most-once**：消息一旦推给消费者就从队列消失，消费者崩了就真的没了。它只有一种正当用法：消息可丢且以最新值为准（坐标、心跳、瞬时指标）。

## 持久化是「与」运算，不是一个大开关

已核实的规则很硬：`delivery_mode` 为 2 的持久消息**加上**持久队列，两者同时成立才算持久化，缺一半都不算（瞬态消息是 `delivery_mode` 1）。这个「与」关系造成两类半吊子：

- 队列 durable、消息发成 transient：重启后队列还在、里面的消息没了。现象是「明明配了持久化还是丢」。
- 消息 persistent、队列非 durable：重启后队列连同内容一起消失。

还有第三件事常被漏掉，而它才是真正的分水岭：**持久化让消息活过单节点重启，不等于活过节点损坏**。消息落在本机磁盘上（`/var/lib/rabbitmq` 下的节点数据目录），那个节点没了，盘上的东西也就没了。要活过多节点故障需要副本机制（下一节）。这就是「哪些是文档、哪些是我们没验的」那条纪律在 RabbitMQ 上的具体形态：三件事——消息落盘、队列可恢复、跨节点副本——各是独立配置，把它们叫作一个「高可用开关」是不成立的。

持久化的代价也要说清，因为它解释 RabbitMQ 的定位。写盘意味着吞吐受磁盘限制；更重要的是队列很长时，RabbitMQ 的行为会明显变差——它的实现是把「可投递的消息」尽量放在内存里以便即时分发，积压变大后它会做分页换出、内存报警、并最终**反过来阻塞发布者**（这个流控行为与阈值本批未核实，压测前请查官方内存与磁盘报警那一页）。所以判断很简单：**你的队列应该常态接近空**。如果设计里出现「积压十万条慢慢消费」，那不是 RabbitMQ 调参能解决的，那是第 8 章的日志流场景。

## 高可用：仲裁队列是当前的答案，但细节要查版本

关于 RabbitMQ 集群能安全讲的只有原则，具体参数名一律要核对当前文档。

第一，**副本机制历史上变过很多次**：早期的经典镜像队列（mirrored queues）已被官方弃用、由基于 Raft 共识的仲裁队列（quorum queues）取代。弃用的时间点、你的版本还支持什么、仲裁队列的队列参数名，**本批未逐字核实**——请查官方 quorum queues 那一页，这一项直接决定「节点挂了消息还在不在」。

第二，仲裁队列不是「加了副本」这么简单：写入走共识日志，延迟与吞吐特性随之改变，官方对单 publisher、消息大小与可用性场景另有说明与限制。要记住的是这笔交易：**为了「一个节点宕机不掉消息」付延迟与吞吐成本**。

第三，多节点必然遇到网络分区（两个半边各自认为自己是合法的一侧），RabbitMQ 有分区处理策略可配置（策略名本批未核实），通用逻辑在第 2 章「分区与顺序」已讲。你至少要能答：分区时你的队列是继续写（可能重复）、停写（保证一致）、还是等客户端重连后由共识收敛。

第四，单机部署也没什么可羞耻的。一个 VPS 上的单节点 RabbitMQ 配上「持久队列 + 持久消息 + 手动 ack + DLX + 幂等消费」，可靠性已经足够支撑绝大多数个人项目：单节点的失效域是这台机器，而你已经用「消息没确认就还在队列里」这条机制覆盖了进程崩溃这一类最常见的故障。**为了「不怕节点挂」而引入三节点集群，是你为不存在的风险付的运维费**（什么时候真的要付，第 9 章给判据）。

## 重试、死信、延迟：把第 4 章的策略落到具体名字

第 4 章讲过三条通用结论：处理不了的消息要有去处且有告警、毒丸「回队头还是回队尾」比次数上限更重要、延迟消息的到期时间必须是数据而不是定时器。它们在 RabbitMQ 里的对应实现：

**死信交换机（DLX）**。队列可以通过参数声明「本队列里被拒绝（且不重回队列）、过期、或队列满而溢出」的消息投递到哪个交换机、用什么路由键。这套参数名与匹配规则**请以当前官方文档核对**，本章不给可照抄的片段。关键在两个实操点：死信消息会带上记录死信历史的消息头（通常包含次数与原因），所以**计数不用你自己维护**，读那个头就行；而 DLX 队列本身必须有人看，否则「有去处」退化成「换个地方静默堆积」，第 4 章那条「要能被告警、能被重放」仍然要你自己做。

**重试的正确形态**。拒绝消息时把 requeue 设成 true，消息会**回到队头附近重新投递**——这正是「毒丸回队头」那个反模式，现象是某个坏消息让 worker CPU 打满并阻塞正常消息。RabbitMQ 没有内建的「指数退避重试」，通行做法是自建两级：处理失败就 nack 到 DLX，DLX 再路由到一个「重试队列」（带 TTL），TTL 到期后经 DLX 回投到业务队列，重试次数用消息头里的计数判断、超限则进最终死信队列。这条链路每个环节都是可观测的队列，比在代码里写 for 循环重试要好得多，但它有第五节要说的那个坑。

**延迟消息**。原生 RabbitMQ **没有**「指定任意时刻投递」的能力，通行做法就两条：上面那种 TTL + DLX 的接力（到期时间是数据，符合第 4 章的原则），或者官方/社区的延迟交换机插件（版本与限制未核实）。用 TTL 方案必须知道它的著名缺陷：队列内消息按顺序判断过期，**队头一条 60 秒的消息会挡住它后面 10 秒的消息**，直到队头过期或被消费。工程解法是「按延迟档位建队列」（`delay.10s`、`delay.60s`、`delay.10m`），一个档位一个队列，队头阻塞就只发生在同档位内。这个取舍值得在面试里讲，更值得在你写「订单 30 分钟未支付自动取消」之前想到——那种场景常常用「扫表 + 到期时间列」比用队列更简单。

## 什么时候 RabbitMQ 是正确答案

选它的理由（都是别的两家做起来别扭的事）：路由规则复杂且要能不改代码地调整；需要逐条确认与单条粒度重试；消息量中等（每秒几十到几千）、要求即时分发；任务队列形态（有工作就领、领完就消失）；优先级队列、按租户分派的公平调度；不想为了异步再引入一个必须回放历史的重量级组件。

不选它的理由（出现任一条就该往下两章看）：需要**回放**（第 8 章的日志模型才是回放语义，RabbitMQ 里消息被确认就没了）；需要**多个独立消费方各自维护进度**且都从历史起点读；常态**积压很大**；吞吐是主要目标（百万级每秒不是 RabbitMQ 的目标形态）；需要事件溯源或变更捕获。

它在个人项目里的真实位置：一个 Docker 容器就能跑起来（Compose 写法与镜像名以第 7 章 Docker 课程为准），自带管理界面能看队列长度、绑定拓扑与消息追踪，这第三点是它相对 Kafka 的**巨大**开发体验优势——你能在 UI 里看到「这条路由键没有绑定」，而 Kafka 里的对应错误往往表现为「消费者什么都没收到但一切正常」。它对 Redis 用户的替代价值也只有一个：**你需要上面那些路由能力时**。

## 常见错误与排查

1. **现象：`publish` 返回成功，队列长度始终为 0。** 原因：路由键与任何绑定都不匹配，消息被静默丢弃（已核实这是默认行为）。怎么确认：看交换机上有没有该队列的绑定、路由键拼写与点分结构；主动开 returned message 回调或挂备用交换机，看有没有消息回来。怎么修：先声明队列与绑定再发消息（顺序在部署脚本里固定下来），并给拓扑做一次「空路由」检查。
2. **现象：本地跑没问题，压测时 worker 内存暴涨、GC 打满。** 原因：没设 `prefetch`，broker 把可投递消息全推给了消费者；或者开了自动确认，处理慢与投递快完全脱钩。怎么确认：管理界面看该队列的「未确认（unacked）」计数是否等于某个消费者独占的一大坨。怎么修：设置 `prefetch`（从「并发数 × 1~2」起步），关闭自动确认，让慢消费者自然减少领取速度。
3. **现象：声明了持久队列，重启后消息还是没了。** 原因：消息发成了瞬态（`delivery_mode` 1）——持久化是两个条件的与运算（已核实）。怎么确认：重启前先单条追踪消息属性，或直接把 publish 的 options 打印出来。怎么修：在封装的发布函数里把持久化设成默认值而不是每次传，避免「新代码忘了传」。
4. **现象：某条消息让 CPU 100%，正常消息也被卡住，日志里全是同一 messageId 的失败。** 原因：处理失败后 nack 且 requeue=true，毒丸重回队头被立刻重投。怎么确认：看该消息的投递计数（消息头里的死信/重投历史）是否单调暴涨。怎么修：失败一律 `requeue: false`，交给 DLX 链做带退避的重试，并设次数上限进最终死信（第 4 章的策略在 RabbitMQ 上的落地）。
5. **现象：延迟消息「有时很准、有时全批一起到」。** 原因：TTL + DLX 方案下的队头阻塞——队头那条更长过期的消息挡住后面的。怎么确认：观察同一队列里消息的「入队时间」与「到期投递时间」差值是否随位置变化。怎么修：按延迟档位拆队列，或改用到期时间为数据的扫表方案。
6. **现象：加了集群后消息重复变多，或某些写入超时。** 原因：队列不是仲裁队列（副本不同步），或节点发生了网络分区，或副本因子与写入容错参数没配套。怎么确认：查该队列的类型与副本数、分区处理策略、以及 broker 日志里的分区/恢复记录。怎么修：**先把队列类型改对再谈高可用**，并核对当前文档里的参数名；同时确认消费端幂等已经做扎实，因为「重复」是这些故障最常见的可观察症状。积压二十万条且「越攒越慢」是另一类问题：那是把任务队列当日志流用，处置办法在第 8 章。

<Exercise title="练习 1 · 四种交换机与七条绑定，算出每条消息去了哪些队列" difficulty="基础">

已有队列与绑定（全部由应用创建）：

```text
exchange A = fanout，名 notify
```

请写出下面五步各自的结果（哪些队列收到，哪些没有任何队列收到）：

1. 向 notify 发一条，路由键 `anything.else`。
2. 向 jobs 发一条，路由键 `email.send`。
3. 向 jobs 发一条，路由键 `email.bulk`。
4. 向 orders 发一条，路由键 `order.eu.high`。
5. 向 orders 发一条，路由键 `order`，随后向 orders 发一条路由键 `order.us.low`。

5. `order` 命中 `#`（`#` 可匹配零个词，已核实），也**只**命中 q.all（因为 `order.*.high` 需要至少三个词）。`order.us.high` 命中 q.premium（`*` = us）与 q.all；`order.us.low` 只命中 **q.all**。这一问的用意：让你确认 `*` 只吃一个词、`#` 能吃多个或零个，且这两个通配符的差异是「段数」而不是「前缀」。

<Exercise title="练习 2 · 三处写坏，分别说出症状、确认方法和判据" difficulty="进阶">

```js
// 坏法一：自动确认 + 没有 prefetch
await ch.consume('jobs', handler, { noAck: true });

// 坏法二：队列持久，消息没设持久
await ch.assertQueue('jobs', { durable: true });
ch.publish('', 'jobs', Buffer.from(payload), {});

// 坏法三：失败就重回队头
ch.nack(msg, { all: false, requeue: true });
```

1. 三处各自的症状是什么？（要求写出「谁先出问题」：内存、重启、CPU）
2. 只用管理界面与队列计数，怎么在不改代码的前提下确认每一条？
3. 坏法三的正确写法为什么不是 `requeue: false` 就完事？你还必须配什么才算「重试」，配不上会退化成什么？

<template #answer>

1. 坏法一的症状是**消费者内存**：消息一投递就从 broker 队列移除（已核实自动确认模式下即删除），于是 broker 端看起来「队列很空、很健康」，而你的进程里堆着几万条待处理消息；一旦进程 OOM 或被 kill，这批消息**永远不会重投**（at-most-once）。坏法二的症状是**重启**：队列元数据活下来、消息不活下来，现象是「重启后队列还在但长度为 0」，且平时毫无征兆——这是最坏的一类 bug，因为它只在故障时暴露。坏法三的症状是 **CPU**：毒丸不断回到队头被立刻重投，形成忙循环，同时把正常消息的处理挤在后面。
2. 三条各有可观察指标。①坏法一：看该队列的 unacked（未确认）计数——自动确认下它**恒为 0**，这本身就是确认信号；再看消费者进程的 RSS 单调上升。②坏法二：单条消息属性里看它是 transient 还是 persistent，或者更粗暴：先灌 100 条、重启 broker、看队列长度是否归零（在预发环境做，做完就把这条列入验收）。③坏法三：同一队列里出现某条消息的投递计数暴涨，且消费速率曲线在某个时刻断崖，CPU 高但吞吐为 0。这个练习真正的价值在于：**三条都有一条能立刻观测的队列指标**，「先找指标再改代码」是本课程反复要的动作。
3. 只把 requeue 改成 false，得到的不是重试，是**立刻进死信**——所有瞬时故障（下游抖动、数据库连接池打满）都会被误判成「这条消息有毒」。要成为重试，至少还需要三样：一个可区分的重试路径（DLX 路由到重试队列而不是最终死信队列）、**递增的间隔**（用重试队列的 TTL 实现，档位化以免队头阻塞）、以及**次数上限**（从死信历史的消息头取计数，超限才落到最终死信）。三样里少任何一样都会退化：少间隔 = 快速重试把下游打死；少上限 = 无限循环；少可区分路径 = 瞬时故障与毒丸混在一起，死信队列变成垃圾场，第 4 章「死信要能被重放」也就无从谈起。

</template>

</Exercise>

<Exercise title="练习 3 · 为多租户订单系统选 RabbitMQ，并给出它撑不住的边界" difficulty="挑战">

场景：SaaS 订单系统，租户 A/B/C，欧洲与美区，优先级三档。需求：注册后异步发欢迎邮件（约 30 分钟后可补发）、支付回调必须不丢、报表按租户隔离消费、故障消息要能人工重放；吞吐峰值每秒约 800 条，单条 1 KB。你选了 RabbitMQ。

1. 画出交换机/队列/绑定的拓扑（不用画图，写清单即可），说明你用的交换机类型与理由。
2. 「支付回调必须不丢」这一句，在 RabbitMQ 上要同时成立**至少四件事**，逐条列出并说明各自失败的表现。
3. 报表需求出现三个月后，产品要求「报表逻辑改了，把过去三个月的事件重新算一遍」。你的拓扑能支持吗？说出为什么，以及你会怎么改架构。
4. 上线后你发现消费速率从某个时间点开始持续下降而队列长度不断上升，给出你排除的前三项与各自的判据。

<template #answer>

1. 最小拓扑：一个 topic 交换机 `orders.events`；绑定规则用「`事件.地区.租户.优先级`」的四段路由键。队列按**消费方**建而不是按事件建：`jobs.email`（绑定 `order.created.*.*`）、`jobs.payment`（绑定 `payment.callback.#`）、`report.tenantA` / `report.tenantB` / `report.tenantC`（各自绑定 `*.#.<该租户>`）、`dlq.payment`。选 topic 的理由：需要多维筛选（地区 × 租户 × 优先级）且规则要能不改代码调整——这正是 RabbitMQ 的核心能力；headers 交换机虽然也能表达租户，但肉眼排查最难，不值得在这个规模上使用。报表按租户分队列是为了让一个慢租户堵住另一个租户的所有报表事件，这是隔离而不是并发。
2. 四件事：① **持久消息 + 持久队列**（`delivery_mode` 2 且队列 durable，已核实二者缺一即不成立），否则重启就没了；② **发布端等待 broker 确认**（confirm 机制 + `waitForConfirms`），否则「publish 返回」不代表 broker 收到；③ **消费端手动 ack、失败不重回队头**，否则处理未完成就删除（已核实消息只在收到确认后移除）；④ **业务写与消息写落在同一事务里**（第 3 章的 outbox 模式），否则「数据库写成功、消息没发」这种不一致任何队列机制都救不了。**第四件最常被漏**，因为它不在 RabbitMQ 里。附带一条诚实边界：单节点时以上四条只保证活过进程重启与崩溃，不保证活过机器损坏；要活过机器需要仲裁队列，且必须核对当前版本的参数与限制。
3. **不支持**，而且不是配置问题。RabbitMQ 的队列语义是「确认后消息消失」（第 2 章队列 vs 日志那条分界），历史不存在于 broker 里。三个月的事件此刻要么躺在你的业务数据库里（那么重算是 SQL 重跑，跟队列无关），要么已经随确认一起消失了。要支持重算，只有两条路：把事件同时写入一个可回放的存储（事件表或对象存储归档），或者改用日志流模型（第 8 章 Kafka）让消费进度只是一个偏移量、可以把游标拨回去重读。正确回答是：**这是需求变化，不是选型错误**——它新增了「回放」这个维度，而回放不属于任务队列的能力。
4. 前三项排除：**①是不是某条毒丸在忙循环**——判据是消费速率下降的同时 CPU 高、且队列里某个消息的投递计数暴涨；**②是不是 prefetch 太小或 worker 数被并发上限卡住**——判据是 unacked 计数长期等于 prefetch 值且 worker 空闲日志多（这是「领得慢」而不是「处理慢」）；**③是不是队列长度触发了 broker 自身的换页/内存报警从而反压发布**——判据是 broker 端出现内存相关报警、发布端出现等待超时而消费端速率正常，同时看队列长度与内存曲线是否同步。**顺带第四项**（如果是报表类长队列）：单个巨大队列本身就是 RabbitMQ 的性能悬崖，这时候的答案不是加消费者，而是把这条队列拆成多个按租户/日期的队列，或者重新判断该不该用队列做积压。

</template>

</Exercise>

## 下一章

这一章把 RabbitMQ 放回它该在的位置：一个**路由灵活、逐条确认、消息消费完就消失**的任务分发器，它的强项是「谁该收这条」这个问题，它的软肋是「这条能不能重来一遍」。下一章 [Redis Stream：轻量级队列](/message-queue-cloud/redis-stream) 看的是光谱的另一端：你多半已经装了一个 Redis，它自带的 Stream 类型能提供一个「够用的」队列——有消费者组、有待确认清单、有重认领机制，而且消费完消息**不消失**。它和 RabbitMQ 的差别不在「谁更简单」，而在于它把消费进度放在了一个日志结构里，因此天然带上了一点回放能力，也因此在保留、内存与投递保证上有另一套完全不同的边界。
