# 可靠性不是「不丢」，是把「丢」和「重」变成你能查、能兜住的状态

一条消息从生产到落地，中间有三个地方可以出事：**投递方交出去之前崩了**（业务库写了、消息没投出去，或者反过来）；**代理存着的那一份没了**（没持久化，进程重启就空了）；**消费方拿到之后崩了**（做了一半，或者做完了没来得及说「我做完了」）。

第一个坑的真实形状是这个：注册接口投出一条欢迎邮件消息，紧接着写用户表的语句因为一个字段为 NULL 失败了。用户不存在，邮件消息在队列里躺着。三小时后 worker 醒来，给一个查无此人的地址发了一封邮件。第二个坑更常见：你以为持久化打开了，其实只是「写进了操作系统的缓冲」，机器掉电那一段就没了。第三个坑最隐蔽：**库里的状态显示这条消息已经处理完成，而副作用从来没有发生过**——恢复扫描看不见它，因为它看起来是成功的。

这三个坑都不是靠「选对消息队列产品」解决的。它们对应三个必须自己决定的东西：**投递方怎么保证业务写与消息写一起成立**、**确认放在副作用之前还是之后**、**消费端重复执行一次会不会出事**。这一章逐个给实测。

<Callout type="verified">

本章实测环境：Windows 10 x64 + Node v25.4.0，2026-10-19，零依赖（`node:sqlite` + `child_process.spawn` 真子进程）。三个数字组分别来自：

```bash
node message-queue-cloud/.scratch/mq-core.mjs crash   # M0：确认时机（before / after / after-dedup），真子进程被杀
node message-queue-cloud/.scratch/mq-core.mjs bench   # M2：outbox 三臂；M3：退避重投实测间隔；M6：幂等键四臂
```

**边界**：这套模型是「SQLite 任务表 + 独立 worker 进程」，不是 RabbitMQ / Kafka / Redis Stream 的等价实现。它证明的是**确认时机、重投、幂等这三条因果**，不证明任何代理的性能或集群行为。代理侧的表述单独立一节，标明文档依据与核实日期。

</Callout>

## 决定你丢消息还是重复消息的，是确认那一行代码写在哪

`crash` 模式用 `child_process.spawn` 起真实的 worker 子进程，在它执行到指定位置时把进程杀掉（`process.exit`，不走 `finally`，不优雅退出），然后由驱动进程做一次恢复扫描：把卡在 `claimed` 的行退回 `ready`，重新投递，数副作用表。三种确认时机的真实输出：

```text
=== M0 真崩溃：确认时机决定是「丢」还是「重」 ===
   [worker] before：已标 done，副作用还没写 → 此刻被杀
   before      崩溃前：done里没副作用=1 条（丢），已领未确认=0 条（可重投）  → 重投 0 次后：done=3/3 副作用行数=2（不同 job=2，重复=0） 墙钟=364ms
   [worker] after：副作用已落库、还没确认 → 此刻被杀
   after       崩溃前：done里没副作用=0 条（丢），已领未确认=1 条（可重投）  → 重投 1 次后：done=3/3 副作用行数=4（不同 job=3，重复=1） 墙钟=501ms
   [worker] after-dedup：重复投递被幂等表挡下，changes=0，副作用没做第二次
   after-dedup 崩溃前：done里没副作用=0 条（丢），已领未确认=1 条（可重投）  → 重投 1 次后：done=3/3 副作用行数=3（不同 job=3，重复=0） 墙钟=501ms
   读法：before 的丢是「库里显示已完成、副作用从没发生」，恢复扫描看不见它；after 的重复是必然代价；after-dedup 用幂等表把重复的副作用归零。
```

把它翻成一句话的表格：

| 确认放在 | 崩在中间的结果 | 恢复扫描能不能救 | 数字 |
| --- | --- | --- | --- |
| **副作用之前**（先标完成） | **丢**：状态显示已完成 | **不能**——扫描只找 `claimed`，这行是 `done` | done里没副作用=1，重投 0 次后副作用只有 2 条（本该 3） |
| **副作用之后**（先做再确认） | **重**：副作用已落库，消息还会再来一次 | 能 | 重投 1 次后 done=3/3、副作用 4 行、重复 1 |
| **副作用之后 + 幂等表** | 重投仍然发生，但**重复的副作用被挡掉** | 能 | 重投 1 次后 done=3/3、副作用 3 行、重复 0 |

**第一行是本章最重要的图。**「先标完成再做副作用」看起来更安全（至少不会重复），它的问题不是会丢——所有方案都会丢一点——而是**它丢得无法发现**。恢复扫描的判据是「有行被领走但没还回来」，一个已经标成成功的行在它眼里就是做完了。你只有在用户投诉「没收到邮件」的那天，才会知道三个月里丢了 200 封。

而「先做再确认」丢不了，代价是会重复。所以这个领域的第一条实用结论是：**先选「会重复」的那一边，然后想办法让重复无害**。这不是妥协，是因为「重复」可查（`SELECT job_id, count(*) FROM effects GROUP BY job_id HAVING count(*) > 1`），「无法发现的丢失」不可查。

## 生产侧：业务写和消息写必须在同一个事务里

`res` 表存业务数据，`jobs` 表是任务表。三臂实测（原文）：

```text
=== M2 生产侧：业务写与任务写不在一个事务里，就会出现「库里没这个人、队列里却有他的邮件」 ===
   没有 outbox：任务已进队列，业务写抛 [NOT NULL constraint failed: res.name] → res=0 jobs=1 ← 幽灵消息，worker 会给一个不存在的人发邮件
   outbox 同事务提交：res=1 jobs=1，一条用户配一条消息
   outbox 同事务回滚：捕获 [NOT NULL constraint failed: res.name] → res=1 jobs=1（仍是上一条的形状，没有多出第三条消息）
```

`res=0 jobs=1` 就是开头那个「给不存在的人发邮件」的形状，而且它是真实报错触发的，不是编的：`NOT NULL constraint failed: res.name`。

正确形状只有两个 INSERT 放进同一个事务：

```sql
BEGIN;
INSERT INTO res (id, name) VALUES (2, 'bob');            -- 业务写
INSERT INTO jobs (id, kind, biz_key, created_at)
  VALUES (2, 'mail', 'user-2', 1760000000000);           -- outbox：同事务里记一条待投递
COMMIT;
-- 之后由一个轮询器把 jobs 里的行投给真正的代理，投成功才标 done
```

第三臂（回滚）证明的是「同事务」这个做法的另一半价值：业务写失败时消息也一起消失，不会留下幽灵。

**但这里有一个几乎所有教程都跳过的洞**：如果消息已经投进代理，而你的应用进程在 `COMMIT` 之后、`ack` 之前崩了——**这条消息投出去过，你却不知道它投出去过**。轮询器重启后会再投一次，于是重复。想完全避免，需要代理支持「消息身份幂等」（同一个 `mid` 投两次只留一份），这不是所有代理都有，而且各家机制不同，本章不作断言。

工程上接受的做法是：**允许生产侧偶尔重复投递，把「重复无害」的责任交给消费端幂等**。这就是 outbox 模式的标准取舍，也是下面那节存在的全部理由。

## 退避重投：「隔多久重试」和「实际隔多久」是两个数

配置写的是 `base=100 × 2^(n-1)`、上限 800 毫秒，三次尝试。实测（原文）：

```text
=== M3 退避重投：实测每次尝试之间的真实间隔，以及上限之后进死信 ===
   三次尝试发生在 +2ms / +145ms / +380ms（相对开始）；相邻间隔=2ms / 143ms / 235ms
   对照配置：退避应为 100ms、200ms（base=100×2^(n-1)，cap=800），实测多出来的部分是每条 20ms 的处理耗时 + 5ms 的轮询粒度 + 调度抖动——「退避多久」和「实际隔多久」是两个数，别在文档里只写前者
   死信行：{"id":1,"state":"dead","attempts":3,"reason":"max attempts reached"}
```

三条实用结论：

- **观测到的间隔 = 退避 + 处理耗时 + 轮询粒度 + 调度抖动。**这里 143 毫秒对配置 100 毫秒、235 毫秒对配置 200 毫秒，差出来的正是每条 20 毫秒的处理与 5 毫秒一次的轮询。**如果你把退避配成 100 毫秒却期望「100 毫秒后重试」，你的监控阈值就要按观测值设。**
- 轮询式恢复有天然的下限精度：轮询间隔 5 毫秒意味着任何小于 5 毫秒的退避都无效。
- **上限必须存在，且用完要有去处。**那行 `state='dead'` 加 `reason='max attempts reached'` 是第 4 章死信队列的全部内容；没有上限的重投是毒丸循环（第 4 章会测出它把后面 5 条正常消息卡成 0/5）。

重投的正确触发条件是「这条消息被领走但没能完成」，实现上有两种：显式失败（消费者主动 nack / 写回 `ready` 并推后 `next_at`），或者超时回收（别的进程死了没来得及说）。后者的真实代理机制叫可见性超时 / pending 认领，**本章不给任何代理的默认秒数**，只提醒：这个值必须大于你的最长正常处理时间，否则一条慢但成功的消息会被反复并发执行，自己制造重复。

## 代理侧的事实：哪些是文档，哪些是我们没验的

这一节单独存在，是因为前面所有实测都发生在 SQLite 任务表上，不能拿来推断代理。以下是本章用到、且在 2026-10-19 通过 RabbitMQ 官方文档核对过的表述：

- 消费者确认默认是**开启**的（`autoAck` 默认为 `false`），也就是「不显式确认就不算消费完成」是默认安全的一侧。
- `basic.ack` 带一个 `multiple` 参数，为真时会一次确认该 delivery tag 之前的所有消息——这解释了为什么「批量确认」能把吞吐提上去，也解释了它的风险：**确认了一条等于确认了一片，其中夹着一条实际没做完的**。
- `basic.nack` / `basic.reject` 的 `requeue` 为真会把消息放回队列；为假则丢弃或按队列的死信配置转走。
- **未确认的消息在通道或连接关闭时会自动回到队列**。这条很重要：进程崩溃时消息不会因为「已经被投出去过」而消失，代理替你把这一类丢兜住了。
- 文档同时警告重投可能造成循环——正是第 4 章毒丸问题的来源。

<Callout type="unverified">

以下是**本机没有验证**、也不要在本项目里假设的部分：队列 / 消息的持久化标志与刷盘语义、镜像队列或仲裁队列的副本行为、集群节点故障时的消息恢复、Kafka 的 ISR 与 acks 参数、Redis Stream 的持久化与消费者组细节。这些都需要真实环境才能观察，本站只给判据：**凡是影响「丢不丢」的配置项，都要用一次真故障来验证，别用配置名来推断。**

另外，上面这几条是 RabbitMQ 文档的表述，代理实现会变；动手前请以你使用的版本的官方文档为准（入口见文末），不要把本节的措辞当成长期事实。

</Callout>

## 幂等：键的粒度决定了幂等等于没做

同一段带唯一约束的幂等表，四种键的选择，各投几次，数 `changes` 与副作用（原文）：

```text
=== M6 幂等键选错，幂等就等于没做 ===
   键=消息 id｜同一条消息被投 2 次                    changes=[1,0] 副作用=1 次
   键=消息 id｜用户连点 2 次（两条消息、同一 order-7）  changes=[1,1] 副作用=2 次
   键=业务动作｜同样两次点击                          changes=[1,0] 副作用=1 次
   键=业务动作｜同一业务动作的消息重投 3 次             changes=[1,0,0] 副作用=1 次
```

`changes` 数组是那条幂等插入语句每次受影响行数的实录：`1` 表示插进去了（第一次，允许做副作用），`0` 表示被唯一约束挡下（已做过，跳过副作用）。所以 `[1,0,0]` 就是「三投一做」。

第二行和第三行的对比是全章的核心：**同一个连点两次的场景，键用消息 id → 副作用 2 次；键用业务动作 → 副作用 1 次。**因为两次点击产生的是两条不同的消息（两个 id），但它们是同一个业务动作（`order-7-扣券`）。

```js
// 幂等表：主键就是幂等键
db.exec('CREATE TABLE dedup (mid TEXT PRIMARY KEY, job_id INTEGER NOT NULL, done_at INTEGER NOT NULL);');

const key = 'order-7:refund';        // 业务动作，不是消息 id
const r = db.prepare(
  'INSERT INTO dedup (mid, job_id, done_at) VALUES (?, ?, ?) ON CONFLICT(mid) DO NOTHING',
).run(key, jobId, Date.now());

if (r.changes) doSideEffect();       // changes=1 才是第一次；changes=0 说明这动作已经做过
```

**`ON CONFLICT DO NOTHING` 而不是先查再插。**先 `SELECT` 再 `INSERT` 是同一个「两个动作之间的窗口」问题（第 2 章 M7b 实测过它的代价：6 条消息投出 18 次执行、重复 12 次）——两个并发消费者会同时查到「没做过」，然后各插一条、各做一次。唯一约束 + 冲突忽略把这两步压成一个原子动作，`changes` 是那个原子操作的返回值。

幂等实现有三种，各有失效场景：

| 做法 | 形状 | 适合 | 会失效的时候 |
| --- | --- | --- | --- |
| **唯一键表**（dedup 表） | `INSERT ... ON CONFLICT DO NOTHING`，看 `changes` | 副作用在别处（发邮件、调第三方） | 幂等表和业务写不在同一个库时，两边不原子 |
| **状态机条件更新** | `UPDATE orders SET state='paid' WHERE id=? AND state='unpaid'` | 副作用就是改自己库里的状态 | 需要跨多张表的复合动作时，条件更新只挡一张表 |
| **操作本身可交换** | 用 `SET x = 值` 而不是 `x = x + 1` | 数值型写入 | 语义变化：扣库存这类天然累减的操作不能改成 SET |

第二种常常比第一种便宜：它不需要额外的表，而且条件更新的 `changes` 天生就是「我是不是第一个」。局限在跨表与外部副作用——发信、扣款这些动作发生在你的库之外，必须回到 dedup 表。

## 幂等挡不住的那一半：对端也收到过重复

幂等表管的是**你这边**别做第二次。它管不了三种情况，这三种在实践中比前两种更常出事：

1. **你的 dedup 记录写成功了，外部调用也发出去了，但外部系统的响应丢了。**你不知道它成没成；重试时幂等表显示「已做过」，于是**你既不重试也不补救**——这条消息永远停在半途。修法：幂等记录要有「进行中 / 已成功」两种状态，而不是一个布尔；进行中且超时的必须回到重试队列。
2. **对端有它自己的幂等窗口，而你的键不在它的窗口里。**发信服务一般按「收件人 + 模板 + 时间窗」去重，你传的 `job_id` 它不认识。修法：把你生成的幂等键作为请求参数传给对端（很多 API 支持 `request_id` / `X-Idempotency-Key` 一类字段），让两边用同一个键。字段名以你所用服务的文档为准。
3. **副作用已经不可逆**（短信发出去了、钱扣了）。这时幂等只是防止更多，不能撤销。唯一实用防线是先攒着别做（延迟 + 合并 + 人工闸门），这在第 4 章延迟消息里会用到。

这三种都指向同一个结论：**幂等是跨系统的键约定，不是本系统的一行 SQL。**只在自己库里建唯一索引，然后假设「重复没了」，是这一章最贵的误解。

## 常见错误与排查

**1. 现象：没有消息丢失的告警，但用户偶尔收不到东西，且永远查不出来为什么。**
原因：确认写在副作用之前（M0 的 `before` 臂），丢了但状态显示完成。
怎么确认：`SELECT count(*) FROM jobs j LEFT JOIN effects e ON e.job_id=j.id WHERE j.state='done' AND e.id IS NULL`——这个数不为 0 就是这个 bug。
怎么修：把确认移到副作用之后，接受重复并加幂等；或者让「标完成」与「副作用写库」在同一事务里（仅当副作用就在同一个库时可行）。

**2. 现象：明明加了幂等，用户连点两次还是收到两封邮件。**
原因：幂等键用了消息 id（或用了每次点击都新生成的值），两次点击是两个键。
怎么确认：`SELECT biz_key, count(*) FROM jobs GROUP BY biz_key HAVING count(*)>1`；再看 dedup 表里那两行的键值是不是一样。
怎么修：键换成业务动作标识（`order-7:refund`），M6 的第二、三行就是这一改的前后对照（2 次 → 1 次）。

**3. 现象：重启之后一段时间里，重复消息暴增。**
原因：恢复扫描把所有 `claimed` 一律退回 `ready` 重投，包括那些其实**已经做完、只差确认**的。
怎么确认：按 `attempts` 分布看，`attempts` 大于 1 的行如果副作用已存在，就是被无谓重投的。
怎么修：重投前先查幂等；并且区分「超时回收」和「主动失败」两种重投，回收窗口要大于最长处理时间（这条在真实代理上就是可见性超时，秒数以官方文档为准）。

**4. 现象：一个下游接口挂了 5 分钟，重投把它的 QPS 打到平时的三倍，恢复得更慢了。**
原因：固定间隔重投 = 在下游已经过载时叠加压力。退避的方向错了（没退避、或退避幅度太小、或没有上限之外的熔断）。
怎么确认：把下游错误率曲线与你的重试速率曲线叠在一起看；重试速率与到达速率同向上升就是它。
怎么修：指数退避 + 抖动（同一批消息不要同时在同一时刻重试）+ 重投上限。实测的退避间隔与配置的差值参见 M3 那行数据：观测值 143/235 毫秒对配置 100/200 毫秒，规划容量时用观测值。

**5. 现象：本地跑「重复消费」的测试，永远测不出重复。**
原因：你的副作用表用了 `job_id` 做主键——重复插入直接被唯一约束挡掉，测试断言「库里只有一行」自然成立，于是**「执行了两次」这件事在数据模型层面根本无法表达**。
怎么确认：把副作用表换成自增主键（能数出「做了几次」），再跑同一个测试。**这是我自己踩过的：初版脚本的 effects 表以 job_id 为主键，「重复」在数据模型层面根本不可表达，直到改成自增主键才测出 M0 里那个「重复=1」。**
怎么修：测量设施必须能观测你声称的问题。用 `count(*)` 与 `count(DISTINCT job_id)` 两个数一起断言，差值就是重复次数。

**6. 现象：加了幂等表之后，偶尔报数据库唯一约束错误，接口 500。**
原因：用了普通 `INSERT`（没写 `ON CONFLICT`），并发到达的两条同键消息里，后到的那个撞约束抛异常，而这段异常没被当成「已经做过」来处理。
怎么确认：看报错原文。本机实录（Node v25.4.0 的 SQLite 错误形状）：

```text
Error: UNIQUE constraint failed: dedup.mid
  code: 'ERR_SQLITE_ERROR',
  errcode: 1555,
  errstr: 'constraint failed'
```

怎么修：**撞唯一约束在幂等语义下是正常结果，不是异常。**要么写 `ON CONFLICT(mid) DO NOTHING` 然后看 `changes`，要么 `catch` 之后按「已处理过」返回成功。用后者时务必只针对唯一约束错误，别把连接失败也当成幂等命中——那会静默丢消息。

要求：把幂等插入写成普通 `INSERT`（不带 `ON CONFLICT`），让两个并发消费者同时处理 `key='order-7:refund'`。记录完整报错、你以为会发生什么、实际发生了什么、以及正确的写法。

<template #answer>

本机实录的报错：

```text
Error: UNIQUE constraint failed: dedup.mid
  code: 'ERR_SQLITE_ERROR',
  errcode: 1555,
  errstr: 'constraint failed'
```

这件事**不是故障，是正确性的证明**：唯一约束挡住了第二个插入者。故障在于你把它当异常抛出接口——那会让用户看到 500，而事实是「这件事已经做好了」。

正确写法是把冲突变成返回值：

```js
const r = db.prepare('INSERT INTO dedup (mid, job_id, done_at) VALUES (?, ?, ?) ON CONFLICT(mid) DO NOTHING').run(key, id, Date.now());
if (!r.changes) return { status: 'duplicate-ignored' };   // 别的消费者已经做过
await doSideEffect(id);
```

实测对照：本章 M3/M6 里的 `changes=[1,0,0]` 就是这条语句在三次投递下的返回值序列，副作用做了 1 次。

反过来说：如果第一次插入失败是因为连接断了，你也返回了 `duplicate-ignored`，那这条消息就永远不会被处理——所以 catch 分支必须只针对唯一约束（判 `errcode` 或错误消息），不能笼统吞异常。

<Exercise title="用 outbox 消灭幽灵消息，并说明它消灭不了哪一种" difficulty="进阶">

要求：把「投消息 → 写业务」的顺序改成「写业务 + 写 outbox（同事务）→ 由投递器投出」，给出你测试的三臂形状；然后诚实回答：这个做法消灭不了哪种不一致，为什么只能靠消费端。

<template #answer>

三臂形状与本章 M2 实测一致：

```text
没有 outbox：res=0 jobs=1        ← 幽灵消息（业务写失败，消息已在队列）
同事务提交：  res=1 jobs=1        ← 一条业务配一条待投递
同事务回滚：  res=1 jobs=1        ← 失败时消息一起消失，没有多余行
```

消灭不了的那种：**消息已经交给代理、但投递器在收到代理确认之前崩了**。代理手里有这条消息，outbox 表里那行还是「未投递」，于是重启后再投一次——重复。outbox 只保证「业务成立则消息一定投出」和「业务失败则消息一定不投出」，它不保证「只投一次」。

只能在消费端解决的原因：投递次数不由你控制（网络重试、代理重投、恢复扫描都会增加它），**唯一由你控制的是「做几次」**。所以链路是：outbox 保证不漏投 → 允许重复投 → 幂等保证重复无害。这三段各解决一件事，缺一段就有一类事故。

想再压缩重复投递，需要代理侧的消息身份去重能力；这不是所有产品都有，本站不作断言，选型时按官方文档核对（第 6～9 章）。

</template>

</Exercise>

```js
for await (const msg of queue) {
  await db.prepare("UPDATE jobs SET state='done' WHERE id=?").run(msg.id);
  await mailApi.send(msg.payload);
  await db.prepare('INSERT INTO effects (job_id, made_at) VALUES (?, ?)').run(msg.id, Date.now());
```

<template #answer>
