# 云服务基础：短信、邮件与第三方 API：对方回你 200，只说明它收下了

第一个故事发生在注册链路上。接口 200、日志干净、监控没有一条异常，运营却说「用户收不到欢迎邮件」。你查代码找不到问题，因为**代码确实没错**：发信服务返回了成功，而它的「成功」表示「这条我接了，接下来我来想办法」，不表示「对方邮箱收下了」，更不表示「用户看见了」。真正失败的那一步发生在你的进程之外，而你从来没有去取那部分结果。

第二个故事是验证码短信。某个促销时段成功率从 99% 掉到 60%，你的代码把所有失败都归成同一个「发送失败」，用户疯狂点重发，触发了运营商侧的频控和风控，成功率进一步掉到 20%。事后复盘，最初那一波是模板被服务商驳回过一次、线上用的是被限流的那条通道——而**这些原因在你自己的日志里根本不存在**，它们只存在于服务商的回执和状态说明里。

第三个故事方向相反。你接了一个第三方回调（支付结果通知），没校验签名、没做去重，对方按它的重试策略投递了三次，你的代码很诚实地执行了三次入账。

三个故事指向同一个判断：**通知与第三方 API 的难点不在调用，在语义**。这一章讲的不是你调哪个 SDK，而是四件事：一条消息从你的代码到用户眼前要穿过几层、每层谁能告诉你结果；哪些失败可以重试、哪些重试只会更糟；回调怎么才可信；以及怎么让「换一家服务商」不要变成「改一遍业务代码」。

<Callout type="unverified">

**本章没有云账号，也没有任何本机实测**：没注册过发信或短信服务、没真发过一条短信、没接过一个真实回调。所以本章**不写**厂商名、产品名、字段名、错误码、签名算法、模板与报备的具体流程、计费单价——这些全部必须回到你所选服务商的现行文档核对，写了就是编造。

有一项外部依据本次没能取到：写作时尝试抓取邮箱服务商公开发信者要求页面，三次请求均未成功（一次被拦截、两次连接失败）。因此关于邮件认证与退订要求，本章只讲**机制和它们各自解决什么问题**，不引用任何条文原文、不写阈值数字。落地前请以你的发信服务与目标邮箱服务商的现行要求为准，不要用本章替代合规检查。

</Callout>

## 「发出去了」有四层，你的代码通常只知道第一层

```text
你的服务 →（1 受理）→ 发信服务 →（2 投递）→ 对方收信服务器 →（3 送达）→ 用户邮箱/手机 →（4 触达）→ 人看见了并行动
```

| 层 | 谁给你证据 | 拿不到时会怎样 | 最常见的误解 |
| --- | --- | --- | --- |
| 1 受理 | 你这次 API 调用的返回 | 完全不知道失败 | 「返回成功 = 用户收到了」 |
| 2 投递 | 服务商的回执/状态查询/回调 | 失败发生在你的视野之外 | 「对方拒收会当场报错」 |
| 3 送达 | 打开事件、投放分类（收件箱或垃圾） | 你无法知道进了垃圾箱 | 「进了垃圾 = 对方故障」，实际常是你的发送声誉 |
| 4 触达 | 你自己业务侧的转化（点链接、填验证码） | 只能猜 | 「转化率下降是产品问题」，有时只是邮箱换了服务商 |

第二层是最该补的，而且它的技术形态决定了第三、四层能不能观测：**回执/回调**（服务商把结果推给你）或**状态查询**（你按消息 ID 去问）。两者都要求你为每次发送留下一个可回查的标识，并在自己的库里保存「这条消息对应哪个业务动作」——这一步做不出来，后面所有的送达优化都无从谈起。

第三层的证据大多来自服务商提供的统计能力（打开、点击、退信分类），它的可信度和可用性各家差异很大，本章不评价。你要知道的是它的存在与用途：**当你怀疑「用户没收到」时，先用第二、三层的证据把问题分层，再去改文案**。分层顺序错了，你会花一周优化一封本来就发不出去的信。

## 邮件：两种接法，和「250 之后事情才真正开始」

邮件协议的老底子决定了它的失败形状：SMTP 是**收件服务器说「我收下」就算成功**的协议。你在对话里拿到的那个接受响应，含义是「对方愿意接手并尽力投递」——接受之后因为邮箱不存在、用户已退订、内容被判垃圾而失败，都只能事后通过退信通知你。这不是某家的缺陷，是协议语义。

于是有两种接法：

| | 直连 SMTP | 走发信服务的 HTTP API |
| --- | --- | --- |
| 你要维护什么 | 连接、重试、退避、连接池、临时失败与永久失败的区分 | 一次带超时的请求，剩下的对方负责 |
| 「成功」的含义 | 对方收件服务器接受了这一封 | 服务商受理了这一封 |
| 失败通知 | 退信邮件（bounce）落到你的回弹地址，需要你自己解析 | 状态查询或回调，结构化 |
| 与你的技术栈 | 需要长连接与队列语义，异步性弱 | 天然是异步任务，可重试可幂等 |
| 声誉与投递率 | 主要由你的出口 IP 与域名历史决定，个人项目几乎没有筹码 | 由服务商的池子承担，代价是账号级共享风险 |

推荐组合只有一种：**业务代码只写「要发」，把「怎么发」交给异步 worker + 发信 API**。理由不是 API 更时髦，而是它和[第 1 章](/message-queue-cloud/why-async)、[第 3 章](/message-queue-cloud/reliable-delivery)的结论严丝合缝——邮件是典型的「又慢又可能失败的非核心副作用」，本就不该站在注册请求的主链路里；而 HTTP API 有明确的请求边界，方便你放超时、放幂等键、放重试退避。直连 SMTP 意味着你还要自己实现一套队列与退避，那是把已经解决的问题再解一遍。

自建 SMTP 中继这条路要单独劝退：投递率主要由**出口 IP 的历史声誉**决定，新 IP 没有历史、共享不出名，被主流邮箱直接拒收或判垃圾是常态。这个判断与任何厂商无关，也和你的代码质量无关，靠的是时间与量级的积累——这恰好是个人项目最缺的两样。

**发送身份是三件不同的事**，搞混了会「什么都配了还是进垃圾」：一是**你用哪个域名发**（发件地址的域必须是你能改 DNS 的域，用服务商的默认地址发等于借用别人的身份，且以后换厂商全部链接失效）；二是**域名上的认证记录**，通常说三件套，它们各解决不同问题——一个声明「哪些服务器被允许代表这个域发信」，一个给邮件本身加上密码学签名以证明未被篡改，一个声明「验证失败时收信方该怎么办、以及报告寄到哪」。前两者都通过还不等于第三个通过，因为**对齐**（alignment，指域名之间要一致而不是各说各话）才是收信方真正用来判定身份的那一刀。三者的记录怎么填、要求到什么程度，本章不写：属于必须核对厂商与目标邮箱现行要求的部分。三是**回弹地址**——没有它，第二层的失败信息无处可去。

**退信要当数据问题处理，不要当重试对象**。硬失败（地址不存在、域无效）重试一万次也不会成功，正确动作是把该地址标记为不可投递并停止发送；软失败（对方暂时不可用、超额）才有重试价值，而且要退避。这套分类与[第 3 章](/message-queue-cloud/reliable-delivery)里「哪些消息该进死信」的判断完全同构。

还有一条与成本无关但会毁掉账号的区分：**事务邮件和营销邮件不是同一类东西**。前者由用户动作触发、用户期待收到；后者是你在打扰。把它们用同一个域名、同一个通道混发，风险是共担的——营销侧的投诉会拖低事务侧的投放分类，于是你的验证码开始进垃圾箱。分开通道、分开域名、分开频控，是每个「顺手发点推送」的功能都该付的架构成本。

开发阶段请**不要真发信**。三种做法按优先级：本地起一个只收集不投递的接收服务并把所有发送指向它；或者在 worker 里加一层「非生产环境只写日志不投递」的开关；或者用服务商的沙箱模式加收件人白名单。三种都要保证一件事：**代码路径是同一个**，否则你测的是「不发信的路径」。

## 短信：内容不是你想发就发

短信和邮件最大的结构差别是**它不是自由文本**。通行的模型是：一个经过审核的**模板**、一个经过报备的**签名**、模板里允许若干**变量**。这意味着三件对工程师很不直观的事：

**文案变更是发布流程，不是配置热改。** 你想在验证码里加一句「请勿转发」，需要提交模板重新审核，审核期间线上发的还是旧文案。所以把短信文案当常量硬编码在代码里，等于把「改一句话」变成「改代码 + 发版 + 等审核」——**模板 ID 放在配置里，文案留在服务商侧**，是这条链路上少踩坑的做法。

**按长度分段计费。** 一条能容纳的字符数是有限的，超出就拆成多条分别计费；变量长度会直接影响最终条数。所以「把用户名塞进模板」这种顺手写法，可能让单价变成两三倍。字符集（是否包含非 ASCII）也会改变每段容量，各家规则本章不写，属必核对项。

**提交响应和回执是两件事。** 你调用发送接口拿到的成功，属于本章四层模型的第一层；真实结果要等回执报告，回执本身可能有延迟、可能拿不到全部、也可能只给分类不给原因。没做回执处理的短信系统，等于把成功率指标建立在「对方没当场报错」上。

验证码短信还有三个纯工程问题：重发按钮必须有冷却，否则用户手动触发的重试正好命中风控；同号码、同设备、同 IP 三个维度都要限（维度只做一个等于没有）——这套限流的做法在[分布式会话、限流与幂等](/data-storage/session-rate-limit-idempotency)里已经讲过，短信只是它最贵的应用场景；验证码有效期与「一次有效」要在服务端判定，而不是靠文案写「5 分钟内有效」。

最后是最该说的一句：**短信是按条付费的，成本随用户量线性增长，而且它常常是可替代的。** 在写「接个短信服务」之前先问能不能不发——邮件、应用内消息、站内通知、把验证从「证明你能收到这个号」改成「证明你控制这个邮箱 + 手机号仅用于找回」，都是合法答案。真需要短信时，也先算清楚「一个注册用户要发几条、峰值多少、单价量级」，再决定它是不是核心链路的必经环节。国际短信还要叠加各国规则差异，本章一律不写，请以服务商的分国家说明为准。

## 第三方 API 的通用对接：八件你必须自己做的事

换掉「第三方」这个词，下面八条对支付、地图、翻译、大模型、发信全部成立。这一节是本章真正可迁移的部分。

```js
// 骨架示例：未在本机对任何真实服务运行过，只表达结构，字段名与错误码请以对方文档为准
const OUTBOUND_TIMEOUT_MS = 5_000;
const RETRYABLE = new Set([429, 500, 502, 503, 504]);

async function callProvider(task, attempt = 0) {
  const signal = AbortSignal.timeout(OUTBOUND_TIMEOUT_MS);      // 1 超时：每次调用都有
  const res = await fetch(endpoint, {
    method: 'POST',
    signal,
    headers: { authorization: `Bearer ${process.env.PROVIDER_KEY}`, 'idempotency-key': task.id }, // 3 幂等键 + 7 密钥
    body: JSON.stringify({ template: task.templateId, to: task.to }),                             // 模板 ID 来自配置
  });
  if (res.ok) return await res.json();
  if (!RETRYABLE.has(res.status) || attempt >= 4) {
    throw Object.assign(new Error('provider rejected'), { fatal: true });                          // 2 不可重试就停
  }
  const wait = Math.min(2 ** attempt * 300, 8_000) * (0.5 + Math.random());                        // 退避 + 抖动
  await new Promise(r => setTimeout(r, Math.max(wait, retryAfterMs(res)));                         // 4 尊重对方的 Retry-After
  return callProvider(task, attempt + 1);
}
```

八件事里代码覆盖了四件，另外四件是**代码之外的约定**：

**5 契约与版本。** 不要解析人类可读的错误文本来判断失败类型，那是对方的文案，改起来不需要通知你；只依赖状态码与结构化的错误字段。对方字段改名、枚举值增加、错误码语义变化，是第三方对接里唯一确定会发生的变更，所以**对未知取值要有默认分支**，而不是 `switch` 完事。

**6 密钥的边界。** 密钥进环境变量或密钥管理，不进代码库、不进构建产物、**尤其不进前端**——浏览器里能看到的字符串等于公开。不同环境用不同密钥，出问题时你能靠「哪把密钥被用了」定位；共用一把密钥的系统，一次泄露要全量轮换。轮换要留重叠期（新旧同时有效一段时间），否则「先改配置还是先换密钥」会变成一次线上事故。

**7 观测按调用计费。** 至少四项：成功率、P99 延迟、你的重试放大倍数（发出去多少次 vs 业务要多少次）、当前积压。第三项最容易被忽略，它意味着你为了一个业务动作向对方付了多次钱。另外要知道：**配额通常是账户级共享的**，你的测试环境和生产环境跑同一把密钥时，是在同一份配额里互相抢。

**8 降级要写明用户可见后果。** 每条链路提前回答「它挂了怎么办」：验证码（换通道，或允许邮箱通道兜底）、订单通知（迟发可以，改成站内可见）、周报（不发即可）。答案的强度取决于业务，但**没有写下来的降级，在故障时等于没有**——因为那时做决定的是凌晨的你。

## 回调：把「他告诉你」做成可信的

方向反过来时，你从调用方变成被调用方，风险清单完全不同。你的服务要公网暴露一个接口，而这个接口的可信度必须由你建立，不是由对方保证。

**先验证来源。** 通行做法是对方用一个共享密钥对请求体做签名，你把同一密钥重算一遍比对。**这只在两个前提下有效**：比较要针对原始字节（不是解析后重新序列化的结果，字段顺序与空格都会变），以及密钥本身不能出现在 URL 里（日志会留下它）。校验失败要拒绝并单独记一条指标——回调验签失败是攻击或配置错误的信号，混进普通错误里就永远不会被发现。

**再假设它会重放。** 投递方按「你没回 2xx 我就重发」的策略工作，所以至少一次到达是默认预期。这与[投递语义](/message-queue-cloud/delivery-semantics)是同一件事，只是发生在 HTTP 层。做法是把「事件唯一标识」写进一张去重表并加**唯一约束**，插入失败就当作「已经处理过」直接返回成功——去重表与业务写入要在同一事务里，否则你还是会在崩溃点上重复执行（事务的边界见[事务](/database/transactions)）。

**还要假设它乱序。** 同一订单的「退款成功」可能先于「支付成功」到达。判定依据必须是**事件自带的时间或序号**，不是到达顺序。看到「状态从成功变回待支付」就报错，是这一类对接里最常见的线上误警。

**先应答，还是先处理？** 常见建议是尽快返回 2xx、把真正的处理丢进队列，因为对方的超时通常很短，你在响应路径里同步做重活会导致它超时重发、然后你真的处理两遍。但要诚实看清代价：**你一旦应答，就等于承诺「这件事我记下了」**，所以「落库」必须发生在应答之前——落一条待处理记录、再应答、再由 worker 消费。跳过落库直接应答，进程一挂消息就凭空消失，那比慢一点严重得多。这套「先落库再应答」与[可靠投递](/message-queue-cloud/reliable-delivery)里的确认顺序是同一个道理。

最后一条最容易被忽略：**回调地址和密钥是需要维护的配置**。换域名、换环境、迁移服务商时，忘记在对方侧改地址的结果是「一切正常但通知全丢了」——因为你的服务没错，只是没人再来找它。

## 不用上整套云：把厂商调用收进一个模块

本章的落点和[第 10 章](/message-queue-cloud/object-storage-and-cdn)的兼容层思路一致：**通知能力是最适合「只用第三方 API、不上整套云平台」的能力**，因为它本来就只有一个 HTTP 边界，输入输出都很窄。窄边界的意义是你可以把「换厂商」做成一个文件的改动。

三条具体做法：

**接口里不出现厂商词汇。** 你自己的函数签名应该讲「发给谁、内容是什么、什么时候有效」，而不是对方的模板字段名、状态枚举和错误码。厂商的表示法在适配层内翻译完，翻译不了的（比如它独有的回执分类）降级成你自己的类别。这和[分层架构](/backend/layered-architecture)里「让换掉数据库只改一个文件」是同一种设计，只是换了一个依赖对象。

**把「哪个通道、哪个模板、什么频控」做成配置。** 文案与模板 ID 留在服务商侧（上一节的原因），通道选择与开关放在你的配置里，两侧都不需要发版就能改——除了模板本身，那个确实要审核。

**「要发」与「怎么发」之间放一张表或一条队列。** 前者由业务写入，后者由 worker 消费。这一层一旦存在，多厂商路由、按通道降级、失败重投、以及「用户到底收到没有」的回查都有了落脚点；没有它，所有这些都只能塞进请求处理函数里，然后你就会得到本章第一个故事那种「200 但没人收到」。

## 常见错误与排查

1. **把 API 成功当成用户收到。** 症状：用户说没收到、你的日志全是成功。排查顺序：先看有没有回执/状态查询能力并真的取了值；再看发送身份与域名认证是否配全；最后才看内容。判据：能取到该消息的投递结果，而不只是受理结果。
2. **所有失败都重试。** 硬退信、参数错、权限错重试只会拖长积压并放大账单。按状态码分类，永久失败直接标记并不再发送，这条与死信队列的处理一致。
3. **没有超时的外部调用。** 症状：对方变慢时你的 worker 全部卡住、积压暴涨，而错误日志一条都没有。判据：给每个外部调用显式设置上限，并单独统计「因超时而失败」的比例。
4. **回调只验签名不去重，或只去重不验签。** 前者被重放就是重复执行，后者把「能被伪造」当成正常流量。两个都要做，且验签失败要能在指标上单独看见。
5. **文案硬编码在代码里，或模板 ID 写死在业务分支里。** 两种都让「改一句话」变成发版。方向是文案进模板、模板 ID 进配置。
6. **测试环境直接真发。** 除了花钱，还会把测试收件人写进真实用户的退订与投诉统计里，污染账号声誉。判据：确认非生产环境走的是收集或跳过路径，且代码路径与生产一致。

判断下面每条属于四层模型（受理 / 投递 / 送达 / 触达）的哪一层，并说明证据从哪里取。

```text
1 「接口返回成功，任务已入队」
2 「对方收信服务器接受了这一封」
3 「这封邮件被投到了收件箱而不是垃圾箱」
4 「用户点进了邮件里的链接」
5 「回执报告里这条的状态是投递失败」
6 「用户填了正确的验证码」
```

<template #answer>

1 受理；2 投递；3 送达；4 触达；5 **投递**（它是第二层的结果，只是由服务商在事后告诉你——这正是「当场不报错」的含义）；6 触达（更准确说是触达之后的行动，属于你自己的业务转化）。

证据来源分成两类：1 来自你这次调用的返回；2、3、5 只能来自服务商的回执、状态查询或统计能力；4、6 只能来自你自己业务侧的事件。一个可验证的自检问题：**你的系统里能不能对某一条具体消息，把 1→2→5 串成一条链**？串不起来，说明你缺的不是发信能力，是「为每次发送留一个可回查标识并保存它与业务动作的对应关系」。这也是[第 3 章](/message-queue-cloud/reliable-delivery)里消息 ID 与幂等键在通知场景的用法。

</template>

</Exercise>

<Exercise title="三段对接代码的问题在哪" difficulty="进阶">

每段说明：会导致什么症状、怎么确认是这个原因、修好的判据是什么。

```text
A  注册接口里同步调用发信 API，用 await 等它返回，没设超时；失败就抛错让接口返回 500。
B  处理回调时：验签通过 → 直接调用扣款函数 → 返回 200。日志里能看到同一事件 ID 出现三次。
C  catch (e) { if (String(e.message).includes('quota')) { sleep(1000); retry(); } }
```

<template #answer>

**A 同时犯了三条错**：慢操作站在主链路里（用户为发邮件干等，正是[第 1 章](/message-queue-cloud/why-async)的动机）；没有超时（对方变慢时请求堆积，且没有错误日志，症状是「越来越慢直到网关超时」而不是报错）；把非核心副作用的失败升级成注册失败（用户重复注册，产生脏数据）。确认方式：看接口耗时分布是否与对方延迟曲线同步；判据：注册接口不再等待发送，发送走队列，且每个外部调用有显式超时上限与独立的超时指标。

**B 缺去重**。验签做对了，但一次成功扣款对应三次执行——因为回调至少一次到达是默认预期。症状形状是「同一事件 ID 多次出现」，你的日志已经给出来了。修法：事件 ID 进去重表并加唯一约束，插入冲突即视为已处理、直接返回 200，且**去重记录与扣款在同一事务**里（见[事务](/database/transactions)）。判据：手动把同一事件重放多次，账户只变一次；且验签失败的请求有单独指标。另外要检查顺序假设：如果退款事件先到，你的状态机会不会报错。

**C 用文本匹配判断失败类型**，并且固定间隔重试。文案是对方的，改写或本地化之后你的分支静默失效，退化成「所有配额错误都不重试」或「全部重试」——取决于默认分支怎么写。固定间隔还会让所有客户端在同一时刻齐发重试。判据：只依赖状态码与结构化错误字段，未知取值有明确的保守默认（当成不可重试并告警，比当成可重试更安全），重试带指数退避与抖动，并**优先尊重响应里给出的重试提示**。

三题的共同方法：**把「对方的行为」当成不可假设的外部条件**——它的响应时间、它的重试策略、它的文案、它的顺序保证，都不是你能控制的，而你的代码必须对每一样都有默认答案。

</template>

</Exercise>

<Exercise title="设计：三类通知一套系统" difficulty="挑战">

一个产品有三类通知：注册验证码（时效强、失败即流失）、订单状态变更（可迟发几十分钟）、每周使用摘要（营销性质，可完全不发）。你只有一台 VPS，预算要求「通知类月支出有明确上限」，且不希望被单一服务商锁死。

请设计并回答：三类各自走什么通道、为什么；「要发」与「怎么发」怎么分层，表结构里最少要有哪些字段；频控与幂等分别解决哪个风险；退信与回执怎么处理，处理结果影响什么；月度成本上限靠什么机制兜住；以及三处必须回服务商文档核对的点。

<template #answer>

**通道按「时效是否可协商」分**。验证码要短时效强触达：主通道按用户可用凭据选择，并有兜底通道（例如邮箱与短信二选一，另一个作为降级）；订单状态可迟发，走队列 + 邮件即可，站内状态作为唯一事实来源（**通知只是提示，不是记录**——用户没收到邮件也应该能在站内看到订单状态，这一条能挡掉大量「通知可靠性」的过度设计）；周报是营销性质，必须与事务类**分开发、分域名单独管理**，且给用户退出入口，理由见正文里「混发风险共担」。

**分层的最小表结构**：一条待发送记录至少要有——业务标识（哪笔订单/哪次注册）、通道与收件人、内容引用（模板 ID 与变量，不存整段文案）、你自己的消息 ID、状态与状态时间、尝试次数与下次可尝试时间、服务商回执标识。有了「消息 ID + 状态 + 回执标识」，四层模型才可能被查询出来；缺了「下次可尝试时间」，退避与延迟发送只能靠外部调度。这套结构本质上就是[第 2 章](/message-queue-cloud/mq-concepts)说的「任务表 + 轮询」形态——个人项目不一定要引入中间件，先用它能拿到九成的收益（判断线见[第 9 章](/message-queue-cloud/choosing)）。

**频控与幂等是两个不同的风险**：频控保护的是「不要触发服务商与运营商侧的限制」，维度要同时按号码/邮箱、用户、设备或 IP；幂等保护的是「同一件事只做一次」，落在发送记录上用唯一约束（同一次注册只允许一条有效验证码消息）。只做前者会重复扣费，只做后者会被限流——正文里那个成功率从 99% 掉到 20% 的故事，就是两个都缺。

**退信与回执**：硬失败标记地址不可投递并停止后续同类发送（这是数据质量，不是重试问题）；软失败退避重试，超上限进入待人工处理状态（对应[死信队列](/message-queue-cloud/dlq-delay-order)）。回执结果应回写到消息 ID 对应的记录上，它影响的第一个数字是成功率的分母——**用「受理数」算出来的成功率是自欺**，要按拿到投递结果的部分算。

**成本上限靠机制而不是靠记性**：按通道设每日发送条数与账单阈值告警、给营销类设「达到月度量就不发」、把「一次业务动作最多触发几次重试」写死在退避上限里（正文代码里的 `attempt >= 4` 就是这个用途）。没有这三条，成本失控是迟早的事，因为**通知支出由外部流量决定，而你无法预知流量**。

三处必须回服务商文档核对、本站不能替你决定的：短信模板与签名的报备流程、审核时长与变量长度限制（决定你能不能热改文案、单价是多少条）；回执的获取方式、字段含义与延迟范围（决定第二层可观测性能做到什么程度）；邮件认证的记录要求、回弹地址形态，以及各家对批量发送方的现行要求（正文已声明这部分未核实）。

会被反驳的地方：只靠一张任务表 + 轮询，在峰值时会出现「扫表压力」和消费延迟抖动。诚实的答案是先接受它，并设两条重算信号——积压常态化为分钟级、或你需要多 worker 与路由规则；到那时再按[第 9 章](/message-queue-cloud/choosing)引入队列，而不是第一天就上。

</template>

</Exercise>
