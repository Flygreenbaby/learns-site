# 用户在等的那三秒里，大部分工作根本不该由他来等

注册接口要依次做「写数据库 → 发欢迎邮件 → 初始化默认数据 → 打点上报」，用户点了按钮之后盯着转圈的图标等了 3 秒。数据库那次写入其实只花了 2 毫秒。剩下 2998 毫秒里，用户在替一个第三方邮件服务的网络往返买单——而那封邮件晚 5 秒到达，没有任何人会察觉。

第二天早上了另一件事：邮件服务商抖了 8 秒，注册接口跟着 500。数据库里的人已经写进去了，邮件没发出去，用户以为自己没注册成功，退出去重新注册一遍，收到「邮箱已存在」。一个非核心操作的失败，把核心流程也拖成了失败。

促销开始的那一分钟，请求量涨了十倍。服务不是处理不过来才崩的，是**请求在完成之前一直占着连接和内存**才崩的：每个请求挂住 3 秒等邮件，10 倍的量就是 10 倍的并发挂起，连接池先耗尽，然后整个进程开始拒绝新连接。

这四个故障指向同一件事：**把「必须马上做完」和「可以稍后做完」混在同一条同步链路里**。这一章讲怎么判断该拆哪一段、拆出去之后你实际上买到了什么、以及最重要的——拆出去之后你会新背上哪些债。后者才是本章真正要读三遍的部分。

本章所有「实测」数字都来自本机的一次真实运行：Windows 10 x64 + Node v25.4.0，日期 2026-10-19，零依赖（只用 `node:http`、`node:sqlite`、`child_process`）。证据脚本在 `message-queue-cloud/.scratch/mq-core.mjs`，四种模式可复跑：

## 先把「等」和「失败」分开量化

同一段慢操作（180 毫秒的下游调用，其中 6 条会瞬时失败），分别放在主链路里同步等待、和放在主链路外先回 202 再后台处理，各打 20 个请求。这是真实的 `node:http` 服务，不是纸面推演：

```js
// 主链路里同步做：用户必须等它做完才能拿到响应
async function sendMailSlow(id) {
  await sleep(180);                       // 模拟第三方发信往返
  if (FAIL.has(id)) throw new Error('下游瞬时失败');  // 20 条里指定 6 条
  db.prepare('INSERT INTO effects (job_id, made_at) VALUES (?, ?)').run(id, Date.now());
}

// A 臂：/inline —— 等它做完再回
app.post('/inline', async (req, res) => {
  const id = Number(new URL(req.url, 'http://l').searchParams.get('id'));
  try { await sendMailSlow(id); res.end('ok'); }
  catch { res.statusCode = 500; res.end('fail'); }
});

// B 臂：/enqueue —— 只落库，立刻回 202，后台循环里带退避重投
app.post('/enqueue', (req, res) => {
  db.prepare('INSERT INTO jobs (id, kind, biz_key, next_at, state, created_at) VALUES (?, ?, ?, ?, ?, ?)')
    .run(id, 'mail', 'user-' + id, Date.now(), 'ready', Date.now());
  res.statusCode = 202;
  res.end('accepted');
});
```

实测输出（原文照抄）：

```text
=== M1 主链路：同步等待 vs 立刻返回 202（20 个请求顺序打，慢操作 180ms，其中 6 条会失败） ===
   同步内联：n=20 p50=189.0 p95=200.0 max=211.0 用户可见失败=6/20 主链路墙钟=3801ms
   异步 202：n=20 p50=3.0 p95=4.0 max=4.0 用户可见失败=0/20 主链路墙钟=64ms
   后台：20 条任务里下游瞬时失败 6 次（全部被重投兜住）墙钟=5050ms 最终 done=20/20 副作用=20
   读法：异步没有让工作变少——后台墙钟比同步主链路还长（退避等待在里面）；它买到的是「用户不再等这 180ms」和「下游抖动不再变成 500」。
```

三个数字值得停一下。

第一，p50 从 189.0 毫秒变成 3.0 毫秒，**这不是性能优化，是责任转移**。工作量一点没少（后台墙钟 5050 毫秒反而比主链路 3801 毫秒长，因为退避等待被算在里面了），只是不再让用户为它挂住一个连接。这个区别决定了你后面所有的取舍。

第二，用户可见失败从 6/20 变成 0/20。同步链路里「下游抖一下」等于「用户看到注册失败」；异步链路里同一个抖动变成了后台的第 2 次尝试。**异步解耦买的第二样东西是失败隔离**——非核心依赖的失败域被挡在核心接口之外。

第三，异步臂把 6 次瞬时失败全兜住了，靠的不是「异步」两个字，是后台循环里的**确认 + 重投**。如果只是把 `await` 换成不 `await`，那 6 次失败就是永久丢失的 6 封邮件。这一点直接通向第 3 章。

同一次配置在两臂间的分位数字会有几毫秒抖动（另一次跑出 p50=187.0 / p95=197.0 / max=220.0），**别拿单个分位数当结论，看量级差**：189 → 3 是 60 倍，几毫秒的抖动不影响任何判断。

## 判据：看这个操作「失败时要不要立刻告诉用户」

「快不快」不是判据，「**失败和延迟是不是用户必须感知**」才是。三条判据按顺序问：

1. **用户下一步动作依赖这个结果吗？** 依赖就留在主链路。验证码没发出去，用户就卡在下一页——这不是异步候选。
2. **它失败了，用户需要立刻看到错误吗？** 需要就留在主链路。「余额不足」必须当场返回；「开票邮件发送失败」不该让用户以为支付失败。
3. **它做多久用户能接受？** 这里要诚实：用户能接受的等待是几百毫秒量级，不是「我觉得 3 秒不算长」。

拿一个真实的注册流程逐条判断：

| 步骤 | 耗时 | 失败要不要立刻告诉用户 | 结论 |
| --- | --- | --- | --- |
| 校验参数、查重 | 1ms | 要，用户要立刻知道哪个字段错了 | 主链路 |
| 写用户表 | 2ms | 要，写失败就是注册失败 | 主链路，**且要和消息投递放在同一个事务里**（第 3 章 M2） |
| 写审计流水 | 5ms | 不要，审计可以补 | 可异步 |
| 发欢迎邮件 | 180ms | 不要，失败了后台重投就行 | 异步的典型 |
| 初始化默认数据（模板、设置） | 300ms | 要看：用户下一页就要用 → 主链路；只在后台统计里用 → 异步 | 取决于下一页 |
| 同步到搜索索引 | 500ms | 不要，索引晚 1 分钟可接受 | 异步 |
| 埋点上报 | 50ms，且第三方常超时 | 绝对不要 | 异步，且要能整批丢弃也不能拖垮主链路 |

最后一行是个陷阱：埋点比邮件更容易出事，因为它常常走一个「挂了但没人管」的第三方端点。**主链路上最危险的依赖，是你已经忘了它存在的那些。**

## 异步有三个层次，只有第三层配叫队列

这一节是全章最实用的部分。大多数人以为「异步」就是把 `await` 拿掉，实际上有三个层次，失效边界完全不同。

**层次一：进程内 fire-and-forget。**

```js
app.post('/register', async (req, res) {
  await insertUser(req.body);
  sendWelcomeEmail(req.body.id);        // 不 await
  res.end('ok');
});
```

看起来优雅。实测它的失败模式（本机 Node v25.4.0 原文）：

```bash
node -e "Promise.reject(new Error('邮件服务超时'))"
```

```text
[eval]:1
Promise.reject(new Error('邮件服务超时'))
               ^

Error: 邮件服务超时
    at [eval]:1:16
    ...

Node.js v25.4.0
```

退出码 1。**一个没被 `await`、也没被 `.catch()` 的 Promise，在 Node 里默认直接把进程打死。**也就是说层次一不但会丢任务，还会因为丢任务而让你的服务重启——把一个小故障放大成一次全站抖动。要么老实 `sendWelcomeEmail(id).catch(logAndStore)`，要么升级到层次二。

顺手更正一个我自己也信过的说法。我实测：

```bash
node -e "setImmediate(()=>console.log('这行会不会打印'))"
```

打印了，退出码 0。所以**「排进事件循环的任务在正常退出前会被丢掉」是错的**——事件循环会把已排的宏任务跑完再退出。真正丢任务的是另外两种时刻：进程崩溃（上面那种退出码 1 就是）、以及**部署重启 / OOM / SIGKILL 时那些还没轮到或正在执行的任务**。层次一的所有任务都活在这些时刻的射程里，因为它们只存在于内存。

**层次二：进程内队列 + 同进程 worker。**

把任务塞进一个数组，`while` 循环消费，限制并发。这解决了层次一的「并发失控」和「未处理 rejection」，但**没有改变存储介质**——积压仍然是内存。部署一次就丢一次。它能支撑的场景是「丢了也就丢了」的日志缓冲、批量合并写入。

**层次三：任务落库 + 独立消费者进程。**

这就是消息队列的形状：投递方只负责把一条持久化的记录交出去，消费方是**另一个进程**，它崩溃、重启、扩容都不影响投递方。

三层的失效对照，用 `crash` 模式的真实输出打底（这个模式用 `child_process.spawn` 起了真的 worker 子进程，在指定时刻把它杀掉）：

```text
=== M0 真崩溃：确认时机决定是「丢」还是「重」 ===
   [worker] before：已标 done，副作用还没写 → 此刻被杀
   before      崩溃前：done里没副作用=1 条（丢），已领未确认=0 条（可重投）  → 重投 0 次后：done=3/3 副作用行数=2（不同 job=2，重复=0） 墙钟=364ms
   [worker] after：副作用已落库、还没确认 → 此刻被杀
   after       崩溃前：done里没副作用=0 条（丢），已领未确认=1 条（可重投）  → 重投 1 次后：done=3/3 副作用行数=4（不同 job=3，重复=1） 墙钟=501ms
   [worker] after-dedup：重复投递被幂等表挡下，changes=0，副作用没做第二次
   after-dedup 崩溃前：done里没副作用=0 条（丢），已领未确认=1 条（可重投）  → 重投 1 次后：done=3/3 副作用行数=3（不同 job=3，重复=0） 墙钟=501ms
   读法：before 的丢是「库里显示已完成、副作用从没发生」，恢复扫描看不见它；after 的重复是必然代价；after-dedup 用幂等表把重复的副作用归零。
```

层次一、层次二在这里连这张表都生成不出来——因为它们没有「已领未确认」这个状态可以查，进程一死，任务在物理上不存在了，**没有任何恢复扫描能找回一个从未落盘的东西**。层次三的第一个价值就是：让「丢」变成一个可以在数据库里查出来的状态。

对照表：

| 能力 | 层次一 进程内不管 | 层次二 进程内队列 | 层次三 落库 + 独立消费者 |
| --- | --- | --- | --- |
| 进程崩溃 / 重启后任务还在 | 否 | 否 | **是** |
| 能否看到积压了多少 | 否 | 只能看到当前进程 | `SELECT count(*) WHERE state='ready'` |
| 能否加 worker 分摊 | 否 | 否（同进程，抢的是同一个 CPU） | **是** |
| 失败后能否重投 | 要自己写，且没有重试计数载体 | 可以，但仍在内存 | 靠行状态，天然可数 |
| 引入新组件 | 零 | 零 | 零（复用已有数据库）或一个代理 |
| 主要代价 | 静默丢失 | 静默丢失 + 内存上限 | 状态要设计，链路要能查进度 |

**「复用已有数据库」这一行值得强调**：个人项目上队列最常见的正确第一步不是装 RabbitMQ，而是往已有的 SQLite / PostgreSQL 里加一张任务表。它已经把层次三最难的部分（持久化、可查询、事务）给你了。代价是取任务的那条 SQL 要写成能竞争消费的形状（第 2 章），以及高吞吐时它会成为瓶颈（第 9 章的选型）。

## 削峰是算术，不是魔法

同步链路里的资源占用是这样的：一个请求挂住 3 秒，就占住一个连接、一份请求上下文、若干内存，**直到它做完为止**。队列改变的是「谁在占」——不再是请求，而是一行数据库记录或一条代理里的消息，便宜几个数量级。

削峰需要多少 worker 是纯算式。**下面这张表是算式，不是实测**，别把它当性能数字引用：

| 场景 | 到达率 λ | 单条处理时间 | 服务能力 μ = worker ÷ 处理时间 | 积压变化 |
| --- | --- | --- | --- | --- |
| 平峰 | 10 条/秒 | 50ms | 4 worker → 80 条/秒 | 不积压，μ 远大于 λ |
| 促销开始 | 300 条/秒 | 50ms | 4 worker → 80 条/秒 | 每秒净积 220 条，1 分钟积 13200 条 |
| 促销加 worker | 300 条/秒 | 50ms | 20 worker → 400 条/秒 | 能追平，但要 4 分钟才把峰值期间的积压清完 |

第三行的 13200 条就是队列存在的意义：同步链路遇到这个负载会直接开始拒绝请求，异步链路把它变成一次可测量的、有尽头的延迟。**「加 worker 能追平但需要 4 分钟」是队列最容易被忽略的性质**——峰值过去之后积压不会瞬间消失，用户会在那 4 分钟里持续看到「处理中」。

这个算式与[数据存储进阶的连接池一章](/data-storage/connection-pool-and-slow-query)是同族，而且两者会被同一波流量同时打爆：**worker 也是连接的使用者**——20 个 worker 每人占一条数据库连接，而池子只配了 4，那 20 个 worker 只会互相排队，等待被搬到另一处，并没有被消除。

## 故障传播：同步链路等于共享失败域

「非核心下游拖垮核心接口」不是玄学，它有一个精确的结构：**在同步链路里，一个请求的失败域是所有被它串起来的依赖的并集。**

注册 = 数据库 ∪ 邮件 ∪ 埋点。任何一个出问题，用户都看到同一个 500。更糟的是重试语义：用户看到 500 会重新提交，而邮件那一步不是幂等的——每重试一次，可能又多排一封邮件。这是第 3 章幂等小节要正面处理的坑。

拆成异步之后，失败域变成：**主链路的失败域 = 主链路上那些同步依赖的并集，异步依赖的故障只影响它的消费者。**M1 里那 6 次下游失败一次都没有变成用户可见的 500，就是这个集合被拆开之后的直接结果。

顺带把生产侧最常见的一个坑在这里点名：**先投消息、再写业务数据**，两步之间失败就会留下一条「幽灵消息」。实测三臂（原文）：

```text
=== M2 生产侧：业务写与任务写不在一个事务里，就会出现「库里没这个人、队列里却有他的邮件」 ===
   没有 outbox：任务已进队列，业务写抛 [NOT NULL constraint failed: res.name] → res=0 jobs=1 ← 幽灵消息，worker 会给一个不存在的人发邮件
   outbox 同事务提交：res=1 jobs=1，一条用户配一条消息
   outbox 同事务回滚：捕获 [NOT NULL constraint failed: res.name] → res=1 jobs=1（仍是上一条的形状，没有多出第三条消息）
```

`res=0 jobs=1` 是这一章最应该记住的一行数据：库里没有这个人，队列里却有他的欢迎邮件。修法是把两条 INSERT 放进同一个事务（第三臂），完整做法（含代理场景下的 outbox 表怎么轮询、为什么不能在事务提交后直接投）放在第 3 章。

## 异步化换来的四样债

**只讲收益的异步化教程是不诚实的。**你从用户身上搬走的等待，会以另外四张账单回来：

| 你新背上的债 | 什么时候会疼 | 本章给出的处理 | 详见 |
| --- | --- | --- | --- |
| 状态必须落库 | 每次部署之后：进程内的进度全没了 | 任务表 + 行状态机（`ready` / `claimed` / `done` / `dead`） | 第 2、3 章 |
| 结果必须能被查到 | 用户问「我注册好了吗」而你只能回 202 | 给 `202` 配一个可轮询的进度端点，或前端先按成功渲染、失败再补提示 | 本章练习 5 |
| 一致性从「强」变成「最终」 | 下一页的数据依赖异步任务写入的结果 | 明确「多久算最终」的 SLA，并把它写进验收标准 | 第 4 章延迟 |
| 重复、丢失、乱序同时出现 | 网络重试、消费者崩溃、多个 worker 并行 | 确认时机 + 消费端幂等 + 按 key 分区 | 第 3～5 章 |

最后一行是这个领域的核心：**这三个问题不是「用了队列才有」的，而是「用了队列才终于要面对」的。**同步链路里它们也在（用户重复提交、请求半途超时、重试打乱顺序），只是被隐藏在一次 HTTP 请求的边界之内。

## 什么时候不该异步

反向判据四条，任何一条成立就别拆：

- **用户下一步就要这个结果。** 支付之后的库存扣减，异步化只会制造「明明付了钱却说未支付」的客服工单。
- **量小。** 一天 200 条任务，一个进程内的定时器足够。引入一个要运维、要监控、版本要升的代理，成本远大于收益——这条与[自托管与云服务那一章](/message-queue-cloud/self-host-vs-cloud)的判断口径一致：先问「这台机器上的东西我能不能看住」，别问「业界用什么」。
- **失败必须回滚主流程。** 一条消息一旦投出去就收不回来，而业务上「这步失败要整个回滚」——那它必须留在事务里。这正是 M2 演示的反面情形。
- **顺序比延迟重要，且你还没想清怎么保序。** 先读第 4 章的顺序性小节再动。

## 常见错误与排查

**1. 现象：接口延迟降下来了，但邮件偶尔就是不发，日志里什么都没有。**
原因：层次一，`sendWelcomeEmail(id)` 不 `await` 也没 `.catch()`；或者写了 `.catch(console.error)` 但 `console.error` 的输出没进你的日志采集。
怎么确认：查任务表有没有对应的行（层次三才有表）；没有表的话，在下游调用处加计数器，把「进入调用」和「调用成功」分别打点，跑一段看两个计数的差。
怎么修：升级到层次三（落库 + 消费者）。中间过渡方案是 `.catch()` 里把失败任务原样写进一张 `failed_jobs` 表，让重启后还能捞起来——这只是权宜，因为它挡不住「进程在副作用执行中途被杀」。

**2. 现象：worker 数量从 4 加到 20，吞吐没变，接口还变慢了。**
原因：worker 抢的不是 CPU，是数据库连接。20 个 worker 挤在连接池上限 4 的池子上排队，同时把主链路的连接需求也挤掉了。
怎么确认：`SELECT state, count(*) FROM jobs GROUP BY state` 看有多少条是 `claimed` 但迟迟不变 `done`（被占用中）；对照连接池的等待计数（见[连接池与慢查询定位](/data-storage/connection-pool-and-slow-query)）。
怎么修：worker 数与池子大小一起算，别让一方单方面扩容。经验起点是每个 worker 只借一条连接，`poolMax ≥ worker 数 + 主链路所需`。

**3. 现象：用户反馈收到两封欢迎邮件，一次比一次间隔更短。**
原因：接口返回 202 但没有任何进度可查，用户以为没成就反复点，每次点击投一条新消息。你的幂等键如果用的是消息 id（每次点击都是新 id），拦不住。
怎么确认：数一下同一个用户/同一个业务动作有几条任务行：`SELECT biz_key, count(*) FROM jobs GROUP BY biz_key HAVING count(*) > 1`。
怎么修：幂等键必须是**业务动作**而不是消息 id（`user-7-register-welcome`），并且写在一个有唯一约束的表里。实测的四臂对照在第 3 章。

**4. 现象：重启之后积压突然暴涨。**
原因：崩溃前 `claimed`（正在处理）的任务没有被任何机制放回 `ready`——进程内队列在层次二必然发生，层次三如果没写恢复扫描也会发生。M0 那行「已领未确认=1 条（可重投）」就是这条扫描要处理的对象。
怎么确认：`SELECT count(*) FROM jobs WHERE state='claimed' AND claimed_at < now() - 超时窗口`——>0 就说明有孤儿。
怎么修：写恢复扫描（把超时的 `claimed` 退回 `ready`），或者让代理用它的可见性超时机制替你做（真实代理的默认值本章不写，见第 3 章文档核实小节）。

**5. 现象：加了队列之后，故障更难定位了。**
原因：一次业务操作被切成「投递 → 排队 → 消费」三段，三段的日志不在一起，也没有任何地方存了它们的关联标识。
怎么确认：随机挑一条用户投诉，只用邮件里那条记录，试着反查它的投递时刻、任务行 id、worker 日志。查不到就是有这个症状。
怎么修：一个 `job_id` 贯穿三段，在投递、领取、完成、失败四处都打；任务表保留 `attempts`、`next_at`、`reason` 三列，让「为什么还没做完」能只靠查表回答。

然后回答：为什么第二条正常退出而第一条打死进程？这两件事的共同点是什么？

<template #answer>

第一条的实测输出（本机 Node v25.4.0）：

Promise.reject(new Error('邮件服务超时'))

    at [eval]:1:16

Node.js v25.4.0

原因：Node 对**没有被处理的 Promise rejection** 默认按未捕获异常处理，进程以非 0 退出；而 `setImmediate` 排入的宏任务会在事件循环耗尽后正常结束进程。

延伸：`process.on('unhandledRejection', ...)` 能把第一类变成日志而不是崩溃，但这只是把症状压下去——那个任务仍然没做完，你必须有地方记下它（也就是 `failed_jobs` 表或层次三）。

<Exercise title="算出你这个场景需要几个消费者" difficulty="进阶">

给定：活动峰值期间任务到达率 300 条/秒，单条处理 50 毫秒，你愿意接受峰值结束后最多 5 分钟把积压清空。

要求：算出至少需要多少个消费者，以及峰值持续 2 分钟时最大积压是多少。**写出算式**，并说明这个数字和数据库连接池配置之间为什么必须一起算。

<template #answer>

服务能力的算式：`μ = 消费者数 ÷ 单条处理时间 = worker ÷ 0.05s`。要消化 300 条/秒需要 `worker ≥ 300 × 0.05 = 15` 个。15 个刚好持平，积压不涨也不降；要在这之上额外清掉已积压的量，需要留出追平速率。

2 分钟峰值期间按 20 个消费者（`μ = 400 条/秒`）：净增速 `λ − μ = −100 条/秒`，不积压反而在追平；按 15 个：净增速 0，最大积压约等于到达率 × 单次处理时间 = `300 × 0.05 = 15` 条常驻在飞。

与连接池必须一起算的原因：20 个 worker 每人至少借一条数据库连接。池子上限 4 时，worker 数加到 20 只会把等待从队列搬到池子，同时挤占主链路。见[连接池与慢查询定位](/data-storage/connection-pool-and-slow-query)里同形状的算式。

<Exercise title="判断哪些步骤不能异步化，并给出理由" difficulty="基础">

下单流程：校验库存 → 扣库存 → 创建订单 → 收支付回调 → 标记已支付 → 扣减优惠券 → 发通知 → 生成发票 → 同步到 BI。

要求：指出其中**必须留在同步链路**的，哪些**取决于实现**（说清取决于什么），以及一条常见但错误的做法。

<template #answer>

必须同步：校验库存、扣库存、创建订单。这三步构成「用户付钱前必须成立」的前提，而且它们必须在**同一个事务**里（见[事务](/database/transactions)）；否则会出现库存扣了但订单没建。

取决于实现：收支付回调 + 标记已支付。回调本身必须同步处理并落库（它是事实来源），但「标记已支付之后的所有派生动作」应当异步。坑在回调重发：同一订单被回调 3 次，标记动作不幂等就会扣 3 次券，所以键要用**业务动作**（`order-7-mark-paid`），见第 3 章 M6 四臂。

常见错误做法：把「扣库存」也异步化，理由是「接口快」。结果并发下单时超卖，因为扣减的串行化保障被搬到了队列之后。**队列提供的是解耦和缓冲，不提供互斥**——互斥要靠自己，见[分布式锁](/data-storage/distributed-lock)。

<Exercise title="给返回 202 的接口补一个能被轮询的进度端点" difficulty="挑战">

要求：用层次三的任务表，实现 `GET /jobs/:id` 返回 `queued` / `processing` / `done` / `failed` 四种状态之一，并说明：为什么不能把内部状态直接暴露给客户端；以及这个端点被前端每 500 毫秒轮询时，你会新增哪个容量问题。

<template #answer>

关键设计是把内部行状态机映射成一个**对外稳定的状态词表**：内部可能是 `ready` / `claimed` / `retrying` / `dead` / `done`，对外只给四个词。理由：内部状态名一旦写进客户端，你就再也改不动它了；而且 `retrying` 对用户毫无意义，他只需要知道「还在处理」。

```sql
SELECT id,
       CASE
         WHEN state = 'done' THEN 'done'
         WHEN state = 'dead' THEN 'failed'
         WHEN state = 'claimed' THEN 'processing'
         ELSE 'queued'
       END AS status
FROM jobs WHERE id = ?;
```

`attempts`、`reason`、`next_at` 不给客户端，只给内部运维接口——它们是排查用的，泄露出去只是给用户制造焦虑（「为什么失败 3 次了」）。

新增的容量问题：轮询是**读放大**。一个任务被轮询到完成可能要 20 次读，而这些读打到的是同一张你正在用它做竞争消费的表。峰值时 300 条/秒的任务会附带约 6000 次/秒的进度查询。对策：给 `(id, state)` 走主键点查（这条是 O(1)）；更省的做法是让轮询读只查状态列（覆盖索引）；或者干脆不要轮询，前端先按成功渲染、失败再通过别的通道提示。**这个读放大正是「队列任务表放主库」这个方案的最大限制**，第 9 章的选型会回到这里。

</template>

</Exercise>
