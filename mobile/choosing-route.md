# 四条路线差的是四笔账，不是技术档次

第一个故事是两个月白干。一个人给自己的笔记产品做 iOS App：证书、签名、上架材料、审核被拒两次、每次等三天。上线三个月，累计安装 40 次，其中十几次是他自己和朋友装的。他后来才承认，那两个月里他一次都没有确认过「用户到底在哪里打开这个产品」——他的用户是在微信里被同事发链接拉进来的，那条链路根本不需要安装。他的成本不是「做了 App」，是**把一个分发问题当成了技术问题**。

第二个故事卡在一个跟代码毫无关系的环节。有人决定做微信小程序，代码写了两周很顺，到联调才发现后端域名的备案还没办下来；而小程序的 request 合法域名要求 HTTPS 且要求域名已完成备案，这是平台侧的硬性前提。于是他的项目在最后一步停了三周等流程。**平台的日历时间不在你的估算里，但它一定在项目的实际工期里。**

第三个故事最常见，也最省时间：一个人把已有的 Web 产品做了移动端适配——视口、安全区、触摸目标尺寸、软键盘——两周后手机上打开的跳出率明显下降，没有新代码架构、没有新账号、没有审核。他做的事情和「做移动端」这四个字在同一个语义下成立，因为**用户要的从来不是 App，是「在手机上能用」**。

这三件事指向同一个结论：**「要不要做移动端」不是一个决定，而是四个决定的组合**——用户在哪里打开它（分发）、它需要多深的系统能力（能力边界）、你能不能接受平台的审核与规则（治理）、你愿意长期维护几套代码（成本）。这一章把这四笔账摊成可填的表格，最后给一棵决策树和三条本站的默认答案。选型的价值不在于选得「高级」，而在于**选完之后你能不能一直维护它**——个人开发者死在项目烂尾上的人，比死在技术不行上的多得多。

## 「移动优先」拆开是三件事，其中只有第三件是选型

这个词被压缩得太狠，以至于很多人以为它是一种视觉风格。拆开来是三件事，件件都能验证：

**第一件是布局起点。**你从 375 CSS 像素宽往上写，而不是从 1440 往下砍。这条纯粹是 [响应式布局与断点](/css/responsive-design) 的实践问题，不涉及任何平台选择，判断标准也简单：把浏览器窗口缩到手机宽度，看有没有横向滚动、有没有需要缩放才点得中的按钮。

**第二件是交互前提。**手指没有 hover，只有一根手指在动，屏幕随时被软键盘占掉一半，网络会在隧道里断掉，用户随时切走 App。这一件是[第二章 移动端 Web 适配](/mobile/mobile-web)的全部内容，它同样是纯 Web 的事——不需要你选任何路线就得做。

**第三件才是选型，而且是分发问题：用户从哪里进入你的产品，以及他下次怎么回来。**注意这一件的技术含量最低、产品含量最高。「做个 App 吧」这句话里真正的意思通常是「我想要一个用户能反复回来的入口」——那是分发诉求，实现它的办法在国内至少有五种：浏览器收藏夹、加到主屏幕的网页、小程序历史入口、商店里的图标、公众号菜单。

**这三件事里，前两件事的收益是确定的、成本是可估的；第三件事的收益取决于你的用户在哪。**本站给所有自学者的一句话建议是：**先把前两件事做完，再讨论第三件事**。因为前两件事无论选哪条路线都不白做（小程序的页面布局也是 CSS 家族，跨端框架的 UI 层也遵守同一套盒模型），而第三件事选错了要以月为单位重工。

## 四条路线的账先摊开：一张可以填的对照表

四个候选：响应式 Web、微信小程序、跨端 App（uni-app / React Native / Flutter / Capacitor 这一类）、原生 App（Swift / Kotlin，或两套都做）。

| 维度 | 响应式 Web | 微信小程序 | 跨端 App | 原生 App |
| --- | --- | --- | --- | --- |
| 新增代码套数 | 0（就是你现在这套） | 1 套 UI + 1 套页面逻辑（Web 与小程序共享后端，不共享 UI 代码，除非上 uni-app） | 1 套共享代码 + 每端配置 | 每个平台 1 套 |
| 你要新学的东西 | 视口、安全区、触摸事件（本站第 2 章） | WXML/WXSS/`setData`/生命周期/平台 API（本站第 3、4 章） | 框架本身 + 它对各端的封装边界 | 平台语言、构建工具、签名与证书 |
| 系统能力（推送、后台、蓝牙、文件、剪贴板） | 最浅，且各浏览器不一 | 中等，能力由平台封装并统一审核 | 深，但要付出「插件层」的成本 | 最深，且没有中间商 |
| 分发摩擦 | 一个链接，零安装 | 扫码或搜索，零安装，微信内闭环 | 商店下载 | 商店下载，双端要分别上架 |
| 谁能拒绝你 | 没有人（自己部署即可） | 平台审核，可被拒可被下架 | 商店审核 + 平台审核 | 商店审核 |
| 更新到你用户手上的延迟 | 秒级（一次部署） | 提审通过后用户下次进入即新版 | 商店审核 + 用户点更新 | 商店审核 + 用户点更新 |
| 性能上限 | 中，受浏览器与网络影响 | 中低，双线程与视图层封装有代价 | 高 | 最高 |
| 离线能力 | 靠 Service Worker，规则见 [HTTP 缓存](/frontend-engineering/http-caching) | 只有本地缓存与 storage，页面本身要平台加载 | 强 | 强 |
| 单人长期维护的现实难度 | 最低 | 中（主要成本是平台规则而不是代码） | 中高 | 高（双端等于两个人） |

这张表不要背，要**填**。填法：在每一行的最后加一列「我的产品在这一行的实际约束」，只填你已经有证据的格子——你现在的移动端跳出率、你的用户在什么场景打开、你的后端域名备案状态、你每周能投入的小时数。**填不满的格子就是你需要先做的小实验**，而不是可以跳过的行。

一个具体的填法示例：一个记账工具，用户是「同事之间互相发链接」，每天打开一两次，需要相机拍票据。这一行的证据指向 Web（零安装、链接分发）+ 能力缺口（相机的拍照体验与相册批量导入在 Web 上会打折扣）。结论就不是「选 Web 还是选小程序」，而是「先做 Web 适配，把拍照体验做成一条可观测的指标，等它真的产生流失再评估小程序」。

## 能力边界要拆成推送、硬件、离线三格分别问

「能力」是一个会骗人的词，因为它是很多个互不相干的能力。分开问，每格的答案都不一样。

**推送。**这一格最容易被当成决定性因素，也最容易被高估。Web 侧有 Push API，但它在移动浏览器上的现实前提与各家支持度不一致，iOS 上还有额外条件；小程序侧的推送是平台规定的一种「订阅」形态，需要用户主动授权、有内容与时机限制，不是你能随便用的消息通道；原生侧能拿到系统的推送服务，但国内 Android 的到达率取决于机型与后台策略，这件事只有真机和真实用户量才能验证。**本站不给任何一方的支持度结论**——你只需要记住判据：**如果推送是你产品的核心价值（而不是运营手段），那它就是路线选择的第一约束，必须用你自己的设备和你自己的用户实测到达率，不能引用别人的表格。** 反过来，如果你的「推送」其实是「订单完成通知」，那邮件与短信可能更可靠，见[短信、邮件与第三方 API](/message-queue-cloud/sms-email-and-api)。

**硬件。**相机、相册、定位、蓝牙、传感器、文件系统、剪贴板。Web 暴露的是一组受权限约束的接口，覆盖常用场景但体验与兼容性不齐；小程序把硬件能力封装成统一的平台 API，好处是所有设备长得一样，代价是**能力清单由平台决定，且要过审核**；跨端框架再在原生能力上包一层插件，于是多了一个「封装层出问题」的归因环节；原生没有中间层。**判据：把你的硬件依赖按「必须多深」排序。**拍一张照片上传，Web 能做；后台持续采集传感器，Web 基本不做；需要低延迟蓝牙与设备直连，你要先问清各平台的权限模型再决定路线。

**离线。**Web 靠 Service Worker 与缓存策略，能做到「二次打开可用」，但缓存的失效逻辑你要自己写清楚，这一条与[HTTP 缓存与协商](/frontend-engineering/http-caching)是同一个问题在移动场景的兑现。小程序的页面本身要由平台加载，你能控制的是本地数据缓存与 storage。原生最容易做彻底离线。判据：**用户会在没有网络的时候打开你的产品吗？**这个问题的答案来自你的产品，不来自技术。

三格里只要有一格的答案是「Web 做不到、而它是我的核心价值」，路线讨论才真正开始。三格都是「做得到的够用」，那你就还停在第 2 章的范围里，一分钱选型成本都不用花。

## 分发是产品问题：用户从哪进来，下次怎么回来

这一节没有任何技术，但它决定前两节的权重。

**进来的路径。**链接是摩擦最小的入口，也是你唯一能完全控制的入口：可以贴在群里、放进文档、发到评论区、印在二维码上。小程序的入口在平台内：搜索、扫码、聊天卡片、公众号关联、历史记录。商店的入口是搜索关键词和榜单，冷启动几乎没有自然流量——对个人开发者，「上架」和「有人下载」之间的距离经常比开发本身更远。**问一句：你现在这一版 Web 的用户是怎么找到你的？**如果答案是「我发给他们的链接」，那么任何需要安装或需要跳出微信的路线，都会在你现有的获客链路上加一道坎。

**回来的路径。**这条是很多人真正想要的东西，而它不是「有 App」才具备的：浏览器收藏、加到主屏幕、小程序的历史入口与「我的小程序」、公众号菜单，都是回访入口。它们的强度不同，但都存在。**别为了一个想象中的「桌面图标」重写整个产品。**

**登录与身份。**微信内有一条现成的身份链路（用户在微信里有稳定标识），这条链路会显著降低你的注册摩擦；代价是它由平台签发，你自己的会话体系要与之对接，服务端要做的事并不少——code 换用户标识、下发你自己的凭证、密钥只留在服务端，这套模型与[会话与登录](/backend/auth-session)是同一个模式的不同提供方。**判断点是：你的产品需不需要拥有用户关系。** 如果用户只属于你的产品（比如他们的数据要能带走），那平台账号只应该是一个登录方式，而不是你的用户体系的地基。

**外链的现实。**在特定宿主环境里，外部链接可能被限制或直接打开为平台内页面。这件事的具体规则会变，本站不复述；但选型时它是真实成本，因为它决定「别人分享你」这条路顺不顺。**核实方式很简单：拿你自己的链接，在你目标用户最常用的两三个宿主里点开一次，看它落到哪里。**

## 发布周期决定服务端欠多少债

这一条经常被忽略，因为它不在「做不做 App」的讨论里，但它是最贵的一笔。

Web 是一次部署全员生效，你的服务端只需要面对**一个版本的客户端**。小程序要走提审：审核期间旧版本还在用户手里跑，新版本提交后你同时要兼容两个版本的接口。原生要走商店：审核时间不可控，且**用户不点更新，你的服务端就要长期面对 N 个旧版本**。

于是有三条实践结论：

**客户端发布周期越长，服务端接口的兼容窗口越长。**接口字段只做加法、不改语义、不删字段，这条与[API 文档与契约](/backend/api-docs)里的契约思维是同一件事，只是在移动端它不是「好习惯」而是「必须」——因为你无法强制用户升级。

**版本要作为请求的一部分。**客户端带版本标识，服务端按版本记录错误率与调用量，你才知道「旧版本还有多少人在用」，从而知道一个改动会影响谁。没有这个数，你对兼容性的判断只能靠感觉。

**「先审核再发布」改变了你的回滚能力。**Web 出问题你可以几分钟内回滚（见[发布与回滚](/devops/release-and-rollback)）；小程序与 App 出问题，你要重新提审，中间时间产品是坏的。这一条直接把「灰度发布」从可选变成必要：入口开关放在服务端，让新功能的可见性可以不发版就关掉。

顺带一句常被误传的机制：商店对「绕过商店更新代码」的政策是会变的、且按平台与时期不同，本站不复述具体条款。**只要知道它存在，不要把「热更新」当成你回滚能力的默认方案。**

## 决策树：五个能二值化的问题

顺序是有讲究的：前面每个问题的答案都能砍掉后面的选项，所以从「最不可逆」开始问。

```text
Q1 你的用户是否需要「安装」才愿意使用你的产品？
   ├─ 否（链接/扫码就能用）  →  先把响应式 Web 做合格（第 2 章），选型到此为止
   └─ 是 / 不确定            →  继续

Q2 产品是否必须在微信生态内完成闭环（分享卡片、群内使用、平台身份）？
   ├─ 是                    →  小程序路线（原生写；多端诉求强烈时再评估 uni-app，见第 5 章）
   └─ 否                    →  继续

Q3 是否有「Web 做不到」的硬能力依赖（后台常驻、深度硬件、低延迟设备直连、重渲染）？
   ├─ 否                    →  Web 或小程序，按 Q2 的分发结论选
   └─ 是                    →  继续

Q4 你能为每个平台各自维护一套代码吗（包括证书、签名、商店材料、旧版本兼容）？
   ├─ 不能，但确实需要原生能力 → 跨端框架，并接受「封装层」的归因成本
   └─ 能，且能力深度是核心壁垒  → 原生（单人通常只能覆盖一个平台）

Q5 无论走到哪：后端是否已经具备「按版本兼容」的能力？
   └─ 没有 → 先补这个，因为它决定了你后面每次发版的回滚能力
```

三个形态的走查。**内容/工具型轻交互**（记账、查询、表单、清单）：Q1 通常答「否」，走到 Web 就停；如果用户确实只在群里用，Q2 命中，做小程序。**社区/媒体型**：分发依赖搜索与外链，Web 是主入口，小程序作为补充入口而不是替代。**重能力型**（运动记录、设备伴侣工具、游戏）：Q3 命中，直接进跨端或原生讨论，这时候「我不会 Swift」不是决策因素，「我需要后台定位且要可靠」才是。

## 成本按「几套代码 × 多久」算，不按「一次开发」算

一次开发的成本是幻觉，长期维护的成本才是真的。可以量化的口径有三个：

**代码套数。**1 套（纯 Web）、2 套 UI（Web + 原生小程序，共享后端）、1 套共享代码编译到多端（uni-app 或跨端框架）。第三种看起来最省，但它把成本搬到了另外两个地方：**抽象层的 bug 归因**（同样的代码在 A 端正常、B 端异常，你要先判断是你的逻辑、框架的编译产物、还是平台本身），以及**条件编译**（一旦开始写「这段只在小程序端执行」，你手里的一套代码其实是 N 套分支的叠影）。本站的口径统一为那个判据——**改一个需求要打开几个文件**：同一套代码的多端分支，和两套独立代码，在改动面这个指标上可能算出接近的数字。这个判据的完整推导在[软件架构：模式与取舍](/computer-science/architecture)。

**每次改动的重复验证量。**多一个端，同一个功能要验证的次数乘以端数，而且乘数发生在「你没预料到的场景」上——比如只在小程序端出现的键盘遮挡、只在某机型出现的布局错位。这一项在估算里最常被写成 1，实际是 2 到 3。

**平台规则的跟进成本。**Web 的标准你几乎不需要主动跟进（浏览器向后兼容），平台能力与政策你需要。它的形态是「某天一个原本能用的接口突然要求新的授权方式」「某类目从下周开始需要资质」。这不是技术问题，是**你的产品有多少部分建立在别人的地基上**的量化结果。

## 本站给的三条默认答案，以及它们各自的失效信号

**默认答案一：先做移动端 Web 适配，它是所有路线的地基，而且是本站性价比最高的一次投入。**理由是确定性：不需要账号、不需要审核、不需要新技能，收益直接落在你现有产品的跳出率上。失效信号是「用户反馈的核心诉求全部落在能力边界那一格」，而不是「页面在手机上看还行」。

**默认答案二：只有分发链路要求时才做小程序，而且先用原生方式写一遍。**理由与[领域首页](/mobile/)的顺序安排一致：先理解平台机制，再看框架替你封装了什么。失效信号很明确——当你发现自己**每次**要用的能力都要绕过框架、或者你的两端差异全靠条件编译维持，说明框架省下的时间已经还回去了。

**默认答案三：原生 App 在「常驻 + 重能力 + 你已经确认用户在商店里搜索你」之前不启动。**这条对个人项目尤其硬：它真正的成本不是开发，是**上线之后你要一直养它**。失效信号是你已经有稳定的回访用户，并且他们明确因为能力缺失而离开——注意是「能力缺失」，不是「他们觉得 App 更正式」。

最后一条通用的：**这三条答案都是可逆性排序后的结果，不是信仰。**数据模型与对外契约是不可逆的，路线选择在多数情况下是可逆的（Web 做好了再包小程序，比小程序做好了再补 Web 常见得多）。所以别把选型当天花板，把它当成「现在最便宜的那一步」。

## 常见错误与排查

**一、把「手机上能打开网页」当成「做了移动端」。**现象：桌面测试一切正常，用户说「手机上不好用」但说不出哪不好。原因：能打开 ≠ 适配，触摸目标尺寸、安全区、软键盘、动态视口都是另一套问题。怎么确认：用真实设备（不是浏览器缩放窗口）走一遍核心流程，把每一次「我用指甲点不到」「输入框被键盘挡住」记下来。怎么修：读第二章，按它的清单逐项处理。

**二、用 WebView 套壳却按 Web 的方式规划。**现象：套了壳，仍然没有推送、仍然要商店审核、首屏比浏览器打开更慢。原因：容器给了你图标和能力接口的入口，但没有替你去掉分发与审核的账。怎么确认：问自己「去掉壳之后产品少什么」。怎么修：要么真的用到原生能力，要么承认它就是 Web，别为壳付维护费。

**三、先选框架再定形态。**现象：技术选型讨论全在「用哪个框架」，没有一句关于「用户在哪里打开」。原因：把手段当成了目标。怎么确认：看你的决策文档里有没有一条写「用户入口」。怎么修：回到那五个问题，按 Q1→Q5 顺序重答一遍，框架只在 Q4 之后进入讨论。

**四、低估平台流程的日历时间。**现象：代码写完两周了还没上线，卡在备案、资质或审核。原因：平台流程不在你的关键路径估算里。怎么确认：把「需要平台方动作」的事项单独列一张表，标上各自的等待时间。怎么修：这些事项**并行启动**，不要等代码写完——域名备案与账号注册在项目第一天就该开始。

**五、一套代码多端，却只在一个端测试。**现象：H5 一切正常，小程序某页面白屏或样式错位。原因：编译产物按端不同，共享代码不等于共享行为。怎么确认：每次改动问「这次我验了几个端」。怎么修：把「两端都过一遍」写进改动完成的定义里，端数越多越要考虑为每端各留一个最小冒烟清单。

**六、把跨端框架的「兼容」当成「一致」。**现象：某个能力在文档里写着「支持多端」，实际某一端的表现、权限或参数不同。原因：兼容是接口签名一致，一致是行为一致。怎么确认：查框架文档里的「端差异」标注，并在真机验一次。怎么修：差异点用条件编译显式写出来并加注释，让它在代码里可见——**隐藏的分支是维护成本的主要来源**。

**七、承诺了 App 却没人养。**现象：商店里挂着半年没更新的版本，评分被「打不开」「闪退」压低，用户看到的是废弃产品。原因：把上架当成交付终点而不是维护起点。怎么确认：看你上一次发版日期，以及旧版本请求占比。怎么修：要么发版并承诺维护，要么把入口收回到 Web 与小程序；**挂着不动是最坏的一种**。

<Exercise title="故意把一个必须留在链接生态的产品选成小程序，把会卡住的环节逐条列出来" difficulty="进阶">

假设你的产品的核心使用场景是「别人在群里或文档里发一个链接，用户点开就用，一次用完不再回来」。现在**故意**选择「只做微信小程序，不做 Web」，然后逐条写出会卡住的环节：入口、审核、后端前提、数据可迁移性、回访假设。最后写一句这个方案唯一成立的条件。

<template #answer>

会卡住的环节至少有五条：**入口**——你的分发链路靠的是任意链接，把一个入口换成「必须扫码或在微信内搜索」，等于给每次分享加一步；**审核**——每个版本都要提审，出问题不能即时回滚（这一条与发布周期那节的账对应）；**后端前提**——request 域名要求 HTTPS 与备案，流程时间不在你手里；**数据可迁移性**——用户关系与身份挂在平台上，未来想搬走要额外做一次映射；**回访假设**——场景本身是一次性使用，平台内的历史入口对你没价值，等于付出了平台成本却换不到平台收益。

唯一成立的条件大致是：你的用户全部在微信内、且分享路径依赖平台的卡片能力（群内转发要能带结构化卡片），并且你能接受平台的审核与规则作为产品的一部分。写不出这个条件的选型，就是跟风。

这题的训练目标是**把「选 A」翻译成「为 A 付哪些账」**，而不是得出「不能选小程序」的结论——小程序在很多场景里确实是对的答案。

## 官方文档与延伸阅读

本章内已核实（2026 年 10 月，用于支撑对照表里「能力边界」与「更新延迟」两行的说法）：

- [MDN · viewport meta](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport) —— 视口关键字集合、`viewport-fit` 与安全区的配套关系、`interactive-widget` 对虚拟键盘行为的三个取值。
- [MDN · length（视口单位）](https://developer.mozilla.org/en-US/docs/Web/CSS/length) —— `vh` 与大视口单位等价、小视口与动态视口单位各自的定义与代价。
- [MDN · touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action) —— `manipulation` 关掉双击缩放、从而取消 click 延迟的官方说明。
- [微信官方文档 · 逻辑层 App Service](https://developers.weixin.qq.com/miniprogram/dev/framework/app-service/) —— 逻辑层不运行在浏览器中、`window`/`document` 不可用、`setData` 把数据发送给视图层。
- [微信官方文档 · WXSS](https://developers.weixin.qq.com/miniprogram/dev/framework/view/wxss.html) —— `rpx` 以页面总宽度 1/750 为基准与换算示例、不支持的选择器类型。

需要你自己核对、本章不下结论的部分：

- [微信官方文档 · 框架入口](https://developers.weixin.qq.com/miniprogram/dev/framework/) —— 平台能力清单、组件与 API 的支持基础库版本，**动手当天查**。
- [caniuse.com](https://caniuse.com/) —— 需要「某 Web 能力在我的用户群里能不能用」时，用它查支持度，但**必须与真机结论对照**，因为国内浏览器变体多。
- [uni-app 官方文档](https://uniapp.dcloud.net.cn/) —— 第五主题材的资料；本章只把它当作「一套代码多端」的成本样本。
- [React Native 官网](https://reactnative.dev/) 与 [Capacitor 官网](https://capacitorjs.com/) —— 跨端与 WebView 容器两条路线的官方定位，本站只做概览级介绍。
