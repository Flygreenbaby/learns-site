# 界面由谁画：三条跨端路线差的是渲染机制，不是语言

第一个故事关于「跨端省不掉的那一半」。一个团队选 React Native，理由是「一套 JS 代码管两端」。产品重度依赖后台定位和蓝牙连接，半年后他们的时间分配是这样的：UI 确实只写了一遍，但每一项硬件能力都要经过原生模块，原生模块要跟着系统版本与框架大版本升级，出问题时报的栈横跨两种语言。**「跨端」跨的是界面层，不跨设备能力层**——这一条在选型那天没人算，在第二年变成主要成本。

第二个故事关于「一致性的代价」。一个做 Flutter 的团队最看重的是视觉：同一套动效和字形在 iOS 与 Android 上长得一模一样，这是自绘引擎给的自由。代价在另一头——**平台原生控件的行为习惯不会自动出现**，返回手势、滚动物理、系统对话框、无障碍语义，都要自己实现或对齐；再加一份引擎带来的体积。一致性买到手了，「像这个系统的 App」要另付。

第三个故事最快也最容易被反问。一个团队用 Capacitor 把已经做好的 Web 应用装进原生壳里，两周就交出了两个商店包，这是 WebView 容器路线**真实且很大**的价值。然后他们反复被问到同一句话：「这是不是就是个网页壳？」审核关注点、离线体验、启动白屏、跟不上的手势与转场，都从这句话里长出来。容器路线的问题不在于它技术不行，在于**它把 Web 的边界原样搬进了 App 的分发形态里**，而那条边界是可见的。

这三件事的层次是同一个：**跨端方案的差别不在「用哪种语言」，在「界面由谁画」。** 一条把 JSX 落到系统真实控件上，一条自带引擎连系统控件都不碰，一条在应用里嵌一个浏览器。语言可以相似，机制完全不同，于是包体积、性能特征、一致性、和原生能力打交道的方式、以及最重要的——**「你已有的 Web 资产能复用多少」**，全都跟着分岔。

这一章是本领域的地图章，不是教学章：**本站不深入教学其中任何一个。** 读完你要能做到两件在真实工作里更有用的事：看懂别人关于跨端的争论在争哪一层，以及在别人问「要不要做个 App」时给出有依据的意见而不是跟风。

## 先问一个层次问题：界面由谁画

把三条路线并排放在一张图上，差别一眼就出来了。

```text
你的代码            界面由谁画                落到设备上是什么
──────────────────────────────────────────────────────────────────
React Native    系统控件（由框架按需创建）   Android View / iOS UIView
Flutter         框架自带的引擎              自己合成、自己绘制的一整张画面
Capacitor       应用内嵌的 WebView          浏览器内核渲染的网页
Web / 小程序     各自的容器（浏览器 / 平台）  本文其他章已经讲过
```

**这一层差别决定了后面所有取舍。** 举两个立刻能看到的推论：

**推论一：谁画界面，就谁负责「像不像这个系统」。** 用系统控件的，天然带上系统的手势、滚动物理与控件行为，代价是不同系统之间要抹平；自绘引擎的，天然一致，代价是系统习惯要自己实现；用 WebView 的，「像不像原生」取决于你的 CSS 和你对平台规范的理解，而系统控件的行为根本不在你的可及范围内。

**推论二：谁画界面，也决定了你已有的资产能不能复用。** 你在[第二章](/mobile/mobile-web)和[CSS](/css/)领域积累的那套东西（布局、单位、媒体查询、无障碍语义），在三条路线里的可搬运率完全不同——这一条对个人开发者常常是决定性的一条，本章最后会正面处理它。

## React Native：JS 写逻辑，控件是原生的

官方文档里那两句话是这一路线的定位所在，逐字抄下来：

> With React Native, you can invoke these views with JavaScript using React components. At runtime, React Native creates the corresponding Android and iOS views for those components.
> Because React Native components are backed by the same views as Android and iOS, React Native apps look, feel, and perform like any other apps.

官方在同一页给的核心组件映射表（核实时间 2026-10-22），这张表就是「原生控件」四个字的具体内容：

| React Native 组件 | Android 侧 | iOS 侧 | Web 上最接近的 |
| --- | --- | --- | --- |
| `View` | `ViewGroup` | `UIView` | 不滚动的 `div` |
| `Text` | `TextView` | `UITextView` | `p` |
| `Image` | `ImageView` | `UIImageView` | `img` |
| `ScrollView` | `ScrollView` | `UIScrollView` | 可滚动 `div` |
| `TextInput` | `EditText` | `UITextField` | `input` |

四条推论，每条都对应一笔真实成本：

**一、写法是 React，不是 HTML。** 你在 Web 里熟到不用想的东西在这里没有对应物：没有 `div`/`span`/`button` 元素，没有级联选择器，样式是 Flexbox 那一套的子集而不是 CSS（官方页面自己写着「Layouts are handled via Flexbox … similar to CSS but applied to native objects」）。**这意味着 Vue/CSS 经验在 React Native 上的搬运率，远低于在 uni-app 或 Capacitor 上的搬运率**——这一点在选型时是加分项还是减分项，取决于你手里已有的资产。

**二、渲染原生控件不等于行为一致。** 同一个组件在两个系统上映射到不同的原生控件，滚动手感、键盘行为、系统对话框都由系统决定。「一次编写」省掉的是 UI 代码，不是「两端各验一遍」。**这一条常被营销话术盖过去，而它是 RN 项目实际工作量的主要来源之一。**

**三、硬件能力经过原生模块。** 官方文档的组件表覆盖的是通用 UI；相机、传感器、后台任务、支付、蓝牙这类要走模块，而模块来自第三方、要跟着框架大版本和系统版本升级。第一个故事的成本就在这里——**注意这一条不是 RN 特有的，Flutter 和 Capacitor 同样有各自的「桥」，只是形态不同。**

**四、这一页官方自己标注了「引用的是遗留 API 集合，需要按新架构更新」。** 这句提醒的价值不是技术细节，而是**读 RN 资料时的方法**：涉及桥、渲染管线的说法要确认它讲的是新架构还是旧架构，否则你会拿一份过时的机制描述去做今天的判断。

本站的立场要说明白：React Native 属于 React 生态。主线技术栈是 Vue 3，所以本章只给定位，不给教学。**如果你的团队已经有大量 React 经验，它是顺路的一条；如果经验全在 Vue，那它相当于「再学一个生态」，这个成本要按一整章来估，不是按「反正都是 JSX」估。**

## Flutter：自带引擎，界面自己画

官方架构概览页（核实时间 2026-10-22）的说法比前一条路线更直白：

> bypassing the system UI widget libraries in favor of its own widget set
> Flutter user interfaces are built, laid out, composited, and painted by Flutter itself
> the engine, written in C++, is designed to interface with the underlying operating system rather than a web browser
> For release, Flutter apps are compiled directly to machine code, whether Intel x64 or ARM instructions, or to JavaScript if targeting the web

官方还把它定位成 "cross-platform UI toolkit"，明确覆盖 iOS、Android、web 与桌面。**四句话讲完了它的优势和它的代价**，逐条翻成判断：

**「绕过系统 UI 控件库」= 一致性最高。** 同一份代码在六个设备上画同一张图，字体、间距、动效曲线全部可控。做品牌化视觉、复杂自定义交互、要求「我们产品的界面在任何地方都长得一样」的团队，这是最直接的价值，也是这条路线最硬的选型理由。

**「自己合成、自己绘制」= 平台习惯要自己给。** 系统控件的行为不在你的渲染里，所以返回手势、滚动物理、对话框、文本选择、无障碍语义这些「本来系统免费送你的」东西，要靠你自己实现或对齐。**推论：用 Flutter 时，「一致」不是免费的，它换来的代价是「你得替系统干活」。** 而这项工作量在 demo 阶段完全看不见，只在用户反馈里出现。

**「引擎与操作系统接口而非浏览器」= 它不是网页壳。** 这一句在商店审核和体验质疑的场景里有实际意义：它和 WebView 容器路线属于不同的技术形态，讨论时不该混为一谈。

**「编译到机器码，Web 端编译到 JavaScript」= 体积与形态按目标平台变化。** 手机上是编译产物（引擎本身要打进包里，这是「体积增加」的来源），Web 上走 JS。**具体增加多少本章不给数字**——它取决于你的构建配置、目标平台和是否做分包/延迟加载，只有你自己的构建产物能回答。

语言层面它用 Dart。本站同样不教学，但要点明一件事：**换语言不是主要成本，换「界面表达方式」才是。** Flutter 的 widget 树组合方式与 CSS + HTML 的分层思路差别很大，一个熟练的 Web 开发者在这里仍然是新手，只是新手期短一些。

## Capacitor 与 Ionic：WebView 容器，复用你已有的 Web 资产

官方对 Capacitor 的定位一句话可核实（核实时间 2026-10-22）：它是一个 "cross-platform native runtime"，让 "Web Native apps" 把 web 代码带到 iOS 与 Android，并且提到构建 Progressive Web Apps 这条路。

**这条路线的技术本质最简单：应用里嵌一个系统 WebView，渲染你已有的网页；需要设备能力时，经过一层原生插件桥出去。** 于是它的成本结构也是三条路线里最极端的——两头都极端：

**复用率最高。** 你现有的 Web 产品（含你在[第二章](/mobile/mobile-web)做的移动端适配、你的 CSS、你的无障碍工作）**基本原样带过去**。对一个人做产品、已有 Web 站点、只是想多一个商店入口的场景，这是三条路线里唯一一条「几天而不是几个月」的。

**上限也最清楚。** 界面由浏览器画，意味着：启动时要加载页面（白屏与否取决于你的构建与资源策略）；动画与手势跟不跟得上系统，取决于你写了什么和这个 WebView 的表现；系统级控件行为不在你手上；**「这是不是网页壳」这个问题会有人问，而它的答案来自你的实际体验而不来自技术分类。**

Ionic 常被和这条路线一起提。本章的诚实标注是：**本批没有单独核实 Ionic 官方页面的原文**，所以下面这句按通用原理写——它长期定位在「用 Web 技术做移动端形态的界面」这一层，提供组件与工具链，运行方式与容器路线一致；具体产品关系与当前形态请以官方当天文档为准。**你在做选型时如果要引用 Ionic，请自己打开它的官方文档确认，不要引用本章。**

## 一张对照表：五个决定成本的轴

不要用「哪个更流行」选型。用这五轴，每轴只回答一个事实问题：

| 轴 | React Native | Flutter | Capacitor 容器 | 你的实际情况 |
| --- | --- | --- | --- | --- |
| 界面由谁画 | 系统控件 | 自带引擎 | WebView | — |
| 已有 Web/Vue 资产的搬运率 | 低（换生态 + 换样式模型） | 很低（换语言与表达方式） | 高（原样带） | 你有什么？ |
| 「像这个系统的 App」 | 大部分免费送 | 要自己实现 | 全靠自己写 | 你的用户在乎吗？ |
| 「各端长得一模一样」 | 要抹平 | 免费送 | 免费送（但送到的是浏览器的一致性） | 品牌一致性值多少？ |
| 设备能力 | 原生模块 | 原生插件 | 插件桥 | 你重度依赖硬件吗？ |

五轴里最容易被忽略的是第四、五行之间的**混淆**：Flutter 和容器路线都「一致」，但它们一致的东西完全不同——一个是「和设计师画的像素一致」，一个是「和浏览器里的一致」。把这两件事当同一件事的团队，会在第一次体验评审时才发现自己选错了。

## 选型场景：按产品特征，不按热度

以下五个场景给的是判据，不是答案。**每个场景的最后一条都是同一个动作：用你自己的核心功能做原型，在你要支持的最低设备上跑一次。**

**场景 A：已有 Web 产品，只想要一个商店入口。** 容器路线。理由：搬运率与时间都压倒性；你缺的不是界面技术，是分发包。**必须提前算的**：审核关注点、离线场景、启动体验，以及「你的 Web 是不是已经做过移动端适配」（[第二章](/mobile/mobile-web)）。

**场景 B：产品以内容/表单为主，视觉要求常规，团队会 React。** RN。理由：系统控件免费送行为一致性，团队语言栈匹配。**必须提前算的**：第三方模块的版本跟进由谁做。

**场景 C：产品价值在自定义视觉与动效，或要求同一界面覆盖手机、桌面、Web。** Flutter。理由：自绘引擎给的一致性无可替代。**必须提前算的**：为「像系统」付的那部分工作量，以及体积对你用户下载意愿的影响。

**场景 D：核心是设备能力或性能边界（持续后台任务、复杂多媒体、大量传感器、实时图形）。** 先别问跨端，先问原生。理由：这类产品的真实工作不在 UI 层，跨端给你的桥反而是要跨的两层。

**场景 E：用户入口在国内的微信生态里。** 先做小程序，不是这三条中的任何一条。理由见[第一章](/mobile/choosing-route)的分发那一格——**分发决定路线，不是技术决定路线。** 这也是为什么本站把小程序放在这条主线、把跨端只放在概览。

## 原生开发什么时候仍不可替代

「不可替代」容易被讲成情绪，其实可以列成判据。**命中任意两条，就别再讨论跨端框架，直接做原生（或者不做）：**

1. **你的核心体验发生在系统层。** 桌面小组件、灵动岛形态、锁屏与控制中心、系统级输入法集成、Watch/车机/电视形态。框架的抽象层覆盖不到这些，你写到最后还是要原生的。
2. **你的性能预算在渲染管线之外。** 后台持续定位与采样、长时录音、蓝牙稳定连接、实时音视频、大量传感器融合。这里的问题是**进程与系统策略**，不是 UI 快不快。
3. **你要跟一个新系统能力同期发布。** 平台刚放出的能力，原生第一时间可用；跨端要等抽象层跟上——第 5 章那条「三层日历」在这里同样成立，只是参与者换成 RN 或 Flutter。
4. **无障碍与安全语义是你的合规要求，不是加分项。** 系统控件自带语义；自己画的界面里，语义要你逐条实现与验证。**如果你在医院、金融、公共服务场景，这一条往往是决定性的。**
5. **你的产品其实只有一个平台。** 只做 iOS 且深度绑定 iOS 生态，那任何跨端都是净负担。

反过来，上面一条都没命中，那原生的优势主要是「什么都不用猜」——它省掉归因层，但换来两份代码。**这笔账在第[一章](/mobile/choosing-route)里已经用四笔账算过，本章不重复展开。**

## Web 优先策略下，这三条路线的真实必要性

本站主线是「Web 优先 + 小程序做分发」，所以这一节要给一个可能不受欢迎的结论：**对绝大多数个人开发者和早期产品，这三条跨端路线的必要性都低于它们的讨论热度。** 理由不是它们不好，是**问题不存在**。

判据四条，按顺序问：

**一、有没有一件用户要做的事，Web 与小程序都做不到？** 如果答案模糊，那你的需求是「想有个 App」，不是「需要 App」。把这句话问出口，很多讨论当场结束。上一节那五条判据是这一问的展开。

**二、你现在这个 Web 产品，在手机上体验合格了吗？** 这一问的性价比最高，因为它不需要任何新技术决策。[第二章](/mobile/mobile-web)那六件事没做完之前，讨论跨端就是在给一个还没修好的界面挑渲染引擎。

**三、分发瓶颈在哪？** 如果你的用户是通过链接与扫码找到你的，那多一个小程序入口的收益，几乎肯定大于多一个商店包（后者要审核、要版本管理、要维护两套发布节奏，见[第一章](/mobile/choosing-route)那条「发布周期决定服务端欠多少债」）。

**四、你能不能同时认真验证两端？** 跨端的真实成本不在第一天，在第 60 天：每次改动要在多个端上验，出问题要先判断是逻辑、编译产物还是平台行为。一个人回答不了「我有没有时间双端验证」，就先别开这个头。**编译得过不等于验过**——这句在第 5 章针对 uni-app 说的话，对三条跨端路线同样成立，而且更成立，因为它们的差异更大。

四条问完还有热情，那再按场景 A/B/C 挑路线。**这套顺序的价值不在于帮你选对，在于帮你把「现在不做」这个选项变成一个有依据的决定**——多数时候，它就是正确答案。

## 常见错误与排查

**一、把「用 JavaScript/类 Web 语法」当成「我会这个」。** 现象：上手期比预期长。原因：语言相同不代表界面表达方式相同（RN 的样式模型、Flutter 的 widget 组合都不是 CSS 直觉）。怎么确认：让团队里最熟 Web 的人读一小时该框架的组件文档，然后问他「你现在怎么画一个底部操作栏」。答不上来就是新手期，按新手估时间。

**二、用 demo 的工作量估全项目。** demo 里没有的东西：设备能力、异常态、无障碍、离线、审核条款、系统版本碎片。怎么修：估工期时显式加一项「桥与模块维护」，并把上一节那五条判据逐条对照你的产品。

**三、以为跨端等于「验一次」。** 现象：某个系统版本上的滚动、键盘或对话框行为不对。原因：界面由系统控件或系统 WebView 决定时，行为归系统。怎么修：验证矩阵按「端 × 系统版本 × 你自己那两台真机」列，写进发布清单，见[发布与回滚](/devops/release-and-rollback)。

**四、把 Flutter 与容器路线都叫「一致」。** 现象：视觉评审时说「这不像我们的设计」，但两端截图完全一致。原因：一致的是渲染，不一致的是平台习惯。怎么修：评审分两次——视觉一致性（设计稿对照）与行为一致性（拿同功能的主流 App 对照）。

**五、把第三方模块当内部代码。** 现象：框架大版本升级卡住，因为某个模块没人维护。怎么修：把每一项设备能力依赖标成外部依赖，写明维护状态与替代方案。这一条与[服务器安全](/linux/server-security)里「依赖是你的负债」的口径一致。

**六、容器路线只测 H5 不测壳内。** 现象：浏览器里正常，装进 App 后启动白屏几秒、返回键行为怪、软键盘顶歪布局。原因：容器有启动路径与系统键盘行为，和浏览器标签页不是一回事。怎么修：**必须在真机装包测**，这条与[第 7 章 真机调试](/mobile/device-debugging)会正面展开。

**七、拿别人的性能数字做自己的决定。** 现象：按网上的帧率与体积对比表选框架。原因：那些数字来自别人的功能、别人的构建配置、别人的设备。怎么修：本章唯一保留的动作——用自己的核心功能做原型，在目标最低设备上跑。**本站也不给数字，正是这个原因。**

**八、在微信生态里做 App 而没做小程序。** 现象：下载量小、注册摩擦大。这不是技术错误，是路线错误——分发那一格没算。怎么修：回到[第一章](/mobile/choosing-route)的决策树重走一遍，先做分发链路要求的那一端。

## 练习

<Exercise title="把三个方案写成一页选型意见" difficulty="基础">

假设你要把一个已有的 Vue 3 Web 产品带到移动端，需要同时考虑微信小程序与 App 两个候选入口。用不超过两百字，写出你会先做哪一个、为什么，并把理由挂到四笔账（钱、时间、风险、机会）中的两笔上。

<template #answer>

一份合格意见的样子（数字按你实际情况填）：

**先做小程序，App 用现有 Web 走容器路线延后评估。** 关键的两笔是「时间」与「风险」：小程序在你已有链路里（用户在微信里，扫码即用，没有安装决策），第 3、4 章那套机制你已经能读；容器路线虽然复用率高，但它的风险项集中在**分发与审核**——商店要审核、包要维护、启动体验要重做，而这些都发生在产品还没验证「移动端入口本身有没有价值」之前。**机会账上要算的是「多一个入口能带来多少留存」而不是「少一个入口会不会被说没技术」**，前者能从你的用户路径里估，后者是情绪。

判断被推翻的信号也很明确：如果用户明确需要后台持续任务、系统级集成或重度硬件（本章那五条判据命中两条），那容器路线与小程序都满足不了，那时才该正面评估 RN 或 Flutter。**先算产品，再挑引擎，这个顺序不要反过来。**

</template>

</Exercise>

<Exercise title="给一个功能标出它真正的成本层" difficulty="进阶">

下面六个功能，逐个判断它的成本主要落在哪一层：UI 层（画界面）、桥层（设备能力与模块维护）、分发层（商店/平台/审核）、系统层（系统习惯与语义）。写出你的判断与一句理由。

```text
1. 一个自定义的滑动转场动画
2. 后台每五分钟采集一次位置
3. 底部导航栏与返回手势
4. 上架时需要的隐私说明与审核材料
5. 一套品牌化的空状态与骨架屏
6. 系统分享面板里出现你的应用
```

<template #answer>

1 **UI 层**。自绘路线在这里最占便宜：一致性免费送；RN 与容器路线要分别处理，且容器路线的上限由浏览器动画能力决定。
2 **桥层，且部分是系统层**。采集的痛点不是界面，是后台策略、权限引导与省电限制——任何路线都要跟系统谈，跨端只多给一层桥的维护。这类功能命中「原生不可替代」第 2 条。
3 **系统层**。底部导航与返回手势是用户对手感的记忆，不是对像素的记忆。用系统控件的路线免费送一部分，自绘路线要你逐条对齐，容器路线基本靠你自己写并且仍不等于系统行为。
4 **分发层**。它跟框架无关，RN、Flutter、容器、原生在商店面前付同一笔钱——而这一笔常常是「要不要做 App」的决定项，见[第一章](/mobile/choosing-route)「先审核再发布」那格。
5 **UI 层**。纯绘制，三条跨端路线都能做到设计稿一致；真正要看的是你已有的 CSS 资产能不能搬——容器路线搬运率最高，这条在第 5 章已经写过判据。
6 **系统层 + 分发层**。出现在系统分享面板要靠原生能力配置（各家框架都走插件/模块），而「能不能被搜到、愿不愿意被安装」是分发层问题。技术层给不了你这两个答案。

**这张题的价值在分布**：如果六个功能里有四个落在桥层、系统层、分发层，那你的项目成本根本不在「界面用谁画」上——**这时讨论框架选型是在解决错误的问题。** 这个检查动作值得每次选型做一次。

</template>

</Exercise>

<Exercise title="设计一次能让你改主意的原型验证" difficulty="挑战">

请你为「要不要做 App」这个决定，设计一次不超过三个工作日、在一台你手上真实的老设备上完成的验证。要求写清：验证哪三件事、每件怎么算通过、哪个结果会让你放弃做 App、哪个结果会让你去做原生而不是跨端。

<template #answer>

一道考「验证设计」的题，答案合格与否看四件事：**是否可执行、是否有失败判据、是否避免了数字对比、是否留出改主意的出口。** 示例方案：

**验证三件事（按这个顺序，前一件不过就停）。**

一、**产品是否被需要**：把现有 Web 的地址直接给你十个真实用户（不要预告「我在做 App」），一周后看有多少人二次打开。**通过线自己定，但必须是「回访」这种可观察行为**。一个人都没回来，就不用讨论 App 了——这是放弃做 App 的那个出口。

二、**Web 在移动设备上的体验底线**：把同一地址装进手机的浏览器（也试一次容器壳，如果有现成的），在你那台最旧的设备上跑三个动作：首屏可交互要等多久、列表快速滚动时是否明显掉帧、软键盘弹出会不会顶歪输入框。**这里不打分、不对比别人的数字，只记「我能不能忍受把它当产品交付」**。因为这三项都是[第二章](/mobile/mobile-web)的内容，先修它们比换引擎便宜得多。

三、**能力边界**：写下你未来六个月内最想做但 Web/小程序做不了的两件事。写不出来 → 不该做 App（这一问就是本章「必要性评估」第一条的实操版）。写得出来但都属于后台任务、传感器、系统级集成 → **做原生**，因为这三条正是「跨端只跨界面层」会硌到你的位置，而你的工作根本不在界面。

**改主意的出口要提前写死**：如果第二件的结果是「修一修就够」，而第三件写不出 Web 做不到的事，那结论是**把精力放回 Web 与小程序**，并给 App 设一个重新评估的条件（例如月活或分发需求达到某个你自己认的门槛）。**没有这一条的验证只是走流程。**

诚实提醒：这三件事都需要真实设备与真实用户，本站无法替你完成，也没有任何文档能替你回答第一件。**能替你回答它们的只有你自己那一周的数据。**

</template>

</Exercise>

## 下一章

本章给的是地图：**跨端的差别在界面由谁画，而多数个人产品真正卡住的地方在分发和 Web 体验本身。** 你如果按本章的评估问完四条、仍然决定要做一个移动端入口，那么接下来要处理的问题就不再是「选哪条路线」，而是两类很具体的事：**代码在模拟器里跑对了、真机上不对；以及你怎么把东西真的送上线。**

下一章是[第 7 章 真机调试](/mobile/device-debugging)，它讲的是微信开发者工具的使用、模拟器与真机的差异为什么让「模拟器过了」不算数、真机预览与远程调试、日志查看，以及一份「工具里正常、真机上不正常」的问题清单——本章容器路线那第 6 条常见错误，正是那要在那里被正面处理的问题。再往后是[第 8 章 发布流程](/mobile/release)，它管的是本章分发层那笔账的操作细节：主体类型、类目与资质、提审自查、被拒原因与版本管理。两章读完，[第 9 章 阶段项目](/mobile/project)会把它们和第 3、4 章的开发闭环一起收成一次真实交付。

如果你现在只想要一个可执行的建议，那就是本章那条贯穿判据：**先做第 2 章，再按第 1 章的决策树决定要不要做第 3 到第 8 章，而跨端路线留到你写得出「Web 与小程序做不到什么」那一天再评估。**
