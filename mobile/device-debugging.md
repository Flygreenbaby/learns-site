# 模拟器只验语法，真机才做终审：把「不一致」变成可复现的证据

第一个故事是白屏。有人在开发者工具里把新页面写完，模拟器一切正常，直接上传提审。体验版发给朋友，第一个反馈是「点进去是空的」。工具里查不出任何问题——真正的差别在两处他看不见的地方：他的项目里勾着「开发环境不校验请求域名」，而那台手机的微信登录的账号还没被加进体验成员；以及真机上跑的**基础库版本**和他工具里选的版本不是同一个。

第二个故事是键盘。一个输入页在工具里怎么滚都对，真机上「一点输入框，提交按钮就被顶到屏幕外」。他在工具里模拟不了这件事——**开发者工具的模拟器不会弹出软键盘**，而这正是[第二章](/mobile/mobile-web)那节「软键盘弹出对布局的影响」在小程序里的复现现场。修完之后他给自己立了一条规矩：任何带输入框的页面，不上真机不算写完。

第三个故事最贵。一个「只在部分用户身上出现」的问题反复出现又消失，他每次都在工具里点「清缓存并重新编译」，于是本地存储里的脏数据被清掉，现象也就跟着消失了。**他用重编译掩盖了现场**，最后是靠真机上带版本号的日志才把链路还原出来：某次接口返回结构变化后，老缓存里没有新字段，而代码默认它一定在。

三个故事讲的是同一件事：**调试的能力不是「会不会用工具」，是「能不能把一次不一致变成可复现、可归因、可验证的证据」。** 工具给你的证据只覆盖一部分层次，剩下的必须由真机和真实环境补上。这一章教你缩小范围的方法，也给你一份「工具里正常、真机上不正常」的问题清单——清单的价值不在于提前知道答案，在于**出问题时你知道该往哪一层看，而不是逐层乱改**。

<Callout type="verified">

**本批核实到的官方事实**（核实时间 2026-10-22）：开发者工具官方页面原文「集成了公众号网页调试和小程序调试两种开发模式……使用小程序调试，开发者可以完成小程序的 API 和页面的开发调试、代码查看和编辑、小程序预览和发布等功能」；官方调试页面的能力清单为 **vConsole、Source Map、真机调试、实时日志** 四项。

**本章的边界**：本批 **0 台真机、0 次工具安装、0 次上传与提审**。所以下面所有操作步骤都写成「你该做什么、看什么、记下什么」，不写成「我已验证」。工具界面项的名称与位置会随版本变化，**以你装到的那一版为准**；涉及具体接口名、参数与限制的地方，本章只引用已核到的官方原文，其余标注未核实。

## 四类证据对应四个动作

先给一张「想看什么 → 去哪儿看」的表。它比工具菜单的罗列有用，因为它按**问题类型**组织。

| 你想知道的 | 用什么 | 得到的证据形态 |
| --- | --- | --- |
| 我的代码是不是按语法跑起来了、报什么错 | 工具里的调试器 | 控制台错误、调用栈（配合 Source Map 还原到源码行） |
| 数据对不对：`data` 里现在是什么 | 工具的调试面板 | 数据快照、事件绑定关系 |
| 样式怎么算出来的、节点树长什么样 | 工具的视图面板 | 节点层级与计算后的样式值 |
| 请求发出去了吗、返回了什么 | 工具的网络面板 | 请求/响应原文、耗时、状态码 |
| 用户设备上实际发生了什么 | 真机 + 真机调试 / vConsole | 真机的实时日志、真实网络与键盘环境 |
| 出了线上问题、手里没有那台设备 | 实时日志（官方能力之一） | 用户侧上报的日志，可事后查 |
| 这份代码到底会被用户拿到哪一版 | 上传 + 版本列表 | 开发版/体验版/线上版的对应关系 |

**最后一行是很多人完全跳过的**，而它恰好是「代码写完」和「用户用得上」之间那段距离的名字。三者的官方定义在第 [8 章](/mobile/release)给出，本章先记住一条：**你在工具里改的代码，和体验版里的代码，和用户手里的代码，是三个不同的产物。**

## 为什么「模拟器过了」不算数：五个层次

模拟器能验的和不能验的，分五层。每层给出「模拟器可验 / 不可验」的判据——**这张表是本章的核心，其余内容都在用它。**

**一、渲染层。** 小程序的视图层运行在 WebView 里，而工具的模拟器是桌面环境的实现：字体、行高、亚像素、图片解码、`rpx` 换算的落点都可能不同（第 3 章讲的单位换算在这里兑现）。**可验**：布局是否成结构、样式语法是否报错。**不可验**：字号是否可读、一根边框在高清屏上是否变粗、图标是否糊。**判据：任何「看起来不对」的视觉问题，最终结论只能由真机截图给。**

**二、基础库版本。** 工具里可以选版本，但用户微信里的版本不由你决定——这是第 5 章那「三层日历」里唯一你管不了的那一格。**不可验**：某接口在低版本上不存在时的降级表现、平台对交互规则的调整。**做法：把「接口不存在」当成必然路径写代码**，用可用性判断兜住，再在真机上验一次。

**三、网络前提。** 工具的「不校验域名」选项会盖掉线上会暴露的三类问题：域名没登记、协议不是 https、证书链不完整（第 4 章原文条款）。**做法：开发期用完就关掉它，并且至少提审前关掉再跑一次全流程。** 这一项的收益极高，因为它把「审核后才发现的错误」变成「提审前发现的错误」。

**四、系统能力与权限。** 键盘、剪贴板、定位授权、相册授权、通知、扫码——这些都发生在系统层，模拟器给不了真实交互。**不可验的典型**：授权被拒后的界面、键盘弹出时的遮挡、切到后台再回来的状态恢复（第 4 章那张 `onShow` 场景表，只有真机能造出「切走再切回」）。

**五、性能与内存。** 长列表滚动、大图解码、一次性传大量数据给视图层的代价，在桌面上会被掩盖。**判据不是「流畅不流畅」这种感受，而是「在你手上最旧那台设备上，走完这条链路你愿不愿意交付」**——这也是第 6 章那条「别拿别人的数字做自己的决定」的同一纪律。

把这五层合起来，就是本章那句结论：**模拟器验的是「代码是否按语法运行」，真机验的是「在用户的条件下运行得对不对」。** 两者不是重复劳动，它们回答的是不同的问题——所以「改完必上真机」不是勤勉口号，是**证据类型的补齐**。

## 三层现场：先确定你在哪一层调试

现象出现在哪一层，决定了你能用什么取证手段。

```text
你眼前（工具）        体验版（真机 + 白名单成员）      线上版（所有用户）
   调试器 / 面板          真机调试 / vConsole              实时日志 / 用户反馈
   完整数据可看           接近真实环境，可复现             只有上报的日志
   快、可改可试           慢、要重新上传                  事后、不可改现场
        └──── 只有前两层能复现的，多半是环境差异 ────┘
        └──── 只有第三层能看到的，多半是条件差异：版本、设备、账号状态 ────┘
```

三条推论：

**一、能在线上复现的问题，先别改代码，先把现场固定下来。** 记录：哪一版、哪个页面路径、什么操作序列、设备与系统、当时的网络。这份记录的价值高于任何一次猜测性修改——这条纪律在[测试](/devops/testing)里叫「先让 bug 稳定，再让它消失」。

**二、体验版是唯一一层「接近真实但你还能控制」的现场。** 所以值得为它建立一个固定动作：**每次准备提审前先出体验版，在真机上跑一遍主流程**，而不是上传完就提审。这一遍的成本是十分钟，收益是省掉一次审核往返（第 8 章会给出那句官方原文：过多的审核不通过可能影响后续时间）。

**三、白名单不是可选项。** 体验版需要成员身份才能打开，这是最常见的「朋友说打不开」根因。把这件事写进你的发布步骤，而不是临时想。

## 一分钟分诊：现象出现时按这个顺序问

不要把这张决策树当查表答案，它是**排除顺序**——目的是最快把嫌疑面从「所有代码」缩到「一层」。

```text
真机上出问题
  ├─ 打开就白屏 / 报错？
  │     ├─ 是 → 先看是不是域名与协议（关掉不校验选项复现）
  │     │        再看基础库版本：这个接口是不是低版本没有
  │     └─ 否 ↓
  ├─ 只有某类设备出现？
  │     ├─ 是 → 视觉类：字体 / rpx 落点 / 安全区 → 用截图对照，逐台记
  │     │        交互类：键盘 / 手势 / 授权 → 只能真机复现
  │     └─ 否 ↓
  ├─ 只有切走再回来 / 返回上一页时出现？
  │     └─ 是 → 生命周期时机问题，回第 4 章那张 onShow 场景表
  ├─ 只有第二次进入 / 用过一段时间才出现？
  │     └─ 是 → 本地存储脏数据。取证：清缓存前后各跑一次同一序列
  ├─ 只有数据量大 / 列表长时才卡？
  │     └─ 是 → 一次提交给视图层的数据量问题（第 3 章那五条官方建议）
  └─ 以上都不是 → 那就把它变成可复现：写操作序列 + 加带版本号的日志，
                   不要靠「再试一次看看」推进
```

**最后那一条最重要**：不可复现的问题不值得动手改代码。改一次「试试看」的成本不只是时间，它会把你的因果记录搞乱——下一次你以为修好了，其实是清缓存了。

## 日志：三种日志各回答什么问题

官方调试能力里的 vConsole、真机调试、实时日志对应三类现场，加上你自己的服务端日志，一共四类，各回答一个不同问题：

| 日志 | 回答的问题 | 必须带的字段 | 常见误用 |
| --- | --- | --- | --- |
| 工具控制台 | 我这行代码执行了吗、抛了什么 | 页面路径（靠上下文即可） | 只在工具里看，从不为真机准备 |
| 真机上的 vConsole / 真机调试 | 这台设备上实际发生了什么 | 接口返回原文、错误对象 | 只截错误弹窗，不记请求参数 |
| 实时日志（官方能力） | 用户身上发生过什么 | 版本号、页面路径、基础库版本、错误 | 上线后才想起没埋日志 |
| 你的服务端日志 | 这个用户请求了几次、哪一次失败 | 你的会话标识、接口名、版本维度 | 没有版本维度，无法判断老客户端 |

写日志的四条纪律，比任何工具名称都耐用：

**一、带上版本标识。**「第 3 版号 + 页面路径」这两个字段能让 80% 的「只在部分人身上出现」变成可判断问题。这一条与[日志与监控](/backend/logging-and-monitoring)里「先有维度再谈分析」的顺序一致。

**二、别把敏感内容写进日志。** 会话凭证、密钥、用户手机号原文都不该出现在日志文本里，它们可能同时进入本地存储与上报链路。这条属于[服务器安全](/linux/server-security)的范围，但在这个领域里更容易被忽略，因为「反正是我自己手机」。

**三、日志要有能关掉的方式。** 上线版本里的详细日志既是攻击面也是性能负担；用一个由服务端控制的开关决定它开不开，别用编译期常量——后者要发版才能关（第 1 章那条「不发版就能关掉」在这里同样成立）。

**四、为「取证」写日志，而不是为「调试这一行」写。** 区别在于：前者记录输入、分支判断的结果和输出，事后能重建路径；后者只证明代码走到过这里。第一个故事里那句「点进去是空的」，需要的正是第二种。

## 工具里正常、真机上不正常：八类现场

这张表按出现频率排。**「怎么取证」那一列是重点——现象本身不值得记，取证动作才值得记。**

| 现象 | 第一现场 | 怎么取证 | 修法方向 |
| --- | --- | --- | --- |
| 请求全部失败，工具里正常 | 域名没登记，或工具勾了「不校验」 | 关掉不校验选项在工具里复跑一次，看是否同样失败 | 回第 4 章那三条检查：域名、https、取消勾选 |
| 布局错位、字号偏小、边线粗细不一 | 渲染层与单位换算差异 | 同一屏在两台设备上截图并排 | 尺寸下限用 `px`，别什么都按 750 设计稿换算 |
| 底部按钮被挡住一半 | 安全区，工具里不表现 | iPhone 真机截图，看底部留白是否等于按钮高度加留白 | 用平台的容器与安全区留白；数值靠真机量 |
| 一点输入框，页面就跑掉 | 软键盘弹出，工具不弹键盘 | 真机上依次点每个输入框，观察顶栏与底部区 | 第 2 章那四种对策里挑最便宜的（滚动到可见） |
| 返回后数据没了或重复加载 | 生命周期时机判断错 | 在 `onLoad`/`onShow` 打日志并带页面栈长度 | 脏标记或上一页回传（第 4 章做法一/二） |
| 第二次进入才出问题 | 本地存储脏数据 | 清缓存前后各跑同一操作序列，对比 | 给缓存加版本与失效条件 |
| 长列表很卡 | 一次提交给视图层的数据过大 | 记录一次提交的键与数组长度，再看卡顿是否随长度变化 | 分页、只传变化字段（第 3 章官方建议） |
| 某些用户那里整块功能消失 | 基础库版本或能力可用性 | 记下出问题用户的版本信息，加可用性判断 | 降级路径 + 服务端开关，别让页面白屏 |

**这张表的正确用法是把它抄成你自己的清单**，每次真机验证时逐项打勾。清单不必一次写完：你在自己的项目里每撞到一个新「真机独有」问题，就加一行——**这份清单会是你在这个领域里最值钱的个人资产**，比任何教程都贴合你的代码。

## 建立「改完必上真机」的最小工作流

不要试图给自己上一套完整测试体系。下面这个最小循环能覆盖绝大多数个人项目的收益：

```text
每次改动的循环（约 8–15 分钟）
  1. 工具里跑一次主流程          → 证明语法与数据通路没错
  2. 关掉「不校验域名」再跑一次   → 证明域名前提成立
  3. 上传出体验版                → 固定一个可追溯的版本号
  4. 真机走同一条链路            → 补齐工具给不了的四层证据
  5. 有问题：按决策树定层，加带版本号的日志取证，再改
  6. 无问题：在记录表里加一行（版本、设备、验过的场景）
```

配套的记录表，四列就够：

```text
版本 | 日期 | 设备（型号 + 系统） | 验过的场景与结论
0.3.1 | 2026-10-22 | iPhone 某型号 | 下单主流程 / 键盘弹出 / 返回后列表位置保持 → 通过
0.3.1 | 2026-10-22 | 某安卓机 | 弱网下首屏 → 骨架屏 6 秒未消失 → 待修
```

**为什么第 3 步「先固定版本号」不可省**：如果你没有把「现象」和「哪一版代码」绑起来，那么第 5 步改完之后你无法证明问题是被你修好的，还是被下一次上传覆盖掉的。这条与[发布与回滚](/devops/release-and-rollback)里「发布物与验证物对齐」是同一件事。

## 常见错误与排查

**一、把工具当验收环境。**现象：审核被拒或用户反馈打不开。原因：工具环境掩盖了域名、基础库、成员白名单、键盘四类差异。怎么改：把上面那个六步循环写进你的流程，缺一环就不算完成。

**二、勾着「不校验域名」一路做到提审。**现象：真机一片请求失败。怎么确认：把勾选取消后再跑一次。怎么改：把它当调试专用开关，用完关回去；这条是本章性价比最高的一处修改。

**三、只在 Android 上测。**现象：iPhone 用户报遮挡。原因：安全区与键盘行为在不同系统上差别明显，第 2 章那条纪律在这里同样成立。怎么改：验证清单里硬性包含「至少一部 iPhone」。

**四、清缓存当成修复。**现象：清了就好，第二天又出现。原因：脏缓存只是症状，你的读写代码假定了字段一定存在。怎么改：给缓存加版本号与失效条件，并让代码能处理「缓存里没有」这条路径。

**五、日志只在开发期存在。**现象：线上问题无从判断。怎么改：上线版本保留最小必要日志（错误 + 版本 + 页面路径），并用服务端开关控制详细级别。

**六、把「真机调试连不上」当代码问题。**现象：工具连不上手机，于是开始改逻辑。原因：这是连接与授权问题，与你的业务代码无关。怎么改：先把「连不上」和「连上后看到异常」当成两类问题分别处理——前者查网络、账号、工具版本，后者才查代码。

**七、一次改多处，然后不知道哪处生效。**现象：改了三个地方，问题消失。怎么改：一次只动一个变量并复现一次。这条纪律来自[测试](/devops/testing)与[复杂度分析](/computer-science/complexity)里那条共同的判断：不能归因的修复不是修复。

**八、没有把「验过」写成可交接的东西。**现象：三个月后你忘了当时哪台设备验过什么。怎么改：那张四列记录表。它的第二个用途是提审被拒时的证据材料。

在任意一个页面上做一个改动：底部固定一条操作栏，内高 44，紧贴屏幕底边，左右不留安全区留白。然后在工具里看一次，在真机（尤其 iPhone）上看一次。

写下两次观察的差别，并给出你的修复方式与「怎么证明修复生效」的判定动作。

<template #answer>

预期现象：工具里完全正常（工具不模拟真实的安全区与容器留白）；真机上底部那条会被系统指示条部分遮挡，或者视觉上「贴得太死」，按钮下半部分难以按准。

修复方向：把底部留白交给安全区，而不是把按钮往上挪几像素——前者是「让布局自己适配」，后者是给某一台设备调参。做法是在容器上留出安全区高度，并保留一个不带安全区时的兜底值（这与[第二章](/mobile/mobile-web)那条 `env()` 写法同源）。

判定动作要写成可观察的：在 iPhone 上打开该页，**用手指按按钮下边缘最靠近屏幕底部的那个点**，看是否能正常触发；再截一张图对比按钮下沿与系统指示条之间是否有可见留白。两条都过才算修好。

再补一条：把「带底部固定操作栏的每个页面」列出来逐个验，不要只验你改的这一页——遮挡问题通常是同一类写法在多处重复的结果，这与[代码规范](/devops/code-standards)里「能被机制保证的才不用检查」的判据一致：这里机制给不了你，所以只能逐个检查。

</template>

</Exercise>

<Exercise title="用一条日志把不可复现变成可复现" difficulty="进阶">

用户反馈「有时候打开列表是空的，退出再进又有了」。你手里没有那台设备。请设计一条（一组字段构成的）日志语句，让下一次发生时能判断问题出在哪一层；并说明这条日志应该出现在哪个环节、上线版本里要不要保留。

<template #answer>

需要的字段不是「出错了」，而是能把四种可能分开的四类信息：

```js
// 在列表请求返回处，一条日志分开四件事：走到没有、返回什么、写了什么、渲染了什么
logger.info('list.probe', {
  appVer: MY_VERSION,          // 你的版本号：区分「只有老版本有」
  page: 'pages/list/list',
  lib: '基础库版本（按平台接口取）',
  reqId: task && task.id,
  statusCode: res && res.statusCode,
  itemsLen: Array.isArray(res && res.data && res.data.items) ? res.data.items.length : -1,
  cachedLen: Array.isArray(cache && cache.items) ? cache.items.length : -1,
  rendered: this.data.list.length
});
```

这四个数就能把现象分流：**`statusCode` 非 2xx** → 服务端或会话失效；**`itemsLen` 为 0 而 `cachedLen` 大于 0** → 渲染取了缓存；**`itemsLen` 正常而 `rendered` 为 0** → 数据到 `setData` 之后没进视图（第 3 章「改 `this.data` 不走桥」那一类）；**`itemsLen` 为 -1** → 返回结构和你的假设不一致，这是第一个故事里那个 bug 的形态。

环节：请求回调处，而不是错误处理分支——因为「空列表」通常不抛错。上线版本：**保留**。这条日志没有敏感内容，代价是一次信息级上报，而它是你唯一能在没有那台设备时取证的手段（第 4 条纪律「为取证写日志」）。同时把详细级别做成服务端可关的开关，见本章第三节第三条。

诚实提醒：`logger`、平台取基础库版本的接口名与 `task.id` 的可用性，本章未逐项核实，按官方文档当天版本替换；这段代码的价值在**字段设计**，不在标识符本身。

</template>

</Exercise>

<Exercise title="把域名前提变成提审前的固定动作" difficulty="基础">

写出你从这个项目开始会长期执行的「提审前 10 分钟检查」，不少于八项，并且每项都要能被一个具体动作判定（不能写「检查网络」这种无法执行的话）。

<template #answer>

一份合格的清单（每项后面是判定动作）：

1. **关掉「开发环境不校验请求域名」，走一遍全部主流程。**判定：所有请求成功；有一条红字就不算过。
2. **域名与线上域名逐字符核对**（子域、端口都算不同）。判定：后台列表里的字符串和代码里的一致。
3. **体验版在自己的手机上跑一遍主流程。**判定：不是「打开过」，是走完成功路径（下单、提交、支付之外的核心动作）。
4. **至少一部 iPhone 上验底部固定区与键盘弹出**。判定：按最下缘能触发、输入时提交按钮仍可达。
5. **弱网或断网场景一次**。判定：有骨架屏/失败态，且不出现白屏。
6. **未登录与登录失效各一次**。判定：不出现「空数据但无提示」的第三种状态。
7. **长列表与大图页面各滚一遍**。判定：可接受的流畅度由你自己定，但要写在记录表里。
8. **版本号与记录表一致**。判定：这一版在记录表里有行，且行里写清验过哪些设备与场景。
9. **包体积报告看一次**。判定：主包与分包的分布符合第 4 章那条「按用户路径划边界」，不是按代码分类。
10. **服务端有这一版的错误维度可看**。判定：能回答「这一版有没有报错」，与[日志与监控](/backend/logging-and-monitoring)的维度要求一致。

**这份清单的正确使用方式是抄下来、贴在项目里、每次提审逐条打勾。**它的第一版不必完整——你在第 9 章阶段项目里每撞一次坑，就补一项。清单里那些需要账号与设备的项属于**真实环境目标**，本机无法代劳；这也是它比任何工具配置都更能决定上线顺利程度的原因。

</template>

</Exercise>
