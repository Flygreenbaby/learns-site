## 这个领域解决什么问题

你的产品上线了，是一个跑在浏览器里的 Web 应用。然后你会陆续遇到这些问题：

- **用户在手机上打开你的页面，布局挤成一团，按钮小得点不中，底部操作栏被 iPhone 的「小黑条」挡住一半。** 这是移动端 Web 适配问题：视口（viewport）、安全区（safe area）、触摸事件与鼠标事件的差异、软键盘弹出把输入框顶出屏幕——每一个都有具体的成因和具体的修法。
- **朋友说：「你这东西怎么没有小程序？发个链接还得跳浏览器。」** 在国内场景，微信小程序承载了大量「用完即走」的产品形态，分享链路、支付能力、用户习惯都指向它。做不做小程序是一个产品决策，但前提是你得知道做它的真实成本。
- **面对「要不要做 App」这个问题，你完全没有判断框架。** 响应式 Web、小程序、跨端 App、原生 App——四条路线的成本、能力边界、分发方式完全不同，选错的代价是以月为单位的重工。
- **学过 Vue 3 之后看小程序文档，感觉「像又不太像」。** 模板像但不是 HTML，数据绑定像但不是响应式，生命周期名字都认识但触发时机不同。这种「似是而非」恰恰是最容易写出 bug 的状态——你以为 `setData` 和改一个 `ref` 是一回事，其实背后是两套完全不同的渲染机制。

**先说清楚本站的立场**：主线技术栈是 Vue 3 + Web，所以本领域以「**移动端 Web 适配 + 微信小程序 + uni-app**」为重点，React Native 只做概览级介绍（它属于 React 生态，与本站主线重叠度低，且学习成本接近再学一个平台）。这个取舍的依据会在第 1 章的路线对比里完整论证，而不是让你凭感觉接受。

另一个诚实的提醒：移动端是本站所有领域里**平台规则依赖最重**的一个。小程序的审核政策、API 能力、类目资质要求由平台方决定且会变化；你写的代码对不对，最终由平台的审核和真机说了算。学这个领域必须养成「以官方文档和真机表现为准」的习惯，博客教程的保质期比 Web 领域更短。

## 前置知识

- [Vue 3](/vue/)——本领域的核心教学方法是「与 Vue 3 的心智对照」：WXML 对照模板语法、`setData` 对照响应式、小程序生命周期对照组件生命周期。没有 Vue 3 基础，这套对照法就失去了锚点，小程序会变成一个要从零硬啃的新体系。

软性依赖：第 2 章移动端 Web 适配本质上是 [CSS](/css/) 与 [HTML](/html/) 知识在移动场景的应用（视口单位、Flexbox、媒体查询都会直接用上）；uni-app 章节会用到[前端工程化](/frontend-engineering/)的构建概念。阶段项目如果要接自己的后端，则需要[后端开发](/backend/)的能力。

## 学习顺序建议

**按 1 → 9 顺序学，但第 1、2 章建议提前。**

- **第 2 章移动端 Web 适配是全站性价比最高的一章**：它直接改善你现有 Web 产品的体验，不需要任何新平台、新账号、新审核。如果你只打算学本领域的一部分，就学这一章。它可以在第一期做产品时就介入。
- 第 1 章的路线对比在做任何投入之前读，它决定你要不要继续往下学第 3–8 章。
- 第 3、4 章必须连着学，而且**对照表要自己动手填**：一边开着 Vue 项目一边开着小程序项目，把两套生命周期、两套数据更新机制并排写下来。只用眼睛看的对照是记不住的。
- 第 5 章 uni-app 放在原生小程序之后是刻意的：**先用原生方式理解小程序的机制，再看 uni-app 帮你封装了什么、封装的代价是什么。** 反过来先学 uni-app，你会在遇到框架覆盖不到的能力时完全无从下手。
- 第 6 章概览不依赖前文，可随时读；第 7、8 章在你真正开始写阶段项目时按需精读。

**当前进度**：九章正文全部上线——第 1 章[要不要做移动端、做哪种](/mobile/choosing-route)、第 2 章[移动端 Web 适配](/mobile/mobile-web)、第 3 章[微信小程序：心智对照（一）](/mobile/miniprogram-model)、第 4 章[微信小程序：心智对照（二）](/mobile/miniprogram-api)、第 5 章 [uni-app](/mobile/uni-app)、第 6 章[跨端方案概览](/mobile/cross-platform)、第 7 章[真机调试](/mobile/device-debugging)、第 8 章[发布流程](/mobile/release)、第 9 章[阶段项目：一个真实上线的小程序](/mobile/project)。**小程序这条线已经闭合**：第 3、4 两章合起来是从架构心智到登录、网络、分包的完整开发闭环，第 5 章把它接到「一套 Vue 代码出多端」，第 6 章给的是跨端方案的地图与「要不要做 App」的评估线，第 7、8 章补上最后一公里——让代码从「写在编辑器里」变成「跑得在手机上、过得去审核」，第 9 章再把前八章组织成一份有里程碑和验收清单的交付。

一件要说清楚的事：本领域是全站**真实环境依赖最重**的领域，第 7、8、9 章里有相当一部分动作在小册子里做不了——它们需要一部真机、一个已注册的小程序账号、一次平台审核或一台部署了后端的服务器。这三章的处理方式是：**能讲清机制、能在本机准备的部分写透；必须由你本人在真实设备上做的部分逐条标注为「真实环境目标」，不假装做过。**所以读第 9 章时请带着一个账号和一部手机，那才是它的执行现场。

## 学习方法

**环境准备（Windows）**：

- **移动端 Web 适配**：零新增环境。Chrome/Edge 开发者工具的设备模拟（Device Mode）是第一调试现场；但注意模拟器不能替代真机——安全区、软键盘、触摸行为都要用自己的手机验证。用自己的 Web 项目开一个分支做适配练习，改完对比截图。
- **微信小程序**：注册一个**个人主体**的小程序账号（免费，能力上比企业主体受限，但学习足够），安装微信开发者工具（Windows 版）。个人主体账号能做什么、不能做什么（如部分类目、支付能力），第 8 章会展开——这些限制本身就是平台认知的一部分。
- **uni-app**：两条路线——用 HBuilderX（DCloud 官方 IDE，开箱即用）或 CLI 方式集成进你现有的 Vite 工程（更接近本站的工程习惯）。Windows 下两者都完整可用。建议先用 CLI + Vue 3 + TypeScript 模板起项目，与你已有的前端工程化经验无缝衔接。
- **真机调试**：需要一部 Android 或 iOS 手机 + 数据线或同网段 Wi-Fi。微信开发者工具的「预览」生成二维码，手机微信扫码即可跑真机，这是小程序开发相比原生 App 最省事的一环。

**练习原则**：每一个「和 Web 不一样」的点，都先在 Web 里按直觉写一遍，再按小程序的规则改一遍，把两次的差异记录下来。这些差异记录就是你的私有对照手册，比任何教程都贴合你的知识背景。

## 阶段项目

**一个真实上线的小程序**。从你已有的产品（第一期的那个）里挑一个适合「用完即走」场景的功能做成小程序，或者做一个新的小工具。完整的实施说明在[第 9 章 阶段项目：一个真实上线的小程序](/mobile/project)——那里给出七个阶段的顺序与里程碑、两份必建目录的结构、接口契约与分包说明的模板、八行真机验证矩阵、提审前后的记录表，以及「哪些能在本机准备、哪些必须你本人在真实环境里做」的分类。验收标准：

- [ ] 技术路线（原生小程序或 uni-app）有书面选型理由，引用第 1 章的对比维度
- [ ] 对接你自己的后端 API：域名已备案并配置进小程序的 request 合法域名（这是国内小程序的硬性要求，提前规划）
- [ ] 登录流程完整：小程序登录 code → 你的后端换取用户标识 → 下发自己的会话凭证，密钥与 appsecret 只存在于服务端
- [ ] 至少两处使用组件化拆分；页面数量达到需要分包的规模，或书面说明为什么不需要
- [ ] 通过微信审核并正式发布，能被搜索或扫码访问（提审被拒也算有效经历：记录被拒原因与修改过程）
- [ ] 在至少两部不同尺寸的真机（含一部 iPhone）上验证过安全区与软键盘场景
- [ ] 如果走 uni-app 路线：同一套代码的 H5 端也部署上线，并记录两端表现不一致的地方及处理方式

## 版本说明

本领域的时效性风险呈明显的两层分布，处理方式不同：

- **Web 标准层（第 2 章）**：viewport、`env()`、触摸事件都是稳定的 Web 标准，时效性风险低。但**浏览器支持度**在演进（如 `100vh` 的替代单位、键盘弹出相关的视口特性），涉及支持度时以 MDN 对应页面的兼容性表为准。
- **平台层（第 3–8 章）**：微信小程序的基础库版本、API 集合、审核政策由平台方持续更新，本站内容以 **2026 年 10 月**的官方文档为准，涉及「某能力是否可用、某类目是否需要资质」的结论，动手前必须重新核对官方文档——这类信息的半衰期可能只有几个月。
- **uni-app**：基于其 Vue 3 版本编写（与 Vue 2 版本在 API 与工程结构上有差异，注意文档页面上的版本切换）。具体版本号以官方文档最新稳定版为准。
- **React Native / Flutter**：仅做定位级概览，不涉及具体版本与 API，因此不受版本变化影响；这也正是「概览不深入」的另一个好处。
