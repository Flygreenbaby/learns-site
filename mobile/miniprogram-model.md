# 小程序所有「不像 Web」的地方，都来自逻辑层碰不到 DOM

第一个现场：**改了数据，界面不动。**一个有 Vue 经验的人写小程序，习惯性地写 `this.data.list[0].count++`，代码跑完没有任何报错，页面上的数字停在原地。他把同一行改成 `this.setData({ ... })` 之后立刻生效，于是得出一个结论：「小程序必须手动刷新」。这个结论是错的，而且错得可惜——真正的原因在下面第二现场里。

第二个现场：**想操作 DOM，报的不是「找不到方法」。**在页面逻辑里写 `document.querySelector('.card')`，拿到的是运行时错误而不是编译错误，因为逻辑层根本不运行在浏览器中——官方文档对这一层的定义里直接写明 `window`、`document` 等不可用。也就是说：小程序不是「DOM 很慢」，是**你写业务逻辑的那个环境里根本没有 DOM 这个东西**。

第三个现场：**模板里的事件写法差一个符号就不灵。**Vue 里可以写 `@click="add(item, 2)"`，小程序里事件绑定只能给出一个方法名，参数得靠 `data-*` 传过去。很多人第一反应是「这不方便」，但这个「不方便」和第二个现场是同一件事的两个面：**模板和逻辑不在一个执行环境里，所以模板里不能塞可执行的表达式。**

这三件事加起来就是本章的主线：**小程序是「两层分离」的架构——逻辑层与视图层各跑在自己的执行环境里，中间靠一条消息通道传数据**。理解这一条，你在 Vue 里养成的直觉哪些该保留、哪些必须改，就不是背出来的，而是推出来的。这一章只做「心智对照（一）」：架构、模板、样式、数据更新四件事；生命周期、路由、网络请求、登录与分包在下一站。

<Callout type="verified">

**本章核实到的官方事实（2026 年 10 月，逐页抓取对照）**：

- 逻辑层（App Service）：使用 JavaScript 引擎，**并非运行在浏览器中，因此 `window`、`document` 等不可用**；`setData` 的作用是**将数据发送给视图层**；框架提供 `App`、`Page` 等注册函数。
- 注册页面（Page）：数据更新要调用 `this.setData`，**直接修改 `this.data` 不会触发视图更新**。
- WXML：是视图层使用的模板语言，指令包含 `wx:for`、`wx:if`、`wx:elif`、`wx:else`。
- 事件：`bind` 系列沿冒泡传递、`catch` 系列会阻止冒泡；事件名是平台给定的集合（`tap`、`longpress`、`touchstart`、`touchmove`、`touchend`、`touchcancel` 等）；事件对象上有 `currentTarget` 与 `target`；可以通过 `data-*` 携带数据。
- WXSS：`rpx` 以**页面总宽度的 1/750** 为基准，官方给出的例子是屏幕宽度 375px 时 `1rpx` 相当于 `0.5px`（同屏 `1vw` 等于 `3.75px`）；支持 `px`、`vw`、`vh`、`%` 等单位；`app.wxss` 是全局样式，`@import` 可导入其它文件；**属性选择器不生效，不支持带参数的伪类与伪元素选择器**。
- 性能页「合理使用 setData」：合理拆分组件以避免过大的 Shadow tree、控制更新频率、减少高频更新的开销、`data` 中只放与渲染相关的数据（官方用「纯数据字段」这一概念表达）、`setData` 只传递发生变化的数据、以及控制后台页面的数据更新。

**本章未逐项核对、动手前请自己查的部分**：`setData` 参考页里路径式键名（形如 `list[0].count`）的完整规则与合并语义、`wx:key` 的差异算法细节、组件样式隔离的具体选项、基础库版本对某个能力的支持起点、以及任何真机表现。**「双线程」是本站用来讲清后果的说法**——官方文档的表述是逻辑层与视图层分离、数据经 `setData` 发送到视图层，本章按这一表述推理，不去断言线程数的具体实现。

## 两层分离是本章节所有规则的共同原因

把官方那两句定义画成图，剩下的事情都能推出来：

```text
      ┌───────────────┐   setData(数据)   ┌────────────────┐
      │   逻辑层       │ ────────────────> │    视图层        │
      │ JavaScript 引擎│                   │ WXML + WXSS     │
      │ 无 window /   │ <──────────────── │ 渲染成界面       │
      │ 无 document   │   事件(名字+参数)   │ 跑在 WebView 里   │
      └───────────────┘                   └────────────────┘
              ▲                                     ▲
              └────────── 平台（原生层）负责转发 ──────┘
```

四个推论，每一个都对应一类 Vue 经验的失效：

**推论一：数据要「过桥」，所以更新是一次提交。**`setData` 的官方定义就是「将数据发送给视图层」。既然是发送，就有序列化与传输成本，也有异步——这和 Vue 里「改一个响应式属性、同一个同步流程里 patch 完 DOM」完全不是一回事。**成本模型变了，写法就该变。**

**推论二：逻辑层没有 DOM，所以模板里不能有可执行表达式。**`@click="add(item, 2)"` 这种写法的本质是「在模板里放一段要执行的 JS」。小程序的模板由视图层解释，逻辑层碰不到视图，于是它只能接受「方法名 + `data-*` 参数」这种数据形态的绑定。**平台的限制不是任性，是架构的一致性。**

**推论三：样式与标签由平台解释，所以能力有边界。**`view`、`text`、`image`、`scroll-view` 不是 HTML 标签，WXSS 是 CSS 家族但不是浏览器 CSS——属性选择器不生效、带参数的伪类伪元素不支持，这些限制都来自「有人替你解释这套样式，而不是浏览器的样式引擎全量接管」。

**推论四：界面在 WebView 里，所以「界面卡顿」有两种完全不同的原因。**一种是逻辑层的 JS 跑太久（计算、递归、同步大循环），一种是数据桥传得太多（一次 `setData` 塞进大对象、长列表整块重发）。前者要优化算法，后者要优化数据量——**分不清这两种，就会用错药。** 这一区分与[渲染性能：为什么改一个值会重画整页](/vue/rendering-performance)里「更新成本由什么决定」的思路一致，只是这里多了一层跨环境传输。

对照你熟悉的那套：Vue 3 里模板编译成渲染函数，运行在同一个 JS 环境里，响应式系统自动追踪依赖、批量更新、patch 真实 DOM（机制见[响应式系统](/vue/reactivity)与[模板语法](/vue/template-syntax)）。小程序把这两半拆成了两个环境。**所以「小程序像 Vue 但又不像」的准确说法是：它的模板层像，它的更新机制是另一套。**

## WXML 与 Vue 模板逐项对照：哪些一样，哪些形似神不同

| 要做的事 | Vue 3 模板 | WXML | 判定 |
| --- | --- | --- | --- |
| 文本插值 | 双大括号包住字段名（Mustache 插值） | 同样用双大括号包住字段名（真实写法见下文事件一节的示例代码） | 形似神不同：WXML 里是纯字符串替换，不能写复杂表达式 |
| 属性绑定 | `:src="url"`，值是 JS 表达式 | 属性值里用双大括号包住 `url` | 方向相反：Vue 是「绑定一个 JS 值」，WXML 是「在字符串里插值」 |
| 条件渲染 | `v-if` / `v-else-if` / `v-else` | `wx:if` / `wx:elif` / `wx:else` | 基本一样（指令名不同） |
| 列表渲染 | `v-for="(x, i) in list"` | `wx:for` 的值写成双大括号包住的 `list`，默认变量名 `item` / `index` | 形似神不同：数据源是插值，变量名靠属性改 |
| 复用提示 | `:key` | `wx:key` | 一样要有，算法细节以官方文档为准 |
| 事件 | `@click="handler"`、可带参数与修饰符 | `bind:tap="handler"` / `catch:tap="handler"`，参数走 `data-*` | **不一样**：只有平台事件名 + 方法名 |
| 双向绑定 | `v-model` | 无对应语法糖，手动 `bindinput` + `setData` | **没有**：得自己接 |
| 计算属性 | `computed` | 无同名机制，在逻辑层算好再 `setData` | **没有**：把「派生值」当成本要传输的数据 |
| 插槽 | `<slot>` / `#name` | 组件有 `slot` 与备用槽，写法不同 | 形似，能力边界不同 |
| 引用子组件实例 | `ref` | `selectComponent` / `createSelectorQuery` 一类查询接口 | 不一样：走查询，不是直接拿实例 |
| class / style 条件 | 数组、对象语法 | 字符串拼接或三元写在插值里 | 形似，表达能力更窄 |
| 局部逻辑 | `<script setup>` 任意 JS | 有独立的 `wxs` 脚本语言（不能在逻辑层执行） | **不一样**：为「视图层要一点逻辑」另设了一门小语言 |

三行判读方式：**「一样」的可以直接类比；「形似神不同」的要重写一遍才知道差异在哪；「没有」的那几项，是你在小程序里必须多做一次 `setData` 的地方**——它们每一个在 Vue 里都靠「自动追踪 + 同环境」省掉了成本，而这两个前提在这里都不成立。

顺带一条对「模板像」的警告：**看着像会让你误以为可以复制粘贴。**从 Vue 项目往小程序搬代码时，最先炸的是表达式（双大括号里的深层取值、方法调用、三元），其次是事件参数，最后才是样式。搬之前先按上表定位这几类改写点，比搬完再逐个报错快。

## 事件绑定只有三条硬规则，但三条都反 Vue 直觉

```html
<!-- WXML：方法名 + data-* 传参；catch 阻止冒泡，bind 允许冒泡 -->
<view class="row" data-id="{{item.id}}" bind:tap="onOpen" catch:touchstart="onHold">
  <text>{{item.title}}</text>
</view>
```

```js
// 逻辑层：参数从事件对象里取，不是从函数签名里取
Page({
  onOpen(e) {
    const id = e.currentTarget.dataset.id; // data-id → dataset.id
    // 想拿到「被点的是哪一行」靠的是 dataset，不是靠闭包捕获 item
  },
});
```

```vue
<!-- 同一件事在 Vue 里的写法：闭包直接把 item 交给函数 -->
<div class="row" @click="onOpen(item)">
  <span>{{ item.title }}</span>
</div>
```

**规则一：`bind` 与 `catch` 的差别是冒泡。**官方明确 `catch` 会阻止事件继续向上冒泡。列表项里嵌套按钮（一行既有「点开」又有「删除」）用 `bind` 就会两个处理函数都跑，这是「点删除结果整行跳转」的标准成因。

**规则二：事件名是平台给定的集合。**`tap`、`longpress`、`touchstart/move/end/cancel` 这些是文档里的枚举，不是你随便命名的自定义事件。Vue 里 `emits` 一套自定义事件名然后 `@my-event` 接住的作法，在 WXML 上没有对应——组件间通信要走别的路（父组件给子组件传属性、子组件通过 `triggerEvent` 触发**组件级**事件；具体 API 形态以官方组件文档为准）。

**规则三：参数只能靠 `data-*`（或先拿 index 再从数据里查）。**这是「模板里没有可执行表达式」的直接后果，也是「`e.currentTarget` 与 `e.target` 必须分清」的原因：`currentTarget` 是绑定处理函数的那个节点，`target` 是触发事件的原始节点——**你挂在行上的 `data-id`，只在 `currentTarget.dataset` 里。** 这与[DOM 与事件](/javascript/dom-and-events)里讲的 `currentTarget` 语义完全一致，只是这里没有 DOM 可以走。

触摸相关的事件名与浏览器里那套同名事件的差异，正好是[第二章](/mobile/mobile-web)那条「Touch Events 不是 Baseline、官方推荐 Pointer Events」的镜像：**Web 上你在往 Pointer 收敛，小程序上你只能用平台枚举的这套触摸事件。**两边不能互推。

## WXSS 是 CSS 家族，但三处差异会咬人

**单位：`rpx` 是把设计稿宽度当成 750 的自动缩放。**官方定义 `rpx` 表达页面总宽度的 1/750，给出的换算例子是：屏幕宽度 375px 时 `1rpx = 0.5px`（同一屏上 `1vw = 3.75px`）。

```text
750rpx ≡ 页面总宽度（100%）
屏幕宽 375px：  1rpx = 0.5px    1vw = 3.75px
屏幕宽 414px：  1rpx ≈ 0.552px  1vw = 4.14px
换算式：       1rpx = 屏幕宽度 / 750
```

用法上的三条判断：**按 750 设计稿标尺寸时用 `rpx`，字体的可读下限和边框粗细用 `px`**（一根 1 物理点宽的线不该随屏幕变粗），需要跟随视口的区域用 `vw`/`vh`（官方支持）。这一节和 [CSS 单位与自定义属性](/css/units-and-custom-properties) 是同一个话题的两个实现：Web 侧那套「视口单位 + 回退」的思路在这里依然成立，只是基准被平台固定成了 750。

**作用域：`app.wxss` 是全局的，页面样式在局部，`@import` 可以把公共样式表拖进来。**这和 Vue 项目里「全局样式表 + 组件 `scoped`」的组合不一样：小程序没有 `scoped` 这个属性给你用，选择器冲突要靠命名约定与组件样式隔离（隔离选项的具体取值本批未核对，以官方组件文档为准）。**换句话说，你在 Vue 里靠机制保证的东西，在这里要靠纪律**——这一点与[代码规范](/devops/code-standards)里「能被机制保证的事才不用检查」的判断刚好相反方向，值得注意。

**选择器：属性选择器不生效，带参数的伪类与伪元素不支持。**这意味着一批 CSS 常用写法直接失效，比如 `[type="text"]`、`li:nth-child(2n)`、`::before` 里带 `attr()` 的组合。可行的替代是：**把「谁该被选中」变成数据的一部分**——在逻辑层算好 class 名再 `setData` 传下去，而不是在样式里写复杂选择器。这个替代方案看着绕，其实和「两层分离」是一致的：**能表达判断的地方是数据，不是选择器。**

## `setData` 是提交，不是赋值

这一节是全章最实用的一段。先看两个环境的同一段意图：

```js
// Vue 3：自动追踪，派生值不用你管
const state = reactive({ list: [{ count: 1 }], total: 0 });
function add() {
  state.list[0].count += 1;   // 改完之后，视图会更新
  state.total = state.list[0].count; // 依赖它的组件被标记后重渲染
}
```

```js
// 小程序：显式提交，改哪个键就发哪个键
Page({
  data: { list: [{ count: 1 }], total: 0 },
  add() {
    const next = this.data.list.map((x, i) => (i === 0 ? { ...x, count: x.count + 1 } : x));
    this.setData({ list: next, total: next[0].count }); // 不发就不会更新
  },
});
```

差异不在「要不要写一行」，而在**谁负责知道什么变了**。Vue 是自动追踪依赖：你只管改，系统算出要重渲染谁（见[响应式系统](/vue/reactivity)）。小程序是你自己声明变化，`setData` 既是「更新 `this.data`」也是「把这些字段发给视图层」。**这就是第一现场那个 bug 的正确解释**：直接改 `this.data` 不是「绕过了响应式」，而是**你根本没走那条桥**，视图层没收到任何消息，所以它保持原样。

于是有三条推论：

**推论一：`setData` 之后立刻读 `this.data` 不能当成「渲染完成」。**它是跨环境提交，视图更新在另一侧发生。需要「数据已提交」的时机时用它的回调参数（参考页细节本批未逐项核对，以官方 `setData` 文档为准），需要「界面已完成」的时机时更要谨慎。

**推论二：路径式更新的存在，是为了让你少发数据。**官方性能页那条「只传发生变化的字段而不是全部数据」，实践中对应的就是**只把变化的那一条传过去**，而不是把整个列表重新构造一遍再发。上面那个 `map` 出来的整表替换是**可以用但应该少用**的写法：一屏十条无所谓，一屏两百条就贵了。

**推论三：「派生值」要显式算。**`computed` 那套自动重算在这里没有，你在逻辑层算好、当成普通数据发过去。于是同一份逻辑，你可能要在 `onLoad`（首次）和每次数据变化处都调一次——**这时候 Vue 的 `computed` 思路会转成一个小函数而不是一个响应式属性**。

## `setData` 的性能账：官方那五条各自在防什么

官方性能页给了可执行的几条建议，本站把它们翻译成「防的是哪个事故」：

| 官方建议 | 防的事故 | 在 Vue 里为什么不用管 |
| --- | --- | --- |
| 控制更新频率、合并调用 | 一次输入框 `bindinput` 里连发七八个 `setData`，界面跟着抖 | 批量更新由调度器做，同帧内的多次修改合并成一次 patch |
| 只传发生变化的字段 | 每次刷新整个列表，数据量随列表长度线性增长 | 依赖追踪天然只更新用到的部分 |
| 避免在滚动、动画的处理函数里高频 `setData` | `onPageScroll` 里更新一个「回到顶部」按钮的显示状态，整页跟着掉帧 | 这类状态通常交给 CSS 或独立的轻量组件 |
| 保持 Shadow tree 规模小 | 单页套太多层组件，节点规模膨胀，更新与首次渲染都变慢 | 组件树也影响 patch 成本，但没有跨环境传输这一层 |
| 不参与渲染的信息别放进 `data`（官方称纯数据字段） | 把原始接口响应、大数组、临时缓存塞进 `data`，每次 `setData` 都可能带着它们过桥 | 这类东西天然放在普通变量或 store 里，不会成为渲染依赖 |

最后一条最容易犯错，也最值得单独写。**`data` 不是「组件状态」的同义词，它是「要发给视图层的东西」。**一段只用于计算中间结果的数组、一份原始 JSON 响应、一个防抖定时器 id，都不该进去。它们在 Web 项目里天然写在别处（`ref` 之外的局部变量、Pinia store、模块作用域），在小程序里被顺手写进 `data` 是常见现象，后果是每一次提交都背着它们走一遍桥。

反过来也要防矫枉过正：**「少用 `setData`」不等于「攒到最后一次性发全部数据」**。前者是合并同一批变化，后者是把整棵状态树重发——判据是发送的字段集合，而不是调用次数。**次数少但每次都大，仍然贵。**

还有一类结构性问题：**长列表。**一次 `setData` 传两百条的代价显然高于传一条。官方性能建议里「保持 Shadow tree 小」指向的就是这一类：分页加载、只渲染可视区域、把不可见的部分收起。具体到本产品的取舍（滚动加载还是虚拟化、缓存多少页）属于经验判断，本站不给统一答案；但有一件事是确定的：**如果你发现自己在滚动里补数据，那就先量一下每次发送的字节数**，这个数是你唯一能拿来算账的东西。

## 常见错误与排查

**一、改了 `this.data` 界面不动。**现象：赋值完没有任何反应，也不报错。原因：没走 `setData`，视图层没收到消息。怎么确认：改成 `setData` 一次，看是否立刻生效。怎么修：所有需要反映到界面上的变化都通过 `setData`；只在逻辑里用的数据放成局部变量或纯数据字段。

**二、点一次按钮跳了两次，或者列表项里的删除触发了整行点开。**现象：父子两层的处理函数都执行。原因：用了 `bind` 而事件会冒泡。怎么确认：在内层处理函数里打印 `e.currentTarget.dataset` 看是谁接的。怎么修：内层改成 `catch:` 前缀，或者把外层判断改成「点击目标是不是子节点」。

**三、`e.target` 上取不到 `data-id`。**现象：`dataset` 是空的。原因：`data-id` 挂在绑定处理函数的节点上，而 `target` 是实际被触发的原始节点。怎么确认：同时打印 `e.currentTarget` 与 `e.target` 的 id 和 dataset。怎么修：用 `currentTarget.dataset`，或者把 `data-*` 挂到真正被点击的那层。

**四、把接口的原始响应整个塞进 `data`。**现象：列表不长但页面卡，`setData` 调用次数很少。原因：桥上传的是整个响应对象而不是界面用到的字段。怎么确认：在提交前打印这一次要发送的字段名与数组长度。怎么修：先在逻辑层裁剪成视图需要的形状再发，原始响应放成不参与渲染的数据。

**五、`input` 输入时页面抖、光标跳。**现象：一边输入一边 `setData` 回显，输入框内容会闪或光标跑到末尾。原因：高频提交 + 把输入值当受控状态反复回写。怎么确认：只在 `blur`（或防抖后）提交一次，看是否还抖。怎么修：让输入框自己持有输入值，只在需要派生显示或提交时才回写。

**六、样式不生效，选择器写了没反应。**现象：CSS 写在页面里，元素却不受影响。原因：用了不生效的属性选择器或带参数的伪类/伪元素。怎么确认：把选择器换成最简单的类名，看是否命中。怎么修：改成 class；需要「按数据判断该谁变色」时，在逻辑层算出 class 名再发下去。

**七、想在逻辑层里拿节点信息，`document` 报错。**现象：运行时报找不到 `document`/`window`。原因：逻辑层不是浏览器环境（官方明确这两个不可用）。怎么确认：看错误发生的位置是否在逻辑层代码里。怎么修：改用平台提供的查询接口拿布局信息，或干脆把布局交给样式而不是拿尺寸回算——后者通常才是正解，也符合[第二章](/mobile/mobile-web)「让布局自己适配」的取向。

**八、模板里写方法调用或深层表达式，界面上什么都不显示。**现象：插值位置空白，控制台不一定报错。原因：WXML 插值的表达能力有限，不是 JS 表达式求值。怎么确认：把它换成一个已经 `setData` 进去的简单字段。怎么修：所有需要判断、拼接、格式化的结果在逻辑层算好；实在需要在视图层做的少量逻辑用 `wxs`（它是独立的小语言，不是 JS 的一部分）。

<Exercise title="把一段 Vue 组件按对照表改写成小程序页面并记录三处必须换机制的地方" difficulty="基础">

找一个你写过的 Vue 3 组件（含列表、一个点击事件、一个由列表算出的合计）。按本章对照表把它写成小程序的 WXML + JS：要求事件参数通过 `data-*` 传、合计在逻辑层算好后随数据一起提交。答案里列出三处「不是换语法，而是换机制」的地方，各写一句为什么。

<template #answer>

三处通常是这样：**双向绑定消失**（`v-model` 变成「读值 + 手动 `setData`」，因为视图与数据不在同一环境，没有编译器替你接那条线）；**`computed` 消失**（合计必须由你在每次列表变化时显式算一次并随数据发出，因为没人追踪依赖，派生值就是一次普通传输）；**事件参数从闭包变成 `data-*`**（模板里不放可执行表达式，所以参数只能作为节点上的数据存在，由事件对象的 `currentTarget.dataset` 带回）。

剩下的差异（`:src` 与插值、`v-for` 的默认变量名、`:key` 与 `wx:key`）属于语法层，照着表改完就能跑。判断自己有没有真懂，就看能不能把这三处讲成同一个原因：**两层分离，数据要过桥。**

</template>

</Exercise>

<Exercise title="故意制造一次「改了数据但界面不动」，并把两种病因分开" difficulty="进阶">

在同一个页面上制造两个「界面不更新」：第一个只写 `this.data.count = 1`；第二个用 `setData` 提交，但提交的字段名写错了一个字母（比如模板里读 `count`，你发的是 `cont`）。写出两个现场各自的表现、你用什么动作把两者区分开、以及第二个错误的排查套路在真实项目里怎么固化成习惯。

<template #answer>

表现相同（界面不动），病因完全不同：第一个是**没提交**，数据也没真的进入提交队列；第二个是**提交了视图不认识的东西**，`this.data` 里多了一个没人读的键，模板读的那个键从未变化。

区分动作只有一条：把这一次 `setData` 的键名集合打印出来，和模板里用到的字段名对一遍。第一个现场打印出来是「确实调了 `setData` 但键名对了却没生效？」——不会，它压根没调用；第二个现场一眼能看出多了一个拼错的键。

固化成习惯的做法有三种，成本递增：写完页面后把模板里所有插值键名抄成一张清单，和 `data` 的初始键对齐（`data` 里该有的键一个都不能少，这正是首次渲染就要求初始值存在的原因）；给页面加一个开发期检查，比对「提交过的键集合」与「模板用到的键集合」的差集；把字段名集中成常量或类型定义，让拼错在编译期暴露（TypeScript 写小程序时可用，代价是类型定义要与模板同步维护）。

这题真正的收获是那句判据：**「界面不更新」永远先问两件事——提交了吗？提交的键有人在读吗？**

</template>

</Exercise>

<Exercise title="给一次昂贵的大列表更新算账并给出两种更便宜的写法" difficulty="挑战">

某个页面把接口返回的 200 条记录整个放进 `data`，模板只用其中 3 个字段；每次用户筛选，代码都重新请求并把整个数组再一次 `setData` 提交。请按官方性能建议（只传变化字段、不参与渲染的信息别放进 `data`、保持 Shadow tree 小）算出这次提交的浪费在哪里，给出两种成本更低的写法，并说明各自要付出的新代价。

<template #answer>

浪费有两处叠在一起：**每次提交的数据量**（200 条的原始对象里 3 个字段之外都是白送，而且原始响应被放进 `data` 后每次提交都可能带它过桥）；**视图节点规模**（200 条一次全渲染，Shadow tree 直接膨胀，首次渲染与后续 diff 都变贵）。

写法一：先裁剪再提交。逻辑层把响应映射成 `{ id, title, time }` 的数组，原始响应放成不参与渲染的数据；筛选时**只提交发生变化的字段集合**，例如返回筛选后的 id 集合让模板判断，或直接提交新数组但确保元素是裁剪后的形状。代价：多一次映射计算，以及筛选逻辑要在逻辑层写清楚（以前可能被模板表达式顺手做了）。

写法二：分批/分页渲染。首屏只提交可视区域附近的数据量，滚动到底再追加。代价：要处理「加载中」「已经到底」、滚动位置保持、以及筛选后需要把已渲染部分重置——**代码复杂度从一次提交变成一套节奏**。

再加一条通用结论：先量，再优化。在这个页面里能量的最直接的数就是「这一次 `setData` 到底传了哪些键、各传了多长的数组」——没有这个数，上面两种写法都只是猜测。这条与[复杂度分析](/computer-science/complexity)里「先算清数据量再看算法」的顺序一致。

</template>

</Exercise>
