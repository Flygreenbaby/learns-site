# 阶段项目：一个真实上线的小程序——七个阶段、三份记录、一部 iPhone

这个项目的定义只有一句话：**把你已有的某个产品功能，做成一个能被别人扫码打开的微信小程序。** 不是「学会小程序语法」，不是「做一个 demo」，是**走完一次从选型到上线的完整链路，并留下可检查的证据**。

为什么终点定在「上线」而不是「写完」？因为这个领域的全部特殊性都在上线那一段：域名要登记、密钥不能进前端、审核看的是你实际提供的服务、回退需要别人的权限、真机和模拟器的结论不一样。这些事实你在第 3、4、7、8 章里读过，但**读过和走过之间的差别，只会在这七个阶段里显出来**——通常以一次被拒或一次「朋友说打不开」的形式。

三条来自前面章节的前提，先立在这里：

**一、路线二选一并写理由。**原生小程序或 uni-app（第 1 章的决策树 + 第 5 章的适合/不适合判据）。这不是作业要求，是因为**你写完三个月后一定会忘记当初为什么这么选**，而那次遗忘正是下次选型犯同样错误的原因。

**二、功能范围要小。**三页原则（本节下面有表）。这个领域的失败模式不是「做得太难」，是「做了六个页面然后卡在提审」。第 9 章唯一的杀手是范围。

**三、真实环境的部分不能靠阅读完成。**需要账号、需要备案好的域名、需要一部 iPhone——这三样都不是本机可以替代的。

<Callout type="unverified" title="本章没有账号、没有设备、没有部署">

**本章的写作边界**：0 个小程序账号、0 台真机、0 次上传与提审、0 次部署。所以下面所有阶段都写成「你要做什么、判据是什么、留什么证据」，**没有任何一步是本站替你完成的**。

凡涉及平台条款（类目、资质、审核规则、分批发布能力、备案要求）的地方，本章只指向官方当天页面并要求你把结论抄进带日期的记录；凡涉及具体接口名或参数而本批未逐项核实的，正文里已就地标注。**代码示例的作用是形状与契约，不是可直接粘贴运行的完整实现**——请把它们当成填空模板，而不是答案。

</Callout>

## 你要交付的三样东西

| 交付物 | 内容 | 怎么算交出来了 |
| --- | --- | --- |
| 可运行工程 | 小程序源码 + 你的后端源码（或对接说明） | 别人 clone 后按 README 能跑起来（哪怕需要自己的 AppID） |
| 上线凭证 | 线上版本的截图或访问方式（扫码/搜索）、版本号与发布备注 | 用户真的能打开；或一份完整的被拒与整改记录 |
| 记录包 | 选型说明、真机验证矩阵、提审自查与整改记录 | 三份都有日期、都有「怎么验的」那一列 |

**第三样最容易被省掉，也最值钱。**代码三个月后会被你重写，而「我在哪一类上被拒过两次」「哪台设备上底部按钮被挡住」这类记录，是你在这个领域里真正积累下来的东西——第 7 章那句「私人清单是最值钱的资产」说的就是它。

顺带把标准放宽一点，免得你卡在最后一步上不动：**提审被拒也算有效经历**（领域首页那条验收项就是这么写的），前提是你记录了被拒原文、你的拆解和改动。假经历是「我改好了，不知道为什么过的」；真经历是「我知道这一版承诺了什么」。

## 选题：三页原则与一张范围表

先填这张表，**再打开编辑器**。填不满左列就说明范围合适；如果右列写了很多，说明你在做两个产品。

| 必做（本版） | 延后到下一版 | 明确不做 |
| --- | --- | --- |
| 一个列表页（含空态、加载态、失败态） | 搜索与筛选 | 分享裂变类玩法（第 8 章那题的结论） |
| 一个详情页 | 收藏 / 历史记录 | 自建用户内容上传与存储 |
| 一个提交类动作（下单、打卡、报名、投稿任一） | 统计面板 | 支付（除非你的主体已确认具备能力） |
| 你自己的后端接口 × 2–4 个 | 分包优化 | 任何你无法说清类目的功能 |

三页原则的依据不是审美，是第 8 章那句：**这一版承诺的范围越小，被拒的原因越容易定位。**四个页面的项目被拒时你要猜是哪一页的问题；三个页面的项目你两分钟就知道。

**选题来源建议按顺序挑**：（a）你现有 Web 产品里「最适合用完即走」的那一个功能；（b）你自己在生活里真的会重复用的一个小工具；（c）不要从「我想练一下组件化」出发选功能——那会让范围决定失去外部约束。

## 阶段 1 · 契约先行：目录结构与后端接口

先定结构再写页面，因为小程序的页面配置是分布式的（每页一个 json），改路径的代价比 Web 高。两种路线的骨架都给你，按需取用：

```text
# 原生小程序路线
miniprogram/
  app.js  app.json  app.wxss
  pages/list/     {list.js, list.json, list.wxml, list.wxss}
  pages/detail/   {...}
  pages/submit/   {...}
  components/item-card/   {item-card.js, .json, .wxml, .wxss}
  utils/request.js        # 唯一的请求出口
  config/host.js          # 环境域名，不散落在页面里
project.config.json
server/                   # 你自己的后端
  routes/items.js  routes/orders.js  auth/
```

```text
# uni-app 路线（CLI + Vue 3 + Vite）
src/
  pages/list/list.vue  pages/detail/detail.vue  pages/submit/submit.vue
  components/ItemCard.vue
  utils/request.js       # 封装 uni.request，状态码在这一层判
  pages.json             # 路由与 tabBar，编译到各端
  manifest.json          # 各端配置
# 同一套代码同时出 H5 与微信小程序：第 5 章那张「两端不一致来源表」是你的测试清单来源
```

接口层是本项目唯一值得写完整的代码，因为**第 4 章那三类事故全部落在这一层**：状态码当成功、域名前提、身份凭证。

```js
// utils/request.js —— 全站唯一的请求出口
const HOST = 'https://api.your-domain.example';   // 必须已在后台登记，必须 https

export function request(path, { method = 'GET', data } = {}) {
  return new Promise((resolve, reject) => {
    wx.request({
      url: HOST + path,
      method,
      data,
      header: { authorization: 'Bearer ' + (wx.getStorageSync('token') || '') },
      timeout: 10000,
      success(res) {
        if (res.statusCode === 401) { reject(new Error('AUTH_EXPIRED')); return; }
        if (res.statusCode >= 200 && res.statusCode < 300) { resolve(res.data); return; }
        reject(Object.assign(new Error('HTTP_' + res.statusCode), { res }));
      },
      fail(err) { reject(Object.assign(new Error('NETWORK_OR_DOMAIN'), { err })); }
    });
  });
}
```

契约表要写成文件（`docs/api.md`），因为它同时是**你的服务端待办清单**和**提审说明里的演示路径来源**：

| 接口 | 方法 | 入参 | 返回 | 未登录 | 备注 |
| --- | --- | --- | --- | --- | --- |
| `/items` | GET | `page`, `size` | `{items, total}` | 401 | 列表页首屏 |
| `/items/:id` | GET | 路径参数 | `{item}` | 401 | 详情页 |
| `/submit` | POST | `{itemId, note}` | `{id}` | 401 | 幂等：同一条重复提交返回同一个 id |
| `/auth/login` | POST | `{code}` | `{token}` | — | 服务端换标识，`session_key` 不下发 |

三条契约纪律，都来自第 1 章「发布周期决定服务端欠多少债」：**字段只做加法**；**每个接口都要能回答「哪个版本在调」**（请求头带你的版本号）；**提交类接口必须幂等**，因为用户在网络差的时候会重复点。

## 阶段 2 · 登录链路：只做对一次，就别再改

按第 4 章那张时序图实现，四个动作的验收判据各不相同：

```text
1. 小程序端 wx.login 拿 code                     判据：每次登录拿到一串非空 code
2. 把 code POST 到你自己的 /auth/login            判据：抓包看请求体里只有 code
3. 服务端调 code2Session 换标识                     判据：服务端日志里有换取结果，
                                                  但响应里没有 openid / session_key
4. 服务端签发你自己的 token 并下发                 判据：token 有有效期，能在服务端吊销
```

**做减法的验证动作**（第 4 章练习 3 那条，这里是正式验收）：把项目里所有出现密钥的位置删干净、重新上传出包，在解压后的产物里全文搜那个字符串——**搜不到才算通过**。这一步比任何代码 review 都有效，因为它验的是产物，不是意图。

另外两条容易漏：（a）**登录不等于已授权用户信息**，界面不要假定昵称头像一定存在，空态要画；（b）**token 过期要有回路**——上面那个 `AUTH_EXPIRED` 分支要真的接到「重新走一次登录」的代码，而不是只打日志。这两项在提审时都会被以「无法使用」的形式抓住。

## 阶段 3 · 页面、组件与分包：先能跑，再谈漂亮

页面按第 4 章的生命周期纪律写：首次加载放 `onLoad`，跨页同步用脏标记或上一页回传，`onShow` 里不要全量重拉。这三句在本阶段会变成一条可观察的判据：**从详情页返回时，列表的滚动位置应该还在。**做不到就是你在 `onShow` 里重拉了。

组件化的验收是「至少两处」，而**选哪两处**决定了它是不是白做：

```text
判据一：某个 UI 块在两个页面出现，或者在一页里重复出现且结构一致 → 抽成组件
判据二：某块有独立的交互与状态（例如卡片里的收藏按钮）→ 适合做组件
反例：把整页包成一个组件，只为了「符合两处」→ 这是形式，不是复用
```

组件边界按第 4 章那两条通道设计：父→子走 `properties`，子→父走 `triggerEvent`；记得**在页面 json 里声明 `usingComponents`**（第 4 章那条「组件不显示，第一现场是 json 少两行」）。

分包的判据不是页面数。三页规模**通常不需要分包**，而领域首页那条验收项允许「书面说明为什么不需要」：

```text
# docs/subpackage.md
本页面的首屏下载量：____（用构建产物大小填，别估）
三页是否都在首屏路径上：是 / 否
结论：不分包，理由 ____
（若结论是分包）边界按用户路径划：入口条件是 ____
```

**注意这里要求的是数字来自构建产物，不是你的猜测**——这也是第 6 章那条「别拿别人的数字做自己的决定」在本章的落点。

## 阶段 4 · 真机验证矩阵：两部设备，含一部 iPhone

这一阶段是本项目里唯一**不可能由本机代替**的部分。矩阵照第 7 章那八类现场设计，每格都要有结论：

| 场景 | iPhone 结论 | 另一台安卓结论 | 判据（什么算通过） |
| --- | --- | --- | --- |
| 首屏加载 | ____ | ____ | 有加载态；弱网下不白屏 |
| 底部固定操作区 | ____ | ____ | 手指按最下缘能触发；截图有无可见留白 |
| 键盘弹出（提交页） | ____ | ____ | 输入时提交按钮仍可达；收起后布局复位 |
| 从详情页返回 | ____ | ____ | 滚动位置保持；不重复请求全部数据 |
| 未登录 / 会话过期 | ____ | ____ | 有引导；能自动重新登录 |
| 空数据 / 接口失败 | ____ | ____ | 三种状态各不相同，不出现「空但无提示」 |
| 长列表滚动 | ____ | ____ | 你能接受的流畅度，且写下判断依据 |
| 提交幂等 | ____ | ____ | 快速点五次，服务端只有一条记录 |

填这张表的三条注意：

**一、结论要写现象，不写「正常」。**「底部按钮下沿距屏幕底约一个按钮高，按最下缘可触发」是可复查的证据；「正常」不是。

**二、iPhone 是硬性项**，因为安全区与键盘行为在不同系统上的差别最明显（第 2 章与第 7 章各说过一次）。只有一台安卓时，**这一格应诚实写成「未验证」**，而不是省略——省略会让三个月后的你误以为验过。

**三、uni-app 路线要加一行**：同一套代码的 H5 端表现，以及两端不一致的地方与处理方式（第 5 章那张来源表按行抄成本项目专用清单）。这是领域首页那条验收项的要求，也是这条路线的真实代价所在。

## 阶段 5 · 提审与发布：把第 8 章的六组清单执行一遍

顺序固定下来，不要临场发明：

```text
1. 关掉「开发环境不校验请求域名」，在工具里走一遍全部主流程
2. 定版本号 → 上传（版本号先于上传，第 8 章那条）
3. 出体验版 → 真机跑阶段 4 的矩阵（改了代码就作废重来）
4. 逐条打勾第 8 章 A–F 六组清单，把打勾结果连同版本号存进 docs/release-log.md
5. 提审：功能说明、演示路径、测试账号写成一份文档，别现编
6. 通过 → 发布 → 立刻在真机上用线上版本再走一遍主流程
   被拒 → 抄原文 → 拆最小单元 → 最小代价处理 → 回第 3 步
```

第 6 步那句「发布后立刻在真机上用线上版本再走一遍」是本项目里最容易忽略、收益又最高的一步：**线上版本是你唯一无法用工具复现的产物**（第 7 章那句「三个不同的产物」在这里收口）。

同时把回退能力确认一遍：**谁有发布与回退权限、联系路径是什么、如果不可达，服务端开关在哪。**第 8 章那个事故题的 sixty-minutes 答案，只有在你自己项目里落过一次才会变成习惯。

## 阶段 6 · 上线后：一周的观察与一次演练

上线不是交付完成，是**另一种状态的开始**。四项：

**一、看三个数**（服务端日志要已有版本维度）：这一版的请求量、错误率、登录失败率。**没有版本维度，这三问一个都答不了**——那就先加维度，别急着改功能。

**二、收两类反馈**：打不开（多半是域名、成员或低版本能力）与看不见内容（多半是接口返回结构和你的假设不一致）。第 7 章那条 `list.probe` 日志在这里第一次产生回报。

**三、做一次五分钟演练**（不是真出事）：假设「导出/提交」这一类新功能在线上出问题，从发现到把它关掉要多久？如果答案是「要发版」或「要找管理者」，那这一项记为**待补**，下一版把开关加上。**演练的价值在于第一次不要是事故本身**（第 8 章练习 3 与备份那章同一条教训）。

**四、写一份 300 字收尾**：这一版最贵的一个决定、一次被拒或线上小事故、下次会改的一条流程。它同时是你第 1 章选型说明里「失效信号」那格的实测数据——**下一次选型时的判断力就是从这份东西里来的**，不是从教程里。

## 里程碑：七阶段与每阶段的完成判据

```text
阶段 0  选型说明 + 前置项清单         判据：docs/route-decision.md 每格有字，含日期
阶段 1  目录结构 + 接口契约文档       判据：契约表 4 列齐全；请求层有状态码判断分支
阶段 2  登录链路 + 减法验证           判据：产物里搜不到密钥；会话过期能自动重登
阶段 3  三页 + 两处组件 + 分包说明    判据：返回时列表滚动位置保持；subpackage.md 有数字
阶段 4  真机矩阵（两部设备）          判据：矩阵每格是现象描述，不是「正常」
阶段 5  自查打勾 + 体验版 + 提审      判据：A–F 六组打勾记录与版本号绑定
阶段 6  上线 + 一周观察 + 一次演练    判据：有版本维度的三个数；演练结论写成待补项
```

**阶段顺序不可打乱的两处**：阶段 0 必须先于任何代码（前置项周期长，第 8 章那个「第六周才发现」的失败模式就来自跳过它）；阶段 4 必须先于阶段 5（第 7 章那句「发布物与验证物对齐」——先提审再补真机验证，等于拿审核员当你的测试设备）。

## 不做什么：范围防线

本项目明确**不要求**以下内容，出现它们通常意味着范围在失控：

- 不做后台管理系统（第 8 章说得很清楚：多一个入口就多一份发布债）。
- 不做支付、不做优惠券、不做分享得奖励（主体、类目与规则风险都高于本项目需要的练习价值）。
- 不引入 UI 组件库来「省时间」——你现在的目标是把平台机制学会，组件库会把第 3、4 章那些约束重新包起来，正好抵消本项目的学习效果。
- 不做多语言、深色模式、动效打磨。它们不是没价值，是**在上线这件事之前不值得付代价**。
- 不追求分包、性能优化、埋点体系。阶段 3 允许你书面说明「不需要分包」。

这份「不做」清单是本项目的护栏。**它的价值不在省事，在于让「上线」这个终点真的可达**——一个只有三页的小程序能在两周内上线，一个有七个页面的小程序会在第四周还在改布局，而后者对学习的收益并不更高。

## 验收清单：逐条怎么留证据

领域首页那七条验收项，落到证据形态如下：

- [ ] **路线选型有书面理由**（证据：`route-decision.md`，含四条路线对照与「我承认的代价」那一格）
- [ ] **对接自己的后端，域名已备案并配置进合法域名**（证据：后台域名列表截图 + 关掉不校验选项后跑通主流程的记录）
- [ ] **登录流程完整，密钥只在服务端**（证据：一次减法验证的搜串结论 + 一次登录抓包的请求/响应字段清单）
- [ ] **至少两处组件化；分包或书面说明不需要**（证据：两个组件目录 + `subpackage.md` 里的构建产物数字）
- [ ] **通过审核并发布，可被搜索或扫码访问**（证据：线上版截图或扫码入口；被拒也算，附整改记录）
- [ ] **两部不同尺寸真机、含一部 iPhone，验过安全区与软键盘**（证据：阶段 4 那张矩阵，每格写现象）
- [ ] **uni-app 路线：H5 端也上线，并记录两端不一致处**（证据：H5 可访问地址 + 不一致清单及处理方式）

**每条都必须带日期。**带日期的记录在这个领域里格外重要，因为平台规则会变——三个月后回看，日期能告诉你「当时的结论在当时是对的」，而没有日期的结论只会让你怀疑自己。

## 常见翻车点

**一、跳过阶段 0，第六周才发现主体不支持支付。**这一条在第 8 章讲过，仍然排第一，因为它是最贵的。怎么防：把前置项清单放在唯一一份不许延后的文档里。

**二、六个页面 + 三个「顺手加的功能」。**现象：始终没到提审。怎么防：填那张三页范围表，右列写满就砍。

**三、验证矩阵全是「正常」。**现象：线上仍出遮挡。原因：结论没有可复查性。怎么防：每格写现象 + 截图编号。

**四、代码验完又改就直接提审。**现象：被拒的正是新改那两行。怎么防：改了就让体验版验证作废（第 8 章那条规矩）。

**五、把请求封装散在页面里。**现象：域名换了要改 12 个文件，状态码判断有的有有的没有。怎么防：全站唯一 `utils/request.js`（第 1 章「收拢到一个适配层」的落地形态）。

**六、提交接口不幂等。**现象：网络差时用户连点，数据库出三条记录。怎么防：阶段 1 契约表里就写上幂等要求，阶段 4 矩阵里点五次验证。

**七、没有版本维度，上线后无法判断「只有新版有问题」。**怎么防：请求头带版本号，日志里落一个版本字段——这是十分钟的事，出事时值四个小时。

**八、把「没被拒」当成「流程没问题」。**现象：一次过审就删掉整改记录的习惯。怎么防：阶段 6 那份 300 字收尾，无论过没过都写。

## 下一章

本领域到此结束：**移动端开发 9 章全部上线。**但请注意这句话的真实含义——上线的是文字，你的小程序还没有。本章七个阶段里只有阶段 0 到阶段 3 可以在你自己电脑前完成，阶段 4 到阶段 6 每一步都需要真实环境：设备、账号、备案好的域名、一次真实的提审。**没有做那些步骤，就不要把上面任何一条写成「已完成」。**

学完之后，按你的实际缺口往下走，这几条是最常见的接续路线：

- 后端接口撑不住、会话与幂等做得别扭 → [后端开发](/backend/)，尤其[会话与登录](/backend/auth-session)与[API 文档与契约](/backend/api-docs)。

- 域名、证书、备案这条链路是你的第一道阻塞 → [部署到 VPS](/devops/deploy-to-vps)与[服务器安全](/linux/server-security)。
- 小程序之外还想把 Web 侧体验做扎实 → 回到[移动端 Web 适配](/mobile/mobile-web)，它是本领域唯一一章不需要任何账号就能立刻改善你现有产品的。
- 界面与交互是你的短板而不是技术 → [CSS](/css/)与[HTML](/html/)，第 2 章的每一节都是它们在一个特定场景下的应用。

最后留一句本领域的判断方式，它比任何一条 API 都耐用：**遇到任何「和 Web 不一样」，先问是不是「数据要过桥」或「逻辑层碰不到视图」；遇到任何「本地能跑、线上不行」，先问平台侧的配置在哪一格；遇到任何「要不要做 App」，先问有没有一件事是 Web 与小程序都做不到的。**这三个问题问下来，你会发现这个领域的技术细节确实很多，但决策的形状始终是稳定的。
