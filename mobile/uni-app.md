# uni-app 省的是「再学一个平台」，欠的是「多一层归因」

第一个故事关于「只在 H5 上测过」。一个团队用 uni-app 做 Vue 3 项目，开发时全程跑 H5——热更新快、能在浏览器里调，效率高得很。临近提审才第一次编译到微信小程序，两天里冒出一串问题：某个用了很久的布局在小程序里错位，某个直接从浏览器 API 拿来的写法运行不了，某个「页面显示时刷新」的逻辑压根没触发过。这些都不是 uni-app 的 bug，是**「一套代码」被当成「一次验证」的代价**。H5 端跑通只证明了你自己的逻辑没错，没证明编译产物和平台解释也没错。

第二个故事关于「平台上新了，框架还没有」。平台每次更新能力（新组件、新接口、旧的交互规则调整），你手上就有三层日历要对齐：平台基础库版本、框架对这些能力的封装版本、你自己项目声明的最低兼容版本。中间任何一层没跟上，你就要决定是等、是绕、还是把这一端的功能延后。**「等框架支持」不是技术问题，是排期问题**，而它在选型那天是可预估的，在上线前是不可预估的。

第三个故事最不好听，但最常见：条件编译写多了，「一套代码」变成了话术。当你发现有十几个地方写着「这一段只在小程序端执行」「那一块只有 H5 要」，你手里的一套代码其实是两套分支的叠影——改一个需求要检查两端，测一个功能要跑两端，**而归因还要多问一层：是我的逻辑错、框架编译产物错，还是平台解释错。**[第一章](/mobile/choosing-route)那条「改一个需求要打开几个文件」的判据，在这里会以让你不舒服的方式生效。

这一章的目标不是劝你别用 uni-app。它给的是这套路线的真实账本：**它省掉的是「再学一个平台的语法」，欠下的是「多一层归因、多一层版本依赖、多一套验证矩阵」。** 会不会划算，取决于你的产品形态，而这一点恰好可以在选型前算清楚。

**本章的性质说明**：本批**没有安装 uni-app、没有创建 uni-app 项目、没有执行任何一次多端编译**。所以本章不给任何「实测通过」的结论。条件编译的语法、注释形式与平台标识来自官方文档页面（核实时间 2026-10-22），属于可核实事实；其余关于编译机制、两端差异来源、封装滞后的描述是基于官方文档表述加上[第 3、4 章](/mobile/miniprogram-model)的小程序机制做的推理，**属于「按通用原理」**。具体版本号、API 支持清单、某个能力在你项目里能否使用，一律以你动手当天的官方文档与你自己编译出来的产物为准。

## 「一套代码编译到多端」到底编译了什么

先把最常见的误解摆正：uni-app **不是**一个在运行时把 Vue 渲染成小程序界面的抽象层。它的重心在编译期——写 Vue 3 语法的源码，按目标平台产出各端自己的工程。可以按三层来看：

```text
你写的                编译期产物                     运行时
────────────────────────────────────────────────────────────
Vue SFC 模板    →   小程序端：WXML + WXSS + JS     →  平台的逻辑层/视图层
                  H5 端：直接走 Vue 渲染            →  浏览器 DOM
uni.* API      →   各端调用不同实现                 →  wx.request / fetch / plus.*
uni.scss / 尺寸 →   rpx、upx 等单位按平台换算         →  平台自己解释样式
pages.json     →   各端各自的路由与页面配置          →  app.json / 前端路由表
```

三层各有各的代价，这是本章后面所有讨论的来源：

**模板层**：Vue 模板语法和 WXML 是两套东西（差异的完整清单在[第 3 章](/mobile/miniprogram-model)那张对照表里）。编译器能翻译大部分，翻译不了的那部分就是你必须避开的写法。**推论：「框架支持的模板写法」不等于「Vue 支持的模板写法」**——凡是依赖可执行表达式、复杂 computed 直插模板的地方，都要怀疑它在小程序端会变成什么。

**API 层**：`uni.request` 在小程序端落到 `wx.request`，在 H5 端落到浏览器请求。API 名字统一了，**语义不统一**。最典型的是第 4 章那三条：域名白名单是平台侧的，H5 端没有；H5 端有 CORS，小程序端没有；本地存储在两端的容量与失效规则也不同。「同一行代码在两端做了不同的事」是这套路线的核心风险。

**配置层**：`pages.json` 被编译成各端的页面配置。这一层的价值很高（一份导航结构管两端），风险也最隐蔽——某个端的配置项框架没暴露出来，你会发现「文档说有这个能力，但我的工程里没地方写」。

一句话总结这套路线的技术本质：**它把「多端差异」从「写多套代码」搬到了「一层你不完全控制的编译器 + 一份条件编译的差异清单」。** 搬运本身是赚的，因为语法重复比归因重复更烦；但搬运不消灭差异，只是换了一个地方放。

## 条件编译：语法、正确用法、滥用边界

官方「条件编译」页面给出的语法是可核实的（核实时间 2026-10-22），照抄如下。

```js
// #ifdef  平台标识     仅当编译到该平台时保留下面这段
// #ifndef 平台标识     反向：编译到「不是该平台」时保留
// #endif              结束

// 平台标识常见值（不完整，动手前查当天文档的列表）：
// H5        网页端
// MP-WEIXIN 微信小程序
// APP-PLUS  App 端
// 其余各家小程序端、快应用等标识按官方列表为准
```

三种文件用的是三种注释符，这一点很容易写错而「条件编译不生效」：

| 出现位置 | 注释形式 | 写法示例 |
| --- | --- | --- |
| js / ts | `//` | `// #ifdef MP-WEIXIN` |
| css / scss | `/* */` | `/* #ifdef H5 */` |
| vue / nvue 模板 | `<!-- -->` | `<!-- #ifdef MP-WEIXIN -->` |

官方页面还说明它作用于 `.vue`、`.nvue`、`.js`、`.css` 等文件类型（`.uts` 也在新版列表里；具体文件类型清单以当天文档为准）。

**正确用法只有一种心态：条件编译是「差异承认书」，不是「调试手段」。** 你写下 `#ifdef` 的时候，本质上是在说「这一处的两端差别我不打算抹平」。所以每个 `#ifdef` 都应该能回答三个问题：差在哪一端、为什么框架没给你抹平、两端各自怎么验。

三类滥用信号，出现任意一条就要停下来重新评估：

**一、同一个功能块里出现三个以上分支。**这通常意味着你在用条件编译模仿一个缺失的抽象层。正确动作不是再加一个 `#ifdef`，是把这块逻辑收进一个「按端实现」的适配模块，让分支只出现在边界上——这和[软件架构](/computer-science/architecture)里「低可逆决策收窄对外表面」是同一条。

**二、`#ifdef` 里包的是业务判断而不是平台差异。**比如「小程序端不显示某个字段」——如果原因其实是「这个字段在没有登录链路时拿不到」，那就不是平台差异，是状态差异，写成条件编译会把 bug 藏进构建产物里（H5 端测不到，小程序端才复现）。**判据：删掉这个分支，两端体验会一样吗？如果本来就该一样，别用条件编译。**

**三、一端已经不再被认真验证。**最危险的形态是「主要维护小程序，H5 端只是编译得过」。这时你的「一套代码」在事实上只剩一套，另一端每次升级都要重新踩坑。这不是框架问题，是流程问题——而流程问题必须靠**双端都进你的发布清单**来解决，见[发布与回滚](/devops/release-and-rollback)里「发布物与验证物要对齐」的思路。

反过来，有一类场景**就该**用条件编译，硬抹平反而错：平台专有的能力（只在某个端存在的组件或接口）、两端的导航形态差异（tabBar 与前端路由）、以及登录链路。这些差异是真实存在的，承认它是工程上的诚实做法。

## 封装的滞后：新 API 什么时候能用

平台更新能力，中间隔着框架。这条链上有三层日历，**你必须分别回答「我的项目走到哪了」**：

```text
平台发布新能力
   └─ 基础库版本：用户微信客户端里实际跑的版本，你控制不了，只能声明最低要求
        └─ 框架封装版本：uni-app 有没有把这项能力暴露成 uni.* 接口
             └─ 你的项目：package.json 里装的框架版本 + 工程配置里声明的最低兼容版本
```

三层任何一层落后，现象都不一样，处理方式也不同：

| 落后的层 | 现象 | 能做的三件事 |
| --- | --- | --- |
| 平台基础库（用户侧） | 一部分用户身上「接口不存在」 | 提高最低版本要求（会拒绝一部分用户）、写可用性判断、延后这个功能 |
| 框架未封装 | `uni.xxx` 报错或文档里没有 | 条件编译里直接调平台原生接口、等框架版本、放弃这项能力 |
| 你的框架版本落后 | 官方文档有、你项目里没有 | 升级框架（**先读升级说明，这是外部依赖升级**，与[代码规范](/devops/code-standards)里「能被机制保证的事」无关，只能靠你自己回归） |

判断动作只有两条，且都在你这边：**读当天的官方文档，看这项能力标注的最低支持版本；读你自己的工程配置，看当前版本。** 本章刻意不写任何具体版本号——本批没有安装或运行任何东西，写死版本会立刻过时并误导你。

一个必须建立的预期：**走封装层，你就永远不可能同时是「平台最新能力的第一个使用者」。** 如果你的产品价值依赖「平台刚放出来的能力」（新的交互形态、新的分发入口、某项刚开放的接口），那这条路线会把你的上线时间绑在框架发版上。这是[第一章](/mobile/choosing-route)四笔账里「机会」那一笔的具体形态，也是**很多人选型时没算、出事时才承认的一项**。

## H5 端与小程序端不一致的常见来源

这张表按「你会在第几天撞到」排序，不是按严重程度。「怎么发现」那一列是本章的重点：**不一致的可怕不在它存在，在于你的开发环境只看得见一端。**

| 来源 | 不一致的表现 | 怎么在提审前发现 |
| --- | --- | --- |
| 生命周期语义 | 页面「显示时刷新」在 H5 端要走前端路由钩子，小程序端要走平台页面生命周期 | 两端各自列一张「进入页面/返回页面/切后台回来」的触发表，对比 |
| 路由与页面栈 | H5 有浏览器历史与前进；小程序是十层页面栈且方向受限 | 在小程序端走一遍最长链路，数 `getCurrentPages().length` |
| 网络前提 | H5 看 CORS；小程序看域名白名单（第 4 章的原文条款） | 关掉工具里的「不校验域名」选项测一次小程序 |
| DOM 与浏览器 API | `window`/`document` 在小程序端不可用 | 全局搜这些标识符；框架没替你拦 |
| 样式单位与解释 | 两端单位换算与选择器解释不同（小程序侧 WXSS 的限制见第 3 章） | 同一屏在两端截图对比，重点看边框粗细、字号下限、安全区 |
| 安全区 | 浏览器侧靠 `env()`，小程序侧由平台容器决定 | 必须真机（含一部 iPhone）看底部按钮和顶部标题 |
| 滚动行为 | 页面滚动、下拉刷新、触底事件的触发条件不同 | 各端跑一遍长列表：下拉、触底、快速回滚 |
| 登录与身份 | H5 用你自己的账号体系；小程序走 code 链路 | 画一张时序图，标出哪些环节只存在于一端 |
| 分享与转发 | 平台专有事件，H5 端只能落到 Web Share API 或提示用户 | 别在 H5 端假装实现「转发」 |
| 本地存储 | 容量、失效时机、清理入口都不同 | 把「缓存没有失效策略」这条按第 4 章的写法收掉 |
| 图标与字体 | 自定义字体的加载规则受平台限制 | 两端各看一次首屏文字是否闪换或变方框 |
| 包体积与分包 | 小程序有主包/分包上限，H5 没有 | 编译产物大小分别看，别只看 H5 的构建输出 |
| 原生导航栏与 tabBar | 小程序由平台绘制，H5 由你的组件绘制 | 两端各截一张含顶栏与底栏的图，对齐间距与遮挡 |

**这张表最重要的用法不是读，是变成你的双端测试清单。**「两端表现不一致的地方及处理方式」是[领域首页](/mobile/)那条阶段项目验收项的字面要求，而它只能靠两端各跑一遍得到——**编译得过的产物不等于验过的产物。**

## 什么项目适合，什么不适合

判据不给「好不好」，给「什么时候划算」。

**适合 uni-app 的四个信号：**

1. **你的两端功能重合度高。**同一套页面、同一套数据、同一套业务规则，只是外壳不同。重合度低于七成，条件编译就会吃掉省下的时间。
2. **你会真的同时发两端，并且都验证。**「顺手也发个 H5」不算，「H5 端在我方发布清单里」才算。
3. **你不依赖平台最新能力。**你要做的是常规形态（列表、详情、表单、支付之外的常规交互），这些能力封装层早就有。
4. **你团队已经有 Vue 3 经验，且不想同时维护两套 UI。**这条是「再学一个平台」的成本节省——第 3 章那张 WXML 对照表能帮你判断你的 Vue 直觉在这里还剩多少能用。

**不适合的四个信号：**

1. **只做小程序、永远不做第二端。**那就写原生小程序：少一层归因、少一层版本依赖、直接对着官方文档写。**这是本站对「单端项目」的默认答案。**
2. **产品价值压在平台刚开放的能力上。**你会被封装版本拖住，见上一节。
3. **你要的是「原生 App 的手感」。**uni-app 到 App 端仍是另一套渲染形态，和[第六章](/mobile/cross-platform)讲的 RN/Flutter 是两类问题；用错工具的表现是「性能与体验怎么调都差一口气」。
4. **你的项目里两端差异本来就很大。**比如 H5 是营销落地页、小程序是工具，共用代码极少——这时「一套代码」的收益接近于零，成本（编译器行为、条件编译）却全额付。

**把它接回四笔账**：uni-app 在「钱」上没有额外开销；在「时间」上省下学平台语法的初始成本，换来「多一层归因」的持续成本；在「风险」上引入外部依赖风险（框架升级、发版节奏），换掉「两个平台各写一遍」的重复工；在「机会」上让你更快覆盖第二个入口，但可能拖慢对平台新能力的第一时间响应。**划算与否的分界，是重合度和你是否真的双端验证——不是框架好不好。**

## 起步路线：两条，选一条

官方提供两种工作方式，本站的取舍口径如下（**本批未安装任何一项，以下不是实测比较，只是判据**）：

| 路线 | 什么时候选它 | 需要注意 |
| --- | --- | --- |
| HBuilderX（官方 IDE） | 想要开箱即用、图形化的项目创建与真机运行、少配环境 | 你的工程习惯会被 IDE 牵着走；与现有仓库工具链（格式化、CI）的对接要另外确认 |
| CLI（Vue 3 + Vite 工程） | 已有前端工程化经验、想在 CI 里出包、想把依赖装在 `package.json` 里管 | 多端编译命令与配置以官方文档为准；工具链版本升级属于外部依赖升级，要有回归计划 |

本站主线是 Vue 3 + Web，**默认建议先走 CLI 路线**——它和你已有的工程习惯同构，出问题时的可观察面更大（你能直接看构建产物）。等你需要在两端之间频繁切换调试、或者要用 IDE 自带的真机运行能力时，再决定要不要装 HBuilderX。

无论哪条路线，起步时先做三件验证（这三件事不需要任何平台账号）：

- [ ] 编译 H5，在浏览器里把主流程走完一次。
- [ ] 编译微信小程序，在开发者工具里把同一条主流程走完一次，**并记录两端表现差异**（就是上一节那张表的私人版）。
- [ ] 把同一份代码在两端各构建一次，比较构建输出：产物大小、有没有只在某一端出现的告警。

第三步是很多人跳过的，而它恰恰是最便宜的预警：**编译器在你还没上线时就把「两端不一样」告诉你了，不要等到审核**。

## 常见错误与排查

**一、把「H5 跑得通」当成「代码没问题」。**现象：小程序端出现莫名错位或接口不调用。原因：只验证了一端。怎么确认：同一动作在两端各录一次屏。怎么修：把双端都写进发布清单，缺一端就不算过。

**二、条件编译不生效。**现象：`#ifdef` 包着的代码在目标端仍然执行/仍然缺失。第一现场不是逻辑，是**注释符用错**——模板里用了 `//`，样式里用了 `<!-- -->`。怎么修：对照本章那张注释形式表；改完确认产物里那段是否被剔除（看编译输出，不看源码）。

**三、用了 Vue 直觉但模板编译不过去。**现象：小程序端某处显示为空、控制台说表达式错误。原因：模板里放了框架翻译不了的写法（第 3 章「模板里没有可执行表达式」那条在封装层依然成立）。怎么修：把表达式搬进 computed 或方法，模板里只留名字。

**四、`window`/`document` 或第三方依赖里用到它们。**现象：H5 正常，小程序运行时报未定义。原因：封装层不改变逻辑层不是浏览器这一事实。怎么修：换平台可用写法，或把这个依赖挪到 H5 分支并写清差异。**别指望框架替你屏蔽这条。**

**五、生命周期钩子写了没反应。**现象：页面返回时刷新逻辑不跑。原因：两端生命周期语义不同，Vue 的钩子不承担平台页面显示事件。怎么修：查当天文档对应端页面生命周期该用哪个，把逻辑放在正确那一层。

**六、请求在小程序端全失败，H5 端正常。**原因：域名白名单是平台侧的，跟框架无关。怎么确认：报错文案里有没有域名不合法；工具里是否勾了跳过校验。怎么修：登记域名（并回到第 4 章那三条检查）。这条与「框架问题」无关，**但因为是两端表现不同，很容易被误判成框架 bug**。

**七、官方文档说支持，我这里报错。**原因：三层日历里某一格落后（多半是你的框架版本或声明的最低兼容版本）。怎么确认：读文档标注的最低支持版本、读你的 `package.json`、读你的工程配置。怎么修：升级（当作外部依赖升级对待，回归后再上线）或走可用性判断兜底。

**八、H5 端的包体积越来越大，小程序端反而报体积超限。**原因：两端产物分布完全不同，用一端的构建数字判断另一端。怎么修：分别看两端输出，小程序侧回到第 4 章的分包规则按用户路径重划。

## 练习

<Exercise title="判断你的项目能不能走这条路" difficulty="基础">

不看任何文档，只做算术。列出你现在这个产品要做的功能（按页面/交互粒度，十到二十项），给每一项标三个记号：**A = 两端完全一样**（同一屏、同一交互、同一数据来源）、**B = 两端相似但形态不同**（比如导航结构、登录入口）、**C = 只在一端存在**。

回答两问：（1）A 类占比是多少？（2）C 类里有没有你「产品价值的核心一项」？

<template #answer>

这道题的判据来自本章「适合/不适合」那一节：**重合度低于七成，条件编译就会吃掉省下的时间。** 算法很简单：A + B 视为可共用面，C 视为分叉面。若 C 类占比超过三到四成，你事实上在做两个项目，只是它们共享一份数据层——这种结构用不着跨端框架，共享业务逻辑 + 两端各写 UI 更清晰（回指[第一章](/mobile/choosing-route)那条「改一个需求要打开几个文件」的判据，两套独立代码在这里未必更贵）。

第二个问题更重要：**如果 C 类里包含「只有平台刚开放的那个入口/能力才能做」的东西，封装层会把它变成排期问题。** 那时正确的设计是：核心链路用两端都有的能力实现，C 类当成某一端的增强功能，而不当成前提。

诚实提醒：这道题的答案只能给你「能不能走」的方向，不能给你成本估算——成本要你按自己的页面数与改动频率算。

</template>

</Exercise>

<Exercise title="写一段合法的差异承认书" difficulty="基础">

需求：页面底部有一个操作按钮。小程序端要避开平台的容器与安全区，H5 端要避开浏览器工具栏与 `100vh` 的坑（第 2 章讲过）。两端的具体处理方式不同。

请写出用条件编译实现这段的骨架，注意三件事：注释符按文件类型选对、两端各有一个明确的分支、每段旁边写清「为什么这里不抹平」。

<template #answer>

要点在于**承认这是真实差异，而不是尝试抹平**。骨架（数值请按你项目实际填，这里不承诺具体像素）：

```html
<!-- 模板里用 HTML 注释形式的条件编译 -->
<view class="bar">
  <!-- #ifdef MP-WEIXIN -->
  <view class="bar-inner bar-mp">主操作</view>
  <!-- #endif -->
  <!-- #ifndef MP-WEIXIN -->
  <view class="bar-inner bar-h5">主操作</view>
  <!-- #endif -->
</view>
```

```css
/* 样式里用 CSS 注释形式 */
.bar { position: fixed; left: 0; right: 0; bottom: 0; }
.bar-inner { padding: 12px 16px; }

/* #ifdef H5 */
.bar-h5 { padding-bottom: calc(12px + env(safe-area-inset-bottom, 0px)); }
/* #endif */

/* 小程序端：容器与安全区由平台决定，这里的值要靠真机量，不能靠估 */
```

三个必须补上的动作，才算合格的「差异承认书」：**（a）**每段旁边写清差在哪一端、为什么框架没抹平；**（b）**在双端测试清单里各加一条，验证方式写具体（如「iPhone 真机看底部按钮是否被小黑条挡住」「桌面 Chrome 缩到 640 高看是否被工具栏裁」）；**（c）**给分支设一个上限——同一功能块超过三个分支就重构，别再加。

另外要防的陷阱是：`env(safe-area-inset-bottom)` 是标准层写法（第 2 章），把它塞进小程序端分支不会生效——**分支写对了文件、写错了平台，是最难查的一类**，因为不报错。

</template>

</Exercise>

<Exercise title="把三层日历变成你的排期约束" difficulty="进阶">

假设平台开放了一个新交互入口，官方文档标注它需要较高的基础库版本。你的产品决定要接它，且你走 uni-app 路线。请写出你上线前必须确认的六件事，并说明哪两件是你**控制不了**的。

<template #answer>

必须确认的六件：

1. **能力本身的条件与限制**：入口在哪些场景出现、需要什么资质或配置——这类条款会变，只能查当天官方文档，不能引用别人（包括本站）的表格。
2. **平台标注的最低基础库版本**：这是用户侧的，你控制不了。
3. **你的框架版本是否已封装这项能力**：`uni.*` 有没有对应接口、文档标了什么版本起支持——这是中间层，你可以用升级影响它。
4. **你项目里声明的最低兼容版本**：这是你能配的，配高了会拒绝一部分用户，这是产品决定，不是技术决定。
5. **可用性判断与降级**：接口不存在时页面表现是什么（不能白屏），以及降级路径要不要在服务端开关后面（第 1 章那条「不发版就能关掉」）。
6. **真机覆盖**：在低版本与高版本设备上各验一次。**这条只能真机做，模拟器给不了结论。**

两件控制不了的是 **2（用户微信客户端的实际基础库版本）** 和 **1 里的平台条款演变**。由此得出本章那条判断的量化形态：**走封装层，你不可能同时是平台新能力的第一批使用者；而即便你不用封装层，用户侧版本你也管不了——差别只在于「延迟由谁决定」。** 如果这两条你的产品接受不了，那这条路线本身要重新评估，而不是在实现阶段想办法绕。

</template>

</Exercise>

场景：你要为已有 Vue 3 Web 产品增加一个移动入口。三个候选：（甲）把现有 Web 适配好当移动站点；（乙）uni-app 一套代码同时出 H5 与微信小程序；（丙）原生小程序 + 现有 Web。

请给出一份不超过三百字的书面选型意见，必须包含：四笔账中你判定最关键的两笔、一个会让你改变结论的失效信号、以及一个明确的验证动作（谁做、什么时候做）。

<template #answer>

一份合格的意见大概长这样（示例，数字按你自己的情况填）：

**结论：先甲，同时用丙验证需求，乙推迟到有第二端重合度证据之后。**

**最关键的两笔账是「时间」与「机会」。** 第 2 章那六件事不需要任何账号、审核或新框架，收益当天可见——这是全部候选里确定性最高的一笔，所以先做。机会账上要算的是：分发是不是当前增长的第一瓶颈？如果「用户找不到入口」比「入口的形态不够原生」更致命，那么第二个入口（小程序）值得马上做；如果分发不是瓶颈，那乙路线省下的语法学习成本，抵不上它引入的归因层与版本依赖。

**乙与丙之间的判据是重合度和验证意愿。** 只有 H5 与小程序两端功能重合明显高、且你会把双端都写进发布清单时才选乙；否则丙更诚实——单端项目写原生少一层归因，第 3、4 章那套约束直接对着文档写。

**验证动作**：第一步不是搭框架，是**做减法实验**——把现有产品里最适合「用完即走」的那一个功能列出来，用两句话写下它的用户路径，然后把这条路径上「需要平台能力」的格子标出来。这张表直接决定要不要做小程序，以及它到底能共用多少。一周内完成，由做产品的人写，不由框架决定。

**这套写法的价值不在结论，在于三个月后你能拿它做对照**——回看当初押的是哪笔账、失效信号出现没有，这比任何框架评测都更能提高你下一次选型的准确度。

本章的判据是「框架值不值」，但它预设了一件事：**你要编译到的那一端是小程序或 H5，也就是界面仍由容器绘制。** 跨端方案里还有两条走完全不同技术本质的路线：一条把 JSX 落到各平台的真实原生控件上，一条干脆自带一个自绘引擎、连系统控件都不用。它们的差别不是「哪个更好用」，而是**「界面由谁画」这个层次上的分歧**，因此性能特征、包体积、能力边界、和原生模块打交道的方式全都不同。
