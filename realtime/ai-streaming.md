# 与 AI 流式输出的关系：一段不能被重放的流，怎么走完三段链路

「逐字输出」在你本机跑得好好的，部署上去变成整段蹦出来——**首块延迟从 30 ms 变成 1294 ms，而模型一个 token 都没少生成**。这不是前端渲染的问题，也不是提示词的问题，是链路里有一层在替你攒字节。

用户在手机上切走标签页，或者按了你做的「停止」按钮，账单上那一笔却还是按整篇回答计的。你检查代码，前端确实 `abort()` 了——**abort 只中止了浏览器到你这台服务器这一段**，你这台服务器到厂商的那一段还在跑，而且跑得很开心。

第三种最贵：某个用户断了一次网，同一句话被生成了两遍，厂商控制台里出现两条几乎同时的长响应。服务端日志里是同一个 URL 被请求了两次，第二次带着一个你从未写过的请求头。是谁在重试？是**浏览器自带的 SSE 自动重连**——那个在第 3 章里被你当成福利、并当场预告过「免费重连在可重放场景是福利，在生成场景是负债」的东西。这一章就是来还这个债的。

这三件事的共同点是：**它们全都在传输与连接生命周期这一层，跟模型本身没有关系。** 所以你在这个领域学过的东西——一条响应可以永不结束、代理会吃字节、连接会假死、断开要退避——在这里全部适用，只是每个约束都换了一个变量。

## 先把链路画出来：三段连接，三种断开，三个负责人

AI 流式的物理形状是三段，不是两段：

```text
浏览器  ──A──  你的服务端  ──B──  厂商 API
   POST 提问      SSE/分块响应        流式响应
```

| | A 段（浏览器 ↔ 你的服务端） | B 段（你的服务端 ↔ 厂商） |
| --- | --- | --- |
| 形态 | 一次 POST 的响应体，`Content-Type: text/event-stream` 或分块文本 | 同样是 HTTP 长响应，具体协议形态各厂商不同（本批未核对） |
| 谁发起 | 用户点「发送」 | 你的服务端收到 A 段请求之后 |
| 断开怎么发现 | `fetch` 的 reader 抛错 / `AbortController` 中止；服务端侧看请求的 `close` 事件 | 读到的流抛错或提前 `done` |
| 谁负责关掉 | 浏览器 + 你的服务端 | **只有你的服务端**——浏览器不知道它的存在 |

「谁发起」和「谁负责关掉」两行是本章的全部痛点浓缩：**A 段的中止不会自动变成 B 段的中止**，浏览器那句 `abort()` 只作用于它自己那一段，而「上游会看到下游断了」是想当然。它跟第 2 章「客户端断开不等于服务端知道」、第 6 章「连接表只在本进程里」是同一类事实，只不过在流式场景下直接对应钱。

还有一个容易漏的角色：**中间那层反代。** 它看不见你的业务语义，只做两件事——按空闲超时决定要不要掐掉、按缓冲策略决定什么时候把字节吐出去。它造成的两类故障分别是下面第四、五节的主角，配置细节在[第 8 章 Nginx 代理 WebSocket](/realtime/nginx-proxy)（SSE 的关缓冲那节同样适用）。

## 这段流不能重放：所以自动重连、续传、补拉三件套要重新检查一遍

第 5 章给你的恢复公式是「先订阅、后补拉、按 ID 去重」，第 3 章告诉你 `EventSource` 会把最后事件 ID 带回去做续传。**这两套东西的隐含前提是：同一条消息重发一次无害，而且历史是可寻址的。** 生成类响应把两个前提都打破了：

- **没有游标可续。** 一次生成的中间状态不在你的数据库里，在厂商的推理进程里，而那个进程通常活不过这一次响应。你不能「从第 387 个 token 接着生成」。
- **重放不是重复，是重新付费而且内容还不一样。** 同一条提问重发一次，你拿到的是另一段文字（采样温度不为零时），账单上是另一笔完整的补全 token。

于是恢复策略必须换一句口号：**不续传，只落库；不自动重来，只让用户显式重来。** 三条具体纪律：

| 纪律 | 怎么做 | 反面样子 |
| --- | --- | --- |
| 生成端点不是订阅端点 | POST，请求体带一个客户端生成的 `requestId`；服务端给它建唯一索引，重复请求返回同一句「已在生成中」 | 做成 GET + `EventSource`，等于亲手把自动重连请进门；只靠前端禁用按钮，两个标签页就绕过 |
| 服务端不默认重试 B 段 | B 段失败就向上报错，重试只发生在用户点「重新生成」时 | 「为了稳定性」加一层指数退避重试，每次退避都在烧新的一次生成 |
| 中断的部分必须落库 | 已生成的文本 + 一个「不完整」标记写进消息表，UI 显示残缺而不是丢弃 | 只在 `done` 时才写库，用户刷新后什么都看不见 |

第三行那张表里的落库设计，形状就是[数据建模](/database/data-modeling)里「一条消息一行」加一个状态字段；幂等键的完整讨论在[会话、限流与幂等](/data-storage/session-rate-limit-idempotency)，本章只强调它为什么在流式场景下**更**必要：这里重复执行的代价是真实货币。

如果你已经把生成做成了 `EventSource`，症状非常好认：断网恢复后同一句话出现两遍，同一个 `requestId` 在服务端日志里出现两次。先查客户端是不是它，别先查网络质量——成因见常见错误⑤，动手复现见练习 2。

## 转发的时候你到底要不要解析：一条分界线

这是本领域第 3 章的线格式知识在你写服务端时会遇到的第一个实际问题。答案取决于你要不要**改**这段流：

| 你要做的事 | 需要解析吗 | 承担什么责任 |
| --- | --- | --- |
| 只是把上游响应原样转给浏览器 | **不需要**，按字节透传即可 | 几乎没有：SSE 是端到端的文本协议，中间代理不需要知道行的边界 |
| 过滤或改写事件（藏掉内部用量事件、换成自己的信封） | 需要，逐行解析；改写还要重新序列化 | 边界责任：一个事件可能被切在两个 chunk 之间，空行与转义都得你自己保证 |
| 记录 token 数、耗时、计费 | 需要，但**可以旁路做** | 只读一份拷贝，不阻塞转发路径 |

最后一行是推荐形状：**转发用字节，观测用旁路解析**。这样链路上最慢的那一段不会因为你要「统计一下」而多一次 JSON 往返，而解析器 bug 也不会变成用户看不见字的故障。

为什么「按字节透传」是安全的而「按行透传」不是，本批用合成流量过。把一条 554 字节、21 个事件、期望文本 50 码元的 SSE 响应按三种边界切碎，喂给两种写法（解析器实现与逐字输出在 [ai-apps 第 3 章](/ai-apps/streaming)）：

| 切分方式 | 朴素写法（每块独立解码＋按空行切＋独立 parse） | 带缓冲区的状态机 |
| --- | --- | --- |
| 逐字节 | 还原 0/50、派发 0 个事件、**零报错**（554 段碎片被静默丢掉） | 还原 50/50，逐字一致 |
| 随机 1~40 字节 | 还原 4/50、派发 3 个事件、parse 抛错 10 条（`Expected ',' or '}' after property value`） | 还原 50/50，逐字一致 |
| 恰好按事件边界 | 还原 50/50、零抛错——**它是对的** | 还原 50/50，逐字一致 |

第三行才是这件事最难堪的地方：**朴素写法在「每个 chunk 恰好是一个完整事件」的时候是对的。** 本机 loopback、响应体小、上游写得慢，三个条件凑在一起就能让它稳定跑几周，然后在线上第一次遇到被切开的事件时炸掉。所以判断标准不是「它现在能用吗」，而是「它依赖 chunk 边界吗」。

按行解析的实现、中文被切成乱码的那个坑（一个汉字的三个字节落在两个 chunk 里）、前端消费侧的全部细节，都在 [ai-apps 第 3 章](/ai-apps/streaming)。本章只画分界线：**只要你不改这段流，就不要解析它。**

## 首字延迟是传输问题：攒字节的那一层不该存在

先给一个本批实测的对照。合成上游每 25 ms 产一个 token、共 40 个，总耗时固定在约 1.3 s，唯一变化的是「几次产出一 `enqueue`」：

```text
=== C 上游每 25ms 产一个 token、共 40 个；差别只在「几次产出一 enqueue」（本机内存流，非网络）===
  每 token 一次            读者可见块数=40 首块到达=30ms 末块=1305ms
  攒 8 个一次               读者可见块数= 5 首块到达=263ms 末块=1311ms
  攒齐全部一次              读者可见块数= 1 首块到达=1294ms 末块=1294ms
  总耗时不变，变的只有首块到达时刻——这就是「逐字变成整段」的全部机制
```

**43 倍的体验差异，一个 token 都没有多等。** 这就是为什么「流式到底买到了什么」这个问题的答案不在模型侧：它买到的是把总耗时换成首字延迟，而任何一层缓冲都会把这份收益原样退回去。（这三个数字是本机内存流的计时，受 Windows 定时器精度影响，别当毫秒级基准用；要看的是「首块时刻随攒块数量线性后退」这个形状。）

链路上会替你攒字节的四层，从下往上排：

| 层 | 攒法 | 怎么确认 | 怎么修 |
| --- | --- | --- | --- |
| 反代响应缓冲 | 攒满一个缓冲块才吐 | 直连服务端口 vs 经域名各测一次首块时刻 | `proxy_buffering off` 或响应头 `X-Accel-Buffering: no`（第 3 章核实过该头，第 8 章有写法） |
| 压缩层 | 攒够再压，flush 不及时 | 首块延迟随响应体大小变化 | 对 `text/event-stream` 关压缩（第 3 章给了三档） |
| 你的服务端 | 攒够一句/一段再写 | 读代码：写响应之前有没有 `join`、有没有等标点 | 收到就写，别为了「看起来流畅」而 buffer |
| 浏览器 | 拿到字节还要等渲染帧 | `console.time` 打在 reader 回调与绘制回调两处 | 前端节流，属 [ai-apps 第 3 章](/ai-apps/streaming) |

第三行那个反模式值得单独骂一句：有人嫌逐字太碎「抖」，就在服务端攒到一个句号再下发。这是把第四层的职责挪到第三层，代价是**每个句号一次延迟**而收益为零——抖动是渲染节奏问题，该用 `requestAnimationFrame` 级节流在前端解决：节流后字符仍是一帧一批，但首字立刻可见。

还有一条纯传输侧的纪律：**别把 token 写进数据库。** 每个增量一次 `INSERT`，会把一条本来只有 CPU 拷贝的链路变成 40 次网络往返的长事务，还会让「首块到达」变成「最后一块落库之后」。正确形状是内存里攒文本、结束时（或超时/中止时）一次性落库，中间状态最多进缓存；写入代价对照见[数据访问设计](/database/data-access-design)。

## 空闲超时不等式换了个变量：最大 token 空档

第 5 章那条不等式——**保活间隔 < 链路上最短的空闲超时**——在这里仍然成立，只是「保活间隔」不再是你能定的常数了。流式期间字节是连续到达的，唯一的空闲期发生在**两次增量之间**，而两次增量之间的间隔你控制不了。本批用编造的间隔分布跑了 2000 次会话（普通 token 间隔 40–200 ms，35% 的会话里夹一次 3–25 s 的工具往返，12% 的会话里夹一次 10–70 s 的长思考）：

```text
=== A 空闲超时不等式（2000 次会话，间隔分布为本站编造的合成数据）===
  会话平均时长=23.6s，单会话最大空档的最大值=69.7s
  proxy_read_timeout= 30s → 会被中间层掐掉的会话=163/2000（8.2%）
  proxy_read_timeout= 60s → 会被中间层掐掉的会话=39/2000（1.9%）
  proxy_read_timeout=120s → 会被中间层掐掉的会话=0/2000（0.0%）
  proxy_read_timeout=300s → 会被中间层掐掉的会话=0/2000（0.0%）
```

**分布是编的，结论的形状不是编的**：会被掐掉的会话比例由「最大空档的右尾」决定，而不是由平均时长决定。平均 23.6 s 的会话，最大空档能顶到 69.7 s。这意味着：

- 想靠加大超时解决，你要加到「比观测到的最大空档还大」，而最大空档取决于厂商某次工具调用要跑多久——**你无法用平均值推出一个安全值**。所以先测量再取值：在你的服务端记一行相邻两次上游增量的间隔，跑几天，看 P99.9 而不是平均。
- 更省的做法是消灭空档而不是放大超时：**在空档里写一行注释**。`: ping\n\n` 是第 3 章核实过的合法保活（冒号开头、客户端忽略、不产生事件，但链路上有了字节）。服务端起一个 10–15 s 的定时器，只在「距离上一次真正写出字节超过这个间隔」时补一行，就把右尾从 70 s 压到了 15 s；代价是每个流多几十字节，收益是你不必把超时调到 300 s。
- 但**注释行不是进度信号**：客户端判断「这段回答还没结束」靠的是流没关闭，不是收到了 ping。混淆这两件事就会把保活当心跳来做业务判死——第 5 章「保活与判死必须分开取值」在流式里同样适用：保活由链路最短超时决定，判死由「一次生成最长可接受多久」决定，后者是产品决定（几十秒量级），不是网络决定。

至于三个具体数（保活间隔、`proxy_read_timeout`、前端判死阈值）——它们取决于你链路上最短那个空闲超时，而那个值只能你自己去读，所以完整算例放在练习 3 的答案里，正文不重复推一遍。

## 取消传播：谁中止谁，不中止要付多少

浏览器侧调 `abort()` 之后，本批实测过合成上游的两种反应：

```text
=== E 点「停止」之后，合成上游还在不在生产（上游共 40 个 token，读者消费到第 12 个时中止）===
  上游不检查 signal：读者消费 12 个后中止；中止瞬间上游已产 12 个，上游走完后累计 40 个（中止后又白产 28 个，跑满 40 才收尾）；读者侧拿到的异常名=AbortError
  上游检查 signal：读者消费 12 个后中止；中止瞬间上游已产 12 个，上游走完后累计 13 个（第 13 次迭代检到中止，主动停住）；读者侧拿到的异常名=AbortError
```

两组都拿到了 `AbortError`，A 段都干净地断了；差别全在 B 段——**上游不看 signal 就继续产，看了才停。** 把这件事翻译成账单（纯算术，平均补全 900 token，放弃者平均在 35% 处停手，每 1000 次请求）：

```text
  放弃率=10% → 不取消计费 900,000 token / 取消计费 841,500 token → 多付 58,500 token（= 取消方案的 +7.0%）
  放弃率=25% → 不取消计费 900,000 token / 取消计费 753,750 token → 多付 146,250 token（= 取消方案的 +19.4%）
  放弃率=40% → 不取消计费 900,000 token / 取消计费 666,000 token → 多付 234,000 token（= 取消方案的 +35.1%）
```

900 与 35% 都是本站为说明形状取的假设，**不是任何厂商的定价或统计**。这张表只要记住那句乘法：多付 = 放弃率 × (1 − 平均停手位置) × 平均补全长度。对话产品里放弃率从来不是 0，而「写了一半发现方向不对」在长文本生成里尤其常见。所以取消传播不是洁癖，是一个能从 35.1% 降到 0% 的成本项。

传播链三段都要写代码，缺一段就断在哪一段（结构示意，本批未安装依赖、未启动服务、未运行）：

```ts
const ac = new AbortController();                        // 浏览器侧
const resp = await fetch('/api/generate', {
  method: 'POST',
  body: JSON.stringify({ requestId, prompt }),
  signal: ac.signal,          // ← 少了它，「停止」只停止你自己的读取，不中止请求
});

export async function handler(req, reply) {              // 服务端：A 段关闭 → 中止 B 段
  const upstreamAc = new AbortController();
  req.raw.on('close', () => upstreamAc.abort());   // 浏览器 abort / 关标签页 / 网络断都走到这里
  const upstream = await callVendor({ body: req.body, signal: upstreamAc.signal });
  // ... 把 upstream.body 原样写到 reply，结束时移除监听
}
```

三个陷阱，都不在任何厂商文档里。**一、`close` 与「正常写完」难区分**：Node 里响应正常结束也可能触发 close，判据用 `req.raw.destroyed` 或写完时先置一个 `finished = true` 标志——这个坑的形状与第 5 章「服务端主动结束与异常断开的区分」完全相同。**二、中止要一路中止到底**：SDK 的流式方法未必真支持 signal，有些只停掉读迭代器、底层请求继续跑完（就是上面那组「不检查 signal」的形态）。这条必须你自己构造场景验证：把上游换成一个你会看到日志的假服务，按停止，看它有没有收到断开；别在真实厂商 API 上做这个实验，那是在花钱买未知。**三、成本之外的另一半是内容**：上游停了，**已经生成的那些字有没有落库**是另一个独立决定，上表的数字只解决「少付多少」，不解决「用户回来看到什么」——中止时把残缺文本连同不完整标记写库，重放交给用户。两件事混在一起写，结果通常是「省钱了但内容丢了」。

## 发布与优雅关闭：一条响应的寿命是分钟级

第 7 章那段 SIGTERM 处理里你在退出前给每条连接发了 `close(1001)`，第 8 章讲了 reload 的 worker 退出语义。流式多出一个不对等的事实：**普通 API 请求以毫秒计，发布几乎不会打断；一条生成响应以十秒到分钟计，每次发布必然打断一批。** 三种处理选一种写进发布流程，别临场决定：等它跑完再退（需要一个「停止接新流、等在跑的流结束」的上限，否则一条卡住的长生成拖住整个发布——具体参数与语义见 [发布与回滚](/devops/release-and-rollback)，本批未在本机验证）；或者直接切断但把残缺落库（依赖上面那条纪律，代价是一批带「不完整」标记的消息）；最糟的是既不等待也不结束响应，客户端只看到一个既不报错也不写完的流，转到自己的判死超时为止。

无论选哪种，前端拿到的都是同一件事：**reader 在没有任何结束事件的情况下拿到 `done` 或抛错**，所以它必须能区分「正常结束」与「连接没了」——那是 [ai-apps 第 3 章](/ai-apps/streaming) 错误处理一节的实现项，本章只把它列为发布设计的前提。

## 常见错误与排查

**① 上线后逐字变成整段，没有任何报错。** → 中间某一层在攒字节。→ 直连服务端端口 `curl -N` 看首块时刻，再经域名测一次比差值（方法见第 8 章验证表）。→ 反代加 `proxy_buffering off` 或响应头 `X-Accel-Buffering: no`；对 `text/event-stream` 关压缩。

**② 用户按了停止，账单没变。** → `abort()` 只作用在 A 段，B 段的上游请求没人取消。→ 服务端记两条日志：A 段 close 时刻、B 段最后一次收到增量的时刻，两者相差越大说明传播越差。→ `req.on('close')` 里 abort 上游，并确认你的调用封装真的支持 signal。

**③ 同一句话出现两遍，厂商后台两条相邻请求。** → 生成端点被做成了 GET 订阅，浏览器 SSE 自动重连替你重试；或你在服务端加了默认重试。→ 看同一个 `requestId` 在日志里出现几次、请求方法是什么。→ 端点改 POST，`requestId` 做唯一索引，重试只由用户显式触发。

**④ 偶发「回答显示一半就停住，转圈不消失」。** → 空档超过中间层空闲超时，连接被单方面掐掉，而 reader 没读到结束事件；另一可能是最后一块没带空行，缓冲区里剩几个字节永远派不出去（本批实测到 18 字节残留）。→ 服务端记录相邻增量间隔的 P99.9，前端检查「收到 done 但没有结束事件」这条分支有没有 UI 出口。→ 空档里写 `: ping\n\n`，并把判死阈值显式写出来、给用户「继续生成」。

**⑤ 把 API Key 放在了前端，或者塞进了 SSE 的 URL。** → 用了 `EventSource`，而它只能 GET、不能加自定义头（第 3 章核实过其构造签名）。→ 打开浏览器 Network 看那个 EventStream 请求的 URL 与头。→ 一律经服务端转发（密钥纪律见[认证：Session、Cookie 与密码哈希](/backend/auth-session)），前端用 `fetch` + reader。

<template #answer>

<template #answer>

服务端会打印**两次生成**：第一次在离线时刻附近异常结束（或被闲置），第二次在浏览器恢复后自动重连时开始，带着 `Last-Event-ID` 请求头。两次输入完全相同，接的是真实厂商就是两笔完整的补全计费。

原因不在网络，在你的端点形状：`EventSource` 的重连语义假设这条流是**可寻址的历史**——浏览器带回最后事件 ID，希望服务端从那个位置继续发（第 3 章核实过 `id` 字段正是为此设置）。而生成没有那个位置：中间态不在你的库里，无法从第 23 个 token 接着生成，你最合理的响应只有「重新生成一遍」或「告诉客户端这条流不能续」。也就是说，**你带了一个答不出这道题的端点，去见了一个专门问这道题的协议。**

订单状态推送上同一份代码是对的：那条流的每个事件都是库里一行可寻址的状态变更，`id` 就是它的序号，重连时从 `where seq > Last-Event-ID` 补发，重复送达无害且能靠去重消掉——正是第 5 章「先订阅、后补拉、按 ID 去重」的场景。

两条改动把生成端点掰回来：① 改 POST，请求体带 `requestId`，服务端加唯一索引拒绝重复；② 别用 `EventSource`，用 `fetch` + reader，顺带解决「不能带自定义请求头」，让认证待在 header 而不是 URL 里（常见错误⑤）。
