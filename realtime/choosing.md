# 三种方案对比与选型：先问方向，再问延迟，最后才问协议

一个「部署进度页」被实现成 WebSocket。三个月后它的代码里长出了心跳、指数退避重连、游标补拉、连接表清理——这四样加起来的工作量超过了进度计算本身，而这个页面本来只需要服务器每分钟告诉它一句话。

另一个反面：群聊用 5 秒轮询做，用户抱怨「对方发完我这边要等一下才出现」。这个需求其实确实需要更实时的通道，但真正难说的是「要快到多少毫秒」。

两个错误的共同点不是技术选错，而是**顺序错了**：从技术出发（我们上 WebSocket 吧），而不是从需求约束出发。本章不讲任何新机制——方向性、延迟、协议开销、断线行为这些概念在前置章节里已经建立——只做一件事：把选型变成一条有淘汰作用的决策链，每一步都能砍掉一些候选，最后剩下的那个就是你该写的东西。附带一个必须提前说的结论：**很多需求走完第一步就被砍掉了**，它们根本不需要长连接。

## 第一步：把「实时」换成一个毫秒数，砍掉一半候选

先复述那条支配一切的算术：**轮询方案的平均感知延迟是间隔的一半**（消息在两次轮询之间的任意时刻产生，客户端平均等半个周期才发现它）。所以你写下的每一个间隔都直接换算成体验。

| 需求的真实延迟预算 | 可行的候选 | 立刻排除 |
| --- | --- | --- |
| 100–300 ms（光标、输入中、游戏状态） | WebSocket | 一切轮询、长轮询（往返叠加太重） |
| 0.5–2 s（聊天消息到达） | WebSocket、长轮询、SSE | 间隔 ≥ 4 s 的短轮询 |
| 2–10 s（业务通知、订单状态） | SSE、短轮询（间隔 3–5 s）、长轮询 | 不需要 WebSocket |
| 10 s–1 min（进度条、行情、设备列表） | 短轮询 + 缓存头 | 任何长连接都是过度设计 |
| 分钟级以上（报表、统计） | 用户手动刷新 / 普通请求 | 全部 |

这一步的正确产出是一句可以写进需求文档的话：**「这条信息晚 X 毫秒到达，用户会不会察觉或受损」**。写不出 X，就不要进入下一步——答案通常是「用一次普通请求就够了」。顺带一条常被忽略的判断：**下行延迟预算和上行频率是两个约束**。上行频率（用户多久发一次）决定了 SSE/轮询这一类「上行另走一次 HTTP」的形态是否够用，它往往比下行延迟更具淘汰力，这是第二步。

## 第二步：方向决定形态，形态决定协议

```text
问 1  服务器需要在没人提问时说话吗？
      否 → 普通 HTTP 请求-响应，结束。别再加协议。
      是 ↓
问 2  客户端上行的频率与延迟要求？
      低频（点按钮、提交一次） → SSE 或轮询家族都可能够，继续问 3
      高频（每次击键、坐标、拖拽） → WebSocket，几乎无争议
      两端持续对发（语音信令、协同、游戏） → WebSocket
问 3  消息是否需要「不丢」并且可由服务端续传？
      需要 → SSE 自带 id / Last-Event-ID 续传；WebSocket 必须自己设计
      不需要（可丢、以最新值为准，例如光标位置） → 两者都行，选实现成本低的
问 4  链路上的代理你改得动吗？
      改不动（公司网关、别人的 CDN） → SSE / 轮询优先，它们不需要协议升级配合
      改得动 → WebSocket 的代价可接受
问 5  在线规模与实例数？
      单实例、连接数在内存预算内 → 都行，看代码量
      多实例 → 广播必须跨进程，见第四步；此时轮询反而是最易扩展的
```

这条链里有两处需要解释清楚，因为它们和直觉相反。

**「高频上行」这一条几乎不给你留余地。** SSE 的单向性不是实现粗糙，是协议定义：客户端不能从事件流里发东西（MDN 已核实这一表述）。你可以「SSE 下行 + POST 上行」，但每次 POST 都要重新走一遍 HTTP：连接可能新建、鉴权中间件重跑、而且**多个 POST 之间没有顺序保证**。对聊天（一秒几条）这没问题；对协同光标（一秒几十条 × 每移动一次）就是灾难。

**「代理改不动」是纯工程约束，但常常才是决定性的一条。** WebSocket 的握手是一次 HTTP Upgrade，链路上任何一个不转发 `Upgrade`/`Connection` 的设备都会让它失败，而且失败症状最坏（`code 1006`，无状态码无原因）。SSE 从头到尾就是一份普通的、还没写完的 HTTP 响应，现成的鉴权、日志、CDN、TLS 全部照常工作。如果你的部署形态里有你无权修改的中间层，那么「SSE 更省事」不是偏好，是风险判断。

## 第三步：七个维度摊开对照（然后指出哪三行真正致命）

| 维度 | 短轮询 | 长轮询 | SSE | WebSocket |
| --- | --- | --- | --- | --- |
| 服务器能否主动开口 | 否（伪装成频繁被动） | 挂起窗口内可 | 是 | 是 |
| 平均延迟 | 间隔 / 2 + RTT | ≈ 一次 RTT | ≈ 一次 RTT | 单帧往返，最低 |
| 上行 | 普通 POST | 普通 POST | 普通 POST | 同一条连接内，双向对发 |
| 每个事件的额外开销 | 完整 HTTP 头 | 完整 HTTP 头 | 几十字节的行格式 | 帧头（2–14 字节量级） |
| 并发连接占用 | 每次瞬时一格 | 每用户长期一格 | 每用户长期一格 | 每用户一条 TCP，**不占浏览器 HTTP 额度** |
| 服务端执行位 | 请求期间 | 挂起期间一直占 | 响应期间一直占 | 连接期间一直占 |
| 代理兼容性 | 最好 | 好（受空闲超时支配） | 好（但受缓冲支配） | 需转发协议升级，最容易配错 |
| 断线恢复 | 下一次问自然补齐 | 要自己重发与续传 | **协议自带重连 + `Last-Event-ID` 续传** | 全无，全要自己写 |
| 鉴权模型 | 每请求鉴权 | 挂起时鉴权一次 | 每（重）连时鉴权一次 | 握手时冻结，长期有效 |
| 二进制载荷 | 不适用 | 不适用 | 文本流，需 Base64（约 4/3 膨胀） | 原生 binary 帧 |
| 可观测性 | 最好（标准请求日志/指标） | 好 | 好 | 差（连接内事件要自己埋点） |
| 需要你写的代码 | 定时器 + 去重 | 挂起表 + 超时协同 | 写流 + 清理 + 保活 | 握手 + 心跳 + 重连 + 补拉 + 幂等 + 清理 |

真正决定成败的只有三行，其余按项目具体情况权衡：

1. **「每用户长期一格」那一行。** 在 HTTP/1.1 下浏览器对同一 origin 有并发连接上限（MDN 明确写作典型 6，并且这个额度**跨同一浏览器的所有标签页共享**，已核实 2026-10-20）。一条 SSE 就吃掉一格，开三个标签页吃三格，你还要留给页面里所有普通请求和图片。WebSocket 不受这个额度约束（它不是 HTTP 请求）。这行常常是「明明 SSE 更简单，但我们最后用 WS」的真实原因。上 HTTP/2 之后这条基本消解。
2. **「响应/挂起期间一直占执行位」那一行。** 它取决于你的运行模型：Node 的事件循环挂起一个请求只是存回调；一个请求一个进程/线程的同步模型挂一万个连接就是一万个进程。同一个功能在不同技术栈上会得出不同结论，这不是代码质量问题。
3. **「断线恢复」那一行。** 这是 SSE 相对 WebSocket 唯一压倒性的免费送东西：浏览器自动重连，并按最后事件 ID 续传。WebSocket 这边这套要全部手写。所以「服务器有话说、客户端只是听」的场景里，SSE 的实现成本明显更低。

## 第四步：规模与基础设施会把答案改掉（三档）

**第一档：单人 MVP，单实例，在线几十到几百。** 唯一重要的指标是**你要维护多少行与业务无关的代码**。排序：短轮询（最少的代码，几乎不坏）< SSE（几十行，重连白送）< 长轮询（要处理挂起与超时协同）< WebSocket（最重，因为第 2 章那张「协议不给你」的表全要自己填）。这一档里如果需求是单向的，SSE 几乎总是正确答案；如果需求是聊天，WebSocket 值得——但你必须承认自己是在承诺写那四件事（重连、补拉、幂等、优雅关闭）。**这一档最该做的是拒绝为分布式设计。**

**第二档：多实例（横向扩容后），在线几千到几万。** 新的支配性约束是**连接分散在不同进程/机器上，而事件产生在另一处**。轮询家族在这里有结构性优势：**任何实例都能应答任何一个请求**，只要状态在共享存储里；而 SSE 和 WebSocket 都必须有一条跨实例广播总线（Redis 发布订阅、消息中间件，或框架自带的适配器），否则就会出现「一半用户收不到」这种最难复现的故障。这一档还会暴露**空闲超时对齐**问题：LB/代理/NAT 的空闲回收周期必须大于你的保活间隔，这对长轮询、SSE、WebSocket 三者都成立，只是 WebSocket 最容易静默中招。

**第三档：移动端为主、或超大并发。** 关注点从「延迟」变成**每条连接的真实成本**：内存、文件描述符上限、TLS 会话保持、以及省电——蜂窝网络下每次唤醒射频都有代价，密集的短轮询是最耗电的形态，而长连接也需要心跳字节。这一档里还有一个必须诚实说出的分支：**如果你的用户主要在原生 App 而不是浏览器**，那么浏览器长连接不是唯一答案，平台推送（APNs/FCM 一类）通常才是正解，它的定位是「低频到达 + 由操作系统统一管电」。本站不覆盖原生推送，这里只负责让你意识到「实时」不等于「自己维护一条常连接」。

一张反向清单，帮你识别自己已经过度设计：单实例服务得住却先上了广播总线；在线不足一千却做了 sticky session；需求是单向通知却写了心跳协议；为了「以后可能要协同」把通知流也搬到 WebSocket。**每一条都意味着你在为不存在的需求付维护费。**

## 第五步：框架和新生事物不在这一层，别在这里比较它们

选型链走到这里必须画一条界线，否则会把「协议」和「库」混在一起比。

- **Socket.IO 不是 WebSocket 的封装，是建立在 WebSocket（并可在失败时回落到长轮询）之上的一个应用层协议。** 它自带房间、自动重连、心跳与降级——也就是把第 2 章「协议不给你」那张表里的东西替你实现了。代价是两端都必须使用它的客户端（浏览器里装了它的 JS，别的标准 `WebSocket` 客户端连不上），线上流量格式不透明，以及体积。这类取舍属于第 7 章（Node 侧实现对照）的主题，本章只给一条选型纪律：**当你发现自己正在手写重连、心跳、房间、ACK 四件套时，才轮到考虑用框架替你管；写不满四件就别引入一个不透明的协议。**
- **`ws` 库**（Node 侧）是贴近协议的薄实现，它不给你房间和重连——这正好是本站希望你先裸写一遍的原因。
- **WebTransport / HTTP/3 一类新传输**提供带背压的多流与数据报语义，长期看会替代一部分 WebSocket 用例（MDN 的 WebSockets API 页面也是这么定位的，已核实其存在与「支持度较低」的表述）。但跨浏览器支持度以 caniuse.com 当前数据为准，本批不写版本号也不写支持率；MVP 阶段把它放在「知道有这条路，现在不走」的位置。
- **HTTP/2 Server Push** 是资源预取机制，不是消息通道，与实时通信无关；主流浏览器后来移除了它（具体版本与时间本批未核实，需要时查 caniuse.com）。
- **gRPC 流式**在「服务之间」的流式很有价值，但浏览器直连需要额外一层，本站的部署主线（Nginx + 浏览器）里它不是候选。

## 一次完整推演：五个场景各走一遍这条链

**① 通知铃铛上的红点。** 方向：纯下行。上行：无（用户点一下就跳转）。延迟预算：3–5 秒完全无感。规模：全站在线，单实例。基础设施：改得动 Nginx 但不想改。链路走到第二步就出结论——**SSE**。代价清单：每用户一条长连接占一格 HTTP/1.1 额度（上 HTTP/2 化解）、需要注释行保活、服务端要清理断开连接。若不用 SSE，退路是 30 秒轮询 + 条件请求（304 空体），代码量更小。

**② AI 回答的逐字显示。** 方向：一次上行（提问）+ 一串下行（token）。延迟：token 到就要显示。上行频率：一次。结论仍然是 **SSE 形状**——但注意第 3 章的硬约束：浏览器不能直连厂商（`EventSource` 只能 GET、不能加 header、API Key 不能进 URL，重连还会重复计费），所以正确形态是「浏览器 ↔（SSE）↔ 你的服务端 ↔（流式读取）↔ 厂商」。**不要用 WebSocket 承载它**：双向能力用不上，白丢 SSE 的重连语义之外还得自己处理「生成中断后不重放」。

**③ 群聊。** 方向：双向。下行延迟预算 0.5–2 s，上行每次发送一条（低频）。走到第二步会发现 SSE 其实也能做（下行 SSE + 上行 POST 发消息），这是很多人不知道的答案。真正的决定性因素是第三个需求：「对方正在输入」需要高频上行 → **WebSocket**（或「SSE + 高频 POST」这种别扭组合）。选 WS 就必须承认要自建四件事：重连与退避、按消息 id 的幂等渲染、断线期间通过 HTTP 补拉、服务端优雅关闭。

**④ 协作白板 / 光标同步。** 方向：双向持续对发。延迟 100–300 ms。消息可丢（以最新值为准）。结论 **WebSocket**，且要点全在客户端节流与合并（把 100 ms 内的多次移动合成一条），以及**背压**：慢网络时丢弃旧坐标而不是堆在 `bufferedAmount` 里——浏览器 `WebSocket` 接口无背压支持（已核实），丢了要丢得有策略。

**⑤ 后台任务进度条（反例）。** 方向：下行。任务跑 90 秒，2 秒间隔的相对误差可忽略。规模：单用户一个任务。结论：**短轮询 + 缓存头 + 条件请求**。如果给它上 SSE，你会多维护一套挂起连接表和一条保活心跳；如果上 WebSocket，你多维护的是整套。这一条存在的意义是提醒：**走完第一步就退出的场景，是本项目里最省钱的决策。**

## 常见错误与排查

1. **现象：需求文档写「要实时」，于是上了 WebSocket，三个月后代码里一半是心跳与重连。** 原因：从没定义延迟预算，把「实时」当功能而不是当数字。怎么确认：问「晚 3 秒到达用户会不会受损」，答不出来。怎么修：回到第一步，把 X 毫秒写进需求；单向场景改 SSE；分钟级场景改轮询 + 缓存头。
2. **现象：同一件事既在轮询又在长连接，负载翻倍且偶发重复渲染。** 原因：迁移没完成，或有人把轮询当「兜底」留着。怎么确认：Network 面板里同时出现周期请求和一条常连接；服务端日志出现同一消息被两条通道投递。怎么修：迁移必须成对（新通道验证通过当天关掉旧通道），并在客户端按消息 id 幂等，让重复投递无害。
3. **现象：在线人数一上千，服务器就顶不住，CPU 却不高。** 原因：在「一个请求一个进程/线程」的运行模型上做长轮询或 SSE，挂起的响应把 worker 池占满。怎么确认：活跃请求数是否≈在线人数；线程/进程池使用率是否 100% 而 CPU 使用率很低（这是典型的「都在等」形状）。怎么修：换能挂起请求的运行模型，或改成短轮询 + 缓存层把请求挡在前面。
4. **现象：本地一台机器一切正常，线上部分用户收不到消息，且「谁收不到」随时间变化。** 原因：实例多了，广播表在各自进程内存里。怎么确认：把各实例的连接数相加与总在线对比；或者固定一个用户，观察他每次登录后能否收到。怎么修：短期把同一用户粘在同一实例，中期引入共享总线。**注意这一条对 SSE 和 WebSocket 同样成立**——「用了 SSE 所以简单」不等于「SSE 能随便横向扩」。
5. **现象：手机用户抱怨耗电、流量，且后台标签页消息完全不实时。** 原因：密集轮询反复唤醒射频；浏览器对后台标签页定时器做节流（实现选择，本批未验证具体阈值），你以为的 5 秒实际变成几十秒。怎么确认：对比前台/后台两种状态下服务端的请求间隔分布。怎么修：拉长间隔 + 回到前台立即对齐一次；用户主要在 App 的话评估平台推送而不是把浏览器长连接搬进 App。
6. **现象：换了 WebSocket 之后「还是慢」。** 原因：慢的根本不是传输，是数据库查询、渲染或网络回源。怎么确认：分别测「事件在服务端产生」到「写出」，与「写出」到「客户端收到」。怎么修：把传输和处理分开优化；这一步没做，任何协议迁移都不会改变观感（第 1 章常见错误第 6 条是同一种病）。

A：**普通请求 + 手动刷新（或 60 秒轮询）**。理由是分钟级延迟预算下，为 5 个观众维持长连接纯属自找维护；代价：切回页面时可能看到旧数字，需要「回到前台立即刷新一次」这个小逻辑。B：**WebSocket**。理由：双向 + 0.5–2 s 预算 + 上行也要求即时，是四项里唯一能同时满足的形态；代价：你要自建重连、幂等渲染、断线补拉、优雅关闭四件套（第 2 章那张表），并且多实例上线时需要广播总线。C：**短轮询（2–3 秒）+ 条件请求**。理由：进度本身秒级变化，2 秒间隔的均延迟 1 秒足够，且任务状态存在数据库里任何实例都能答；代价：一个任务最多 150 次请求，但相比引入挂起连接管理，这个成本便宜得多。D：**SSE**（本题的正解在这条）。理由：纯下行、2–10 s 预算、在线 800 人可承受 800 条挂起响应、重连与续传白送；代价：HTTP/1.1 下每用户每标签页占一格并发连接额度（上 HTTP/2 化解），且服务端要做连接清理与保活。E：**WebSocket**。理由：100–300 ms + 高频上行 + 持续对发；代价：必须做客户端节流与合并、必须处理背压（浏览器接口无背压，慢网络时会堆积待发数据），并且消息可以丢——所以要按「最新值覆盖」而不是「逐条重放」来设计。可接受答案是 A/C 都不上长连接；如果你给 C 配了 SSE，请说出你的连接清理与保活代码在哪。

</template>

</Exercise>

<Exercise title="练习 2 · 把选型变成算术，再加一个会坏掉的条件" difficulty="进阶">

在线 5,000 人，全服事件产生速率 20 条/秒（每条要推给相关的约 200 人）。技术栈：Node 单实例 + Nginx + HTTP/1.1。间隔类方案取 4 秒。

1. 短轮询：每秒多少请求？假设请求 + 空响应合计 700 B，带宽多少？
2. 长轮询与 SSE：并发挂起连接大约多少条？服务端 CPU 与内存的主要开销落在哪里？
3. WebSocket：与第 2 问相比，浏览器侧与代理侧的区别是什么？
4. 现在把条件改成 **4 个实例、没有共享总线**。逐一说出四个方案里哪些立刻坏、哪些只是变贵。
5. 你的最终选择与该选择必须额外实现的最少功能集。

<template #answer>

1. `5000 / 4 = 1250 req/s`；带宽 `1250 × 700 B ≈ 875 KB/s ≈ 75 GB/天`，而真实事件只有 20 条/秒——**有效负载占比约 1.6%**。这一行就足够把短轮询判死，除非你能用 304 把空响应压到几十字节。
2. 挂起连接约 5,000 条（每人一格，HTTP/1.1 下同一浏览器还会因额度限制而被迫合并通道）。CPU 几乎不花在「等待」上（事件驱动模型挂请求只是存回调），主要开销是：① 5,000 条 socket 与定时器/心跳的内存；② 每个事件到达时遍历相关订阅者的查找成本；③ Nginx worker 的连接数上限与文件描述符上限（`worker_connections`、`ulimit`）。**这里最容易漏的是第 ③ 项：应用能撑住不代表代理撑得住。**
3. 同样是 5,000 条 TCP 连接，但 WebSocket **不占用浏览器对同一 origin 的 HTTP 并发额度**（它已脱离 HTTP 请求语义），所以页面里其他资源请求不受挤压；SSE 每条都算一格。代理侧的区别是反向的：WebSocket 需要 Nginx 正确转发协议升级，配错就是 1006；SSE 是普通响应，天然兼容但会被缓冲（要 `X-Accel-Buffering: no`）。空闲超时这一项两者完全一样，都需要保活。
4. **短轮询：不坏**，只是贵——任何实例都能应答任何请求，无状态在这一点上是真优势。**长轮询：不坏但会错乱**——事件产生的实例和挂着用户请求的实例不同，必须跨实例投递，否则表现为「有时即时、有时等下一次轮询」。**SSE：立刻坏**，用户挂在实例 A，事件在实例 B 产生，收不到。**WebSocket：立刻坏**，同理。后两者都需要一条共享总线（Redis 发布订阅或消息中间件）或框架适配器；这是第 9 章的主题。
5. 答案不唯一，判据要对：选 SSE 或 WebSocket 都可以，但你必须显式承认额外功能集是「保活心跳 + 断线续传（SSE 靠 `id`，WS 要自己写）+ 跨实例广播 + 优雅关闭 + 客户端幂等渲染」，并说明 5,000 在线在单实例内存预算内为什么够用（或者一开始就上总线）。如果你选「先维持单实例、把总线的钱留到有第二个实例那天」，那也是正确答案——前提是写清楚触发条件（比如连接数达到实例容量的 70%）。错误答案是「选 WebSocket 因为它最强」。

</template>

</Exercise>

<Exercise title="练习 3 · 四个功能、一套技术栈、一张上线顺序" difficulty="挑战">

你是这个应用唯一的技术负责人。产品要求四个功能：群聊、AI 回答流、部署通知、协作白板。约束：一个人维护；单实例部署，VPS + Nginx + HTTPS；HTTP/2 已可用；数据库只有一个；现在没有任何实时基础设施。

1. 给出**最少**的技术栈组合（不许四个功能各一套协议），并说明哪些功能可以共用它。
2. 有没有一个方案是「全部塞进 WebSocket」？给出它相对「WS + SSE 并用」在实现复杂度上的具体增减项，然后做决定。
3. 排出四个功能的上线顺序，每个阶段给出可验证产出与回退方案。
4. 写出你**主动拒绝**的两个「看起来该做」的设计，以及各自将来在什么信号出现时才做。

<template #answer>

1. 最少组合是**一条 WebSocket 承载三个功能（群聊、白板、部署通知）+ AI 回答流走 SSE（经服务端转发）**。理由：群聊与白板的方向性、延迟预算、消息形状完全一致（双向小包 + 高频上行），必然共用一条连接和一个消息信封；通知是低频下行，走同一条连接只是多一种事件类型，几乎零额外成本——它不该单独开一条 SSE，那会白白多占一格连接额度。AI 流必须留在 SSE 形状上：它的上行只有一次提问（普通 POST），而且它的**中断与不重放语义**与生成类请求绑定，用 fetch/SSE 转发比在 WS 上再造一套「会话 + 取消 + 增量」更省事（第 3 章练习 3 的结论）。
2. 「全塞 WS」省掉的是：第二条通道的鉴权与生命周期代码、多一个部署形态、多一个可观测面。增加的是：为 AI 生成手写「取消传播 + 断线后绝不自动重放」的语义（SSE 这边你只要**别用** EventSource 的自动重连），以及一个「请求体大、响应慢」的流在 WS 上会变成一条长事务消息，需要自己分片与超时管理。净结论：如果只有聊天 + 白板 + 通知，选单一 WS；AI 流存在时保留 SSE 通道更便宜，因为它把「重放有害」这件事的默认方向摆对了——**SSE 的免费重连在可重放场景是福利，在生成场景是负债。**
3. 顺序按「最小可验证 + 失败面最小」排：**① 通知**（一条 WS，只做服务器→浏览器，先跑通握手、心跳、优雅关闭三件，产出：控制台里能看到 101 与一条自定义心跳消息，回退：关掉它改 30 秒轮询，零业务影响）；**② 群聊**（加上行与消息信封，产出：两个标签页互发消息、拔网线 30 秒重连后历史无缺口，回退：回到轮询读取历史）；**③ AI 流**（独立 SSE 端点 + 服务端转发 + AbortController 取消传播，产出：能看到逐字渲染且点停止后上游请求同时被中止，回退：改成一次性返回全文）；**④ 白板**（同一条 WS 上加坐标事件，做节流与最新值覆盖，产出：200 ms 内其他端可见、慢网络时旧坐标被丢弃而不是堆积，回退：降级为「松手时才同步」）。每一步都有可证伪产出，不做「四个一起上」。
4. ① **拒绝跨实例广播总线**（Redis pub/sub）：现在单实例，加了只会增加一个故障源与一条要维护的凭据。出现信号再做：连接数逼近实例容量、或部署从 1 个服务变成 2 个。② **拒绝消息持久队列（Kafka/Redis Stream 一类）**：聊天历史直接落库、按游标补拉就够，队列解决的是「生产与消费速率不匹配」，你现在没有这个问题。同理可拒绝 sticky session、协议自动降级、多主题复用（multiplexing）框架——它们都属于第三档规模的问题，写下来比写代码有用（第 9 章会正面讲这条边界什么时候必须过）。

</template>

</Exercise>

## 官方文档与延伸阅读

本章不引入新的协议事实，它引用第 1、2、3 章已经核实过的结论。站内衔接：算术与轮询代价在第 1 章[为什么请求-响应不够](/realtime/why-http-is-not-enough)；「协议不给你什么」那张表在第 2 章 [WebSocket 协议](/realtime/websocket-protocol)；单向性、连接额度与 `X-Accel-Buffering` 在第 3 章 [SSE：单向服务器推送](/realtime/sse)。反代与超时对齐的配置在 [Nginx](/linux/nginx)（本领域第 8 章会针对 WebSocket 逐行讲）；部署形态与回滚在 [部署到 VPS](/devops/deploy-to-vps) 与 [发布与回滚](/devops/release-and-rollback)；鉴权与会话模型在[后端会话与鉴权](/backend/auth-session)。

- [MDN · 使用 Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) —— **已核实**（2026-10-20）：本章对照表里「SSE 单向、客户端不能从流里发消息」「不用 HTTP/2 时受每浏览器每域名典型 6 条并发连接限制且额度跨标签页共享」「默认自动重连且 `id` 用于续传」三行出自本页。
- [RFC 6455 · The WebSocket Protocol](https://www.rfc-editor.org/rfc/rfc6455) —— **已核实**（2026-10-20）：§1.7「独立的 TCP 协议」、§5.3 客户端到服务端必须掩码、§7.4.1 关闭码含义与 1005/1006 不出现在帧里。本章用它支撑「WebSocket 的失败症状为什么是 1006」与「它不占 HTTP 并发额度」这两个判断。
- [MDN · WebSockets API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) —— **已核实**（2026-10-20）：标准 `WebSocket` 接口不支持背压（`WebSocketStream` 才有流与背压，且支持度有限）、WebTransport 作为后续方向但跨浏览器支持不足。本章第五步只据此定性，不写版本号与支持率。
- [Socket.IO 官方文档](https://socket.io/docs/v4/) —— 建议读它自己关于「Socket.IO 不等于原生 WebSocket」的说明。**本批未逐字核对该页**，因此本章对它的定位只写到「建立在 WebSocket 之上、两端必须配套使用的应用层协议」这一层，完整取舍留给第 7 章。
- [caniuse.com](https://caniuse.com/) —— HTTP/2、`WebSocketStream`、`WebTransport` 的实际浏览器支持度一律以本页当前数据为准；本章刻意不写支持率。
