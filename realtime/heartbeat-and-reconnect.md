# 心跳与断线重连：连接还在，不代表对方还在听

第 2 章那张「协议给你的、协议绝不给你的」表里，欠得最狠的两行就是本章要还的：**心跳**与**重连**。它们之所以欠，是因为 WebSocket 建立之后长得太像一条「永远不断的线」了，而事实是——它会不断地、安静地、不通知你地死掉。

三个故障形状，都是本项目里高频出现的：

第一个，服务端往一条「看起来还在」的连接推了 200 条消息，全成功，日志一条错误也没有。用户五分钟后回到页面，界面还停在旧状态。真相是中间那台设备的空闲映射早就被回收了，**它只断了去程，没断回程**：服务端发出去的字节消失在半路，TCP 没有收到 RST，所以应用层什么都看不到。这类故障最难的不是修，是**你的系统里没有一条数据能证明「对方收到了」**。

第二个，手机从 Wi-Fi 走开换成蜂窝，客户端的连接其实已经死了 40 秒，页面显示的还是「在线」。用户在地铁里给别人发消息，提示「发送失败」，而对方那边显示他在线。**在线状态是一种用心跳超时推断出来的假设，不是一个事实**——它的滞后正好等于你的判死阈值。

第三个，服务端滚动发布，重启了 4 秒。5,000 条连接同时断，客户端代码里写的是「断开后立刻重连」，于是 5,000 次握手在同一个瞬间砸回来，其中每一次握手都要解析 token、查一次数据库、重建会话。发布结束后的 30 秒里，数据库连接数打到上限，鉴权接口 p95 从 20ms 变成 6 秒，**看起来像「重连之后系统更慢了」，实际是重连风暴把你的鉴权路径变成了拒绝服务攻击的目标**。

## 假死是分层的：谁知道连接死了，谁知道对方还在听

「连接断了」这句话至少有四个不同的含义，搞清楚死在哪一层，才知道该由谁来发现它：

| 层 | 谁知道 | 不知道时会怎样 | 谁负责发现 |
| --- | --- | --- | --- |
| TCP 层 | 只有收到 RST/FIN 的一侧 | 拔网线、`kill -9`、掉电：本侧永远不会「知道」，直到发送超时 | 没有自动通知；**只能靠应用层主动证明双向可达** |
| 中间设备层（NAT、负载均衡、代理） | 设备自己知道，它不会告诉你 | 空闲超时后悄悄丢掉映射，一侧发出的字节被静默丢弃，两侧都以为还在 | 只能靠「一段时间内没收到任何字节」推断 |
| 协议层（ping/pong） | 发 ping 的一方，靠 pong 判断 | pong 只证明**对端协议栈还在**，不证明业务能处理 | 协议给了工具，第 2 章已核实：收到 ping 必须回 pong |
| 应用层 | 你的代码 | 进程活着、TCP 活着，但事件循环被大任务卡住，收得到处理不动 | **必须你自己发一次「带业务动作」的往返** |

这条分层表里最值钱的一条判断是：**只有「双向都有字节」才算连接活着**。能发不能收（第一个故障）是最危险的形态，因为你的发送调用不会报错。所以别问「连接断了吗」，问「我最后一次**收到**这个对端的任何字节是什么时候」。

顺带一条同样重要的推论：**发送成功不是送达证据**。把这条与[短信、邮件与第三方 API](/message-queue-cloud/sms-email-and-api)里「对方回你 200，只说明它收下了」放在一起看，你会得到本项目反复出现的思想：**任何「我发出去了」都必须翻译成「谁给了我什么证据」**。长连接这边证据更薄——连「收下」都不是应用层语义。

## 心跳有两个目的，用一个间隔糊在一起是本章最常见的设计错误

**保活**：让链路上的中间设备不要因为空闲而回收映射。**判死**：在合理时间内发现对端已经不在了。

这两个目的对间隔的要求方向相反，必须分开取值再统一：

- 保活间隔必须**小于**链路上最短的那个空闲超时。而那个最短值取决于你控制不了的设备。所以正确做法不是猜一个数，而是**把它测出来**：从服务端到浏览器，中间每一跳（本机代理、家庭路由器、云上负载均衡、反向代理）都可能有一个空闲超时，取其中最小者。云上那一个通常写在产品文档里；本站没有云账号，不写具体数值，你查到你自己的那一个，然后拿它当上限。
- 判死阈值 = 保活间隔 × 允许错过的次数。**这个数直接等于「用户最多要多久才看到更新」**，也等于「在线状态最多滞后多久」。它是个**产品参数**，不是网络参数——把它交给运维拍脑袋定，就是第二个故障的成因。

一个具体取舍（手算，非产品数字）：假设 ping 与 pong 控制帧各按 15 字节估（帧头小、载荷极短），单条连接每 25 秒一次往返：

- 每条连接每天 86400 / 25 = 3,456 次往返，约 6,912 帧 × 15 B ≈ **104 KB / 天 / 连接**。
- 5,000 条连接：**约 500 MB / 天**，摊到每秒 400 帧（200 对往返）。
- 间隔从 25 秒改 5 秒，字节量与帧数同时 ×5 → 约 2.5 GB / 天、每秒 2,000 帧。

结论不是「心跳很贵」，而是：**带宽和 CPU 通常不是限制项，判死滞后才是**。5 秒间隔给你 10–15 秒的判死滞后（乘以容忍次数），25 秒给你 50–75 秒。**真正逼你缩短间隔的是「中间设备的最小空闲超时」，真正逼你延长间隔的是「每秒要处理多少帧和多少个定时器」**。这两条给完，间隔自然出来了，不需要抄别人的数。

一个例外：客户端主要在**蜂窝网络**上时，代价不是字节而是**射频唤醒**，密集短心跳会明显影响耗电（这是[选型那章](/realtime/choosing)第三档规模的判断，本章不重复）。

## 控制帧还是应用层消息：谁能收到，收到又意味着什么

WebSocket 协议自己有 ping/pong 控制帧，第 2 章已核实「收到 ping 必须回 pong」。**但注意回 pong 的是谁**：是协议栈，不是你的业务代码。它自动回，不需要你写任何处理，也正因如此——**pong 回来只证明对端的 TCP 与协议实现还活着，完全不证明你的事件循环有空、handler 没抛错、订阅表还没烂**。

由此得出两条设计规则：

1. **想要「协议栈活着」的证据 → 用控制帧。** 便宜、自动、跨语言一致。
2. **想要「业务还能处理」的证据 → 用应用层消息**：发一个带业务含义的请求（比如让服务端回一次「你的订阅仍然有效」或者「当前状态版本号」），这个往返必须穿过你的 handler，才能证明第 4 层没死。

浏览器这边有一条硬约束要认清：标准 `WebSocket` JS 接口**没有**向服务端发送 ping 控制帧的能力（第 2 章核实过的 MDN 接口清单里不存在这个操作）。所以浏览器发起的心跳只能是应用层消息；控制帧方向通常是「服务端 ping、浏览器协议栈自动 pong」。**这条限制决定了你只能做单向判死**：服务端能通过 pong 判断浏览器协议栈是否还在，浏览器却无法用同样方式判断服务端——**浏览器侧的判死只能靠「一段时间内没收到任何字节」或者应用层自问自答**。设计客户端时要按「我判断不了服务端死没死，我只能判断我太久没听到动静」来写，而不是照抄服务端那套。

通用形状（**不写任何库的方法名与选项**，本批无法核对；名称请在该库 README 里确认）：

```text
每条连接记 lastSeenAt = 最后一次收到「任何」入站字节的时刻
服务端：超过保活间隔没动静 → 发一次探测；超过判死阈值 → 关闭、移出连接表、清理订阅
客户端：周期性发一条带业务动作的请求；超过判死阈值没收到任何字节 → 主动 close() 再进重连
```

那个「主动 close()」很多人省。省下之后的现象是：**连接已经死了，你的代码还在往它写**，UI 一直显示「已连接」，因为 readyState 还是 OPEN。只有主动关闭才会产生关闭事件、才会触发重连逻辑——**「发现死了」和「让它算死了」是两个动作，缺一不可**。

## 重连：退避、抖动、上限，以及放弃之后干什么

**指数退避**不是为了让客户端更快连上，是为了让服务端能活下来。序列手算一遍（基数 0.5 秒、倍数 2、封顶 30 秒）：0.5 → 1 → 2 → 4 → 8 → 16 → 30 → 30……前七次累计等待 61.5 秒。**这条曲线的形状意味着：一次 30 秒的服务端重启，客户端会在第 1、2、4 分钟各试一次——它一定能连上，但中间那段时间对用户是「不工作」**。所以退避曲线不能只看「总会连上」，要和「这段时间里用户的操作怎么办」一起设计（下一节）。

**抖动（jitter）**是把同时到达摊开。第三个故障里那 5,000 次同时握手，如果每次等待时间取「封顶值内的随机数」，同一瞬间的尖峰就被摊进一个时间窗。**但必须诚实：抖动不减少总量，只改变分布。**5,000 次重连的总成本一次没少，只是不再同时砸下来。真正让服务端活下来的，是下面这三件与退避无关的事：

1. **握手不等于鉴权完成。** 如果每条重连都要查一次数据库做 token 校验，重连风暴就变成了数据库攻击。用可以本地验证的凭证形式（自包含、无查表）或者把校验结果做短 TTL 缓存，是把成本从 5,000 次查询降到几十次的地方。这个乘法与[连接池与慢查询](/data-storage/connection-pool-and-slow-query)里那条是同一个：**实例数 × 每实例池大小 = 数据库看到的连接数**；这里是**连接数 × 每连接的鉴权成本**。
2. **接受连接要有上限，并且超限时明确拒绝。** 没有上限的重连风暴会把「一部分人先用上」变成「所有人一起不可用」。宁可返回一个明确的关闭码，让客户端知道「现在别硬挤」。
3. **服务端重启时主动通知。** 优雅关闭时发一个可识别的关闭码再断，客户端就能区分「我掉了」和「它在发布」——后者可以慢一点、错峰一点再重连。第 2 章核实过的关闭码表里，1001（Going Away）就是给这种「我知道我要走了」的场景用的；**不要用 1006，那个码的意义恰恰是「这不是对端发来的」**。

**上限与放弃**：重连不能无限进行。触发放弃的条件要写成规则而不是感觉：连续失败超过 N 次或总时长超过 M 分钟 → 停止重连，降级到别的获取方式（轮询一次状态、或者提示用户手动刷新），并把「我在降级」这件事显示出来。**最坏的设计是「永远在后台重连，界面永远显示旧数据」**——用户以为一切正常，实际上已经断了三分钟。

还有一种放弃必须显式写成「不重连」：**协议或配置错误**。如果服务端因为 Origin 校验失败、子协议谈不拢、鉴权不合法而拒绝握手，那这些错误重连一万次也不会变好；无限退避重试只会把「你的配置错了」伪装成「网络不稳」，并且顺手把服务端打忙。**重连逻辑要按「这个失败是可重试的还是终态的」分叉**，判断依据就是第 2 章那条已核实的规定：**服务端不想升级时返回普通 HTTP 错误状态码**——4xx 类握手失败基本是终态，连接层失败才值得退避重试。

## 重连之后：状态恢复才是这个项目真正的难点

连上了，然后呢？断线期间别人发的消息、改的状态、进的房间，全都错过了。这里有三种做法，只有一种是对的。

关键概念是**游标（cursor）**：一个单调递增的序号，代表「我看到的进度」。它必须是序号，**不能是时间戳**——时钟会跳、会校正、多实例之间的时钟不同步，而「按时间取大于某点的记录」在边界上一定会重叠或漏。这条与[投递语义](/message-queue-cloud/delivery-semantics)、[Redis Stream](/message-queue-cloud/redis-stream)里条目 ID 的两段结构是同一件事：**用可比较的进度替代不可靠的时刻**。

三种顺序的结果：

| 做法 | 漏 | 重 | 判定 |
| --- | --- | --- | --- |
| 先补拉历史，再订阅增量 | **会漏**：补拉请求发出到订阅生效之间到达的那几条，既不在历史里也不在增量里 | 不重 | 错。这是最常见写法，也是第二个故障「聊天记录缺一段」的直接来源 |
| 先订阅增量，再补拉历史 | 不漏 | **会重**：补拉窗口与增量窗口必然重叠 | 对，但前提是客户端按消息 ID 去重 |
| 订阅时把游标交给服务端，由服务端保证从该游标起连续下发 | 不漏 | 取决于服务端实现 | 最干净，代价是服务端要留存历史（那就落到队列/存储，见[第 7 章](/message-queue-cloud/redis-stream)） |

```text
正确时序（第二种，重叠换取不丢，靠去重换不重）

t0  连接断开，本地 lastSeq = 42
t1  退避后重连成功（服务端不知道也不该知道你错过多少）
t2  立刻注册增量监听 —— 此后到达的消息先入一个待合并缓冲，不直接渲染
t3  发一次 HTTP 请求：GET /messages?room=x&after=42   （游标，不是时间）
t4  历史返回，与 t2 缓冲合并：按 seq 排序、按 id 去重、丢弃 <= 42 的
t5  渲染，把 lastSeq 更新为合并后的最大值
t6  之后的增量正常渲染，仍然按 id 做一次「已渲染」检查
```

**看明白这个设计的代价**：它是通过**故意制造重叠**来消除缺口的，而重叠意味着「同一条消息会被处理两次」。这不是 bug，这是方案。它在[第 3 章](/message-queue-cloud/reliable-delivery)有一个名字：**at-least-once + 消费端幂等**。你在本项目里已经用唯一约束钉死了重复副作用，在这里同一套语义换了个方向——只不过「副作用」是「往界面渲染一条消息」，幂等表是「已渲染 ID 集合」。

所以这一节最值得记住的一句是：**长连接只是投递通道，不是消息的存放处。**错过的消息能不能补回来，取决于它们是否落在一个有进度、可回放的地方（数据库、Stream、队列）。通道断了你可以重连，**存储没了你就只能道歉**。这条接缝在项目章里从另一个方向讲过：[把慢操作异步化](/message-queue-cloud/project)——**队列负责「不在的人」，长连接负责「现在在线的人」**。

补拉还有第二个边界：**离线多久就要补多少**。一个标签页在包里躺了三天，重连时把三天的历史全拉下来，界面卡死、请求超大。正确设计要同时给三个限制：**分页、上限、以及超限后的降级动作**（比如只补最近 200 条，其余提示「加载更早的记录」并让它按需翻页；或者干脆告诉用户「离线太久，请刷新页面」）。**「保证一条不漏」和「不能一次拉爆」是两个必须同时满足的目标**，只写前者的人会在第一个长期离线用户身上翻车。

## 服务端侧：连接表、清理与优雅关闭

- **连接表是进程内存**。这条决定了[多实例的广播问题](/realtime/scaling-out)整章——先知道边界在哪，本章不展开。
- **每个连接挂的定时器要能删**。心跳定时器、补拉缓冲、订阅集合，都在连接关闭时清掉。漏清的现象是「内存缓慢上涨，且断线越多涨得越快」；确认方法是把连接反复断开几千次，看进程内存是否回到基线。
- **优雅关闭的顺序**：先停止接受新握手 → 向已有连接发一个可识别的关闭信号 → 给一个短窗口让它们处理 → 到点强关。**顺序反了会出现「客户端收到要重连的信号时，服务端还在接新连接」，滚动发布期间连接在实例间来回抖动。**
- **在线状态是推断，不是事实**：连接表里有他，只说明「最近一个判死阈值内没听到坏消息」。任何「当前在线」「正在输入」的显示都得接受它可能是 N 秒前的世界。

## 你现在就能做的实验（不需要任何服务，本站未执行）

这一节的每一条都能在**你自己的浏览器**里十分钟内做完，而且比读三遍本章有用。本站没有环境执行，所以每条都给出「预期你会看到什么」和「它证明本章哪一句」：

1. **DevTools 切离线**：打开一个能跑的实时页面，Network 面板筛 WS，看到绿色双向箭头后，把 Throttling 切到 `Offline`（拔网线、开飞行模式是它的物理层版本）。预期：客户端侧不会立刻报错，服务端侧也不会立刻知道；发送调用照样「成功」。它证明的是「**没有字节往来时谁都不掌握事实**」。
2. **恢复在线**：等 60 秒再切回 `No throttling`。预期：连接**不会自动活过来**（服务端已经关闭；如果它没关，那就是你的判死阈值太长）。看 close 码是几、`wasClean` 是不是 `false`。这一条直接对应翻车点里 1006 的判读。
3. **切后台**：把标签页切到别的 tab 待 10 分钟再回来。预期：**你可能发现心跳明显变稀、重连滞后**——浏览器对后台页面的定时器有限制，具体限制各浏览器不同，本站未核实也不写数值。这条实验的产出是你自己那台浏览器上的真实节流行为，它是你决定「客户端心跳能不能只靠 `setInterval`」的唯一依据。
4. **故意把重连写成没有退避**：延迟固定 100ms，开 20 个标签页刷新。预期：服务端日志里同一来源高频握手——「第三个故障」的最小版本。

## 常见错误与排查

1. **现象：UI 一直显示「已连接」，但消息一条都收不到。** 原因：连接在半路被单向掐断，`readyState` 仍是 OPEN，服务端发送不报错。怎么确认：看这条连接最后一次**入站**字节的时间戳，而不是看状态字段。怎么修：判死阈值 + 到点主动 `close()` 再走重连。
2. **现象：服务端重启后 30 秒内鉴权接口全线变慢，连接数打满。** 原因：客户端无退避、无抖动、且握手路径含数据库查询。怎么确认：把重连次数与握手期间的 SQL 查询数各打一行日志，相乘。怎么修：退避 + 抖动 + 把校验改成可本地完成或有短缓存的形式 + 服务端连接上限。
3. **现象：重连后聊天记录缺了一段。** 原因：先补拉后订阅，中间那段两头都不沾。怎么确认：在补拉返回与订阅生效之间手工塞一条消息，看客户端有没有它。怎么修：反过来——先订阅进缓冲，再补拉，合并去重。
4. **现象：同一条消息在界面上出现两次。** 原因：重叠是方案的必然副产物，而你没按 ID 去重。怎么确认：给每条消息打 ID 并统计渲染次数。怎么修：维护「已渲染 ID」把重复丢掉——**别试图消灭重叠，要消灭重叠的后果**。
5. **现象：心跳与 pong 都正常，业务却不处理消息。** 原因：pong 只回到协议栈，事件循环被卡住或 handler 一直抛错。怎么确认：发一条必须执行业务动作才能应答的心跳。怎么修：两层心跳分开，业务判死用应用层那条。
6. **现象：三类「没设边界」的并发症——对配置错误无限重连、离线三天后一重连就白屏、内存随断线次数缓慢上涨。** 原因依次是：把 4xx 握手失败当网络故障重试；补拉无上限无分页；连接关闭时没清定时器与订阅缓冲。怎么确认：记录握手的 HTTP 状态码；把游标设成三天前看返回体大小与耗时；反复断开几千次看内存是否回到基线。怎么修：重连按可重试/终态分叉并直接向用户显示终态；补拉加分页、上限与超限提示；清理逻辑集中到一个幂等的关闭回调里（关闭事件可能触发两次）。

<Exercise title="把六个说法归进四层" difficulty="基础">

下面六句话分别描述的是哪一层的失联（TCP 层 / 中间设备层 / 协议层 / 应用层）？谁应当发现它、用什么手段发现？最后一问：哪一句话描述的情形**永远不会**被自动通知？

A 对端机器掉电，本机没有收到任何包。B 家庭路由器把空闲映射回收了，去程字节消失。C 收到 ping 但 pong 没回来。D 对端进程活着但事件循环被一个大任务占满。E TCP 收到一个 RST。F 连接显示 OPEN，但三分钟内没有任何入站字节。

<template #answer>

A：TCP 层，且**没有任何自动通知**——这正是「只能靠应用层主动证明双向可达」的依据。B：中间设备层，靠「一段时间没收到字节」推断，或用小于其空闲超时的保活间隔避免它发生。C：协议层，pong 缺失就是判死信号。D：应用层——这一层 **pong 会正常回来**，控制帧心跳测不出它，必须用带业务动作的心跳。E：TCP 层里本机能立刻知道的那种。F：不属于某一层，但它是应用层唯一可用的证据（最后一次入站字节的时刻），判死阈值就该挂在这里。

唯一「永远不会自动通知」的是 A。整章的设计前提就是这一句：**不要为「会被通知」设计，要为「只能自己推断」设计。**

<Exercise title="找出这份心跳重连实现的缺陷" difficulty="进阶">

某客户端代码，注释里标了 A/B/C/D 四处：

```text
A: const PING_MS = 300000;            // 每 5 分钟发一次应用层心跳
B: setTimeout(connect, 1000);         // 断开后固定 1 秒重连，一直试
C: GET /history?since=<Date.now()>    // 重连后按当前时刻补拉
D: 收到消息就直接 append 到列表末尾     // 渲染路径
```

指出四处各自的后果，并说明每一处会在哪个故障实验里暴露（本章第 8 节编号）。

<template #answer>

A：5 分钟的心跳间隔通常**长于链路上最短的空闲超时**，保活目的直接落空；判死滞后更是达到十几分钟，在线显示彻底失真。暴露方式：实验 1/2 ——切离线后你几乎不可能及时发现。

B：固定间隔 + 无限重连 = 两个问题叠在一起。没有指数退避与抖动，服务端重启时全体客户端在同一秒回来，形成风暴；而「一直试」意味着终态错误（鉴权失败、Origin 被拒）也会被永久重试。暴露方式：实验 4（20 个标签页把握手打满）；终态那半要靠记录握手状态码才能确认。

C：用**时间戳**当游标，边界必然出问题——多实例时钟不同步、时钟校正、同一毫秒内产生的消息被 `>` 排除掉。这就是「先补拉后订阅会漏」之外第二种漏法，而且是静默的。暴露方式：在补拉与订阅之间手工插一条消息（实验 3 的加强版），再对比列表与服务端真实记录。

D：没有按消息 ID 去重，而正确设计必然产生重叠（先订阅再补拉），所以每条离线期间的消息都会出现两次。暴露方式：断网 10 秒期间让对方发三条消息，重连后数列表里有几条。

四处对应本章四节各一条主张：间隔要由最短超时决定、退避是为了服务端活着、游标必须是序号、重叠必须配去重。

</template>

</Exercise>

<Exercise title="设计一个离线三十秒不丢、离线三天不炸的恢复协议" difficulty="挑战">

为一个房间聊天场景设计客户端与服务端的完整协议：连接可能随时断，用户可能离线 30 秒也可能离线三天。要求给出（1）游标的形态与放置位置；（2）连接建立到恢复完成的步骤顺序；（3）三个数值上限以及它们的取值依据；（4）重复与漏取各自靠什么消除；（5）哪些环节需要真实环境才能验证。写完后指出你这份设计里最容易被反驳的一点。

<template #answer>

一、**游标**：每个房间一个单调递增整数序号（由服务端在写入消息时分配，与消息落库同一事务），客户端为每个房间各存一份「已渲染到的最大序号」，放在 IndexedDB 或 localStorage 而不是内存——离线三天的前提就是它必须比页面活得久。**不用时间戳**，理由同练习二的 C。

二、**顺序**：连接建立 → 带上每房间游标发起订阅（增量先入缓冲）→ 对每个房间发一次补拉（`after=游标`）→ 历史与缓冲按 ID 去重、按序号排序合并 → 更新游标 → 冲刷缓冲开始正常渲染。**订阅一定在补拉之前**，宁可重叠。

三、**三个上限**：单次补拉条数（例：200 条）；每房间可回放窗口（例：保留最近 7 天，超窗只给「记录太早，请刷新」）；重连尝试（例：最多 8 次，退避封顶 30 秒，累计约 2 分钟后放弃并降级为轮询一次状态）。取值依据必须是**可核对的对象**：单条消息平均字节 × 200 要小于一个响应体预算；回放窗口的长度等于「你愿意为历史数据付多少存储」；重连上限等于「你愿意让一个用户多久之后看到真实提示」。写成数字，不要写成「适量」。

四、**重复靠 ID 去重**（客户端「已渲染 ID」+ 服务端写入时的唯一约束，与[幂等那章](/data-storage/session-rate-limit-idempotency)同构）；**漏靠订阅先于补拉的重叠消除**。如果服务端能在订阅时直接从给定游标连续下发，第 2 步可以省掉 HTTP 补拉，但那要求服务端留存历史——那就变成存储问题，参见[Redis Stream](/message-queue-cloud/redis-stream)与[投递语义](/message-queue-cloud/delivery-semantics)。

五、**需要真实环境才能验证的**：中间设备的最小空闲超时（要真实链路）、后台标签页的定时器节流（要真实浏览器且要放后台）、三天离线后的补拉体积与耗时（要有真实历史数据量）、连接数上限与拒绝行为（要多实例或压测）。**可以在你机器上现在就验证的**：顺序对不对（手工在补拉与订阅之间塞一条消息）、去重生效（数重复条数）、退避曲线（把时间打印出来即可）、上限触发后的降级提示（把游标改老即可造出三天）。

**最容易被反驳的一点**大概是第 2 步的重叠策略：它假设「历史与增量能安全合并」，但消息一旦被编辑或删除，按 ID 去重就不再等价——客户端可能已经渲染过 v1，补拉回来的是 v2，而缓冲里还有 v1。**一个诚实的答案要么给消息加版本号并按版本合并，要么明确声明本设计不支持编辑/删除，并把它写成协议的已知限制**——把限制写出来，比假装它不存在安全。

</template>

</Exercise>
