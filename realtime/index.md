## 这个领域解决什么问题

HTTP 的请求-响应模型有一个根本约束：**服务器不能主动给浏览器发消息**。浏览器问一句，服务器答一句，答完连接上的这一轮就结束了。可你的产品里有一大类需求恰恰是「服务器有话要主动说」：

- **聊天功能**：对方发来消息，你的页面要立刻显示，而不是等你刷新。用轮询（每隔几秒请求一次「有新消息吗」）实现的话，1000 个在线用户意味着每几秒 1000 个几乎全是「没有」的无效请求——延迟和成本都不可接受。
- **实时通知**：部署完成了、订单状态变了、有人评论了你，通知铃铛上的红点要自己亮起来。
- **协同与状态展示**：「谁正在输入」「当前在线人数」「协作文档里别人的光标位置」。
- **AI 流式输出**：大模型逐 token 生成，你要边生成边显示，而不是等 30 秒后一次性蹦出全文。这是本领域知识在当下最高频的应用场景。

实现这些功能，你会在三个技术方案之间做选择：轮询（polling）、服务器发送事件（SSE，Server-Sent Events）、WebSocket。选错了会付出真实代价：用 WebSocket 做纯单向的 AI 流式输出是过度设计；用轮询做聊天是浪费与延迟双输；不知道 SSE 天然自带断线重连而 WebSocket 要自己实现心跳重连，你会在多写几百行代码之后才发现。

还有一个部署层的坑在等着你：**WebSocket 连接经过 Nginx 反向代理时，如果没配协议升级相关的头部，握手会静默失败**——浏览器报 1006 之类看不出所以然的错误，本地直连却一切正常。这类「本地好的、上线就坏」的问题，正是本领域要提前拆掉的。

## 前置知识

- [后端开发](/backend/)——你需要能用 Fastify 写 HTTP 服务、理解请求生命周期，本领域的服务器端实现全部构建在这些能力之上。
- [Linux](/linux/)——需要第二期水平中的 Nginx 部分：反向代理、配置结构、日志。本领域有一整章讲 Nginx 代理 WebSocket 的配置，不懂 Nginx 基本盘会寸步难行。

另外两点软性依赖：[计算机基础](/computer-science/)的网络章节（TCP、HTTP）能让你理解 WebSocket 握手为什么长那个样子，但不阻塞本领域学习；如果项目涉及多实例部署，[数据存储进阶](/data-storage/)的 Redis 部分会在第 9 章被引用。

## 学习顺序建议

**严格按 1 → 11 顺序学。** 这个领域的章节依赖链比多数学领域更紧：

- 第 2、3 章（两个协议）必须先于第 4 章（对比选型）——没分别实现过就对比，只会背结论。
- 第 5 章（心跳重连）必须在你写完第一个能跑的 demo 之后学，否则你无法体会「假死连接」是真的会发生。
- 第 7 章（Node 实现）依赖第 2、3 章的协议理解；第 8 章（Nginx）依赖第 7 章有东西可代理。
- 第 9 章扩展性放在很后面是刻意的：**在单机单实例就能服务你全部用户的阶段，不要提前为分布式设计**。学它是为了知道边界在哪，不是为了立刻用上。

第 10 章与 [AI 应用开发 · 流式响应与前端渲染](/ai-apps/streaming) 是**同一件事的两半**：本领域只管传输与生命周期（三段链路、缓冲与首字延迟、超时不等式、取消传播、为什么这段流不能重放），事件怎么解析、增量怎么渲染、停止按钮的契约、应用层错误分类全部在 AI 领域那一章。先学哪边都可以，两边互相引用、刻意不重复。

**当前进度**：第 1–4 章（需求与 HTTP 边界、WebSocket、SSE、选型）构成第一个闭合的知识层——学完你能判断「要不要长连接」和「要哪一种」；第 5 章（心跳与断线重连）与第 9 章（多实例的广播问题）合起来是第二个知识层：**一条长连接会怎么死、怎么恢复，以及当连接分散在多个进程里时「发给谁」这个问题怎么答**。这两章曾放在同一批上线，因为它们共用同一套可靠性语义（重叠投递 + 幂等），而那套语义在[消息队列领域的第 3、5 章](/message-queue-cloud/reliable-delivery)与它的[阶段项目](/message-queue-cloud/project)里讲得最透。

第 6、7、8 章已经上线，它们是第三个闭合层——**实现链**：一张表（房间与在线状态）、一层进程（Node 侧库与框架的分界）、一层部署（代理、超时与上线验证）。这三章必须按这个顺序读，因为它们的依赖是单向的：没有第 6 章那张表，第 7 章「库到底替你做了什么」就无从对照；没有第 7 章那个同端口共存的形状，第 8 章就退化成两份要分别验证的代理配置；而第 8 章的不等式要用第 5 章的判死阈值当变量。

第 10 章与 AI 领域那一半是**同批写的**，边界就在动笔前定下：传输、生命周期、断连行为归本领域，模型 API 的事件解析、前端消费、取消与错误处理归 [AI 应用开发](/ai-apps/streaming)。两章各自在开头声明了另一半归谁，同一套推导只出现在一边——首块延迟实测、超时不等式、取消传播的成本表只在第 10 章，跨块解析三组实测、UTF-8 切开、渲染节流算术与「停止」的三件事只在 AI 那一章。[第 11 章阶段项目](/realtime/project)已上线，本领域到这儿闭合：需要 Nginx 与 VPS 才能验收的部分，和能在本机跑到底的部分，在那一章里是分开放在两张清单上的，本站没跑过的条目一律没写「实测」。

**本领域的核实边界**：第 6 章那组循环计时与算术模拟是**本机 Node v25.4.0 真跑出来的**（脚本在 `realtime/.scratch/`，参数与种子在章内公开），它测的是形状，不是任何库或产品的吞吐。第 10 章的首块延迟、断开传播与成本那几组同样出自本机零依赖合成流脚本（`realtime/.scratch/ai-stream-lifecycle.cjs`，逐字输出留在同目录），样本是本站构造的合成上游，**没有连接任何厂商 API、没有网络请求**；该章的服务端代码是结构示意，本批未安装依赖、未启动服务。第 7、8 章涉及库与代理的具体行为时，本站**没有安装任何依赖、没有启动过任何服务、没有 Nginx 环境与云账号**，因此两章的代码是结构示意、配置结论分档标注为「站内已核实 / 机制推导 / 请你现场核对」；写作者尝试抓取外部文档核对类名与默认参数时请求全部被环境拦截，这一点已逐字写进各章开头的「本章的核实边界」。第 11 章的数字同样是本机跑出来的：握手响应哈希、帧头的三种长度形式、一条 600 字节消息被切成三帧、关闭码规则、房间表悬挂计数、广播扇出与竞争消费、在线状态滞后、背压斜率、先订阅后补拉的重复条数，全部出自零依赖脚本 `realtime/.scratch/ws-codec.cjs`（逐字输出留在同目录），不联网、不启服务、不绑端口；而 Nginx 代理、HTTPS、真实 VPS、浏览器开发者工具那几条**本站没有环境，一律标注为需要真实环境**。现在本领域 11 章全部上线，正文里的「见第 N 章」都已带链接。

## 学习方法

**环境准备（Windows）**：

- Node.js LTS + TypeScript，浏览器用 Chrome/Edge（开发者工具 Network 面板可筛选查看 WebSocket 连接的帧内容，这是本领域最重要的调试工具）。
- 本地开发阶段不需要任何额外服务：`ws` 库一个 npm 依赖即可起步。**不要一上来就用 Socket.IO**——它会用自动重连和降级机制把协议细节全部藏起来，你会「做出来了但没学到」。先用 `ws` 裸写一遍，再回头看 Socket.IO 帮你做了什么。
- 进入第 8 章后需要 Nginx 环境：可以用 Docker Desktop 起一个 Nginx 容器模拟，但**强烈建议最终在真实 VPS 上再走一遍**——代理超时、HTTPS 下的 `wss://`、防火墙这些只有真实环境才暴露。VPS 准备参照 [Linux 领域](/linux/)。
- 模拟弱网：浏览器开发者工具自带网络节流（throttling）与离线（offline）切换，第 5 章的重连测试全靠它；这是本机就能做、但多数人从不做的练习。

**练习原则**：每个协议先手写最小实现（服务端 + 浏览器客户端各 30 行左右），跑通后再加功能。「最小实现先跑通」在本领域尤其重要，因为 WebSocket 的故障模式（握手失败、代理截断、假死）在最小实现里最容易定位。

## 阶段项目

**实时聊天室**：一个部署在你自己 VPS 上的多房间聊天室，验收标准：

- [ ] 支持多个房间，用户可选择加入；消息实时到达房间内所有连接，不需要刷新
- [ ] 显示每个房间的在线人数；一个用户断线后，人数在心跳超时阈值内更新（阈值取值要能说出理由）
- [ ] 客户端断网重连：手动切断网络 30 秒后恢复，客户端自动重连（指数退避），并重连后通过一次 HTTP 请求补拉离线期间的消息，聊天记录无缺口
- [ ] 服务端基于 Node + `ws`（或说明为什么选 Socket.IO），与 Fastify 服务共存于同一部署
- [ ] 经 Nginx 反向代理 + HTTPS 对外提供服务，`wss://` 连接正常；能展示对应的 Nginx 配置并解释每一行升级相关指令的作用
- [ ] 用浏览器开发者工具截图证明：握手请求返回 101、消息以帧的形式双向流动
- [ ] （可选加分）实现一个「服务器公告」功能，用 SSE 而不是 WebSocket 推送，并在 README 里解释这个选择的理由

## 版本说明

- **协议层**：WebSocket 基于 RFC 6455（2011 年定稿，此后无破坏性变更），SSE 是 WHATWG HTML 现行标准的一部分（Living Standard）。两者都属于「定稿后极稳定」的技术，时效性风险低。
- **`ws` 库**：以 npm 上最新稳定大版本为准，本站不锁定版本号；其 API 多年保持稳定，大版本升级主要涉及 Node 版本要求。
- **Socket.IO**：文档以 v4 系列为准（编写时的当前主线）。注意 Socket.IO 的客户端与服务端主版本需要匹配，升级前先读其官方兼容说明。
- **Nginx**：以发行版仓库最新稳定版为准，本文引用的指令（`proxy_http_version`、`proxy_set_header`、`proxy_read_timeout`）在 1.x 全系可用。
