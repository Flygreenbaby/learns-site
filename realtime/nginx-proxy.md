# Nginx 代理 WebSocket：代码全对、拓扑也只有一条，握手还是死在中间那层

第一个故障的诡异之处在于「前后端都说是对方」。浏览器控制台只有一行 `WebSocket connection to 'wss://…' failed … code 1006`，没有 HTTP 状态码；后端日志里**连一条握手记录都没有**。加 Nginx 之前一切正常。根因是这条链路中间多了一个默认行为完全不同的转发者：代理按 HTTP 语义转发，而 `Upgrade` 和 `Connection` 是逐跳头，默认不会传给上游——于是你的实时服务收到的是一个普通 GET，它不该回 101，也就永远不会有连接。这一层的机制与逐字官方配置在 [Linux · Nginx](/linux/nginx) 那一节已经核实过（包括本站用 Node 写两条转发路径复现出的「A 组上游收不到 `Upgrade` 头 → 客户端拿到 400；B 组透传 + 保持 HTTP/1.1 → 客户端拿到 101，升级后 21 字节裸帧逐字节一致」），本章不重复那部分推导，只做实时服务特有的四件事：**把这一层的每个头对应到它会坏掉的哪种现象；把超时链与心跳取值接上；把 SSE 的缓冲问题落到配置行上；给你一套上线前 15 分钟能跑完的验证顺序。**

第二个故障上线两周后才出现：白天正常，晚上没人用的时候连接莫名其妙断，客户端重连之后又好了。查的是 `proxy_read_timeout` 默认 60 秒——**它在「这段时间内没读到上游字节」时就掐连接**，而你为了省流量把心跳间隔设成了 120 秒。这一条的关键不是「把超时调大」，而是「间隔必须由链路里最短的那个空闲超时决定」，本章第四节把它写成一条可算的不等式。

第三个故障是 SSE 的：本地 `curl -N` 一条条准时到，经过代理之后变成「一批一批到」，**没有任何错误**。缓冲不是失败，是延迟，所以它不会出现在任何监控里，只会出现在用户体验里。

## 先说清这一层为什么在你的架构里

一个 VPS 上的典型形态是：Nginx 监听 80/443，终止 TLS，转发给同机的 Node 进程。实时服务因此获得三样东西和一样代价：证书与域名只有一份、静态资源与 API 与实时端点共用端口、可以有多个上游服务；代价是**你的 WebSocket 连接的每一次握手、每一段空闲、每一个字节都要穿过一个不理解「长连接」的转发者**（除非你为它单独开端口并单独配证书）。第 7 章那个「同端口共存」的选择，正是为了让这条链路只有一条要验证。

理解下面这张表，本章剩下的部分都是它的推论：**升级之后 Nginx 退化成一条裸字节管道**，所有 HTTP 层的能力（gzip、限流、`add_header`、缓存）对已升级的连接全部失效。这意味着你在 Nginx 上为 WebSocket 做的事，只有握手那一刻有效。

## 逐个头：谁默认被改，谁必须显式写

握手是一次带 `Upgrade: websocket` 的 GET。经过代理时每个字段的默认命运不同，而排障时你要能说出「缺哪一行对应哪个现象」：

| 字段 | 默认行为 | 缺了/错了会怎样 | 上游怎么确认 |
| --- | --- | --- | --- |
| `Upgrade` | **逐跳头，默认不转发** | 上游看不到它，就不回 101；浏览器读成 1006，后端日志里没握手 | 上游打印收到的头（Linux · Nginx 那节就是这么复现的） |
| `Connection` | 同上，且代理到上游通常写死为 `close` | 只有 `Upgrade` 没有它，握手照样失败 | 同上，两个头要一起看 |
| 请求版本 | 代理默认按 HTTP/1.0 转发 | HTTP/1.0 里没有 `Upgrade` 语义，且强制短连接 | 打印请求行：`GET /ws HTTP/1.0` 就是这一条 |
| `Sec-WebSocket-Key` | 属于 WebSocket 握手字段，正常应透传 | 被吃掉时上游算不出 `Accept`，客户端校验失败 | Linux · Nginx 那节 A 组输出显示它「被代理吃掉了」 |
| `Host` | 默认被改写为 `proxy_pass` 里写的那个字 | 上游做虚拟主机/绝对 URL 生成时会错 | 打印 `req.headers.host` |
| `X-Forwarded-For` / `-Proto` / `-For` | **不自动加**，要你自己写 | 上游看到的客户端 IP 全是 127.0.0.1，限流与审计失效 | 上游打印这三项；`wss` 下 `-Proto` 必须是 `https`，否则应用会以为自己是明文 |
| Origin | 透传，但**没人替你校验** | 跨站 WebSocket 劫持的入口（第 2 章） | 握手日志里记下 Origin，验证你确实做了白名单 |

配置形状。`map` 那两行与「写死 `Connection: upgrade` 会让普通请求也带这个头」的原因，Linux · Nginx 一节已逐字核实过官方给法；这里只补实时服务必须自己决定的三项（超时、SSE 关缓冲、握手路径独立于普通 API）：

```nginx
# 放在 http {} 里：没有 Upgrade 头时把 Connection 写成 close，有则写 upgrade
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 443 ssl;
    server_name app.example.com;

    # 实时端点：握手 + 空闲超时
    location /ws {
        proxy_pass http://127.0.0.1:3000;
        # 官方配置里那行 proxy_http_version 1.1; 的注释是版本相关的（见 Linux · Nginx 逐字引用）
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_read_timeout  120s;      # 必须 > 你的保活间隔，见第四节的不等式
        proxy_send_timeout  120s;
        proxy_connect_timeout 5s;      # 这条管「连不上上游」，与空闲无关
    }

    # SSE 端点：透传不是问题，缓冲才是
    location /events {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_buffering off;           # 或者让上游发 X-Accel-Buffering: no
        proxy_cache off;
        chunked_transfer_encoding on;  # 事件流是分块传输的
        proxy_read_timeout 120s;
    }
}
```

`proxy_http_version 1.1` 这一行要不要写、在你的版本上默认是什么，**是版本相关事实**：官方那段配置里带着一条注释说明它适用于哪个版本之前，本站在 Linux · Nginx 一节逐字引用过那条注释，本章不复述版本号判读。**上线前请对照你所用 Nginx 版本的官方文档确认一次**，并把结论写进你的部署说明。这是本章唯一一处「你必须自己核对才能配」的地方，其他行都不依赖版本。

## 升级之后，你以为生效的东西其实都失效了

101 之后代理只搬字节。三条直接后果：

**压缩无效。** 已升级的连接不走 `gzip`——而 Nginx 的 `gzip_types` 默认只含 `text/html`（该默认值在 Linux · Nginx 一节已核实），所以「我给 WebSocket 开了 gzip」这件事在两个层面都不成立。要压消息体就在应用层自己压（二进制帧里带压缩后的字节），代价是 CPU 与可读性。

**限流与鉴权只在握手有效。** `limit_req` 作用在请求上，一条活了一小时的连接对它是「一个请求」。这条的真实含义是：**你的实时服务内部要有消息级限流**，代理给不了；原理与[会话、限流与幂等](/data-storage/session-rate-limit-idempotency)同一条，只是维度从请求变成消息速率。反过来这也说明重连风暴为什么危险——第 5 章那个「滚动发布后 4 秒内 5,000 次握手」的事故里，握手是真实请求，`limit_req` 这时才管用，它可以保护你的鉴权路径不被打穿（配置写法与 `burst` 的真实语义见 Linux · Nginx 的限流一节）。

**`add_header` 与缓存对已升级连接无效，对 SSE 有效——而「有效」在这里是坏事。** SSE 就是一个还没写完的普通 HTTP 响应（第 3 章），它会吃到代理的响应缓冲、也可能吃到 `proxy_cache`。缓冲让消息成批到达，缓存让事件流被当成可复用内容——后者比前者严重得多，因为它可能把「上一个用户的流」发给下一个请求。所以 SSE 的 location 上 `proxy_cache off` 与关缓冲两件事都要做。

## 空闲超时不等式：心跳与代理的唯一正确关系

排障里最容易搞混的两个数，一个决定「谁先掐」，一个决定「你多快知道」：

```text
proxy_read_timeout     = 代理在「多久没读到上游字节」之后关闭这条连接
判死阈值 = 保活间隔 × 容忍次数 = 你的应用判断「对方没了」所需的时间
```

两者不是同一个东西，也不该互相调成一样大。正确的关系是一条不等式：

```text
保活间隔  <  链路上最短的空闲超时（Nginx 的 proxy_read_timeout、云负载均衡的 idle timeout、
            移动网络的 NAT 超时、公司出口防火墙的会话超时，取最小值）
proxy_read_timeout  >  保活间隔 × 一个安全系数（至少 2，别踩着）
```

第一条不满足，就会出现第二个故障：连接被中间层以「空闲」为由掐掉，而你的应用以为一切正常。`proxy_read_timeout` 官方默认 60 秒（Linux · Nginx 一节核实），这一条意味着**任何大于 60 秒的心跳间隔默认都会撞上它**——所以官方在同一页给出的建议是「由被代理服务定期发 ping 帧保活」，本站把超时压到 300 ms 复现出「握手成功但空闲即断」的现象也证实了这条机制。第二条不满足则是反向事故：把 `proxy_read_timeout` 调成 3600 秒而心跳间隔 60 秒，半开连接一直占着 worker 与上游的连接额度，这跟 Linux · Nginx 一节的结论一致——**优先用应用层心跳，别把超时调到 1 小时**，那只是让死连接更晚被发现。

链路上「还有谁在掐连接」这件事不能靠猜，只能靠测。判据：**断开时刻是否随你改的某个参数移动**。方法见第六节实验 3。云厂商负载均衡的空闲超时是这一层最常见的隐形来源，本站没有云账号，**本章不写任何厂商的默认秒数**——请以你控制台里那一项的当前值为准，并把它写进部署说明，因为「谁在掐」必须可追溯。

## 混合内容、明文回环与证书这一层

页面是 `https://`，脚本里写 `ws://`，浏览器会直接拒绝（混合内容），报错形态和第 2 章那个 1006 不同：它在控制台里明确说「不安全」。规则只有一句：**页面加密，连接就必须是 `wss://`。** 而 TLS 在 Nginx 终止时，Nginx 到上游那一段走明文 `ws://` 是可以的（第 2 章已核实这条），前提是上游只监听回环地址——`127.0.0.1:3000` 而不是 `0.0.0.0:3000`。这条前提要真的检查：上游一旦对公网监听，明文段就从「同机回环」变成「可被抓包的网络」，凭据与消息都暴露。

握手阶段的凭据不能依赖 `X-Forwarded-*` 之外的东西，也别让实时端点从 URL query 里读长期 token（会进 access log，第 2 章说过）。证书本身、`ssl_certificate` 挂法、续期定时器怎么确认真的在跑，都在 [Linux · Nginx](/linux/nginx) 的 HTTPS 一节，本章不重讲；只补实时服务特有的一点：**证书续期失败的表现之一是「WebSocket 连不上而网页还能打开」**，因为浏览器对已打开页面缓存了连接，而新握手会因证书过期被拒。把 `wss` 握手放进你的续期后检查清单，理由就在这里。

## reload 与发布：这一层的长连接不会跟着配置走

`nginx -s reload` 之后旧 worker 会处理完存量连接再退出。对短请求无所谓，对一条活几小时的 WebSocket 就有两个后果：旧 worker **长期不退出**（占着内存与 fd），以及你新旧两套配置在同一时刻都活着。这一节本批未逐字核对官方对 worker 退出的描述，请以「controlling nginx」相关页面为准并**在你的环境实测一次**：改一个可观测的配置项、reload、然后看旧 worker 什么时候消失。如果需要它到点必须退出，Nginx 有 `worker_shutdown_timeout` 这一类指令，本站未核对其语义与默认值，动手前先查文档再配。

真正会打掉连接的是上游重启：那时按第 5 章那条做——上游在 `SIGTERM` 里先广播 1001 再退出，客户端看到 1001 立刻重连而不是长退避。代理层不需要为这件事配任何东西，但它需要能观察到：**发布窗口内握手数会集中爆发**，这正是第四节里 `limit_req` 保护鉴权路径的场景。

## 上线前的验证顺序（15 分钟，本站未执行）

顺序不能换，因为每一步排除一个变量。你需要两个东西：`curl` 与浏览器开发者工具的 Network 面板（筛 WS）。

| 步 | 命令 / 动作 | 预期 | 不通过说明什么 |
| --- | --- | --- | --- |
| 1 | `curl -i -N http://127.0.0.1:3000/ws -H "Connection: Upgrade" -H "Upgrade: websocket" -H "Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==" -H "Sec-WebSocket-Version: 13"` | 首行 `HTTP/1.1 101 Switching Protocols`，且有 `Sec-WebSocket-Accept` | 上游自己就不回 101：代码问题（路径、版本头、鉴权），**先别碰 Nginx** |
| 2 | 同一条命令打到域名（经代理） | 同样 101 | 上游 101 而代理不 101 ⇒ 就是透传那几行；这一步和第 1 步的差值就是本章的全部内容 |
| 3 | 浏览器建立连接后静置，从连接建立计时到断开 | 不断开，或断开时刻 = `proxy_read_timeout` 且随你改它而移动 | 断开且不随参数移动 ⇒ 链路上还有另一个空闲超时（云 LB / NAT），改小保活间隔 |
| 4 | 发一条业务消息，两侧各看一次 | 帧能读成你定义的消息；`X-Forwarded-Proto` 在上游是 `https` | 上游拿到 `http` ⇒ `-Proto` 没写对，应用层的 URL 与 Cookie `Secure` 判断会错 |
| 5 | 用普通 HTTP 请求打同一个 location | 正常响应，不被 `Connection: upgrade` 污染 | 说明 `map` 生效；写死头的配置在这里必炸 |
| 6 | SSE：直连上游端口与经代理各测一条消息的到达时间 | 两边接近；经代理明显成批 ⇒ 缓冲 | 缓冲没关；先看 `X-Accel-Buffering: no`（MDN 的 SSE 示例就是这个头，第 3 章已核实），再确认该路径没有被压缩（`Content-Encoding`） |
| 7 | `nginx -t` 通过并 reload 之后，重跑第 2 步 | 仍 101 | 防止「改了没生效」（旧 worker 还在服务，或改的是另一个 server 块） |

第 2 步与第 1 步的对照是这一章最有价值的一次动作：**同一条命令，两个目标，差异只可能是代理。** 很多人跳过它，然后花一天在协议语义里找一个部署问题。

## 常见错误与排查

1. **现象：浏览器 1006，后端日志里没有握手记录。** 原因：`Upgrade`/`Connection` 没透传，或代理按 HTTP/1.0 转发。怎么确认：跑验证第 1、2 步，比较两次首行；或让上游打印收到的请求行与两个头。怎么修：`proxy_http_version 1.1` + 两个 `proxy_set_header` + `map`。
2. **现象：本地正常，经域名后「消息能到但成批到」。** 原因：代理响应缓冲（SSE 最常见）或压缩层攒块。怎么确认：直连上游与经代理各测一次到达时间；看 `Content-Encoding`。怎么修：`X-Accel-Buffering: no`、该 location `proxy_buffering off`、对 `text/event-stream` 关压缩。
3. **现象：空闲几分钟后固定断开，白天正常深夜也断。** 原因：`proxy_read_timeout`（默认 60 s）短于你的保活间隔，或链路上另有更短的空闲超时。怎么确认：断开时刻是否随 `proxy_read_timeout` 移动。怎么修：把间隔压到最短空闲超时之下，并让 `read_timeout > 间隔 × 2`；**不要**把超时调到 1 小时来「解决」它。
4. **现象：上游日志里所有客户端 IP 都是 127.0.0.1，限流和审计失效。** 原因：`X-Forwarded-For`/`X-Real-IP` 没配，或应用不解析它们。怎么确认：握手时打印这三项。怎么修：加上那两行，并在应用里取真实来源；**注意别把这个头当可信来源**（直连时客户端可以自己伪造），信任链见 [服务器安全](/linux/server-security)。
5. **现象：`https` 页面里 WebSocket 连不上，控制台说混合内容。** 原因：脚本写死 `ws://`。怎么确认：看控制台的报错类型（混合内容有专门措辞，与 1006 不同）。怎么修：按页面协议推导——`location.protocol === 'https:' ? 'wss' : 'ws'`，别把 scheme 写进配置常量。
6. **现象：改了配置没变化。** 原因：命中的是另一个 `server` 块（`server_name` 决定谁接住请求）或另一个前缀更长的 `location`；也可能是旧 worker 还在服务存量连接。怎么确认：`nginx -T` 看最终生效配置里有没有你那一行；新建一条连接测，别用存量的。怎么修：`location` 优先级与匹配顺序在 Linux · Nginx 那节讲透了，按那节判。
7. **现象：发布时瞬时大量重连，鉴权接口被打挂。** 原因：全员重连是长连接发布的固有现象，握手是真请求。怎么确认：看 `limit_req` 的拒绝计数与握手 QPS 曲线。怎么修：上游先发 1001 让客户端有序退避（第 5 章），必要时对握手路径限流；这属于容量决定，不属于配置技巧。

<Exercise title="把七个现象配到正确的配置行" difficulty="基础">

现象：① 1006 且后端无握手记录；② 消息成批到达；③ 空闲整 60 秒断开；④ 客户端 IP 全是 127.0.0.1；⑤ 控制台报混合内容；⑥ 普通 API 请求带上 `Connection: upgrade` 后行为异常；⑦ 发布瞬间鉴权接口 5xx。

为每个现象指出该改哪一行（或哪一类配置），并说明它属于「握手透传」「缓冲」「超时」「转发信息」四组里的哪一组。

<template #answer>

① `proxy_http_version` + 两个 `proxy_set_header` + `map`——**握手透传**。② `proxy_buffering off` 或让上游发 `X-Accel-Buffering: no`，外加对 `text/event-stream` 关压缩——**缓冲**。③ `proxy_read_timeout` 与保活间隔的关系（第四节那条不等式）——**超时**。④ `X-Forwarded-For` / `X-Real-IP` 加上应用侧解析——**转发信息**。⑤ 前端按页面协议推导 scheme：这一条**不在 Nginx 上**，它属于「链路之外」，是七条里最容易被配错层的一条（把它当成 `listen ssl` 的问题去查，会查很久）。⑥ 把 `Connection: upgrade` 写死而没有 `map`——**握手透传**的反向表现：普通 API 请求也带着这个头去上游。⑦ 不是配置错误，是容量：`limit_req` 保护握手路径 + 上游发 1001 让重连有序——四组之外，属发布设计，硬塞进「超时」是概念错误。

判据一句：①⑥ 只在**握手那一刻**发生，②③ 在**连接存活期间**发生，④⑤ 在**链路之外**发生，⑦ 在**发布窗口**发生。能把七个现象先分到这四个时段里，排查时间会掉一个量级。

</template>

<Exercise title="算出你的保活间隔并证明它成立" difficulty="进阶">

已知：`proxy_read_timeout` 用默认 60 秒（本站已核实这是官方默认）；你的云端负载均衡空闲超时你**不知道**；移动网络 NAT 超时通常远小于 60 秒但具体值不可查。请：① 写出你的保活间隔上界与推理过程，不许写「设成 30 秒比较稳妥」；② 说明你如何用一个实验**证明**「掐连接的是 Nginx 还是那个未知的负载均衡」，写清观测量和判断标准；③ 若结论是负载均衡在掐，你有哪两条修法，各自代价是什么（一条改配置、一条改应用）；④ 你的判死阈值会不会因此变动，为什么。

<template #answer>

一、**上界**由「链路上最短的空闲超时」决定，而你目前唯一知道的确切值是 `proxy_read_timeout` 的 60 秒（本站已核实这是官方默认），移动 NAT 通常更短且不可查。所以间隔必须**显著小于 60 秒**，写法要成推理链：「先按远小于 60 起（例如 20–25 秒），再用第二问的实验把上界收紧」，并让 `read_timeout > 间隔 × 2` 真的成立。把「设成 30 秒比较稳妥」交上去，等于没做这道题——它没有说明 30 是被什么约束的。

二、**观测量是断开时刻是否随 `proxy_read_timeout` 移动**。把它改成 30 秒再测一次：断开点跟到 30 秒附近 ⇒ 是 Nginx；始终在某个固定秒数断开且与该参数无关 ⇒ 是链路里另一个空闲超时在掐。再加一组正交证据：把保活间隔压到 10 秒，如果从此不断开，就证明触发条件是「空闲」而不是「连接存活总时长」——这两类掐法的修法完全不同，值得花两分钟区分。

三、两条修法与代价：**改配置**（调大 `read_timeout`）代价是半开连接更久地占着 worker 与上游的连接额度，第四节明确反对把它当主修法；**改应用**（缩短保活间隔）代价是每秒帧数与定时器数量上升，第 5 章那组心跳算术就是这笔账，而且间隔变短通常会让判死滞后也变短（要保住滞后就得加大容忍次数）。链路里那个未知数你改不了，所以第三条路是「接受它，把间隔压到它之下」——这是唯一不需要他人配合的方案。

四、**会变**。间隔是判死阈值的乘数，间隔被链路压小之后只有两种选择：加大容忍次数（保住滞后，代价是判死更不精确）或接受滞后变短（帧数上升）。这个取舍必须写成产品决定而不是运维参数——第 6 章那句「把这条等式交给运维拍脑袋定，就是故障二的成因」在这里同样成立。

</template>

</Exercise>

<Exercise title="写一份上线检查说明并让它能被反驳" difficulty="挑战">

你要把实时聊天室（第 11 章）部署到 VPS：Nginx + HTTPS + 一个 Node 进程，端口 3000 监听 `0.0.0.0`。写一份不超过 300 字的上线检查说明，包含：① 验证顺序（不许照抄本章那张表，要写出为什么这个顺序排除变量）；② 你必须现场核对而不能照抄本章的**两处**内容，各写出核对入口；③ 一个上游监听地址带来的具体风险与修法；④ 发布窗口会发生什么，你提前告诉用户什么；⑤ 这份说明里最可能被打脸的一条。

<template #answer>

评分只看六件事。一、**顺序必须先上游后代理**：第 1 步不过就说明代码自己就不回 101，此时碰 Nginx 只是在制造第二个问题；第 1、2 步的**差值**才是代理问题——写出这条逻辑，比背下七步更值钱。之后再排空闲与转发信息，最后 reload 复测一次防止「改了没生效」。

二、两处必须现场核对、不能照抄本章：**`proxy_http_version 1.1` 在你所用版本上是否需要显式写**（核对入口是官方 WebSocket 指南那一节；本站只在 Linux · Nginx 一节逐字引用了配置与那条版本注释，没有做版本判读），以及 **worker 退出行为与 `worker_shutdown_timeout` 的语义**（本站明确未核对）。一份上线说明里如果全是「照本章配」，它就是不可信的；能主动标出「本章没核对过的两处」反而是这份说明最有价值的部分。

三、`0.0.0.0:3000` 有两个后果：明文 `ws://` 段暴露到公网（凭据与消息可被抓包），以及**任何人都能绕过 Nginx 直连实时端点**，你的 Origin 校验、`limit_req`、转发信息全部失效。修法：上游只监听 `127.0.0.1`，并在防火墙上确认 3000 不对公网开放——规则写法见[网络与端口](/linux/networking)与[服务器安全](/linux/server-security)，别把「只听回环」和「防火墙没挡」当成同一道防线。
