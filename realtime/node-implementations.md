# Node 侧实现对照：先决定谁连你的端点，再决定用哪个库

第一个事故很安静。服务端用 Socket.IO 写的，浏览器里一切正常。两周后同事用 Python 脚本做压测，或者小程序页面想连同一个地址，握手直接失败——不是「性能不行」，是**根本连不上**。排查方向一开始全跑偏：查防火墙、查 Nginx、查证书，因为所有人都以为那是一个 WebSocket 端点。它确实跑在 WebSocket 之上，但它的握手路径、帧格式和事件语义都不是原生 WebSocket，标准客户端不知道该怎么开口。

第二个事故更常见：本地 `ws://localhost:8080/ws` 一切正常，部署后 `wss://app.example.com/ws` 报 1006。真正的改动只有一处——实时服务被挂在**另一个端口的独立进程**上，而 Nginx 只代理了框架那一个端口。于是这不是库的选择问题，是**拓扑**问题：你的握手请求根本没到实时服务那里，或者到了但代理层没透传升级头。两件事的修法完全不同，而日志上看起来一样。

第三个事故是自我诊断错误：一次正常发布之后所有在线用户掉线，客户端过了半分钟才陆续重连。结论被写成「`ws` 太薄，连重连都不管，该换框架了」。真相是协议里本来就没有「服务端要优雅下线」这件事，第 5 章那条「实例下线要用 1001 广播后再退进程」的活**换了任何库都得你自己干**。把「自己没做」记成「库不提供」，会让你在下一个库上重复同样的故障。

这三件事合起来是本章的唯一主题：**库和框架不会改变协议的事实，它们只改变「那四件套由谁写」和「你还能不能看见线上到底跑了什么字节」。**

本批写作时，本站尝试抓取外部文档以核对 WebSocket 库与实时框架的类名、选项与默认参数，**两次请求均被环境拦截，全部不可用**。因此本章：**不写**任何库的选项默认值、版本号、包名与参数表；最小实现里出现的类名与选项名只作为「常见写法」的**结构示意**，与你安装版本不符时以官方 README 为准。「浏览器发不出协议层 ping」「握手是一次带 Upgrade 的 GET」「保留码不得用于发送」沿用[第 2 章](/realtime/websocket-protocol)已核实的条目，「Socket.IO 是建立在传输之上的应用层协议」沿用第 4 章的定位，本章不重复论证。需要你自己跑才能确认的：那两条 `node -e` 验证、同端口共存是否成立、强杀与优雅关闭读到的关闭码差别——**本章没有安装任何依赖、没有启动过任何服务，代码是形状而不是实测输出。**

## 先把三层分开：协议、库、框架

| 层 | 它负责什么 | 它给你什么 | 它绝对不给你什么 |
| --- | --- | --- | --- |
| 协议层（RFC 6455 / SSE） | 握手、帧、关闭码、单连接内有序 | 双向字节通道；SSE 另送重连与续传 | 身份、房间、顺序编号、背压策略、心跳（见[第 2 章](/realtime/websocket-protocol)那张「不给」表） |
| Node 标准库（`http` 的 `upgrade` 事件） | 把一次带 `Upgrade` 的请求交给你，并在你同意后切成裸字节 | 「与 HTTP 服务共存于同一端口」的能力 | 任何 WebSocket 帧的解析与组装 |
| WebSocket 库（`ws` 这一类） | 帧、握手、关闭、ping/pong、发送队列 | 一个能收发文本/二进制的连接对象，以及它的缓冲深度 | 房间、重连策略、消息语义、鉴权 |
| 实时应用框架（Socket.IO 这一类） | 在传输之上定义一套**自己的**应用层协议 | 房间、ACK、自动重连、心跳、传输降级、命名空间 | 与标准客户端的互操作；帧的可读性 |

这张表里最要紧的是最后两行的分界：**第三层帮你省的是体力，第四层帮你省的是决策，而第四层收回的是可见性。** 你选错层的典型表现是：在第三层里手写第四件（房间、重连、心跳、ACK 全自己写，写到第五百行），或者在第四层里排查第三层的问题（连接断了不知道真因，因为工具里看到的帧不是协议帧）。

## 一个最小可用的实时服务长什么样

本章的交付物是这个形状。它同时提供 HTTP 与 WebSocket，**共用一个端口**，这样部署形态只有一条链路要代理（第 8 章只需要一份配置）。

```ts
// 结构示意。类名与选项名按常见写法给出，本批无法核对 README（见本章末说明）；
// 若与你安装版本的签名不同，以官方 README 为准——要交付的是这个结构，不是标识符。
import http from 'node:http'
import { WebSocketServer } from 'ws'

const server = http.createServer((req, res) => {          // 普通 HTTP 照常处理
  if (req.url === '/healthz') { res.writeHead(200); res.end('ok'); return }
  res.writeHead(404); res.end()
})

const wss = new WebSocketServer({
  server,                       // 关键：交给已有的 http.Server，而不是另开端口
  path: '/ws',
  verifyClient: async ({ origin, req }, done) => {
    // 握手是唯一的鉴权机会（第 6 章第一条）。这里必须做完：
    // ① Origin 白名单；② 一次性握手票据换出 uid；③ 拒绝非法就 done(false)
    if (!ALLOWED_ORIGINS.has(origin)) return done(false, 403, 'bad origin')
    const uid = await verifyTicket(readTicket(req))        // 别在 URL 里放长期 token
    if (!uid) return done(false, 401, 'unauthorized')
    ;(req as any).__uid = uid
    done(true)
  },
})

wss.on('connection', (conn, req) => {
  const uid = (req as any).__uid
  const rooms = new Set<string>()                          // 反向表的连接侧，见第 6 章
  let lastSeen = Date.now()
  conn.on('message', (raw) => {
    lastSeen = Date.now()                                  // 只在【入站】字节上更新
    const msg = parse(raw)                                 // 格式自己定，协议不管
    if (msg?.t === 'hb') return conn.send(JSON.stringify({ t: 'hb', ts: lastSeen }))
    route(uid, rooms, msg)                                 // 广播在循环体外做准备
  })
  conn.on('close', () => registry.drop(conn, rooms))       // 必须清理，否则计数漂移
})

// 服务端方向的探活：库能发协议层 ping，浏览器不能（第 2 章已核实）
const tick = setInterval(() => {
  for (const c of wss.clients) {
    if (Date.now() - c.lastPongAt > PONG_DEADLINE) { c.terminate(); continue }  // 判死
    c.ping()
  }
}, KEEPALIVE_INTERVAL)

// 优雅下线：协议不会替你做，实例退出前必须自己广播「我要走了」
process.on('SIGTERM', () => {
  clearInterval(tick)
  for (const c of wss.clients) c.close(1001, 'server restarting')
  wss.close(() => server.close(() => process.exit(0)))
})
```

十二件事被塞进这六十行，逐条对上前面几章：共用端口（否则代理链路翻倍）、握手期鉴权（第 6 章）、Origin（第 2 章）、入站才更新 `lastSeen`（第 5 章）、服务端能发 ping 而客户端不能（第 2 章）、判死阈值到点主动断（第 5 章）、`close` 清理订阅（第 6 章）、1001 与优雅下线（第 5 章）、`terminate()` 与 `close()` 的区别（前者不发关闭帧，客户端会读成 1006，第 2 章说过它是「部署问题的签名」）。

**为什么必须先自己写一遍这个：** 这十二件事是你之后判断框架「值不值得引入」的唯一依据。没写过就直接上框架，你会遇到第一个事故那种情形——把一个协议层问题查成网络问题，因为框架把你的探活、你的关闭码、你的握手全接过去了，你在开发者工具里看到的东西不再能对应到本章这张表。

## Socket.IO 不是 WebSocket 的封装：三条可检验的判据

第 4 章给过这条定位（[三种方案对比与选型](/realtime/choosing)），这里把它变成能检验的三句。**本批两次抓取 socket.io 官方文档均被环境拦截，因此本节不写它的方法名、默认事件名、参数与版本号**；它自己的文档里有一节专门说明「Socket.IO 不等于原生 WebSocket」，那节是本章最好的对照材料，请你自己读完把结论抄回决定文档。

一、**传输层是可协商的。** 它可以在 WebSocket 与 HTTP 长轮询之间选择或回落，所以你连上的「那个东西」在建立之前还有一段它自己的握手。后果：`proxy_read_timeout` 一类超时会作用在两种完全不同的流量形态上，第 8 章的验证方法也跟着变——你不能用「原生 WebSocket 握手通不通」来判断「Socket.IO 客户端能不能连」。

二、**它在协议里加了语义。** 命名空间、房间、事件名、需要回执的 ACK、自带心跳——这些正是第 2 章那张「协议不给你」表里的东西。这不是「封装得更厚」，这是**另一套应用层协议**，只是常常跑在 WebSocket 之上。

三、**两端必须配套。** 原生 `new WebSocket(...)` 连不上它的端点，其他语言的通用客户端也一样。这就是第一个事故的完整解释，也是选型真正的第一问。

于是「要不要用 Socket.IO」从来不是「哪个库更好」，而是一个**边界问题**：

```text
你的实时端点会被谁连接？
  只有你自己的浏览器页面           ⇒ 配套成本可以接受，框架的四件套值得拿
  还有小程序 / 移动原生 / Python 脚本 / 第三方系统
                                  ⇒ 必须暴露标准协议端点；要么自己写，要么让框架旁边再挂一条标准入口
你的调试能力要求？
  需要看线上真实帧、写协议级测试、抓包排障 ⇒ 透明度损失是真实成本
  只做业务功能，不打算碰协议层            ⇒ 可以不付这个成本
```

第三行不是偏好问题。你的产品一旦接了「别人要连我」这种需求（微信服务号回调、硬件设备、内部脚本、另一个后端服务），标准协议就是硬约束，而这时框架引入的那层私有语义会变成要拆的东西。**先问谁能连，再问用哪个库**，这个顺序能省掉一次重构。

体积与依赖面也要放进同一笔账：多一层框架意味着它的服务端包、它的客户端包、两者版本要匹配（不匹配的表现常常是「本地能用、线上偶发」），以及升级时你的排查路径整体换掉。这类成本在第 4 章那条「写不满四件套就别引入」的纪律里已经给过判断方向，具体到项目就一句：**你能不能列出它替你管的那四件，并且说得出一旦它挂了你怎么排障。**

## 在 Fastify 这类 HTTP 框架旁边挂实时服务：三种形状

关键机制只有一条，其余都是它的推论：**协议升级发生在路由之前。** 一次 `GET /ws` 带 `Upgrade: websocket` 的请求，走的是 `http.Server` 的 `upgrade` 事件，不会经过框架的路由、钩子、序列化器、拦截器和全局鉴权。所以框架替你管的横切能力，一个都不会自动作用到握手上——这就是为什么第 6 章说「身份必须在握手时定死」，也是为什么很多人「加了框架的鉴权钩子就以为 WebSocket 也安全了」。

三种形状与各自的代价：

| 形状 | 机制层描述 | 代价 | 什么时候这是对的选择 |
| --- | --- | --- | --- |
| 同一端口共存 | 从框架拿到它底层那个 `http.Server`，把 WebSocket 服务交给它，或自己接 `upgrade` 事件并按 `path` 判定后握手 | 要拿到框架暴露的 server 实例；升级事件的判定要自己写；框架版本相关 | 默认选择。一个人部署、一条 Nginx upstream、一套 TLS、一份鉴权 |
| 独立端口/进程 | 实时服务自己 `listen` 一个端口，框架服务另一个 | 两条代理链路（第 8 章要配两份）、两套证书或明文回环、跨进程要传身份或共享票据、鉴权逻辑两处 | 实时服务需要独立伸缩、独立发布、独立故障域（第 9 章的前提就在这） |
| 框架插件 | 框架生态里存在「把 WebSocket 接进路由体系」的插件形态 | 引入一层与框架版本绑定的依赖；行为由插件决定，你的排障要穿过它 | 你确认需要框架的鉴权与日志真正作用在握手上，且读过插件行为而不是「装了就好」 |

本批同样无法核对 Fastify 文档的具体接口名，所以这里给的是**判据和验证方法**，不是配置。你要做的验证是两行代码的事，而且现在就能在本机跑（本站未安装依赖、未启动服务）：

```bash
# 验证一：升级事件到底有没有落到你拿到的那个 server 上
node -e "const h=require('node:http').createServer();h.on('upgrade',(req)=>{console.log('upgrade',req.url,req.headers.upgrade)});h.listen(0,()=>console.log('on',h.address().port))"
# 预期：用浏览器连一次该端口的 ws://，终端打印出 upgrade /ws websocket
# 验证二：确认你的实时端点和 HTTP 端点在同一个端口上（curl 打 /healthz 与手工握手各一次，见第 2 章那条 curl）
```

第一条属于 Node 标准库长期稳定的事件名，本批未逐字核对官方 `http` 文档；动手前对照一次，它对不上就停下来——**「升级事件到底出现在哪个对象上」这一条判错，后面所有配置都是在猜。**

## 怎么选：一条有淘汰作用的顺序

不要从「哪个库更流行」开始。按这个顺序问，问到底就有答案：

1. **端点要不要被非浏览器客户端连？** 要 ⇒ 标准协议，本章第一节那个最小实现；不要 ⇒ 下一问。
2. **我需要的四件套（房间、重连、心跳、ACK）有几件？** 少于两件 ⇒ 用 HTTP/SSE 或最薄的写法，别引入协议层框架（第 4 章）；三四件且都是业务必需 ⇒ 下一问。
3. **我能接受调试透明度下降吗？** 需要抓包、写协议测试、给别的系统提供端点 ⇒ 不能，自己写薄实现；只做业务功能 ⇒ 下一问。
4. **愿意为框架的升级耦合付成本吗？**（服务端与客户端版本匹配、依赖面、排查路径整体改变）愿意 ⇒ 用框架；不愿意 ⇒ 薄实现 + 自己写四件套，代码量通常比想象小，因为它只有本章那六十行的形状。

三档规模下这条链会怎么走，说清楚以免变成教条：一个人做产品（第 11 章那种聊天室）——薄实现 + 单实例，第 9 章的复杂度全部不引入，框架的四件套里你当下只需要房间与重连两件；有真实用户在涨但仍是单体——同一条链，只是把本章「现在就能做的实验」都跑一遍，把背压阈值和判死延迟定成产品参数；一旦接入第三方客户端或硬件——第 1 问直接决定你必须提供标准端点，这时框架从「省事」变成「要多挂一条入口」。

## 常见错误与排查

1. **现象：`ws://localhost:8080/ws` 通，`wss://域名/ws` 报 1006。** 原因：实时服务与 HTTP 服务不在同一个端口/进程，代理只转发了其中一个。怎么确认：直接从服务端侧看这条握手到底有没有到达你的 `connection` 回调；上游连日志都没有，问题就在链路不在代码（第 8 章那条 curl 是判据）。怎么修：优先改成同端口共存；确实要独立端口，就两条链路都配代理并各自验证。
2. **现象：框架的全局鉴权钩子写了，WebSocket 仍能匿名连入。** 原因：升级请求不经过路由与钩子。怎么确认：不带凭据发起一次握手，看 `connection` 是否照样触发。怎么修：把鉴权搬到握手处（`verifyClient` 这一类入口或你自己接 `upgrade` 的判定），并在拒绝时返回普通 HTTP 错误码而不是硬断（第 5 章：终态错误要让客户端停止重连）。
3. **现象：第三方脚本、小程序连不上你的「WebSocket 端点」。** 原因：服务端用的是应用层框架的私有协议。怎么确认：用原生 `WebSocket` 客户端连一次，或看握手路径是不是框架自定义的那条。怎么修：要么提供标准协议入口，要么让对方用配套客户端——**别用「换个库」解决一个协议边界问题。**
4. **现象：一次发布打掉全部连接，客户端过了很久才回来。** 原因：没有 `SIGTERM` 处理，进程被硬杀；客户端只能从 1006 猜「断了」，再按它自己的退避慢慢试。怎么确认：看服务端有没有发过关闭帧、看客户端读到的码是 1001 还是 1006。怎么修：先广播 1001 再关（本章代码里有这四行），并在发布说明里写明「会全员重连一次」。
5. **现象：内存缓慢上涨，`close` 事件看起来都触发了。** 原因：清理只做了一半——连接从 `wss.clients` 里消失了，但你挂在它上面的房间集合、`setInterval`、待补拉缓冲还在。怎么确认：打印房间数与所有房间成员数之和（第 6 章那条），而不是连接数。怎么修：把 `lastSeen` 与缓冲放进一个随连接一起销毁的对象里，清理走同一函数。
6. **现象：换成框架之后，之前能抓到的帧看不懂了，排障效率暴跌。** 原因：传输协商与私有语义改变了线上字节。怎么确认：打开开发者工具看帧内容是否还能读成你定义的应用层消息。怎么修：在框架之上再打一层自己的日志（消息序号、连接 id、房间），把可见性找回来——这是引入框架的**真实成本**，不是可选项。

<Exercise title="故意制造一次 1006 并解释它" difficulty="进阶">

按下面步骤做（本机，装一个 WebSocket 依赖即可，本站未执行）：① 用本章最小实现在同端口起服务；② 浏览器连上并进入一个房间；③ 不发送 `SIGTERM`，直接强杀进程；④ 观察客户端读到的关闭码与 `wasClean`；⑤ 再走一遍，但这次正常 `Ctrl+C`（触发 SIGTERM 处理）后再杀进程，比较两次的关闭码。

写清楚：两次为什么不同；`terminate()` 与 `close()` 在字节层差别是什么；如果你的服务在 Nginx 之后，第③步的现象会和第 8 章哪种故障混在一起，你用什么方法把它们分开。

<template #answer>

强杀（③）⇒ 没有关闭帧，TCP 被内核结束，客户端读成 **1006**、`wasClean = false`；有 `SIGTERM` 处理（⑤）⇒ 服务端先发 `close(1001)`，客户端读成 1001、`wasClean = true`，并且**能据此决定立刻重连而不是长退避**——这个区别只有协议层给了码才存在，也是第 5 章那条「终态与可重试要分叉」的前提。

`terminate()` 直接销毁底层 socket，不发任何帧；`close()` 发关闭帧并等对端回应后再结束。所以「用 `terminate()` 表达服务器要重启」等于主动把可诊断信息抹掉，和第 2 章那条「1006 是部署问题的签名」正好配成一对：一个是你在制造签名，一个是你在读签名。

第三问是这道题真正要的东西：在 Nginx 之后，**「空闲超时把连接掐了」也表现为 1006**，两者现象完全一样。区分方法是看**时间**——超时断开有几乎固定的空闲时长（把它和你的保活间隔、`proxy_read_timeout` 三个数摆在一起比，第 8 章第四节那条不等式），而进程退出造成的断开发生在发布或崩溃那一刻、与空闲无关。再加一条硬证据：上游日志里那次握手的 `connection` 记录之后，有没有一条来自服务端的关闭。搞混的代价是去调心跳间隔来解决一个部署问题，或者反过来。

</template>

</Exercise>

<Exercise title="给一个真实产品做实现选型决定" difficulty="挑战">

场景：个人开发者做一个「小组协同白板」，Web 端自己写，另外要求：① 一年后可能出微信小程序；② 想让开源社区能接第三方客户端；③ 需要房间、断线重连、光标位置高频广播、偶尔需要「这条消息我收到了」的确认。

<template #answer>
