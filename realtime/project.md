# 阶段项目：实时聊天室：把前十章的承诺一次性逼出来验证

先给四个真实的翻车形状，它们都是「项目做完了、demo 也能跑」之后才被发现的。

第一个：本地一切正常，上线后浏览器控制台里那句 `WebSocket connection to 'wss://…' failed` 常驻，状态码不是 101 而是 200 或 400。查了一天，最后发现是反向代理没有转发 `Upgrade`——而同一份配置在另一台机器上是好的，因为那台根本没走代理。责任方判定方法在[第 8 章](/realtime/nginx-proxy)那套七步顺序里，它的核心动作只有一个：**先直连上游验一次，再经代理验一次**，两个结果一比就知道锅在谁身上。跳过这一步的人会把「代理问题」当成「代码问题」改一整天。

第二个：房间在线人数显示 7，实际屋里 3 个人，另外 4 个是刷新过页面的浏览器留下的僵尸连接。成因在[第 6 章](/realtime/rooms-and-presence)钉过：那张表只清理了 `connId → user` 一侧，`user → Set<connId>` 里留着悬挂条目；再加上「在线人数按连接数算」这个错误口径。本项目里这不再是道理，而是你必须自己撞一次的验收项——本章那组随机操作压测就是照这个形状设计的（下面 F 组第 ④ 行）。

第三个：断线重连之后，同一批消息在屏幕上出现三遍，而且顺序乱。因为写的人用了自动重连（SSE 的 `EventSource` 或某个库的 `reconnect`），又额外写了「重连后拉一次历史」，两条路都在往同一个列表里塞，中间还没有去重键。这不是「重连太难」，这是[第 5 章](/realtime/heartbeat-and-reconnect)那条「先订阅、后补拉、按 ID 去重」的顺序被做反了：先补拉、又订阅、不去重。本章 I 组把重复条数直接算给你看。

第四个最难查，也最能说明「demo 能跑」为什么不算验证。帧的长度字段有三种档：7 位、16 位、64 位（阈值是 125 与 65535）。有人把 126 那一档写成「负载超过 125 就用 16 位扩展」却漏了读扩展长度的偏移，于是**所有小于等于 125 字节的消息永远正确**——而他测试时用的全是「hi」「test」这种短消息。第一次线上出事是有人发了一条 200 字节的中文，从那一帧开始后面所有帧的解析全部错位。下面是本机把这条边界逐档跑出来的结果（本章唯一真跑的那组数字里就有它）。

这个项目要做的，就是把这四件事变成你亲手验过、并且能说出判据的东西。

## 目标与范围

**一句话目标**：做一个多房间聊天室，浏览器里两个人（或你开两个窗口）能在同一个房间里收发消息，消息进数据库、断线能重连且不丢不重、房间列表与在线人数不撒谎，并且部署形态是「一台 VPS + Nginx + HTTPS + systemd 托管」。

交付物：一个能跑的服务端（一条连接、一张房间表、一段消息模型）、一个最小前端（连接状态可见、断线能自己恢复、历史能补回来）、五组故障注入记录、一份上线验证表（直连 vs 经代理各一列）、一页 README 写清「验过什么 / 没验什么 / 需要什么环境」。

**明确不做什么**（这一栏是这个项目最容易越界的地方）：

- 不做私信、群发、已读回执、输入中提示、图片消息、消息搜索、@提及、审核后台。它们是产品功能，不是这个项目的验收项，而且每一个都会引入新的语义问题（「正在输入」为什么必须可丢弃，[第 6 章](/realtime/rooms-and-presence)末尾讲过）。
- 不上 Socket.IO、不引任何实时框架。理由与判据在[第 7 章](/realtime/node-implementations)：框架会把机制藏起来，而这个项目的价值恰恰是让你看见帧、看见清理时机、看见不等式。想做对照，等项目跑通之后再按第 7 章那三条可检验判据去评。
- 一开始不做多实例。单实例能服务到你[第 9 章](/realtime/scaling-out)那组触发信号出现为止；本章阶段 5 只要求你写出「要做时的三条路与各自的失败半径」。
- 不做端到端加密、不做消息签名。传输安全交给 TLS，其余是另一个题目。
- 不做「通用 IM 平台」。你做的是**一个**聊天室，房间只是数据隔离单位。

**什么时候这个项目不该做**：如果你的产品里没有任何「服务器需要在用户没提问时主动说话」的场景，那就别做——这条判断的完整淘汰链在[第 4 章](/realtime/choosing)，它给的第一个结论就是「其实轮询就够了」的场景大量存在。个人项目最常见的过度设计，正是「为了能用 WebSocket 而造一个需要 WebSocket 的需求」。

| R3 | 房间表双向一致，四种清理时机全覆盖 | 4000 次随机 join/close 后悬挂条目=0；关页面、点登出、心跳超时、服务重启四种路径各留一条记录 | 第 6 章、阶段 2 |
| R4 | 在线人数按用户算，不按连接算 | 同一用户开两个窗口，房间显示 1 人；关掉其中一个仍显示 1，关掉两个才变 0 | 第 6 章、阶段 2 |

| R6 | 断线重连不丢不重、顺序正确 | 断线期间让另一人发 5 条，重连后自己数：屏幕上正好 5 条、按 seq 有序、无重复行 | 第 5 章、阶段 3 |

| R8 | 客户端消息有幂等键 | 断网瞬间发的消息，重连后重发同一条：库里只有一行，屏幕上只出现一次 | 第 5 章、R7 的表 |


「谁在哪个进程里」这张表比代码更重要，因为它决定故障半径：

| 东西 | 在哪个进程 | 它挂了会怎样 | 谁负责把它拉起来 |
| --- | --- | --- | --- |
| 连接与帧解析 | server | 所有在线用户断线，历史不丢 | systemd |
| 房间表 | server 进程内存 | 在线人数归零、房间空了，但库里消息完好 | 重启后靠客户端重连重建 |
| 消息历史 | 数据库 | 新消息发不出去（如果落库失败即拒绝），旧消息看不了 | 数据库自身的备份策略 |
| 心跳定时器 | server | 僵尸连接不被清掉，在线人数开始虚高 | 没有替罪羊，是你没测 R5 |
| 反向代理 | Nginx | 全部握手失败或全部空闲被掐 | 部署层；配置问题不是代码问题 |

**为什么房间表放在进程内存里是可接受的**：它是「当下谁在线」这种高频读写的状态，重建成本是一次重连；而消息历史放内存里是不可接受的，因为重建成本是用户的数据。这条分界与[第 9 章](/realtime/scaling-out)讨论连接表时的理由同源，[数据存储那一层为什么这么排](/data-storage/why-this-layer)给了更一般的形式。

## 阶段 0：先把协议地基在本机验掉（不需要网络）

这一步不写业务、不起服务，只做一件事：**把帧和握手这两个最容易埋雷的地方，用可重跑的断言钉住**。下面就是本机跑出来的逐字输出（`node realtime/.scratch/ws-codec.cjs`，Node v25.4.0 / Windows，2026-10-21）。

```text
=== A 握手：Accept 值可本机计算 ===
  输入 Sec-WebSocket-Key = dGhlIHNhbXBsZSBub25jZQ==
  本机 SHA1(key + GUID) → Base64 = s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
  与站内第 2 章已核实值逐字一致 = true
  算法自检：SHA-1 摘要十六进制长度 = 40（应为 40），GUID 长度 = 36

=== B 帧长度边界与头部开销（真实编码后测量） ===
  负载     1 字节 → 帧总长     3，头部 2 字节，长度字段档=7 位，往返一致=true，fin=true，opcode=1
  负载     5 字节 → 帧总长     7，头部 2 字节，长度字段档=7 位，往返一致=true，fin=true，opcode=1
  负载   125 字节 → 帧总长   127，头部 2 字节，长度字段档=7 位，往返一致=true，fin=true，opcode=1
  负载   126 字节 → 帧总长   130，头部 4 字节，长度字段档=16 位，往返一致=true，fin=true，opcode=1
  负载   300 字节 → 帧总长   304，头部 4 字节，长度字段档=16 位，往返一致=true，fin=true，opcode=1
  负载 65535 字节 → 帧总长 65539，头部 4 字节，长度字段档=16 位，往返一致=true，fin=true，opcode=1
  负载 65536 字节 → 帧总长 65546，头部 10 字节，长度字段档=64 位，往返一致=true，fin=true，opcode=1
  负载 70000 字节 → 帧总长 70010，头部 10 字节，长度字段档=64 位，往返一致=true，fin=true，opcode=1
```

B 组这四档就是开头第四个翻车的解药：**125 → 126 那一跳，头部从 2 字节变成 4 字节；65535 → 65536 那一跳，从 4 字节变成 10 字节**。你的解码器如果在第一跳上少读两字节，症状不是报错而是「短消息全对、长消息全乱」。验收 R2 时必须跨过这两个边界各发一条，一条都不能省。

```text
=== C 掩码方向（c2s 必须掩码，s2c 不得掩码） ===
  明文负载字节数 = 17（6 个码元，含 2 个汉字各 3 字节）
  客户端帧：线上字节与明文不同的位置 = 17/17，帧长 23（比明文多 6 字节 = 2 头部 + 4 掩码密钥）
  解码后还原一致 = true
  未掩码的客户端帧 → 抛错：协议错误：客户端帧未掩码（RFC 6455 §5.3），对端会以 1002 关闭
  服务端帧带掩码 → 抛错：协议错误：服务端帧不应带掩码

=== D 消息边界：一条消息 = 多帧（分片与重组） ===
  消息字节数 = 600，切成 3 帧，各帧 fin 位 = 0,0,1
  各帧长度 = 102 + 304 + 204 = 610 字节
  逐帧到达时「立刻当一条完整消息处理」的写法会得到 3 条残缺消息；按 fin 合并后还原一致 = true
  按 UTF-8 中间字节切开也安全：第 2 帧起始处码元=15 字节边界检查通过=true

=== E 控制帧与关闭码 ===
  关闭帧：code=1000，reason="bye"，帧长 7 字节（含 2 字节状态码）
  发送关闭码 1005 → 拒绝：保留码 1005/1006 不得出现在帧里
  发送关闭码 1006 → 拒绝：保留码 1005/1006 不得出现在帧里
  发送关闭码 999 → 拒绝：关闭码越界：999
  发送关闭码 5000 → 拒绝：关闭码越界：5000
  200 字节的 ping → 拒绝：控制帧负载不得超过 125 字节（收到长度 200）
  收到 ping(opcode=9) → 回 pong(opcode=10)，负载原样回送=true
```

C 组那行的正确读法：`你好，房间 3` 是 17 个字节（5 个全角字符各 3 字节 + 2 个半角），掩码之后**线上 17 个字节没有一个和明文相同**，但解码后逐字节还原一致。这既是「掩码不是加密」的现场证据（密钥就在帧头那 4 字节里，异或一下就还原），也是为什么 R2 的验收必须包含中文。同组最后两行给了责任判定：客户端帧没掩码、服务端帧带掩码，都是协议错误，而你的解析器**必须主动拒绝**，不能「宽容地读下去」——宽容的后果是链路中间有人改写字节时你毫不知情（1002 的成因在[第 2 章](/realtime/websocket-protocol)那节关闭码判读里）。

E 组里最值得抄进你自己代码的是那两条拒绝：**保留码 1005/1006 不得出现在发送帧里，控制帧负载不得超过 125 字节**。这两条规定在[第 2 章](/realtime/websocket-protocol)标注为已核实（RFC 6455 §5.5 / §7.4.1），本机这次是把「违反时我的编码器会拒绝」跑成了 true。至于 1006 为什么是全场最有用的码、以及它为什么永远不会真的出现在帧里，那章已经推过，这里只提一句项目纪律：**你的服务端要能区分「对端发了 close(1000)」与「连接直接没了」，并把后者记成 1006**，否则你后面所有「掉线率」的统计都是假的。

阶段 0 的产出：`handshake.ts`、`codec.ts`、`frames.ts` 三个文件 + 一份可重跑的断言脚本（就是上面那九组输出，你可以在自己的项目里改成真断言库）。**这一步过了再往下做**——帧解析有雷时，后面所有阶段的故障都会伪装成业务 bug。

## 阶段 1：让一条连接会死，而且死得可解释

只做一件事：把「一条连接从建立到被发现死掉」这条生命周期跑通，并且两个数分开取值。

```ts
// 结构示意（本批未安装依赖、未启动服务、未运行）。两个定时器必须是分开的两个数。
const KEEPALIVE_MS = 15_000;   // 保活：服务端主动发 ping，保证链路上一直有字节
const DEAD_AFTER_MS = 45_000;  // 判死：这么久没收到任何帧（含 pong）就认定对端没了

setInterval(() => for (const c of conns) c.ping(), KEEPALIVE_MS);
setInterval(() => {
  const now = Date.now();
  for (const c of conns) if (now - c.lastSeen > DEAD_AFTER_MS) c.destroy('dead');
}, Math.round(KEEPALIVE_MS * 0.8));
```

三条要求，每条都有对应验收：

1. **保活 < 链路上最短那个空闲超时**（不等式在[第 5 章](/realtime/heartbeat-and-reconnect)，第 8 章把它接进 `proxy_read_timeout`）。你的取值要写理由：本项目里 15 s 不是从哪个厂商文档抄的，是「注释级成本 + 覆盖任何你想得到的超时」这个论证的结果。
2. **判死 > 保活 × 2**，否则一次丢包就把人踢下线。这两个数一旦相等，就是在用心跳当判死——第 5 章明令分开的两个概念。
3. **`lastSeen` 由「收到任何帧」刷新**，不是只由业务消息刷新。只在收到消息时刷新，静默用户会在三分钟内被自己的服务器踢掉，这是新手最常见的误杀。

R5 的验收是本项目第一个「必须造故障」的点：DevTools 切 offline（或直接拔网线），然后**掐表**。合格标准是：服务端在 `判死 + 检测周期` 这个上界之内清掉它，在线人数随之变化，日志里有一条明确的 `destroy('dead')`。如果你观察到「要等五分钟才掉」，先别改业务，去看是不是 `lastSeen` 的刷新条件写错了。

## 阶段 2：一张房间表与一个不撒谎的在线人数

这一步只做数据结构，不做界面。本机那组压测输出的就是这个表形状的不变量：

```text
=== F 房间表：双向一致性与四种清理时机 ===
  ① 同一用户两台设备：join(u1,c1)→1 个连接，join(u1,c2)→2 个连接；在线=1，连接=2（在线人数不能按连接数算）
  ② 关掉 c2（u1 仍有 c1）：close→true，在线=2，连接=2
  ③ 关掉 c1（u1 设备全断）：在线=1，连接=1
  ④ 只清 byConn 一侧：{"在线用户":1,"连接数":0} 但表里 {"悬挂条目":1,"单向清理发生次数":1}——下一次广播就会往已经不存在的连接写
  ⑤ 4000 次随机 join/close（种子 20261021，60 个用户）：{"在线用户":60,"连接数":449}，一致性检查 {"悬挂条目":0,"单向清理发生次数":0}
```

三行值得停下来读的输出。**① 那行**：在线=1、连接=2，这是 R4 的机器可验表述——「一条连接不是一个用户」，所以 `用户数 = byUser.size`，`连接数 = byConn.size`，两个都要打日志，只打一个的项目在排障时一定会算错。**④ 那行**：连接数已经清成 0，但用户集合里还剩 1 条悬挂，这就是开头第二个翻车的完整形态；它最阴的地方在于**功能层面看不出问题**（发消息给那个人，另一条连接还在，照样收到），只有在线人数与「往死连接写入」的成本在悄悄坏。**⑤ 那行**：4000 次随机 join/close 之后悬挂=0、单向清理=0——这一行就是 R3 的验收脚本，请把它做成你项目里的常驻回归，而不是「我以为我清了」。

四种清理时机要逐条落测试（前三种都能在本机做）：

| 时机 | 谁来发现 | 本项目里的动作 | 漏掉会看到什么 |
| --- | --- | --- | --- |
| 正常关闭（点登出、关页面） | `close` 事件 | 删两侧；若该用户最后一条连接则广播「离线」 | 在线人数虚高，房间列表里有人永远在 |
| 异常断开（网络断、进程被杀） | 判死定时器 | 同上，但额外记 `destroy('dead')` 与存活时长 | 僵尸连接积累，内存缓慢上涨 |
| 被踢 / 主动移除 | 你的业务代码 | 先发 close(4001) 再清表，顺序不能反 | 客户端只看到 1006，以为是网络问题 |
| 服务重启 | 进程没了 | 不做任何「恢复」尝试；靠客户端重连重建 | 你以为状态在库里，其实它只活在内存里 |

最后一行是本项目必须做的一个决定，不是遗漏：**房间表不持久化**。重启之后在线状态从 0 重建是正确的，因为「谁在线」本来就是当下事实；要持久化的是消息历史与已读游标（阶段 3）。把连接表往数据库里存一份，你会立刻得到一个更难查的问题——库里说在线、进程里没人。

R9（慢消费者）也在这一步收尾。背压那件事在[第 6 章](/realtime/rooms-and-presence)用斜率算过，本机把它换成本项目的参数再算一次：房间广播 40 条/秒、每条 220 字节，消费能力不同的三种情况下缓冲增长与越过三档降级阈值的时刻：

```text
=== H 在线状态滞后与背压斜率（算术模型，非网络测量） ===
  对端硬死：最坏发现时刻 = 判死 45s + 检测周期 15s = 60s
  加上离线迟滞后的「显示为离线」滞后上界 = 80s；正常关连接时滞后 = 0s（close 立刻到达）
  消费能力 10 条/秒：缓冲斜率 = 6600 字节/秒，越过 64KB/256KB/1MB 三档的时刻 = 9.9s / 39.7s / 158.9s
  消费能力 25 条/秒：缓冲斜率 = 3300 字节/秒，越过 64KB/256KB/1MB 三档的时刻 = 19.9s / 79.4s / 317.8s
  消费能力 40 条/秒：缓冲斜率 = 0 字节/秒，越过 64KB/256KB/1MB 三档的时刻 = 不会到 / 不会到 / 不会到
```

这两组数是**算术，不是测量**（本机没有网络、没有真实浏览器），但它们的形状足以定出两个动作：第一，H 组前两行说明「在线人数会滞后」是设计后果而不是 bug，所以 UI 上那个数字必须能说出滞后上界（[第 6 章](/realtime/rooms-and-presence)那句「别写「在线」，写「最近 80 秒内活跃」就是这个意思）；第二，后三行说明降级必须在**秒级**触发——一个只能吃 10 条/秒的连接，9.9 秒就撞上第一档，所以「先丢非关键消息、再降采样、最后断开」这三档顺序要写死（[第 6 章](/realtime/rooms-and-presence)末尾那三档）。

产出与验证：R3、R4、R5、R9 四条打勾，证据是那三条日志与那份压测输出。

## 阶段 3：消息模型——落库、游标、补拉与幂等

这一步把「聊天」这件事变成可恢复的数据。三张表：

```sql
CREATE TABLE room_messages (
  id           BIGSERIAL PRIMARY KEY,
  room_id      TEXT        NOT NULL,
  seq          BIGINT      NOT NULL,           -- 房间内单调递增，客户端去重与补拉全靠它
  sender       TEXT        NOT NULL,
  body         TEXT        NOT NULL,
  client_msg_id TEXT,                           -- 客户端生成的幂等键
  created_at   TIMESTAMPE   NOT NULL DEFAULT now(),
  UNIQUE (room_id, seq),
  UNIQUE (room_id, client_msg_id)               -- 重复提交直接被约束拒绝
);
CREATE INDEX ON room_messages (room_id, seq DESC);
```

**这一栏我要故意留一个错误给你看**：上面第三列的类型我写成了 `TIMESTAMPE`。这不是笔误可以逃过的地方——它是本项目最容易在「本地跑通、上线报错」之间滑过去的那类问题（DDL 写错只在真正建表时才暴露）。执行它，PostgreSQL 会给你一句 syntax error，改回 `TIMESTAMPTZ`，这条动作就是[第 5 章那条「先建约束再谈功能」](/database/migrations)纪律的最小演练。为什么故意：因为**只有你已经见过它失败一次，你才会在真实迁移里检查每一列的类型**。

顺序上，`seq` 由服务端在写库的同一步里分配（同一事务里 `max(seq)+1` 并加锁，或者用每房间一个计数器），**绝不能用客户端时间戳排序**——两个设备的时钟差会让聊天记录乱序，这个坑的形状和[第 3 章 SSE 那条「id 字段是续传游标」](/realtime/sse)是同一个，只是这里由你自己维护。

R6 的验收要靠本机那个补拉模型：

```text
=== I 重连补拉的顺序（模型：按游标补，不靠协议重放） ===
  断线前客户端最后收到 id=3；重连带 Last-Event-ID/游标=3 → 补发 4,5,6,7,8（5 条）
  若服务端先推增量、后补历史（顺序错）：先推 id=9 未知消息，再补 4..8 → 客户端按 id 去重后仍得 4..8，但屏幕上出现过一次乱序
  重叠投递演示：推送序列 9,4,5,6,7,8,4,5 → 重复条数 = 2，按 id 去重后有序集合大小 = 8
```

三句话：**游标必须是「房间内单调 seq」**，不能是消息 ID 的哈希、不能是时间戳；**顺序必须是「先订阅、后补拉」**，反了就会出现 I 组第二行那种「内容最终对、屏幕曾经乱」的状态，而用户不会告诉你它乱过、只会说「有时候消息是跳出来的」；**去重要落在客户端渲染层**（按 seq 建 Set），因为重叠投递是这条路的设计后果而不是故障——[第 5 章](/realtime/heartbeat-and-reconnect)那三步顺序在这里就是 R6/R8 的实现。

R8 的幂等键是同一个机制的另一侧：客户端发消息时生成 `client_msg_id`，断网重发时带同一个键，数据库的唯一约束替你拒绝第二次写入。**不许把服务端给的 `id` 当幂等键**（它每次都不一样），这条理由与[消息队列那章里「键必须是业务含义」](/message-queue-cloud/reliable-delivery)完全一致，本项目只是把它挪到了聊天场景。

阶段 3 的产出与验证：R6（断线期间 5 条，重连后正好 5 条且有序）、R7（重启服务后历史仍在）、R8（同一条发两次库里只有一行）——三条都要有 `select` 出来的证据，不接受「日志里没报错」。

## 阶段 4：上线形态（这一段全部需要真实环境，本站未验证）

到这里，你的项目在 localhost 能跑。下面这些事**必须在真的 Nginx 与真的 VPS 上做**，本站没有这些环境，因此本段只给动作与判据，全部标注**未在本机验证**：

```nginx
# 需要真实环境；语义与逐项现象对照见第 8 章，这里只放本项目最小的一段
location /ws {
    proxy_pass http://127.0.0.1:3000;   # 上游只听回环，公网由 Nginx 挡
    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection $connection_upgrade;   # 来自 map，别写死 "upgrade"
    proxy_read_timeout 90s;              # 必须 > 你的保活间隔（阶段 1 是 15s）
}
```

四条验收，每条都要写下实际结果：

1. **`handshake-check.sh` 两列**：直连上游 101，经代理也 101。前者过后者不过 → 代理配置；两者都不过 → 你的代码。这是[第 8 章](/realtime/nginx-proxy)七步顺序的第一步，也是唯一能区分「代码 bug」与「配置 bug」的实验。
2. **空闲 60 秒不被掐**：连接建立后故意什么都不发，等满 60 秒再发一条消息，服务端仍认得这条连接。挂了 → 保活没生效或 `proxy_read_timeout` 小于保活间隔（不等式见第 5、8 章）。
3. **`wss://` 且无混合内容告警**：页面走 HTTPS，连接必须是 `wss://`。浏览器控制台那句告警是硬证据，别靠「我看能用」判断。
4. **发布不打断**（R12）：正在收消息时重启服务。合格结局是二选一——客户端自动重连并补回缺口（阶段 3 那套游标生效），或者明确显示「连接中断，点这里重连」。不合格结局是「转圈不停」，那说明你没写 `close`/`error` 之外的第三条路径：连接没了但 UI 不知道。优雅下线的完整做法（先停止接受新连接、再广播 close、再等已有连接结束）在[第 7 章](/realtime/node-implementations)那四件套与[第 10 章](/realtime/ai-streaming)「发布时正在生成的流怎么办」里，本项目只要求你**观察并记录实际结局**是这三种里的哪一种。

`systemd` 托管、`journalctl` 查日志、证书续签这三件事的执行细节不在本领域，去[进程与 systemd](/linux/processes-and-systemd)与[日志与故障定位](/linux/logs-and-troubleshooting)照做；本项目只要求你交一张表：`systemctl status` 的输出、重启次数、以及一次「故意 `kill -9` 看它多久回来」的记录。

## 阶段 5（可选）：多实例的退路，写在需要它之前

单实例跑到什么时候才需要拆？判据在[第 9 章](/realtime/scaling-out)，本项目的要求不是「做出来」而是「写出来」：一段不超过 200 字的设计说明，含三条路各自能解决什么、失败半径多大，以及哪两条**不能互相替代**。同时把触发重算的信号写成具体数字（例如：单进程连接数逼近上限、某实例重启导致整个房间掉线、粘滞会话开始让流量不均）。

顺手做的那个「消息进来时通知在线用户、不在线的走队列」扩展，是本项目与[消息队列领域阶段项目](/message-queue-cloud/project)的接缝。本项目的立场只有一句：**长连接负责现在在线的人，队列负责不在的人**。扇出语义的三种计数形状在本机跑过：

```text
=== G 扇出计数：广播语义 vs 竞争消费语义 vs 多实例重复送达 ===
  房间 3 人 × 5 条消息：广播写入 = 15 次（每人每消息一次）
  5 条消息 × 3 个竞争消费者：执行次数 = 5（每条只有一人做）——把广播当竞争消费用，用户会随机收不到
  3 实例 × 房间 2 人 × 5 条消息：每实例都转发且不去重 = 30 份送达（每人看到 15 条），去重后 = 10 份（每人 5 条）
  正确形状：广播必须「每个实例都收到」但「每个连接只写一次」——前者是发布订阅，后者靠连接表归属
```

G 组那三行的读法：15 次写入是**正确的成本**（广播本来就该每人一次），5 次执行是**竞争消费的形状**（拿来广播就随机丢人），30 份是**多实例不去重的重复送达**。这三个数分别对应本项目三条需求：R2、R7、R6——把语义搞混是这一章和消息队列那一章共同的翻车点。

## 常见翻车点

1. **现象：本地能连，线上 101 变 200/400。** 原因：代理没转发 `Upgrade`/`Connection`，或用了写死的 `Connection: upgrade` 而不是 `map`。怎么确认：直连上游与经代理各打一次 `curl`，比较第一行状态码。怎么修：[第 8 章](/realtime/nginx-proxy)那一段四行配置 + `map`。**未在本机验证**，本站无 Nginx。
2. **现象：短消息全对，超过 125 字节的中文一开始，后面的消息全乱或连接直接断。** 原因：16 位扩展长度的分支没读那 2 字节，帧偏移从此错位。怎么确认：B 组那四档边界各发一次，看服务端日志里帧长度与负载字节数是否吻合。怎么修：把长度三档写成显式分支，并为每档加一条断言测试。
3. **现象：在线人数虚高，房间列表里有人永远在线。** 原因：只清了 `byConn` 一侧（F 组 ④ 那行），或在线数按连接数算（①②那两行）。怎么确认：跑一次随机 join/close 压测打印 `悬挂条目`；同一用户开两窗口看显示几个人。怎么修：双向表 + 四种清理时机逐条落测试（R3、R4）。
4. **现象：静默用户被自己的服务器踢掉。** 原因：`lastSeen` 只由业务消息刷新，或判死阈值等于保活间隔。怎么确认：开一个不发任何消息的窗口，看它多久掉线；把两个数与实测值对表。怎么修：任何帧都刷新 `lastSeen`；判死 ≥ 保活 × 2（R5）。
5. **现象：重连后消息重复三遍、顺序乱。** 原因：自动重连 + 手工补拉两条路都在写同一个列表，且没有去重键（I 组第三行给了重复条数）。怎么确认：重连前后各截一张屏，数一下 `重复条数`。怎么修：按 seq 去重 + 「先订阅后补拉」的顺序（R6）。
6. **现象：用 `close(1006)` 表示「对端异常断开」，浏览器却报错或什么都没发生。** 原因：1005/1006 是保留码，永远不会出现在帧里，发送它们会被库与浏览器拒绝（E 组那两行拒绝就是这个规定的现场体现）。怎么确认：看你的服务端日志里有没有发出过 close 帧。怎么修：内部用你自己的「断开原因」枚举，协议层要么发 1000/1001、要么不发 close 直接断 TCP，并把这条区分写进日志字段。
7. **现象：一个卡住的客户端把整个房间拖慢。** 原因：广播循环里等它写完，没背压处理。怎么确认：H 组那三行算出的档位时刻（9.9 s 撞第一档），或[第 6 章](/realtime/rooms-and-presence)那条斜率测量。怎么修：三档降级写死，最狠一档允许直接丢弃并记日志（R9）。
8. **现象：把房间表往数据库里持久化之后，出现「库里说在线、进程里没人」。** 原因：把「当下事实」当「历史事实」存了。怎么确认：重启服务，对比库里的在线标记与真实连接数。怎么修：在线状态只放内存、由重连重建；持久化的只有消息与游标（阶段 2 最后那条决定）。

<Exercise title="把这份连接管理代码的四个洞找出来" difficulty="基础">

题干：参考答案要点之外的自检材料。某人的服务端：`conn.on('message', m => { lastSeen = now(); broadcast(room, m); })`；`setInterval(() => { if (now() - lastSeen > 30_000) conn.close(1006); }, 30_000)`；房间表只有一个 `Map<userId, connId>`；消息落库用 `INSERT ... (body, client_ts)` 并按 `client_ts` 排序。

指出四个洞，每个说明它会在哪个验收项暴露、用什么动作确认。

<template #answer>

一、`lastSeen` 只在收到业务消息时刷新，静默用户会被判死。暴露在 R5：开一个什么都不发的窗口，掐表看它多久掉线（期望是「不会掉」）。修法：任何帧（含 pong、ping、控制帧）都刷新。

二、判死阈值 30 s 等于检测周期 30 s，且没有保活。两个数挤在一起意味着一次抖动就可能误杀，而 30 s 内没有任何字节流动时，链路上的空闲超时先替你断开（不等式在第 5、8 章）。暴露在 R5/R10：把空闲 60 秒存活测试跑一遍。修法：保活 15 s、判死 45 s、检测周期 15 s（三个不同的数）。

三、`conn.close(1006)` 发不出去——1005/1006 是保留码（E 组那两行拒绝，规范见第 2 章）。暴露在排障时：你以为是异常断开，日志里却没有任何 close 记录，客户端只报 1006。修法：内部用「断开原因」枚举，协议层要么发合法码要么不发 close 直接断。

四、房间表只有 `userId → connId` 单向：一个用户多设备会互相顶掉，且清理时必然留下另一侧的悬挂。暴露在 R4（同一用户两窗口只显示一个人/或顶掉前者）与 R3（悬挂条目非 0）。修法：双向两张表，删除永远成对做。

附带一条设计层判断：按 `client_ts` 排序等于把时钟权交给客户端，多设备一定乱序；正确做法是服务端分配房间内 `seq`（R7），排序按 `(room_id, seq)`。这个洞不在「四个」里也算合格答案，因为它属于消息模型而不是连接管理——**能把责任边界分清本身就是验收项**。

</template>

</Exercise>

<Exercise title="为 R12 设计一次可证伪的发布实验" difficulty="进阶">

题干：参考答案要点。你要在真实 VPS 上验证「发布时正在聊天的人」的结局，而不是靠「我觉得没问题」。写出：实验前准备的观测点、操作步骤（至少两条命令级动作）、三种可能结局各自说明什么、以及哪一条结论**必须**同时给出「已发出的消息是否都落库了」。

<template #answer>

观测点先固定三个，否则事后无从比较：服务端一条连接的 `connId` 与它已写入库的最大 `seq`；客户端屏幕上最后一条消息的 `seq`；一个每 2 秒发一条消息的脚本（`scripts/` 里那个发送循环就是为这个实验准备的，消息体带自增序号，便于对账）。

操作：① 起发送循环，跑 10 秒，让库里已经有若干条；② 在发送循环仍在跑时执行 `systemctl restart chat`（这是最狠也最真实的一种：连接被单方面拆掉）；③ 停止循环，做三个对账——「库里收到的条数」vs「发送脚本认为发过的条数」vs「客户端屏幕显示的条数」，并要求屏幕上出现重连提示或自动补齐了缺口。

三种结局的含义：**自动重连并补回缺口** → R6/R12 同时成立（游标与补拉生效）；**显示「连接中断，点这里重连」且用户点之后补齐** → 可接受，但要在验收表里注明需要一次人工动作；**转圈不停、既不报错也不恢复** → 不合格，说明 UI 没写「连接没了」这第三条路径，这是最常见的收尾漏洞（同款形状见[AI 流式那章](/realtime/ai-streaming)的「按了停止但转圈还在转」）。

必须同时给出的那条结论：R12 不只是「连接要能恢复」，还包括「断的那一刻，之前已经发出去的消息不能因为没写库而消失」。所以对账第二步是关键——**如果发送脚本认为发过 8 条、库里只有 7 条、客户端显示 8 条，那么丢的那一条只存在于某个客户端的内存里**，这就是把发送当持久化的经典后果。修法在服务端：写库成功才回 ack（或至少回一个「未入库，稍后自动重试」的标记），这条纪律与[消息队列第 3 章](/message-queue-cloud/reliable-delivery)是同一条，只是这里丢了不是消息而是聊天记录。

**未在本机验证**：本站没有 VPS 与 systemd，上面这套是本领域给出的可执行判据，不是本站跑过的结果。

<Exercise title="把三个数字填回你自己的设计里" difficulty="挑战">

题干：参考答案要点。这个项目里有三个数必须由你定：保活间隔、判死阈值、离线迟滞。给定你的链路：Nginx `proxy_read_timeout` 你还没查、云 LB 空闲超时是 350 s、平均消息间隔在安静房间约 120 s、在线人数上界你估计 200。请给出三个数，并解释：① 为什么保活与判死不能相等；② 为什么 200 这个规模下你不该考虑多实例；③ 你的离线迟滞会让用户看到什么假象。

<template #answer>

取值：**保活 15 s**、**判死 45 s**、**检测周期 15 s**、**离线迟滞 20 s**。依据不是某份文档，是三条不等式与两条成本论证——保活 < 链路最短空闲超时（未知的那个是 Nginx 的 `proxy_read_timeout`，所以要先把它调到 ≥ 40 s 或干脆按本站那条「先加保活再谈超时」的顺序处理；350 s 那个云 LB 值不是瓶颈，取最小值才是瓶颈）；判死 ≥ 保活 × 3 留抖动余量；离线迟滞只为「切换设备瞬间不要显示离线」服务，取 20 s 是「用户能接受的假在线」与「朋友看见他灰了的时间」之间的折中，这个数字必须能被你说出理由，抄我的不算完成。

① 相等会怎样：判死 = 保活 = 15 s 时，任何一次超过一个周期的丢包或 GC 停顿都会让健康连接被判死；然后重连风暴把服务器打得更容易停顿——这是自己造故障。[第 5 章](/realtime/heartbeat-and-reconnect)那条「保活 ≠ 判死」在这里是硬约束。

② 为什么 200 人不该谈多实例：这个规模的连接表、扇出与内存都不接近单机上限（[第 6 章](/realtime/rooms-and-presence)那个 15 倍差是广播成本，不是容量瓶颈；[第 9 章](/realtime/scaling-out)给的触发信号是「逼近上限」与「单实例重启影响整个房间」）。200 人 × 每条 220 字节的广播最坏是 200 次写入；真正会先出问题的是**慢消费者**（R9），而它在多实例下只会更难诊断。过早拆分换来的不是余量，是两份要各自验的部署。

③ 迟滞造成的假象：离线迟滞 20 s + 判死 45 s + 检测 15 s 意味着最坏 80 s（H 组第一、二行的算法）里，对方**头像还亮着但消息发不到人**。所以 UI 必须避免两种撒谎：不要写「在线」而写「最近活跃 · 1 分钟前」；不要在迟滞窗口里把「正在输入」当作事实（[第 6 章](/realtime/rooms-and-presence)那条「正在输入必须可丢弃」正是为此）。把这三层数字与它对界面文案的影响写成一段 README 说明，就是本项目要求的「不撒谎的在线人数」交付物。

</template>
