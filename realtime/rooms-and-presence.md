# 房间与在线状态：你以为是实体的东西，其实是一张会漏水的表

第一个故障不报错，所以拖得最久。房间成员显示 3 人在线，人走了还是 3 人，重启进程才恢复。查了一小时广播逻辑，最后发现 `close` 事件里只删了「这条连接」，没删「这条连接订阅过的每个房间」——那张表只会变大，计数永远朝着一个方向漂。

第二个故障是产品同学先看见的：一个人同时开着手机和电脑，或者两个标签页。他把其中一个关掉，页面上他从「在线」掉成「离线」，又立刻弹回「在线」。更糟的是房间人数从 12 跳到 21——因为代码数的是**连接**，产品要的是**人**，这两者在真实世界里差着一倍多（本章末尾那组模拟给出的比值是 1.80×）。

第三个故障来得很快：某个成员的网络在传文件，房间其他人突然发现消息变慢、顺序乱、偶尔收不到。服务端日志没有任何异常——广播是「同步 for 循环挨个 send」，而发送是往这条连接的写队列里塞。队列只进不出时，塞的人不知道自己塞了多深（模拟里 52 秒就堆过 1 MB，不设上限跑到 30 分钟是 35 MB）。**广播不是「把消息交给系统就完了」，它是有归属、有上限、有失败策略的一次资源分配。**

这三件事共用一个根因：把「房间」「在线」「已发送」当成了协议或框架给你的实体，而它们其实都是**你在自己进程里维护的一张表**，以及这张表在四种时机下能不能被正确清理。本章讲这张表的形状、它的成本、它的失效方式。跨进程之后这张表怎么同步，是[第 9 章](/realtime/scaling-out)的事，本章一律不碰。

本章的数字分三类，读的时候请分开对待。**本机 Node v25.4.0 真跑出来的**只有一组循环计时和三组算术模拟（脚本 `realtime/.scratch/rooms-broadcast.cjs`，种子 20261021，零依赖、不联网），它们测的是**形状**：序列化位置的成本斜率、卡住连接的缓冲增长速率、判死阈值与心跳带宽的对应、多标签页的连接/用户比值。**沿用站内已核实事实**的是「浏览器发不出协议层 ping」「关闭码语义」「在线状态的滞后等于判死阈值」这几条（出处见第 2、5 章，本章不重复论证）。**没有验证过的**是任何真实库的广播行为、任何真实网络下的往返与丢包表现、以及任何产品级连接数上限。多标签页那组的分布是本章设定的抽样规则，不是真实用户统计；末节四个实验本站未执行。

## 一条连接不是一个用户：先把身份这件事钉死

握手是一次 HTTP 请求，鉴权只能发生在这一次上；101 之后 HTTP 语义全部失效（见[第 2 章](/realtime/websocket-protocol)），**服务端再也没有「每个请求重新确认身份」的机会**。这条约束决定了房间里所有事的形状：

- 连接的拥有者必须在握手时就确定并挂到连接对象上，形式就是 `conn.uid = <握手时验证过的用户 id>`。握手期的凭据放哪里、为什么长期 token 不能裸放 URL query（会进 access log），第 2 章已经讲过，本章不复述，只用它给的结论：用一次性、短 TTL 的握手票据。
- 断线重连之后是**一条全新的连接**，旧连接的身份、订阅、游标都不会自动跟过来。客户端必须在重连后的第一条消息里把「我是谁、我在哪些房间、我看到第几号了」重新交给你——这件事和第 5 章的补拉是同一条时序，不要设计成两条。
- 房间 id 不能当作授权凭证。**「知道房间号」不等于「可以进这个房间」**。`join` 必须服务端查一次成员表；把房间 id 拼进 URL 就默认合法，是实时版的越权访问（IDOR），原理和修法见[会话与鉴权](/backend/auth-session)。

判据一句话：**任何你在 `message` 回调里信任的「这个人是谁」，都必须能追溯到握手时那一次验证。** 如果它来自客户端自报的字段，那它就不是身份，是输入。

## 房间在内存里必须是双向的

一张表就够写出来了，但它必须能两个方向查：

```ts
// 通用形状：不涉及任何库的 API。conn 是你自己包的一层，里面至少有 uid 和 send()
type Room = { id: string; conns: Set<Conn> }
class Registry {
  private rooms = new Map<string, Room>()          // 房间 -> 成员（广播要用）
  private subs = new Map<Conn, Set<string>>()      // 连接 -> 房间（清理要用）

  join(conn: Conn, roomId: string) {
    let r = this.rooms.get(roomId)
    if (!r) { r = { id: roomId, conns: new Set() }; this.rooms.set(roomId, r) }
    r.conns.add(conn)
    let s = this.subs.get(conn)
    if (!s) { s = new Set(); this.subs.set(conn, s) }
    s.add(roomId)
  }

  // 四个入口都必须走到这里：主动离开、close 事件、判死超时、进程退出前的优雅关闭
  drop(conn: Conn, roomId: string) {
    const r = this.rooms.get(roomId)
    r?.conns.delete(conn)
    if (r && r.conns.size === 0) this.rooms.delete(roomId)   // 空房间要收回，否则房间表只涨不消
    const s = this.subs.get(conn)
    if (s) { s.delete(roomId); if (s.size === 0) this.subs.delete(conn) }
  }

  roomsOf(conn: Conn): string[] { return [...(this.subs.get(conn) ?? [])] }
  membersOf(roomId: string): Conn[] { return [...(this.rooms.get(roomId)?.conns ?? [])] }
}
```

单向表（只有 `rooms`）在 `close` 时无法回答「这条连接订阅了什么」，于是第一节那个计数漂移必然发生——**不是概率问题，是数据结构问题**。上面 `drop()` 的四行清理是本章最该抄走的东西。

还有四个容易被漏掉的时机，每个都对应一类线上现象：

| 时机 | 不做会怎样 | 必须做的事 |
| --- | --- | --- |
| 客户端主动 `leave` | 表里留着它，直到超时才发现 | 立即 `drop`，并广播成员变化 |
| `close` 事件到来 | 房间永久漏一条连接（第一节故障） | 遍历 `roomsOf(conn)` 逐个 `drop` |
| 判死阈值到点 | 同上，且客户端已收不到任何东西 | 服务端主动 `close()` 后按 `close` 走同一条清理（见第 5 章） |
| 进程重启 / 滚动发布 | 全房间「消息发不到」而页面显示已连接 | 优雅关闭：先广播再退进程；客户端必须重新 `join` |

**房间成员表不持久化，也不该持久化。** 它是「此刻谁可达」的快照，重启后清空是正确行为，客户端重连后重新订阅是协议的一部分。把它存进数据库，你会得到一个既不是事实也没人维护的僵尸表。

## 广播真正花钱的地方，不在遍历

下面这组是**本机 Node v25.4.0 跑出来的真实计时**（脚本与参数见本章末，测的是循环形状，不是任何库或产品的吞吐）：一个房间 60 条消息（10 条/秒 × 6 秒），两种写法——A 序列化一次把同一份字节发给所有人；B 在按连接的循环里各序列化一次。

```text
房内连接=50   序列化一次=0.3ms   每连接各一次=2.8ms   单条消息成本=0.05ms
房内连接=200  序列化一次=0.1ms   每连接各一次=5.1ms   单条消息成本=0.08ms
房内连接=800  序列化一次=0.5ms   每连接各一次=16.1ms  单条消息成本=0.27ms
```

读法要说诚实：**第一列全在 1 ms 以下，已经落进计时噪声区，那个「倍数」不能当结论引用**（200 连接那行的分母比 50 连接还小，就是噪声的证据）。能引用的是绝对值：每连接各序列化一次，在 800 连接时单条消息花 0.27 ms，按 10 条/秒算是**一个核的 0.27%**。

所以这一节的判断是反直觉的：**在这个量级上，序列化位置根本不是瓶颈，别拿它做优化。** 真正会炸的是你在循环里顺手加的第二件事：

```text
一条消息 800 个接收者，循环体里每连接做一次「取成员昵称/查权限/读配置」：
  每次 0.5 ms → 400 ms   每次 2 ms → 1.6 s   每次 5 ms（一次真实查询）→ 4.0 s
```

这三行不需要跑——它是乘法，而乘法的意思很直白：**广播循环是把这个成本乘以房间人数，普通请求循环只乘以一。** 后面这条决定了三条纪律：

1. 循环体外做完所有准备（成员列表、payload、权限判定），循环体里只留 `send`。
2. 需要按连接定制内容（例如每人带自己的 `cid`）时，先问这份定制值能不能提前批量算好，而不是在循环里逐个查。
3. 房间人数一涨，先复查的不是「要不要序列化一次」，而是**「这个循环体里有没有 IO」**。有 IO 的广播循环，在单实例里是延迟放大器，在多实例里还会叠上第 9 章的总线放大。

顺序性是同一件事的另一面：**广播不保证房间成员收到消息的顺序一致**，因为两条消息之间有并发写入（不同生产者、不同 worker、甚至同一个循环里的两次 `send` 被中途的异步任务打断）。要给顺序就必须有**房内单调序号**，且由服务端在入房队列处赋值——这就是第 5 章那个「游标必须是序号不能是时间戳」在房间里的落点。时间戳做序的结果是：同一房间两个人看到的消息顺序不同，而且没人报错。

## 发送成功不是送达：给每条连接一个预算

第 5 章已经给过判据「只有双向都有字节才算连接活着」。这一节给它的工程后果：**你调用 `send` 时，数据只是进了本进程里这条连接的写队列**，队列有多深、什么时候能被网络排空，`send` 不告诉你。

模拟场景：一个房间 200 条连接，其中 1 条卡在拥塞线路上，服务端每秒往房间推 10 条、每条 2 KB，不检查任何东西：

```text
第 10s 该连接缓冲=200 KB
第 30s 该连接缓冲=600 KB
第 60s 该连接缓冲=1200 KB（已超我们假设的 1 MB 上限）
超过 1 MB 的时刻=第 52s；若完全不设上限，30 分钟后=35 MB
其余 199 条正常送达；被丢掉的只有卡住那一条
```

两个结论。第一，**无界队列的代价是内存，而且是一条最差的连接替你决定涨多快**：800 条连接里只要有一条长期卡住，30 分钟 35 MB，一晚上几十条就够把一个 Node 进程推到 OOM；这也是[消息队列项目章](/message-queue-cloud/project)里那个「worker 半夜 OOM 而接口成功率 100%」的同族事故——成功率从来不看队列深度。第二，**降级是可以只作用于一条连接的**：断开那条卡住的，其余 199 条毫发无损。所以策略必须写成三选一，而不是「发出去就算成功」：

| 策略 | 怎么做 | 适合什么 | 代价 |
| --- | --- | --- | --- |
| 断开（默认推荐） | 队列深度或缓冲字节超过阈值就主动 `close()`，让客户端走重连 | 聊天、通知、协同 | 这条连接错过断开期间的消息，靠第 5 章补拉找回 |
| 丢弃 + 显式告知 | 保留最新若干条，旧消息丢掉，并发一条「你被降级了，请补拉」 | 高频状态（位置、进度条、正在输入） | 客户端必须能处理「缺一段」 |
| 无界缓冲 | 什么都不做 | **没有适合的场景** | 内存与延迟一起失控，最终由操作系统替你决定 |

阈值怎么取不要抄数：它是「你愿意为一条卡住的连接保留多少内存」乘以连接数预算。用上面那组数反推：想给 800 条连接各留 1 MB，就是 800 MB——先算这个乘法，再决定阈值，顺序不能反。而「丢弃」这一档必须配一条**告知消息**，否则你只是把「慢」换成了「静默缺一段」，那比慢更难查。

浏览器侧同样有这件事：`readyState` 和发送缓冲是连接级事实（数值语义见第 2 章），客户端在网络差时也应该有自己的队列上限，否则标签页就是手机上的那颗雷。

## 在线状态是推断出来的，而且它滞后得明明白白

判死阈值那一等式（阈值 = 保活间隔 × 允许错过的次数 = 用户最多多久看到更新 = 在线状态最多滞后多久）在第 5 章已经推过，这里只用它算在线状态这一件产品事项。800 条连接、容忍次数取 3，心跳走**应用层 JSON 消息（按每帧 64 字节估）**——注意这和第 5 章那组「协议层 ping/pong 帧约 15 字节」的估算是两种不同的帧，别混着看：

```text
间隔= 5s 判死阈值= 15s 每秒帧=320 每天心跳=1687.5 MB 最坏「已走但仍显示在线」=15s
间隔=10s 判死阈值= 30s 每秒帧=160 每天心跳= 843.8 MB 最坏=30s
间隔=15s 判死阈值= 45s 每秒帧=107 每天心跳= 562.5 MB 最坏=45s
间隔=30s 判死阈值= 90s 每秒帧= 53 每天心跳= 281.3 MB 最坏=90s
间隔=60s 判死阈值=180s 每秒帧= 27 每天心跳= 140.6 MB 最坏=180s
半开连接（每 30s 检查一次）平均误报在线=14.9s，样本 4000
```

最后一行值得停一下：**平均误报约等于检查间隔的一半**，不是「间隔的 3 倍」。因为半开连接的真实断开时刻均匀落在两个检查点之间。这和[第 1 章](/realtime/why-http-is-not-enough)那句「轮询的平均延迟是间隔的一半」是同一个算术，出现的地方比你想的多——它意味着**你写在 UI 上的「在线」，在平均意义上是 15 秒前的世界**（阈值取 90 s 时是最坏 90 s、平均约 15 s）。所以第一个产品决定不是「心跳多快」，而是「这个页面需不需要知道别人在不在线」。多数时候不需要，那就把这整套字段删掉，问题消失。

需要的时候，别把三种状态压成一个布尔：

| 状态 | 判据 | 该显示成什么 | 谁能推断错 |
| --- | --- | --- | --- |
| 有连接 | 连接表里存在 | 不显示，只用于内部路由 | 半开连接会让它为假 |
| 可送达 | 最近一个判死阈值内有入站字节 | 「在线」 | 就是上面那组滞后 |
| 在看这个房间 | 已 `join` 且未离开 | 「3 人正在看」 | 挂页面不进房的人会算进去 |
| 正在输入 | 应用层事件，几秒 TTL | 输入气泡 | 客户端不发「停止输入」就永久亮 |

**「正在输入」必须走可丢弃的通道**：它是每秒可能多次的状态变化，不是消息。做节流（首次立即发、之后合并到 1–2 秒一次）和超时自动熄灭（服务端 5 秒没收到续期就当作停），否则它会成为房间里最大的流量来源，还会留下永远亮着的输入气泡。

## 多标签页：连接数不等于人数

模拟里 500 个在线用户、每人 1–4 个标签页（分布是本章设定的抽样规则，不是真实用户统计，`rnd()` 种子 20261021，脚本见本章末）：

```text
连接数=898 用户数=500 虚高倍数=1.80×
拥有 ≥2 条连接的用户=259（51.8%）
随机断开一条连接时「不该改变在线人数」的情形=1056/2000（52.8%）
```

这组数字里真正要用的只有第一行：**按连接计数会在字面上把人数放大接近一倍。** 而第三行说明「在线人数」这个字段不能在 `close` 时直接减一——一半以上的断开是同一个用户的另一条连接还活着。做法是把 presence 聚合建立在 `uid` 上，而不是 `conn`：

```text
连接集合：conn -> uid                在线用户集合：uid -> Set<conn>
断开一条连接：从该 uid 的 Set 里移除；Set 变空 ⇒ uid 进入「待判离线」
「待判离线」再等一个判死阈值（或等该用户的其他连接仍在）⇒ 才广播离线
```

那个「再等一会儿」是必须的：不加延迟，同一用户切换标签页、手机切蜂窝、页面刷新都会造成一次离线/上线闪烁，而这正是第二个故障的现象。**离线状态要迟滞（hysteresis），上线状态不用**——因为上线有硬证据（收到字节），离线只有「没收到东西」这种弱证据，这是第 5 章四层失联在产品字段上的直接后果。

还有一件事别做错：房间成员数按连接算还是按用户算，必须**全站一致**并在 UI 文案上诚实。写「8 人在线」而实际是 8 条连接，用户看到同一时刻的头像只有 5 个，就会怀疑整个系统。

## 这张表要花多少内存，什么时候才轮到第 9 章

单实例能服务多少人，先做三个乘法（和第 5 章那组估算同一套方法，这里换成房间的形状）：

- **每连接的固定开销**：至少是 socket 对象 + 读写缓冲 + `uid` + 订阅集合 + 心跳计时器。fd 也是资源，Linux 侧的默认上限与调法见[网络与端口](/linux/networking)。
- **每张房间表**：房间数 × 成员引用数。注意私信房间是**乘出来的**——每对好友一个房间，1 万用户的关系网可以生成几十万房间号。房间表要惰性创建、空了就收回（上面 `drop()` 里那行），否则你会先把内存花在房间号上。
- **广播的瞬时开销**：payload 字节 × 房间人数 × 消息速率。这一项决定峰值时段的内存，也是上面「慢客户端」那节的预算来源。

三个比容量更能决定要不要跨实例的问题，第 9 章会完整回答，这里只给入口：单实例挂了你能接受多大范围的重连、发布时能不能接受全员重连、延迟预算是不是秒级。**在房间人数一两百、连接几千的阶段，把跨实例的复杂度引进来是净损失**——这句话就是本章和第 9 章的分工线：本章负责「一张表的正确清理与诚实降级」，第 9 章负责「两张表之间没有共识」。

## 现在就能做的实验（不需要任何中间件，本站未执行）

1. **两个标签页同房间**：本机一个进程、一个端口，浏览器开两个标签页连同一个房间。一边发消息一边看另一边的到达延迟。这是最小可用形态，也是第 9 章那个「换端口就会失败」的对照组。
2. **制造漏清理**：把 `drop()` 里「遍历 `roomsOf(conn)`」那一行注释掉，然后在 DevTools 里 `Offline` → 等超过判死阈值 → 恢复在线，反复三次。预期房间人数每次 +1 且不回落。这一步的价值是让你亲眼看见第一节那个故障，而不是读到我这句话。
3. **看队列深度**：把消息大小改成 100 KB、速率改 10 条/秒，然后让一个标签页处于 `Offline`，每 10 秒打印该连接的缓冲字节。对照上面那组 200 KB / 600 KB / 1200 KB 的斜率，判断你的阈值应该设在第几秒。
4. **presence 抖动**：同一浏览器开三个标签页进同一房间，关掉其中两个，观察「在线人数」在什么时候变化、变化几次。如果你看到先 3 → 2 → 1 且伴随一次「离线」通知，说明没做迟滞。

## 常见错误与排查

1. **现象：房间人数只涨不跌，重启进程才正常。** 原因：`close` 里没按「连接 -> 房间」那张反向表清理，或者表本来就是单向的。怎么确认：打印 `rooms` 的 size 与所有房间成员数之和，它们会一起单调增长。怎么修：双向表 + `drop()` 那四行。
2. **现象：同房间两个人看到的消息顺序不一样。** 原因：用时间戳或客户端到达时刻排序。怎么确认：让两个人同时发消息，比较各自界面里两条消息的先后。怎么修：服务端在房内给每条消息赋单调序号，客户端按序号插入。
3. **现象：房间人数把「8 条连接」显示成「8 人」，头像只有 5 个。** 原因：presence 按连接聚合。怎么确认：同一浏览器开两个标签页，看数字是否 +2。怎么修：按 `uid` 聚合，离线加迟滞窗口。
4. **现象：一个成员网络差，整个房间消息变慢。** 原因：广播循环里做了带 IO 的准备工作，或对慢连接无界缓冲导致进程 GC 压力上升。怎么确认：打印循环耗时与每条连接的缓冲深度（别只看消息是否发出）。怎么修：循环体外准备、循环体内只 `send`；给缓冲设上限并到点断开。
5. **现象：客户端显示「已连接」但收不到房间消息。** 原因：重连后是一条新连接，没有重新 `join`；服务端那张表里没有它。怎么确认：服务端按 `conn` 打印订阅集合，看这条新连接是否有房间。怎么修：把「重新订阅 + 交出游标」写进重连成功后的第一条消息，和第 5 章的补拉合成一套时序。
6. **现象：「正在输入」气泡常亮不熄。** 原因：客户端在停止输入/断线时不发结束事件，服务端也没有 TTL。怎么修：服务端每个 `uid` 挂一个 5 秒超时，续期事件到达才重置；客户端 `beforeunload` 与 `close` 前都发一次停止。
7. **现象：房间越用越大，内存不回落，即使成员都走了。** 原因：空房间对象没从 `rooms` 删除。怎么确认：打印房间数而不是成员数。怎么修：`conns.size === 0` 就删表，并给房间号做惰性创建。

<Exercise title="找出这段广播实现里的四个缺陷" difficulty="进阶">

下面是某聊天室的实现片段（`conn.uid` 在握手时已验证）。它在功能测试里能跑通，上线后出现：房间人数漂移、偶发整房卡顿、切换标签页时 presence 闪烁、两个人看到的消息顺序不一致。

```ts
const rooms = new Map<string, Set<Conn>>()      // 只有这一张表

function join(conn: Conn, roomId: string) {
  if (!rooms.has(roomId)) rooms.set(roomId, new Set())
  rooms.get(roomId)!.add(conn)
  broadcast(roomId, { t: 'presence', n: rooms.get(roomId)!.size })
}

conn.on('close', () => {
  for (const [, set] of rooms) set.delete(conn)   // 遍历所有房间
})

function broadcast(roomId: string, obj: unknown) {
  for (const c of rooms.get(roomId) ?? []) {
    c.lastSeen = Date.now()                        // 顺手记一下
    const body = JSON.stringify({ ...obj, nick: nickOf(c.uid) })
    c.send(body)
  }
}
```

逐条指出四个缺陷分别造成上面哪个现象，并说明最小修法。不许用「加个锁」「换个框架」作为答案。

<template #answer>

一、**单向表**。`close` 里遍历所有房间确实能删干净，但代价是 O(房间数)：房间几十万时这条清理本身就是卡顿来源，而且空房间对象从不回收，表只涨不消。同时 `presence` 广播用的是 `set.size`（连接数）不是人数 → 数字虚高、切标签页闪烁。修法：补 `conn -> rooms` 反向表，`drop()` 里两个方向一起清；presence 按 `uid` 聚合并给离线加迟滞窗口。

二、**循环体里有 IO 和副作用**。`nickOf(c.uid)` 如果是一次查询或缓存 miss，成本要乘以房间人数——本章那组乘法给出 800 × 5 ms = 4.0 s，这就是「偶发整房卡顿」的来源；`c.lastSeen = Date.now()` 顺手放进广播是同一类错误，而且更隐蔽：它让判死依赖「我给别人发过消息」而不是「他说过话」，一个永远收不到入站字节的连接会被判定为活着（第 5 章那条「只有双向都有字节才算」）。修法：进 `broadcast` 前一次性算好成员昵称映射，循环体只留 `send`；`lastSeen` 只在**入站**字节时更新。

三、**没有房内序号**。payload 里没有时间戳也没有序号，接收端只能按到达顺序插入，于是两个人看到的顺序不同且无人报错。修法：服务端在房内给消息赋单调 `seq`，并把它接进第 5 章的补拉游标——同一个序号，两处用途。

四、**发送没有预算**。`c.send(body)` 之后不检查缓冲深度，卡住的那条连接只进不出，本章那组斜率给出 52 秒堆过 1 MB、不设上限 30 分钟 35 MB。修法：发送前看该连接的缓冲，超阈值就 `close()` 并走同一条清理路径（正好复用缺陷一的修果），其余成员不受影响；这条决策要写成产品参数而不是「加个保护」。

四个缺陷对应四个现象：漂移与卡顿来自一、二，闪烁与虚高来自一，顺序错乱来自三，慢房间来自二、四。**没有一个是「缺少某个库」造成的**，所以「换个框架」不修任何一条——框架反而会把这些现象藏得更深（第 7 章那条透明度成本）。

</template>

</Exercise>

<Exercise title="为一个小房间产品写 presence 决定" difficulty="挑战">

你的产品是 20 人以内的工作小组协同：需要显示「谁在这个文档里」，不需要显示「谁在线」。请写一段不超过 250 字的决定，包含：① 你按连接算还是按用户算，为什么；② 判死阈值取多少、这个数从哪个产品要求反推（引用第 5 章那等式）；③ 「离开文档」和「连接断开」要不要当成同一件事；④ 心跳走协议层帧还是应用层消息，各按什么代价判断（提示：本章和 [第 5 章](/realtime/heartbeat-and-reconnect) 各估过一种帧大小）；⑤ 你这套决定里最容易被反驳的一点。

<template #answer>

评分只看六件事，不看文笔。① **按用户算**，理由要能落到「同一用户多条连接是常态」这一句（本章那组模拟给出 1.80×，50 人以内的小组仍然成立，因为比例与规模无关）；② 阈值从产品要求反推——「谁在这个文档里」最多能接受多久滞后？答 10 秒就要写出「间隔 × 容忍次数 = 10」这一等式并据此选间隔，**不许倒过来说「照惯例 30 秒」**（第 5 章原话：把这条等式交给运维拍脑袋定，就是故障二的成因）；③ **不该当成同一件事**：主动离开立即广播，断开要迟滞——否则用户刷新一次页面就闪一次离线，而文档协同场景里刷新是日常动作；这一条最能看出是否真的理解「在线是推断」；④ 20 人规模下协议层帧与应用层消息的带宽差不是决定项（把「每帧字节 × 86400 ÷ 间隔 × 连接数」写出来就看得出来都不贵），决定项是**浏览器发不出协议层 ping**（第 2 章已核实）⇒ 客户端方向只能走应用层消息，服务端方向才谈得上用控制帧；⑤ 必须写出会被反驳的一点，诚实的答案通常是**内存与清理正确性没有量化**：「谁在这个文档里」要为每个 `uid` 挂迟滞计时器、为每个文档挂一个成员集合，文档数 × 在线人数一旦上去，这些挂着的结构比心跳先成为问题（第 9 章「每连接成本重新量一次」的判据在这里同样成立）；⑥ 通篇要出现具体数字或明确推导，写「保持合理的心跳间隔」直接不及格。

一种完全成立的相反答案是：**这个场景根本不该做 presence**，只显示「最近编辑过这份文档的人」，用落库时间而不是连接推断。如果你的决定选了这条路，必须能说出你放弃了什么（实时感）以及为什么它值（少一整张会漏水的表和一个判死阈值）。
