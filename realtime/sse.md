# SSE：一条永不结束的 HTTP 响应，把断线重连白送给你

你给「部署完成通知」选了 WebSocket。上线后运维同事问的第一个问题是：为什么我的浏览器控制台每隔四十多秒就出现一次红字，然后自动恢复？第二个问题更贵：为什么本地开发一切正常，走公司网关的那批机器全部收不到？

这两个问题的答案都在同一个选择上。WebSocket 换掉了 HTTP 的语义，代价是链路上每一个设备都得配合这次协议升级，而它自己的规范里**不包含**重连——你得手写。SSE（Server-Sent Events，服务器发送事件）走的是另一条路：它就是一次普通到不能再普通的 HTTP GET，服务器把响应的头部写完、然后**永远不把响应结束**，中间一段一段往里写文本。因为它太普通了，代理不认识的新东西一个都没有；又因为它是标准里明确定义了重连语义的协议，浏览器**自带**断线重连和续传，你一行都不用写。

先把边界钉死，避免本章被误读：**SSE 是单向的**。数据只能从服务器流向浏览器，客户端想说话必须另走一次普通 HTTP 请求。它不是「简化版双向协议」，而是一种「服务器把话及时送到，上行照旧」的通信形态。

<Callout type="unverified" title="本章哪些是核实过的规范事实，哪些是要你自己造场景验证的">

线格式字段、`Content-Type: text/event-stream`、注释行用途、`retry` 单位、浏览器默认自动重连、`close()` 是唯一永久终止手段、跨源需要 `withCredentials`、不用 HTTP/2 时同一域名并发连接数上限（MDN 明确写作典型 6 且跨同一浏览器所有标签页共享）、`X-Accel-Buffering: no` 用于规避代理缓冲——这些来自 MDN 的 SSE 文档，核实时间 2026-10-20，在「官方文档与延伸阅读」里逐条对应。没有实测的部分：本环境没有服务器、没有 Nginx、没有跑过任何事件流，所有示例输出都写作「预期结果」。另外有三处边界（非 200 响应时是否停止重连、字段解析对空格的精确处理、`id` 回传的具体请求头名）我只写到「标准如此定义 + 你必须自己构造场景验证」的程度，因为本批未逐字核对 WHATWG 原文，练习 2 就是拿来做这件事的。

## 它到底是什么：一个还没写完的响应

服务器的响应长这样（下面是**逐字节写在 socket 上的内容**，不是文件）：

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: 第一条消息

: 这一行以冒号开头，是注释，客户端直接忽略

event: deploy
id: 20261020-0731
data: {"stage":"prod","ok":true}

```

协议本质一句话：**`text/event-stream` 是一个允许服务器分很多次写完的 HTTP 响应**。没有 `Upgrade`，没有 101，没有新端口，浏览器和中间设备都认为这是一个还在传输中的普通响应体（实际传输靠 chunked 编码或持续写入）。这带来 SSE 最大的优点和最大的两个坑。

优点是兼容性：现成的 HTTP 鉴权、Cookie、跨域策略、日志、监控、限流、TLS 全部照常工作，不需要为它单独改代理。第 2 章那个「Nginx 没配 Upgrade 就 1006」的经典故障，在 SSE 上根本不存在。

坑一：既然它是 HTTP 响应，**所有会干预 HTTP 响应的东西也都会干预它**——压缩层会攒够一块才发，代理会缓冲响应体，缓存层会试图复用。这三个都可能让「实时」变成「延迟几秒到几十秒」，而且不报任何错误。第五节给修法。

坑二：既然它没结束，它就一直占着一个连接。而浏览器对同一 origin 的并发连接数是有实现上限的，这也是 SSE 被用得比想象的少的主要原因。

## 线格式：四个字段，一条空行才算发消息完毕

规则简单到可以背，但每一条都有对应的翻车方式（MDN，已核实 2026-10-20）：

| 写法 | 语义 | 常见的错 |
| --- | --- | --- |
| `data: 内容` | 消息载荷。连续多行 `data:` 会被**以换行拼接**成一条消息的 data，尾部换行被去掉 | 把一段 JSON 拆成多行 `data:` 发，客户端拿到的是带换行的字符串，`JSON.parse` 当场失败 |
| `event: 名字` | 事件类型。给了这个名字，浏览器派发**同名事件**；不给则派发 `message` | 服务端写了 `event: deploy`，客户端只挂了 `onmessage`，永远收不到 |
| `id: 值` | 设置「最后事件 ID」，**重连时用于续传** | 忘了发 id，重连后要么漏消息要么全量重放 |
| `retry: 3000` | 把重连等待时间设为 3000 毫秒（必须是整数，非整数被忽略） | 以为它限定的是超时，其实只是「等多久再试」 |
| `: 任意文本` | 注释，客户端忽略。规范文档明确说它可以用来**保持连接活着** | 不知道能这么用，于是靠发假消息保活，污染业务流 |
| （空行） | **一条消息到此结束并派发** | 每写完 `data:` 忘记补空行，客户端永远不触发事件 |

服务端最小实现，不依赖任何框架（Node 原生 HTTP，Fastify/Express 里同理，关键是**别调用结束响应的 API**）：

```js
// 预期行为：浏览器 console 里依次打出 "hello" 和结构化事件；本批未在本机运行
export function sseHandler(req, res) {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    Connection: 'keep-alive',
    'X-Accel-Buffering': 'no',      // 直接对 Nginx 一类代理关缓冲，见第五节
  });
  res.write('retry: 2000\n\n');     // 告诉浏览器：断了 2 秒后自己回来

  let n = 0;
  const send = (event, data) => {
    n += 1;
    res.write(`id: ${n}\n`);
    if (event) res.write(`event: ${event}\n`);
    res.write(`data: ${JSON.stringify(data)}\n\n`);   // 一条 data + 空行
  };

  send('hello', { at: Date.now() });
  const keepAlive = setInterval(() => res.write(': ping\n\n'), 20000);
  const tick = setInterval(() => send('metric', { online: 12 + n }), 5000);

  req.on('close', () => {            // 客户端离开必须清理，否则定时器永远在跑
    clearInterval(keepAlive);
    clearInterval(tick);
  });
}
```

`req.on('close')` 这一句是 SSE 服务端最容易漏的资源漏洞：一个挂起的响应 + 一个每 5 秒写一次的定时器，客户端早就关了页面，服务端还往里写。写几十行代码时它是内存泄漏，写几年代码时它是「为什么凌晨有几十个僵尸连接在给不存在的用户发消息」。

## EventSource：三行代码，附带一套你不该白丢的重连

浏览器侧 API 小得可怜：

```js
const es = new EventSource('/sse/notifications');   // 默认同源；跨源要传 { withCredentials: true }

es.onopen = () => console.log('事件流已建立');
es.onmessage = (e) => console.log('无名字消息:', e.data);
es.addEventListener('metric', (e) => render(JSON.parse(e.data)));
es.onerror = (err) => console.warn('出错或正在重连', err);
```

`e.lastEventId`、`e.origin`、`readyState`（连接中 / 开放 / 已关闭）是事件对象与实例上另外三个有用的属性。真正值钱的、也是本章最想让你记住的是这一条：**连接一旦中断，浏览器会自动重连，并且把「最后收到的 id」带回给服务器**（MDN 已核实「默认自动重连」，以及 `id` 字段的作用就是设置重连时用的最后事件 ID；回传所用的请求头名 `Last-Event-ID` 属 HTML 标准定义，本批未逐字核对该页，你在服务端打一行日志就能亲眼看到它）。

对比一下就明白这值多少代码。WebSocket 那边你要自己写：重连触发条件、指数退避与抖动、重连后往哪个游标补拉、补拉与实时流的去重、以及「服务端主动结束」和「异常断开」的区分。SSE 把第一件和第二件的一半送给了你，而服务器只需要做一件事：**把 `id` 发出去，并在重连请求里读回它，从那之后开始补发。**

```js
// 服务端：用 Last-Event-ID 做续传，避免重连后漏消息或全量重放
export function resumable(req, res) {
  openStreamHeaders(res);
  const after = Number(req.headers['last-event-id'] ?? -1);   // 浏览器重连时会带
  for (const item of db.messagesAfter(after)) {              // 先补历史
    writeEvent(res, { id: item.seq, event: 'msg', data: item });
  }
  subscribeLive(req.user.id, (item) =>
    writeEvent(res, { id: item.seq, event: 'msg', data: item }));
}
```

这条自动重连同时是个陷阱，因为它**不带业务判断**。两种典型误伤：

- 任务已经结束了，你只是 `res.end()`，浏览器仍然会重连，服务器于是又开一个流、又发一遍完整历史。修法是在结束前发一条具名事件（例如 `event: done`）让客户端主动 `es.close()`——`close()` 是唯一能永久终止重连的手段（已核实）。也可以让服务端返回非 200 状态（比如 410 Gone）来表达「这个流不再存在」，但**非 200 时浏览器究竟是停止重连还是继续退避重试，属于需要自己构造场景确认的边界**，别把它当已验证事实写进关键路径。
- AI 生成这类「重放等于重新计费」的场景。SSE 的自动重连会替你重新发起同一个请求，如果你把生成请求做成了可重放的，用户断一次网就多烧一次 token。第 4 章的选型会正面处理这个矛盾。

`onerror` 的语义要读准：它同时覆盖「出错了」和「正在重连中」，因此**在 error 里直接判定连接已死是错的**；要看 `readyState` 是否为 CLOSED 才能区分「彻底失败」与「暂时不通」。这也是很多人写 SSE 时把正常的网络抖动当成致命错误、手动关掉连接的原因。

## 单向就是单向：把方向矩阵画对

| 场景需要的方向 | SSE | WebSocket |
| --- | --- | --- |
| 服务器 → 浏览器推送消息 | ✅ 本职 | ✅ |
| 浏览器 → 服务器发命令 | 走普通 POST，与流无关 | ✅ 同一条连接内 |
| 两端同时对发低延迟小包 | ❌ 上行要新起请求 | ✅ |
| 服务端需要知道「谁还活着」 | ⚠️ 只能靠连接是否还在，或另做心跳上报 | ✅ |
| 二进制大块下传 | ⚠️ 线格式是文本，二进制要 Base64，膨胀约 4/3 | ✅ 原生 binary 帧 |

这张表里 SSE 那一行的 ⚠️ 值得多说一句：事件流本体是 UTF-8 文本，所以传图片、传 protobuf 必须编码，白白多 33% 流量与一次 CPU 编解码；而 WebSocket 有原生 binary 帧。反过来说，如果你的载荷本来就是 JSON，SSE 这个「文本协议」的特征毫无成本，还顺带让你在 `curl -N` 里能直接肉眼读流——这点对调试友好度的贡献非常大，别低估。

「上行用 POST」不是妥协，而是把职责分清楚：写操作本来就该走有状态码、有幂等键、有重试语义的 HTTP（[后端 HTTP 与 REST 语义](/backend/http-and-rest) 里幂等键与条件请求那一套在 SSE 架构里**完全适用**，在 WebSocket 架构里则要你自己重建）。很多团队上了 WebSocket 之后才发现，他们把「发消息」这件事从有明确失败反馈的 HTTP 世界，搬进了一个只能靠超时猜测的世界。

## 连接额度、代理缓冲、假死：三个来自部署形态的问题

**连接数上限。** MDN 把「不用 HTTP/2 时受同一域名最大并发连接数限制（典型 6）」直接列为 SSE 的限制，并且说明这个额度是**按浏览器统计、跨同一域名的所有标签页共享**（已核实 2026-10-20）。后果非常具体：用户开了三个标签页，每页一条 SSE，你在 HTTP/1.1 上就吃掉了三个格子，剩下三个还要承担页面里所有普通请求和图片。缓解顺序：先上 HTTP/2（一条连接多路复用，这个问题基本消失）；再考虑把多个逻辑频道合并成一条流（服务端按用户过滤后下发，客户端自己分发）；实在不行才考虑 WebSocket 单连接承载多主题。这是第 4 章选型的一个硬指标，别到上线后才发现。

**代理与压缩缓冲。** 现象是「消息全都能到，但一批一批地到，或者晚 3–10 秒」，而且**没有任何错误**。责任方通常是三层之一：Nginx 一类代理的响应缓冲、gzip 中间层（压缩器会攒块）、应用框架的响应缓冲。修法从便宜的到彻底的：① 服务端加 `X-Accel-Buffering: no` 响应头（MDN 的 SSE 示例里就是这个头，已核实），它对 Nginx 生效且不需要改服务器配置；② 在该 location 上 `proxy_buffering off;`（配置写法与逐行解释见第 8 章）；③ 对 `text/event-stream` 关闭压缩，或确认你的压缩层支持逐块刷新。确认方法只有一条：**对比直连上游端口与经过代理的到达时间**，同一条消息，两边各测一次。这一步没做，你会把部署问题当成协议问题排查一整天。

**空闲假死。** 和第 1 章长轮询、第 2 章 WebSocket 是同一种病：长时间没有任何字节，NAT 或 LB 会单方面丢掉映射。SSE 的解法最优雅——**定期写一行注释**：`: ping\n\n`。它以冒号开头，客户端解析时直接忽略，不产生事件、不进业务代码，但链路上有了字节。间隔取链路上最短那个空闲超时的 60–70%，20 秒左右是常见起点（上面示例就是这么写的）。

## 什么时候该用 SSE，什么时候不该

该用，当以下条件同时成立：**下行是主要需求**；载荷本来就是文本/JSON；你希望少写重连与续传代码；链路上有一堆你改不动的代理；订阅关系是「服务器有话说」。

具体到本课程的场景：

- **通知铃铛、订单状态、部署进度**——教科书级的 SSE。单向、低频、需要可靠续传、量小。
- **AI 流式输出**——大模型逐 token 返回本身就是 SSE 格式，服务端把上游的流转发给浏览器即可，用 `fetch` + `ReadableStream` 自己解析（因为要 POST 请求体、要带 API Key 或 header、还要能被中断——`EventSource` 不能 POST、不能自定义请求头，这是它的构造签名决定的硬限制，已核实其 API 只有 URL 与 `withCredentials`）。厂商的具体事件格式变化快，本批不写厂商参数，以 [AI 应用开发](/ai-apps/) 领域与本领域第 10 章标注了核实日期的内容为准。
- **只读仪表盘、行情、日志跟随（类似 `tail -f` 的 Web 版）**——SSE 便宜且能被普通 HTTP 监控体系看见。

不该用：**上行频繁且低延迟**（打字即发、光标同步、协作编辑）；需要**双向小包对发**（这是 WebSocket 的领地，第 2 章的四件自建事项逃不掉）；载荷以**二进制大块**为主（Base64 的 4/3 膨胀与编解码 CPU 不划算）；需要**每个客户端都有大量独立订阅主题且服务端要按主题反向控制**（技术上能做，但你会开始在 HTTP 响应上重建一个协议，那不如直接用 WebSocket）。

## 常见错误与排查

1. **现象：本地 `curl -N` 一切正常，浏览器经过域名访问就延迟数秒、成批到达。** 原因：代理或压缩层缓冲。怎么确认：分别用「直连上游端口」与「经过完整链路」测同一条消息的到达时间；再检查该路径是否被 gzip（响应头里的 `Content-Encoding`）。怎么修：`X-Accel-Buffering: no` + 该 location `proxy_buffering off` + 对事件流关闭压缩。
2. **现象：服务端明明在写，客户端一个事件都不触发。** 原因：消息结尾没有那个**空行**（`\n\n`），浏览器认为这条消息还没写完。怎么确认：`curl -N` 看原始字节，检查是不是只写了一个 `\n`。怎么修：统一封装一个写事件的函数，末尾固定补空行（上面示例里的 `data: ...\n\n`）。
3. **现象：`onmessage` 收不到具名事件。** 原因：服务端写了 `event: deploy`，客户端只挂了 `onmessage`——那只会收到**没有 event 字段**的消息（派发为 `message`）。怎么确认：看原始流里有没有 `event:` 行。怎么修：`addEventListener('deploy', …)`，或者干脆统一用无名消息 + JSON 里带 `type` 字段自己分发（更省心的约定）。
4. **现象：`JSON.parse` 随机失败，字符串里有换行。** 原因：把一段 JSON 用多行 `data:` 发出，浏览器按规范把它们以换行拼接了。怎么确认：`console.log(JSON.stringify(e.data))` 看里面是否嵌着 `\n`。怎么修：一条消息一行 `data:`；确实要多行载荷就改用多个事件分开发，或在外层加 base64。
5. **现象：页面关掉很久，服务器还在往里写，连接数只增不减。** 原因：没监听客户端断开、定时器没清理；或者更狠的情况——客户端在 `onerror` 里手动重连，同时又存在浏览器自动重连，两条流并存。怎么确认：服务端给每条流打 id 并记录 `close` 事件是否触发。怎么修：`req.on('close')` 清理一切；**永远不要自己再写一套重连**，除非你有明确理由（比如要在重连之间做退避上限控制），否则就是双通道。
6. **现象：断线重连后消息漏了一段，或者历史被整个重放了一遍。** 原因：没发 `id`，或发了 `id` 但服务端不读 `Last-Event-ID`。怎么确认：在流里看有没有 `id:` 行，同时把服务端接到请求的头部打日志。怎么修：id 用单调递增序号（不是时间戳，时钟会跳），并重连时从 `Last-Event-ID` 之后补发。
7. **现象：用户开了第二个标签页，整站变慢。** 原因：HTTP/1.1 下每个 SSE 各占一格并发连接额度，且这个额度跨标签页共享。怎么确认：Network 面板里看普通请求是否长时间停在 pending / queued。怎么修：上 HTTP/2；或把多频道合并成一条流。

```text
data: delta

```

1. 浏览器总共会派发几次事件？分别是什么事件名、`e.data` 的准确内容是什么？
2. `id: 42` 这条之后连接断开，重连请求里会发生什么？
3. `retry: 1500` 会被派发成一个事件吗？它改了客户端的什么状态？

<template #answer>

共 3 次派发。① 第一个空行结束的第一条消息：事件名 `message`（因为没有 `event:` 行），`e.data === "alpha"`。② 第二块有两行 `data:`，按规范以换行拼接成**一条**消息，所以 `e.data === "beta\ngamma"`，事件名仍是 `message`——这是唯一一次「两行 data 不等于两条消息」的陷阱来源。③ 第三块 `event: metric` + `id: 42` + `data: {"v":1}`，派发为一个名为 `metric` 的具名事件，`e.data === '{"v":1}'`（字符串，要自己 `JSON.parse`），并且 `e.lastEventId === "42"`。开头的 `: ready` 是注释，被忽略、不派发；两个 `data:` 之间和结尾的那些**空行**只作为消息结束标记，本身不派发任何事件。

第 2 问：这条被记录为「最后事件 ID」，浏览器自动重连时会在请求头里带回它（`Last-Event-ID: 42`），服务端据此从 42 之后继续发——这就是 SSE 送你的续传，前提是服务端真的去读它。第 3 问：`retry` 不产生任何事件，它把重连等待时间改成 1500 毫秒（整数毫秒；非整数被忽略）。注意它只影响等待时长，不影响消息可靠性，也**不是**超时设置。

</template>

</Exercise>

<Exercise title="练习 2 · 三种写坏的服务端，说出各自的现象并自己验证" difficulty="进阶">

同一个客户端：

```js
const es = new EventSource('/feed');
es.onmessage = (e) => console.log('msg', e.data);
es.onerror = () => console.log('error', es.readyState);
```

服务端有三个错误版本（只列出与正确版本的差异）：

```text
A  响应头写成 Content-Type: application/json，其余不变
B  Content-Type 正确，但每个事件只写 data: xxx\n，没有结尾空行
C  Content-Type 正确、格式正确，但框架在响应上套了 gzip，且代理层开了响应缓冲
```

1. A、B、C 各会出现什么现象？哪一类会看到 `error`，哪一类只是「收不到」？
2. 分别用什么一条命令就能看见真相？（要求：不修改服务端代码就能定位）
3. 写出你验证「非 200 时浏览器是否继续重连」的最小实验步骤。为什么这件事必须由你自己验证，而不是由教程告诉你？

<template #answer>

A：内容类型不对，`EventSource` 会判定这不是事件流——浏览器给出 error，`readyState` 变成 CLOSED（不同浏览器的报错文案不一样，常见是 `The buffer passed to dataChannel are exhausted` 之类无意义信息，或以 `TypeError`/网络错误形式出现；具体文案本批未验证，不要背）。现象是「立刻失败、没有一条消息」，而且是**不重连**的失败，因为「这不是 event-stream」属于流本身不合法，不是链路抖动。B：格式合法但每条消息永远没有结束标记，浏览器认为消息还在写，于是不派发任何东西——现象是「连接正常、没有任何事件、也没有错误」。这是最难受的一类：不报错，只是沉默。C：内容最终会到，但延迟数秒且成批出现；如果 gzip 缓冲到一定块大小才刷新，短消息可能长时间看不到。它同样不报错，因为你没法从客户端区分「服务器还没发」和「中间有人攒着」。

第 2 问：`curl -N -sD - http://127.0.0.1:PORT/feed` 不加服务端改动就能看到全部真相——A 会显示头里的 Content-Type 与原文；B 会看到只有单换行、没有空行分隔；C 直连上游时逐条即时到达，而经过域名（带代理）时成批到达，两者一对比就锁定了责任层。补一个 `--compressed` 或看响应头有没有 `Content-Encoding: gzip` 就能确认压缩参与。第 3 问：让服务端对同一 URL 在第二次请求返回 410（或 500），客户端只观察两件事——`onerror` 触发后 `readyState` 是否为 CLOSED，以及服务端访问日志里有没有出现第二次重连请求；把间隔和次数记下来即可。必须由你验证的原因是：这条边界依赖浏览器实现与版本，规范文字与各家行为并不完全一致，而且**它直接决定你的流结束时会不会形成重连风暴**。任何教程（包括本章）给出的「应该是停止重试」都不该被你写进关键路径，除非你在自己的浏览器上看见过它失败。

</template>

</Exercise>

<Exercise title="练习 3 · 给 AI 回答做流式：为什么这里 SSE 好用但不能直连" difficulty="挑战">

需求：用户在页面输入问题，你的服务调用上游大模型，模型以流式（逐 token，上游本身就是 SSE 格式）返回，页面要边生成边显示，并且有「停止生成」按钮。约束：API Key 绝不能进浏览器；请求参数在 POST 体里；一次生成可能持续 30 秒以上。

1. 为什么这一步不能用 `EventSource` 直接连上游？给出至少两条由 API 形状决定的理由。
2. 画出正确的链路，指出哪一段用 SSE、哪一段用别的，并说明服务端如何做到「边收边转发」而不是等全文。
3. 浏览器到你这段的自动重连，在这个业务里会造成什么具体损失？给出你的处理方式。
4. 「停止生成」要怎样传播到上游？如果只关浏览器到服务端这一段会发生什么。

<template #answer>

1. ① `EventSource` 只能发 GET，而生成请求的参数必须放在请求体里；② 它的构造签名只接受 URL 与 `{ withCredentials: true }`（已核实），**不能添加自定义请求头**，所以带不了 `Authorization`——而 API Key 放 URL 就等于把凭据写进访问日志与代理日志，这条直接否决。再加一条业务理由：`EventSource` 的重连语义是「重新发起同一个请求」，对生成任务不成立。
2. 链路：浏览器 →（你的域名，SSE 下行）→ 你的服务端 →（HTTPS，流式读取上游响应体）→ 上游厂商。服务端把上游的字节流按行切、解析出每个 `data:` 块，**每解析出一条就立刻写一条事件给浏览器**，绝不做「等上游结束再一起返回」；否则流式就没有意义了。用 `fetch` 拿上游响应后用 `res.body.getReader()` 循环读，配合 `TextDecoder` 的 `stream: true`（否则多字节字符会被切断），自己维护一个「未完成的行」缓冲区处理跨 chunk 的半行。上游厂商事件格式以各家文档为准（本批未核实具体厂商，字段与结束标记会变化）。浏览器这一端也用 `fetch` + ReadableStream 解析，而不是 `EventSource`——理由同上，你要 POST、要带 header、要能中断。
3. 自动重连等于**把同一个生成请求再发一遍**：多烧一次 token、页面出现两段互相冲突的答案、并可能触发上游限流。处理办法是别让这条通道使用 `EventSource` 的自动重连（改用 fetch 流式就没有这个语义）；如果你确实用了 EventSource 承载「已生成内容回放」，那么服务端必须为每次生成分配 `id`，重连时按 `Last-Event-ID` **回放已生成的部分而不是重新生成**，并给生成任务一个可判定的结束事件让客户端 `close()`。这里最重要的判断是：SSE 的免费重连只在「重放无害」的场景里才是福利。
4. 必须做取消传播：浏览器用 `AbortController.abort()` 断掉 fetch，服务端在 `req.on('close')`（或读流的错误分支）里立刻 abort 它到上游的那条请求。只关下游的话，服务端会继续把一次完整生成跑完——你照常付费，而且上游连接与内存被无谓占住；这类「用户看不见但账单看得见」的泄漏是流式服务最常见的成本事故。顺带一条：这类场景不需要 WebSocket，因为方向仍然是「上行一次 POST、下行一串结果」，是 SSE 的形状。

</template>

</Exercise>
