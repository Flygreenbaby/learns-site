# 为什么请求-响应不够：每一轮对话都必须由浏览器先开口

你的聊天页面有一条消息在服务器上等了两秒多才显示出来。同一时刻，服务器日志里躺着 333 条/秒的请求，URL 全部一模一样，路径后面挂着同一个 `?since=1739500000`，其中绝大多数响应是空的 `[]`。你的 CPU 没有在做业务，它在做的是「回答没有人问第二遍的问题」。

这个现象的根源不在代码写得差，而在 HTTP 的语义本身：**一次通信由客户端发起，服务器把这一份响应写完，这一轮就结束了**。服务器不能说「我还有一句要补给你」，因为它手上没有一个还能开口的通道——连接可能还开着（HTTP/1.1 的 keep-alive 就是干这个的），但那条连接上已经没有属于这次请求的响应边界了。要写第二份数据，就必须等到客户端再问一次。

于是所有「实时」方案都在解决同一个问题：**怎样让服务器有机会主动开口**。可用的路子只有两类——要么让客户端问得足够快、足够便宜，把「主动」伪装成「频繁被动」（轮询家族，本章）；要么改掉这一问一答的边界，让一次请求对应一条永不结束、或者干脆脱离 HTTP 语义的响应（SSE 与 WebSocket，本领域第 2、3 章）。选错的代价很实在：给纯单向的通知流上 WebSocket 是过度设计，给聊天用 5 秒轮询是延迟与成本双输。

<Callout type="unverified" title="本章的数字有两类来源，都不叫实测">

本章出现的请求量、并发连接数、字节数、延迟值都是**按公式推算或按典型构造样本算出来的**，用来教你怎么算账，不是任何真实压测的结果。当前工作环境是 Windows + Node，没有 Linux 服务器、Nginx、真实公网流量，也没有跑过任何轮询压测，所以**没有任何一节可以标为实测**。协议事实来自标准与官方文档：握手与帧的语义来自 RFC 6455，SSE 的格式与限制来自 MDN，两处核实时间均为 2026-10-20，写在「官方文档与延伸阅读」里并逐条标注用途。凡是浏览器实现值（后台标签页的定时器节流下限、同一域名的并发连接数上限），我会明说这是实现选择而非规范要求，动手前自己复核。

## keep-alive 复用的是字节通道，不是「开口的机会」

最容易搞错的一点，是把「连接复用」当成「会话保持」。

HTTP/1.1 默认 `Connection: keep-alive`：一次 TCP 连接上可以连续跑很多个请求-响应，省掉重新握手与 TLS 协商的成本。但它复用的是**传输层的字节通道**，请求的语义边界一个字节都没变——服务器把响应结束标记写完（`Content-Length` 到达、或者 chunked 终止块发出）之后，这条连接就回到「等待客户端发起下一个请求」的状态。此时服务器手上握着一条活的 TCP 连接，却没有任何 HTTP 语法允许它往上面写东西。硬写只有一种后果：把下一个响应的字节流污染成乱码。

HTTP/2 走得更远一点：一条连接上跑多个并发流（stream），每个流对应一个请求-响应。这解决了队头阻塞与连接数问题，但**流的发起权仍然在客户端**，服务器依然不能凭空开一条流去推消息。（HTTP/2 曾经提供过 Server Push，但那是对静态资源的预取机制，不是消息通道，且主流浏览器后来移除了它——具体版本与时间本批未核实，需要时查 caniuse.com 与 MDN 该页当前状态。）

| 机制 | 复用了什么 | 没有解决什么 |
| --- | --- | --- |
| HTTP/1.1 keep-alive | TCP 与 TLS 的建立成本 | 响应写完就失去开口权；并发请求仍受连接数限制 |
| HTTP/2 多路复用 | 连接数与队头阻塞 | 流仍由客户端发起；服务器无主动写入语法 |
| HTTP 缓存与条件请求 | 重复请求的带宽与算力 | 只是让「问一次」更便宜，问的频率还是要客户端决定 |

结论要记得很硬：**把 HTTP 调到最快，也调不出「服务器主动」这件事**。想要服务器开口，只能改变通信形态，而不是优化通信参数。这一节和[后端 HTTP 与 REST 语义](/backend/http-and-rest) 里的「超时链条：keep-alive 上谁先闭嘴」是同一条链路的两侧——那一章讲的是连接什么时候被谁关掉，本章讲的是连接开着的时候谁有权说话。

## 先把「实时」变成数字，否则无法判断需要哪种方案

「实时」不是一个技术目标，是一个延迟预算。把需求写成毫秒，选型才会从争论变成算术。

按经验档位划分（这是需求量级，不是规范值）：

| 需求 | 可接受的端到端延迟 | 典型例子 |
| --- | --- | --- |
| 输入中状态、光标位置 | 100–500 ms | 「对方正在输入…」，协作文档的光标 |
| 聊天消息到达 | 500 ms – 2 s | 单聊、群聊、客服会话 |
| 业务通知 | 2 – 10 s | 订单状态变更、部署完成、评论提醒 |
| 状态面板 | 10 s – 1 min | 后台任务进度、库存数量、在线设备列表 |
| 报表与统计 | 分钟级及以上 | 日报表、聚合指标 |

关键的一条算术：**轮询方案的平均感知延迟是间隔的一半，而不是间隔本身**。消息在两次轮询之间的任意时刻到达服务器，客户端平均要等 `间隔 / 2` 才发现它，最坏等一个完整间隔。所以 3 秒轮询的均延迟约 1.5 秒 + 一次请求的往返与处理时间，它对「通知」够用，对「输入中」根本不可能达标（要压到 250 ms 均延迟需要 500 ms 间隔，那就是每用户每秒两次请求）。

反向也要判断：**很多需求并不需要实时**。用户点「保存」之后想知道成没成，这就是一次普通请求-响应，加长连接只是把复杂度白白引进来。判断标准只有一条：**这条信息的变化是不是由服务器或其他用户触发、而客户端不可能知道它何时发生**。不是，就别上长连接。

## 短轮询：写对它只有三个要点，代价却是全部

短轮询（short polling）就是客户端按固定间隔发请求问「有新的吗」。实现简单到不需要框架，但能写对的人不多，因为三件必须处理的事都不在 happy path 上。

```js
// 最小可用但已考虑真实约束的轮询骨架
let cursor = 0;              // 上次拉到的位置，去重与续传全靠它
let timer = null;
let inflight = false;        // 上一请求没回来就绝不再发

async function pollOnce() {
  if (inflight || document.visibilityState !== 'visible') return;
  inflight = true;
  const t0 = Date.now();
  try {
    const res = await fetch(`/api/messages?since=${cursor}`, {
      headers: { 'If-None-Match': etag || '' },   // 空响应尽量变 304
      signal: AbortSignal.timeout(8000),          // 必须有超时，否则挂死
    });
    if (res.status === 304) return;               // 服务器明确说「没变化」
    const json = await res.json();
    for (const m of json.items) render(m);        // 渲染要按 id 去重
    cursor = json.nextCursor;
    etag = res.headers.get('ETag') || '';
  } catch (err) {
    failure += 1;                                 // 失败要退避，不要原频率硬冲
  } finally {
    inflight = false;
    schedule();
  }
}

function schedule() {
  const backoff = Math.min(30000, base * 2 ** failure);   // 指数退避
  timer = setTimeout(pollOnce, backoff);   // 用 setTimeout 递归，不用 setInterval
}
```

三个要点的理由：`inflight` 保护是因为 `setInterval` 不管上一次有没有回来，网络一慢就会并发发请求，而并发请求的响应**到达顺序不保证**——带着旧 `cursor` 的响应后到，会把已经渲染过的消息再渲染一遍，或者把 `cursor` 往回退造成重复。`visibilityState` 保护是因为用户切到后台的标签页仍在打你的服务器，这是轮询成本失控的头号原因。退避保护是因为服务出问题时，所有客户端会以原频率继续轰炸，把自己的故障放大成雪崩。

现在算账。假设 1,000 个在线用户、5 秒间隔：

- 请求量：`1000 / 5 = 200 req/s`，一天 `200 × 86400 ≈ 1,730 万`次。
- 空响应率：如果消息真正产生的速率是每分钟 30 条，那么有效数据只占 `30 / (200 × 60) ≈ 0.25%` 的请求，其余是纯开销。
- 字节账：一个 GET 请求头 + 一个 JSON 数组为空的响应头， uncompressed 典型各在数百字节量级；按每次往返 700 B 估，`200 × 700 B ≈ 140 KB/s`，一天约 11 GB，几乎全是在传输「没有」这个词。这里的单请求字节数是**按典型头尺寸的估算，未在本机测量**，你要用真实响应头自己替换：`curl -sD - -o /dev/null` 看你的一条到底多少字节。

真正的代价不在带宽，在**每次请求都要重过的整条链**：TLS 已复用可以省掉握手，但鉴权中间件要跑、路由要匹配、数据库查询要打（哪怕 `[]` 就返回）、日志要写、监控指标要计。你的 QPS 上限被一个和业务无关的东西占掉了。移动端还有一层隐性成本：蜂窝网络下每次发请求都要唤醒射频，后台轮询是耗电大户，这也是为什么平台会把后台定时器节流到很粗的粒度。

## 长轮询：把「没有」这个答案延迟到有新东西为止

长轮询（long polling）改了一个字：服务器**不立刻回答「没有」**。客户端问「有新消息吗」，服务器把请求挂起，一直到有数据、或者到达超时上限才返回；客户端拿到响应后**立刻**再发起下一轮。

```text
客户端                                   服务器
  |---- GET /wait?since=42 -------------->|  没有数据，挂起（不写响应）
  |                                       |
  |            …… 挂起 20 秒 ……            |
  |                                       |<-- 新用户发来一条消息
  |<--- 200 消息体（事件到达）-------------|  立刻兑现挂起的请求
  |---- GET /wait?since=43 -------------->|  又开始下一轮挂起
  |                                       |
  |            …… 挂起到 30 秒超时 ……      |
  |<--- 200 空数组（超时返回）-------------|  客户端马上重连
```

它买到了什么：延迟从「平均半个间隔」降到「事件到达即返回 + 一次往返」，也就是几十毫秒级；同时把无效请求从每秒几百次降到「每个挂起窗口一次」，请求量与在线人数成正比而与消息频率无关。

它留下了四个问题，而且每一个都会在你上线后真实咬你一次：

1. **每个挂起请求都要占住一个服务端执行位。** Node 的事件驱动模型在这里便宜得很：挂起一个请求只是往 Map 里存一个 callback，不占线程，一进程挂几万个连接主要花的是内存。但换成「一个请求一个进程/线程」的同步模型（传统 PHP、某些 Servlet 容器配置），1,000 个在线就意味 1,000 个活着的工作进程——内存直接爆，而这和代码质量无关，是运行模型的性质。**这是为什么同一个长轮询功能在不同技术栈上会得出完全不同的结论。**
2. **每个事件仍然付一次完整的 HTTP 头成本。** 挂起省掉了重复的「没有」，但每一次真实推送依然要走一个完整请求-响应：头尺寸与短轮询同级，只是次数少得多。
3. **超时的所有权不在你手里。** 挂起窗口必须小于链路上**任何一个**中间设备的空闲超时——浏览器、Nginx 的 `proxy_read_timeout`、云厂商 LB 的空闲超时、运营商 NAT。谁先闭嘴决定了你的连接什么时候被悄悄切断。这条判断链在[后端 HTTP 与 REST 语义](/backend/http-and-rest) 与 [Nginx](/linux/nginx) 里各自有细节；实操纪律只有一条：**服务端挂起窗口设成 25–30 秒，并在响应里带上明确的超时语义**，让客户端把它当成正常事件立刻重连，而不是当错误。
4. **通道数量吃浏览器额度。** 浏览器对同一 origin 的 HTTP/1.1 并发连接数有实现上限（主流浏览器典型是 6，MDN 在 SSE 页面把它作为「SSE 的主要限制」明确写出，2026-10-20 核实）。这个数字是浏览器实现选择，不是 HTTP 规范要求。一个长轮询通道就占掉一格额度；开两个标签页各挂一个通道，剩下能并发下载资源的格子就更少了。这也是长轮询在真实页面上越用越别扭的结构性原因。

| 维度 | 短轮询 | 长轮询 |
| --- | --- | --- |
| 平均延迟 | 间隔 / 2 + 往返 | 一次往返（事件驱动） |
| 请求量 | 与在线人数 × 频率成正比 | 与在线人数 × 挂起窗口倒数成正比 |
| 服务端占用 | 每个请求瞬时占用 | 每个用户长期占用一个执行位与一格连接额度 |
| 中间设备风险 | 低（每个请求都很短） | 高（受最短的那个空闲超时支配） |
| 断线语义 | 下一次问自然补上 | 必须自己处理「挂起被打断后如何续传」 |
| 上行（客户端发消息） | 普通 POST | 普通 POST（仍然没有反向通道） |

最后那一行常被忽略：长轮询解决的是**下行**，客户端要发消息照样得另发一个 POST。它不是双向通道，只是把单向做得更及时。

## 有些需求其实只需要把轮询做便宜

选型不是「越实时越高级」。下面这些场景，正确答案就是把短轮询做得更便宜，而不是引入长连接：

- **后台任务进度条**：任务本身要跑 90 秒，2 秒间隔查询的相对误差可以忽略；用 WebSocket 反而要处理「任务在服务端重启后进度归零」的连接恢复问题。
- **库存、汇率、排行榜**：数据本身分钟级更新，人眼也读不了那么快。用[HTTP 缓存](/frontend-engineering/http-caching) 加 `max-age=30` 让 CDN 或浏览器直接替你挡掉绝大部分请求，比任何推送方案都便宜。
- **低频个人通知**：用户一天上线两次，每次 30 秒。轮询的总成本几乎为零，而长连接要额外解决鉴权过期、多标签页、假死重连三件事——复杂度是你一个人的时候最贵的东西。
- **需要被 SEO 或调试工具看见的数据流**：轮询就是普通请求，能缓存、能重放、能在 Network 面板一眼看懂；长连接的可观测性要自己搭。

判断口诀：**先问「延迟降低到多少会让用户感知变好」，再问「为此我要多付几条连接」。** 当你的答案里说不出一个具体毫秒数，通常说明普通请求就够了。前端侧这三档 API 的具体调用形态（`fetch` 定时器、`EventSource`、`WebSocket` 对象）在[JavaScript 的网络与存储](/javascript/network-and-storage) 里已经有一节对照，本章刻意不重复——本章只负责把「为什么必须换形态」这件事讲透，具体协议在第 2、3 章拆开。

## 常见错误与排查

1. **现象：明明加了页面隐藏判断，服务器日志里后台标签页还在打。** 原因：判断写在回调里但间隔由 `setInterval` 驱动，切回前台时积压的一批 tick 同时触发；或者节流逻辑只判断了 `document.hidden` 却没在 `visibilitychange` 时重置定时器。怎么确认：控制台里看 `setInterval` 的调用栈与实际发起时间戳，服务器侧按 `session` 或 IP 聚合请求间隔。怎么修：改成 `setTimeout` 递归 + 在 `visibilitychange` 里 `clearTimeout` 并立即补一次请求（回到前台要马上对齐状态）。
2. **现象：轮询一切正常，但带宽与 CPU 都高。** 原因：每次返回完整列表，没有条件请求，也没有分页游标。怎么确认：抓一条响应看状态码是 200 还是 304、body 里有多少条是客户端已经有的。怎么修：加 `ETag`/`If-None-Match` 让「无变化」走 304 空体，同时用 `since` 游标只返回增量。
3. **现象：偶发同一消息渲染两次，或消息顺序乱了。** 原因：请求重叠。上一请求还没回，下一次已经带着同一个 `cursor` 发出去，两个响应乱序到达。怎么确认：在 Network 面板看同一 URL 是否有时间上重叠的两个 pending 请求。怎么修：`inflight` 闸门 + 客户端按消息 id 去重（幂等渲染），并把 `cursor` 更新改成「只前进不后退」。
4. **现象：长轮询上线后，隔几分钟必然出现一次「消息延迟十几秒」。** 原因：链路上某个中间设备的空闲超时比你挂起的时间短，它悄悄把连接切了，你的客户端直到下一次心跳或超时才发现。怎么确认：对比服务端挂起时长分布与 Nginx `proxy_read_timeout`、LB 空闲超时；被切的连接在服务端日志里表现为「客户端提前断开」而不是「正常返回」。怎么修：把挂起窗口压到最短那个超时的 60–70%，并在客户端设置略大的请求超时，让「超时」成为一条正常分支而非错误分支。
5. **现象：服务一重启，所有客户端同时重连，数据库被瞬时并发打挂。** 原因：所有客户端用完全相同的重连间隔，故障恢复时刻被同步成了一次尖峰。怎么确认：重连时刻的直方图是不是一个尖锐的柱。怎么修：指数退避之上加随机抖动（jitter），把重连摊开。
6. **现象：加了 WebSocket 之后延迟没降。** 原因：换掉了「拉新消息」，但页面的其他逻辑仍在按老周期发 HTTP 请求；或者推送已到位，慢的是渲染与数据库查询。怎么确认：Network 面板里过滤你的轮询 URL，看是否还有周期请求；同时看服务端事件生成到写出之间的耗时。怎么修：把「传输」与「处理」分开量，别把优化错了对象的结果算在协议头上。

4. 这一改动值不值得，取决于哪个业务问题——你需要先向提需求的人确认什么？

1. 现状：`800 / 4 = 200 req/s`，一天 `200 × 86400 = 17,280,000` 次请求；带宽按 2.5 KB 往返算是 `200 × 2.5 KB = 500 KB/s`，一天约 41 GB。改成 10 秒：`800 / 10 = 80 req/s`，一天约 691 万次，请求量降到 40%，带宽约 16.6 GB/天。
2. 每分钟 20 条事件，现状每分钟请求 `800 × 15 = 12,000` 次，所以带数据的响应占比 `20 / 12000 ≈ 0.17%`。改成 10 秒后是 `20 / (800 × 6) ≈ 0.42%`——**注意分母也变了，但两档都在千分之几的量级**：这说明轮询的本质浪费不会因为把间隔调大就消失，只会让每个请求「更可能问到东西」而已。
3. 平均延迟 `间隔 / 2`：现状约 2 秒，改后约 5 秒（最坏各为一个完整间隔：4 秒与 10 秒）。这一行算术就是本章「均延迟是间隔的一半」那条。
4. 取决于**通知是否可以接受 10 秒级延迟**。如果这是「订单已完成」的提醒，5–10 秒完全够用，那就该省这 60% 请求；如果是「对方正在输入」，改成 10 秒是把产品做坏。所以要先确认的是「这条信息的延迟预算」，不是「能不能更快」。附带要点：既然 99.8% 的响应是空的，比调间隔更有效的是让空响应变 304（几乎零 body），以及考虑把间隔改成事件驱动的长轮询或推送。

</template>

</Exercise>

<Exercise title="练习 2 · 故意把轮询写坏，然后解释你看到的三个现象" difficulty="进阶">

在本地任意静态页面里做这个实验（不需要服务器；把 fetch 的目标换成一个会慢的 URL，或者用一段 `await new Promise(r => setTimeout(r, 3000))` 模拟慢响应）：

```js
setInterval(() => {
  console.log('tick', Date.now());
  fetch('/api/slow').then(r => r.json()).then(render);
}, 1000);
```

然后：① 连续放 30 秒不动；② 把标签页切到后台 2 分钟再切回来；③ 让 `/api/slow` 真的需要 3 秒才回。

你观察到：`tick` 每秒打印一次，但请求数量在 ③ 里迅速堆积；② 切回前台后有一批日志几乎同时打印；③ 的响应到达顺序和发出顺序不一致，页面出现重复条目。

1. 为什么 ③ 会「堆积」而不是「变慢」？`setInterval` 的调度语义是什么？
2. ② 里那批同时打印的 tick 说明浏览器对后台标签页做了什么？这是规范要求还是实现选择？
3. 顺序错乱与重复条目分别对应哪一层的问题，各怎么修？
4. 为什么这段代码换成 `setTimeout` 递归就能同时解决 ② 和 ③ 的一半问题？

<template #answer>

1. `setInterval` 只负责「每 1000 ms 触发一次回调」，它不知道也不关心上一次回调里发出的请求是否已经结束。回调里发起的是异步请求，于是 3 秒响应意味着任意时刻有约 3 个请求在途，请求数按 `响应耗时 / 间隔` 放大——这是「堆积」而不是「变慢」的准确描述：并发数在涨，不是节奏在慢。
2. 说明浏览器在后台标签页**节流**了定时器：切回前台时积压的 tick 被快速补齐，日志挤在一起。这是**浏览器实现选择，不是任何规范要求的行为**，具体阈值（历史上桌面 Chrome 对后台定时器有 1 秒下限、并对长期后台页面进一步收紧）会随版本变化，本批未在本机验证，所以不要把某个具体毫秒数当成事实写进代码；能确定的是「不能假设后台仍按你的间隔运行」。
3. 顺序错乱是**传输层**问题：解决它是让请求串行化（在途闸门），或在响应里带序号、客户端只接受比当前游标更大的值。重复条目是**应用层**问题：解决它是幂等渲染，即按消息 id 去重（`Map` 存已见 id），并保证游标「只前进不后退」。把这两件事混为一谈是常见错误——串行化并不能消除重复（网络重试照样会带来同一条消息）。
4. `setTimeout` 递归是「完成之后再排下一次」，天然保证同一时刻至多一个在途请求，直接消掉堆积与大部分乱序。但它对 ② 只解决一半：定时器仍会被后台节流，所以还需要显式监听 `visibilitychange`，在回到前台时立刻补一次请求把状态对齐。「节流」这件事你控制不了，「回来之后马上校正」是你必须自己做的。

</template>

</Exercise>

<Exercise title="练习 3 · 谁先闭嘴：长轮询的半开竞态" difficulty="挑战">

你实现了长轮询，参数如下：

```text
你的 Node 服务：每个 /wait 请求挂起 60 秒后返回空数组
Nginx：proxy_read_timeout 60s
云 LB：空闲超时 350 秒（未改动）
浏览器 fetch：AbortSignal.timeout(70000)
```

上线后现象：大约每分钟有一次「消息明明已经发了，客户端十几秒后才看到」，而且**没有**任何请求失败记录，服务端日志显示这些挂起的请求「正常返回」。

1. 这条链路上谁最可能先动手？为什么服务端看起来一切正常？
2. 把四个数字改成一组自洽的值，并说明选取理由（给出「服务端挂起窗口」与「代理读超时」之间应有的关系）。
3. 除了调数字，协议上还有一种做法能让这种「静默重连」不再造成延迟。是什么？
4. 如果这条链路以后换成 WebSocket，同样的空闲超时会带来什么新故障？为什么这一类问题不属于协议本身，而属于部署形态？

<template #answer>

1. 最可能动手的是 **Nginx：`proxy_read_timeout 60s` 与你的挂起窗口 60s 相等**，两者赛跑，代理经常略早一点点切断上游。它对客户端回的是「响应结束」，对上游是超时断开，于是**上游视角里请求走完了自己的一生（没有异常），客户端视角里连接被正常关闭后立刻重连**——没有任何一方报错，但事件窗口被拉长约一次「重连 + 重新挂起」，这就是十几秒延迟的来源。这类问题的特征正是「全链路 200，只有慢」。
2. 让**每一层的空闲超时都严格大于上一层的挂起窗口**，并把挂起窗口设成最短那个约束的安全余量。例：服务端挂起 25 秒（`res.setTimeout` / 自己 `setTimeout` 返回空数组）；Nginx `proxy_read_timeout 40s`（必须大于 25，留出处理与网络时间）；LB 350 秒保持不动；浏览器 fetch 超时 40 秒（略大于服务端挂起 + 往返，收到空数组就立即发起下一轮，这是正常分支）。核心关系：**代理超时 > 服务端挂起窗口 > 单次往返时间**，永远不要让代理与你的挂起窗口相等。
3. 让服务端**主动、周期性地把挂起窗口结束掉**（心跳式空响应），并且结束点由服务端决定而不是被中间设备决定；同时给每条消息一个单调递增 id，客户端重连时带上游标补拉。这样即便连接被打断，「有没有丢」也是可判定、可恢复的，而不是靠运气。这正是 SSE 用注释行保活 + `id`/`Last-Event-ID` 续传的思路（本领域第 3 章），以及 WebSocket 需要应用层心跳的原因（第 2、5 章）。
4. WebSocket 空闲时链路上完全没有任何字节（除非你发 ping/pong），**超过 LB 空闲超时的静默期会让中间设备单方面丢弃映射**，而两端都还以为连接活着——于是出现「发送成功但对方永远收不到」的假死，比长轮询更糟，因为长轮询至少每次都在产生新请求。这一类故障的根因是 NAT/LB/代理的**空闲连接回收策略**，与 WebSocket 规范本身无关：同一个协议换一种部署形态就没事，所以它属于部署形态问题，也是本领域第 8 章要专门处理的部分。

</template>

</Exercise>
